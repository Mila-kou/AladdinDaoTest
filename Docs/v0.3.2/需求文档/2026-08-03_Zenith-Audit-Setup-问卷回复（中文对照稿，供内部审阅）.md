## 2. 你们集成的协议里，管理员（或其他角色）能设置的值有没有限制？包括数组长度限制？

**外部协议集成**：三个可插拔的 oracle provider，统一走 `IOracleProvider` 接口——

- **Chainlink Data Streams**（低延迟、链下签名报告 + 链上 DON 签名验证）——大多数市场的主价格源。
- **Chainlink 经典链上价格源**（`AggregatorV2V3Interface`）——次要/兜底价格，以及 sequencer 在线状态检测。
- **Pyth**（链上 pull 模式）——既用作对主价格源的偏离度校验参考，也可以单独作为一个 provider 选项。

**管理员可设置的值及其边界**：

- **喂价心跳/过期时间**（`PRICE_FEED_HEARTBEAT_DURATION`）：校验逻辑是 `block.timestamp - lastUpdateTimestamp`，但**我们没有对这个值本身设任何链上的最小/最大值限制**——理论上管理员可以把它设得很大，从而悄悄允许过期价格生效。生产环境目标值：WNT/USDC 喂价 3600 秒；测试默认值是 60 秒。
- **价格/乘数精度**（`priceFeedMultiplierKey`/`dataStreamMultiplierKey`）：只校验非零，没有上界，也没有跟喂价源实际精度做交叉核对。
- **主价格年龄上限**（`MAX_ORACLE_PRICE_AGE`，生产环境 60 秒）和**多币种价格提交的时间戳跨度上限**（`MAX_ORACLE_TIMESTAMP_RANGE`，60 秒）——都是管理员可配置，都有 revert 校验。
- **参考价偏离度上限**（`MAX_ORACLE_REF_PRICE_DEVIATION_FACTOR`，生产环境 2%）——限制主价格相对 Pyth 参考价能偏离多少，超了直接 revert。
- **缓存的"recorded"价格最大存活时间**（`MAX_RECORDED_PRICE_AGE`，生产环境 24 小时）——这个为什么比看起来重要，见第 4 题。
- **Data Stream 点差折减系数**：硬性封顶在 ≤100%（`Precision.FLOAT_PRECISION`），是唯一一个真正有链上硬上限的值。

**数组长度**：整个协议里我们**几乎不用固定数值上限**作为防御手段。唯一的例外是订单执行回调数据（`FX100Keys.MAX_DATA_LENGTH`，管理员可配置，在 `BaseHandler.validateDataListLength` 里校验）。其他地方——外部调用中转（`ExternalHandler.makeExternalCalls`）、多币种 oracle 价格提交数组、以及所有批量领取类函数（抵押品、推荐返佣、UI 手续费）——都只校验"**并行数组长度相等**"，没有上界；实际的天花板是区块 gas 上限。我们的 relay/免 gas 批量下单路径额外把总 calldata 大小封顶在 50,000 字节，这间接限制了数组大小，但本身不是一个长度校验。我们欢迎你们的团队专门压测这个模式（通过大数组做 gas 消耗攻击，来自一个有权限但被攻破或配置错误的调用方），因为我们没有把"数组长度封顶"当作主要防御层。

## 3. 协议里有没有涉及链下机制（比如 keeper 机器人、套利机器人等）？我们默认这些机制不会作恶、延迟或掉线，除非你们另有说明。

有——好几个 keeper 角色，各自把守一个特定的有权限入口：

| Keeper | 入口函数 | 掉线/延迟会怎样 |
|---|---|---|
| **Order keeper** | `OrderHandler.executeOrder` | 订单会一直挂着没执行；用户在过期窗口后可以自行撤单。市价单超时会自动退款；限价/触发单会"冻结"等待重新执行。**优雅降级——不存在无需权限的兜底执行者。** |
| **Frozen-order keeper** | 解冻/重试因滑点/输出金额校验失败的订单 | 冻结的订单会一直冻结（执行费已经花掉）直到这个 keeper 出手。 |
| **Liquidation keeper** | `LiquidationHandler.executeLiquidation` | **请不要假设这个总是及时运行。** 如果延迟，资不抵债的仓位会持续累积——这是真实的风险累积型失效模式，不是优雅降级。 |
| **ADL keeper** | 轮询全局净兑付率 + `AdlHandler.executeAdl`（滞后区间，参数可配置——目前暂定超过 75% 开启 ADL，回落到 ≤50% 关闭；另有独立的提款闸门暂定在超过 65% 时拦截 LP 提款） | **同样请不要假设这个总在运行。** 如果在风险事件期间掉线，协议没有自动去杠杆的兜底机制。**注：以上百分比阈值是暂定的可配置参数，不是写死的合约常量，主网上线前可能还会调整。** |
| **Recorded-price 刷新器** | `AdlHandler.refreshLatestRecordedPrices`——**完全无需权限**，没有任何角色校验 | 见第 4 题——这个一旦停摆，波及范围会异常大。 |
| **Relay / "Express"（免 gas）执行方** | 链下 relayer 提交用户 EIP-712 签名的意图，垫付执行费，收取 relay 手续费 | **完全无需权限——任何人都可以充当 relayer/执行方，除了用户自己的签名验证之外没有任何链上角色限制。** 如果这个链下服务掉线，只有免 gas/子账户的体验会降级——用户可以退回普通（非免 gas）方式下单。优雅降级。 |

**Oracle 价格提交本身是混合模式**：底层价格数据（Chainlink Data Stream 报告、Pyth 更新）自带各自网络的密码学签名，链上验证——这部分在"任何持有有效签名报告的人都能提交"这个意义上是无需信任/无需权限的。但是**携带这个价格数组的交易本身**，要看它挂在哪个入口上——挂在 order/liquidation/ADL keeper 的入口上就受相应角色权限约束，**唯一的例外**是 recorded-price 刷新器，对所有人开放。

**请不要假设我们的 keeper 完全可靠**——尤其是 liquidation keeper 和 ADL keeper 是风险关键型的，我们希望你们的审查能明确考虑这两个 keeper 延迟/掉线时会发生什么，而不只是理想路径。

## 4. 即使打破某条不变量/性质造成的影响很小或未知，你们仍然希望它成立的性质有哪些？

1. **四方核心资金持有者之间的零和不变量。** 每一次改变状态的操作，都应满足 `Δ(trader 余额) + Δ(LP vault 资产) + Δ(position vault) + Δ(fee receiver)= 0`——系统里任何地方都不应该凭空产生或销毁价值。这是我们测试覆盖最充分的一条不变量（专门的 E2E 账本测试套件在每个场景后都会断言这条），也是我们最希望被重点标注的一条——哪怕只是某个边缘场景下能被打破。
2. **动态点差绝不能让清算/ADL 以优于 oracle 价的价格成交。** 不管普通交易的定价公式怎么演化（参见 v0.3.2 scope 文档里的负点差新功能），强制平仓永远不能拿到"返利"。
3. **全局净兑付率是唯一的风控闸门**，计算公式是 `Σ_市场 [max(0, 多头浮盈) + max(0, 空头浮盈)] / 资金池USD价值`，跨所有共享同一个 LP vault 的市场累加。这里隐含了一个假设——如果这个假设被打破我们希望被标注出来——即配置在某个 LP vault 下的所有市场，实际上真的都共享那一个 vault；新市场上架流程理应保持这一点，但这只是计算公式里内嵌的假设，并没有一个独立的校验去强制它。
4. **ADL 执行必须严格、单调地降低全局净兑付率，否则 revert。** 我们知道除了这条单调性校验之外，没有独立的"单次 ADL 力度上限"——最初设想的"防止过度降杠杆"保护并没有作为一条独立的不变量落地——我们想知道这一点是否比我们预想的更重要。
5. **收紧风险的操作要求新鲜价格；放松风险的操作可以容忍过期价格。** 这个不对称设计（LP 提款闸门和关闭 ADL 都要求新鲜的 oracle 数据；开启 ADL 则不要求）是有意为之，不是疏漏——但如果你们认为这个不对称本身可能被利用，我们想听听。
6. **资金费结算路由是刻意设计成不对称的**：当交易者净应付资金费时，资金会路由进可领取的协议手续费账本，而不是直接付给 LP；反过来的方向（LP 直接付给交易者）我们认为目前是一条不可达的防御性分支，不是真实生效的路径——如果它其实是可达的，我们希望被标注出来。

**补充说明**：本仓库/本次提交里包含的测试套件（`test/external`、`test/fixtures`、`test/integration`、`test/vault`，共 19 个文件）是基于场景的，**不包含** Foundry 风格的 `invariant_*`/`StdInvariant` 模糊测试框架。

## 5. 请说明你们做的任何设计选择。

**先说几条比较基础、会影响后面很多设计的原则性事实：**

- **整个协议里唯一的抵押品/结算资产是 USDC。** 每一笔 LP 存款、每个仓位的抵押品、每一次盈亏结算，全部以 USDC 计价并支付——指数资产（BTC、ETH 等）只是现金结算型合成永续合约的价格参考，不存在指数资产本身的实物交割，协议里任何地方都不支持多抵押品资产。`MarketFactory.createMarket` 在创建市场时会直接校验抵押品资产必须等于 vault 唯一持有的资产。有一个细节值得说明：USDC 自身的价格仍然是走 oracle 喂价的（跟其他资产用同一套 Chainlink/Pyth provider，另外有一个"稳定币区间"钳制机制把价格拉向参考价），并不是写死等于 `$1`——如果 USDC 出现严重脱锚，会跟其他任何资产一样，直接传导进系统里每一笔资金池/仓位的 USD 估值。
- **每个市场都共享同一个 LP vault，这是架构上强制的，不只是一个假设。** `MarketFactory.vault` 在合约构造时设置一次，且是 `immutable`——同一个 factory 部署出来的所有市场，都共享那一个 vault。这正是第 4.3 条全局净兑付率风控模型能成立的关键前提——如果你们发现有任何路径可能让某个市场的账务偏离这个前提，请一定标注出来。
- **每个（账户, 市场, 方向）组合只对应一个净仓位——没有对冲模式/多仓位模型。** 仓位的 key 是 `keccak256(account, marketIndex, isLong)`——是确定性的，没有 nonce/计数器。在同一方向重新开仓，永远是合并进已有仓位而不是新建一个；一个用户在同一个市场最多同时持有一个多头仓位和一个空头仓位，不会有多个。

FX100 是 **GMX v2（Synthetics）** 的一个 fork，从 GMX 按市场隔离资金池的模型，改成了共享单一抵押品资产（USDC）的模型。相对上游 GMX v2 最主要的几处偏离，按偏离程度从大到小排列：

- **全局净兑付率风控模型**取代了 GMX 按市场的储备金因子模型——这是上面"共享 vault"这条原则的直接后果：一旦偿付能力要跨所有共享同一份抵押品的市场来判断，单个市场自己的储备金因子就没有意义了。完整推导见上面第 4.3 条（如果对你们审查有帮助，我们也很乐意直接跟你们团队走一遍完整推导过程）。
- **普通自愿交易的动态点差可以为负**（v0.3.2 新功能），参考了 Avantis 那种"帮助市场恢复平衡的订单给予激励"的模式，同时刻意保持清算/ADL 执行价继续钉在旧的 floor-at-0（绝不优于 oracle 价）行为上。如果对你们的审查有帮助，完整的设计理由和促成这个决定的风险分析我们可以直接分享。
- **三方手续费分账，复用了一个已经被审计过的 `RevenuePool`/`ProtocolTreasury` 分账器**（见第 6 题），而不是 GMX 那种更简单的单一 fee receiver 模型——协议手续费拆分给协议金库、类似保险基金的"燃烧"分配、以及拿走剩余部分的 LP vault。
- **子账户槽位固定为每账户 4 个**（v0.3.2 新功能，见 v0.3.2 scope 文档 §0.4）——刻意用"固定、gas 可预测、易于推理"的上限，替换掉原来无上限的地址集合设计。
- **推荐返佣模块的代码在仓库里，但本次发布刻意保持"未激活"状态**（推荐等级未配置），等待重新设计——具体依赖的操作性约束见 audit scope 文档 §3.1。
- **为交易不活跃的市场做的 recorded-price 缓存机制**（`Oracle.latestRecordedPrices`）——用一个"影响面是全局的"存活性风险（见第 3/4 题）换取了"能对那些光靠自然交易活动不足以让自己价格缓存保持新鲜的市场，也计算出一个全局风险比率"这个能力。

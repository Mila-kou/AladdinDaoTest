## 概述
### 目的
现有 `test/e2e/LpLifecycle.t.sol` 只做方向性断言（`assertGt`/`assertLt`）。本套件验证 LP 存取款全生命周期的**精确 USDC 金额**，包括：
- LP 存入收到的 shares 数量（精确）
- 领取时的 USDC 金额（与 NAV 挂钩，精确推导）
- 交易活动对 LP 领取金额的精确影响
- Epoch 锁定机制的正确执行
- 多 LP 按比例承担盈亏的精确分配
### 设计原则
1. **NAV 不变的场景**：精确 `assertEq`（shares 公式往返无损）
2. **NAV 变化的场景**：解析推导期望值后 `assertApproxEqAbs(±1e6)`（`1e6` = 1 USDC unit，来自整数除法舍入）
3. 所有场景同时验证四方资金守恒（`_assertZeroSum`）
### 核心机制说明
LP 存入时收到 shares，shares 代表对池子的所有权比例。**从存入到 claim 之间一直参与池子盈亏**——如果池子盈利（trader 亏损/资金费流入），NAV 升高，claim 金额增加；如果池子亏损（trader 盈利），NAV 降低，claim 金额减少。`claimWithdrawRequest` 使用**领取时**的 NAV，不是发起提款时的 NAV，这是正确的设计行为。

## 第一节：LpSnapshot 结构 + E2ELedger 扩展
在 `test/e2e/accounting/fixtures/E2ELedger.t.sol` 末尾追加。
### 新增结构体
```solidity
struct LpSnapshot {
    uint256 lpUsdc;       // usdc.balanceOf(lp)
    uint256 lpShares;     // lpVault.balanceOf(lp)
    uint256 totalSupply;  // lpVault.totalSupply()
    uint256 nav;          // lpVault.nav()
    uint256 totalAssets;  // lpVault.totalAssets()
}
```
### 新增常量
```solidity
uint256 internal constant LP_ASSET_SCALAR = 1e12; // USDC 6 decimals → 18 decimals
uint256 internal constant LP_PRECISION    = 1e18; // VaultBase.PRECISION
```
### 新增函数
```solidity
function _lpSnapshot(address lp) internal view returns (LpSnapshot memory s) {
    s.lpUsdc      = usdc.balanceOf(lp);
    s.lpShares    = lpVault.balanceOf(lp);
    s.totalSupply = lpVault.totalSupply();
    s.nav         = lpVault.nav();
    s.totalAssets = lpVault.totalAssets();
}

function _assertLpReturn(
    uint256 actualAssets,
    uint256 expAssets,
    uint256 tolerance,
    string memory label
) internal {
    assertApproxEqAbs(int256(actualAssets), int256(expAssets), tolerance, label);
}
```

## 第二节：计算公式速查
所有期望值必须在测试注释中写出推导过程。
```javascript
assetScalar = 1e12  (USDC 6 decimals, scaled to 18)
PRECISION   = 1e18  (VaultBase constant)

# NAV 计算
nav = totalAssets × assetScalar × PRECISION / totalSupply
    = totalAssets × 1e30 / totalSupply

# 存入：获得的 shares
shares_received = assets_deposited × assetScalar × PRECISION / nav_at_deposit
               = assets_deposited × 1e30 / nav_at_deposit

# 领取：获得的 USDC（用 claim 时的 NAV）
assets_claimed = shares_locked × nav_at_claim / PRECISION / assetScalar
              = shares_locked × nav_at_claim / 1e30

# LP 在池中的占比
lp_fraction = lp_shares / totalSupply

# 交易对 LP 的精确影响
lp_impact = trader_pnl × lp_fraction

# NAV 更新后的期望 LP 领取金额
nav_new = (totalAssets - trader_pnl) × 1e30 / totalSupply
assets_claimed = shares_locked × nav_new / 1e30
```
**初始状态（fixture 默认）：**
```javascript
POOL_SEED = 1_000_000e6 USDC → 1e12 raw units
admin shares = 1e12 × 1e30 / 1e18 = 1e24
LP 存入 500_000e6 → shares = 5e11 × 1e30 / 1e18 = 5e23
LP fraction = 5e23 / (1e24 + 5e23) = 1/3
```

### L1：存入→无交易→epoch→领取（NAV 不变，精确 assertEq）
**目的**：基线验证 shares 公式和 claim 公式的精确往返。
```javascript
前置计算：
  LP 存入 500_000e6 USDC
  shares = 500_000e6 × 1e30 / 1e18 = 5e23

无交易 → NAV 保持 1e18 不变

领取期望：
  assets = 5e23 × 1e18 / 1e30 = 5e11 = 500_000e6 USDC  ← 精确取回

关键断言：
  assertEq(sharesReceived, 5e23)
  assertEq(claimed, LP_DEPOSIT)          // 精确，tolerance = 0
  assertEq(s1.lpUsdc - s0.lpUsdc, LP_DEPOSIT)
  assertEq(s1.lpShares, 0)
  _assertZeroSum(s0_ledger, s1_ledger)   // 四方守恒
```
---
### L2：存入→trader 获利→epoch→领取（NAV 降低）
**目的**：验证 LP 承担 trader 盈利的精确金额。
```javascript
trader 开多 100k USD（2x 杠杆），price 2000→3000 (+50%)，平仓

sizeInTokens = 100_000e30 / 2_000e12 = 50e18
trader_pnl   = 50e18 × (3000e12 - 2000e12) / 1e30 / 1e24 = 50_000e6 = 50k USDC

pool 缩水：1_500_000e6 → 1_450_000e6
NAV_new = 1_450_000e6 × 1e30 / 1_500_000e24
        = 1.45/1.5 × 1e18 = 0.96667e18

LP_LOSS = 50_000e6 × (1/3) ≈ 16_667e6

期望领取：500_000e6 - 16_667e6 = 483_333e6
assertApproxEqAbs(claimed, 483_333e6, 1e6)
assertLt(claimed, LP_DEPOSIT)
_assertZeroSum(...)
```
---
### L3：存入→trader 亏损→epoch→领取（NAV 升高）
**目的**：验证 LP 从 trader 亏损中获益的精确金额。
```javascript
trader 开多 100k USD，price 2000→1500 (-25%)，平仓

sizeInTokens = 50e18
trader_loss  = 50e18 × (1500e12 - 2000e12) / 1e30 / 1e24 = -25_000e6

pool 增加：1_500_000e6 → 1_525_000e6
NAV_new = 1_525_000e6 × 1e30 / 1.5e24 = 1.01667e18

LP_GAIN = 25_000e6 × (1/3) ≈ 8_333e6

期望领取 ≈ 500_000e6 + 8_333e6 = 508_333e6

assertApproxEqAbs(claimed, 508_333e6, 1e6)
assertGt(claimed, LP_DEPOSIT)
_assertZeroSum(...)
```
---
### L4：存入→资金费积累→epoch→领取（NAV 升高）
**目的**：验证 LP 从资金费收入中获益的精确金额。
```javascript
setUp: 不调用 _setZeroFunding()（保留真实资金费率）

trader 开多 100k USD → warp 7天（flat price）→ 关仓

fundingFee = sizeInTokens × Δ(negFundingPerSize) / FLOAT_PRECISION / USDC_PRICE

LP 收到的资金费 = fundingFee × LP_FRACTION

期望领取 ≈ LP_DEPOSIT + fundingFee × (1/3)

assertApproxEqAbs(claimed, expected, 1e6)
assertGt(claimed, LP_DEPOSIT)
```
---
### L5：两个 LP 先后存入→trader 获利→各自领取
**目的**：验证多 LP 按比例承担损失，且比例计算精确。
```javascript
LP_A 存入 500k → shares_A = 5e23
LP_B 存入 500k → shares_B = 5e23

after LP_A: totalAssets = 1.5M, totalSupply = 1.5e24
after LP_B: totalAssets = 2M,   totalSupply = 2e24
LP_A 占 25%；LP_B 占 25%；admin 占 50%

trader 获利 50k → 池子缩水到 1.95M
LP_A_loss = 50k × 25% = 12_500e6
LP_B_loss = 50k × 25% = 12_500e6

期望 LP_A 领取 ≈ 487_500e6
期望 LP_B 领取 ≈ 487_500e6

assertApproxEqAbs(claimed_A, claimed_B, 1e6)
assertApproxEqAbs(claimed_A, 487_500e6, 1e6)
_assertZeroSum(across both claims)
```
---
### L6：initiate 和 claim 之间 NAV 变化（用 claim 时 NAV）
**目的**：核心行为验证——shares 锁定期间仍参与池子盈亏。
```javascript
步骤：
  1. LP 存入 500k（NAV = 1e18），shares = 5e23
  2. 发起提款请求（shares 锁定在 vault，record unlockAt）
  3. trader 获利 50k → NAV 降到 0.96667e18
  4. warp EPOCH_0_END → LP 领取

预期：
  claimed = 5e23 × 0.96667e18 / 1e30 ≈ 483_333e6

关键断言：
  assertApproxEqAbs(claimed, 483_333e6, 1e6)
  assertLt(claimed, LP_DEPOSIT)
  assertNe(nav_at_initiate, nav_at_claim)
```
---
### L7：epoch lock 机制验证
**目的**：验证 epoch 到期前不能 claim，到期后可以 claim。
```javascript
步骤：
  1. LP 存入 500k，发起提款请求
  2. epoch 未结束时尝试 claim → 应 revert
  3. warp EPOCH_0_END → 再次 claim → 成功
  4. 验证领取金额精确（NAV 不变 → assertEq(claimed, LP_DEPOSIT)）

关键断言：
  vm.expectRevert();
  lpVault.claimWithdrawRequest(0, lp);

  vm.warp(EPOCH_0_END);
  uint256 claimed = lpVault.claimWithdrawRequest(0, lp);
  assertEq(claimed, LP_DEPOSIT)
```

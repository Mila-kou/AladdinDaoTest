> **这是前端交易面板"显示值是否正确"的唯一参考文档。** 提 bug 时直接看本文档对应条目。 - **前端开发**看 §2 公式（每个显示值应该怎么算）+ §3 已知问题（哪里错了、该怎么改）。 - **测试**看 §0 速查表（核对了哪些字段）+ §4 怎么自动跑。 - **活文档**：核对项不断增加 → 本文档持续补充；发现新错误 → 记到 §3（编号 `FE-{n}`）。 可执行真值：``test/frontend-e2e/formulas.ts``（纯函数，已对线上逐 wei 验证）。 自动核对脚本：``scripts/verify/scrapePanel.ts``（① 层，CDP 读面板）。 三层模型与运行：``FRONTEND_E2E_PLAN.md`` · ``FRONTEND_E2E_SETUP.md``。
记号：`WEI=1e18`（价差/价格定点）、`FLOAT=1e30`（因子/USD）、抵押币(USDC)价 `colPrice≈1e24`（$1）、

## 2. 字段公式（真值规范）
### 2.1 Total Spread = Constant + Depth + Skew（clamp ≥0）`dynamicSpread()`
| UI 行 | 公式 | 备注 |
|---|---|---|
| Constant Spread | `constantPriceSpread`（直接读市场参数） | 固定，如 0.01% |
| Depth Spread | `max( exp(orderSize×param/depth) − 1 , orderSize/depth ) / 100`，封顶 `MAX_PRICE_IMPACT_SPREAD` | `exp` 用 Balancer LogExpMath 逐位移植；`depth`= 开方向用 ask、平方向用 bid。小单≈0 |
| Skew Impact | `skewFactor × skewRef / 1e18`，改善失衡取负，clamp[min,max] | `skewRef=( |
| **Total** | `Constant + Depth + Skew`（≤0 → 0） | 等于面板 "Price Impact" 行 |
`orderSize`/`tokenDelta`（喂 skew 的预备值，按模式分支）：
- 开仓 USD 模式：`tokenDelta = 多 sizeUsd/index.max / 空 ⌈sizeUsd/index.min⌉`，`orderSize=sizeUsd`
- 开仓 token 模式：`tokenDelta = sizeInTokens`，`orderSize = sizeInTokens×index`
- 平仓：`tokenDelta = sizeInTokens`（事件值），`orderSize = sizeUsd`
> **OI=0 开第一笔的 skew**：skewBefore=0、skewAfter=100% → skewRef=50% → skew=factor×50%。 MSOL 实例：`2.5e15×0.5 = 1.25e15 = 0.125%`（与前端、链上逐 wei 一致 ✅）。
### 2.2 Est. execution price `executionPrice()`
```plain text
useMax = (开仓&多) 或 (平仓&空)
execPrice = useMax ? ⌈ index.max × (1 + total) / 1e18 ⌉
                   :   index.min × (1 − total) / 1e18
```
MSOL：`200e12 × (1+0.00135) = 200.27e12 = $200.27` ✅（链上 `200270050479803` 逐 wei）。
> **核对口径（2026-06-22 修正）**：开仓 exec 用的是 ticker 的 **bid/ask 一侧**（开多 ask、开空 bid，源 `selectedMarketPricesAtom`），而面板上唯一的 "Oracle Price" 行是 Positions 面板的 **mid**（`pricesBySymbolMapAtom`，同源 `tickersDataAtom` 但取 mid）。两者在 bid≠ask 时本就不等，故 `scrapePanel` 的检查①已从「严格等式 `exec==mid×(1±spread)`」改为**同侧判定**：开多 `exec≥oracle`、开空 `exec≤oracle`（与平仓相反，见 §2.10）；bit-exact 的 exec 由 watch ③ 核。
### 2.3 Max acceptable（incl. slippage）`acceptablePrice()`
```plain text
Max acceptable = execPrice × (1 ± slippage)   （多 +、空 −）
```
MSOL：`200.27 × (1+0.5%) = $201.25` ✅。这是"所见即所发"——必须等于提交订单里的 `acceptablePrice`（②）。
### 2.4 Fee / Fee 费率 `feeAmount()`
```plain text
Fee = applyFactor(orderValueUsd, positionFeeFactor) / colPrice.min
    = orderValueUsd × positionFeeFactor   （USDC ≈ $1）
```
MSOL：`0.02% × $200 = $0.04`。Fee 行标签里显示的费率（`Fee(0.0200%)`）必须 == 链上 `positionFeeFactor`。
### 2.5 Collateral / Pay amount
```plain text
Collateral（进仓位的保证金）= Order Value / leverage
Pay amount = Collateral + Fee
```
MSOL 2x：`Collateral=$100`，`Pay=$100+$0.04=$100.04`。
### 2.6 Order Value / Leverage
```plain text
Order Value = sizeInTokens × oracle           （名义仓位 USD）
Leverage    = Order Value / Collateral          （真实下单杠杆，= 面板显示的 "2x"）
```
> ⚠️ 不要从杠杆滑杆的 `aria-valuenow` 读杠杆——`getByRole('slider',{name:'Leverage'})` 命中的是**持仓面板的 Adjust-Margin 滑杆**（valuemax=400），不是下单表单。用 `Order Value / Collateral`。
### 2.7 Liquidation Price `liquidationPrice()` — 见 §3 **FE-1**（当前前端算错）
最终公式：
```plain text
多头:  liqPrice = entry × (1 + minCF_liq + feeFactor) − netCollateralUsd / sizeInTokens
空头:  liqPrice = entry × (1 − minCF_liq − feeFactor) + netCollateralUsd / sizeInTokens
```
### 推导（从合约清算条件反解）
合约 `isPositionLiquidatable`（用**清算因子** `MIN_COLLATERAL_FACTOR_FOR_LIQUIDATION`）判定：
**当"扣掉平仓费、按当前价计盈亏后的剩余抵押"低于维持保证金时，就清算。**
```plain text
剩余抵押 = netCollateral + PnL(P) − 平仓费   ≤   sizeInUsd × minCF_liq   → 清算
```
其中（以多头、设清算触发价为 P 为例）：
- `sizeInUsd = sizeInTokens × entry`（开仓时按**执行价**记的名义额），故 `sizeInUsd / sizeInTokens = entry`
- `PnL(P) = sizeInTokens × (P − entry)`（多头：价格越低越亏）
- `平仓费 = sizeInUsd × feeFactor`
- `维持保证金 = sizeInUsd × minCF_liq`
代入并取等号（恰好触发）：
```plain text
netCollateral + sizeInTokens×(P − entry) − sizeInUsd×feeFactor = sizeInUsd×minCF_liq
sizeInTokens×P = sizeInTokens×entry + sizeInUsd×(minCF_liq + feeFactor) − netCollateral
两边 ÷ sizeInTokens，且 sizeInUsd/sizeInTokens = entry：
P = entry×(1 + minCF_liq + feeFactor) − netCollateral / sizeInTokens     ✅（多头）
```
空头同理（PnL = sizeInTokens×(entry − P)）得 `P = entry×(1 − minCF_liq − feeFactor) + netCollateral/sizeInTokens`。
### ⭐ 三个核心、容易被忽略的点（也是要告知社区的）
1. **`entry` 必须用"执行价"，不是 index/oracle 价。**
开仓成交价 = `oracle × (1 ± 动态价差)`，**执行价就是 entry price**——合约把 `sizeInUsd` 记成 `sizeInTokens × 执行价`。
所以整条公式里的 entry 自始至终是执行价。**用 index 价会把清算价算偏**（这正是 FE-1）。
1. **必须计入"平仓手续费"。**
清算条件是"**扣掉平仓费**后还不够维持保证金就清算"——即平仓费让仓位**更早**被清算（多头清算价更高、空头更低）。
公式里 `(minCF_liq + feeFactor)` 的 `feeFactor` 就是这一项。**漏掉它会让清算价显得更安全**。
1. **其余（尤其 funding 资金费）假设为 0。**
funding 随时间累积、依赖未来的资金费率，**开仓那一刻无法估算**，所以预览/估算里取 0。
实际链上清算会把已累积的 funding 计入（付 funding 会让你更早清算）——**这是预览的固有近似，不是 bug**；
平仓方向的动态价差同理通常 ≈0（平掉使盘改善失衡时 skew 取负被 clamp），也按 0 处理。
### 参数说明
- `minCF_liq` = 清算因子（≠ 开仓校验的 `MIN_COLLATERAL_FACTOR`；MSOL：清算 0.5% / 开仓 1%）
- `feeFactor` = **平仓** position fee 因子（MSOL 0.02%）——注意它在公式里以 `entry×feeFactor` 的形式代表了平仓费，所以 `netCollateralUsd` **不再单独扣平仓费**（否则重复扣）。
- `sizeInTokens` = 仓位 token 数；`entry = sizeInUsd / sizeInTokens` = 平均**执行价**（非 oracle）
- `netCollateralUsd` = **平仓后预计剩余抵押（不含平仓费那一项）**，完整定义：
```plain text
  netCollateralUsd = collateralUsd + 平仓 priceImpact − pendingFunding
```
- `collateralUsd` = 链上 `collateralAmount`（已是**扣过开仓费**后的余额）按抵押币价折 USD
- `平仓 priceImpact` = 现在平掉这笔会吃到的价格冲击（USD，正=改善/负=损耗）；本市场 `MAX_POSITION_IMPACT_FACTOR_FOR_LIQUIDATIONS=0` → 恒为 0
- `pendingFunding` = 链上待结算资金费（仓位欠的，`negativeFundingFeeAmount`）
> #### ⚠️ closingImpact 在「清算价」和「Unrealized PnL」里取舍**不同**（社区高频问题） 同一个"平仓 price impact"，在页面两处计算里待遇相反，必须分清： | 计算项 | 是否含平仓 priceImpact | 原因 | |---|---|---| | **清算价 liqPrice**（本节）| **含**（在 `netCollateralUsd` 里）| 清算判定问的是"**如果现在平掉**，剩余抵押够不够维持保证金"——平仓必然吃 impact，所以要算进去 | | **持仓 Unrealized PnL**（§2.9c，页面显示的浮盈亏）| **不含** | 浮盈亏是"按当前 oracle 价**标记**的毛价格盈亏"，仓位**还没平**，impact 尚未发生 → 不计入 | **一句话给社区**：页面上那个 **Unrealized PnL = 毛价格 PnL，不含平仓 impact 也不含任何费**；平仓 impact 只有**真正点平仓那一刻才实现**，它体现在**净值 / 预计可得（Est. Receive）**里，以及**清算价**的剩余抵押估算里。所以"浮盈亏"和"现在平真能拿回多少"本就是两个数，差额≈平仓 impact + 各项费。详见 §2.9(c)。
### 2.8 Max leverage（杠杆滑杆动态封顶）`maxLeverage()` — 见 §3 **FE-2**
合约的最大杠杆校验**不是** `名义size/保证金`，而是对**净保证金**：
```plain text
remainingCollateralUsd = collateralUsd + positionPnlUsd − closeFeeUsd
liquidatable 当:  remainingCollateralUsd < sizeInUsd × minCollateralFactor
```
- `positionPnlUsd` 新开仓瞬间是**负的**：入场吃了价差（sizeInUsd 含价差，代币按 index 估值）= 立刻的浮亏。
- 所以 1% 下限作用在「扣掉入场价差(当浮亏)+开仓费+平仓费后的**净**保证金」上。
**最大可开杠杆：**
```plain text
L_max = 1 / ( minCF + s_open + s_close + f_open + f_close )
```
（`minCF`=开仓校验的 `MIN_COLLATERAL_FACTOR`；`s_open/s_close`=开/平方向 dynamicSpread；`f_open/f_close`=各一次手续费）
MSOL 实例（对空盘开 1 MSOL 多头）：`minCF=1%`、`s_open=0.135%`、`s_close≈0`（平掉该多头改善失衡→skew 取负→clamp 0）、`f=0.02%×2`：
```plain text
L_max = 1 / (0.01 + 0.00135 + 0 + 0.0002 + 0.0002) ≈ 85.1x
```
→ 所以 90x 开不出来；最高约 **85x**（线上实测 remaining $1.9117 < 下限 $2.0027）。
**想让用户能开到 100x，`MIN_COLLATERAL_FACTOR` 设多少**（目标 L=100、f=0.02%×2、maxTotalSpread=0.1%）：
反解 `minCF = 1/L − (s_open+s_close) − (f_open+f_close)`
| 假设 | 计算 | `MIN_COLLATERAL_FACTOR` |
|---|---|---|
| 保守（开/平都按最坏 0.1%） | 0.01 − 0.002 − 0.0004 | **0.76%**（`7.6e27`） |
| 现实（平仓改善失衡 → s_close=0） | 0.01 − 0.001 − 0.0004 | **0.86%**（`8.6e27`） |
建议 `MIN_COLLATERAL_FACTOR=0.76%`（恰好边界，留冗余可 0.7%）。
⚠️ 它同时是**维持保证金率**——调低=杠杆更高=清算更晚=LP 风险更大。若只想放宽开仓上限不动清算线，让它与 `MIN_COLLATERAL_FACTOR_FOR_LIQUIDATION` **分别设置**。
### 2.9 持仓面板 Positions（分类 `positions`）
持仓表每行的 `leverage` 用面板自洽即可；**`liqPrice` 与 `Unrealized PnL` 改为按链上 `Reader.getPositionInfo` 逐项精确核对**（旧的 panel-only 简化公式漏了链上待结算资金费，会误判 SHORT，见变更记录 2026-06-22 / [FE-?]）。
**数据来源（从合约哪里读）：** `Reader.getPositionInfo(dataStore, referralStorage, positionKey, prices, 0, false, 0x0, true)`，逐持仓取：
- `position.numbers.sizeInUsd / sizeInTokens / collateralAmount`（持仓态，**与价格无关**）
- `fees.funding.negativeFundingFeeAmount`（待结算资金费，position 欠的；**与价格无关**。FX100 **无借贷费**，所以 pending fees 只有这一项）
- `basePnlUsd`（= 在**平仓执行价**下的 PnL，**含**平仓 price impact，仅作 info）
`positionKey = keccak256(abi.encode(account, marketIndex, isLong))`；`account` = **连接的钱包**（见 §4 账户解析）。
**(a) leverage** — 持仓面板按**净抵押**算（与价格无关）：
```plain text
leverage(显示) == sizeInUsd / netCollateral
              == sizeInUsd / (collateralUsd − pendingFundingUsd)
```
> **注意（2026-06-26 BTC 实测厘清）**：持仓面板的杠杆用 **`sizeInUsd`（开仓执行价记的名义额，价格无关）÷ 净抵押**，净抵押 = `collateral − 待结算资金费`。 早期文档写的 `Value / Margin`（Value=size×**实时** mark、Margin=毛抵押）**两处都不对**：① 用实时价 → 在真实 Chainlink feed 市场（BTC/ETH）会随价格每块漂移；② 没扣 pending funding。在 MSOL（mock 价静止 + funding≈0）上两式恰好接近，所以早期没暴露；BTC 上偏 ~0.6x。 实测：BTC LONG `sizeInUsd=$1218.28`、`collateral=$121.97`、`pendingFunding=$5.22` → `1218.28/(121.97−5.22)=1218.28/116.75=`**10.43x** = 面板 10.43x ✅（用毛 Value/Margin 得 9.80x，错）。 杠杆**与价格无关**（sizeInUsd 是开仓时定的），所以 BTC 实时价移动时这一项不应抖动；会抖的只有 PnL（见 (c)）。验证器 `scrapePanel` 已改为此口径核对。
**(b) liqPrice** — SDK `getLiquidationPrice` 非同币分支（USDC ≠ 标的），完整公式：
```plain text
mcf = minCollateralFactorForLiquidation ;  ff = positionFeeFactorNotImproved
liquidationCollateralUsd = max(sizeUsd × mcf, MIN_COLLATERAL_USD)
closingFee               = sizeUsd × ff
remainingCollateral      = collateralUsd + priceImpact − pendingFunding − closingFee
LONG  liq = (liquidationCollateralUsd − remainingCollateral + sizeUsd) / sizeTokens
SHORT liq = (remainingCollateral − liquidationCollateralUsd + sizeUsd) / sizeTokens
```
本市场链上已确认：`MIN_COLLATERAL_USD = 0`、`MAX_POSITION_IMPACT_FACTOR_FOR_LIQUIDATIONS = 0`（→ priceImpact=0）、无借贷费。所以化简为 `entry×(1±f) ∓ (margin − pendingFunding)/size`（f=mcf+ff）。
- 实测（2026-06-22，MSOL）：SHORT 0.5@entry200 / col$33.7504 / **pendingFunding$0.2417** → `(33.7504−0.2417−0.02 − 0.5 + 100)/0.5 = 265.9775` ✅ 面板 265.97（旧简化式漏 funding 得 266.44 → 误判 FAIL）。LONG 1.4998（今天刚加仓 pendingFunding≈0）→ `112.0817` ✅ 面板 112.1。
**(c) Unrealized PnL** — **毛价格 PnL**（在 oracle 价下），**不含平仓 price impact、不含任何费**：
```plain text
LONG  Unrealized PnL = sizeTokens × oracle − sizeUsd
SHORT Unrealized PnL = sizeUsd − sizeTokens × oracle      （正盈利时再按 pool PnL 上限 cap）
```
> **关仓 price impact 要不要算进 Unrealized PnL？不要。** 这是设计意图，前端做对了（``positions.ts:49-53`` 注释明确）。平仓 impact 只有真正平仓那一刻才实现，它进的是**净值 / 预计可得（Est. Receive）**，不进 Unrealized PnL。链上 `basePnlUsd`（含 impact）与毛 PnL 之差 = 平仓 impact，脚本作 info 行打印对照。 **两个数的关系（给社区讲清"为什么浮盈亏 ≠ 现在平能拿回多少"）**： ``` Unrealized PnL（显示）= 毛价格 PnL                       ← 不含 impact、不含费 平仓净得 / Est. Receive ≈ collateral + 毛PnL + 平仓impact − 平仓费 − pendingFunding                          = collateral + Unrealized PnL +（平仓 impact − 费 − funding）  同一个"平仓 impact"也出现在清算价的 `netCollateralUsd` 里（§2.7 对照表）——因为清算价问的也是"现在平掉还剩多少抵押"。**唯独页面顶部那个浮盈亏不含它。**
- 实测（MSOL SHORT 0.5，oracle≈$200，entry$200）：毛 PnL `100 − 0.5×200 = $0`（=面板 0）；`basePnlUsd = −$0.1975`（=−动态价差 0.1975%×$100）；平仓 impact = −$0.1975（只在平仓实现）。
- SDK 侧把这件事分得很清楚：`getPositionPnlUsd`（毛，显示用）vs `getPositionPnlAfterFees`（含 impact 含费，净值用）—— 见 §6 SDK 核对。
> **实时 feed 的快照漂移（核对容差，非 bug）**：PnL = `sizeTokens × price`，唯一随价格变的持仓字段。在真实 Chainlink feed 市场（BTC/ETH）上，**面板渲染 PnL 那一刻的价** 与 **验证器随后读 oracle 行那一刻的价** 之间，价格已变（每块都动）→ 两个 PnL 必有微差。误差上界 = **名义敞口 × 价格漂移**（不是 |PnL|×%，因 PnL 可能≈0）。验证器容差取 `sizeUsd × 6e-4`（与清算价的 USDC 漂移项同款）。MSOL（mock 价静止）上该差≈0。实测 BTC：面板 −17.24 vs 链上 −17.76（差 $0.52 ≈ 名义 $1218 的 0.043%，在容差内）。
### 2.10 平仓弹窗 Close Position（分类 `close`）
平仓"市价单"（`执行价 = oracle ∓ 价差`，多头平仓=卖→减，空头平仓=买→加）：
```plain text
Min acceptable == 执行价 × (1 − slippage)   （平多，卖出，最差更低）
               == 执行价 × (1 + slippage)   （平空，买入，最差更高）
执行价方向       == 平多 exec<oracle / 平空 exec>oracle（顺带给出 impliedSpread）
Est. Receive    == 退款金额：精确值 = 已实现PnL − 平仓费 − 资金费 + 释放的抵押
                   （processCollateral 瀑布）→ 由 watch ③ 逐 wei 核对，① 只展示+粗校验
```
- 实例（平多 1 MSOL）：exec `$199.73`、Min acceptable `199.73×0.995=$198.73` ✅、impliedSpread 0.135%、Est.Receive `67.07 USDC`（精确在 ③）。
- 弹窗打开时会盖住下单表单（label 重名），脚本自动**跳过 open-form 分类**，只跑 close。
### 2.11 资金费模型 Funding Fee（持仓行 `Funding` 列 + tooltip）— FX100 与标准 GMX 不同
**核心：FX100 把资金费自动结算进保证金（collateral），没有需要手动领取的 claimable 余额。** 这是与标准 GMX（轻仓侧累积 `claimableFundingAmount`、需单独 `claimFundingFees`）最大的区别。
**链上证据（合约逐项）：**
- 开/加仓 ``IncreasePositionUtils.sol:243-244``：
```plain text
  collateralDeltaAmount -= fees.totalCostAmount;                       // 欠的资金费（含在 totalCost）→ 从保证金扣
  collateralDeltaAmount += fees.funding.positiveFundingFeeAmount;      // 收的资金费 → 加进保证金
```
- 平/减仓 ``DecreasePositionCollateralUtils.sol:131``：`remainingCollateralAmount += positiveFundingFeeAmount`（收的进退款），欠的走 `payForCost` 从抵押扣。
- **全仓库无任何 `incrementClaimableFunding` 调用** → GMX 的 `claimableFundingAmountPerSize` 不再维护 → `claimableLongTokenAmount / claimableShortTokenAmount` 恒为 0。
**资金的两套账（务必分清）：**
| 账本 | 字段 | 流向 | 说明 |
|---|---|---|---|
| 逐仓 per-size | `negativeFundingFeeAmount`(付) / `positiveFundingFeeAmount`(收) | 重仓侧付 ↔ 轻仓侧收，**直接进/出保证金** | 多空之间平衡的那部分 |
| floor funding | `positionPaysLp`（稳态 ≥0，**切换窗口可短暂为负**） | **持仓 → LP 池**（负时 LP 反向垫付） | Long/Short 公式差（floor fee）造成，即使多空平衡也照收；⚠️ 因 `skew` 取 1h EMA 而 `diffOI` 取瞬时，失衡快速切换时 `positionPaysLp` 可短暂为负（LP 垫付，时间错配）——见合约侧 **R3-B03**（`BUGS.md`），影响 `实施 spec §四` 的 ≥0 假设 |
**资金费率公式（合约权威，[`MarketUtils.sol:596-660`](../../../../fx100-contracts/src/market/MarketUtils.sol#L596-L660)）：**
```plain text
diffOI = longOI − shortOI                                 // 当前瞬时多空差
skew   = EMA₁ₕ( diffOI / totalOI )                        // ⚠️ 1 小时 EMA 平滑，非瞬时（MarketUtils:575-589）
f_long  = clamp(floorFactor + baseFactor × skew,  min, max)   // ⚠️ floor 只加在 long 侧
f_short = clamp(            − baseFactor × skew,  min, max)
positionPaysLp = longOI·f_long·dt + shortOI·f_short·dt   // 双方各付各的，净额 → LP（= dt·[longOI·floor + base·skew·diffOI]）
```
- 每一侧的率 `f>0` = 该侧**付**（计入 negativeFundingFeePerSize）；`f<0` = 该侧**收**（positiveFundingFeePerSize）。
- **均衡时（skew=0）**：`f_long = floorFactor > 0`（多头仍付 floor 给 LP）、`f_short = 0` → **funding 不为零**。这正是列 tooltip "Zero at equilibrium" 说法错误的根因。
- ⚠️ **`positionPaysLp` 非恒 ≥0**：`skew` 用 EMA、`diffOI` 用瞬时，失衡快速切换时二者可反号 → `base·skew·diffOI < 0` → `positionPaysLp` 短暂为负（**LP 垫付**，时间错配）。链上已复现 −0.00076 USDC。见合约 **R3-B03**（`BUGS.md`）。
- 前端列显示的 `fundingLongRatePct / fundingShortRatePct` = `f × 360000 / 1e30`（每秒→每小时%，``markets.ts:182-183``）——"Hourly" 正确。
**一句话给社区**：LP 拿到的资金费本质是 **Long/Short 费率公式差（floor fee）**；剩余部分在多头与空头之间平衡。无论付还是收，都**自动结算进你的保证金**（付→保证金减少，收→保证金增加），**无需手动领取**。

挂单列表的每一行对应一个**未执行的触发单**（Limit/Stop/TP/SL）。**数据来源（从合约哪里读）**：账户挂单键列表 `ACCOUNT_ORDER_LIST`（`DataStore.getBytes32ValuesAt`）→ 逐 key `Reader.getOrder(dataStore, key)`，取 `numbers.orderType / triggerPrice / sizeDeltaUsd / acceptablePrice`、`flags.isLong / autoCancel`。验证脚本：`triggerLimitOrder.ts --list`（只读，不执行）。
| 列字段 | 真值（链上） | 显示规则 / 已知问题 |

### 2.13 限价/触发单预览 Limit / Stop（`open-form` 的触发单分支）
FX100 **无订单簿**，所有成交都在 **oracle 价**。下单区的 Limit/Stop 不是"挂在某价位等对手成交"，而是**"oracle 触达 trigger 即转市价成交"**（market-on-trigger）。四种触发单与触发条件（**LONG；SHORT 全部镜像**）：
| 类型（UI 语义） | OrderType | 触发条件（LONG） | 触发条件（SHORT，镜像） | acceptablePrice（哨兵） |
|---|---|---|---|---|
| 抄底（Limit 开多 / 追跌开空） | LimitIncrease (1) | Oracle ≤ trigger | Oracle ≥ trigger | 开仓：买 MaxUint256 / **SHORT 卖 0** |
| 追涨（Stop 突破开多 / 跌破开空） | StopIncrease (6) | Oracle ≥ trigger | Oracle ≤ trigger | 同上（增仓侧） |
| 止盈 TP（平多 / 平空） | LimitDecrease (3) | Oracle ≥ trigger | Oracle ≤ trigger | 平仓：**LONG 卖 0** / SHORT 买 MaxUint256 |
| 止损 SL（平多 / 平空） | StopLossDecrease (4) | Oracle ≤ trigger | Oracle ≥ trigger | 同上（减仓侧） |
**核心事实（合约层，要告知社区）：** `acceptablePrice` 参数**存在且被合约强制执行**（``BaseOrderUtils.sol` getExecutionPriceForIncrease/Decrease`），但 SDK 对**所有触发单**都把它设成**哨兵**（买侧 `MaxUint256`＝任意高价可接受 / 卖侧 `0`＝任意低价可接受），即"触发后任意价成交"=市价。
- 增仓侧 ``increase.ts:412`` `acceptablePrice = isLong ? maxUint256 : 0n`；减仓侧 ``decrease.ts:550`` `= isLong ? 0n : maxUint256`。
- Stop 单**永远**哨兵（硬编码）；Limit 单哨兵是因 app 传 `isSetAcceptablePriceImpactEnabled=false`（``useCreateOrder.ts:666``）。
- ⇒ **下单区显示的 "Max acceptable (incl. slippage)" 与 "Max slippage" 对触发单全不生效**（只对市价单 0/2 是真值 = exec×(1±slip)）。这是 FE-29/30 的根因。
- 价格控制全靠**触发条件方向**：抄底/止盈成交 ≤/≥ trigger（**有利封顶**）；追涨/止损**无封顶**（急行情可能明显偏离 trigger，但满足"不错过突破/止损必出")。
**8 类触发单 acceptablePrice 实测矩阵（2026-06-26 全链上确认）：**
| 方向 | LimitIncrease | StopIncrease | LimitDecrease(TP) | StopLossDecrease(SL) |
|---|---|---|---|---|
| LONG | Max（实测成交 $180） | Max（$260） | 0（$250） | 0（$165） |
| SHORT | 0（$220） | 0（镜像） | Max（实测 $165 PnL+$54.70） | Max |
> 即 **增仓哨兵 = `isLong?Max:0`、减仓哨兵 = `isLong?0:Max`**，SHORT 完整镜像 LONG。详尽的命名/交互/文案建议（产品+社区文档）见独立文档 `LIMIT_ORDER_UI_SUGGESTIONS.md`。 **预览盈亏口径（FE-30，高优）**：TP/SL 预览的 Est.P&L / Est.Receive / 面板 Est.execution **应按 `triggerPrice` 算**，当前误按"现价"算 → SL 止损会把亏损显示成盈利。详见 §3 FE-30。
### 2.14 顶栏 Market Header（分类 `market-header`）
交易页顶栏的市场统计。**数据来源（从合约哪里读）**：`Reader.getMarketInfo(...)`（即 SDK `selectedMarketInfoAtom` / `marketInfo`），逐字段：
**(a) Open Interest（long / short / total）** — `selectedMarketOIAtom`（``markets.ts:138-169``）
```plain text
首选： openInterestLong  = marketInfo.longInterestUsd  / 1e30     // 源 CUMULATIVE_OPEN_COSTS，与协议记账口径一致
       openInterestShort = marketInfo.shortInterestUsd / 1e30
回退（marketInfo 未就绪）： OPEN_INTEREST_IN_TOKENS × mid / 1e30   // mid=(min+max)/2
total = long + short
```
> ❌ **FE-25**：顶栏 OI 走 `marketStats` API，按 `currentChainIdAtom` 查；该值默认 **99918(BASE_FORK)** ≠ fork 的 **99917(BASE_SEPOLIA_FORK)** → 查到的链没该 market → 显 **$0/$0**（价格/Funding 走链上 `marketInfo`(99917) 故正常）。即时修：`localStorage['fx100:currentChainId']='99917'`；根治：`DEFAULT_APP_CHAIN_ID` 对齐部署链。
**(b) Funding / h（long / short 费率）** — `selectedMarketFundingAtom`（``markets.ts:175-194``）
```plain text
fundingLongRatePct  = longFundingFactorPerSecond  × 360000 / 1e30    // 每秒 → 每小时 %（×3600×100，bigint 内完成）
fundingShortRatePct = shortFundingFactorPerSecond × 360000 / 1e30
```
> 费率**机制/正负含义**见 §2.11（floor→LP、均衡不为零、各侧各付净额流向 LP）。这里只是 per-second→per-hour 的展示换算。"Hourly" 标签正确。
**(c) Available Liquidity（long / short）** — `marketInfo.availableLongUsd / availableShortUsd / 1e30`，链上 ``ReaderUtils.getAvailableLiquidityUsd`` 计算 = **四个上限取最小**：
```plain text
reservedUsd(LONG)  = openInterestInTokens × indexPrice.max      // 多头按标的现价计提
reservedUsd(SHORT) = cumulativeOpenCosts                        // 空头按开仓成本计提（与价格无关）
OI = cumulativeOpenCosts(isLong)
availableUsd = max(0, min(
    maxOpenInterest        − OI,                  // ① 硬上限 MAX_OPEN_INTEREST
    poolUsd × maxOIFactor  − OI,                  // ② 池值×最大 OI 因子
    poolUsd × reserveFactor          − reservedUsd,   // ③ 池值×储备因子
    poolUsd × openInterestReserveFactor − reservedUsd // ④ 池值×OI 储备因子
))   // poolUsd = poolUsdWithoutPnl（不含未实现 PnL 的池值）
```
> 含义：还能再开多少名义敞口（受池子储备 + OI 上限四重约束）。bit-exact 由合约算，① 只核 `面板显示 == marketInfo 字段 /1e30`。
**(d) Mark / Index price** — `markPrice = tickerMidPrice ?? mid`、`indexPrice = maxPriceUsd`（顶栏标价；与 §2.2 的开仓 bid/ask 一侧口径不同，见 §2.9 注）。
**(e) 24h Volume / Change%** — `volume24h`(raw USD，UI 做 K/M/B 压缩) / `change24hPercent`——**链下统计**(`marketStats`/subsquid)，非链上真值，仅展示（不纳入 ① bit-exact）。
| 字段 | 期望/公式 | 核对 | 数据来源 |
|---|---|---|---|
| Open Interest L/S/Total | marketInfo.long/shortInterestUsd /1e30（回退 OI_tokens×mid） | ⏳ scrape 待接 | 链上 marketInfo（❌FE-25 chainId） |
| Funding/h L/S | fundingFactorPerSecond ×360000/1e30 | ⏳ | 链上 marketInfo（§2.11 机制） |
| Available Liquidity L/S | availableLong/ShortUsd /1e30 = min(4 caps) | ⏳ | 链上 ReaderUtils |
| Mark / Index | tickerMid / maxPriceUsd | ⏳ | ticker / 链上 |
| 24h Vol / Change% | 链下统计 | ℹ️ 不核 | subsquid/marketStats |

> **现象**：前端的清算价 / 杠杆 / 目标 size 估算，把抵押的 **USDC 按面值 $1** 计，未用真实 USDC stream 价（~$0.9997）。 **实测（Adjust Leverage → 2x）**：Target Size 显示 **$159.77 = 2 × 79.88**（USDC@$1）；正确应 `targetLev × collateralUsd = 2 × (79.88×$0.99966) = $159.71`。差 $0.06 → 加 size 到 $159.77 后，**实际达成杠杆 = sizeUsd/collateralUsd = 159.77/79.85 = 2.001x，而非整 2.000x**（轻微过冲）。 **影响面**：Adjust Leverage 的 Target Size；Adjust Margin / Adjust Leverage 的 Est.Liq（叠加 FE-6 的略过 mcf）；持仓面板 liq（表现为面板↔验证器的 USDC 价差）。量级 ~0.025–0.05%。 **定性**：纯**计价口径**问题（USDC≠$1），账本/链上正确；用户体感是"目标杠杆/清算价有微小偏差"。 **建议**：所有把 USDC 抵押并入 USD 计算的地方（leverage、size、liq），统一用 USDC oracle/stream 价折算，而非 $1。 ① `scrapeLeverage` 已按面板口径（USDC@$1）核对其自洽（PASS），并在 info 行打印**正确 USD 值 + 实际达成杠杆**作为 FE-8 标注。
### FE-10 — TP/SL 触发价越过清算价无警告（止损永不成交）
> **现象**：止损(SL)触发价设在**清算价的亏损侧**时（LONG: SL 价 < 清算价；SHORT: SL 价 > 清算价），价格到达 SL 之前**仓位已先被清算**，该止损单永远无法成交。前端**无任何校验/提示**，照常允许下单。 **链上行为**：合约 keeper 执行该 SL 时，平仓亏损 > 剩余抵押 → `OrderHandler` 以 reason `"pnl"` **冻结订单**（`OrderFrozen`，tx 仍 success，仓位不变、`isFrozen=true`），不会成交。 **实测**：LONG 入场 $200 / 抵押 53.13 USDC / size 0.663457 MSOL → 清算价 ≈ $120。 - SL = **$100**（< 清算价）：下单成功，但 force-execute 时被 `"pnl"` 冻结（$100 时亏损 0.663457×(200−100)=$66.35 > 抵押 $53.13）。 - SL = **$150**（> 清算价）：正常（与 TP $250 配对，触发 TP 全平后该 SL 被 autoCancel）。 **建议**：SL 输入框校验触发价是否越过当前清算价（方向相关）；越过时给**警告**（例："止损价 $X 低于清算价 $Y，价格可能在止损触发前先被清算"），**仍允许下单**（用户可继续）。TP 同理可提示无意义触发价。 **定性**：UX/校验缺失（非账本错误）；合约侧冻结是正确的兜底，但用户在 UI 上看不到原因。 **附**：本次同时验证了 **autoCancel 联动正确**——仓位 size→0（TP 全平）时，该方向所有 `autoCancel=true` 的 decrease 单（含先前被冻结的 $100 SL）全部自动取消；`autoCancel=false` 的单不受影响。前端 TP/SL 下单已正确置 `autoCancel=true`。

> **建议原文**：Limit/Stop 做成按钮切换（类似 Reduce-only），并放到 Reduce-only 下面。 **评估（部分采纳）**： - ✅ **样式统一**合理——做成清晰的二选一段控/按钮组，与表单其余控件视觉一致。 - ⚠️ **位置要慎重**：Limit｜Stop 决定了 Trigger Price 的**含义**（Limit=Oracle ≤ trigger 抄底；Stop=Oracle ≥ trigger 追涨，见 §2.13）。它是 Trigger Price 输入框的"方向开关"，**应紧邻 Trigger Price**（当前就在其正上方，是对的）。若挪到 Reduce-only 下方（Leverage、TP/SL 之后），开关与它控制的字段被拉远 → 用户先填 trigger，再到很下面才改 Limit/Stop，容易设反方向（这正是 FE-29 想消除的歧义）。 - **推荐**：①保留位置在 **Trigger Price 正上方**，仅把样式统一成按钮组；或 ②若产品坚持下移，则下移后 Trigger Price 区必须有**实时方向回显**（配合 FE-32 的 ≤/≥ 标），且 "Place Limit/Stop" 按钮文案随之联动，避免脱节。 - 注意：Reduce-only 是 **on/off 开关**（单一布尔），Limit/Stop 是**二选一**，二者交互模型不同——"类似 Reduce-only"指视觉风格，不要做成开关语义。
### FE-32 — 删除 Trigger Price 下的 "Buy when Oracle ≤ 100"（保留方向标）
> **建议原文**：删掉 "Buy when Oracle ≤ 100"，因为 Trade Details 已有 "Limit buy: once Oracle ≤ 100, opens at 100 or lower." **评估（合理，带一处保留）**： - ✅ 去重合理——同一句话出现两次确实冗余，精简方向对。 - ⚠️ 但 helper 行是**唯一在输入点旁、即时确认触发方向（≤ vs ≥）**的地方；≤/≥ 设反是触发单最高频、最危险的错误。Trade Details 在面板更下方（可能需滚动才看全）。 - **推荐**：删掉整句文字，但在 Trigger Price 输入框旁**保留一个紧凑方向标**（如输入框前缀 `Oracle ≤` / `Oracle ≥` 的小 chip，或灰字 "≤"/"≥"），随 Limit/Stop 与多空联动。若产品确认 Trade Details 在该断点**始终免滚动可见**，则可彻底删除、不留方向标。
### FE-33 — Max slippage 值精简为 "Not applicable"，解释入 tooltip

### FE-34 — Est. execution price 合并 Execution 行 + 动态 tooltip + 值改 "Market on trigger"
> **建议原文**：把 "Execution" 行内容并到 "Est. execution price" 下；Est. execution price 的 tooltip 换成 "No order book: your price is a trigger, not a resting limit. Activates when the oracle drops to 100, then buys at the prevailing oracle price (at or below 100)."； 值 "100" 换成 "Market on trigger"（不要 "— fills at 100 or lower"，Trade Details 已说）。 **评估（合理，带一条硬性要求：tooltip 必须动态）**： - ✅ 合并 "Execution" 单独行进 Est. execution price 的 tooltip/副标，减少重复行；值显 **"Market on trigger"**（市价触发本就没有单一预估价，这样诚实），去掉 "— fills at 100 or lower"（与 Trade Details 重复）。 - 🔴 **硬性要求：tooltip 不能写死 "drops … buys"**。FX100 有 4 类触发单 × 多空（§2.13），方向词必须按 `orderTriggerKind`（Limit/Stop）× `isLong` 动态生成：   - 抄底 Limit Buy（开多 LimitIncrease）：oracle **drops to** X → **buys** at X or **lower**   - 追涨 Stop Buy（开多 StopIncrease）：oracle **rises to** X → **buys** at X or **higher**（无封顶，急行情可能明显偏离，见 §2.13）   - SHORT 镜像（开空 Limit=oracle rises / Stop=oracle drops；sells 侧）   - TP/SL（减仓）同理换 buys/sells 与 rises/drops   建议把这套句子收进 `triggerOrderCopy.ts`（FE-29 已建该文件）统一产出，UI 只取 key。 - 前半句 "No order book: your price is a trigger, not a resting limit." 是通用解释，4 类共用，写得好，保留。
### FE-35 — Order Status 弹窗 "Limit Price" → "Trigger Price"
> **建议原文**：Order Status 页的 "Limit Price" 改成 "Trigger Price"。 **评估（强烈赞成）**：与 FE-29 同根——FX100 无订单簿、acceptablePrice 是哨兵、市价触发成交（§2.13），叫 "Limit Price" 会让用户误以为有"挂在该价的限价单"。**"Trigger Price" 才准确**。须对**所有触发单**（Limit / Stop / TP / SL）统一，不止 Limit。Order Status 弹窗其余字段（Position/Order Type/Size/Leverage/Pay amount）保持。

> **建议原文**：所有 "Liquidation Price" 都改成 "Est.

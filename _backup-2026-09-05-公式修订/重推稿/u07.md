## 10. Funding 资金费

v0.3.2 的资金费是**双轨**结构，两轨在不同时刻发生，测试必须分开断言：

1. **市场轨（只记账，不动钱）**——每笔订单执行开头调用 `updateFundingState`，把两侧的每 Token 累计指数 `negative/positiveFundingFeePerSize` 往前推、刷新 `fundingUpdatedAt` 与 skew EMA，并 `emitFunding`。**v0.3.2 起这一步不产生任何代币转移**（v0.3.1 在这里按 `positionPaysLp` 直接记可领费用或从 LPVault 转账，已删除）。
2. **仓位轨（真实现金流）**——仓位加仓/减仓/平仓/清算/ADL 时，先按该仓自己的指数差算出 `negativeFundingFeeAmount`（应付）与 `positiveFundingFeeAmount`（应收），再调用 v0.3.2 新增的 `MarketUtils.settleFundingFees` 按**该仓净差**在 LPVault ↔ PositionVault ↔ 可领费用账本之间搬运。

> 版本差异（v0.3.1 → v0.3.2）：`updateFundingState` 删去 `positionVault` 入参、整段资金搬运移除；新增 `external function settleFundingFees(positionVault, dataStore, eventEmitter, market, negativeFundingFeeAmount, positiveFundingFeeAmount)`；`positionPaysLp` 被源码注释降级为 observability-only。§10.1～§10.5 的数值公式两版一致。

**调用链锚点**：

| 环节 | 源码锚点 | 说明 |
| --- | --- | --- |
| 订单执行开头刷新市场指数 | `src/order/ExecuteOrderUtils.sol::executeOrder`（L32，`PositionUtils.updateFundingState` 调用在 L52）→ `src/position/PositionUtils.sol::updateFundingState`（L482）→ `src/market/MarketUtils.sol::updateFundingState`（L402） | 在 `processOrder` **之前**执行；所有订单类型（市价 / 限价 / 止损 / 清算 / ADL）共用同一入口，因此清算与 ADL 也会先推指数 |
| 加仓路径结算 | `src/position/IncreasePositionUtils.sol::processCollateral`（L198，settle 调用在 L219） | 传入**应付额** `fees.funding.negativeFundingFeeAmount` |

### 10.1 市场 Open Interest USD

> 源码：`src/market/MarketUtils.sol::getNextFundingAmountPerSize`（L475）、`src/price/Price.sol::midPrice`（L25）

```text
indexMidPrice = (indexTokenPrice.min + indexTokenPrice.max) / 2   // 向下取整

longOIUsd  = longOpenInterestInTokens  × indexMidPrice
shortOIUsd = shortOpenInterestInTokens × indexMidPrice

totalOIUsd = longOIUsd + shortOIUsd
```

- `openInterestInTokens` 取自 `openInterestInTokensKey(marketIndex, isLong)`，单位是 index token 的原始最小单位；乘以价格后得到 `1e30` 精度 USD。
- **零 OI 早退**：`totalOIUsd == 0` 时函数**立即返回全零 `result`**（避免除零）。注意这**不是完全 no-op**：调用方 `updateFundingState` 随后仍会
  - 把 `fundingUpdatedAt` 写成 `block.timestamp`；
  - 把 `fundingSkewEma` **写成全零**（`result.skewEMA` 是默认初始化的空结构），即**抹掉已有的 skew EMA 历史**；
  - 以三个 0 值 `emitFunding`。
  此时 long/short × negative/positive **共四个 per-size 增量槽位全为 0**，`applyDeltaToNegative/PositiveFundingFeePerSize` 的四次调用全部因 `delta == 0` 早退，不发 `NegativeFundingFeePerSizeUpdated` / `PositiveFundingFeePerSizeUpdated` 事件。

### 10.2 Skew 与 EMA

> 源码：`src/market/MarketUtils.sol::getNextFundingAmountPerSize`（L500-L514）、`src/common/math/ExponentialMovingAverage.sol::saveValue`（L64）/ `::emaValue`（L72）

原始 skew（有符号，`1e18` 精度；Solidity 整数除法**向零截断**）：

```text
rawSkew = (longOIUsd - shortOIUsd) × 1e18 / totalOIUsd
```

写入与取值分两个分支：

```text
if (skewEMA.lastTime == 0)                       // 该市场第一次有 OI 的 funding 更新
    skewEMA = { lastTime: now, sampleInterval: 3600,
                lastValue: rawSkew, lastEmaValue: rawSkew }
else
    skewEMA.lastEmaValue = emaValue(旧状态)       // 用旧 lastValue / lastEmaValue / lastTime 算
    skewEMA.lastValue    = rawSkew
    skewEMA.lastTime     = now

skew = emaValue(skewEMA)                          // 参与费率计算的值
```

`emaValue` 自身的三个分支：

```text
if (lastTime >= block.timestamp)          → 返回 lastEmaValue
else
    e = (block.timestamp - lastTime) × 1e18 / sampleInterval
    if (e > 41e18)                        → 返回 lastValue          // 视为完全收敛
    else
        alpha = exp(-e)                                              // 1e18 精度
        返回 (lastValue × (1e18 - alpha) + lastEmaValue × alpha) / 1e18
```

**关键行为（易踩坑）**：`saveValue` 先把 `lastTime` 改成 `block.timestamp`，紧接着的 `emaValue()` 因此命中第一个分支，直接返回刚算出的 `lastEmaValue`。也就是说——

- **本次观测到的 `rawSkew` 不影响本次费率**，它要到**下一次** funding 更新时才通过 `lastValue` 参与加权；
- 只有 `lastTime == 0` 的首次初始化例外：`lastValue = lastEmaValue = rawSkew`，本次费率直接用原始 skew；
- 同一区块内的第二次 funding 更新（`lastTime == block.timestamp`）EMA 不前进，`durationInSeconds` 也为 0，整轮增量为 0。
- `sampleInterval` 固定 3600 秒，只在首次初始化时写入，不可配置。

### 10.3 每秒费率

> 源码：`src/market/MarketUtils.sol::getNextFundingAmountPerSize`（L526-L539）、`src/utils/Calc.sol::clamp`（L21）

```text
longFundingFactorPerSecond
= clamp(
    fundingFloorFactor + (fundingBaseFactor × skew) / 1e18,
    minFundingFactorPerSecond,
    maxFundingFactorPerSecond
  )

shortFundingFactorPerSecond
= clamp(
    (-fundingBaseFactor × skew) / 1e18,
    minFundingFactorPerSecond,
    maxFundingFactorPerSecond
  )
```

- 精度 `1e30` / 秒；`skew` 是 `1e18` 精度，所以除数是 `1e18` 而不是 `1e30`。
- 有符号整数除法**向零截断**（负数不向下取整）。
- `clamp(value, min, max)`：`value < min → min`；`value > max → max`；否则原值。`min` 与 `max` 共用同一对上下界，**多空两侧用的是同一组边界**。
- `fundingFloorFactor` 只加在 long 侧，short 侧没有 floor 项——多空费率**不对称**，不能假设 `shortRate == -longRate`。
- 符号约定：**正 = 该侧支付，负 = 该侧收取**。

### 10.4 市场累计 Funding（per-size 指数）

> 源码：`src/market/MarketUtils.sol::getNextFundingAmountPerSize`（L519、L541-L576）、`::getSecondsSinceFundingUpdated`（L985）、`::applyDeltaToNegative/PositiveFundingFeePerSize`（L943 / L965）、`src/utils/Precision.sol::applyFactor`（L38）/ `::toFactor`（L117、L129）

时长：

```text
durationInSeconds
= (fundingUpdatedAt == 0) ? 0 : (block.timestamp - fundingUpdatedAt)
```

- `fundingUpdatedAt == 0` 分支返回 0（不是从创世时间起算），因此**市场的第一次 funding 更新增量必为 0**。
- 链停摆或市场被禁用期间 funding 照常累计，源码明示不做补偿修正。

每侧独立判定（`long` / `short` 各一段，互不影响）：

```text
if (openInterestInTokens.side > 0):
    if (sideFundingFactorPerSecond > 0):
        negativeFundingFeePerSizeDelta.side
        = ⌊ ⌊ sideOIUsd × (sideRate × duration) / 1e30 ⌋ × 1e30 / sideOpenInterestInTokens ⌋
    else:                                    // 含 sideRate == 0
        positiveFundingFeePerSizeDelta.side
        = ⌊ ⌊ sideOIUsd × (|sideRate| × duration) / 1e30 ⌋ × 1e30 / sideOpenInterestInTokens ⌋
```

- **两步都向下取整**：内层 `Precision.applyFactor(uint256, uint256)` 直接转 `Math.mulDiv`（该重载**没有** `roundUpMagnitude` 形参，恒向下取整），外层 `Precision.toFactor(uint256, uint256)` 转调三参重载并传 `roundUpMagnitude = false`。
- 注意这**不是两次连续除法**：中间 floor 之后又乘回了 `1e30`，因此**不能改写成 `⌊ sideOIUsd × sideRate × duration / sideOpenInterestInTokens ⌋` 一次算完**——那属于重排乘除顺序，结果可能差 1 wei。（若真是两次连续除法，`⌊⌊x/m⌋/n⌋ = ⌊x/(m·n)⌋` 恒成立，合并是安全的。）
- 中间量 `sideOIUsd × sideRate × duration / 1e30` 就是该侧本次累计的 USD 资金费（`1e30` 精度）。
- `sideRate == 0` 落入 `else` 分支，`|0| = 0` → delta 为 0，等价于不动账。
- 该侧 `openInterestInTokens == 0` 时整段跳过，**即使另一侧有 OI 也不会给空侧记账**。
- 增量写回：`applyDeltaToNegative/PositiveFundingFeePerSize` 在 `delta == 0` 时早退且**不发事件**；非零时 `applyDeltaToUint` 累加并发 `NegativeFundingFeePerSizeUpdated` / `PositiveFundingFeePerSizeUpdated`。事件字段是 `isLong`（bool）/ `delta`（uint）/ **`value`**（uint，累加后的新值）——源码里那个局部变量虽然叫 `nextValue`（`MarketUtils.sol` L954 / L976），但 `MarketEventUtils.sol`（L147-L164 / L166-L183）写进日志的键名是 `value`，E2E 按 `nextValue` 取字段会取空。
- 两个指数都是 `uint256` 且**单调不减**，同一侧同时只可能有一个在增长。

### 10.5 单仓应付 / 应收

> 源码：`src/pricing/PositionPricingUtils.sol::getPositionFees`（L352，读 latest per-size）与 `::getFundingFees`（L394）、`src/market/MarketUtils.sol::getFundingAmount`（L696）

```text
negativeFundingFeeAmount        // 应付，roundUpMagnitude = true
= ⌈ position.sizeInTokens
    × (latestNegativeFundingFeePerSize - position.negativeFundingFeePerSize)
    / (1e30 × collateralTokenPrice.min) ⌉

positiveFundingFeeAmount        // 应收，roundUpMagnitude = false
= ⌊ position.sizeInTokens
    × (latestPositiveFundingFeePerSize - position.positiveFundingFeePerSize)
    / (1e30 × collateralTokenPrice.max) ⌋
```

- **单位与选价侧配对**：`1e30` 与价格**合并成一个除数做一次除法**（`Precision.mulDiv(sizeInTokens, diff, FLOAT_PRECISION * price, roundUp)`），不是先除 `1e30` 再除价格；拆成两次除法属于重排乘除顺序，会算错。
- **选价侧**：向上取整的一侧配 `collateralTokenPrice.min`（分母更小 → 应付 Token 更多），向下取整的一侧配 `collateralTokenPrice.max`（分母更大 → 应收 Token 更少）。两边都朝对协议保守的方向倾斜。源码注释说明向上取整是为了防止用户靠频繁更新仓位把资金费磨成 0。
- **乘的是整仓 `sizeInTokens`，不是本次 `sizeDelta`**。任何仓位动作（含 `sizeDelta = 0` 的纯增减保证金）都对**全仓**结算一次资金费。
- `latest... - position...` 是 `uint256` 减法：若仓位基准大于市场最新值会 revert（下溢）。正常路径下指数单调不减且基准每次结算后重置，不会触发。
- **基准（baseline）重置规则**：
  - 新开仓（`position.sizeInUsd() == 0`）：`IncreasePositionUtils.sol::increasePosition`（L63-L77）在算费用之前先把两个基准写成市场最新值 → 本次两个金额均为 0，`settleFundingFees` 两个分支都不命中。
  - 加仓：结算完后 `setNegative/PositiveFundingFeePerSize(latest...)`（L114-L115）。
  - 部分减仓：`DecreasePositionUtils.sol`（L285-L286）在仓位仍存续时重置基准。
  - 全平（`sizeInUsd == 0 || sizeInTokens == 0`）：仓位记录被 `PositionStoreUtils.remove` 删除（L279-L283），不写基准。

### 10.6 positionPaysLp（仅观测量，v0.3.2 不产生现金流）

> 源码：`src/market/MarketUtils.sol::getNextFundingAmountPerSize`（L578-L587）、`src/market/MarketEventUtils.sol::emitFunding`（L130）

```text
positionPaysLp
= ( signedFloor(longOIUsd  × longRate  × duration / 1e30)
  + signedFloor(shortOIUsd × shortRate × duration / 1e30) )
  / collateralTokenPrice.midPrice()
```

- `signedFloor` = 先按绝对值向下取整再补符号（`Precision.applyFactor(uint256, int256)`）；最外层除法是有符号整数除法，**向零截断**。
- 符号：`> 0` 表示仓位侧净支付 LP，`< 0` 表示 LP 净支付仓位侧。
- **v0.3.2 起该值只进 `Funding` 事件（`intItems[2] = "positionPaysLp"`），不参与任何转账**。源码注释明确说明它只用于 observability，因为各仓位的实际资金费是各自独立取整的。**不要用它推导 LPVault / PositionVault 的余额变化**——那是 §10.7 的事。
- v0.3.1 的旧行为（`positionPaysLp > 0` 记 `FUNDING_FEE_TYPE` 可领、否则 LPVault 转账）**已删除**，沿用旧口径会算错所有 Vault 余额断言。

### 10.7 仓位结算：settleFundingFees（v0.3.2 新增）

> 源码：`src/market/MarketUtils.sol::settleFundingFees`（L445-L469）

```text
settleFundingFees(positionVault, dataStore, eventEmitter, market, negAmt, posAmt):

  if (negAmt > posAmt):
      incrementClaimableFeeAmount(market.marketIndex, market.collateralToken,
                                  negAmt - posAmt, FUNDING_FEE_TYPE)   // 只记账本，不转账
  else if (posAmt > negAmt):
      IVault(market.vault).transferOut(market.collateralToken,
                                       positionVault, posAmt - negAmt) // LPVault → PositionVault
  else:                                                                 // 相等
      不动账
```

- 只搬**净差**，不是两笔总额。
- `negAmt > posAmt` 分支**不发生代币转移**：差额本来就留在 PositionVault 里（仓位抵押品已被扣减），只是把它标记为 `FUNDING_FEE_TYPE` 可领（`claimableFeeAmountKey(marketIndex, collateralToken, FUNDING_FEE_TYPE)`）。
- **资金去向不对称（Vault 余额断言必读）**：
  - 仓位**净支付**时，钱进的是 `FUNDING_FEE_TYPE` 可领账本 → `FeeHandler::claimFees` 从 **PositionVault** 转到 FeeHandler → `withdrawFees`（`onlyFeeKeeper`）转给 `FEE_RECEIVER` / RewardSplitter。**LPVault（`market.vault`）的余额不会因此增加**。
  - 仓位**净收取**时，钱是从 **LPVault** 转出到 PositionVault。
  - 即：LP 只在一个方向上出钱。断言"LP 收到资金费"会失败。
- `incrementClaimableFeeAmount` 在 `delta == 0` 时早退，不发 `ClaimableFeeAmountUpdated`。
- `claimableFeeAmount` 只被 `FeeUtils` 读写，不进入 LP 池估值。

**两条调用路径传入的第一个金额参数不同（v0.3.2 最容易漏掉的细节）**：

| 路径 | 传入 `negativeFundingFeeAmount` 位的实参 | 含义 |
| --- | --- | --- |
| 加仓 `IncreasePositionUtils.sol::processCollateral`（L219） | `fees.funding.negativeFundingFeeAmount` | **应付额** |
| 减仓 / 平仓 / 清算 / ADL `DecreasePositionCollateralUtils.sol::processCollateral`（L141） | `collateralCache.result.amountPaidInCollateralToken` | **实付额** |

两条路径的 `positiveFundingFeeAmount` 位都传 `fees.funding.positiveFundingFeeAmount`（应收额，不打折）。

**加仓路径**（`IncreasePositionUtils.sol::processCollateral`）：

```text
collateralDeltaAmount -= fees.totalCostAmount            // 含 negativeFundingFeeAmount
collateralDeltaAmount += fees.funding.positiveFundingFeeAmount
```

抵押品不足时在 `increasePosition` 里以 `FxErrors.InsufficientCollateralAmount` revert（L98-L105），因此加仓路径**要么全额付清、要么整笔回滚**，不存在部分支付。

**减仓路径**（`DecreasePositionCollateralUtils.sol::processCollateral`，L127-L166）顺序敏感：

```text
① remainingCollateralAmount += positiveFundingFeeAmount        // 应收先并入押金
② payForCost(costUsd = negativeFundingFeeAmount × colPrice.min)
     remainingCostInOutputToken = ⌈costUsd / colPrice.min⌉ = negativeFundingFeeAmount（整除）
     先从 output.outputAmount（已到账的正 PnL）扣，再从 remainingCollateralAmount 扣
     → amountPaidInCollateralToken ≤ negativeFundingFeeAmount
③ settleFundingFees(..., amountPaidInCollateralToken, positiveFundingFeeAmount)
④ if (amountPaidInCollateralToken < negativeFundingFeeAmount)
       emitInsufficientFundingFeePayment(marketIndex, token,
           expectedAmount = negativeFundingFeeAmount,
           amountPaidInCollateralToken)
⑤ if (remainingCostUsd > 0) → handleEarlyReturn(step = "funding")
       非「全平且清算/ADL」时以 FxErrors.InsufficientFundsToPayForCosts revert（③④ 一并回滚）
```

- ③ 在 ⑤ 之前执行：只有在 `isInsolventCloseAllowed`（全平 **且** 清算单或 ADL）时这笔"欠费结算"才会真正落账，缺口由 LP 承担。
- ④ 的事件在 v0.3.2 只有 4 个字段（`token` / `marketIndex` / `expectedAmount` / `amountPaidInCollateralToken`）；v0.3.1 的第 5 个字段 `amountPaidInSecondaryOutputToken` 与整条 holding-address 兜底路径已删除。
- `payForCost` 的 `remainingCostUsd` 在 v0.3.2 改为 `remainingCostInOutputToken × collateralTokenPrice.min`（v0.3.1 直接赋 Token 数量，单位错误），会影响该步早退时上报的欠费 USD 数值。

### 10.8 数值示例（自算校验）

> 源码：按 `src/market/MarketUtils.sol::getNextFundingAmountPerSize`（L490-L587）与 `::getFundingAmount`（L696）的整数运算逐步复算

假设：抵押品 USDC（6 位，`colPrice.min = colPrice.max = 1e24`）；index token 18 位，`indexMidPrice = 3e15`（$3,000）；`longOITokens = 10e18`、`shortOITokens = 5e18`；`fundingFloorFactor = 0`、`fundingBaseFactor = 3e21`；不触发 clamp；`duration = 3600`；EMA 已收敛到 `rawSkew`。

```text
longOIUsd  = 10e18 × 3e15 = 3.0e34            ($30,000)
shortOIUsd =  5e18 × 3e15 = 1.5e34            ($15,000)
rawSkew    = 1.5e34 × 1e18 / 4.5e34 = 333333333333333333

longRate   = 0 + 3e21 × 333333333333333333 / 1e18 =  999999999999999999000
shortRate  =   -(3e21 × 333333333333333333) / 1e18 = -999999999999999999000

多头累计 USD = ⌊3.0e34 × (longRate × 3600) / 1e30⌋ = 107999999999999999892000000000   ($0.108)
空头累计 USD = ⌊1.5e34 × (|shortRate| × 3600) / 1e30⌋ = 53999999999999999946000000000  ($0.054)

negativeFundingFeePerSizeDelta.long
= ⌊107999999999999999892000000000 × 1e30 / 10e18⌋ = 10799999999999999989200000000000000000000
positiveFundingFeePerSizeDelta.short（同式，除以 5e18）= 相同值

多头仓位 sizeInTokens = 1e18：
negativeFundingFeeAmount = ⌈1e18 × 1.07999...e40 / (1e30 × 1e24)⌉ = 10800   (0.010800 USDC)
空头仓位 sizeInTokens = 1e18：
positiveFundingFeeAmount = ⌊1e18 × 1.07999...e40 / (1e30 × 1e24)⌋ = 10799   (0.010799 USDC)

positionPaysLp = (1.07999...e29 - 0.53999...e29) / 1e24 = 53999   (仅事件，不转账)
```

校验：$30,000 × 1e-9/s × 3600s = $0.108 ✓（`longRate = 999999999999999999000` 在 `1e30` 精度下约等于 1e-9 / 秒）。

同一 per-size 增量下多头**进位**付 10800、空头**舍尾**收 10799，但这两笔**互不轧差**（见 §10.7）：多头那 10800 全额进 `FUNDING_FEE_TYPE` 可领账本（币留在 PositionVault、最终流向 `FEE_RECEIVER`），空头那 10799 由 LPVault 转出到 PositionVault，分属两个不同账本。ceil/floor 配对的效果是系统整体收进的比付出的多 1 wei，**不是**两笔在同一个池子里对冲。E2E 不要按多空对称值断言，也不要把两笔写进同一个余额期望式。

### 10.9 E2E 断言要点

> 源码：`src/market/MarketUtils.sol::updateFundingState`（L402）/ `::settleFundingFees`（L445）、`src/market/MarketEventUtils.sol::emitNegative/PositiveFundingFeePerSizeUpdated`（L147 / L166）/ `::emitFunding`（L130）、`src/position/PositionEventUtils.sol::emitInsufficientFundingFeePayment`（L152）

- 每个仓位动作至少断言四组：① 市场两个 per-size 指数与 `fundingUpdatedAt` 的刷新；② 该仓 `negative/positiveFundingFeeAmount`；③ 仓位抵押品 / output 的变化；④ **LPVault 与 PositionVault 的余额差额 + `FUNDING_FEE_TYPE` 可领账本**。只看 `Funding` 事件不足以证明结算正确。
- 取 per-size 事件字段时用键名 `isLong` / `delta` / **`value`**（不是 `nextValue`），见 §10.4。
- 净支付方向的期望是「LPVault 余额不变 + `FUNDING_FEE_TYPE` 可领 +净差」；净收取方向才是「LPVault 余额 −净差」。两个方向的期望式不对称。
- `positionPaysLp` 只作为事件字段核对，**不得**用于任何 Vault 余额期望值。
- 市场 OI 归零后的下一次订单执行会**清空 skew EMA 并推进 `fundingUpdatedAt`**：跨"清仓再开仓"的场景不能沿用之前的 EMA 快照。
- 参数读取一律用 `getInt` 读 floor / base / min / max 四项；`min` 通常为负值。
- 减仓路径断言资金费时，必须区分 `negativeFundingFeeAmount`（应付）与 `amountPaidInCollateralToken`（实付）；两者不等时应同时出现 `InsufficientFundingFeePayment` 事件，且该笔交易只可能是「全平 + 清算/ADL」。

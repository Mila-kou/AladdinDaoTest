### 1.2 核心变化说明
**旧机制（priceImpactUsd 加法模型）：**
```javascript
pnlUsd = positionValue - costBasis + priceImpactUsd
```
价格冲击作为 USD 值加到 PnL，与执行价格解耦。
**新机制（dynamicSpread 作用于执行价格）：**
```javascript
dynamicSpread = constantPriceSpread + priceImpactSpread + skewImpact
executionPrice = indexPrice ± dynamicSpread（多头加，空头减）
pnlUsd = (sizeInTokens × executionPrice) - costBasis
```
动态扩展直接调整执行价格，数学上等价但更直观，且可拆分为三个独立分量。
### 1.3 getDynamicSpread 组成（`PositionPricingUtils.sol:152`）

<tr>

### 1.4 潜在问题
**问题 1：dynamicSpread 为负时截断为 0（L171-173）**
```solidity
if (dynamicSpread <= 0) {
    return (0, balanceWasImproved);
}
```
当 skewImpact 为强负值（大幅改善平衡的订单）时，整体 dynamicSpread 可能为负。截断为 0 意味着用户得到标准价格，符合设计意图（鼓励平衡订单），**不是 Bug**，但需要测试极端情况。
**问题 2：getPriceImpactSpread 指数运算潜在溢出（L192）**
```solidity
LogExpMath.exp(int256(orderSize * priceImpactParameter) / int256(depth))
```
若 `orderSize * priceImpactParameter` 溢出 `int256`（约 5.8×10\^76），exp 会 revert。虽然有 `maxPriceImpactSpread` 上限（L198），但该上限在 exp 之后应用，无法防止溢出。**建议合约工程师检查参数范围**，确保实际配置下不会溢出。
**问题 3：isBalanceWasImproved 仅比较绝对值（L239-242）**
```solidity
return nextImbalance.abs() < currentImbalance.abs();
```
从完全平衡（currentImbalance=0）开始的任何订单都不会改善平衡，该函数返回 false，skewImpact 为正值（增加成本），行为符合逻辑。

### 2.2 行为说明
- `isSizeDeltaUsd=true`：`sizeDelta` 单位为 USD（原有行为）
- `isSizeDeltaUsd=false`：`sizeDelta` 单位为索引 token 数量

### 2.3 已知 Bug（未修复）
**ExecuteOrderUtils.sol L76 — token 模式订单最小手续费比较错误：**
```solidity
// FIXME: use the resolved USD size after token-size orders are converted through execution price.
if (params.order.sizeDelta() >= minOrderSize) {
    executionFee = 0;
}
```
`minOrderSize` 单位为 USD（从 `executionFeeSubsidizeKey` 读取），但 token 模式下 `sizeDelta()` 单位为 token 数量。对于 ETH（\~2000 USD/token），token 数量远小于 USD 值，导致 token 模式的大订单被错误地收取执行费。
**严重性：中等**。仅影响手续费补贴逻辑，不影响订单正确执行，但会导致 token 模式用户多付 gas。建议优先修复。

## 3. LP Vault NAV 时序修复（BUG 修复）

</tr>
<tr>
<td>`src/vault/VaultBase.sol`</td>
<td>新增 `_convertToAssets(shares, nav)` 和 `_convertToShares(assets, nav)` 避免双重 NAV 调用</td>
</tr>

### 3.2 旧 Bug 说明
**deposit() 原有问题：**
```javascript
transferFrom() → [NAV 变化] → convertToShares()  ← 错误：NAV 已含新存入资产
```
资产转入后 NAV 增加，导致 shares 被少分配（新存入的资金参与了分母）。
**修复后：**
```solidity
shares = _convertToShares(assets, nav());  // 先按当前 NAV 计算 shares
IERC20(asset).safeTransferFrom(...);       // 再转账（LPVault.sol:189-191）
```
**claimWithdrawRequest() 原有问题：**
多请求时每次单独调用 `nav()`，若批量 claim 期间 NAV 发生变化（理论上在非 reentrancy 场景下不变，但代码健壮性差），结果不一致。
**修复后（L248-255）：**
```solidity
uint256 currentNav = nav();  // 一次读取
for (...) { shares += _claimWithdrawRequest(..., currentNav); }
assets = _convertToAssets(shares, currentNav);  // 统一转换
```
### 3.3 修复评估
**修复正确**。但需注意 `_claimWithdrawRequest` 的返回值已从返回 assets 改为返回 shares，任何外部调用者需适配（当前仅 LPVault 内部调用，无外部影响）。

### 4.3 BUG-017：资金费率 token 数量计算精度
**旧代码：** `getFundingAmount` 除以 `Precision.FLOAT_PRECISION_SQRT`（一个常量），无法正确将 USD 值转换为 token 数量。
**修复后（L812-816）：**
```solidity
uint256 price = roundUpMagnitude ? collateralTokenPrice.min : collateralTokenPrice.max;
return Precision.mulDiv(
    positionSizeInTokens, fundingDiffFactor, Precision.FLOAT_PRECISION * price, roundUpMagnitude
);
```
转换路径：`fundingFeeUsd / price = fundingFeeInToken`，正确。四舍五入方向也正确（付款方向上取整，收款方向下取整）。**修复正确**。

## 5. 抵押品/PnL 计算修复（BUG-003）
### 5.1 变更文件
`src/position/DecreasePositionCollateralUtils.sol`（核心三阶段修复）
### 5.2 旧 Bug 说明
旧代码提前将负 PnL 从 positionVault 转走，但此时 remaining collateral 尚未完整处理，可能导致 vault 余额为负或转账失败。
### 5.3 新三阶段处理逻辑（L\~160-260）
```javascript
阶段 1：支付资金费率（payFundingFees）
阶段 2：结算 PnL（正 PnL 从 lpVault 转入；负 PnL 从 positionVault 转出至 lpVault）
阶段 3：支付交易手续费（payForCost）→ feeAmountForPool 转至 vault
```
每个阶段都有 `remainingCostUsd > 0` 的提前退出逻辑（handleEarlyReturn），确保资金不足时不会 panic。
### 5.4 潜在问题
**正 PnL 的 token 转换精度（L\~170）：**
```solidity
pnlToken = pnlUsd / indexTokenPrice.max
```
使用 `.max` 价格（最保守方向）。若索引 token 价格波动，用户实际收到的 token 数量略低于名义 pnl 价值，差异在正常市场条件下可忽略不计。**不是 Bug**，是有意的保守计算。

## 8. Reader 新接口（ExecutionPriceResult）
### 8.1 变更文件
`src/reader/ReaderPricingUtils.sol`
### 8.2 新 struct
```solidity
struct ExecutionPriceResult {
    uint256 sizeDeltaUsd;           // 最终 USD 大小（含 token 转换）
    uint256 sizeDeltaInTokens;      // token 数量
    uint256 dynamicSpread;          // 动态扩展（basis points）
    uint256 executionPrice;         // 最终执行价格
    bool    balanceWasImproved;     // 是否改善了市场平衡
}
```
前端可通过此接口预计算执行价格和 dynamicSpread，用于显示 "price impact" 等 UI 信息。

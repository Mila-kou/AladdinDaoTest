# FX100 业务测试总览（面向业务评审）
**日期**: 2026-07-30
**这份文档是什么**：用业务语言总结"我们已经验证过哪些业务场景"，方便业务人员评审测试覆盖是否完整、需要补充什么，**不要求你去看代码或测试函数名**。
**这份文档不是什么**：不是逐条测试用例清单（那份技术版在 [`TEST_CATALOG.md`](TEST_CATALOG.md) 和[可搜索交互网页](https://fx100-test-ledger.vercel.app/)，给工程师/审计用）。本文档以端到端（E2E，即完整走一遍真实用户操作）测试为主，集成测试作为补充，**同一个业务场景如果 E2E 和集成测试都测过，这里只出现一次，不重复列**。如果想看每个业务点下面具体测了哪些数值场景，看配套的 [`BUSINESS_TEST_CASES.md`](BUSINESS_TEST_CASES.md)（同样是业务语言，颗粒度精确到每条用例的具体数字）。
**怎么用这份文档**：按业务模块往下看，每个模块下是一张"已验证场景"表和一段"已知缺口/待评估"提示。评审时如果觉得某个场景描述不够、担心还有没覆盖到的情况，直接在 Notion 对应行留评论或勾选即可，我们会据此补充测试用例，然后回来更新这份文档——这是一个持续滚动完善的过程，不是一次性验收。
---
## 零、先说清楚：我们现在最大的缺口是什么
在看"已经测了什么"之前，先说清楚"还完全没测什么"——这两类目前完全没有，需要业务判断优先级、决定要不要投入：
1. **极端市场行情模拟**：目前的测试覆盖的是"价格涨跌 X%""崩盘""脱锚到 Y 价"这类**单点、可预期**的行情冲击，但没有覆盖：
- 闪崩后**大量仓位同时触发清算**的"踩踏"场景（清算引发价格进一步冲击、进而引发更多清算的连锁反应）
- Oracle **连续多次故障**叠加交易高峰（喂价刚恢复就又故障、恢复窗口内订单堆积）
- 多个风控参数（点差、skew、资金费、清算阈值）在**同一时刻都被推到最坏值**的复合极端场景
1. **大规模压测/并发**：目前测试基本是"1-2 个交易者、1-2 个市场"的规模，没有覆盖：
- 大量交易者、大量挂单**同时**下单/成交/取消时系统是否还能正确处理（不止是"对不对"，还有"扛不扛得住、gas 会不会爆"）
- 大量已上线市场（比如 20+ 个）同时运作时的整体性能（`RiskControl.int.t.sol` 里有一条 gas 基准测试测到 20 个市场，但只测了只读查询的 gas，不是真实并发压测）
- 长期（数月级）运营中资金费持续累积、多次参数调整叠加后的复合效应（目前多为几天到 30 天量级的场景）
1. 除此之外还有一些较小的缺口，会标注在对应模块下面。
**建议**：业务先判断这两类缺口的优先级——是否要在正式上量前做，还是接受"先上线、边观察边补"。确定优先级后我们据此规划下一批测试。

## 一、开仓与仓位管理
覆盖"交易者怎么开仓、加仓、平仓，钱和持仓数字是否分毫不差"这一最基础的业务链路。

| 已验证的业务场景 | 验证要点 |
|---|---|
| 多头/空头开仓，价格上涨/下跌后平仓 | 盈亏结算精确到 USD 分位，LP 与交易者之间资金零和转移 |
| 同价加仓、部分平仓（25%/50%）、连续多步操作 | 持仓规模、抵押品按比例精确增减，多步操作后不产生累积误差 |
| 用"token 数量"下单（而非 USD 金额）开仓/部分平仓 | 两种下单方式换算结果完全一致，不会因下单方式不同产生体验/记账差异 |
| 空头部分平仓（历史上出过卡单问题的场景） | 专项回归：空头部分平仓在零/有资金费、高杠杆等条件下均正常完成，不再卡单 |
| 多个交易者同时在同一市场开多、开空 | 各自资金流独立零和，不会互相污染；多空对称持仓时 LP 净敞口趋近于零 |
| ETH、WBTC 等多个市场同时有持仓 | 各市场持仓/持仓量互相隔离，平掉一个市场不影响另一个市场；两个市场同时盈利时 LP 精确承担两笔盈利之和；一盈一亏时 LP 净敞口被部分对冲而非简单相加 |
| 手续费率/分账比例被治理调整 | 不同费率下手续费金额精确按比例缩放，分账比例调整后 LP 与"可领取"账本精确对应 |
| 美元计价模式下"几乎全平仓"（比总仓位只少 1 wei） | 换算 token 数量的取整不会让 token 侧提前清零而美元侧仍有账面残余——系统自动识别并归一化为真正的全平仓 |

**已知缺口/待评估**：
- 没有覆盖"同一交易者在多个市场同时持有大量仓位"的复合场景（目前多市场测试是单一持仓为主）。
- 没有模糊测试大范围随机金额/杠杆组合下是否始终零和——目前是若干组预设好的具体数值场景。

## 二、杠杆与保证金管理
覆盖"能加多大杠杆、保证金能不能随便取"这两条直接关系资金安全边际的规则。

| 已验证的业务场景 | 验证要点 |
|---|---|
| 用户尝试开到协议允许的最高杠杆（100倍） | 精确验证抵押品是否够用的两道校验门（含开仓费、双向点差摩擦），恰好不够/恰好够用的边界都被钉住到分/wei 级别 |
| 真实订单簿深度参数下的"推荐抵押品"是否真的够用 | 发现并验证了一个真实落差：简化模型算出的推荐抵押品在真实深度冲击下可能仍不够，为前端提示文案提供依据 |
| 用户不平仓、单独提取部分保证金 | 分批提取后仓位维持存续；提取全部保证金（相当于抽干仓位）会被拒绝；提取的资金确实到账用户钱包 |
| 最低抵押金额（美元门槛）限制 | 低于门槛的开仓/提取会被拒绝并全额退款，恰好等于门槛可以通过 |
| 平仓时抵押品扣减顺序（资金费→盈亏→手续费） | 各阶段扣减顺序正确，某一阶段抵押品耗尽会正确转入清算流程而非继续错误扣减 |
| 部分平仓后剩余抵押品跌破最低门槛（v0.3.2 已确认设计，`docs/bugs/BUGS.md` R7-B02） | 用户请求的是普通部分平仓（如 30%），但执行后剩余抵押品美元价值会跌破最低门槛时，合约不会拒绝也不会按请求比例执行，而是**静默把整个仓位平掉**——这是刻意设计（避免留下抵押品不足、随时可能被清算的"僵尸仓位"），2026-08-06 已用测试固化该行为；前端下单前宜提前预判并提示用户 |

**已知缺口/待评估**：
- 没有覆盖"用户在接近最高杠杆时连续小额加仓，一步步逼近边界"这种渐进式试探场景。
- 🟠 **新发现：开仓保证金门槛与清算保证金门槛互相独立，缺乏交叉校验**：两个参数各自都有自己的上限检查，但彼此之间没有任何比较——如果误配置成"清算门槛比开仓门槛更高"，一笔刚成功开仓、价格完全没变的仓位会立即可被清算；同时开仓门槛本身还可以被设为 0（且理论上的"按持仓规模动态提高门槛"兜底机制实际上从未真正启用过），组合起来可以开出远超设计杠杆上限的仓位。两者均已用测试证实（外部审计 Zenith #19/#25），见 `docs/bugs/BUGS.md` R8-B19/R8-B25，待修复。

## 三、清算与风险处置（含自动减仓 ADL）
这是资金安全里风险最集中的一类场景——覆盖"什么时候该清算、清算怎么结算、极端行情下怎么保护 LP 池"。**这是全仓库测试覆盖最深的模块**（`LiquidationBoundary.t.sol` 单个文件就有 26 个用例，专门用来钉住各种边界情形）。

| 已验证的业务场景 | 验证要点 |
|---|---|
| 价格崩盘触发清算 | 交易者收到剩余抵押品，LP 精确吸收亏损，四方资金零和 |
| 纯资金费长期侵蚀抵押品触发清算（价格不变） | 即使价格完全没变，长期持仓的资金费成本也能独立触发清算——这是容易被忽视但真实存在的路径 |
| 新开仓的"保护期"（一段时间内不会被清算） | 保护期精确到秒的边界（最后一秒仍受保护、到期立刻可清算）；保护期内用户仍可正常加减仓，但不能被用来延长/缩短保护期本身；不同推荐人等级对应不同保护期时长 |
| 清算区内的操作限制 | 清算区内允许全平仓，但**不允许部分平仓**（防止边平边保留危险仓位）；追加保证金到刚好越过阈值可以自救成功 |
| "危险区"（比清算区宽松但已进入警戒）内的操作规则 | 危险区允许追加保证金/达到最小比例的部分平仓/加仓，但比例不足会被拒绝——比清算区规则更细致的一档 |
| 清算手续费的分配 | 清算费按比例拆分给 LP 与手续费接收方，即使费率很高（如20%，超过剩余抵押品）清算流程依然能正确完成 |
| 价格冲击、资金费同时叠加恶化仓位（复合场景） | 资金费+崩盘+价格冲击三重叠加下，验证多大的追加保证金才能真正完成救援 |
| 清算判定要把"应收正向资金费"计入抵押品 | 修复过的真实缺陷回归：空头应收资金费必须算进清算判定，否则会被提前误判为可清算 |
| 自动减仓（ADL）：交易者浮盈过大威胁 LP 池时强制部分/全部减仓 | 触发阈值（全局净兑付率超限）精确生效；部分执行后仓位与账本精确减半；全部执行后状态机正确复位；多空双向对称验证；四方资金变动之和精确为零 |
| LP 池整体偿付能力监控 | 全局净兑付比率跨市场正确累加；比率超限时 LP **提款**会被拦截（但存款和"发起提款请求"不受影响，避免系统最需要资金时反而挡住新钱进来），比率回落后自动解除无需人工干预 |
| LP 池亏损封顶（防止单边行情打穿净值） | 交易者浮盈计入 LP 池亏损时会被封顶（不封顶亏损端），即使 1000% 的极端浮盈也严格封顶生效 |

**已知缺口/待评估**：
- **多仓位连锁清算（踩踏）没有覆盖**：目前每个清算场景基本是单一仓位，没有验证"一笔清算导致的价格冲击/资金费变化，引发第二、第三笔仓位接连被清算"的连锁反应。
- **ADL 与清算同时大规模触发的场景没有覆盖**：极端行情下可能同时有大量仓位需要 ADL、又有大量仓位需要清算，两套机制交织运作时的整体行为未验证。
- 🟠 **ADL 对"新开仓保护期"完全免疫，与清算路径不对称**：清算对保护期内的仓位有硬性 on-chain 兜底（`isPositionLiquidatable` 校验不通过会 revert），但 ADL 执行路径全程没有检查保护期字段，2026-08-06 已用测试证实——保护期内的仓位一样会被 ADL 强制减仓。已登记为待修复项（见 `docs/bugs/BUGS.md` R7-B01，P1，待产品/工程决策是否需要给 ADL 补一道保护期豁免）。
- 🟡 **新发现：浮盈封顶比例设为 0% 时封顶机制完全失效**：模块表格里验证过的"浮盈封顶"机制（如 10%/20%/5% 等档位都严格生效），唯独在封顶比例被设成 0% 这个特殊值时会失效——0% 本该表示"浮盈全部封顶到 0"，实测却几乎按未封顶的全额支付。当前全部 24 个已上线市场该参数都配置为正常值，暂无实际影响，但底层逻辑缺陷是真实的（外部审计 Zenith #20），见 `docs/bugs/BUGS.md` R8-B20，待修复。
- 保护期/危险区的规则已经覆盖得很细，但都是逐条独立验证，没有验证"同一仓位连续经历保护期→危险区→清算区"的完整状态迁移全过程。
- **清算/ADL 共用的定价公式，架构改造已经落地实施（不再是"评估中"）**（详见模块九"动态价差与价格冲击"）：现在这条公式有一条"成交价不能优于市场公允价"的底线，清算/ADL 因此天然安全；这条底线在改造后**继续对清算/ADL 生效不变**（新方案明确要求判定/执行两条路径都保持 floor-at-0、不给 rebate），只有普通开平仓允许价格优于公允价——2026-08-03 已核对 `release/v0.3.2` 的实施代码与落地方案逐条一致。清算/ADL 路径的正向上限（`maxDynamicSpread`）沿用了普通交易那份配置，不是完全独立豁免——**团队已拍板保留这个现状（与其他交易保持一致）**，不是遗留问题，详见 `docs/audit/2026-08-03-v032-audit-fix-verification.md` §3.3。本仓库测试分支的 `src/` 基线尚未同步到 v0.3.2，同步后需要补齐清算/ADL 隔离场景的回归测试。

## 四、资金费（Funding Fee）结算
覆盖多空双方按持仓量失衡程度互相支付的资金费机制。

| 已验证的业务场景 | 验证要点 |
|---|---|
| 持仓量失衡时，多的一方向少的一方支付资金费 | 支付方向、费率计算公式正确；持仓规模翻倍资金费同比例翻倍（线性关系） |
| 多空持仓量平衡时 | 双方资金费率近似相等，不存在无理由的资金费方向性偏移 |
| 极端失衡下的费率上下限 | 无论失衡多极端，费率始终被上下限钳制，不会失控 |
| 资金费与价格盈亏组合结算 | 持仓的最终盈亏是"价格变动"和"资金费成本"两者叠加的结果，两者组合计算正确，长期持仓（15-30天）资金费侵蚀收益的方向和幅度正确 |
| 资金费的记账去向（v0.3.0 改造后） | 交易者应付的资金费不再直接进 LP 池，而是记入独立的"可领取"账本，这个改造已验证生效——LP 池净值不受资金费直接影响 |
| 资金费如何影响 LP 最终能取回的钱 | 有交易活动时 LP 赎回金额与"无交易基线"对比，资金费累积不改变 LP 赎回金额（因为已改路由，不再直接进池） |

**已知缺口/待评估**：
- 覆盖的都是几天到一个月量级的持仓周期，**没有覆盖数月甚至更长周期的资金费累积**，长周期下的舍入误差是否会累积放大未验证。
- 没有覆盖资金费率参数（floor/base/min/max）被治理**临时调整**时，对已有持仓资金费结算的影响。
- 🟠 **新发现：风控预言机推送的资金费参数更新实际不生效**：自动化风控预言机（Chaos Labs）推送资金费调整时走的是错误的存储通道，写入本身不报错，但资金费引擎实际读取的是另一个完全独立的位置——等于预言机的自动化响应被静默吞掉，风险事件发生时资金费拿不到应有的自动调整（外部审计 Zenith #1），见 `docs/bugs/BUGS.md` R8-B01，待修复。
- 🟠 **新发现：生产环境实际使用的资金费配置通道没有任何数值校验**：不论是较低权限的运维角色还是最高权限的配置角色，通过这条通道设置资金费上下限时，系统都不检查数值是否离谱、上下限顺序是否颠倒——一次误操作就可能让全市场资金费失控（外部审计 Zenith #16/#23），见 `docs/bugs/BUGS.md` R8-B16/R8-B23，待修复。
- 🔴 **新发现（Critical）：交易者付给 LP 方向的资金费，LP 实际只拿到 40%**：设计意图是这部分资金费 100% 结算给 LP，但走完实际的分账链路后，另外 60% 被当作跟开平仓手续费一样的协议收入分给了国库和保险库——这是持续性、结构性的 LP 价值流失，不需要任何攻击行为，正常交易就会持续发生（外部审计 Zenith #30，本轮严重性最高），见 `docs/bugs/BUGS.md` R8-B30，待修复，优先级最高。

## 五、手续费、执行费补贴与推荐返佣
覆盖交易手续费怎么收、怎么分给协议/LP/推荐人，以及小额订单的 gas 补贴机制。

| 已验证的业务场景 | 验证要点 |
|---|---|
| 开仓/平仓手续费收取与分账比例 | 不同费率下金额精确按比例缩放；LP 与"协议可领取"两个去向的分账比例（0%/50%/100% 等档位）精确生效 |
| 手续费从产生到最终提现的完整流水 | "记账→从仓位金库转到手续费处理合约→再提现给最终接收方"三段式流水线，每一段资金转移都精确核对，权限控制（谁能提现）正确生效 |
| 手续费三方分账（协议金库/保险基金/LP，`RevenuePool` 分账器） | 按约定比例（如 40/30/20% + 10% 余数）精确分给三方 + 生态余数，多笔累积一次性提现，权限门控正确 |
| 推荐返佣：交易者绑定推荐码后，推荐人从手续费中抽成 | 按等级比例精确计算返佣金额；交易者的专属折扣会反向减少推荐人的返佣（折扣分给了交易者）；未绑推荐码不产生任何返佣 |
| 手续费费率分层：引导交易者向"改善市场失衡"方向下单 | 改善失衡方向享受更低费率，方向判断正确（不会弄反） |
| 限价/触发单成交时的手续费与盈亏结算 | 限价单按"触发时刻的价格"而非"下单时刻的价格"计算手续费与盈亏，避免用旧价格套利或被错误结算 |
| 小额订单的执行费（gas）豁免 | 达到豁免阈值的订单可以零 gas 代币创建并执行；豁免阈值如果部署时忘记配置会导致"全场免费"（已知运维风险点，测试专门覆盖了这个容易被忽视的坑，确保能被立刻发现而不是悄悄放行） |
| 多个市场独立配置手续费/点差参数 | 不同市场可以配不同费率/点差，互不覆盖 |

**已知缺口/待评估**：
- 推荐返佣的"实际领取"（`claimAffiliateRewards`）目前受一个已知合约 bug 阻塞（详见 `docs/bugs/BUGS.md` R2-B02）。**2026-08-03 更新**：该 bug 已在 `release/v0.3.2` 修复（`initItems(2)`→`initItems(3)`），但本仓库测试分支的 `src/` 基线仍是 v0.3.1，尚未同步——相关测试仍暂时标记跳过，等下次 `src/` 同步 v0.3.2 后再补上这段回归、删除 skip。
- 手续费三方分账目前是新落地的机制，还没有和"极端行情下大量清算/ADL 同时发生"的场景组合测试过。
- 🔴 **新发现（Critical）：本节的三方分账比例被不加区分地套用到了资金费上**：这里验证的"协议金库/保险基金/LP 三方分账"设计上是给开平仓手续费、清算费用的协议收入分账，但实测发现资金费（模块四）也被套用了完全相同的分账比例——资金费本该 100% 归还 LP，结果 LP 只拿到 40%（外部审计 Zenith #30），详见模块四"已知缺口"及 `docs/bugs/BUGS.md` R8-B30，待修复，优先级最高。

## 六、LP 存取款与资金池（NAV / 份额）
覆盖 LP（流动性提供者）存钱进池子、池子净值随交易盈亏变化、到期取钱这一整条链路。

| 已验证的业务场景 | 验证要点 |
|---|---|
| LP 存款、无任何交易活动 | 到期精确领回同等金额（净值全程不变） |
| 交易者盈利/亏损如何影响 LP 能拿回的钱 | 交易者盈利→LP 净值下跌→LP 领取金额减少；交易者亏损→LP 净值上涨→LP 领取金额增加（"此消彼长"的核心承诺被验证成立） |
| 多个 LP 按份额比例公平分摊盈亏 | 两个等额 LP 按持股比例精确均摊损失，不存在谁多吃谁少吃 |
| LP 发起提款到实际到账之间，池子净值仍在变化 | 结算用"实际领取时点"的净值，而不是"发起提款时点"的净值（份额锁定期内仍参与损益，这是容易出错的边界，已验证正确） |
| 提款的时间锁与周期（epoch）机制 | 未到解锁时间/周期未结束时提款会被拒绝，到期后能精确到账；批量领取多笔不同时间发起的提款请求金额精确加总 |
| 全局风险指标超限时的提款限制 | 只拦截"实际取现"，不拦截"存款"和"发起提款请求"（避免系统最需要资金时反而挡住新钱），指标回落后自动解除 |
| 策略托管资产计入净值 | LP 池子把资金托管给策略合约的部分也正确计入总资产与净值计算 |

**已知缺口/待评估**：
- 没有覆盖大量 LP 同时在同一个 epoch 内密集存取款的规模化场景。
- 没有覆盖 LP 池净值极端下跌（比如接近于零）时的边界行为。

## 七、订单类型与触发单（限价 / 止盈止损 / 改单 / 取消）
覆盖除"市价立即成交"之外的各类挂单机制。

| 已验证的业务场景 | 验证要点 |
|---|---|
| 限价开仓（抄底/追涨）、止盈、止损单 | 价格没到目标位前必须阻塞、不能提前成交；到达目标位后按"触发时刻的价格"而非"下单时刻的价格"成交，多空双方向都验证 |
| 开仓时同时附带 TP/SL（Bracket Order） | 一边触发后另一边自动取消，不会变成"孤儿单"继续存在甚至误触发再平一次仓；双边都设置自动取消时，触发顺序不会误取消自己 |
| 限价/止盈止损单的部分平仓 | 按比例正确结算剩余仓位，入场价格不受影响 |
| 用户主动改单（改价格/改数量） | 改单后旧的触发条件立即失效；非订单所有者不能改别人的单；改价后如果恰好落入当前价格区间会立即成交 |
| 用户/协议主动取消挂单 | 限价单可随时取消；市价单需等待一小段时间防止抢跑套利；平仓后遗留的止盈止损挂单会被自动清理，不会变成"孤儿订单" |
| 回调通知机制（供接入协议的外部合约使用） | 订单成交/取消时外部合约能收到恰好一次、key 正确的通知；回调本身出错不会影响订单执行结果 |

**已知缺口/待评估**：
- 限价单大量堆积在同一价位、价格触及时集中成交的场景没有覆盖（属于"大规模压测"缺口的一部分，见第零节）。

## 八、Oracle 与价格风控
覆盖协议赖以定价的预言机喂价，在各种故障/异常场景下是否"宁可暂停也不用错价结算"。

| 已验证的业务场景 | 验证要点 |
|---|---|
| 喂价源停更（心跳过期） | 开仓/清算/ADL 都被正确冻结，不会继续用旧价结算；故障恢复后挂单全部正常执行 |
| 一次真实故障应急演练固化为可重复的运维手册 | 运维通过临时调宽心跳容忍度让系统恢复的操作流程，已验证有效并保留为可重复执行的 runbook |
| 价格来源（Provider）切换 | 首次启用无需延迟（不影响正常上线流程），重复切换需要强制延迟（防止攻击瞬间紧急换源），禁止切到未启用的来源 |
| 极端偏离参考价的价格 | 明显偏离市场的价格会被拒绝；边界值（恰好在允许范围内/刚超出）精确验证 |
| 次级价格来源（备用喂价）的优先级与降级 | 有专用备用源时优先取用；备用源过期或缺失时的降级回退路径不会导致系统卡死 |
| L2 Sequencer（排序器）异常 | Sequencer 宕机时拒绝原子操作；恢复后有一段观察期同样拒绝，观察期过后才恢复正常 |
| `refreshLatestRecordedPrices` 权限变化（v0.3.1） | 该运维接口从"仅限定角色可调"改为任何人都可调用刷新价格缓存，已验证新权限模型下价格校验本身不受影响、原角色仍可正常使用 |

**已知缺口/待评估**：
- 见第零节"极端市场行情模拟"——**连续多次故障叠加**、**故障恢复瞬间的订单洪峰**尚未覆盖。

## 九、动态价差与价格冲击（定价模型）
覆盖每笔交易实际成交价是怎么算出来的——这决定了交易者到底按什么价格成交。

| 已验证的业务场景 | 验证要点 |
|---|---|
| 开仓价格上浮、平仓价格下沉（点差保护 LP） | 四个方向（多开/空开/多平/空平）的加减符号与取整方式都验证正确，不会出现系统性偏差 |
| 订单规模越大，成交价越差（价格冲击） | 大单和小单不会拿到相同的成交价，市场深度模型确实生效，避免大户无成本反复进出侵蚀 LP |
| 改善市场失衡方向的一方享受更优价格 | 反向操作（拉回平衡）的一方确实拿到比顺势加剧失衡更好的成交价，引导多空自我平衡的经济设计生效 |
| 价格冲击/失衡冲击的封顶保护 | 即使构造出理论上极端的冲击值，也会被上限参数封顶，不会算出不合理的天价滑点 |
| 不同市场独立配置价差/冲击参数 | 每个市场可以按自己的流动性深度配不同的冲击系数，互不影响；新市场忘记配置冲击参数时会优雅降级（只剩基础点差），不会导致交易瘫痪 |
| USD 计价单与 token 计价单的定价一致性 | 两种下单方式共用同一套定价公式，结果完全等价 |
| 前端预估价格与链上实际成交价一致 | reader 给用户看的预估执行价与实际链上成交价误差在 1 wei 以内，不会出现"预估一个价、成交另一个价"的体验落差 |
| 连续开仓-加仓-部分平仓-全平仓的完整持仓周期 | 每一步的执行价方向、点差区间、前端预估与链上状态全程保持一致，没有跨步骤的状态污染 |

**已知缺口/待评估**：
- 目前对价格冲击公式本身有一处已知的数学边界问题（`exp` 指数计算在极端参数下会直接报错而不是被优雅封顶），已经在近期的审计核对中发现并记录为待修复项（见 `docs/bugs/BUGS.md` R5-B02）。**2026-08-03 更新**：该问题已在 `release/v0.3.2` 修复（`exp` 调用前新增超界判断，超界直接封顶而不 revert），本仓库测试分支的 `src/` 基线尚未同步到 v0.3.2，正向回归测试待下次同步后补上。
- **动态价差的安全底线改造已经落地实施（不再是"评估中"）**：现在的定价公式保证成交价"最多免费成交，绝不会优于市场公允价"，这条底线本身测试覆盖充分（含清算/自动减仓场景下同样生效的验证）。此前团队评估的类似 Avantis 的改造方案——允许在特定条件下（交易帮助市场恢复多空平衡时）成交价优于公允价，作为额外激励——**已在 `release/v0.3.2` 实施**（`4a40477`/`c8b84e3`/`7d639c9` 三个 commit），2026-08-03 已核对：新增的 9 个测试用例全部通过，实现与落地方案（`docs/analysis/pricing/impl_spec_negative_dynamic_spread.md`）逐条一致，含"判定/执行继续 floor-at-0（不给 rebate）、只有普通开平仓允许负 spread"这条关键安全边界。清算/ADL 路径只清零了负向下限，沿用了普通交易的正向上限（`maxDynamicSpread`）——**团队已拍板保留这个现状（与其他交易保持一致），不再单独放开**，完整细节见 `docs/audit/2026-08-03-v032-audit-fix-verification.md` §3.3。本仓库测试分支的 `src/` 基线尚未同步到 v0.3.2，`BUSINESS_TEST_CASES.md` 模块九列出的测试缺口清单待同步后逐条补齐（多数已随实施 commit 自带测试，同步后可直接引用，见该文档模块九末尾说明）。

## 十、抵押品价格精度（USDC 价格波动/脱锚）
覆盖一个容易被忽视的假设——"USDC 恒等于 1 美元"——如果这个假设被打破会发生什么。

| 已验证的业务场景 | 验证要点 |
|---|---|
| USDC 价格偏离 1 美元时的抵押品估值、盈亏兑付、手续费扣款 | 三个环节分别使用了正确的价格口径（估值用偏保守的价格、盈亏兑付用偏优的价格、手续费扣款用偏保守的价格），不会全部误用同一个价格 |
| 仅 USDC 单独脱锚（标的资产价格不变）也能独立触发清算 | 验证清算判定不只盯着交易标的的价格，USDC 自身的价格变化同样纳入风险判断 |
| 极小价格偏差下的边界判断 | 用 0.01%~0.02% 级别的极小偏差反复验证"严格小于"而非"小于等于"的精确边界，确保没有失之毫厘的判断错误 |

**已知缺口/待评估**：
- 目前验证的 USDC 偏离幅度多在 1-60% 区间（含模拟脱锚到 $0.40 的场景），但都是"价格线性偏离"，**没有覆盖 USDC 价格剧烈震荡（快速涨跌反复）的场景**。

## 十一、Gasless（免手续费代付）与子账户委托
覆盖用户不需要持有 gas 代币就能交易，以及授权他人代为操作账户的场景。

| 已验证的业务场景 | 验证要点 |
|---|---|
| Relayer（中继方）代付执行费，事后从用户 USDC 报销 | 代付-报销-多余部分退款整套资金闭环分毫不差；relayer 代付上限生效，超限会被拒绝 |
| 签名安全边界 | 签名过期、使用错误私钥签名、链 ID 不匹配等场景均被正确拒绝，防止伪造或跨链重放 |
| 批量操作（一次提交多笔订单） | 批量创建/取消订单正确落账，只收取一次中继费 |
| 子账户委托：授权他人代表自己操作 | 授权次数上限生效（用尽后拒绝新操作）；撤销授权后立即失效；连续多次授权的计数正确递增；持仓归属始终是主账户而非子账户 |
| 子账户 + Gasless 组合场景 | 两套机制叠加时（谁能代表谁、代多久、代多少次）四类治理性约束仍然正确生效 |
| 命名多设备槽位（v0.3.2 新增，"Named Agent"设计） | 最多 4 台命名设备各自独立授权；同名设备重新登记覆盖旧地址、不留孤儿；槽位用满后拒绝新设备；同一地址不能借不同设备名重复登记；按地址撤销授权 vs 按设备名彻底删除设备两种操作语义不同（前者保留设备列表方便日后重新授权，后者才真正腾出槽位容量），已经 2026-08-06 工程师确认为刻意设计 |

**已知缺口/待评估**：
- 已知有 4 个签名重放/权限相关的边界用例目前标记为"待合约侧确认"（vm.skip，详见测试账本），不是没测，而是等合约工程师确认预期行为后再转为正式断言。
- 没有覆盖大量 relayer 同时为大量用户代付的规模化场景。
- 🔴 **新发现：子账户可以自己给自己当中继人，反复抬价抽取主账户资金**：中继费机制没有对"子账户"身份做专属的费用上限，子账户可以让自己直接充当中继方、故意抬高交易的 gas 出价，把可收取的中继费一路推高，反复操作即可把主账户的 USDC 逐步转走——突破了"子账户只能交易、不能挪动资金"的设计承诺（外部审计 Zenith #2），见 `docs/bugs/BUGS.md` R8-B02，待修复；部署配置里有一个跟子账户身份无关的全局兜底参数，如果运维记得配置会大幅削弱攻击效果，但不能替代专属修复。

## 十二、如何参与评审 / 如何让这份文档持续更新
1. **评审方式**：逐个模块看"已验证的业务场景"表，判断是否已经覆盖了你认为重要的情形；重点看每个模块下的"已知缺口/待评估"，以及第零节的系统性缺口，判断优先级。
2. **怎么提反馈**：在 Notion 对应文档里直接评论或勾选你觉得需要补充的场景（越具体越好，比如"XX 市场行情下 YY 操作会怎样"），不需要懂代码。
3. **反馈之后会发生什么**：我们会根据反馈评估现有代码是否已经处理了这个场景（可能只是没写测试，也可能是代码本身没考虑到），针对性补充测试用例（如果发现是代码没考虑到的真实问题，会同步登记到 bug 跟踪文档），然后更新这份文档里对应模块的表格。
4. **这是一个滚动过程**：不追求一次性覆盖所有场景，目标是让业务对"测试覆盖到哪儿了"始终有清晰、及时的认知，逐步把缺口补上。

## 17. 仓位全字段与保证金口径

> 语义与列名以需求《FX100 持仓面板数字口径统一规范（Margin / Net Value / Leverage / uPnL / Funding）》2026-07-15 为准；公式体、取整、选价以 v0.3.2 源码为准。两者不一致处逐条记在本版**需求↔实现差异台账**里（台账条目按标题引用，不按序号引用）。注意 §22 差异表目前**尚未收录**本次新查实的四条（Reader funding 预览 ×2 且恒取 `.long` 侧、零 OI 时 `fundingSkewEma` 被清零而 `fundingUpdatedAt` 照刷、LP 现金流触发点由 `updateFundingState` 迁到 `settleFundingFees`、`PositionIncrease/Decrease` 事件字段重排），不要把 §22 当作完整清单。

### 17.1 Position 原始字段

```text
positionKey = keccak256(abi.encode(account, marketIndex, isLong))
```

源码锚点：`Position.sol::getPositionKey`。同一账户、同一市场的 Long 与 Short 使用不同 key，可同时存在。

字段结构：`Position.Props{ Addresses{account}, Numbers{...10 项}, Flags{isLong} }`（`Position.sol::Props/Addresses/Numbers/Flags`），v0.3.2 与 v0.3.1 完全一致，无增删。

| 字段 | 单位 / 精度 | 含义 | 写入锚点 |
| --- | --- | --- | --- |
| `account` | address | 仓位所有者 | `IncreaseOrderUtils.sol::processOrder` |
| `marketIndex` | uint256 | 市场序号（非地址） | 同上 |
| `isLong` | bool | 多空方向 | 同上 |
| `sizeInUsd` | USD × 1e30 | 名义仓位规模 / 开仓成本基数 | `IncreasePositionUtils.sol::increasePosition` |
| `sizeInTokens` | index token 登记 decimals（raw 单位） | 与 index token 注册精度一致，**不是恒定 1e18**；以部署登记 / `TestCode/config/mock-resources.json` 的 index token `decimals` 为准——当前基线三个 fork 的 index token（FXMOCK）均为 **18 位**（同文件里的 `oracle.decimals` 是价格源精度，不是 token 精度） | 同上 |
| `collateralAmount` | collateral token 原生精度 | 已入仓抵押品数量 | 同上 / `DecreasePositionUtils` |
| `negativeFundingFeePerSize` | 累计值（1e30 factor / token） | 该仓位上次结算的**应付** Funding 基准 | `IncreasePositionUtils.sol::increasePosition` |
| `positiveFundingFeePerSize` | 累计值（1e30 factor / token） | 该仓位上次结算的**应收** Funding 基准 | 同上 |
| `increasedAtTime` | unix seconds | 最近加仓时间；**纯存入保证金（sizeDelta=0）也会刷新** | 同上 |
| `decreasedAtTime` | unix seconds | 最近减仓时间 | `DecreasePositionUtils.sol::decreasePosition` |
| `graceStart` | unix seconds | 清算保护起点 | `IncreaseOrderUtils.sol::processOrder` |
| `graceEnd` | unix seconds | 清算保护终点 | 同上 |

两条必须显式断言的分支：

1. **Funding 基准只在新开仓时对齐市场值**：`IncreasePositionUtils.sol::increasePosition` 中 `if (position.sizeInUsd() == 0)` 才把两个 `fundingFeePerSize` 置为市场当前值，因此首次开仓不产生 Funding；已有仓位加仓则走正常结算，事后再把基准刷新到 `fees.funding.latest*FundingFeePerSize`。
2. **grace 只在仓位创建时写一次**：`IncreaseOrderUtils.sol::processOrder` 的 `if (position.account() == address(0))` 分支内才 `setGraceStart(block.timestamp)` / `setGraceEnd(block.timestamp + gracePeriodBase)`，其中
   `gracePeriodBase = liquidationGracePeriodBase[marketIndex] × liquidationGracePeriodTierMultiplier[tier] / 1e18`（`tier` 来自 `referralStorage.referrerTiers(account)`）。**加仓、补保证金、减仓都不重置 grace**。`LiquidationUtils.sol::createLiquidationOrder` 在 `graceEnd > block.timestamp` 时直接 revert `PositionNotLiquidatable`。

### 17.2 Entry Price、Mark Price 与仓位数量

```text
entryPrice = sizeInUsd / sizeInTokens        （Solidity 整数除法向下取整）

displaySizeUsd   = sizeInUsd / 1e30
displaySizeToken = sizeInTokens / 10^(index token decimals)     （当前基线 = 1e18）
```

`entryPrice` 是多次加仓后的加权结果，因为 `sizeInUsd` 与 `sizeInTokens` 都按增量累计（`IncreasePositionUtils.sol::increasePosition`）。它包含实际开仓成交价（含动态点差）影响，不是 Oracle 中间价。合约不存储 `entryPrice` 字段，展示层自行相除。

> **与主文档其它未改写章节的冲突，以本节为准**：§16.5「Token Size = `sizeDeltaInTokens / 1e18`」、§21 速查表的「Size Token 展示 `sizeInTokens / 1e18`｜所有标的统一 18 位」与「`sizeDeltaInTokens`（Token 模式）｜所有标的统一 18 位」仍把 18 位当作全局常量。合约不保证 index token 是 18 位，当前基线恰为 18 位只是登记结果。待那些章节改写时同步。

“Mark Price”必须标注用途，三种口径不可混用：

| 用途 | 选价 | 锚点 |
| --- | --- | --- |
| 行情/展示 uPnL | `midPrice = (min + max) / 2` | `Price.sol::midPrice` |
| 市场级 PnL / 风控（maximize=true） | Long 取 `max`、Short 取 `min` | `Price.sol::pickPriceForPnl` |
| 市场级 PnL / 风控（maximize=false） | Long 取 `min`、Short 取 `max` | 同上 |
| 精确单仓 PnL | Reader 返回的**含点差平仓执行价** | `ReaderPositionUtils.sol::getPositionInfo` → `executionPriceResult.executionPrice` |

精确 PnL 必须用 Reader 的 `basePnlUsd`，不能单独拿 K 线价乘数量。

### 17.3 Margin 字段（链上原值 vs 净额口径）

```text
marginToken = position.collateralAmount                    （链上原始抵押品）

marginUsd
= collateralAmount × collateralTokenPrice.min              （同 PositionUtils.sol::isPositionLiquidatable 的 collateralUsd）

effectiveMarginToken                                       （需求规范的 Margin 列）
= collateralAmount
- negativeFundingFeeAmount
+ positiveFundingFeeAmount

effectiveMarginUsd
= effectiveMarginToken × collateralTokenPrice.min
```

Funding 净额本身（**收 − 付**）见 §19.2 的 `displayFundingToken`，本节不再另起同义符号。方向提醒：**v0.3.1 文档（第 951–952 行）与本次被替换的旧 §17.3 此处的 `pendingFundingNetToken` 写的都是「付 − 收」**（`negativeFundingFeeAmount - positiveFundingFeeAmount`），本版起全文统一为「收 − 付」，与 §19.2 及前端 `liqPriceUtils.ts::getPositionNetFundingUsd`（`positive - negative`）一致。**照两版旧 §17.3 按名取值的脚本一律需要反号**，不要因为「只是 v0.3.1 的老写法」而略过被替换掉的 v0.3.2 旧稿。

选价与取整（`MarketUtils.sol::getFundingAmount`，经 `PositionPricingUtils.sol::getFundingFees` 调用）：

| 分量 | 除数选价 | 取整 | 理由 |
| --- | --- | --- | --- |
| `negativeFundingFeeAmount` | `collateralTokenPrice.min` | **向上**（`roundUpMagnitude=true`） | 应付端不能少扣 |
| `positiveFundingFeeAmount` | `collateralTokenPrice.max` | **向下**（`roundUpMagnitude=false`） | 应收端不能多给 |
| 两者换算成 USD 时 | 一律 `collateralTokenPrice.min` | — | 与 `isPositionLiquidatable` 中 `collateralCostUsd` / `positiveFundingFeeUsd` 同源 |

注意：Token 数量阶段两侧用的是**不同的价格边**（min vs max），换算 USD 阶段才统一到 `.min`。核对脚本不能用同一价格边一次算完。

命名对照（**同一批数在四处的不同名字，核对时必须逐一映射**）：

| 层 | 名称 | 表达式 / 口径 |
| --- | --- | --- |
| 需求规范 §4.1 | `Margin` | 抵押品 + 资金费净额 → 对应本文 `effectiveMarginToken` / `effectiveMarginUsd` |
| 本文档 | `marginToken` / `marginUsd` | 链上原值 `collateralAmount`（§21 速查表 “Margin Token / Margin USD” 同义） |
| 本文档 | `effectiveMarginToken` / `effectiveMarginUsd` | 净额口径，是杠杆分母与 Net Value 的基数 |
| 前端（面板列） | `apps/fx-base-app/src/components/features/trade/_position/liqPriceUtils.ts::getPositionMarginUsd` | `collateralUsd + (pendingPositiveFundingFeesUsd − pendingFundingFeesUsd)` —— 严格等于 `effectiveMarginUsd`，**不含 PnL、不含 borrowing fee** |
| 前端 SDK（杠杆分母） | `packages/sdk/src/utils/positions.ts::getLeverage` 的局部量 | `collateralUsd + (pnl ?? 0) − pendingFundingFeesUsd − pendingBorrowingFeesUsd + pendingPositiveFundingFeesUsd` —— 比上一行多了 `pnl` 与 borrowing fee 两项；**当前基线因 `showPnlInLeverage: false`（传 `pnl = undefined`）且无 borrowing fee 而与上一行同值，这是配置巧合、不是同一公式**，改配置或接入 borrowing fee 后两者会分叉（同文件的 `leverageWithPnl` 恒传 `pnl`，天然是另一个数） |
| 合约 | 无单一字段 | 由 `collateralAmount` 与 `fees.funding.*` 派生 |

页面只显示一个 “Margin” 时按需求取净额口径（= `effectiveMarginUsd`），但文档、脚本与看板必须按上表映射到具体符号；若同屏还要展示未结算前的链上原值，必须另起列名（如 “Collateral (on-chain)”），不得两处都叫 Margin。正 Funding 与负 Funding 要分列保留，避免先相减后丢失方向证据。

负数规则：`effectiveMarginToken` 允许为负（长期重亏付费仓位），展示不钳制；`marginToken`（= `collateralAmount`）是 `uint256`，合约侧无“负 collateralAmount”状态——加仓路径若 `collateralDeltaAmount < 0` 且超过现有抵押品会 revert `InsufficientCollateralAmount`（`IncreasePositionUtils.sol::increasePosition`），减仓路径通过支付瀑布逐级消耗（见 §17.6）。

### 17.4 Position Leverage 与 Margin Ratio

合约不存杠杆字段，只存“最低抵押要求”。

```text
positionLeverage（展示）
= sizeInUsd / effectiveMarginUsd                           （需求 §4.3 的 Margin 即本文 effectiveMargin）

minCollateralUsdForLeverage（合约风控线）
= Precision.applyFactor(sizeInUsd, minCollateralFactor)
= sizeInUsd × minCollateralFactor / 1e30                   （Math.mulDiv，向下取整）

marginRatio（展示；必须写成 1e30 标度的 factor 才能与 minCollateralFactor 直接比）
= Precision.toFactor(remainingCollateralUsd, sizeInUsd)
= remainingCollateralUsd × 1e30 / sizeInUsd                （按绝对值向下取整）
  ← 这里的 remainingCollateralUsd 指合约 equity（本节下方定义）
```

（`remainingCollateralUsd` 是 `int256`；`isPositionLiquidatable` 里 `<= 0` 有独立的早退分支 `(true, "< 0")`，因此展示层算到负 `marginRatio` 时应直接显示清算态而不是比 factor。）

**量纲告警**：`minCollateralFactor` 是 1e30 标度的 DataStore 原始值（与 §11.2 的 `minCollateralUsdForLeverage`、§18.1、§20.2 的 `reserveFactor` 同约定）。若把 `marginRatio` 写成纯比值 `remainingCollateralUsd / sizeInUsd`（量级约 0.005），它与 `minCollateralFactor` 差整整 1e30：直接写 `marginRatio < minCollateralFactor` 会对任何仓位恒成立，且 BigInt 整除下分子分母同为 ×1e30 还会先被截成 0（正撞 §1.3 的取整告警）。要保留纯比值定义，判据必须同步降标度为 `marginRatio < minCollateralFactor / 1e30`。

**核对断言最好完全绕开 marginRatio**：合约原式是整数比较

```text
remainingCollateralUsd < Precision.applyFactor(sizeInUsd, minCollateralFactor)
→ (true, "min collateral for leverage")            （PositionUtils.sol::isPositionLiquidatable）
```

`applyFactor` 走 `Math.mulDiv` 向下取整、`toFactor` 也向下取整，两次截断方向不对称，因此 `toFactor(remainingCollateralUsd, sizeInUsd) < minCollateralFactor` 与链上原式**在边界上恰好差 1 wei**：设 `X = sizeInUsd × minCollateralFactor / 1e30`，当 `X` 除不尽时，在 `remainingCollateralUsd == ⌊X⌋` 这一个点上，比值式判「可清算」而链上原式判「不可清算」；`X` 整除时两者完全一致。按整数原式核对才与链上逐 wei 一致。

`minCollateralFactor` 有**两个取值分支**（`PositionUtils.sol::isPositionLiquidatable`）：

```text
forLiquidation == true  → MarketUtils.getMinCollateralFactorForLiquidation(marketIndex)   清算线
forLiquidation == false → MarketUtils.getMinCollateralFactor(marketIndex)                 操作线
```

调用侧的取值：

| 路径 | `forLiquidation` | `shouldValidateMinCollateralUsd` | 锚点 |
| --- | --- | --- | --- |
| 加仓 / 纯存入保证金 | `sizeDeltaUsd == 0`（纯存入=true，真加仓=false） | true | `IncreasePositionUtils.sol::increasePosition` |
| 减仓 / 提取保证金 | false | false | `DecreasePositionUtils.sol::decreasePosition` |
| Reader 清算查询 | 调用方传入 | 调用方传入 | `Reader.sol::isPositionLiquidatable` |

`remainingCollateralUsd` 取自 `PositionUtils.sol::isPositionLiquidatable`，是**含整仓平仓执行价 PnL 与全部平仓成本**的 equity（见 §18.1），与 §17.3 的 `marginUsd` / `effectiveMarginUsd` 都不是同一个数：

```text
remainingCollateralUsd
= collateralUsd
+ fullClosePnlUsd(执行价)
+ positiveFundingFeeAmount × collateralTokenPrice.min
- totalCostAmount × collateralTokenPrice.min
```

其中 `fees` 由 `getPositionFees` 以 `isLiquidation = false`、`uiFeeReceiver = address(0)` 求得，因此 `totalCostAmount` **既不含清算费也不含 UI 费**——判定线比实际清算结算更宽松一点，两者不可互相代入。

展示约束：

- 持仓杠杆不把未实现 PnL 放入分母，因此不应仅因价格刷新而抖动；Funding 累积、加减抵押品和仓位更新会改变杠杆。
- 当 `effectiveMarginUsd <= 0` 时不得显示负杠杆或 Infinity，应显示风险态并走清算判断。前端两条路径都是按**自己的杠杆分母**判空，不是按本节的合约 equity：面板路径 `liqPriceUtils.ts::getPositionDisplayLeverageBps` 在 `getPositionMarginUsd() <= 0`（= `effectiveMarginUsd`）时返回 `undefined`；SDK `packages/sdk/src/utils/positions.ts::getLeverage` 在其分母（见 §17.3 前端 SDK 行，面板场景 = `effectiveMarginUsd`）`<= 0` 时返回 `undefined`。
- 下单面板的目标杠杆与持仓面板的当前杠杆不是同一字段。

**命名陷阱**：`remainingCollateralUsd` 这个名字在本系统里有**至少五个互不相等的含义**，按名对齐必错：

| 出处 | 含义 | 与本节 equity 的差 |
| --- | --- | --- |
| `PositionUtils.sol::isPositionLiquidatable`（本节） | 含整仓平仓执行价 PnL 与平仓成本的 equity；也是 revert `LiquidatablePosition(string,int256,int256,int256)` 的**第 2 个参数**（第 3、4 个是 `minCollateralUsd` / `minCollateralUsdForLeverage`） | — |
| `PositionUtils.sol::willPositionCollateralBeSufficient` 返回值 | `collateralAmount × collateralTokenPrice.min`（仅在 `realizedPnlUsd < 0` 时再减负已实现 PnL）；**不含费用、不含 Funding、不含未实现 PnL**。加仓路径不足时作为 revert `InsufficientCollateralUsd(int256)` 的**唯一参数**抛出（`IncreasePositionUtils.sol::increasePosition`）；减仓路径同一个返回值改叫 `estimatedRemainingCollateralUsd`，进 §17.7 的订单自动改写 | 少了 PnL、Funding 与全部平仓成本 |
| **SDK 对外字段** `packages/sdk/src/types/positions.ts::PositionInfo.remainingCollateralUsd`（赋值见 `packages/sdk/src/modules/positions/positions.ts:658`） | `collateralUsd − pendingFundingFeesUsd − pendingBorrowingFeesUsd`，**不加正 Funding、不含 PnL** | 少了「整仓平仓 PnL + 正 Funding − 平仓成本」；**与 §17.3 的 `effectiveMarginUsd` 恰好差一个 `pendingPositiveFundingFeesUsd`，不可互换** |
| `packages/sdk/src/utils/positions.ts::getLeverage` 的局部量 | 杠杆分母（面板场景 = `effectiveMarginUsd`） | 少了「整仓平仓 PnL − 平仓成本」 |
| `packages/sdk/src/utils/positions.ts::getLiquidationPrice` 的局部量（`collateralToken ≠ indexToken` 分支） | `collateralUsd + priceImpactDeltaUsd − 待结算费 − closingFeeUsd` | 清算价反解专用，不是任何一列展示值 |

三条落地提醒：

1. **脚本按名从 SDK 读到的是第 3 行那个公开字段**，既不是第 1 行的合约 equity，也不是 `effectiveMarginUsd`。前端 `apps/fx-base-app/src/lib/orders/leverage.ts::getAdjustLeverageCollateralUsd` 的注释明写 “Prefer the SDK's remainingCollateralUsd”，调整杠杆的抵押基数走的正是这一行——拿它去核 Margin 列或杠杆，会稳定偏出一个正 Funding，产生假缺陷。
2. 链上侧的第 1、2 行分别由上表两个 revert 携带出来，`TestCode/src/scenarios/xt-mkt-runner.ts` 的 `CANCEL_REASON_ABI` 就是按这两个签名解码的；链上 / Reader / SDK 三侧同名量必须一次映射到位再比数。
3. 用它做阈值时必须写清是哪一个：**按名对齐会把杠杆不可用的阈值错设在清算 equity 上**，反过来也会把加仓预检的阈值当成清算线。

### 17.5 Unrealized PnL、ROE 与 PnL%

```text
展示口径（需求 §4.4，毛盈亏）：
Long  unrealizedPnlUsd = sizeInTokens × markPrice - sizeInUsd
Short unrealizedPnlUsd = sizeInUsd - sizeInTokens × markPrice

精确口径（Reader，用于断言）：
basePnlUsd = ReaderPositionUtils.getPositionInfo(...).basePnlUsd

roe = unrealizedPnlUsd / roeMarginBasisUsd
```

合约侧整仓 PnL（`PositionUtils.sol::_getPositionPnlUsd`）与展示口径的三处差别，必须逐条对齐后再比数：

1. **价格**：合约用含动态点差的 `executionPrice`（平仓侧），展示用 `markPrice`（中间价）。
2. **PnL cap**：`totalPositionPnl > 0` 时，用 `MarketUtils.getCappedPnl(..., MAX_PNL_FACTOR_FOR_TRADERS)` 对**市场侧总 PnL** 封顶；若 `cappedPoolPnl != poolPnl && cappedPoolPnl > 0 && poolPnl > 0`，单仓 PnL 按 `totalPositionPnl × cappedPoolPnl / poolPnl` 等比缩放（`Precision.mulDiv`，向下取整）。其中 `poolTokenUsd = poolAmount × collateralTokenPrice.min`。展示口径不做 cap。
3. **按比例拆分取整**：`positionPnlUsd = mulDiv(totalPositionPnl, sizeDeltaInTokens, sizeInTokens, roundUpMagnitude = totalPositionPnl < 0)`——**亏损按绝对值向上取整**，盈利向下取整。

`unrealizedPnlUsd` 是纯价格盈亏，不含 Funding、平仓费和动态点差成本。`roeMarginBasisUsd` 在 Position 原始结构中不存在：

- 若产品定义为“初始保证金”，必须由成交历史 / indexer 维护；
- 若产品定义为“当前保证金”，则保证金调整后 ROE 会变化；
- 页面、SDK 和测试必须共用同一定义，禁止以 `collateralAmount` 临时代替但仍标注为“初始保证金”。

### 17.6 Net Value 与 Est. Receive

**Net Value（需求 §4.2 新增列，展示口径）**：

```text
netValueUsd
= effectiveMarginUsd + unrealizedPnlUsd - closePositionFeeUsd

closePositionFeeUsd
= sizeInUsd × positionFeeFactor / 1e30                      （展示按 worst-case 档位取值）
```

`positionFeeFactor` 在合约里是**双档**的（`FX100Keys.sol::positionFeeFactorKey(marketIndex, balanceWasImproved)`）：`PositionPricingUtils.sol::getPositionFeesAfterReferral` 按 `balanceWasImproved` 选档，而 `balanceWasImproved` 只有在算出动态点差之后才知道（`PositionPricingUtils.sol::getDynamicSpread`）。展示层取“未改善”档（前端 `lib/orders/leverage.ts::getPositionFeeRate` 先取 `positionFeeFactorForBalanceWasNotImproved`，缺失才回退改善档），与链上实际值可能差一个档位。**注意“未改善档 = 保守”只是配置约定，合约不作校验**：`FX100Keys.sol::positionFeeFactorKey` 的两档是彼此独立的 DataStore 键，源码里没有任何 `notImproved >= improved` 的断言。本文未逐市场读取链上两档实际值，核对前请先读 `positionFeeFactorKey(marketIndex, false)` 与 `(marketIndex, true)` 确认大小关系；若某市场配反，展示值会变成乐观估计而非保守估计。

**Est. Receive / Est. Pay（实际结算）**：v0.3.2 的减仓输出结构 `PositionUtils.DecreasePositionCollateralValuesOutput` 只剩 `{outputToken, outputAmount}`，**`secondaryOutputToken` / `secondaryOutputAmount` 两个字段已删除**，`claimCollateral` 通道亦已整体移除（`MarketUtils.sol` 中 `incrementClaimableCollateralAmount` / `claimCollateral` / `batchClaimCollateral` / `_getClaimableFactor` 全部删除）。旧 ABI 解析会直接读不到字段。

概念展示式：

```text
estimatedReceive
= collateral
+ positiveFundingFeeAmount
- negativeFundingFeeAmount
+ closePnl
- closePositionFee
- uiFee
- liquidationFee(仅清算单)
```

实际结算按 `DecreasePositionCollateralUtils.sol::processCollateral` 的固定顺序，每一步都可能提前返回：

```text
1. 正 PnL > 0：outputAmount += basePnlUsd / pnlTokenPrice.max（向下取整），LPVault → PositionVault
2. remainingCollateralAmount = collateralAmount + positiveFundingFeeAmount
3. payForCost(负 Funding：negativeFundingFeeAmount × collateralTokenPrice.min)
4. settleFundingFees(实付负 Funding, 正 Funding)      ← 见 §19.2
5. 实付 < 应付 → emit InsufficientFundingFeePayment（3 个 uintItems）
6. remainingCostUsd > 0 → handleEarlyReturn("funding")
7. 负 PnL < 0：payForCost(-basePnlUsd)；仍有欠 → handleEarlyReturn("pnl")
8. payForCost(totalCostAmountExcludingFunding × collateralTokenPrice.min)
   - 全额付清 → 分配 feeAmountForPool / POSITION_FEE_TYPE / LIQUIDATION_FEE_TYPE / UI_POSITION_FEE_TYPE
   - 未付清 → fees 清空为 getEmptyFees(fees)，再 handleEarlyReturn("fees")
9. initialCollateralDeltaAmount 上限钳到 remainingCollateralAmount（超出发 OrderCollateralDeltaAmountAutoUpdated）
10. outputAmount += 实际提取额；remainingCollateralAmount -= 同额
```

`payForCost`（同文件 `::payForCost`）自身的分支：`costUsd == 0` 直接返回；否则
`remainingCostInOutputToken = ceil(costUsd / collateralTokenPrice.min)`，先从 `output.outputAmount` 扣、再从 `remainingCollateralAmount` 扣；仍有剩余则
`result.remainingCostUsd = remainingCostInOutputToken × collateralTokenPrice.min`（v0.3.2 修正：v0.3.1 此处直接把 Token 数量当 USD 返回）。

最后一道闸门（`DecreaseOrderUtils.sol::_validateOutputAmount`）：

```text
outputUsd = outputAmount × oracle.getPrimaryPrice(outputToken).min
outputUsd < order.minOutputAmount → revert InsufficientOutputAmount
```

因此精确到账值必须读 Reader 的完整减仓预览，不能用 `collateral + unrealizedPnl` 作为到账断言。

**数值示例**（需求 §6 同一组数：抵押 100 USDC、`sizeInUsd` = 1000 USD、平仓费率 0.2%、应付 Funding 3、应收 1；下式把 USDC 按 $1 计，故 Token 数与 USD 数同值——真实核对必须按 `collateralTokenPrice.min` 换算，脱锚时两者不等）：

```text
marginToken          = 100                  （链上原值，不含 Funding）
effectiveMarginToken = 100 - 3 + 1 = 98.00  （= 需求的 Margin 列）
uPnL(+2%)            = 1000 × 2%   = +20.00
closeFee             = 1000 × 0.2% = 2.00
netValue             = 98 + 20 - 2 = 116.00
leverage             = 1000 / 98   = 10.2040… → 10.20x
Funding 列           = 1 - 3       = -2.00（收 − 付，= Margin tooltip 净额行同数）
```

价格转为 −8.6% 时：`uPnL = -86.00`，`netValue = 98 - 86 - 2 = 10.00`，`effectiveMarginToken` 仍为 98.00（不随价格变；但见台账「需求「Margin 不随价格变」在合约层成立，但 Reader 读到的 Margin 会随时间与价格变」一条：抵押品 min/max 价差与 Reader 的时间外推会让它并非严格常量）。

### 17.7 调整保证金与目标杠杆

**加保证金 / 加仓（`IncreasePositionUtils.sol::increasePosition` + `::processCollateral`）**：

```text
collateralDeltaAmount
= initialCollateralDeltaAmount
- fees.totalCostAmount                      （= totalCostAmountExcludingFunding + negativeFundingFeeAmount）
+ fees.funding.positiveFundingFeeAmount

nextCollateralAmount = collateralAmount + collateralDeltaAmount
```

分支与校验：

- `collateralDeltaAmount < 0` 且 `collateralAmount < -collateralDeltaAmount` → revert `InsufficientCollateralAmount`。
- `sizeDeltaUsd > 0` 才调用 `MarketUtils.validateOpenInterestReserve` 与 `willPositionCollateralBeSufficient`（后者不足时 revert `InsufficientCollateralUsd`；纯存入保证金**两项都不校验**，见 §20.2）。该预检用的 `minCollateralFactor` 是 `max(getMinCollateralFactorForOpenInterest(...), getMinCollateralFactor(marketIndex))`，可能**严于** §17.4 的操作线。
- 结尾统一 `validatePosition{minPositionSize: true, maxPositionSize: true, minCollateralUsd: true, forLiquidation: sizeDeltaUsd == 0}`——**纯存入保证金按清算线校验，真加仓按操作线校验**。

**减保证金 / 减仓（`DecreasePositionUtils.sol::decreasePosition`）**：

```text
nextCollateralAmount
= collateralAmount
+ positiveFundingFeeAmount
- 实付负 Funding
- 实付负 PnL
- 实付费用
- 实际提取额
```

`DecreasePositionUtils.sol::decreasePosition` 内一共有**七处订单自动改写**，其中前六处发事件、**第 7 处不发任何事件**；**必须按源码顺序断言**（用例若按错顺序构造，会看到与预期不同的那一条先触发）：

1. **订单规模钳到仓位规模**：`maxSizeDelta = isSizeDeltaUsd ? sizeInUsd : sizeInTokens`；`order.sizeDelta() > maxSizeDelta` 时——`LimitDecrease` / `StopLossDecrease` 发 `OrderSizeDeltaAutoUpdated` 并 `setSizeDelta(maxSizeDelta)` + 重算 `getDecreaseOrderSize`；**其它订单类型（市价减仓 / 清算 / ADL）直接 revert `InvalidDecreaseOrderSize(sizeDeltaUsd, sizeInUsd)`**。
2. **USD 比例减仓凑满 `sizeInTokens` → 归一为全平**（v0.3.2 新增，源码注释明写针对 Long 的 USD 比例减仓向上取整）：`isSizeDeltaUsd && sizeDeltaUsd < sizeInUsd && sizeDeltaInTokens == sizeInTokens` 时发 `OrderSizeDeltaAutoUpdated`、`setSizeDelta(sizeInUsd)` 并重算 `getDecreaseOrderSize`，使 PnL、费用、OI、事件统一按整仓 `sizeInUsd`。该条件只可能由 Long 触发——USD 模式下只有 Long 走 `roundUpDivision`（`PositionUtils.sol::getDecreaseOrderSize`），Short 走向下取整不可能凑满 `sizeInTokens`。**归一后 `sizeDeltaUsd == sizeInUsd`，第 4～6 条所在的 `sizeDeltaUsd < sizeInUsd` 分支块整块不再进入。**
3. **`initialCollateralDeltaAmount` 钳到 `collateralAmount`**：超出时发 `OrderCollateralDeltaAmountAutoUpdated`。此条与是否部分减仓无关，全平也会执行。

以下三条在 `sizeDeltaUsd < sizeInUsd`（部分减仓）分支块内，依次判断：

4. `!willBeSufficient || (estimatedRemainingCollateralUsd + estimatedRemainingPnlUsd) < MIN_COLLATERAL_USD`：
   - `sizeDeltaUsd == 0`（纯提取）→ revert `UnableToWithdrawCollateral`；
   - 否则把 `initialCollateralDeltaAmount` 改写为 0（`OrderCollateralDeltaAmountAutoUpdated`），并把该金额按 `collateralTokenPrice.min` 折回 `estimatedRemainingCollateralUsd`。
5. 改写后仍 `(estimatedRemainingCollateralUsd + estimatedRemainingPnlUsd) < MIN_COLLATERAL_USD` → `sizeDelta` 改写为 `maxSizeDelta`（全平，`OrderSizeDeltaAutoUpdated`）。
6. 剩余 `sizeInUsd - sizeDeltaUsd < MIN_POSITION_SIZE_USD` → 同样改写为 `maxSizeDelta`（全平，`OrderSizeDeltaAutoUpdated`）。

以下一条在部分减仓分支块**之后**、`processCollateral` **之前**执行，全平路径必经：

7. **全平时把 `initialCollateralDeltaAmount` 强制置 0**（`DecreasePositionUtils.sol:238-241`，源码注释「set the initial collateral delta amount to zero to help ensure that the order can be executed」）：条件为 `sizeDeltaUsd == position.sizeInUsd() && order.initialCollateralDeltaAmount() > 0`。

   ⚠️ **这一处不发任何事件**，且它是全平路径上对订单的最后一次写入——包括被第 2/5/6 条升级为全平的订单。后果有两条，都会让断言写错：
   - 事件与 Reader 里读到的 `initialCollateralDeltaAmount` 在全平场景**恒为 0**，**不能**用它表示"本次提取的保证金"；真正还给用户的是 `output.outputAmount`（含 `remainingCollateralAmount` 全额）。按"requestedCollateralWithdrawal"建模会整整少算一份本金。
   - 因为不发事件，**无法靠事件流发现这次改写**；只能靠"订单创建时的 `initialCollateralDeltaAmount` 与执行后读到的值不一致"来反推。用例若断言"全平时该字段等于创建时的值"会必然 FAIL，而那不是缺陷。

**只按事件名断言不成立**：第 1、2、5、6 条发的是同一个 `OrderSizeDeltaAutoUpdated`，且 USD 模式下 `maxSizeDelta` 就等于 `sizeInUsd`，四条的 `nextValue` 可能完全相同，光看 `nextValue` 分不开。可用的区分依据是方向与顺序：第 1 条是**下调**（`prevValue > nextValue`，且只可能来自 `LimitDecrease` / `StopLossDecrease`），第 2、5、6 条都是**上调至全平**（`prevValue < nextValue`），其中第 2 条与第 5、6 条互斥（归一后不再进部分减仓分支块），第 5、6 条的差别在触发条件（剩余抵押 vs 剩余仓位规模）。第 3、4 条共用 `OrderCollateralDeltaAmountAutoUpdated`，靠 `nextValue` 可分（第 3 条是 `collateralAmount`，第 4 条恒为 0）。

此外 `DecreasePositionCollateralUtils.sol::processCollateral` 在支付瀑布第 9 步还会把 `initialCollateralDeltaAmount` 钳到 `remainingCollateralAmount`（见 §17.6），发的仍是 `OrderCollateralDeltaAmountAutoUpdated`——它发生在上述六条之后、且在另一个文件里，所以同一笔减仓可能出现不止一条该事件，必须按发生顺序解读。

**目标杠杆的产品估算**（合约无此路径，纯展示派生）：

```text
targetSizeUsd = targetLeverage × effectiveMarginUsd
sizeChangeUsd = targetSizeUsd - sizeInUsd
```

`sizeChangeUsd > 0` 走加仓路径收费和点差；`sizeChangeUsd < 0` 走减仓路径计算 PnL、点差和输出。最终结果必须通过对应路径的 `minCollateralFactor` 校验（加仓=操作线、减仓=操作线、纯存入=清算线，见 §17.4 表）。

## 19. Funding 展示字段

### 19.1 市场费率

合约费率为每秒 `1e30`（`FLOAT_PRECISION`）精度，`clamp` 到 `[minFundingFactorPerSecond, maxFundingFactorPerSecond]`（`MarketUtils.sol::getNextFundingAmountPerSize`）。页面按小时百分比展示：

```text
hourlyRate        = fundingFactorPerSecond × 3600
hourlyRatePercent = fundingFactorPerSecond × 3600 × 100 / 1e30
```

合约符号约定（同函数内 `if (result.longFundingFactorPerSecond > 0)` 分支）：**正数 = 该侧支付**（累加到 `negativeFundingFeePerSize`），**负数 = 该侧收取**（绝对值累加到 `positiveFundingFeePerSize`）。若 UI 采用“负值 = 用户支付、正值 = 用户收取”，则：

```text
displayFundingRatePercent
= -fundingFactorPerSecond × 3600 × 100 / 1e30
```

符号翻转只发生在展示层，不得改变合约累计值的方向。注意 `fundingFloorFactor` 只加在 Long 侧（`f_long = clamp(floor + base × skew / 1e18, …)`；`f_short = clamp(-base × skew / 1e18, …)`），因此两侧费率一般不互为相反数。

### 19.2 单仓应付 / 应收与 LP 结算

精确 Token 公式（`MarketUtils.sol::getFundingAmount`，`Precision.mulDiv` 的 `roundUpMagnitude` 决定取整方向；分母是 `FLOAT_PRECISION × price` 一次合并除，不是两次独立除）：

```text
negativeFundingFeeAmount
= ceil(
    sizeInTokens
    × (latestNegativeFundingFeePerSize - position.negativeFundingFeePerSize)
    / (1e30 × collateralTokenPrice.min)
  )

positiveFundingFeeAmount
= floor(
    sizeInTokens
    × (latestPositiveFundingFeePerSize - position.positiveFundingFeePerSize)
    / (1e30 × collateralTokenPrice.max)
  )

displayFundingToken
= positiveFundingFeeAmount - negativeFundingFeeAmount        （需求 §4.5 Funding 列，收 − 付）
```

- 负 Funding 在下次仓位更新或平仓时扣入成本；正 Funding 在下次仓位更新或平仓时增加保证金（`IncreasePositionUtils.sol::processCollateral` 的 `collateralDeltaAmount += positiveFundingFeeAmount`；`DecreasePositionCollateralUtils.sol::processCollateral` 的 `remainingCollateralAmount += positiveFundingFeeAmount`）。两侧都不需要用户 claim。
- 每次结算后仓位的正负 `fundingFeePerSize` 基准更新到 `fees.funding.latest*`（`IncreasePositionUtils.sol::increasePosition`），防止重复计费。

**LP 现金流口径（v0.3.2 变更，必须与 §10.6 一致）**：

`MarketUtils.sol::updateFundingState` 在 v0.3.2 **不再产生任何 LP 现金流**，它只做四件事：推进两侧 `fundingFeePerSize` 索引、写 `fundingUpdatedAt`、写 `skewEMA`、发 `Funding` 事件。`GetNextFundingAmountPerSizeResult.positionPaysLp` 的字段注释已降级为 “informational accrued amount only; LP cash flow is realized when a position settles funding”，函数体注释亦写 “emitted for observability only and is not used for settlement”；且 `updateFundingState` 的 `PositionVault` 参数已被删除。

现金流改由新增的 `MarketUtils.sol::settleFundingFees` 在**仓位结算时**按**该仓的 negative − positive 净差**执行：

```text
settleFundingFees(negativeFundingFeeAmount, positiveFundingFeeAmount):

negative > positive → FeeUtils.incrementClaimableFeeAmount(
                        marketIndex, collateralToken,
                        negative - positive, FUNDING_FEE_TYPE)

positive > negative → IVault(market.vault).transferOut(
                        collateralToken, positionVault, positive - negative)

negative == positive → 无动作（无事件、无转账）
```

两个调用点的**入参不同**，核对时不能混用：

| 调用点 | 传入的 negative | 传入的 positive |
| --- | --- | --- |
| `IncreasePositionUtils.sol::processCollateral` | `fees.funding.negativeFundingFeeAmount`（应付全额） | `fees.funding.positiveFundingFeeAmount` |
| `DecreasePositionCollateralUtils.sol::processCollateral` | `collateralCache.result.amountPaidInCollateralToken`（**实付额**，可能 < 应付） | `fees.funding.positiveFundingFeeAmount` |

减仓/清算路径实付不足时补发 `InsufficientFundingFeePayment`（`PositionEventUtils.sol::emitInsufficientFundingFeePayment`），v0.3.2 字段由 4 项减为 **3 项**：

```text
addressItems[0] = token
uintItems[0] = marketIndex
uintItems[1] = expectedAmount                 （= negativeFundingFeeAmount）
uintItems[2] = amountPaidInCollateralToken
（v0.3.1 的 uintItems[3] = amountPaidInSecondaryOutputToken 已删除）
```

v0.3.1 的旧行为——`updateFundingState` 内按 `positionPaysLp > 0` 累加 `FUNDING_FEE_TYPE`、否则 LPVault 向 PositionVault 转账，以及减仓路径把 secondary output 的欠款转给 `HOLDING_ADDRESS` 的 `incrementClaimableCollateralAmount` 分支——**在 v0.3.2 全部删除**，不得再作为断言依据。

因此每个仓位动作必须同时断言：① 两个 `fundingFeePerSize` 索引基准刷新；② 仓位 `collateralAmount` / `outputAmount` 变化；③ 市场 Vault 与 PositionVault 的资金差额或 `FUNDING_FEE_TYPE` 账本增量。只检查市场 `Funding` 事件不成立。

**数值示例**（构造值，USDC 6 位，`collateralTokenPrice.min = 1e24`）：

```text
市场：longOIUsd = 1e35（$100,000）、longOIInTokens = 5e19（50 个 index token，18 位）
      longFundingFactorPerSecond = 1e22（= 1e-8/秒）、duration = 3600s

negativeFundingFeePerSizeDelta.long
= toFactor(applyFactor(1e35, 1e22 × 3600), 5e19)
= (1e35 × 3.6e25 / 1e30) × 1e30 / 5e19
= 3.6e30 × 1e30 / 5e19
= 7.2e40

单仓 sizeInTokens = 5e18（5 个 token，名义 $10,000）：
negativeFundingFeeAmount
= ceil(5e18 × 7.2e40 / (1e30 × 1e24))
= ceil(3.6e59 / 1e54)
= 360000 = 0.36 USDC

校验：$10,000 × (1e-8 × 3600) = $10,000 × 0.0036% = $0.36 ✓
hourlyRatePercent = 1e22 × 3600 × 100 / 1e30 = 0.0036% ✓
```

**Reader 预览的已知偏差（两版皆有，核对必须知道）**：`ReaderPositionUtils.sol::getPositionInfo` 在把虚拟增量并入 `latest*FundingFeePerSize` 时写死

```text
uint256 multiplier = 2;
latestNegativeFundingFeePerSize += nextFundingAmountResult.negativeFundingFeePerSizeDelta.long × 2;
latestPositiveFundingFeePerSize += nextFundingAmountResult.positiveFundingFeePerSizeDelta.long × 2;
```

但 v0.3.2 的 `MarketUtils.sol::getNextFundingAmountPerSize` **没有对 per-size 增量做任何减半**（注释里所说的 GMX 双 Token 市场折半逻辑在 FX100 不存在），且这里**恒取 `.long` 侧增量、不区分仓位方向**。结果：Reader 返回的 `fees.funding.negativeFundingFeeAmount / positiveFundingFeeAmount` 相对链上实际结算值会**多算自上次 `updateFundingState` 以来那一段的两倍，且空头仓位取的是多头侧增量**。断言链上实际扣款请以 `PositionFeesCollected` 事件的 `negativeFundingFeeAmount` / `positiveFundingFeeAmount` 为准，Reader 预览只能作参考上界。详见台账「Reader 的待结算资金费预览把增量翻倍，且空头取多头侧增量」一条。

### 19.3 Funding 时间与零 OI

```text
fundingDuration
= MarketUtils.getSecondsSinceFundingUpdated(marketIndex)
= fundingUpdatedAt == 0 ? 0 : blockTimestamp - fundingUpdatedAt
```

`fundingUpdatedAt == 0`（市场从未更新过 Funding）返回 0，不是把 `blockTimestamp` 当作 duration。

**零 OI 分支不是“跳过写库”**（`MarketUtils.sol::getNextFundingAmountPerSize` + `::updateFundingState`）：

```text
totalOpenInterest = longOIInTokens × indexMidPrice + shortOIInTokens × indexMidPrice
totalOpenInterest == 0 → getNextFundingAmountPerSize 返回全零 result（含零值 skewEMA 结构体）并 return
```

随后 `updateFundingState` **照常执行到底**：

1. 四次 `applyDeltaTo{Negative,Positive}FundingFeePerSize` 因 `delta == 0` 在函数入口 early-return，**不写库、不发事件**；
2. `dataStore.setUint(fundingUpdatedAtKey(marketIndex), block.timestamp)` —— **`fundingUpdatedAt` 照刷**；
3. `dataStore.setBytes32(fundingSkewEmaKey(marketIndex), result.skewEMA.toBytes32())` —— `result.skewEMA` 是零值结构体，**已有的 skew EMA 被覆盖成 `bytes32(0)`**（`lastTime`/`sampleInterval`/`lastValue`/`lastEmaValue` 全部清零）；
4. `MarketEventUtils.emitFunding(marketIndex, 0, 0, 0)` —— **仍发 `Funding` 事件**，三个 `intItems` 全为 0。

后果与断言要点：

- 市场 OI 归零再重新开仓时，EMA 从零重建：`skewEMA.lastTime == 0` 分支会用当前 skew 初始化 `lastTime = block.timestamp`、`sampleInterval = 3600`（EMA 的**时间常数**，见 §20.1）、`lastValue = lastEmaValue = skew`（`MarketUtils.sol::getNextFundingAmountPerSize`）。历史 EMA 记忆丢失。
- 零 OI 期间 `fundingUpdatedAt` 被不断推进，等于把这段空窗时间从 `duration` 中扣掉——重新有 OI 后 duration 只从最后一次刷新算起。
- 用例断言“零 OI 时 Funding 无变化”只能断言两个 `fundingFeePerSize` 与 `FUNDING_FEE_TYPE` 账本不变，**不能断言 `fundingUpdatedAt`、`fundingSkewEma` 或 `Funding` 事件不变**。

> **与主文档其它未改写章节的冲突，以本节为准**：§21 速查表 Funding / Skew 行的备注仍写「零 OI no-op」，与本小节查实的「`fundingUpdatedAt` 照刷、`skewEMA` 被清零、`Funding(0,0,0)` 照发」相反。待该表改写时同步。

页面“下一次 Funding”倒计时如存在，必须明确它是刷新提示；合约按实际经过秒数连续累计，没有固定结算周期（`sampleInterval = 3600` 是 EMA 的**时间常数**，既不是收费周期，也不是「每小时采一次样」的离散采样周期，见 §20.1）。

## 20. 市场与风险展示字段

### 20.1 Open Interest 与 Skew

Funding 用的 OI（`MarketUtils.sol::getNextFundingAmountPerSize`，选价 `indexTokenPrice.midPrice()`）：

```text
longOIUsd  = longOpenInterestInTokens  × indexTokenPrice.midPrice()
shortOIUsd = shortOpenInterestInTokens × indexTokenPrice.midPrice()
totalOIUsd = longOIUsd + shortOIUsd

skewRaw = (longOIUsd - shortOIUsd) × 1e18 / totalOIUsd      （WEI_PRECISION，可为负）
skew    = skewEMA.saveValue(skewRaw) 之后的 emaValue()       （时间常数 3600s，展开见本节下方「EMA 的分支与衰减」）
```

`totalOIUsd == 0` 时函数直接返回全零，`skewRaw` 不计算（避免除零），页面 skew 展示 0 / N/A，不能显示 NaN。**费率用的是 EMA 后的 skew，不是当期 skewRaw**——页面若展示瞬时 skew 必须标注口径。

**EMA 的分支与衰减**（`ExponentialMovingAverage.sol::saveValue` / `::emaValue`）：

- `skewEMA.lastTime == 0`（首次或被零 OI 清零后）→ 初始化 `lastTime = block.timestamp`、`sampleInterval = 3600`、`lastValue = lastEmaValue = skewRaw`，随后 `emaValue()` 返回 `skewRaw` 本身。
- 否则 `saveValue(skewRaw)` 先把 `lastEmaValue` 更新为**按旧样本算出的 EMA**，再写入 `lastValue = skewRaw`、`lastTime = block.timestamp`；紧接着的 `emaValue()` 因 `lastTime == block.timestamp` 走 `else` 分支直接返回该 `lastEmaValue`。
  即 **本次采样到的 skew 不影响本次费率，只影响下一次更新**——用例构造 skew 后必须再推进一次 `updateFundingState` 才能看到费率变化。
- 衰减是**连续指数衰减**，不是按 1 小时一格的离散采样：`e = dt × 1e18 / sampleInterval`、`alpha = LogExpMath.exp(-e)`（1e18 定点，即数学上的 `alpha = exp(−dt / 3600)`），返回值 `= lastValue × (1e18 − alpha) + lastEmaValue × alpha`，再整除 `1e18`。`sampleInterval = 3600` 是**时间常数**（dt 每过 3600s 旧 EMA 权重衰减到 `1/e`），不是「每 3600s 才更新一次」：`saveValue` 在每次 `updateFundingState` 都会调用，与是否满一小时无关。
- `e > 41e18`（即 `dt > 41 × sampleInterval` ≈ 41 小时）时直接返回 `lastValue`（`exp(−41)` 已小于 1 wei，长时间未更新则完全采纳最新样本）。

> **与主文档其它未改写章节的冲突，以本节为准**：§10.2 把它写成「随后进入一小时采样间隔的 EMA」、§21 速查表写成 `EMA1h((longOI-shortOI)/totalOI)`，两处都会被读成「每小时采一次样」的离散 EMA，据此复算会得到与链上不同的费率。实际是时间常数 3600s 的连续指数衰减。待那两节改写时同步。

除上面的 Funding OI 之外，还有两个 OI 口径必须与它区分开——下表四行互不等价（单位也不全相同），任何一处都不能互相替换：

| 口径 | 定义 | 选价 | 用途 | 锚点 |
| --- | --- | --- | --- | --- |
| `openInterestInTokens` | Token 计数（非 USD） | — | Funding、储备校验的基数 | `MarketUtils.sol::getOpenInterestInTokens` |
| Funding OI USD | `openInterestInTokens × indexTokenPrice.midPrice()` | **mid** | skew / 费率 | `::getNextFundingAmountPerSize` |
| `totalNominalOI` | `(longOIInTokens + shortOIInTokens) × indexTokenPrice.max` | **max** | 储备闸门 | `ReaderUtils.sol::getMarketInfo`、`MarketUtils.sol::validateOpenInterestReserve` |
| `cumulativeOpenCosts` | 该侧全部仓位的**开仓成本**累计（USD×1e30，与当前价格无关） | — | 硬上限 / 软上限 / 市场 PnL | `MarketUtils.sol::getCumulativeOpenCosts` |

### 20.2 Reserve 与 Available Liquidity

Reader 的可用流动性是**三道闸门取最小**（`ReaderUtils.sol::getAvailableLiquidityUsd`，按 `isLong` 分别返回 `availableLongUsd` / `availableShortUsd`）：

```text
poolUsdWithoutPnl                                    （maximize=false → collateralTokenPrice.min）
= IVault(market.vault).totalAssets() × collateralTokenPrice.min

totalNominalOI
= (longOpenInterestInTokens + shortOpenInterestInTokens) × indexTokenPrice.max

openInterest = cumulativeOpenCosts(marketIndex, isLong)        ← 按侧，且是开仓成本口径

hardCap        = maxOpenInterest[marketIndex, isLong]
hardRemaining  = hardCap > openInterest ? hardCap - openInterest : 0

factorCap      = poolUsdWithoutPnl × maxOpenInterestFactor[marketIndex, isLong] / 1e30
factorRemaining= factorCap > openInterest ? factorCap - openInterest : 0

reserveCap     = poolUsdWithoutPnl × reserveFactor[marketIndex] / 1e30
reserveRemaining = reserveCap > totalNominalOI ? reserveCap - totalNominalOI : 0

availableUsd = min(hardRemaining, factorRemaining, reserveRemaining)
```

三个要点：

1. **储备闸门与另外两个闸门用的不是同一个 OI**：`reserveRemaining` 减的是**双边合计的 `totalNominalOI`（按 `indexPrice.max` 估值）**，而 `hardRemaining` / `factorRemaining` 减的是**该侧的 `cumulativeOpenCosts`（开仓成本口径）**。
2. 三处都用 `>` 判断后作差，不足时钳到 0，不产生负值。
3. `maxOpenInterestFactor` 这一档在 v0.3.1 文档里被漏写；`reserveFactor` 是市场级（不分多空），另两个是按侧配置。

链上真正的拦截点（不是 Reader）：

| 校验 | 触发时机 | 判据 | 锚点 |
| --- | --- | --- | --- |
| `validateOpenInterestReserve` | **仅 `sizeDeltaUsd > 0` 的加仓**（纯存入保证金不校验） | `totalNominalOI > poolUsd × reserveFactor / 1e30` → revert `InsufficientReserveForOpenInterest` | `MarketUtils.sol::validateOpenInterestReserve` |
| `validateOpenInterest` | 更新 OI 后，**且仅 `delta > 0` 时**（`MarketUtils.sol::applyDeltaToCumulativeOpenCosts` 内 `if (delta > 0)` 才调用，减仓不校验） | `cumulativeOpenCosts > maxOpenInterest` 或 `> poolUsd × maxOpenInterestFactor / 1e30` → revert `MaxOpenInterestExceeded` | `MarketUtils.sol::validateOpenInterest` |

两处的 `poolUsd` 都取 `getPoolUsdWithoutPnl(..., maximize=false)`，即 `collateralTokenPrice.min`。

页面若没有纳入全部闸门（还有 `MIN_POSITION_SIZE_USD`、`maxPositionSizeUSD`、`minCollateralFactor` 等），应标为“估算可用流动性”，提交前仍由合约最终校验。

**数值示例**（构造值：USDC 6 位、`collateralTokenPrice.min = 1e24`；index token 18 位、$2000 → `indexPrice.max = 2e15`）：

```text
totalAssets = 1e12（$1,000,000）
poolUsdWithoutPnl = 1e12 × 1e24 = 1e36                        （$1,000,000）

longOIInTokens + shortOIInTokens = 3e20（300 个 token）
totalNominalOI = 3e20 × 2e15 = 6e35                           （$600,000）

reserveFactor = 8e29（80%）
reserveCap    = 1e36 × 8e29 / 1e30 = 8e35                     （$800,000）
reserveRemaining = 8e35 - 6e35 = 2e35                         （$200,000）

Long 侧：cumulativeOpenCosts = 4e35（$400,000）
maxOpenInterest[long]       = 5e35（$500,000） → hardRemaining   = 1e35（$100,000）
maxOpenInterestFactor[long] = 6e29（60%）
factorCap                   = 1e36 × 6e29 / 1e30 = 6e35        → factorRemaining = 2e35（$200,000）

availableLongUsd = min(1e35, 2e35, 2e35) = 1e35                （$100,000，硬上限最紧）
```

### 20.3 Pool、PnL Obligation 与 ADL

```text
poolUsdWithoutPnl                                       （MarketUtils.sol::getPoolUsdWithoutPnl）
= IVault(market.vault).totalAssets() × (maximize ? collateralTokenPrice.max : collateralTokenPrice.min)
```

Reader `getMarketInfo` 传 `maximize=false` → 用 `.min`。

市场侧 PnL（`MarketUtils.sol::getPnl`）：

```text
openInterest        = cumulativeOpenCosts(marketIndex, isLong)
openInterestInTokens= getOpenInterestInTokens(marketIndex, isLong)

openInterest == 0 || openInterestInTokens == 0 → return 0     （早退分支）

price = indexTokenPrice.pickPriceForPnl(isLong, maximize)
Long  pnl = openInterestInTokens × price - openInterest
Short pnl = openInterest - openInterestInTokens × price
```

PnL / Pool 比例（`MarketUtils.sol::getPnlToPoolFactor`）——注意分母的选价是 `!maximize`：

```text
poolUsd = getPoolUsdWithoutPnl(market, collateralTokenPrice, !maximize)
poolUsd == 0 → return 0                                       （早退分支）
pnlToPoolFactor = pnl × 1e30 / poolUsd                        （Precision.toFactor）
```

`ReaderUtils.sol::getMarketInfo` 对 `longPnlToPoolFactor` / `shortPnlToPoolFactor` 都传 `maximize=true`，即 **PnL 取对交易者最有利的一边（Long 用 `indexPrice.max`、Short 用 `indexPrice.min`），池子取 `collateralTokenPrice.min`**——分子最大、分母最小，比例最保守。

全局净负债与 ADL（`MarketUtils.sol::getNetObligation` / `::getGlobalNetObligationRatio` / `::isGlobalNetObligationRatioExceeded`，Reader 入口 `ReaderUtils.sol::getAdlState`）：

```text
每个市场（选价 oracle.getSecondaryPrice(indexToken, isADLStart)，maximize=true）：
marketNetObligation = max(longPnl, 0) + max(shortPnl, 0)      （跨边不轧差）

全局：
globalPoolUsd = getPoolUsdWithoutPnl(
                  market[遍历中的第一个市场],
                  oracle.getSecondaryPrice(collateralToken, isADLStart),
                  maximize = false)                            → collateralTokenPrice.min

globalPoolUsd == 0 → globalNetObligationRatio = 0              （早退分支）
globalNetObligationRatio = Σ marketNetObligation × 1e30 / globalPoolUsd

pnlFactorType = isAdlEnabled ? MIN_PNL_FACTOR_AFTER_ADL : MAX_PNL_FACTOR_FOR_ADL
isADLStart    = !isAdlEnabled
isExceeded    = globalNetObligationRatio > dataStore.getUint(pnlFactorType)      （严格大于）
```

三个必须写明的口径细节：

1. **选价是 `getSecondaryPrice(..., isADLStart)`，不是 primary price**（`Oracle.sol::_getSecondaryPrice`）：token 为零地址返回 `(0,0)`；配了 Chainlink 价格源则返回 `Price.Props(price, price)`（min=max）；否则用 `latestRecordedPrices[token]`，且**只有 `isADLStart == false` 时才校验 `MAX_RECORDED_PRICE_AGE`**（超龄 revert `MaxPriceAgeExceeded`），记录为空则 revert `EmptySecondaryPrice`。核对时不能用现货 primary price 复算。
2. **多个市场共享同一 LPVault，分母只取一次**：源码在 `i == 0` 分支里取第一个市场的池子 USD 作为全局池子值（注释 “All markets share the same vault”），不是按市场累加。
3. 阈值键随 ADL 当前状态切换：未开启 ADL 用 `MAX_PNL_FACTOR_FOR_ADL`（启动阈值），已开启用 `MIN_PNL_FACTOR_AFTER_ADL`（退出阈值），判定为**严格大于**，等于阈值不触发。

`getAdlState` 返回四元组 `(latestAdlTime, shouldEnableAdl, globalNetObligationRatio, globalNetObligationRatioThreshold)`，页面展示的“ADL 风险”应直接用这四个值，不要自行拼装分子分母。

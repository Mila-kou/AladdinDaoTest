## 18. 清算价格与风险展示

**合约里没有清算价这个字段，也没有任何返回清算价的函数。** 全链上只有 `PositionUtils.sol::isPositionLiquidatable` 的三元组 `(bool, reason, IsPositionLiquidatableInfo)`——"给定这一组价格，这个仓位现在是否可清算"。所谓"清算价"是对该判定不等式按 index 价做的**代数反解**，属于 T2 产品派生字段（§0.1），不是 T0/T1。任何"去读一下合约的 liquidationPrice"的核对设计都无法落地，`Reader.sol` 里也只有 `isPositionLiquidatable`，没有 `getLiquidationPrice`。

本节只讲反解与展示：判定不等式本身、`balanceWasImproved`、成交价与三条件的完整分支见 §11；维持要求的三个因子分支见 §11.2 / §11.3；Margin / Net Value / Est. Receive 的符号定义见 §17.3 / §17.6；本节不重复推导，只在必要处引用。清算执行链（内部订单、清算费、insolvent 早退、事件身份）见 [`Liquidation-(v0.3.2).md`](../../versions/v0.3.2/Liquidation-(v0.3.2).md)。

### 18.1 判定不等式的符号形式

把 §11.1 的 `remainingCollateralUsd` 写成待反解的形式（全部 1e30 USD 标度）：

```text
Q  = position.sizeInTokens          （标度 = index token 登记 decimals，见下方警告）
S  = position.sizeInUsd
P  = 清算判定用的成交价 executionPrice
C  = position.collateralAmount × collateralTokenPrice.min
Fp = fees.funding.positiveFundingFeeAmount × collateralTokenPrice.min
F  = fees.totalCostAmount × collateralTokenPrice.min
     （= 平仓位费 − 折扣 + 负 Funding；uiFee = 0、liquidationFee = 0，见 §11.1）

remaining(P) = C + Fp − F + (isLong ? Q×P − S : S − Q×P)
```

不可清算（safe）当且仅当三条件全部不成立（§11.2 按顺序短路，此处只取合取式）：

```text
T = max(
      shouldValidateMinCollateralUsd ? dataStore.getUint(MIN_COLLATERAL_USD) : 0,
      floor(S × minCollateralFactor / 1e30)          ← 因子由 forLiquidation 选，§11.2
    )
T* = max(T, 1)          ← 条件② 是 remaining <= 0，所以"safe"要求 remaining ≥ 1

safe  ⟺  remaining(P) ≥ T*
```

`T*` 里的 `max(…, 1)` 不是修辞：两个阈值都配成 0 时，条件①③ 都不成立，边界完全由条件② 的 `<= 0` 决定，最后安全值是 `remaining = 1`（1e-30 USD）。**除条件② 外都是严格小于**，等于阈值不触发清算（§11.2）。

**Q 的标度警告**：`sizeDeltaInTokens = sizeDeltaUsd / executionPrice`，而 oracle 价标度是 `10^(30 − tokenDecimals)`（`ChainlinkPriceFeedUtils.sol` / `PythPriceFeedUtils.sol` 的 `60 - feedDecimals - tokenDecimals` 注释），所以 **`sizeInTokens` 的标度等于该 index token 在 token registry 登记的 decimals，合约不保证 18 位**。前端 `packages/sdk/src/utils/positionPrecision.ts::getPositionSizeDecimals` 把它硬编码成 18 并在注释里断言"所有 token 都如此"；这在当前部署下成立只是因为合成 index token 全部按 18 位登记（`tx-fork` 的 FXMOCK 为 18 位；WBTC 曾按 8 位登记后被修正为 18）。**本节所有除以 `10^indexDecimals` 的地方一律按实际登记值取，不得写死 `1e18`**；核对脚本必须先读 token decimals 再算。

### 18.2 闭式清算价（成交价口径，精确到 1 wei）

在**同一份快照**（`C`、`Fp`、`F`、`T*`、`Q`、`S` 全部固定）下，`remaining(P)` 对 `P` 是严格单调线性的，可以精确反解。注意反解出来的是 **`executionPrice`**，不是 index 价——两者的换算见 18.3。

**异币种抵押（v0.3.2 的常规形态）**：抵押品价格不随 index 价变，`C`、`Fp`、`F` 全是与 `P` 无关的常数。

```text
Long  ：safe ⟺ Q×P ≥ S + T* + F − C − Fp        令 N⁺ = S + T* + F − C − Fp
        最后安全成交价     P_safe = ceil(N⁺ / Q)          （N⁺ ≤ 0 时不可清算，无解）
        第一个可清算成交价 P_liq  = P_safe − 1

Short ：safe ⟺ Q×P ≤ C + Fp + S − F − T*        令 N⁻ = C + Fp + S − F − T*
        最后安全成交价     P_safe = floor(N⁻ / Q)         （N⁻ < 0 时立即可清算）
        第一个可清算成交价 P_liq  = P_safe + 1
```

**取整方向必须与方向配对**：多头向上取整、空头向下取整。反了会把边界推到不可清算的一侧，1 wei 级用例（"最后安全价 / 第一个可清算价"两笔交易）必定判错。

**同币种抵押（抵押品 = index token）**：抵押品本身随价格变，`C = A × collateralTokenPrice.min`，而同一资产满足 `collateralTokenPrice = indexTokenPrice × 10^(d_index − d_collateral)`，所以 `C` 要挪到分母：

```text
A     = position.collateralAmount
scale = 10^(indexTokenDecimals − collateralTokenDecimals)

Long  分母 = Q + A × scale     P_safe = ceil ( (S + T* + F − Fp) / 分母 )      ← 分母恒 > 0
Short 分母 = Q − A × scale     P_safe = floor( (S − T* − F + Fp) / 分母 )      ← 分母可能 ≤ 0，见下

分母 == 0 → 无解（空头且抵押数量恰好等于仓位数量时，净敞口为零）
```

⚠️ **空头同币种的分母可能为负或零**（抵押数量折算后超过仓位 token 数，即 `A × scale ≥ Q`）。分母为负时不等式两边同除会**翻转方向**，`floor` 必须改成 `ceil`；分母为零时价格再高也不会触发该条件（该仓在这个维度上不可清算，需由条件 ① / ② 兜底）。写空头同币种用例前先判分母符号，不要直接套上式。

`F` 与 `Fp` 仍留在分子：它们虽然是抵押品计价，但链上是先算 USD 再除抵押价、随后又乘回抵押价（`positionFeeAmount = ⌊⌊S×factor/1e30⌋ / colPrice.min⌋`，Funding 同理走 `MarketUtils.sol::getFundingAmount` 的合并分母），一来一回后在 USD 口径上与抵押价近似无关，只剩两次取整的尾差。**用异币种公式去核同币种仓位会算出偏低的清算价**（分母少了抵押数量），这是清算价核对最常见的口径错。

**但在 v0.3.2 上要先确认这条分支是否可达**：`MarketStoreUtils.sol::get` 把每个市场的 `collateralToken` 直接读全局单键 `FX100Keys.COLLATERAL_TOKEN`（`MarketFactory.sol::createMarket` 建市场时同样只读该键），**协议层没有 per-market 抵押品**。因此"同币种抵押"只在全局抵押品恰好等于某市场 index token 时对**那一个**市场成立；当前 fork 与 dev 站的全局抵押品是 USDC（6 位），index token 是合成 token，**同币种分支不可达**。前端 `packages/sdk/src/utils/positions.ts::getLiquidationPrice` 用 `getIsEquivalentTokens` 判分支，该函数除地址相等外还会在"任一方 `isSynthetic` 且 symbol 相同"时判为等价——用例里给合成 token 起与抵押品相同的 symbol 会误入同币种分支。

**PnL 封顶不进入闭式的前提**：`_getPositionPnlUsd` 只对 `totalPositionPnl > 0` 做池级等比缩放（§11.1）。清算边界附近仓位必然处于亏损侧，缩放不触发，所以闭式里可以直接用 `Q×P − S`。若要反解的是"盈利仓位因费用/Funding 被清算"的边界（大额负 Funding 场景），必须先确认 `cappedPoolPnl == poolPnl`，否则闭式失效，只能走 18.3。

### 18.3 闭式失效的来源与精确边界（Reader 二分）

闭式给的是**成交价**。链上真正拿来比的是 oracle 价，两者隔着一层 `dynamicSpread`（`PositionUtils.sol::getExecutionPriceForDecrease`，清算路径 `allowNegativeSpread = false`）：

```text
Long ：executionPrice = floor( indexTokenPrice.min × (1e18 − d) / 1e18 )
Short：executionPrice = ceil ( indexTokenPrice.max × (1e18 + d) / 1e18 )
d = clamp(skewImpact + constantPriceSpread + priceImpactSpread, minD', maxD')
minD' = max(minDynamicSpread(marketIndex, isLong), 0)      ← 清算强制抬到 0
maxD' = max(maxDynamicSpread(marketIndex, isLong), minD')
```

**整仓清算判定下 `d` 与 index 价无关**，所以“成交价 → index 价”是一次除法，不需要不动点。逐项拆开（源码亲验，`PositionPricingUtils.sol::getDynamicSpread` / `::getSkewImpact` / `::getSkewRef` / `::getPriceImpactSpread` / `::isBalanceWasImproved`）：

| 分量 | 是否随 index 价变 | 原因 |
| --- | --- | --- |
| `constantPriceSpread` | 否 | 直接读配置 |
| `skewImpact` | **否** | `getSkewRef` 是 `\|L−S\|/(L+S)` 的比值，整仓平仓时 `usdDelta` 与两侧 OI 同乘 `midPrice`，比值不变 |
| `balanceWasImproved` | **否** | 同上，`\|nextImbalance\| < \|currentImbalance\|` 两边同比缩放 |
| `priceImpactSpread` | **否** | `getPriceImpactSpread` 用的是 `params.usdDelta.abs()`，而**它在 L164 被调用，早于 L166 的 `getNextOpenInterest`**（后者才在 L303 把 `usdDelta` 改写成 `tokenDelta × midPrice`）。清算路径传进来的是 `PositionUtils.sol:711` 的 `-cache.sizeDeltaUsd`——全平时即仓位存储的 `sizeInUsd`，是**已入账的 USD 常量，与当前 index 价无关** |

也就是说，**整仓清算判定里 `d` 的三个分量全部尺度不变**，闭式反解出的成交价可以一次换算回 index 价：

```text
Long   indexMin = ceil (P_safe × 1e18 / (1e18 − d))
Short  indexMax = floor(P_safe × 1e18 / (1e18 + d))
```

> 这与**开仓/部分减仓**路径不同：那两条路径传给 `getDynamicSpread` 的 `usdDelta` 来自订单的 `sizeDeltaUsd`，token 计价下它由 `tokenDelta × 价格` 派生，才会随价格变。本节结论只覆盖**全平清算判定**。

**订正记录（2026-09-05）**：初稿把 `priceImpactSpread` 判为“随 index 价变”、并据此要求走不动点迭代——依据是 `orderSize = |usdDelta| = Q × midPrice`。该推导把 `getNextOpenInterest` 对 `usdDelta` 的改写（L303）当成了发生在 `getPriceImpactSpread`（L164）之前，与源码次序相反。已按实际调用次序订正。

除此之外还有四类闭式无法覆盖的偏差：oracle `min/max` 双价（判定用 min/max，`midPrice` 又用于点差）、抵押品脱锚（`.min` 与 `.max` 不等，见 18.6 的示例）、正 Funding 的 `.max` 折 token / `.min` 折回 USD 的不对称（§11.1）、以及盈利侧 PnL cap。

**精确边界只有一个权威口径：定点二分 `Reader.sol::isPositionLiquidatable`。**

1. 固定同一份快照：区块、市场参数、仓位字段、Funding 索引、抵押品与 index 的 `min/max` 价。
2. **入参必须与要复现的链上路径一致**——真清算 gate 是 `(shouldValidateMinCollateralUsd = true, forLiquidation = true)`（`DecreasePositionUtils.sol::decreasePosition`）；开仓/加仓校验是 `(true, sizeDeltaUsd == 0)`；减仓收尾是 `(false, false)`（§11.3）。传错这两个布尔会得到另一条线的价格。
3. 只改 `prices.indexTokenPrice.min/max`，Long 从当前价向下、Short 向上二分。
4. 二分到 1 wei，同时记录"最后安全价"与"第一个可清算价"，并记下第一个可清算价返回的 `reason` 与 `info` 三元组。
5. 展示值必须落在这两个边界的显示舍入区间内；断言"清算价等于某个数"必须写成区间断言。

**Reader 不是执行等价物**，两处已知差异（详见 `Liquidation-(v0.3.2).md` §6.2）：

- `Reader.sol::isPositionLiquidatable` 先 `PositionStoreUtils.get` 再直接判定，**不预先推进 Funding**；`PositionPricingUtils.sol::getPositionFees` 取的是已持久化的 `getNegativeFundingFeePerSize / getPositiveFundingFeePerSize`。真实清算交易在判定前会先更新 Funding。同一 oracle 报文下两者可以不同号。
- Keeper 预检传的是 `(false, true)`，与链上的 `(true, true)` 不同，只因全局 `MIN_COLLATERAL_USD` 触线的仓位会被预检漏掉。

### 18.4 v0.3.2 相对 v0.3.1：清算阈值本身在移动

`isPositionLiquidatable` 在 v0.3.2 只改了两处（v0.3.1↔v0.3.2 逐行 diff 确认），但两处都直接移动清算价：

| 改动 | v0.3.1 | v0.3.2 | 对清算价的方向 |
| --- | --- | --- | --- |
| 合成订单的 `orderType` | 不设置（枚举零值，即 `Order.OrderType.MarketIncrease`；`OrderType` 中**没有** `MarketSwap` 成员）→ 非清算单 → `allowNegativeSpread = true` | `cache.params.order.setOrderType(Order.OrderType.Liquidation)`，**无条件、与 `forLiquidation` 入参无关** → `allowNegativeSpread = false`，`minD'` 抬到 0 | 配置了负 `minDynamicSpread` 的市场：Long 判定成交价从 `min×(1−d_neg) > min` 降到 `≤ min`，Short 从 `max×(1+d_neg) < max` 升到 `≥ max`，**两个方向都变严**，清算价向现价靠拢 |
| `cache.balanceWasImproved` | 声明后从未赋值，恒 `false` → 仓位费恒取 `positionFeeFactorKey(marketIndex, false)` 档 | `= executionPriceResult.balanceWasImproved`，进入 `getPositionFeesAfterReferral` 选档 | 整仓平仓在**持仓占优的一侧**时通常判 improved → 取 improved 档费率（配置约定更低）→ `F` 变小 → **清算价远离现价**；在少数派一侧则仍是 notImproved 档 |

两处方向相反，净效果只能逐市场读键定：`minDynamicSpread(marketIndex, isLong)`、`maxDynamicSpread(marketIndex, isLong)`（**分方向**两个键）、`positionFeeFactorKey(marketIndex, true/false)` 两档。合约不校验 `notImproved ≥ improved`（§17.6），也不校验 `minCollateralFactorForLiquidation ≤ minCollateralFactor`（§11.2）；配反了闭式仍然成立，只是方向直觉反过来。

18.3 已证明 `balanceWasImproved` 在整仓清算下与价格无关，所以它在一次二分里是常量——**但它随 OI 变化**，任何改变多空 OI 的交易（包括别人的开平仓）都会翻档，清算价随之跳变。用例必须把 OI 快照与清算价快照绑在同一区块。

### 18.5 前端两条路径与合约的项级对照

前端有两套清算价实现，**界面归属见 [FX100-前端代码公式.md](./FX100-前端代码公式.md) §6 的表**；本节只做与合约的项级对照。两点补充事实（同一 head 源码亲验）：多个界面实际是 **Path A 优先、Path A 返回 `undefined` 时才回退 Path B**（`OrderPreview.tsx` 的 `preview?.liquidationPrice` 优先、`PositionLeverageDialog.tsx` 的 `sdkEstimatedLiq ?? estimatedLiq.newLiqPrice`），不是固定二选一；核对时按"该界面这一次实际取到哪个值"取基准，两条都要能对上。

**Path A**（`packages/sdk/src/utils/positions.ts::getLiquidationPrice`，bigint 全程）与 §18.2 闭式同构。令 `L = liquidationCollateralUsd`、`I = priceImpactDeltaUsd`、`F_ui = totalPendingFeesUsd + closingFeeUsd`，展开后：异币种多头 `(S + L + F_ui − I − C) / Q`（源码写成 `(L − remainingCollateralUsd + S) / Q`，`remainingCollateralUsd = C + I − F_ui`），同币种多头 `(S + L + F_ui − I) / (Q + A × scale)`——与 18.2 的 `N⁺ / Q`、`(S + T* + F − Fp) / (Q + A×scale)` 逐项对得上，只差下表列出的项。逐项差异：

| 项 | 合约判定（`PositionUtils.sol::isPositionLiquidatable`） | Path A | 影响 |
| --- | --- | --- | --- |
| 维持线 | `max(MIN_COLLATERAL_USD, ⌊S×mcf_liq/1e30⌋)`，`MIN_COLLATERAL_USD` 由 `shouldValidateMinCollateralUsd` 开关 | `liquidationCollateralUsd = max(applyFactor(S, mcf_liq), minCollateralUsd)`，**恒含地板** | 与真清算 gate 一致；但下单预览调用点传 `minCollateralUsd: 0n`（`useCreateOrder.ts`），小仓位预览会丢掉绝对地板、清算价偏乐观 |
| 平仓位费 | `⌊⌊S×factor/1e30⌋ / colPrice.min⌋ × colPrice.min`，档位取**实际** `balanceWasImproved` | `getPositionFee(marketInfo, S, false, referral).positionFeeUsd`，**档位写死 `false`**、USD 口径单次 `applyFactor` | improved 市场上高估费用 → 清算价偏保守；抵押品脱锚时两次 floor 的尾差另计（§8 已述，先统一口径再比） |
| 返佣折扣 | 由链上 `ReferralUtils.getReferralInfo` + Pro 档决定 | **调用点不一致**：持仓面板（`packages/sdk/src/modules/positions/positions.ts`）传真实 `userReferralInfo`，`PositionMarginDialog` / `PositionLeverageDialog` / `useCreateOrder` 均传 `undefined` | 同一仓位在持仓行与弹窗里可以显示两个清算价，差额恰是折扣项；不是缺陷但必须按界面分别取基准 |
| 负 Funding | `fees.funding.negativeFundingFeeAmount` 含在 `totalCostAmount` 内 | `pendingFundingFeesUsd` 计入 `totalPendingFeesUsd` | 口径一致 |
| **正 Funding** | `+ positiveFundingFeeUsd`（`.max` 折 token、`.min` 折回 USD） | **函数签名里根本没有这个入参** | Path A 系统性少算一项抵押 → 多头显示的清算价偏高、空头偏低，**两个方向都偏保守（显示更接近现价）**；净收 Funding 的仓位偏差最大 |
| Borrowing | v0.3.2 `PositionPricingUtils.PositionFees` **无 `borrowing` 字段**，合约不结算 | `pendingBorrowingFeesUsd` 参与 `totalPendingFeesUsd` | 对 v0.3.2 ABI 恒解析为 `0n`，当前不产生偏差；一旦后续版本接上会立刻分叉，不能因为"现在为 0"就从核对项里删掉 |
| 价格冲击 | v0.3.2 **没有**加性 price impact 项，冲击只体现为成交价上的 `dynamicSpread` | `priceImpactDeltaUsd` 三分支（`maxPositionImpactFactorForLiquidations` 上限、`getPriceImpactForPosition` 的 `positionImpactFactorPositive/Negative` + 指数模型、`pendingImpactAmount`，正向归零、负向夹到上限） | **该模型是 v0.3.2 上的死代码**：`MAX_POSITION_IMPACT_FACTOR_FOR_LIQUIDATIONS` 与 `POSITION_IMPACT_FACTOR` / `POSITION_IMPACT_EXPONENT_FACTOR` 在 `src/` 里只有 `FX100Keys.sol` 的定义与 `MarketUtils.sol` 里**无调用方**的 getter；`Position.Numbers` 也没有 `pendingImpactAmount` 字段（SDK 读到的恒为 `0n`）。所以正常部署下 `I = 0`；**但若测试环境把这些遗留键配成非零值，页面清算价会移动而链上判定纹丝不动**——这是一条只能靠"读键确认为 0"排除的陷阱 |
| `dynamicSpread` | 判定成交价含 `d`，且清算路径 `minD' = 0` | **完全没有** | Path A 反解的是"成交价 = index 价"的近似；`d ≠ 0` 时与二分结果分叉，`constantPriceSpread` 越大分叉越大 |
| PnL cap | 盈利侧按 `MAX_PNL_FACTOR_FOR_TRADERS` 缩放 | 无 | 清算边界在亏损侧，通常无影响（见 18.2 末） |
| 精度 | 整数运算 | 分支末尾是 `(分子 / 分母) × 10^posSizeDecimals`——**先除后乘** | 截断发生在乘回标度之前，最多损失 `10^posSizeDecimals` 个 wei（相对误差 ~1e-16），逐 wei 比对时要按此放宽 |

**Path B**（`apps/fx-base-app/src/components/features/trade/_position/liqPriceUtils.ts::estimateNewLiqPrice`）：

```text
Long ：liqPrice = entryPriceUsd × (1 − 1/leverage)
Short：liqPrice = entryPriceUsd × (1 + 1/leverage)
entryPriceUsd = Number(formatUnits(entryPrice, 30)) × visualMultiplier   ← JS 浮点
```

它忽略 `mcf_liq`、平仓费、Funding、price impact，也没有同币种分支——等价于把 §18.2 的 `T*` 和 `F` 全部置零、`C` 取杠杆分母。**任何情况下不要拿 Path B 当 parity 基准**；它是浮点，与 bigint 路径只能比到显示精度。方向上它系统性偏乐观（清算价离现价更远，示例见 18.6）。

### 18.6 数值示例（自验）

沿用 §11.6 的同一组数，改为反解清算价。USDC 抵押（6 位，先设 `colPrice.min = max = 1e24`，即 $1），index token 按 18 位登记（价标度 `1e12` / USD），BTC 多头，`d = 0`。

```text
S = 1e34 (10,000 USD)      Q = 1e17 (0.1 BTC)      隐含 entry = S/Q = 1e17 (100,000 USD)
A = 5.5e8 (550 USDC)       negativeFundingFeeAmount = 1e6 (1 USDC)   positive = 0
positionFeeFactor(false) = 6e26 (0.06%)   mcf_liq = 5e27 (0.5%)   MIN_COLLATERAL_USD = 1e31 (10 USD)

positionFeeAmount = ⌊⌊1e34 × 6e26 / 1e30⌋ / 1e24⌋ = ⌊6e30 / 1e24⌋ = 6e6
totalCostAmount   = 6e6 − 0 + 1e6 = 7e6
C  = 5.5e8 × 1e24 = 5.5e32          F  = 7e6 × 1e24 = 7e30          Fp = 0
T  = max(1e31, ⌊1e34 × 5e27 / 1e30⌋) = max(1e31, 5e31) = 5e31       T* = 5e31

N⁺     = S + T* + F − C − Fp = 1e34 + 5e31 + 7e30 − 5.5e32 = 9.507e33
P_safe = ⌈9.507e33 / 1e17⌉ = 9.507e16     → 95,070.000000000000000000 USD/BTC
P_liq  = 9.507e16 − 1
```

回代验证（用 §11.1 的正向式子）：

```text
P = 9.507e16 ：positionValue = 1e17 × 9.507e16 = 9.507e33
               PnL = 9.507e33 − 1e34 = −4.93e32
               remaining = 5.5e32 − 4.93e32 + 0 − 7e30 = 5e31 = T*
               ① 5e31 < 1e31？否   ② 5e31 <= 0？否   ③ 5e31 < 5e31？否（严格小于）→ 不可清算 ✓

P = 9.507e16 − 1：remaining = 5e31 − 1e17
               ① 否   ② 否   ③ 5e31 − 1e17 < 5e31 → 可清算，reason "min collateral for leverage" ✓
```

量纲自检：`5.5% (=550/10000) − 0.5% (mcf) − 0.07% (费+Funding) = 4.93%`，`100,000 × (1 − 4.93%) = 95,070` ✓。

**三条路径在同一仓位上的对照**：

```text
合约二分边界                       95,070.00
Path A（I=0、Fp=0、无折扣、d=0）   ((5e31 − (5.5e32 − 1e30 − 6e30) + 1e34) / 1e17) × 1e18
                                 = (9.507e33 / 1e17) × 1e18 = 9.507e34 → 95,070.00   ← 逐 wei 相等
Path B（面板杠杆 = ⌊1e34 × 10000 / 5.49e32⌋ = 182149 BPS = 18.2149x）
                                 100,000 × (1 − 1/18.2149) ≈ 94,510.0 → 偏乐观 560 USD（0.59%）
                                 （1/leverage 恰为 549/10000 = 5.49%，BPS 取整与浮点只影响末位）
```

**Path A 在"点差为 0、正 Funding 为 0、遗留 impact 键为 0、无返佣"时与合约逐 wei 相等**——18.5 表里那些差异项就是唯一的分叉来源。逐项打开验证：

```text
正 Funding 打开（positiveFundingFeeAmount = 2e6，即 Fp = 2e30）：
    合约 N⁺ = 9.507e33 − 2e30 = 9.505e33 → 95,050.00
    Path A 不变                          → 95,070.00（高估 20 USD/BTC，多头方向偏保守）

抵押品脱锚（tx-fork 实配 colPrice.min = 9.99e23、max = 1.001e24，即 $0.999 / $1.001）：
    C  = 5.5e8 × 9.99e23 = 5.4945e32
    positionFeeAmount      = ⌊6e30 / 9.99e23⌋ = 6,006,006
    negativeFundingFeeAmount = ⌈1e30 / 9.99e23⌉ = 1,001,002    ← 与费用同样按脱锚价折算，不能沿用 $1 下的 1,000,000
    totalCostAmount = 6,006,006 + 1,001,002   = 7,007,008
    F  = 7,007,008 × 9.99e23 = 7.000000992e30
    N⁺ = 1e34 + 5e31 + 7.000000992e30 − 5.4945e32 = 9.507550000992e33 → 95,075.50（比 $1 假设高 5.50 USD/BTC）
```

抵押品按 `$1` 硬算是一类系统性误差：**`tx-fork` 的共享 USDC Mock Oracle 就配了 `min = 9.99e23`、`max = 1.001e24`（`TestCode/config/mock-resources.json`），链上从来不是 $1**。

### 18.7 清算距离、保护期与前端状态

```text
Long  liquidationDistance = (markPrice − liquidationPrice) / markPrice
Short liquidationDistance = (liquidationPrice − markPrice) / markPrice
```

锚点 `liqPriceUtils.ts::liqDistancePercent`（×100 输出百分比，`markPriceUsd == 0` 返回 0），配套的 `::liqPriceFromMarkPercent` 把方向无关的"安全距离"翻成"清算价相对现价的带符号位置"（多头安全时为负、空头安全时为正）——**两个量正负号约定不同，混用会把安全仓位标成危险**。距离用的 `markPrice` 是中间价选边结果（前端 §1），与判定用的 `min/max` 不是同一个数，距离本身只是 T3 展示量。

**保护期**（`IncreaseOrderUtils.sol::processOrder` 的 `position.account() == address(0)` 分支，只在**仓位首次创建**时写；`LiquidationUtils.sol::createLiquidationOrder` 的闸门）：

```text
graceStart = block.timestamp
graceEnd   = block.timestamp
           + ⌊ liquidationGracePeriodBaseKey(marketIndex)
               × liquidationGracePeriodTierMultiplierKey(referrerTiers(account)) / 1e18 ⌋

拒绝条件：position.graceEnd > block.timestamp → revert PositionNotLiquidatable(positionKey)
graceRemaining = max(0, graceEnd − blockTimestamp)
```

`graceEnd − 1` 仍受保护；`graceEnd` 与 `graceEnd + 1` 放行进入后续判定（"放行"不等于"一定被清算"，仍要过三条件）。加仓、减仓、加/减保证金、页面刷新、oracle 更新都**不重置**；配置或 tier 事后变化也不回写存量仓位；全平删仓后重开算新仓位，按当时配置重新生成。

**前端的 15 分钟是兜底常量，不是链上事实**：`apps/fx-base-app/src/lib/liquidationProtection.ts` 的 `DEFAULT_LIQUIDATION_PROTECTION_SECONDS = 15 * 60` 只在 `graceStart` 缺失时用来倒推窗口起点；`graceEnd <= 0` 时整个窗口返回 `null`（无保护，不是默认 15 分钟）。任何"新仓自动 15 分钟"的文案都必须回读 `liquidationGracePeriodBaseKey` × tier multiplier 验证。

**页面状态不是链上枚举**。合约没有 `safe / near / liquidatable / liquidating / liquidated` 任何一个字段；已清算只能由"Position 消失 + 同一 orderKey 上 `OrderCreated.orderType == Liquidation` 与 `PositionDecrease.orderType == Liquidation` 的事件链"证明（`Liquidation-(v0.3.2).md` §6.4）。当前实现：

- `liqPriceUtils.ts::isPositionLiquidatable`（**同名不同物**，与合约函数无关）判据是 `netValue <= 0` **或** mark 价越过本地估算的清算价，**不是 Reader bool**；
- 徽标另有一层抑制：`lib/liquidationProtection.ts::isLiquidatableBadgeVisible` 在保护期内隐藏 `Liquidatable` 徽标，只保留红色清算价与倒计时。所以"红色清算价 + 无徽标"是保护期内的正常态，不是漏显示。

因此页面的 `Liquidatable` 只能标为本地估算/GAP，不得断言成"Reader 判定可清算"；用例要把"本地估算态""Reader 预检 bool""链上执行结果"分三列记录。

### 18.8 风险面板上的其它展示量

`Unrealized PnL` / `ROE` 的定义与合约整仓 PnL 的三处差别见 §17.5，`Net Value` / `Est. Receive` 的展示式、`processCollateral` 的实际结算顺序与 `_validateOutputAmount` 闸门见 §17.6，本节不重复。风险面板特有的一个陷阱必须在这里讲清：

**同一行里有三个都叫"净值"的数，互不相等**：

| 出处 | 表达式 | 用途 |
| --- | --- | --- |
| 合约 `PositionUtils.sol::isPositionLiquidatable` 的 `remainingCollateralUsd` | `C + Fp − F + 整仓平仓执行价 PnL` | **唯一的清算判定基准** |
| SDK `packages/sdk/src/utils/positions.ts::getPositionNetValue` 的 `netValue` | `collateralUsd − 待付 Funding − 待付 Borrowing − closingFee − uiFee + pnl + impact 两项` | 驱动 `Liquidatable` 判定与徽标 |
| App 面板显示的 `Net Value`（`liqPriceUtils.ts::getPositionPanelNetValueUsd`） | `getPositionMarginUsd + unrealizedPnlUsd − getPositionCloseFeeUsd` = `(C + 正 Funding − 负 Funding) + uPnL − 平仓费` | **只是屏幕上那一列** |

判定用的是第二个，显示的是第三个，两者相差一项**正 Funding**（v0.3.2 上 borrowing 与 impact 恒为 0，uiFee 在无 uiFeeReceiver 时为 0，所以差额通常就是 `pendingPositiveFundingFeesUsd`；`closeFee` 两侧取的档位来源也不同——SDK 走 `getPositionFee(..., false, referral)`，面板走 `lib/orders/leverage.ts::getPositionFeeRate` 且不含返佣）。后果：**净收 Funding 的仓位会出现"屏幕上的 Net Value 还是正数、`Liquidatable` 徽标已经亮起"**——这不是渲染 bug，是两个不同的量。核对时必须点名取哪一个，`remainingCollateralUsd` 这个名字在本系统里还有第三个含义（`willPositionCollateralBeSufficient` 的返回值），命名陷阱表见 §17.4。

需求侧对这一层是有意识的（持仓面板口径规范 §4.2：「Net Value 是导航仪不是判决书」），但它给的兜底——「清算真值以 Liquidatable 徽章和清算价为准（它们按合约口径算）」——**在当前实现上不成立**：徽章走的是上表第二行的本地 `netValue` 加本地估算清算价（18.7），不是合约口径，也不是 Reader bool。同一份需求还把"判定不计应收"列为待修复的临时差异，而合约侧 v0.3.1 起就已计入——这条差异如今只留在前端 `getPositionNetValue` 里。

`Est. Receive` 与清算的交集只有一条：清算是被迫全平，`liquidationFee` 只在**执行**阶段计入（§8），判定阶段恒为 0（`isLiquidation = false`，§11.1）。所以"清算触发时用户还剩多少"必然小于"判定时的 `remainingCollateralUsd`"，两者不可互相代入；insolvent 早退时残值可能为 0 且费用整包不进 claimable（`Liquidation-(v0.3.2).md` §5.4）。

### 18.9 核对清单

| 检查项 | 通过标准 |
| --- | --- |
| 不去找链上清算价字段 | 断言基准是 `Reader.isPositionLiquidatable` 的 bool + `info` 三元组，不是任何"清算价"读数 |
| Reader 入参 | 与要复现的路径配对：真清算 `(true, true)`、开仓校验 `(true, sizeDeltaUsd == 0)`、减仓收尾 `(false, false)` |
| 边界取整 | 多头 `ceil`、空头 `floor`；同时记录"最后安全价"与"第一个可清算价"两笔 |
| 等号语义 | 条件①③ 严格小于（等于不触发），条件② `<= 0`；`T*` 取 `max(阈值, 1)` |
| 抵押品分支 | 先读 `FX100Keys.COLLATERAL_TOKEN` 全局键确认是否同币种，再选分母 |
| 精度标度 | `sizeInTokens` 按 index token 登记 decimals 取，禁止写死 `1e18`；抵押品价按 `.min` / `.max` 分别取，禁止按 $1 硬算 |
| 遗留 impact 键 | 用例环境先读 `POSITION_IMPACT_FACTOR` / `MAX_POSITION_IMPACT_FACTOR_FOR_LIQUIDATIONS` 确认为 0，否则前端与链上必然分叉 |
| 两档费率 | 逐市场读 `positionFeeFactorKey(marketIndex, true/false)`，不假定 improved 档更低 |
| 两条 minCF | 逐市场读 `MIN_COLLATERAL_FACTOR` 与 `MIN_COLLATERAL_FACTOR_FOR_LIQUIDATION`，不假定后者更低——需求文档所称"两者之差即安全缓冲"在链上不成立（`ConfigUtils.sol` 不校验该跨键关系；dev 站 26/26 市场两键同值，缺陷单 `BUG-FE-WDMAXLIQ-024`） |
| 前端基准 | 按界面确定这一次实际取到的是 Path A 还是回退的 Path B；Path B 永不作 parity 基准 |
| 保护期 | 用 `graceEnd` 三点（−1 / = / +1）覆盖；duration 回读链上 base × tier multiplier，不认 15 分钟文案 |
| 净值取名 | 断言里写清是合约 `remainingCollateralUsd`、SDK `netValue` 还是面板 `Net Value` |

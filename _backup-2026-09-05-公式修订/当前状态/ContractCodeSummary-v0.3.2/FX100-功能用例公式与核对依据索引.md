## 0. 三层与权威等级

同一个业务量在三个项目里可能各算一遍，含义与可断言性完全不同。**引用公式前先确认自己引的是哪一层。**

| 层 | 代码 | 等级 | 用途 | 能否作断言基准 |
| --- | --- | --- | --- | --- |
| 合约 | `fx100-contracts` @ `primary.head` | **A** | 链上最终标准 | **是**，0 容差（需同序复刻） |
| 前端 SDK / App | `fx100-apps` @ `frontend.head` | **B** | 页面预估与显示 | 否。只验"算法与合约等价"，不验等于链上（[前端公式](./FX100-前端代码公式.md)） |
| Keeper（决定型） | 同上，`apps/keeper` | **K1** | 输出**进入链上输入**：选中的 oracle 报文、gas limit、时间窗 | 否，但**它是实际值的组成部分**，必须能重算或从提交报文锚定 |
| Keeper（筛选型） | 同上 | **K2** | 只影响何时被处理 / 是否入候选 | **否**，只验"不漏"；用例 FAIL 时作归因候选 |

用例侧对应关系（用例矩阵的「层」列只有合约层/前端层，Keeper 不是层值，它是「入口 = Keeper RPC」的执行角色）：

| 用例前缀 | 引哪层 | 容差 |
| --- | --- | --- |
| `CT-*` 合约层 | A | 0 容差 |
| `FT-*` 前端层 | B（并列出对应 A 用于说明差异项） | 到分 |
| `XT-*` 跨层 | A + B 的验收关系 | 见各主题 |
| 任意用例的实际结果偏离 | 先查 K1/K2 归因表（[Keeper 公式 §10](./FX100-Keeper代码公式.md#10-对测试与核对的影响归因表)） | — |

**三层不要求相等**。以清算价为例，正确的验收关系是：前端预估接近合约边界 · Keeper 不遗漏进入风险区间的仓位 · 最终是否清算完全以合约 Reader 判定为准。

## 1. 页面展示口径

“公式 / 依据”应拆成以下信息，不再把公式、代入值和文字备注混在一个段落里：

| 展示块 | 内容 | 数据要求 |
| --- | --- | --- |
| 计算规则 | 通用公式与方向分支，如 Long Increase 的 `executionPrice` 规则 | 必须来自自动化证据的 `formula`；Reporter 不推导、不改写 |
| 本次代入 | 本次运行使用的输入值、精度、取整方向和计算结果 | 必须记录输入来源与原始整数；不能只保存格式化值 |
| 核对依据 | Reader、事件、余额快照、DataStore 或业务约束 | 对应自动化证据的 `note` / source metadata |
| 公式来源 | 版本、章节、源码路径和 commit | 至少能追溯到本文索引或核心公式总表 |

如果本条证据没有保存单项公式，页面必须显示“本条证据未保存单项公式”，并提供 v0.3.2 核心公式入口。不能因为核对项名称带有 `=`、`Δ` 或计算结果，就反向拼出一条公式。

### 3.1 Keeper 层归因索引（K1 / K2）

以下量**不在合约公式里**，但会改变用例观测到的实际值或时序。断言前先排除它们，再判定为缺陷。

| 现象 | Keeper 侧成因 | 等级 | 章节 |
| --- | --- | --- | --- |
| 执行价对不上"按某个 oracle 快照算的期望" | 提交哪份报文由 Keeper 按方向挑极值 | K1 | [§1 价格报文选择](./FX100-Keeper代码公式.md#1-价格报文选择k1) |
| 清算实际发生价与页面预估有 bp 级差 | 清算路径取**最新有效**报文，不做方向极值 | K1 | [§1.2](./FX100-Keeper代码公式.md#12-side-选法分支表多条件) |
| TP/SL 减仓单失败一次后成功 | oracle 时间窗未覆盖 `positionIncreasedAtTime` 下界（已知缺口） | K1 | [§2 oracle 时间窗](./FX100-Keeper代码公式.md#2-oracle-时间窗下界k1) |

## 4. 自动化证据建议字段

后续核对引擎可逐项补齐以下字段；Reporter 只负责展示：

```json
{
  "name": "执行价格",
  "status": "PASS",
  "before": null,
  "after": "2032740628092499",
  "expected": "2032740628092499",
  "formula": "Long executionPrice = ceil(indexPrice.max × (1e18 + dynamicSpread) / 1e18)",
  "formulaInputs": [
    { "name": "indexPrice.max", "value": "...", "source": "Oracle snapshot" },
    { "name": "dynamicSpread", "value": "...", "source": "independent calculation" }
  ],
  "formulaBasis": {
    "release": "v0.3.2",
    "section": "4.5 加仓成交价",
    "sourcePath": "TestCase/E2E/ContractCodeSummary/v0.3.2/FX100-核心字段计算公式.md",
    "contractCommit": "13880f2416918f4fed3fea86d7f1023084a3ce0d"
  },
  "note": "原始整数按 Index Token Decimals = 18 展示；本次使用向上取整"
}
```

最低要求：

1. `formula` 只保存真实执行或独立预期值计算使用的公式。
2. `formulaInputs` 必须保留原始整数、单位、decimals、来源区块和取整方向。
3. `note` 用于解释核对依据或异常，不承担公式字段职责。
4. `formulaBasis` 必须绑定 release 与 commit；部署参数另绑 environment、deployment ID 和 blockNumber。
5. 只有 Actual 与 Expected 来自相互独立的读取/计算路径时，才能标记为独立核对通过。

## 5. 推荐计算与核对顺序

一条交易用例统一按以下顺序生成证据：Oracle → 数量单位转换 → OI / Skew → 动态点差 → 成交价 → PnL → Funding → 费用 → 抵押品与输出 → OI / Vault / 账本 → Keeper fee → 余额、DataStore、Position 与事件四层断言。

完整细节见[核心公式 §23](./FX100-核心字段计算公式.md#23-e2e-预期值计算顺序)。

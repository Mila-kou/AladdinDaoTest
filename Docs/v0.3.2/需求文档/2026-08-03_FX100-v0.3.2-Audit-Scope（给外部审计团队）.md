## 3. Known caveats and design notes for the audit team

### 3.1 Referral module — inert by configuration, not by code

`src/referral/ReferralUtils.sol` is a library compiled into in-scope contracts: `PositionPricingUtils.getPositionFees` computes referral discounts/affiliate rewards on every trade, and `ExchangeRouter.claimAffiliateRewards` can transfer accrued rewards out of `PositionVault`. These referral code paths can be treated as out of scope under the following **operational constraints, which we commit to for this release**:

- Referral tiers remain unconfigured (tier `totalRebate = 0`), so all referral discount/reward amounts compute to zero.
- The `claimAffiliateRewards` feature can additionally be disabled entirely via a dedicated feature-flag DataStore key.

The referral module will be redesigned and audited separately before activation.

### 3.2 Foundational design principles

A few things worth knowing up front, since they shape a lot of the rest of the design:

- **USDC is the only collateral/settlement asset in the entire protocol.** Every LP deposit, every position's collateral, every PnL settlement is denominated and paid in USDC — index tokens (BTC, ETH, etc.) are pure price references for cash-settled synthetic perpetuals; there is no physical delivery of the index asset and no multi-collateral support anywhere. `MarketFactory.createMarket` enforces this directly (collateral token is validated against the vault's single asset at market-creation time). One nuance worth flagging: USDC's own price is still oracle-fed (via the same Chainlink/Pyth providers, with a "stablecoin band" clamp toward a reference price), not hardcoded to exactly `$1` — a severe USDC depeg would flow through into every pool/position USD valuation in the system, same as any other asset.
- **Every market shares exactly one LP vault, enforced architecturally, not just assumed.** `MarketFactory.vault` is set once at construction and is `immutable` — every market created by a given factory deployment shares that one vault. This is the load-bearing assumption behind the protocol's global risk-ratio computation (which sums exposure across every market against pooled collateral) — please flag any path where a market's accounting could diverge from this.
- **One net position per (account, market, side) — no hedge-mode / multi-position model.** Position keys are `keccak256(account, marketIndex, isLong)` — deterministic, no nonce/counter. Re-opening the same side always merges into the existing position rather than creating a new one; a user can hold at most one long and one short position per market simultaneously, never more than one of each.

### 3.3 Known configuration footguns

Several DataStore parameters default to `0` when unconfigured, and a `0` default silently produces an extreme, easy-to-miss behavior rather than a safe default. These need to be on the deployment checklist as explicit-configuration-required per market:

- `EXECUTION_FEE_SUBSIDIZE` / `EXECUTION_FEE_SUBSIDIZE_SIZE` unset (=`0`) → **all orders in that mode are fee-waived** (unlimited free execution).
- `MAX_RELAY_SWAP_WNT_CAP` unset (=`0`) → **no cap** on relay swap amounts.
- `MIN_DYNAMIC_SPREAD` / `MAX_DYNAMIC_SPREAD` unset (=`0`/`0`) → the clamp collapses to exactly `0` regardless of the underlying computed value, meaning **all spread cost (constant + price-impact + skew-impact) is silently zeroed out for every trade on that market** — not a partial/rebate-only effect, but fully free execution with no spread cost at all. `scripts/parameters/market.sample.json` sets explicit non-zero values for the markets it covers, so tooling to configure this correctly exists — per-market onboarding must not skip it.

### 3.4 Recorded-price keeper — single point of failure with global blast radius

`AdlHandler.refreshLatestRecordedPrices` is a fully permissionless function (anyone can call it) that exists because `Oracle.latestRecordedPrices[token]` only updates as a side effect of organic trading — thinly-traded markets need this function called periodically by an off-chain keeper to keep their cached price fresh. If that keeper stops, and any single one of the currently-listed markets' cached price exceeds `MAX_RECORDED_PRICE_AGE` (24h in production config), the protocol's global risk-ratio computation reverts entirely — which freezes LP withdrawals and ADL state updates **across every market**, not just the stale one. This is an off-chain-liveness-dependent global blast radius worth explicit attention, even though nothing here is a code defect per se.

### 3.5 `MarketUtils.settleFundingFees` — real value-transfer on a very hot path

This function settles realized position funding against the LP vault: it transfers tokens out of the LP vault to the position vault (or increments claimable protocol-fee accounting for the opposite sign), based on the net of `positiveFundingFeeAmount`/`negativeFundingFeeAmount` passed in from the caller. It's called from both `IncreasePositionUtils.increasePosition` and `DecreasePositionCollateralUtils.processCollateral` — i.e., on every position increase/decrease where funding is realized, which is a very common case. Recommend auditors specifically check: reentrancy around the transfer call, and correctness of the sign/magnitude computed at each call site.

### 3.6 Dynamic spread can be negative for voluntary trades; liquidation/ADL execution stays floor-at-0

`PositionPricingUtils.getDynamicSpread` returns a signed value (`int256`). Two DataStore keys, `MIN_DYNAMIC_SPREAD`/`MAX_DYNAMIC_SPREAD` (configured per market × long/short), bound the result. An `allowNegativeSpread` flag — derived from whether the order is a liquidation order or an ADL order — forces the effective minimum back to `0` for those forced-close paths, so liquidation/ADL execution can never be better than the oracle price, while ordinary voluntary trades can receive a negative spread (effectively a rebate) when they improve the market's balance. **By design, the positive-side cap (`maxDynamicSpread`) is shared between liquidation/ADL and ordinary trades — it is not independently exempted for forced closes.** See §3.3 for the associated zero-configuration footgun.

### 3.7 Subaccount delegation is bounded to 4 named slots per account

`SubaccountUtils` enforces a hardcoded `MAX_SUBACCOUNT_SLOTS = 4` — each slot is identified by a caller-supplied string name, matched by string equality against existing active slots or claimed as the first inactive slot; `MaxSubaccountSlotsExceeded` reverts once all 4 are active for an account, and `DuplicateSubaccount` reverts if the same subaccount address is already bound to a different slot for that account. Worth dedicated review: the slot-matching logic, the duplicate-subaccount check, and whether removing/re-adding slots can leave stale active-flag/subaccount-address state behind.

### 3.8 Price-impact exponent is explicitly bounded before use

`PositionPricingUtils.getPriceImpactSpread` computes its exponent via `Math.mulDiv` (full-precision, avoids intermediate-multiplication overflow) and explicitly checks the result against `LogExpMath`'s domain limit before calling `exp`, returning the configured `MAX_PRICE_IMPACT_SPREAD` cap directly if the exponent would exceed it. This sits on the `isPositionLiquidatable` call path, so it's worth confirming this bound is airtight — a revert here would make liquidation itself unexecutable for the affected market.

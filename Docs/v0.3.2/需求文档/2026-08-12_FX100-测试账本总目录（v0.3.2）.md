- **是**：一份可审计、可增量维护的测试清单——按 `test/` 目录结构 1:1 拆成 50 份子文档（`docs/testing/catalog/`），每份子文档逐条列出该目录下所有测试函数、对应的 `src/` 源码文件、业务语言的一句话说明、当前通过/失败/跳过状态。

## 五、数据生成方法（如何刷新这份目录）
所有"通过/失败/跳过"状态与用例清单均来自脚本化流程，**不是人工维护**：
```bash
# 1. 跑全量测试，导出逐用例 JSON 结果
forge test --json > /tmp/full_results.json

# 2. 解析 + 按 test/ 目录分组 + 抓取每个测试文件的 src/ 依赖，生成 51 组 manifest
python3 scripts/testing/generate_test_catalog_manifests.py /tmp/full_results.json docs/testing/catalog/_data

# 3. 每组 manifest 对应 docs/testing/catalog/<group>.json，
#    人工/LLM 据此撰写或更新 docs/testing/catalog/<group>.md（业务语言说明 + 状态列，状态必须与 manifest 完全一致）
```
`scripts/testing/generate_test_catalog_manifests.py` 已提交入库，任何时候想刷新本目录（比如新增了一批测试），重新跑上面三步即可——第 2 步是纯脚本、结果 100% 可复现；第 3 步的"业务语言说明"部分仍需人工/LLM 撰写，但状态列不需要，脚本产出的 manifest 就是唯一真相来源。
**新增测试时的维护约定**：
1. 新测试文件加入某个已有目录（如新增一个 `test/unit/oracle/XXX.t.sol`）→ 重新生成该组 manifest，在对应子文档追加一个 `## test/unit/oracle/XXX.t.sol` 小节。
2. 新测试目录（如 `test/unit/newmodule/`）→ 按本文档 §三 的分组规律新建一份 `docs/testing/catalog/unit/newmodule.md`，并在本文件 §二/§三 补充一行。
3. 任何一条状态从 ✅ 变成 ❌/⏭（或反之）→ 更新对应子文档该行状态，并同步维护 §四 的非通过清单。
4. **每个新增的 `## \<test-file-path>` 小节必须包含一段 `**测试目的与范围**：...` 段落**（紧跟在 `对应源码：` 行之后、用例表格之前），用业务语言说明这批测试为什么写、想守住什么风险或不变量，不要只是逐行复述表格里已有的用例说明——这段文字会被 `scripts/testing/build_test_ledger_page.py` 解析并显示在网页的文件分组标题下。
5. 网页里每条测试用例的可展开代码详情是 `build_test_ledger_page.py` 在生成阶段自动从对应 `.t.sol` 文件里按函数名提取的（brace-matched 提取），不需要人工维护——只要子文档里的测试函数名与 `.t.sol` 里的真实函数名一致即可自动生效。

## 六、与其他测试文档的关系
- `docs/analysis/<module>/<module>.md` 的"测试重点"章节：偏重"这个 src 模块该测哪些场景、是否有已知缺口"的设计视角（可能包含尚未实现的测试建议）；本目录偏重"现在实际存在哪些测试、跑起来是什么状态"的现状快照，两者互补，不重复维护。
- `docs/analysis/BUGS_AND_ISSUES.md` / `docs/analysis/BUG_MANAGEMENT_GUIDE.md`：bug 本身的详细描述、严重程度、修复建议；本目录只做"测试用例 ↔ bug 编号"的快速定位（§四）。
- `docs/reports/2026-07-16-v030-test-implementation-report.md`（"PR #4 测试实施报告"）：面向 v0.3.0 版本发布的验收报告，按 17 个变更点组织；本目录是版本无关的、持续维护的全量现状快照。

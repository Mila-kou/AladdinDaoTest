## 一、架构背景（为什么不能沿用 GMX 公式）
FX100 与 GMX v2 的两个根本差异决定了风控公式必须改造：
维度 │ GMX v2 │ FX100
抵押品池 │ 双资产：多头池 WETH、空头池 USDC，赔付路径分侧配对 │ **单资产：所有市场共用一个 USDC LP 池**
LP 份额定价 │ GLP 定价包含 pending PnL（scaling 可配） │ **\`pendingPnlScalingFactor = 0\`**：NAV = totalAssets / totalSupply，不含 pending PnL
由此产生两个核心结论：
1. **单边口径双重计账**：GMX 的 PnL 检查全是单边（`isLong`），单边对单池是对的；FX100 多空共用一个池，每边各拿全池做分母 = 池容量被计两次。多头均价 \< 现价 \< 空头均价时多空**同时盈利**，两边各 0.5×pool 不触发任何单边阈值，但 LP 实际义务已达 1.0×pool。→ 风控度量必须改为**净义务口径**（sum 正 PnL）。
2. **多空天然对冲**：LP 真正要赔付的是盈利侧的净 PnL，不是名义 OI。多空平衡时即使名义 OI 远超 poolUsd，LP 实际风险极低。→ 容量参数可以 \> 1，资本效率远高于 GMX。

## 二、风控参数总览（改造后全部参数）
参数 │ 键维度 │ 口径 │ 建议值 │ 作用
`RESERVE_FACTOR` │ per-market（不分 isLong） │ 多空**合计**名义 OI / poolUsd │ 1.0\~1.5（起步）→ 3.0（成熟） │ 市场容量上限，开仓时检查
`MAX_PNL_FACTOR_FOR_ADL` │ **全局单键** │ 全局净义务比 `Σ net_i / poolUsd` │ 0.75 │ ADL 触发门槛
`MIN_PNL_FACTOR_AFTER_ADL` │ **全局单键** │ 全局净义务比 │ 0.50 │ ADL 退出水位
`MAX_PNL_FACTOR_FOR_WITHDRAWALS` │ **全局单键** │ 全局净义务比 │ 0.65 │ LP 提款（claim）封锁门槛
`MAX_PNL_FACTOR_FOR_TRADERS` │ per-market × isLong（维持现状） │ 单边 │ 0.90 │ 结算 PnL 硬上限，最后被动防线
要点：
- **没有** `NET_RESERVE_FACTOR`（不引入）。
- **没有** `MAX_PNL_FACTOR_FOR_DEPOSITS`（删除现有死代码键）——存款不设任何 gate（§六）。
- 4 个 PnL 参数与市场数量无关，新上市场只需配 `RESERVE_FACTOR` 和 `MAX_OPEN_INTEREST`，不动任何 PnL 参数。
- 参数水位关系：`AFTER_ADL(0.50) < WITHDRAWALS(0.65) < ADL(0.75) < TRADERS(0.90)`。

## 三、核心概念：净义务
### 3.1 定义
```plain text
per-market 净义务: net_i = max(0, longPnl_i) + max(0, shortPnl_i)
全局净义务比:      pnlRatio = Σ_i net_i / poolUsd

poolUsd = vault.totalAssets() × USDC 价（现有 getPoolUsdWithoutPnl，单池，无 isLong）
```
### 3.2 PnL 的精确口径（重要，避免误解）
`longPnl_i` / `shortPnl_i` **直接复用现有 \`getPnl\`**（`MarketUtils.sol` 内已实现），它是**该侧全部仓位的聚合净值**：
```solidity
// O(1)：只读两个累计量，无仓位遍历
int256 openInterest = getCumulativeOpenCosts(dataStore, marketIndex, isLong);   // 该侧累计开仓成本
uint256 openInterestInTokens = getOpenInterestInTokens(dataStore, marketIndex, isLong);
int256 openInterestValue = openInterestInTokens × price;                        // 该侧当前总价值
pnl = isLong ? openInterestValue − openInterest : openInterest − openInterestValue;
```
- **侧内盈亏互抵**：同侧内 A 仓位 +100、B 仓位 −60 → 该侧 PnL = +40。不是"逐仓位挑盈利求和"（那需要 O(N) 遍历仓位，链上不可行）。
- **跨侧不互抵**：max(0,·) 分别取正后相加，多空同时盈利时义务叠加。
- 经济含义：该侧全部仓位以当前价同时平仓时 LP 的净支付额。亏损仓位的抵扣以其抵押品为上限，由清算引擎保证（与 GMX 同假设，无需额外处理）。
### 3.3 状态机（全局 pnlRatio 驱动）
```plain text
状态一（Safe）:   pnlRatio ≤ 0.65  → LP 存款✅ / 提款✅ / ADL 不触发
状态二（Danger）: 0.65 < pnlRatio ≤ 0.75 → LP 存款✅ / 提款❌ / ADL 不触发
状态三（ADL）:    pnlRatio > 0.75  → LP 存款✅ / 提款❌ / ADL 触发（策略见 §五）
状态四（Buffer）: ADL 执行后 0.50 ≤ pnlRatio ≤ 0.75 → 提款仍封锁直到 < 0.65

存款任何状态都允许（§六）。
```

## 四、Layer 1 — RESERVE_FACTOR（per-market 容量控制）
### 4.1 语义与公式
`RESERVE_FACTOR_i` = 该市场**多空合计**名义 OI 相对 LP 池的占比上限。开/增仓时校验（与方向无关）：
```plain text
(longOITokens_i + shortOITokens_i) × price.max ≤ RESERVE_FACTOR_i × poolUsd
```
分工：RESERVE_FACTOR 只管"这个市场总共能开多大"；多空偏斜由 funding/skew 定价引导 + 净义务层控制；单边极端集中由 per-side `MAX_OPEN_INTEREST` 硬顶兜底（已实现，不动）。
### 4.2 实现
原 `validateReserve`（双边净 PnL 版）删除；`validateOpenInterestReserve` 改为：
```solidity
function validateOpenInterestReserve(
    DataStore dataStore,
    Market.Props memory market,
    MarketPrices memory prices
) internal view {
    uint256 poolUsd = getPoolUsdWithoutPnl(dataStore, market, prices.collateralTokenPrice, true);
    uint256 reserveFactor = getReserveFactor(dataStore, market.marketIndex);  // per-market，可 > 1

    // 多空合计名义 OI
    uint256 totalNominalOI = (
        getOpenInterestInTokens(dataStore, market.marketIndex, true)
            + getOpenInterestInTokens(dataStore, market.marketIndex, false)
    ) * prices.indexTokenPrice.max;

    uint256 maxAllowed = Precision.applyFactor(poolUsd, reserveFactor);

    if (totalNominalOI > maxAllowed) {
        revert FxErrors.InsufficientReserveForOpenInterest(totalNominalOI, maxAllowed);
    }
}
```
**键**：`FX100Keys.RESERVE_FACTOR(marketIndex)`，不分 isLong。
**取值**：1.0\~1.5 起步，运行稳定后可逐市场调高至 3.0（成熟市场高、新市场保守）。RESERVE_FACTOR \> 1 是安全的——合计名义超池不等于 LP 欠钱，实际义务由 ADL + 提款 gate + TRADERS cap 三层控制。

## 五、ADL（全局触发 + 执行策略）
### 5.1 触发与退出（合约强制）
```plain text
触发: Σ_i net_i / poolUsd > MAX_PNL_FACTOR_FOR_ADL（全局，0.75）
退出: Σ_i net_i / poolUsd ≤ MIN_PNL_FACTOR_AFTER_ADL（全局，0.50）
```
注意是**全局**口径，不是 per-market：净义务的分布动态集中，per-market 阈值无法设置（设高了多个市场各自未达阈值但全局早已超限；设低了单个热门市场被过早 ADL）。
### 5.2 执行策略（Keeper 按此排序，链外监控审计）
层级 │ 选择规则 │ 理由
1. 选市场 │ `net_i` 最大的市场优先 │ 减仓对全局比率的边际效果最大
2. 选方向 │ 该市场内盈利较大的一侧；多空同时盈利时两侧依次 ADL │ LP 义务只来自盈利侧
3. 选仓位 │ 该侧内按盈利率（pnl/size）降序（沿用现有 GMX ADL 排序机制） │ 优先减最暴利仓位
循环 │ 重复 1-3 直到全局比率 ≤ 0.50 │ —
### 5.3 合约 vs Keeper 职责
- **合约强制**（`AdlUtils.validateAdl` / `executeAdl` 改造）：
  1. 全局净义务比 \> `MAX_PNL_FACTOR_FOR_ADL` 才允许执行；
  2. 被 ADL 的目标市场/方向自身 pnl \> 0（亏损仓位永远不被 ADL，其归宿是清算）；
  3. 全局比率 ≤ `MIN_PNL_FACTOR_AFTER_ADL` 后拒绝继续执行（防过度减仓）。
- **Keeper 策略**（链外）：按 §5.2 排序选择目标。排序不写入合约（链上枚举全市场全仓位排序 gas 不可行），由链外监控审计。

## 六、LP 存取款
### 6.1 提款：claim 时检查全局净义务 gate
`LPVault.claimWithdrawRequest()` 新增检查：
```solidity
function claimWithdrawRequest(uint256 requestId, address receiver) external nonReentrant {
    _advanceEpoch();
    // ... existing checks ...
    _validatePnlForWithdrawal();  // Σ net_i / poolUsd ≤ MAX_PNL_FACTOR_FOR_WITHDRAWALS，超限 revert
    // ... 后续提款逻辑
}
```
实现：LPVault 持有 `dataStore`/`oracle` 引用（admin 可配置），迭代 `allMarkets` 累加 `net_i`，对比 `MAX_PNL_FACTOR_FOR_WITHDRAWALS × poolUsd`。
理由：NAV 不含 pending PnL，高净义务状态下提款 = 按虚高 NAV 卖出退出，把即将兑现的亏损甩给留守 LP——必须封锁，直到 ADL/平仓把净义务降回 0.65 以下。
### 6.2 存款：不设任何 gate
`LPVault.deposit()` **维持现状，不加任何检查**。同时删除 `MAX_PNL_FACTOR_FOR_DEPOSITS` 键及 `validateMaxPnl` 中的 DEPOSITS 调用面（死代码）。
理由：scaling=0 下 NAV 不含 pending PnL，高净义务时存款 = 按虚高 NAV 买入，兑现后 NAV 下跌，损失由存款人自担、原 LP 受益——机制自带反激励，无套利路径，无需封锁。且新资金摊薄 pnlRatio，是高风险状态下的系统自救通道。
```plain text
验证：pool 1000 / supply 1000 / NAV 1，pending 盈利 880
存款人投 1000（NAV=1 拿 1000 shares）→ 兑现 880 → NAV = 0.56
存款人取回 560（亏 440）；原 LP 从本应的 0.12 升到 0.56
```
已知接受的边界行为（P2 监控，无需合约处理）：交易者深度亏损未兑现时，存款人可按不含该未实现收益的 NAV 入场搭便车。不造成偿付风险，清算兑现快、窗口小。前端应展示全局净义务比，让存款人知情。

## 七、TRADERS cap：维持现状不动
`getCappedPnl` / `MAX_PNL_FACTOR_FOR_TRADERS`（per-market × isLong，单边口径）**完全不改**。
理由：它在每次结算时按当时剩余 poolUsd 重算上限（单笔最多拿走剩余池的 90%），串行结算在数学上不会把池打穿为负。它是 Keeper 全部失效时的最后被动防线；保持原实现避免改动已验证的结算路径。

## 八、取价方案（计算 Σ net_i 用）
`Oracle.primaryPrices` 是 per-tx 设置、执行后 `clearAllPrices()` 清除，不能依赖；keeper 也不会为一笔 claim 批量签 20 个市场的价。分层取价：
```plain text
对每个 market 的 indexToken：
1. 有 Chainlink feed → ChainlinkPriceFeedUtils.getPriceFeedPrice(dataStore, token)（同步读，已有实现）
2. 无 feed → 读持久缓存 latestRecordedPrice[token]
   （新增：keeper setPrices 时写入 {price, timestamp}，不随 clearAllPrices 清除）
3. 缓存超 staleness 上限（建议 24h）：
   - claim 路径：revert（等 keeper 刷新该市场价格后再 claim）
   - ADL 路径：该市场仍以缓存价计入 Σ（触发判断宁可偏旧不漏算），但不允许对该市场执行 ADL
```
无 feed 资产的缓存由日常交易自然刷新（每笔订单执行都 setPrices）。

每市场 net_i = 4 个 DataStore 读（两侧 cumulativeOpenCosts + openInterestInTokens）+ 1 次取价 ≈ 15\~20k gas；20 市场全量 ≈ **300\~400k gas** + 一次 `totalAssets()`。
- ✅ claim 提款（7 天锁定后的低频操作）：可接受
- ✅ ADL keeper 交易：可接受
- ❌ 开/平仓交易路径**不做**全局计算（开仓只查本市场 RESERVE_FACTOR，O(1)）

## 十二、测试用例要求（实现后由测试侧编写）
### RESERVE_FACTOR（多空合计容量）
- T-R01: 合计名义 \< RF × poolUsd → 开仓成功
- T-R02: 合计名义超限 → revert（无论本次增仓是 Long 还是 Short——检查与方向无关）
- T-R03: sum 口径：同一合计总量、不同分布（3.0+0 vs 1.5+1.5）→ 检查结果一致
- T-R04: RF = 3.0 时合计名义 2.8× poolUsd → 成功（factor \> 1 合法）
- T-R05: 单边吃满合计额度 → RF 通过但仍受 per-side MAX_OPEN_INTEREST 约束（两检查互补独立）
- T-R06: 多市场 RF 之和远超 1 → 各市场独立检查均通过（无跨市场聚合）
### 净义务口径 / ADL
- T-N01: 多空均亏 → Σ net = 0，gate 全开、ADL 不触发
- T-N02: 单市场多空同时盈利各 0.4×pool → Σ = 0.8 \> 0.75 → ADL 触发（sum 口径核心验证）
- T-N03: Σ = 0.7：claim 封锁（\>0.65）但 ADL 不触发（\<0.75）——状态二
- T-N04: sum 而非 \|差\|：long +0.4、short +0.3 → net = 0.7（非 0.1）
- T-N05: 跨市场聚合（gate）：两市场各 0.35 → Σ = 0.7 \> 0.65 → claim revert
- T-N06: 跨市场聚合（ADL）：两市场各 0.4 → Σ = 0.8 \> 0.75 → ADL 触发
- T-N07: ADL 目标方向必须盈利：对 pnl ≤ 0 的一侧执行 ADL → revert
- T-N08: ADL 退出：Σ 降至 ≤ 0.50 后继续 ADL → revert
- T-N09: 多空同盈触发 ADL 时优先减盈利较大一侧（Keeper 策略回归）
- T-N10: TRADERS cap：单边 pnl \> 0.9×pool 结算被 cap；连续结算后 pool 余额恒 \> 0
- T-N11: 聚合口径：同侧 +100/−60 → 该侧 PnL = +40（侧内互抵），net 按 +40 计
- T-N12: 取价分层：无 feed 市场用缓存价计入 Σ；缓存超龄 → claim revert、该市场禁被 ADL
### LP 存取款 Gate
- T-G01: Σ/pool \< 0.65 → 存款、claim 均允许
- T-G02: 存款永不封锁：Σ/pool = 0.88 → deposit 仍成功，shares 按当前 NAV 铸造
- T-G03: Σ/pool \> 0.65 → claim revert
- T-G04: Σ \> 0.75 → ADL 触发，执行后 Σ \< 0.50
- T-G05: Σ/pool 回落 \< 0.65 后 claim 成功
- T-G06: 高位存入大额 USDC → pnlRatio 被摊薄，提款 gate 可重新打开

## 十四、实现落地情况（v0.3.0，2026-07-16 核对收官）
P0 全部落地（`MarketUtils.sol` / `AdlUtils.sol` / `LPVault.sol` / `FX100Keys.sol`），17 个变更点中本规范对应 A-1\~A-5 五条，均有测试背书（全量 1878 过 / 14 预期 stub）。核对与走查明细见 `2026-07-08-v030-implementation-verification.md`（一）、`2026-07-13-v030-code-walkthrough.md`（A-1\~A-5）。以下是实现与本文口径的主要出入，供审计参考：
1. **§八取价方案比本文更精细**：本文原提案是"claim 严格 revert / ADL 容忍旧价但排除该市场"的二元设计。实际实现（`Oracle.getSecondaryPrice(token, isADLStart)`、`MarketUtils.getNetObligation/getGlobalNetObligationRatio` 的 `isADLStart` 参数）是按调用点分别设置的非对称时效策略：**收紧风控的动作（提款 gate、关闭 ADL、执行 ADL）要求价格严格新鲜；放松风控的动作（开启 ADL）容忍过期缓存价**——四个调用点（提款 gate / `updateAdlState` 开启 / `updateAdlState` 关闭 / `executeAdl` 前后置）各自取值，比本文的二元设计更保守、也更复杂。
2. **executeAdl 的 staleness 检查是全局硬性的**：任一无 Chainlink feed 的市场缓存价超过 `MAX_RECORDED_PRICE_AGE`（新键名，由旧 `MAX_ATOMIC_ORACLE_PRICE_AGE` 改名而来，语义从"原子操作时效"变为"缓存价时效"），整笔 `executeAdl` 直接 `revert MaxPriceAgeExceeded`，而不是本文 §八原述的"该市场以旧价计入 Σ 但单独排除出 ADL 目标"。运营需保证所有市场（尤其新上市场）定期喂价，否则单个滞后市场可阻断全局 ADL。
3. **全局比率触发实现为显式两阶段状态机**，而非 §五伪代码隐含的"每次调用直接比较 ratio"：`AdlUtils.updateAdlState()` 是无参迟滞开关（keeper 需轮询调用，状态未变则 `revert AdlStateUnchanged`），`executeAdl` 只检查 `isAdlEnabled` 标志 + 前置比率 + 目标方向盈利 + 后置单调性。触发**完全依赖 keeper 主动调用 \`updateAdlState\`**，不会自动置位。
4. **单笔 ADL 无"过度去杠杆"上限**：原设想中隐含的"防止一次性砍太多"保护（`PnlOvercorrected`）已被删除，`executeAdl` 只保证执行后 ratio 单调下降，不限制单笔降幅（实测单笔可砍掉仓位 90%+ 仍通过校验）。keeper 执行策略层需自律控制单笔幅度。
5. **poolUsd 取价方向与本文伪代码相反**：§三伪代码用 `price.max`，实际实现取 collateral **min** 价（方向更保守，比率偏大更易触发 gate）；分母跨市场场景固定取"第一个市场"的 vault（依赖"所有市场共享同一 LPVault"的部署不变量，需要作为新市场上线 checklist 的强制项）。
6. §十一实现任务清单中的 P0 项全部完成；P1-1（gate 封锁期间 `unlockAt`/取消请求）仍未实现，为已知遗留（初始化请求排队不受 gate 影响，只在领取时刻检查）。
详细的逐条实现讲解、风险点评估与手动执行测试命令，见 `docs/superpowers/specs/2026-07-13-v030-code-walkthrough.md` §A-1\~A-5 与 `docs/superpowers/specs/2026-07-08-v030-implementation-verification.md` 一节。

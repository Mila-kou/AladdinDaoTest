## 1. getDynamicSpread / 定价模型
### 1.1 单元测试（建议文件：`test/unit/pricing/DynamicSpread.t.sol`）
#### TC-DS-01：零订单量返回 (0, false)
```javascript
输入: usdDelta = 0
预期: getDynamicSpread returns (0, false)
```
#### TC-DS-02：仅 constantPriceSpread 贡献（其余参数为 0）
```javascript
配置: constantPriceSpread = 100e30, priceImpactParameter = 0, skewImpactFactor = 0
输入: usdDelta = 1000e30（任意非零值）
预期: dynamicSpread = 100e30, balanceWasImproved = false
验证: getDynamicSpread 返回值等于 constantPriceSpread
```
#### TC-DS-03：skewImpact 负值足以使 dynamicSpread ≤ 0，截断为 0
```javascript
配置: constantPriceSpread = 50e30
      skewImpactFactor = 负值（开空改善平衡时 balanceWasImproved=true，skewImpact 取负）
      配置使 skewImpact + constantPriceSpread <= 0
输入: 改善平衡的开空订单
预期: getDynamicSpread returns (0, true)
意义: 验证“改善平衡的订单不被惩罚”的截断行为
```
#### TC-DS-04：priceImpactSpread 线性下限（小订单 exp ≈ 线性）
```javascript
已知: max(exp(x)-1, x) ≈ x when x ≪ 1
配置: orderSize * priceImpactParameter / depth 很小（< 0.01e18）
预期: priceImpactSpread ≈ orderSize / depth / 100（线性部分）
验证: 与手动计算值偏差 < 0.1%
```
#### TC-DS-05：priceImpactSpread 受 MAX_PRICE_IMPACT_SPREAD 上限约束
```javascript
配置: MAX_PRICE_IMPACT_SPREAD = 500e30（500 bps）
      设置极大订单使理论 priceImpactSpread > 500e30
预期: priceImpactSpread 被限制为 500e30
验证: dynamicSpread 中的 priceImpactSpread 分量 == MAX_PRICE_IMPACT_SPREAD
```
#### TC-DS-06：depth 为 0 时返回 0（防除零）
```javascript
配置: bidOrderBookDepth = 0（或 askOrderBookDepth = 0）
输入: 对应方向的订单
预期: getPriceImpactSpread 返回 0（不 revert）
```
#### TC-DS-07：isBalanceWasImproved — 从均衡（currentImbalance=0）发起订单
```javascript
初始状态: longOI = shortOI（完全平衡）
操作: 开多头（增加 longOI）
预期: isBalanceWasImproved = false（从 0 到正偏斜，绝对值增大）
```
#### TC-DS-08：isBalanceWasImproved — 从偏斜状态改善
```javascript
初始状态: longOI > shortOI（多头偏重）
操作: 开空头（减少偏斜）
预期: isBalanceWasImproved = true
      skewImpact 为负值（折扣）
```
#### TC-DS-09：skewImpact 被 maxSkewImpact 上限约束
```javascript
配置: maxSkewImpact = 200e30
      设置参数使计算 skewImpact > 200e30
预期: skewImpact 被限制为 200e30
```
#### TC-DS-10：skewImpact 被 minSkewImpact 下限约束（负值）
```javascript
配置: minSkewImpact = -100e30（允许最大折扣）
      设置参数使计算 -skewImpact < -100e30
预期: skewImpact = -100e30（不超过折扣上限）
```

### 1.2 集成测试（建议文件：`test/integration/DynamicSpreadIntegration.t.sol`）
#### TC-DS-INT-01：执行价格随 dynamicSpread 正确偏移（多头开仓）
```javascript
操作: 开多头，订单大小 = S
      当前 constantPriceSpread = C
预期: 实际 executionPrice = indexPrice + dynamicSpread * indexPrice / PRECISION
      position.sizeInTokens = sizeDeltaUsd / executionPrice
验证: 通过 Reader.getExecutionPriceForIncrease 预估值与实际执行一致
```
#### TC-DS-INT-02：改善平衡的空头享有价格折扣（dynamicSpread 减小或为 0）
```javascript
初始: 多头 OI > 空头 OI（多头偏重）
操作: 开较大空头（使 balanceWasImproved=true）
预期: 空头的 dynamicSpread < 同等多头的 dynamicSpread
      若折扣足够大，dynamicSpread 可为 0（执行价格等于 oracle 价格）
```
#### TC-DS-INT-03：不同市场 skewImpact 参数独立
```javascript
配置: market[0] skewImpactFactor = 0.1%, market[1] skewImpactFactor = 0.5%
操作: 在两个市场下同等不平衡条件下执行相同大小订单
预期: market[1] 的 dynamicSpread 包含更大的 skewImpact 分量
```

## 2. Token 数量订单（isSizeDeltaUsd）
### 2.1 单元测试（建议文件：`test/unit/order/TokenSizeOrder.t.sol`）
#### TC-TSO-01：isSizeDeltaUsd=false 时 sizeDelta 单位为 token
```javascript
输入: sizeDelta = 1e18（1 个 ETH token），isSizeDeltaUsd=false
      indexTokenPrice = 2000 USDC
预期: getPositionSizeDeltaInTokens returns 1e18
      等效 USD 大小 = 2000 USDC（由 executor 内部计算）
```
#### TC-TSO-02：isSizeDeltaUsd=true 时保持原 USD 计算
```javascript
输入: sizeDelta = 2000e30（2000 USD），isSizeDeltaUsd=true
      indexTokenPrice = 2000e30（2000 USD）
预期: getPositionSizeDeltaInTokens returns sizeDelta / indexTokenPrice = 1e18
```
#### TC-TSO-03：清算/ADL 订单强制为 USD 模式
```javascript
场景: 创建清算订单
预期: order.isSizeDeltaUsd() == true（无论传入值）
来源: LiquidationUtils.sol, AdlUtils.sol 强制设为 true
```
#### TC-TSO-04：updateOrder 更新 isSizeDeltaUsd
```javascript
前提: 检查 OrderHandler.updateOrder() 是否校验 isSizeDeltaUsd 变更
场景: 创建 token 模式订单后调用 updateOrder 改为 USD 模式
预期: 状态正确更新（或拒绝，取决于业务设计）
```
#### TC-TSO-05（回归）：FIXME-001 — token 模式订单手续费比较错误
```javascript
场景: token 模式订单，sizeDelta = 1e18（1 ETH），当前 ETH 价格 = 2000 USD
      minOrderSize = 100 USD（以 USD 存储）
预期（当前有 Bug）: sizeDelta(1e18) >= minOrderSize(100e30) 为 false → 收取 executionFee
预期（修复后）: 转换为 USD 后 2000 USD >= 100 USD，应免费
标注: vm.skip(true) 直到 FIXME-001 被修复
```

## 3. LPVault NAV 时序
### 3.1 单元测试（建议文件：`test/unit/vault/LPVaultNav.t.sol`）
#### TC-LPV-01：deposit — shares 在 transferFrom 前计算
```javascript
初始: vault NAV = 1000 USDC，totalShares = 1000
操作: deposit(100 USDC)
预期: shares = 100 * 1000 / 1000 = 100（按存入前的 NAV 计算）
      不受 transferFrom 后的 NAV 变化影响
验证: 通过 deposit 后读取 balanceOf(receiver)
```
#### TC-LPV-02：deposit — NAV 为 0 时（第一个存款者）
```javascript
初始: vault 为空（totalShares = 0，NAV = 0）
操作: deposit(1000 USDC)
预期: _convertToShares 处理 totalShares=0 情况
      不 revert
```
#### TC-LPV-03：claimWithdrawRequests — 批量 claim 使用同一个 NAV
```javascript
初始: 用户有 3 个 withdrawRequest，分别为 100/200/300 shares
操作: claimWithdrawRequests([0,1,2])
预期: 三个请求使用同一 currentNav 计算 assets
      total assets = (100+200+300) * NAV
验证: 比较批量 claim 与逐个 claim 的总 assets 是否相等
```
#### TC-LPV-04：_claimWithdrawRequest 返回 shares（不是 assets）
```javascript
验证: _claimWithdrawRequest 内部返回 request.shares
      外层统一用 _convertToAssets(totalShares, currentNav) 一次性转换
```
#### TC-LPV-05：deposit 后立即 withdraw 无精度损失
```javascript
操作: deposit(1000 USDC) → initiateWithdrawRequest(shares) → wait → claimWithdrawRequest
      期间 NAV 不变
预期: 取回金额 == 1000 USDC（无精度损失）
```

## 4. 资金费率计算修复
### 4.1 单元测试（建议文件：`test/unit/market/FundingFeeCalc.t.sol`）
#### TC-FF-01（BUG-006）：零 OI 时不 revert，funding fee per size = 0
```javascript
初始: openInterestInTokens.long = 0（无多头持仓）
操作: 调用 getFundingFees
预期: result.negativeFundingFeePerSizeDelta.long = 0
      不 revert（旧版本会除零 panic）
```
#### TC-FF-02（BUG-006）：仅单边有 OI 时另一边 fee = 0
```javascript
初始: openInterestInTokens.long = 100e18，openInterestInTokens.short = 0
操作: 调用 getFundingFees（多头支付）
预期: result.negativeFundingFeePerSizeDelta.long > 0
      result.negativeFundingFeePerSizeDelta.short = 0（无空头持仓，跳过计算）
```
#### TC-FF-03（BUG-017）：getFundingAmount 以 token 为单位，精度正确
```javascript
输入: latestFundingAmountPerSize = 1e30
      positionFundingAmountPerSize = 0
      collateralTokenPrice.min = 2000e30
      positionSizeInTokens = 1e18
      roundUpMagnitude = true
预期: result = positionSizeInTokens * 1e30 / (FLOAT_PRECISION * collateralTokenPrice.min)
验证: 手工计算值与函数返回值一致
```
#### TC-FF-04（BUG-017）：roundUpMagnitude=true 使用 price.min（对付款方最不利）
```javascript
输入: collateralTokenPrice.min = 1800e30, collateralTokenPrice.max = 2000e30
      roundUpMagnitude = true
验证: 使用 price.min（1800），导致 fundingAmount 更大（付款方多付）
```
#### TC-FF-05（BUG-017）：roundUpMagnitude=false 使用 price.max（对收款方最保守）
```javascript
输入: 同上，roundUpMagnitude = false
验证: 使用 price.max（2000），导致 fundingAmount 更小（收款方少收）
```

## 5. 三阶段抵押品处理（BUG-003）
### 5.1 集成测试（建议文件：`test/integration/DecreaseCollateralPhases.t.sol`）
#### TC-DCP-01：完整三阶段顺序执行（余额充足）
```javascript
场景: 开仓后持有正向 PnL，关仓
验证: 阶段顺序 = 资金费率 → PnL → 手续费
      三阶段均无 handleEarlyReturn
      feeAmountForPool 正确转至 vault
```
#### TC-DCP-02：资金费率不足触发提前退出（阶段 1 failed）
```javascript
场景: 持仓亏损，剩余抵押品仅够支付部分资金费率
操作: 关仓
预期: handleEarlyReturn("funding") 触发
      positionVault 不 underflow
      remaining collateral = 0
```
#### TC-DCP-03：资金费率够但 PnL 不足（阶段 2 failed）
```javascript
场景: 大额亏损，抵押品支付完资金费率后无法覆盖 PnL 亏损
预期: handleEarlyReturn("pnl") 触发
      LP vault 从 position vault 收到所有剩余抵押品
```
#### TC-DCP-04：前两阶段够但手续费不足（阶段 3 failed）
```javascript
场景: 亏损恰好等于抵押品，手续费无法支付
预期: handleEarlyReturn("fees") 触发
      fees = getEmptyFees
      事务仍能完成
```
#### TC-DCP-05：正 PnL 路径 — lpVault 向 positionVault 转账
```javascript
场景: 开多仓，价格上涨 20%，关仓
验证: lpVault 资金流出（支付用户利润）
      positionVault 接收 PnL
      用户获得正确的 collateral + pnl
```

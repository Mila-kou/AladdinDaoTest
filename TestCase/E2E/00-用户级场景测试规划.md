# FX100 用户级场景测试规划

> 适用页面：`https://fx100-dev.vercel.app/trade`  
> 测试定位：站在真实交易用户视角验证完整业务旅程，而非逐个控件验收  
> 基线：见 [Docs/contract-releases/CURRENT.json](../../Docs/contract-releases/CURRENT.json)（已部署环境取 `deployments[]`，目标主测取 `primary`；撰写时：主测 v0.3.2 / 对比 v0.3.1 / 唯一部署为 @v0.3.1 快照 base-sepolia），目标方案与当前行为分开标注  
> 规划日期：2026-08-02

## 1. 为什么重新按场景组织

交易用户不会孤立地“点击杠杆按钮”或“打开订单标签”。资深交易员通常会先判断行情、资金费、持仓拥挤度和流动性，再选择订单、管理风险、等待执行、分批退出并复盘到账；资深测试工程师则会沿同一旅程主动制造价格、时间、网络、服务和状态边界。

因此 `TestCase/E2E` 分为两层：

| 层 | 作用 | 文档 |
|---|---|---|
| 用户旅程层 | 验证一个有明确交易目的的连续操作是否完成 | `scenarios/S01～S08` |
| 功能原子层 | 为旅程提供单控件、空态、输入和基础兼容回归 | `FX100-Trade页面功能测试用例.md` |

用户旅程层是发布验收主入口；功能原子层不再作为业务覆盖的唯一依据。

## 2. 两类核心角色

### 2.1 资深交易员

关注“能否按预期成交、风险能否控制、实际到账是否可信”：

1. 交易前比较预言机价、K 线、资金费、OI、多空拥挤和可用流动性。
2. 根据趋势/反转策略选择市价、低吸限价、突破追单、止盈和止损。
3. 用预览判断执行价、Price Impact、费用、杠杆上限和清算距离。
4. 开仓后加仓、加减保证金、分批止盈、移动止损或全平。
5. 在危险区利用保护期自救，并理解“加仓不重置保护期”。
6. 长时间持仓时关注资金费对净抵押、杠杆和清算价的侵蚀。
7. 在多市场间切换、控制总风险，并识别浅流动性和大单冲击。
8. 根据频率选择 Standard 或 Flash，一键撤单并处理执行异常。

详细行为模型见 [01-资深交易员场景地图.md](01-资深交易员场景地图.md)。

### 2.2 资深测试工程师

关注“边界是否精确、状态是否守恒、异常是否可恢复、数据是否一致”：

1. 对金额、杠杆、价格、时间、OI、流动性做边界值和边界外最小单位测试。
2. 覆盖订单 `Pending / Waiting / Executing / Executed / Cancelled / Frozen / Revert` 状态迁移。
3. 注入 RPC、oracle、keeper、indexer、钱包拒签和网络切换异常。
4. 区分 Cancel 退款、Freeze 不退款、Revert 保持订单三种资金语义。
5. 对页面、Reader、交易回执和索引数据做同区块双源/多源核对。
6. 验证重试、重复点击、刷新、切账号和切市场不会重复下单或串数据。
7. 验证 BTC/ETH、USD/Token、USDC 非 1 美元、多语言和移动端精度兼容。
8. 验证 Flash consent、会话密钥、授权续期、撤销、设备和账户隔离。

详细风险模型见 [02-资深测试工程师场景地图.md](02-资深测试工程师场景地图.md)。

## 4. 文档权威性与冲突处理

项目文档存在历史版本，场景预期按以下顺序决定：

1. `Docs/contract-releases/CURRENT.json` 所载已部署版本（`deployments[]`）的链上行为及其验证报告（撰写时为 @v0.3.1 快照：2026-07-29 验证报告）；`primary` 目标版本的变化以 `Docs/contract-releases/<primary.version>/` 交付物为准，逐项追踪见 [03 §5](03-需求文档追踪矩阵.md)。
2. 2026-07-30 汇总文档、内部/外部审计核对。
3. 2026-07-22 实施版规范。
4. 2026-07-15 Oracle 规范、2026-07-26/28 Flash 安全与同意规范。
5. 更早的讨论版仅用于补充背景，不覆盖新实施口径。

冲突示例：Flash 文档早期描述 `24h / 90 单 / 1h 离开锁`，后续产品决策改为 `90 天 / 1,000,000 次 / 去掉 1h 锁 / 默认保持连接`。E2E 同时验证部署现状和目标口径，若环境仍是旧行为，记录为“基线差异”，不能擅自把旧行为判为新需求通过。

负 Dynamic Spread 同样属于“待评审实施”：当前 release 的非负行为按现状回归，负值 rebate 用例标为 `PENDING`，合入后再转为正常验收。（2026-08-21 注：负点差已在 CURRENT.json `primary` 版本合入——见 `Docs/contract-releases/v0.3.2/01-代码变化分析.md` §4；已部署环境仍为 @v0.3.1 快照的非负行为。执行时按环境实际部署版本判定，PENDING 解除条件见 03 §5 第 2 行。）

## 5. 用例设计方法

每个场景至少包含：

- 角色与交易意图；
- 前置状态和可复现测试数据；
- 连续用户步骤；
- 页面即时反馈；
- 页面、交易回执、Reader/合约和索引数据核对；
- 超时/失败分诊；
- 清理动作和证据。

场景采用以下组合方法：

| 方法 | 应用 |
|---|---|
| 用户旅程 | 从连接、下单到退出和历史复盘 |
| 状态迁移 | 订单、仓位、保护、Flash 会话 |
| 边界值 | 100x、最小抵押、触发价、保护期、OI、滑点 |
| 决策表 | 多/空 × 开/平 × 市价/触发 × 价格方向 |
| 故障注入 | RPC、oracle、keeper、indexer、拒签、掉线 |
| 多源一致性 | 页面 vs Reader vs tx receipt vs indexer |
| 组合风险 | 价格 + funding + impact + USDC 价格 + 时间 |

## 6. 执行分层

| 执行层 | 目的 | 数据强度 |
|---|---|---|
| P0 发布门禁 | 首单、开平仓、撤单、危险区、保护期、资金语义、Flash 安全 | 页面 + tx + Reader；关键账本引用合约 E2E |
| P1 版本回归 | 条件单、长持、费用、异常恢复、多市场 | 双源核对 + 状态迁移 |
| P2 完整回归 | 本地化、移动端、键盘、体验持久化 | 页面状态与可用性 |

## 7. 统一判定规则

1. keeper 等待预算默认 60 秒。keeper 不健康导致未成交，记 `BLOCKED`；keeper 健康但状态错误，记 `FAIL`。
2. Cancel：订单删除、资金退款、不可重试；Freeze：订单保留冻结、资金不退、可重试；Revert：订单原状态和资金不变、可重试。
3. 页面动态数值采用 T3 显示舍入，权威读数采用 T0；两者分别留证。
4. 交易用例 PASS 至少记录 tx hash；FAIL 需要截图、tx hash（若有）和区块号。
5. 场景结束必须清除残留仓位、挂单、Flash 测试授权和异常注入。
6. 手工核对（`[M]` / MANUAL）：结论必须由人核对页面表现，或必须在浏览器钱包里真人操作（连接、切账户、切设备、拒签），设计上不产出自动化代码。判据 = `dev-readonly` 页面核对 ∪ `browser-wallet-keeper` 钱包交互。它与 `NOT_AUTOMATED`（尚未实现，属于欠账）、`BLOCKED`（外部依赖阻塞）、`SKIP` 都不得混用；标记手工核对不免除执行与留证义务，未人工执行并回填证据前不计入通过，也不进入自动化覆盖率分母。当前 17 条：SCN-001 ~ SCN-008、SCN-053 ~ SCN-058、SCN-061、SCN-063、SCN-064。

## 8. 本轮不纳入用户级主流程的内容

配置管理员、fee keeper、RevenuePool 分账、LP 策略托管、协议升级和治理属于后台/合约/运维角色，不混入交易用户 E2E。它们原由 `Test/project/fx100/cases` 的 unit/integration/ledger 用例覆盖——该目录已随旧树归档移出工作区（见 CLAUDE.md「原 `Test/` 目录已移出工作区」说明，除 `TestCode/tools/fx100-legacy/` 收编副本外不再引用归档路径）；现由合约仓 `test/` forge 套件（映射见 `Docs/contract-releases/v0.3.2/06-测试影响与准入结论.md` §2「forge 映射」列）与 TestCode 对账层承担域级覆盖；只有当其结果直接影响交易用户页面（费用、流动性、ADL、oracle）时，才在本目录验证用户可见结果。

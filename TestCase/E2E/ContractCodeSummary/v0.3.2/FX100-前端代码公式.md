# FX100 前端计算公式（代码口径）

> **代码版本**：`Github/fx100-apps@develop` @ `dfa36d0b5295d20246df2ae42fec50327fb0ace3`（2026-09-03）。SDK = `packages/sdk`，App = `apps/fx-base-app`。基线登记见 [`CURRENT.json`](../../../../Docs/contract-releases/CURRENT.json) 的 `frontend.head` / `frontend.subpaths`。**`develop` 是移动分支**——引用本文行号必须连同该 head 一起引，rebase 后以函数名重新定位。
>
> **与既有文档的分工**：本文是**前端代码实现口径**。[`Docs/…/FX100-页面字段计算公式.md`](../../../../Docs/Gordon-Notion需求文档归档/汇总/FX100-页面字段计算公式.md) 是**需求文档口径**（Notion 归档整理），两者冲突时**以代码为准**（工作区规则 4）。合约层见 [FX100-核心字段计算公式.md](./FX100-核心字段计算公式.md)，Keeper 层见 [FX100-Keeper代码公式.md](./FX100-Keeper代码公式.md)。
>
> **权威性**：前端计算是 **B 级**——派生显示量。它的验收标准是「算法与合约约束等价」，**不是**「数值等于链上」。合约里根本没有"杠杆""清算价"这两个变量。
>
> **判来源再比公式**：前端不是所有字段都自己算（还有 `reader-call` / `simulate-call` / `event-derived` 三种）。定位方法、四件套比对法与差异台账见 skill `fx100-formula-parity`；本文只收**前端自己算**的公式本体。

## 0. 通用运算与精度

| 记号 | 定义 | 锚点 |
| --- | --- | --- |
| `applyFactor(v, f)` | `v × f / 1e30`，**向零截断** | `utils/numbers.ts:60` |
| `PRECISION` | `1e30` | `utils/numbers.ts:15` |
| `BASIS_POINTS_DIVISOR` | `10000`（杠杆用 BPS） | `utils/numbers.ts:11` |
| `bigMath.mulDiv(a,b,c)` | `a × b / c`，截断 | `utils/bigmath.ts` |
| 仓位规模精度 | `getPositionSizeDecimals(indexToken)` | `utils/positionPrecision.ts` |

USD 量一律 `× 1e30`。**价格标度必须区分两层**——这是本层最容易出错的地方：

| 层 | 标度 | 来源 |
| --- | --- | --- |
| 合约 / oracle 报文 | `USD × 10^(30 − tokenDecimals)` | 链上原值 |
| **SDK `TokenPrices.minPrice/maxPrice`** | **恒定 `USD × 1e30`，按「整枚」token 计价，与 tokenDecimals 无关** | `parseUsdPrice = parseUnits(v, 30)`（`utils/tokens.ts:21`） |

两层之间由 `parseContractPrice(price, tokenDecimals) = price × 10^tokenDecimals` 换算（`utils/tokens.ts:17`）；`convertToUsd(amount, decimals, price) = amount × price / 10^decimals`（`utils/tokens.ts:54`）与 SDK 标度自洽。**拿合约标度去套本文的 SDK 公式，结果会整体偏 `10^tokenDecimals` 倍。**

**全链路 bigint**——唯一例外是 §6 的 Path B（浮点），见该节警告。

## 1. 价格选边（与合约、Keeper 四处同构）

**锚点**：`utils/prices.ts:12` `getMarkPrice()` · `:20` `getShouldUseMaxPrice()`

```
shouldUseMaxPrice = isIncrease ? isLong : !isLong
markPrice = shouldUseMaxPrice ? prices.maxPrice : prices.minPrice
```

| 动作 | 方向 | 用哪一边 |
| --- | --- | --- |
| 开仓 | 多 | `max`（ask） |
| 开仓 | 空 | `min`（bid） |
| 平仓 | 多 | `min`（bid） |
| 平仓 | 空 | `max`（ask） |

**四处同构**——这是三层一致的正面样板，任何一处改了都要同步：

| 层 | 表述 | 锚点 |
| --- | --- | --- |
| 合约 | `useMax = (开仓&多) 或 (平仓&空)` | `PositionUtils.getExecutionPriceForIncrease/Decrease` |
| SDK 显示 | `getShouldUseMaxPrice` | `utils/prices.ts:20` |
| SDK 执行侧 | `useMaxForSide(side)` | `utils/fx100Orders.ts:108` |
| Keeper | 直接 import SDK 同一函数 | `chain/minMaxPriceSelector.ts:124` |

### 1.1 下单预览取价（多条件）

**锚点**：`utils/trade/increase.ts:471` `getIncreasePositionPrices()`

| 条件 | `indexPrice` | 抵押品价 |
| --- | --- | --- |
| 限价/触发单（`triggerPrice > 0` 且有 `limitOrderType`） | **= `triggerPrice`** | 抵押品与 index 同币种 → 也用 `triggerPrice`；否则 `minPrice` |
| 市价单 | `getMarkPrice(isIncrease=true, isLong)` | `minPrice` |

⚠️ 限价单预览把 **triggerPrice 直接当成交价**展示。合约侧 triggerPrice 只是**执行闸门**，真实成交仍走 `oracle × (1 ± dynamicSpread)`。因此**限价单的"预览价 ≠ 成交价"是设计如此，不是缺陷**；核对时不要拿预览价当期望成交价。

## 2. 入场价与仓位价值

**锚点**：`utils/positions.ts:49` `getEntryPrice()` · `:95` `getPositionValueUsd()`

```
entryPrice     = mulDiv(sizeInUsd, 10^posSizeDecimals, sizeInTokens)     ← sizeInTokens ≤ 0 时 undefined
positionValue  = convertToUsd(sizeInTokens, posSizeDecimals, markPrice)
```

`entryPrice` 是 **`q/s` 的平均执行价**（含历次成交的点差），**不是** index/oracle 价。用 oracle 价代替会按"杠杆 × 现价 × 距离"量级偏。

## 3. PnL（含池级封顶等比缩放）

**锚点**：`utils/positions.ts:59` `getPositionPnlUsd()`

```
totalPnl = isLong ? positionValue − sizeInUsd : sizeInUsd − positionValue

totalPnl ≤ 0  →  直接返回（亏损不封顶）

totalPnl > 0  →  查池级封顶，若 cappedPnl ≠ poolPnl 且两者都 > 0：
    totalPnl ← mulDiv( totalPnl , cappedPnl / 1e18 , poolPnl / 1e18 )
```

| 分支 | 是否缩放 |
| --- | --- |
| 亏损（`≤ 0`） | 否 |
| 盈利且池未触顶（`cappedPnl == poolPnl`） | 否 |
| 盈利且池已触顶 | **是**，按 `cappedPnl / poolPnl` 等比缩小 |

⚠️ **精度点**：实现是**先各自除 `1e18` 再 mulDiv**，不是 `mulDiv(totalPnl, cappedPnl, poolPnl)`。做 parity 比对时必须同序复刻这两步除法，否则末位会差。

**例子**（构造值）：`totalPnl = 1000`、`poolPnl = 5000`、`cappedPnl = 4000` → 缩放后 `1000 × 4000/5000 = 800`。

### 3.1 净值与费后 PnL

**锚点**：`utils/positions.ts:107` `getPositionNetValue()` · `:126` `getPositionPnlAfterFees()`

```
pendingFeesUsd = pendingFundingFeesUsd + pendingBorrowingFeesUsd        （:101）

netValue     = collateralUsd − pendingFeesUsd − closingFeeUsd − uiFeeUsd
               + pnl + totalPendingImpactDeltaUsd + priceImpactDiffUsd

pnlAfterFees = pnl − pendingFeesUsd − closingFeeUsd − uiFeeUsd
               + totalPendingImpactDeltaUsd + priceImpactDiffUsd
```

两式只差一个 `collateralUsd`。

## 4. 杠杆（单位 BPS，合约无此变量）

**锚点**：`utils/positions.ts:155` `getLeverage()`

```
remainingCollateralUsd = collateralUsd + pnl − (pendingFunding + pendingBorrowing) + pendingPositiveFunding

remainingCollateralUsd ≤ 0  →  undefined（不显示）

leverage(BPS) = mulDiv(sizeInUsd, 10000, remainingCollateralUsd)
```

| 分量 | 为什么在式子里 |
| --- | --- |
| `+ pnl` | 调用方传 `undefined` 时按 `0` 处理——**传不传决定这是"含浮盈杠杆"还是"不含浮盈杠杆"，两个口径都在页面出现过** |
| `− 待付 funding/borrowing` | 下次操作会从保证金扣走 |
| `+ 待收 funding` | FX100 双向净额结算，待收也会结进保证金；漏了它会与持仓面板的 Margin 列不一致（代码注释明示） |

**分母压的是净抵押，不是毛保证金**——与合约 `isPositionLiquidatable` 的约束同口径。

**例子**（构造值）：`sizeInUsd = 10000`、`collateralUsd = 1000`、`pnl = 0`、待付 funding `= 5`、待收 `= 0`

```
remaining = 1000 + 0 − 5 + 0 = 995
leverage  = 10000 × 10000 / 995 = 100502 BPS = 10.05x
```

## 5. 清算价 Path A（SDK 权威路径，四分支）

**锚点**：`utils/positions.ts:182` `getLiquidationPrice()`。`preview.liquidationPrice` 非 null 即走本路径。

### 5.1 公共项

```
closingFeeUsd     = getPositionFee(marketInfo, sizeInUsd, false, referral).positionFeeUsd    ← 含平仓费！
totalPendingFees  = pendingFundingFeesUsd + pendingBorrowingFeesUsd
totalFeesUsd      = totalPendingFees + closingFeeUsd

liquidationCollateralUsd = max( applyFactor(sizeInUsd, minCollateralFactorForLiquidation),
                                minCollateralUsd )
```

### 5.2 `priceImpactDeltaUsd` 的三条分支（顺序敏感）

```
maxNegative = −applyFactor(sizeInUsd, maxPositionImpactFactorForLiquidations)
```

| 条件 | `priceImpactDeltaUsd` |
| --- | --- |
| `useMaxPriceImpact = true` | `= maxNegative`（直接取最大负向） |
| 否则 | ① 按 `−sizeInUsd` 算全平的 impact；② 若为正，按最大影响因子封顶；③ **加上 `pendingImpactUsd`**（正的用 `minPrice` 折算、负的用 `maxPrice`）；④ 结果 > 0 → **归零**；⑤ 结果 < `maxNegative` → 夹到 `maxNegative` |

⚠️ 第 ④ 步：**正向 impact 一律归零**——清算价计算里只认对用户不利的一侧。

### 5.3 四个分支的闭式（多条件）

令 `q = sizeInUsd`、`s = sizeInTokens`、`L = liquidationCollateralUsd`、`I = priceImpactDeltaUsd`、`F = totalFeesUsd`、`C = collateralUsd`、`A = collateralAmount`。

**分支 1：抵押品与 index **同币种**（如 mETH 抵押交易 mETH）** — 抵押品本身随价格变，分母要带上抵押数量：

```
scale = 10^(posSizeDecimals − collateralToken.decimals)

多头  分母 = s + A × scale        liqPrice = (q + L − I + F) / 分母 × 10^posSizeDecimals
空头  分母 = s − A × scale        liqPrice = (q − L + I − F) / 分母 × 10^posSizeDecimals

分母 == 0  →  undefined
```

**分支 2：抵押品与 index **不同币种**（如 USDC 抵押交易 mETH，最常见）**：

```
remainingCollateralUsd = C + I − totalPendingFees − closingFeeUsd

多头  liqPrice = (L − remainingCollateralUsd + q) /  s  × 10^posSizeDecimals
空头  liqPrice = (L − remainingCollateralUsd − q) / −s  × 10^posSizeDecimals
```

最后统一：`liqPrice ≤ 0 → undefined`；`q ≤ 0` 或 `s ≤ 0` 时函数一开始就返回 `undefined`。

### 5.4 例子（构造值，异币种多头）

`q = 10000`、`s = 4.0922`、`C = 1000`、`mcf_liq = 0.5%`、`ff = 0.05%`、`I = 0`、待付 funding `= 0`、`minCollateralUsd < 50`

```
closingFee = 10000 × 0.0005 = 5
L          = max(10000 × 0.005, minCollateralUsd) = 50
remaining  = 1000 + 0 − 0 − 5 = 995
liqPrice   = (50 − 995 + 10000) / 4.0922 = 9055 / 4.0922 ≈ 2212.75
```

展开即 `(q + q·mcf_liq + q·ff − C) / s`——与合约不等式 `净抵押 < q × mcf_liq` 的代数反解同构。

**同币种多头对照**：同样 `q=10000`、`s = 4 ETH`、另有 `A = 1 ETH` 抵押（同为 18 位，`scale = 1`）

```
分母     = 4 + 1 = 5
liqPrice = (10000 + 50 − 0 + 5) / 5 = 2011
```

分母多了抵押数量——因为抵押品跌价与仓位亏损同时发生，清算来得更快。**用异币种公式去核同币种仓位会得到偏低的清算价**，这是清算价核对最常见的口径错。

## 6. 清算价 Path B（App 层回退，浮点）

**锚点**：`apps/fx-base-app/src/components/features/trade/_position/liqPriceUtils.ts:49` `estimateNewLiqPrice()` · `:17` `useLiqPriceEstimate()`

**Path A 与 Path B 的关系是「优先 / 兜底」，不是「界面二选一」**：

| 界面 | 主路径 | 兜底 | 调用点 |
| --- | --- | --- | --- |
| 下单预览 | **Path A** | Path B | `OrderPreview.tsx:332-348`：先取 `preview?.liquidationPrice`（来自 `useCreateOrder.ts` 的 SDK `getLiquidationPrice`），**仅当它为 null 且 `estimatedLeverage > 0`** 才 `estimateNewLiqPrice` |
| 杠杆调整弹窗 | **Path A** | Path B | `PositionLeverageDialog.tsx:491-495`：改动目标时 `sdkEstimatedLiq ?? estimatedLiq.newLiqPrice`；未改动时优先用持仓已有的 `position.liquidationPrice` |
| 保证金调整弹窗 | **Path A** | 无 | `PositionMarginDialog.tsx:521` → SDK `getLiquidationPrice` |
| 持仓列表 / 面板 | **Path A** | 无 | SDK `getPositionsInfo` → `getLiquidationPrice` |

⚠️ **不要按「这个界面走 B」去取核对基准**。正确做法是：先判 SDK 是否返回了值——返回了就按 Path A 核（可逐 wei 对），返回 null 才按 Path B 核（只能对到显示精度）。证据上要记录**本次实际走的是哪条**，而不是按界面预设。

> 更正记录（2026-09-05）：本表初版写成「下单预览 / 杠杆弹窗走 Path B」，是只查了 `estimateNewLiqPrice` 的调用点、未核实它是主路径还是兜底所致。已按 `fx100-apps@develop` @ `dfa36d0b` 逐行复核订正。**这类错误的通用防法：找到调用点后必须再看一层——它是被优先取用，还是仅在上游返回空时兜底。**

```
多头  liqPrice = entryPrice × (1 − 1/leverage)
空头  liqPrice = entryPrice × (1 + 1/leverage)
```

| 项 | Path A | Path B |
| --- | --- | --- |
| 最低抵押因子 `mcf_liq` | 计入 | **忽略** |
| 平仓手续费 | **计入** | 忽略 |
| 待付 funding / borrowing | 计入 | 忽略 |
| price impact | 计入（三分支夹取） | 忽略 |
| 同币种抵押分支 | 有 | **无** |
| 数值类型 | bigint 全程 | **JS `Number` 浮点**（`Number(formatUnits(price, 30))`） |

⚠️ **两个使用限制**：
1. Path B 用于下单预览与杠杆调整弹窗，以及 SDK 结果不可用时的回退；**保证金调整弹窗不走它**（见上表）。**任何情况下不要拿 Path B 做 parity 基准。**
2. 它是浮点。与 bigint 路径的结果**不可逐 wei 比对**，只能比到显示精度。

**同一仓位两路径对照**（构造值，接 §5.4：`entry = 10000/4.0922 ≈ 2443.7`、`leverage = 10x`、多头）

```
entry  = 10000 / 4.0922 ≈ 2443.67
Path A = 9055 / 4.0922 ≈ 2212.75
Path B = 2443.67 × (1 − 1/10) = 9000 / 4.0922 ≈ 2199.31
差     = 55 / 4.0922 ≈ 13.44 USD（占 Path A 的 0.61%），Path B 偏乐观（显示的清算价更远）
```

⚠️ `LiqPriceRow.tsx` 上 "(excluding fees)" 的标注对 **Path A 是错标**——Path A 实际含平仓费，该描述只适用 Path B。

## 7. 最低抵押门槛：三条不同的线

**锚点**：`utils/positions.ts:383` `getMinCollateralFactorForPosition()` · `:406` `getMinCollateralUsdForPositionAction()` · `:437` `getMinCollateralUsdForLiquidation()`；`utils/trade/decrease.ts:445` `getMinCollateralUsdForLeverage()`

### 7.1 公共的因子（随 OI 上浮，**分方向**）

```
openInterest = (isLong ? longInterestUsd : shortInterestUsd) + openInterestDelta
multiplier   = isLong ? minCollateralFactorForOpenInterestLong
                      : minCollateralFactorForOpenInterestShort

minCollateralFactor = max( mulDiv(openInterest, multiplier, 1e30),
                           marketInfo.minCollateralFactor )        ← OI 越大门槛越高
```

⚠️ **OI 与乘数都按 isLong 分方向取**，多空两侧是不同的字段、不同的值。写成单一字段会在两侧 OI 不对称时算错。

### 7.2 三条线的区别

| 函数 | 用哪个因子 | 有无 `minCollateralUsd` 地板 | 用在哪 | 相对高低 |
| --- | --- | --- | --- | --- |
| `getMinCollateralUsdForPositionAction` (`positions.ts:406`) | `minCollateralFactor`（随 OI 上浮） | **有** | 开仓 / 加仓 / 调保证金的校验 | **最高（最严）** |
| `getMinCollateralUsdForLiquidation` (`positions.ts:437`) | `minCollateralFactorForLiquidation` | **有** | 清算判定、往可清算仓位存钱（`forLiquidation=true`） | **最低（最松）** |
| `getMinCollateralUsdForLeverage` (`decrease.ts:445`) | `minCollateralFactor`（同第一条） | **无** | 减仓路径的杠杆约束校验 | 与第一条同因子，但**没有地板** |

```
前两条：max( applyFactor(sizeInUsd, 因子), marketInfo.minCollateralUsd )
第三条：applyFactor(sizeInUsd, minCollateralFactor)          ← 少了 max(...) 那层
```

⚠️ 第三条**不是**「只差因子」——它与第一条因子相同，差的是**有没有 `minCollateralUsd` 绝对地板**。小仓位时这个差别最大：仓位规模小到 `applyFactor(size, factor) < minCollateralUsd` 时，前两条被地板顶住、第三条继续往下走。

把三条线混用，会让「开仓被拒但还没到清算」这段区间、以及小仓位减仓的用例判错。

## 8. 手续费预览

**锚点**：`utils/fees/index.ts:31` `getPositionFee()`

```
factor = balanceWasImproved ? positionFeeFactorForBalanceWasImproved
                            : positionFeeFactorForBalanceWasNotImproved

positionFeeUsd = applyFactor(sizeDeltaUsd, factor)
uiFeeUsd       = applyFactor(sizeDeltaUsd, uiFeeFactor ?? 0)

无 referralInfo → 直接返回（discount = rebate = 0）
有 referralInfo → totalRebateUsd = applyFactor(positionFeeUsd, totalRebateFactor)
                  discountUsd    = applyFactor(totalRebateUsd, discountFactor)
                  positionFeeUsd ← positionFeeUsd − discountUsd
```

⚠️ 这是 **USD 口径的单次 `applyFactor`**；合约侧是 `⌊⌊sizeUsd × factor / 1e30⌋ / colPrice.min⌋` 的**两次独立 floor**（先 USD 再折 token）。两边比对时必须先统一到同一口径再比，否则会看到 1 wei 级差异并误判。

**例子**（构造值）：`sizeDeltaUsd = 10000`、`factor = 0.05%` → `positionFeeUsd = 5`。若 `totalRebateFactor = 20%`、`discountFactor = 50%`：`totalRebate = 1`、`discount = 0.5` → **最终 4.5**。

**清算价里的调用**（§5.1）传的是 `balanceWasImproved = false`（不利档）且 `referralInfo` 由调用方决定——页面 display 路径传 `undefined`，所以**页面显示的清算价不含返佣折扣**。

## 9. 执行费与 relay

**锚点**：`utils/fees/executionFee.ts:10` `getExecutionFee()` · `:57` `estimateRelayerGasLimit()` · `:83` `approximateL1GasBuffer()` · `:99` `estimateBatchGasLimit()` · `:124` `estimateBatchMinGasPaymentTokenAmount()` · `:192/:202` 增/减仓 gas 上限估算

## 10. 与合约的关系速查

| 前端量 | 合约有对应变量吗 | 验收方式 |
| --- | --- | --- |
| `markPrice` 选边 | 有（`useMax`） | **一致**，四处同构（§1） |
| `entryPrice` | 无（`q/s` 派生） | 恒等式自证 |
| PnL | 有（`_getPositionPnlUsd`） | 算法等价；注意封顶缩放的两步除法（§3） |
| 杠杆 | **无** | 只能验"与 `isPositionLiquidatable` 的净抵押约束等价" |
| 清算价 | **无**（合约只判布尔） | Path A ⟺ 合约不等式代数反解；最终以 `Reader.isPositionLiquidatable` 为准 |
| 手续费 | 有（`getPositionFees`） | 口径不同（USD vs token 两次 floor），先统一再比（§8） |
| 最低抵押 | 有（两个不同的 key） | 三条线别混（§7） |

**三层验收关系**（同 Keeper 文档 §9）：

```
前端预估清算价  ≈  合约清算边界        （B：验算法一致，不验等于链上）
Keeper 近似价   不遗漏风险仓位          （K2：只验不漏）
最终是否清算    以合约 Reader 判定为准  （A：唯一断言基准）
```

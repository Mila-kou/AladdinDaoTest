## 11. 清算判定

清算资格的唯一判定函数是 `PositionUtils.isPositionLiquidatable`。它不读任何“清算价”字段——合约里不存在清算价，只有“给定一组价格，这个仓位现在是否可清算”的布尔判定（闭式清算价估算见 18.2，精确边界见 18.3）。

判定分三步：① 用一张**合成的整仓清算减仓单**算出假设成交价；② 按该成交价算剩余抵押品；③ 与两条阈值比较。三步的取价侧、取整方向、以及使用哪个 `minCollateralFactor`，都由入参和订单类型决定，下面逐条展开。

### 11.1 清算前剩余抵押品 USD

**前置一：合成订单（v0.3.2 新增 `orderType`）**

`isPositionLiquidatable` 在函数内部现造一个临时 `Order`，只用于喂给成交价函数，永远不会被提交执行：

```text
order.sizeDelta        = position.sizeInUsd     （整仓）
order.isSizeDeltaUsd   = true
order.isLong           = position.isLong
order.acceptablePrice  = isLong ? 0 : type(uint256).max
order.orderType        = Order.OrderType.Liquidation   ← v0.3.2 新增，无条件设置
```

`orderType = Liquidation` 是 v0.3.2 的新增行，**不带任何 `if`，与 `forLiquidation` 入参无关**（设计依据见 Dynamic Spread 允许为负方案三.1 / 三.1.1）。因此开仓校验、减仓校验、真清算 gate、Reader 只读查询四条路径的判定，全部走清算成交价规则。

`acceptablePrice` 取 0 / `type(uint256).max` 等价于关闭可接受价校验：`BaseOrderUtils.getExecutionPriceForDecrease` 的 `(isLong && p >= acceptable) || (!isLong && p <= acceptable)` 必然成立，原样返回，不会 revert。

**前置二：判定用成交价与 `balanceWasImproved`**

`PositionUtils.getExecutionPriceForDecrease`：

```text
（1）拆单量：getDecreaseOrderSize —— rawSizeDelta == position.sizeInUsd 命中整仓分支
    sizeDeltaUsd      = position.sizeInUsd
    sizeDeltaInTokens = position.sizeInTokens        （整仓不产生取整误差）

（2）allowNegativeSpread
    = !(isLiquidationOrder(orderType) || secondaryOrderType == Adl)
    此处 orderType 恒为 Liquidation → allowNegativeSpread = false

（3）PositionPricingUtils.getDynamicSpread
    dynamicSpread = skewImpact + constantPriceSpread + priceImpactSpread
    若 allowNegativeSpread == false 且 minDynamicSpread < 0 → minDynamicSpread 抬到 0
    若 maxDynamicSpread < minDynamicSpread                → maxDynamicSpread 抬到 minDynamicSpread
    dynamicSpread = clamp(dynamicSpread, minDynamicSpread, maxDynamicSpread)   （1e18 标度）
    balanceWasImproved = |下一时刻多空差| < |当前多空差|

（4）成交价（1e30 标度）
    Long : executionPrice = floor(indexPrice.min × (1e18 - dynamicSpread) / 1e18)
    Short: executionPrice = ceil (indexPrice.max × (1e18 + dynamicSpread) / 1e18)
```

- **清算 / ADL 只清零了下限，没有取消上限**：`maxDynamicSpread` 仍沿用普通交易那一份市场配置，清算成交价同样被它封顶（方案九.3 已定案保留）。
- **`balanceWasImproved` 是 v0.3.2 才接上的**：v0.3.1 的 `cache.balanceWasImproved` 从未被赋值，恒为 `false`；v0.3.2 改为 `cache.balanceWasImproved = executionPriceResult.balanceWasImproved`。它随后进入费率档位选择，**会移动清算阈值本身**，详见下面“费用”小节。

**positionPnlUsd（含 PnL 封顶）**

`PositionUtils.getPositionPnlUsdWithExecutionPrice` → `_getPositionPnlUsd`，入参 `sizeDeltaInTokens = position.sizeInTokens`（整仓）：

```text
positionValue    = position.sizeInTokens × executionPrice
totalPositionPnl = isLong ? positionValue - position.sizeInUsd
                          : position.sizeInUsd - positionValue

若 totalPositionPnl > 0（仅盈利侧封顶）：
    poolTokenUsd  = vault.totalAssets × collateralTokenPrice.min
    poolPnl       = MarketUtils.getPnl(market, prices.indexTokenPrice, isLong, maximize=true)
    cappedPoolPnl = getCappedPnl(poolPnl, poolTokenUsd, MAX_PNL_FACTOR_FOR_TRADERS)
                  = min(poolPnl, floor(poolTokenUsd × maxPnlFactor / 1e30))
    若 cappedPoolPnl != poolPnl 且两者均 > 0：
        totalPositionPnl = floor(totalPositionPnl × cappedPoolPnl / poolPnl)

positionPnlUsd = mulDiv(totalPositionPnl, sizeDeltaInTokens, position.sizeInTokens,
                        roundUpMagnitude = (totalPositionPnl < 0))
```

- `maxPnlFactor` 走 `maxPnlFactorKey(MAX_PNL_FACTOR_FOR_TRADERS, marketIndex, isLong)`，是**分市场分方向**的键，与 12.4 里 ADL / 提款用的全局单键不是一回事。
- 整仓判定下 `sizeDeltaInTokens == sizeInTokens`，最后一步按比例缩放是恒等变换；取整方向只在部分平仓路径（见第 6 节）才有影响。
- 亏损侧不封顶，`roundUpMagnitude = true` 表示亏损按绝对值向上取整（对用户不利方向）。

**费用（判定口径，不含清算费）**

`PositionPricingUtils.getPositionFees`，入参 `sizeDeltaUsd = position.sizeInUsd`、`uiFeeReceiver = address(0)`、`isLiquidation = false`、`balanceWasImproved` 取上面第（3）步的实际值：

```text
positionFeeFactor = positionFeeFactorKey(marketIndex, balanceWasImproved)   ← 档位随平衡方向切换
positionFeeAmount = floor( floor(sizeInUsd × positionFeeFactor / 1e30) / collateralTokenPrice.min )
uiFeeAmount          = 0        （uiFeeReceiver = 0，早退）
liquidationFeeAmount = 0        （isLiquidation = false）

totalCostAmount = positionFeeAmount - totalDiscountAmount + negativeFundingFeeAmount
```

`negativeFundingFeeAmount` / `positiveFundingFeeAmount` 由 `MarketUtils.getFundingAmount` 折算，两侧取价和取整**不对称**：

```text
negativeFundingFeeAmount = ceil ( sizeInTokens × Δnegative / (1e30 × collateralTokenPrice.min) )
positiveFundingFeeAmount = floor( sizeInTokens × Δpositive / (1e30 × collateralTokenPrice.max) )
```

**剩余抵押品**

```text
collateralUsd
= position.collateralAmount × collateralTokenPrice.min

collateralCostUsd
= totalCostAmount × collateralTokenPrice.min

positiveFundingFeeUsd
= positiveFundingFeeAmount × collateralTokenPrice.min

remainingCollateralUsd
= collateralUsd
+ positionPnlUsd
+ positiveFundingFeeUsd
- collateralCostUsd
```

三项 USD 折算**都用 `collateralTokenPrice.min`**。注意 `positiveFundingFeeAmount` 是按 `.max` 价折成 token 数、又按 `.min` 价折回 USD 的，价差不为零时这部分抵押品被系统性低估；负资金费方向相反（`.min` 折 token、`.min` 折回），不存在这层不对称。

`negativeFundingFeeAmount` 已经包含在 `totalCostAmount` 里，**不要再单独减一次**。

### 11.2 最低抵押品要求与判定条件

**因子选择由 `forLiquidation` 入参决定，不是“清算 vs 正常”二分**：

```text
forLiquidation == true  → minCollateralFactor = MIN_COLLATERAL_FACTOR_FOR_LIQUIDATION
                                                minCollateralFactorForLiquidationKey(marketIndex)
forLiquidation == false → minCollateralFactor = MIN_COLLATERAL_FACTOR
                                                minCollateralFactorKey(marketIndex)
```

源码注释约定 `MIN_COLLATERAL_FACTOR_FOR_LIQUIDATION` 应低于 `MIN_COLLATERAL_FACTOR`（清算线松于开仓线），但**合约不校验这个跨键关系**。`ConfigUtils.validateRange`（public）只对两者各自设了独立上限：

```text
MIN_COLLATERAL_FACTOR_FOR_LIQUIDATION ≤ 1e28   （1%）
MIN_COLLATERAL_FACTOR                 ≤ 5e28   （5%）
```

这两条是**因子的上限**，正着读是“维持要求最多只能配到仓位规模的 1%、开仓要求最多只能配到 5%”，反过来读是“清算档允许的最高杠杆不会低于 100x、开仓档不会低于 20x”；它们不是杠杆的下限。两者相等（安全垫为零）或反向配置都能通过 Config 校验，实际值以链上配置为准。

```text
minCollateralUsdForLeverage
= floor(position.sizeInUsd × minCollateralFactor / 1e30)
```

判定按源码顺序短路返回，先命中先返回，`reason` 字符串不同：

```text
① shouldValidateMinCollateralUsd == true 时：
   remainingCollateralUsd < dataStore.getUint(MIN_COLLATERAL_USD)   → reason "min collateral"
   （该入参为 false 时这一条整段跳过，info.minCollateralUsd 保持 0）

② remainingCollateralUsd <= 0                                      → reason "< 0"

③ remainingCollateralUsd < minCollateralUsdForLeverage             → reason "min collateral for leverage"

以上都不满足 → 不可清算，reason 为空串
```

除第②条是 `<= 0` 外，其余都是**严格小于**：恰好等于阈值不触发清算。

`MIN_COLLATERAL_USD` 是全局单键（`FX100Keys.MIN_COLLATERAL_USD`），不分市场不分方向。

**前置早退（只在 `validatePosition` 路径存在）**

`PositionUtils.validatePosition` 在调用 `isPositionLiquidatable` 之前先跑：

```text
validateBasicPositionInfo：
    sizeInUsd == 0 || sizeInTokens == 0 → revert InvalidPositionSizeValues
    市场未启用                          → revert（validateEnabledMarket）

shouldValidateMinPositionSize == true：
    sizeInUsd < MIN_POSITION_SIZE_USD（全局键）→ revert MinPositionSize

shouldValidateMaxPositionSize == true：
    maxPositionSizeUSDKey(marketIndex) > 0 且 sizeInUsd > 该值 → revert MaxPositionSize
    （配置为 0 表示不限制，与 12.5 的 MAX_OPEN_INTEREST 没有这条豁免不同）

isLiquidatable == true → revert LiquidatablePosition(reason, remaining, minCollateralUsd, minCollateralUsdForLeverage)
```

`Reader.isPositionLiquidatable` 与 `DecreasePositionUtils` 的清算 gate 直接调 `isPositionLiquidatable`，**不走这些早退**。

### 11.3 四个调用点与参数取值

| 调用点 | 场景 | `shouldValidateMinCollateralUsd` | `forLiquidation` | 实际生效的因子 |
|---|---|---|---|---|
| `IncreasePositionUtils.increasePosition` → `validatePosition` | 开仓 / 加仓 / 纯加保证金之后 | `true` | `cache.sizeDeltaUsd == 0` | 真实开仓加仓（`sizeDeltaUsd != 0`）→ `MIN_COLLATERAL_FACTOR`；**纯加保证金（`sizeDeltaUsd == 0`）→ `MIN_COLLATERAL_FACTOR_FOR_LIQUIDATION`** |
| `DecreasePositionUtils.decreasePosition` 清算 gate | `isLiquidationOrder` 时的执行前置 | `true` | `true` | `MIN_COLLATERAL_FACTOR_FOR_LIQUIDATION`；判定为**不可清算**时 revert `PositionShouldNotBeLiquidated` |
| `DecreasePositionUtils.decreasePosition` 收尾 | 减仓 / 部分平仓后，**仅当剩余仓位非零** | `false` | `false` | `MIN_COLLATERAL_FACTOR`（同时 min / maxPositionSize 两项校验都关闭） |
| `Reader.isPositionLiquidatable` | 前端 / off-chain 只读 | 调用方传入 | 调用方传入 | 取决于入参——**前端要复现哪条链上路径，就必须传对应的这两个布尔值** |

两条容易踩的分支（**前提是该市场配了 `MIN_COLLATERAL_FACTOR > MIN_COLLATERAL_FACTOR_FOR_LIQUIDATION`**；11.2 已说明合约不校验这个关系，实配需在目标环境读键确认，两者相等时下面两条都不成立）：

- **纯加保证金走的是清算档因子**。设计意图是“补保证金只要能把仓位拉出清算区间就应放行”，不要求同时满足开仓档的最大杠杆；副作用是补完保证金的仓位可能只满足清算档、达不到开仓档，下一笔加仓会被 `MIN_COLLATERAL_FACTOR` 拒掉。
- **减仓收尾用的是 `MIN_COLLATERAL_FACTOR`（开仓档）**，不是清算档：部分平仓后剩余仓位必须满足更严的开仓档才放行，所以“仓位处于可清算状态时用户仍能手动全平”（全平后 `sizeInUsd == 0`，整段校验被跳过），但**部分平仓可能反而 revert**。

17.4、18.1、18.2、21 把维持要求一律写成 `sizeInUsd × minCollateralFactorForLiquidation`，那只对 `forLiquidation == true` 的路径成立；算开仓 / 减仓校验的期望值时必须换成 `MIN_COLLATERAL_FACTOR`，算持仓面板的 Maintenance Margin 时也要先确认页面想复现的是哪条路径。

### 11.4 第二道防线：`willPositionCollateralBeSufficient`

`PositionUtils.willPositionCollateralBeSufficient` 是独立于 `isPositionLiquidatable` 的杠杆闸门：**不算任何费用、不碰 `dynamicSpread`、不计未实现 PnL，只把入参里为负的 `realizedPnlUsd` 计入**。它自身只返回 `(willBeSufficient, remainingCollateralUsd)`，**从不 revert**，后果由调用方决定。

```text
collateralTokenPrice   = getCachedTokenPrice(market.collateralToken, market, prices)
remainingCollateralUsd = values.positionCollateralAmount × collateralTokenPrice.min

若 values.realizedPnlUsd < 0：remainingCollateralUsd += values.realizedPnlUsd   （正 PnL 不计入，防价格操纵）
若 remainingCollateralUsd < 0 → 返回 (false, remainingCollateralUsd)

minCollateralFactor
= max(
    getMinCollateralFactorForOpenInterest(market, values.openInterestDelta, isLong)
      = floor( (cumulativeOpenCostsUsd(marketIndex, isLong) + openInterestDelta)
               × MIN_COLLATERAL_FACTOR_FOR_OPEN_INTEREST_MULTIPLIER(marketIndex, isLong) / 1e30 ),
    MIN_COLLATERAL_FACTOR(marketIndex)
  )

minCollateralUsdForLeverage = floor(values.positionSizeInUsd × minCollateralFactor / 1e30)
willBeSufficient            = remainingCollateralUsd >= minCollateralUsdForLeverage   ← 大于等于即放行
返回 (willBeSufficient, remainingCollateralUsd)
```

**两个调用点，入参与后果完全不同**：

| 调用点 | 触发条件 | `positionSizeInUsd` | `positionCollateralAmount` | `realizedPnlUsd` | `openInterestDelta` | `!willBeSufficient` 的后果 |
|---|---|---|---|---|---|---|
| `IncreasePositionUtils.increasePosition` | `cache.sizeDeltaUsd > 0`（纯加保证金跳过） | `position.sizeInUsd`（已含本次增量） | `position.collateralAmount`（已含本次增量） | `0` | `0` | `revert InsufficientCollateralUsd(remainingCollateralUsd)`——该错误**只存在于这一处** |
| `DecreasePositionUtils.decreasePosition` | `cache.sizeDeltaUsd < position.sizeInUsd`——**每一笔部分减仓、以及每一笔纯提取保证金单（`sizeDeltaUsd == 0`）都会走**，只有整仓全平跳过 | `position.sizeInUsd - cache.sizeDeltaUsd`（减仓后规模） | `position.collateralAmount - order.initialCollateralDeltaAmount`（扣掉本次提取） | `cache.estimatedRealizedPnlUsd`（有符号，可为负） | `-cache.sizeDeltaUsd`（负值） | 不 revert `InsufficientCollateralUsd`，走下面的三级降级 |

减仓侧的 `realizedPnlUsd` 来自本笔订单自己的成交价：

```text
executionPrice           = getExecutionPriceForDecrease(params, prices.indexTokenPrice).executionPrice
estimatedPositionPnlUsd  = getPositionPnlUsdWithExecutionPrice(..., executionPrice,
                                                               position, position.sizeInTokens)
estimatedRealizedPnlUsd  = mulDiv(estimatedPositionPnlUsd, cache.sizeDeltaInTokens, position.sizeInTokens,
                                  roundUpMagnitude = (estimatedPositionPnlUsd < 0))
estimatedRemainingPnlUsd = estimatedPositionPnlUsd - estimatedRealizedPnlUsd
```

**减仓侧的三级降级**，触发条件是两条并列取或——`!willBeSufficient` **或** `(estimatedRemainingCollateralUsd + estimatedRemainingPnlUsd) < MIN_COLLATERAL_USD`：

```text
① cache.sizeDeltaUsd == 0（纯提取保证金）
     → revert UnableToWithdrawCollateral(estimatedRemainingCollateralUsd)

② 否则不 revert：把 order.initialCollateralDeltaAmount 静默置 0
     （emit OrderCollateralDeltaAmountAutoUpdated），
     并把已扣的 initialCollateralDeltaAmount × collateralTokenPrice.min 加回 estimatedRemainingCollateralUsd

③ 回填之后仍有 estimatedRemainingCollateralUsd + estimatedRemainingPnlUsd < MIN_COLLATERAL_USD
     → order.sizeDelta 自动改成 maxSizeDelta 并重算拆单量，**订单被升级为整仓全平**

（另有一条同型自动升级：减仓后剩余 sizeInUsd < MIN_POSITION_SIZE_USD 时同样改成整仓全平）
```

**因子方向随路径相反**：开仓路径 `openInterestDelta = 0`，且调用发生在 `updateOpenInterest` 之后，`cumulativeOpenCosts` 已含本次增量，因子随该侧持仓规模上升而**收紧**；减仓路径 `openInterestDelta = -sizeDeltaUsd` 为负，算的是**减仓后**的 OI，因子是**放松**的。这一层与 `MIN_COLLATERAL_FACTOR` 固定档并列取大。

**“不受 v0.3.2 负点差改动影响”只对开仓路径成立**：函数体本身确实不碰点差，但减仓路径喂进来的 `realizedPnlUsd` 由 `getExecutionPriceForDecrease` 的成交价推出，而用户发起的 `MarketDecrease` 既不是 `Liquidation`、也不带 `secondaryOrderType = Adl`，`allowNegativeSpread = true`——负点差会直接改变这道闸门的入参与自动降级的触发点。

### 11.5 宽限期与清算单创建

判定为可清算不等于马上能被清算。`LiquidationUtils.createLiquidationOrder` 第一件事就是宽限期闸门：

```text
position.graceEnd > block.timestamp → revert PositionNotLiquidatable(positionKey)
```

`graceEnd` 只在**仓位首次创建**时写入（`IncreaseOrderUtils.processOrder` 的 `position.account() == address(0)` 分支），加仓、补保证金都不刷新：

```text
tier       = referralStorage.referrerTiers(account)
multiplier = liquidationGracePeriodTierMultiplierKey(tier)          （1e18 标度）
graceStart = block.timestamp
graceEnd   = block.timestamp
           + floor(liquidationGracePeriodBaseKey(marketIndex) × multiplier / 1e18)
```

宽限期内即使 `isPositionLiquidatable` 返回 true，也建不出清算单；宽限期过后创建的清算单 `orderType = Liquidation`、`sizeDeltaUsd = position.sizeInUsd`（整仓）、`acceptablePrice = isLong ? 0 : max`（无滑点保护）、`uiFeeReceiver = 0`、`initialCollateralDeltaAmount = 0`。执行时 `DecreasePositionUtils` 的清算 gate 会**再判一次**（`forLiquidation = true`），此时若已不可清算则 revert `PositionShouldNotBeLiquidated`。

### 11.6 数值示例（自验）

USDC 抵押（6 位小数，`collateralTokenPrice.min = max = 1e24`），BTC 多头。仓位数量与 index 价按本文档统一口径取 **18 位标的精度**（`sizeInTokens = 标的 × 1e18`，对应 index 价标度 `1e30 / 1e18 = 1e12` 每 USD）。市场配置 `MIN_COLLATERAL_FACTOR_FOR_LIQUIDATION = 5e27`（0.5%）、`MIN_COLLATERAL_FACTOR = 1e28`（1%）、`MIN_COLLATERAL_USD = 1e31`（10 USD）、`positionFeeFactor(false) = 6e26`（0.06%），`dynamicSpread` clamp 后为 0。

```text
仓位：sizeInUsd = 1e34 (10,000 USD)  sizeInTokens = 1e17 (0.1 BTC)
     隐含入场价 = 1e34 / 1e17 = 1e17 (100,000 USD/BTC)
     collateralAmount = 5.5e8 (550 USDC)
     negativeFundingFeeAmount = 1e6 (1 USDC)，positiveFundingFeeAmount = 0，无折扣
价格：indexPrice.min = indexPrice.max = 9.5e16 (95,000 USD/BTC)

executionPrice    = floor(9.5e16 × 1e18 / 1e18)      = 9.5e16
positionValue     = 1e17 × 9.5e16                    = 9.5e33  (9,500 USD)
totalPositionPnl  = 9.5e33 - 1e34                    = -5e32   (-500 USD，亏损不封顶)
positionPnlUsd                                       = -5e32

positionFeeAmount = floor(1e34 × 6e26 / 1e30) / 1e24 = 6e30 / 1e24 = 6e6   (6 USDC)
totalCostAmount   = 6e6 - 0 + 1e6                    = 7e6
collateralUsd     = 5.5e8 × 1e24                     = 5.5e32  (550 USD)
collateralCostUsd = 7e6 × 1e24                       = 7e30    (7 USD)

remainingCollateralUsd = 5.5e32 - 5e32 + 0 - 7e30    = 4.3e31  (43 USD)

① 4.3e31 < 1e31（10 USD）？否
② 4.3e31 <= 0？否
③ forLiquidation=true ：minCollateralUsdForLeverage = floor(1e34 × 5e27 / 1e30) = 5e31 (50 USD)
                        4.3e31 < 5e31 → 可清算，reason "min collateral for leverage"
   forLiquidation=false：minCollateralUsdForLeverage = floor(1e34 × 1e28 / 1e30) = 1e32 (100 USD)
                        4.3e31 < 1e32 → 同样判可清算，但走 validatePosition 时是 revert LiquidatablePosition
```

若把 `balanceWasImproved` 翻成 `true`、且该市场 improved 档费率为 3e26（0.03%），`positionFeeAmount` 降为 3e6、`totalCostAmount` 降为 4e6、`collateralCostUsd` 降为 4e30，`remainingCollateralUsd` 升到 4.6e31（46 USD），第③条仍触发但余量变化——这就是 v0.3.2 接线 `balanceWasImproved` 后**清算阈值本身会移动**的具体形态。

## 12. 市场与 ADL 风控字段

本节字段服务三类闸门：开仓时的持仓上限与储备上限（12.5、12.6）、LP 提款闸门与 ADL 触发（12.4、12.7）、以及交易者 PnL 封顶（12.2 末尾的 `getCappedPnl`）。三类用的键形状、取价来源都不同，逐条区分。

**先约定两个同名不同义的“Open Interest”**，后文一律用带后缀的名字：

| 本文名称 | 存储 / 来源 | 口径 | 随价格变动 | 用在哪 |
|---|---|---|---|---|
| `cumulativeOpenCostsUsd` | `cumulativeOpenCostsKey(marketIndex, isLong)`，按 ±`sizeDeltaUsd` 累加 | **成本口径**：该侧全部仓位 `sizeInUsd` 之和 | 否 | 12.2 PnL 的成本项、12.5 OI 上限、11.4 的动态因子 |
| `openInterestInTokensUsd` | `openInterestInTokensKey(marketIndex, isLong)` × 某个 index 价 | **市值口径**：该侧持仓 token 数的当前价值 | 是 | 10.1 Funding（`midPrice`）、12.2 的 `openInterestValue`（`pickPriceForPnl`）、12.6 储备（`indexPrice.max`）、20.1 / 20.2 展示 |

10.1 与 20.1 写的 `longOIUsd / shortOIUsd` 属于市值口径；12.5 的上限校验属于成本口径。两者在盈亏不为零时数值不同，**不能互相代入**。

### 12.1 池子 USD

`MarketUtils.getPoolUsdWithoutPnl`：

```text
poolUsdWithoutPnl
= IVault(market.vault).totalAssets × (maximize ? collateralTokenPrice.max : collateralTokenPrice.min)
```

不含任何 pending PnL。各调用点传的 `maximize` 与取价来源：

| 调用点 | `maximize` | 实际取价 | 价格来源 |
|---|---|---|---|
| `validateOpenInterest`（12.5 软顶） | `false` | `.min` | 主签名价（由 `updateOpenInterest` 透传） |
| `validateOpenInterestReserve`（12.6） | `false` | `.min` | 主签名价 |
| `getGlobalNetObligationRatio`（12.4 分母） | `false` | `.min` | **二级价** `oracle.getSecondaryPrice(collateralToken, isADLStart)` |
| `getPnlToPoolFactor`（12.3） | `!maximize`（与 PnL 侧相反） | `maximize=true` → `.min`；`maximize=false` → `.max` | 调用方给的 `MarketPrices.collateralTokenPrice` |
| `ReaderUtils.getMarketInfo`（只读展示） | `false` | `.min` | 调用方给的 `MarketPrices` |
| `_getPositionPnlUsd` 的 `poolTokenUsd`（11.1） | — | 直接写 `.min`，未走本函数 | 主签名价 |

三道**校验型**闸门——`validateOpenInterest`、`validateOpenInterestReserve`、`getGlobalNetObligationRatio`——恒取 `.min` 侧且不接受调用方指定（分母偏小 → 比率 / 占用偏大 → 更早触发保护）。唯一的例外是 `getPnlToPoolFactor`：它传的是 `!maximize`，调用方给 `maximize = false` 时分母取 `.max`；该分支经 `Reader.getPnlToPoolFactor` 与 `MarketUtils` 的 oracle 重载对外可达，但只用于只读展示，不构成闸门。

### 12.2 市场多空 PnL

`MarketUtils.getPnl`：

```text
cumulativeOpenCostsUsd = getCumulativeOpenCosts(marketIndex, isLong)
openInterestInTokens   = getOpenInterestInTokens(marketIndex, isLong)

若 cumulativeOpenCostsUsd == 0 或 openInterestInTokens == 0 → 直接返回 0     ← 早退分支

price = indexTokenPrice.pickPriceForPnl(isLong, maximize)
      isLong  且 maximize → .max      isLong  且 !maximize → .min
      !isLong 且 maximize → .min      !isLong 且 !maximize → .max

openInterestValue = openInterestInTokens × price        （市值口径）

pnl = isLong ? openInterestValue - cumulativeOpenCostsUsd
             : cumulativeOpenCostsUsd - openInterestValue
```

```text
netPnl = getPnl(..., isLong=true, maximize) + getPnl(..., isLong=false, maximize)
```
（`getNetPnl`，两侧用**同一个** `maximize`。12.4 的净义务不是这么算的，见下。）

传单个 `uint256` 价格的重载会把它包成 `Price.Props(p, p)`，此时 `pickPriceForPnl` 退化为恒等，`maximize` 无影响。

`getCappedPnl` 用于交易者侧封顶：

```text
pnl < 0 → 原样返回（亏损不封顶）
否则    → min(pnl, floor(poolUsd × maxPnlFactorKey(pnlFactorType, marketIndex, isLong) / 1e30))
```

注意这里的键是 `maxPnlFactorKey(type, marketIndex, isLong)`，**分市场分方向**；12.4 的 ADL / 提款阈值用的是同名常量的**全局单键**。

### 12.3 PnL / Pool Factor

`MarketUtils.getPnlToPoolFactor`：

```text
poolUsd = getPoolUsdWithoutPnl(market, prices.collateralTokenPrice, !maximize)
若 poolUsd == 0 → 返回 0                                      ← 早退分支
pnl     = getPnl(market, prices.indexTokenPrice, isLong, maximize)

pnlToPoolFactor = Precision.toFactor(pnl, poolUsd)
                = sign(pnl) × floor(|pnl| × 1e30 / poolUsd)
```

- 分子分母的取价侧**故意相反**：`maximize=true` 的 PnL 配 `.min` 的池子，得到最保守（最大）的比率；`maximize=false` 时两边同时翻面，分母改取 `.max`。
- `toFactor` 对有符号数是**按绝对值向下取整再补符号**（负数不是向负无穷取整）。
- 另一重载自行用 `oracle.getPrimaryPrice` 组装 `MarketPrices`，只能在有主签名价的交易上下文里调用。

### 12.4 Global Net Obligation（提款闸门与 ADL 触发）

**per-market 净义务**，`MarketUtils.getNetObligation`：

```text
indexTokenPrice = oracle.getSecondaryPrice(market.indexToken, isADLStart)   ← 二级价，不是主签名价

longPnl  = getPnl(market, indexTokenPrice, isLong=true,  maximize=true)     ← 取 .max
shortPnl = getPnl(market, indexTokenPrice, isLong=false, maximize=true)     ← 取 .min

marketNetObligation = max(longPnl, 0) + max(shortPnl, 0)
```

两侧**都传 `maximize=true`**：多头取 `.max`、空头取 `.min`，各自站在对 LP 最不利的一侧。跨侧不互抵（先各自 `max(·,0)` 再相加），侧内互抵（`getPnl` 本身就是该侧聚合净值）。

**全局比率**，`MarketUtils.getGlobalNetObligationRatio`：

```text
遍历 MarketStoreUtils.getMarketIndices(0, marketCount) 的全部市场：
    netObligation += getNetObligation(market, isADLStart)
    仅 i == 0 时：
        poolUsd = getPoolUsdWithoutPnl(
                      market,
                      oracle.getSecondaryPrice(market.collateralToken, isADLStart),
                      false)                      ← maximize=false → collateralTokenPrice.min

若 poolUsd == 0 → 返回 0                                       ← 早退分支

globalNetObligationRatio = Precision.toFactor(netObligation, poolUsd)
                         = floor(netObligation × 1e30 / poolUsd)
```

分母只在第一个市场取一次，依据是“所有市场共享同一 `LPVault`”这一部署不变量；合约**不校验**这个不变量。

**二级价语义**（`Oracle._getSecondaryPrice`）：

```text
token == address(0)                    → Price(0, 0)
有 Chainlink feed                      → Price(p, p)（min == max，maximize 失去意义）
无 feed 且 latestRecordedPrices 为空   → revert EmptySecondaryPrice
无 feed 且 isADLStart == false 且
   timestamp + MAX_RECORDED_PRICE_AGE < now → revert MaxPriceAgeExceeded
否则                                    → 返回缓存价
```

`isADLStart == true` 是**唯一容忍过期缓存价**的分支（“开启 ADL”是收紧风控的方向，宁可用旧价也不漏算）。

**阈值比较**，`MarketUtils.isGlobalNetObligationRatioExceeded`：

```text
maxRatio   = dataStore.getUint(pnlFactorType)      ← 直接用基键，全局单键，不经 maxPnlFactorKey
isExceeded = globalNetObligationRatio > maxRatio   ← 严格大于
```

四个调用点各自的 `pnlFactorType` / `isADLStart`：

| 调用点 | `pnlFactorType` | `isADLStart` | 超限时行为 |
|---|---|---|---|
| `LPVault._validateWithdrawalsAllowed` | `MAX_PNL_FACTOR_FOR_WITHDRAWALS` | `false` | `revert WithdrawGlobalNetObligationRatioExceeded` |
| `AdlUtils.updateAdlState`，当前 `isAdlEnabled == false`（尝试**开启**） | `MAX_PNL_FACTOR_FOR_ADL` | `true`（容忍过期缓存价） | 超限 → 置 `isAdlEnabled = true` |
| `AdlUtils.updateAdlState`，当前 `isAdlEnabled == true`（尝试**关闭**） | `MIN_PNL_FACTOR_AFTER_ADL` | `false` | 不超限 → 置 `isAdlEnabled = false` |
| `AdlHandler.executeAdl` 前置 | `MIN_PNL_FACTOR_AFTER_ADL` | `false` | **不超限**才是异常 → `revert AdlNotRequired` |
| `ReaderUtils.getAdlState`（只读） | 同 `updateAdlState` 的迟滞规则 | 同左 | 只返回，不写状态 |

**数值示例（自验）**：两个市场共享一个 vault，`totalAssets = 1e12`（1,000,000 USDC，6 位小数），USDC 有 feed 故 `min = max = 1e24`。

```text
poolUsd = 1e12 × 1e24 = 1e36                       (1,000,000 USD)
市场 A：longPnl = +3e35, shortPnl = -5e34 → net_A = 3e35
市场 B：longPnl = -2e34, shortPnl = +5e35 → net_B = 5e35
Σ netObligation = 8e35

globalNetObligationRatio = floor(8e35 × 1e30 / 1e36) = 8e29     (= 80%)
MAX_PNL_FACTOR_FOR_ADL = 7.5e29 (75%)  → 8e29 > 7.5e29 → 可开启 ADL
MAX_PNL_FACTOR_FOR_WITHDRAWALS = 6.5e29 (65%) → 提款被封锁
```

### 12.5 Open Interest 上限（成本口径）

`MarketUtils.validateOpenInterest`，**只在 `applyDeltaToCumulativeOpenCosts` 的 `delta > 0` 分支调用**——减仓、平仓、清算、ADL 都不校验：

```text
oi = cumulativeOpenCostsUsd(marketIndex, isLong)        （已含本次增量）

硬顶：oi > maxOpenInterestKey(marketIndex, isLong)
      → revert MaxOpenInterestExceeded(oi, maxOpenInterest)

软顶：poolUsd = getPoolUsdWithoutPnl(market, collateralTokenPrice, false)      （.min 价）
      cap     = floor(poolUsd × maxOpenInterestFactorKey(marketIndex, isLong) / 1e30)
      oi > cap → revert MaxOpenInterestExceeded(oi, cap)
```

- 两条都是 **per-side**（分方向独立），且**严格大于才 revert**，恰好等于上限放行。
- `MAX_OPEN_INTEREST` 配置为 0 时任何正 OI 都会 revert，**没有“0 表示不限制”的豁免**（与 11.2 里 `maxPositionSizeUsd > 0` 的写法相反）。
- 校验对象是**成本口径**的 `cumulativeOpenCostsUsd`，不随 index 价波动；价格上涨不会把已有持仓推过这条线。

### 12.6 储备上限 RESERVE_FACTOR（市值口径，双边合计）

`MarketUtils.validateOpenInterestReserve`，由 `IncreasePositionUtils` 在 `cache.sizeDeltaUsd > 0` 时调用（纯加保证金跳过）：

```text
poolUsd        = getPoolUsdWithoutPnl(market, prices.collateralTokenPrice, false)     （.min 价）
totalNominalOI = ( openInterestInTokens(long) + openInterestInTokens(short) )
                 × prices.indexTokenPrice.max                    ← 市值口径、双边合计、不分方向
maxAllowed     = floor(poolUsd × reserveFactorKey(marketIndex) / 1e30)

totalNominalOI > maxAllowed → revert InsufficientReserveForOpenInterest(totalNominalOI, maxAllowed)
```

与 12.5 的分工：`RESERVE_FACTOR` 管“这个市场总共能开多大”（双边合计、市值口径、`indexPrice.max`），`MAX_OPEN_INTEREST` 管“单边硬顶”（成本口径）。两者独立生效。`reserveFactor` 允许 > 1e30（即比率 > 100%），`ConfigUtils.validateRange` 给它的上限是 `RESERVE_FACTOR ≤ 1e31`（1000%）。

### 12.7 ADL 状态机与执行校验

**状态开关**，`AdlUtils.updateAdlState`——无参迟滞开关，必须由 ADL keeper 主动轮询调用，不会自动置位：

```text
isAdlEnabled  = dataStore.getBool(isAdlEnabledKey())
pnlFactorType = isAdlEnabled ? MIN_PNL_FACTOR_AFTER_ADL : MAX_PNL_FACTOR_FOR_ADL
isADLStart    = !isAdlEnabled

shouldEnableAdl = globalNetObligationRatio > dataStore.getUint(pnlFactorType)

shouldEnableAdl == isAdlEnabled → revert AdlStateUnchanged(...)      ← 状态没变就 revert，不写状态
否则：setIsAdlEnabled(shouldEnableAdl)；setLatestAdlAt(block.timestamp)
```

**执行**，`AdlHandler.executeAdl`（`onlyRole(ADL_KEEPER)`），按顺序：

```text
1. AdlUtils.validateAdl
     !isAdlEnabled                       → revert AdlNotEnabled
     oracle.maxTimestamp() < latestAdlAt → revert OracleTimestampsAreSmallerThanRequired

2. isGlobalNetObligationRatioExceeded(MIN_PNL_FACTOR_AFTER_ADL, isADLStart=false)
     不超限 → revert AdlNotRequired(ratio, threshold)
     ⚠ 这里用的是**退出水位** MIN_PNL_FACTOR_AFTER_ADL，不是触发水位 MAX_PNL_FACTOR_FOR_ADL；
       触发水位只在 updateAdlState 置位时把过一次关

3. pnl = MarketUtils.getPnl(market, prices.indexTokenPrice, isLong, maximize=true)   ← 主签名价
     pnl <= 0 → revert AdlPnlNotPositive(marketIndex, isLong, pnl)

4. AdlUtils.createAdlOrder
     sizeDeltaUsd > position.sizeInUsd → revert InvalidSizeDeltaForAdl
     订单：orderType = MarketDecrease（不是独立类型）
           isSizeDeltaUsd = true
           acceptablePrice = isLong ? 0 : type(uint256).max     （无滑点保护）
           uiFeeReceiver = address(0)，executionFee = 0
           updatedAtTime = oracle.minTimestamp()

5. FeatureUtils.validateFeature(executeAdlFeatureDisabledKey(AdlHandler, uint256(order.orderType())))
     该开关被打开（功能禁用）→ revert，本步在建单之后、执行之前

6. 以 secondaryOrderType = Adl 执行订单
     → getExecutionPriceForDecrease 里 allowNegativeSpread = false（v0.3.2 新增，与清算同口径）

7. 后置：nextRatio = getGlobalNetObligationRatio(isADLStart=false)
     nextRatio >= 步骤 2 的 ratio → revert InvalidAdl(nextRatio, ratio)
     只要求**严格单调下降**，没有单笔降幅上限
```

第 3 步用的是主签名价（本笔交易 oracle 报文），第 2 / 7 步用的是二级价——同一笔 `executeAdl` 里的两套价格来源不同，算期望值时不能混用。

ADL 若是部分减仓（`sizeDeltaUsd < position.sizeInUsd`），第 6 步的订单执行同样会走 11.4 那道 `willPositionCollateralBeSufficient` 闸门与它的自动降级链，可能把 ADL 单就地升级为整仓全平。

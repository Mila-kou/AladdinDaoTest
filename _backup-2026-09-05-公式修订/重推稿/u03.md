## 4. 动态点差与成交价格

v0.3.2 的点差链路相对 v0.3.1 有一次结构性改造（`src/pricing/PositionPricingUtils.sol::getDynamicSpread`）：返回类型由 `uint256` 改为 `int256`，`if (dynamicSpread <= 0) return 0` 的硬编码地板被**按市场 × 方向可配置的 `Calc.clamp(raw, minDynamicSpread, maxDynamicSpread)`** 取代，普通开平仓因此可以拿到负点差（成交价优于 oracle）；清算与 ADL 通过 `allowNegativeSpread=false` 把有效下限抬回 0。整章公式全部以 `1e18` 为标度（`1e18 = 100%`），`dynamicSpread` 在事件里位于 **intItems**（`PositionIncrease` 的 `intItems[1]`、`PositionDecrease` 的 `intItems[3]`，**0 基下标**，`src/position/PositionEventUtils.sol:64` / `:114`；按中文“第 1 项”的 1 基直觉解析会取到 `collateralDeltaAmount`），链下按无符号解析会读错负值。

本章所有函数锚点：

| 环节 | 源码锚点 |
| --- | --- |
| 点差总合成 | `src/pricing/PositionPricingUtils.sol::getDynamicSpread` |
| 深度冲击分量 | `src/pricing/PositionPricingUtils.sol::getPriceImpactSpread` |
| OI 前后快照 | `src/pricing/PositionPricingUtils.sol::getNextOpenInterest` / `getNextOpenInterestParams` |
| 偏斜参考与改善判定 | `src/pricing/PositionPricingUtils.sol::getSkewRef` / `isBalanceWasImproved` |
| 偏斜分量 | `src/pricing/PositionPricingUtils.sol::getSkewImpact` |
| 加仓成交价 | `src/position/PositionUtils.sol::getExecutionPriceForIncrease` |
| 减仓成交价 | `src/position/PositionUtils.sol::getExecutionPriceForDecrease` |
| acceptablePrice 闸门 | `src/order/BaseOrderUtils.sol::getExecutionPriceForIncrease` / `getExecutionPriceForDecrease` |

### 4.1 动态点差

`PositionPricingUtils.sol::getDynamicSpread(GetDynamicSpreadParams params) → (int256 dynamicSpread, bool balanceWasImproved)`：

```text
早退：params.usdDelta == 0 → return (0, false)     ← balanceWasImproved 也强制为 false

constantPriceSpread = CONSTANT_PRICE_SPREAD[marketIndex]              （uint，1e18）
priceImpactSpread   = getPriceImpactSpread(params)                    （见 4.2，int，恒 ≥ 0）
skewImpact          = getSkewImpact(...)                              （见 4.4，int，可正可负）

rawDynamicSpread = skewImpact + int256(constantPriceSpread) + priceImpactSpread

minDynamicSpread = getInt(MIN_DYNAMIC_SPREAD[marketIndex][order.isLong])
maxDynamicSpread = getInt(MAX_DYNAMIC_SPREAD[marketIndex][order.isLong])

分支①  if (!allowNegativeSpread && minDynamicSpread < 0)  minDynamicSpread = 0
分支②  if (maxDynamicSpread < minDynamicSpread)           maxDynamicSpread = minDynamicSpread

dynamicSpread = Calc.clamp(rawDynamicSpread, minDynamicSpread, maxDynamicSpread)
```

`Calc.clamp`（`src/utils/Calc.sol::clamp`）语义：`value < min → min`；否则 `value > max → max`；否则原值。**等号不属于钳制侧**（`value == min` 或 `value == max` 都返回原值）。

要点与陷阱：

- **上下界来源是 DataStore 的 `getInt`，维度为 `(marketIndex, isLong)`**（`FX100Keys.sol:613` / `:621`），且这里的 `isLong` 取自 `params.isLong`＝调用方传入的 **`order.isLong()`**（`PositionUtils.sol:624` / `:713`），不是 `position.isLong()`。两者在正常仓位路径上恒等（仓位键含 isLong），核对脚本仍应按 order 侧取值。
- **两个键未配置 → 点差恒 0，且常数点差一并被吞**。`getInt` 对未写入的键返回 `0`，于是 `clamp(raw, 0, 0)`：`raw > 0` 走 `value > max → max = 0`，`raw < 0` 走 `value < min → min = 0`。结果不是“退回 v0.3.1 的 floor-at-0”（那种口径会保留正的常数点差），而是**整条点差链路失效、执行价恰好等于 oracle 选价**。这是 v0.3.2 升级漏配的事故形态（对照用例 `Docs/contract-releases/v0.3.2/05-重要参数边界场景.md` B32-1-01）。
- **`max < min` 的错配不会 revert**：分支②把区间坍缩成 `[min, min]`，点差恒等于 `min`（B32-1-05）。`Config.sol::setInt` 只过 `_validateKey`，**不经 `ConfigUtils.validateRange`**，越界与相对关系全无链上校验。
- **负点差的实际下限由两层 clamp 中更紧的一层决定**：`skewImpact` 自己已在 `[MIN_SKEW_IMPACT, MAX_SKEW_IMPACT]` 内被钳过一次（4.4），`minDynamicSpread` 是第二层。部署脚本默认 `minSkewImpact = 0`（`scripts/config/defaults.ts:58` / `:84`，两个市场都是 0），此时 `skewImpact ≥ 0`，`raw` 恒非负，`minDynamicSpread = −2e16` 的默认值**永不生效**；要让点差真能为负，必须先把 `MIN_SKEW_IMPACT` 调负。各环境实际写入值随 fork 重建漂移，**以现场 `DataStore.getInt` 读回为准**（本文只引用 `defaults.ts` 与 `07-清算数据核对公式表.md` 记录的 tx-fork 值，未现场读链核实）。
- 默认 `maxDynamicSpread = 1e18`（100%）在子项钳制齐全时同样不可达，但**三项自然上限按市场而异**：`MAX_SKEW_IMPACT` 与 `CONSTANT_PRICE_SPREAD` 都是 per-market 键（`FX100Keys.sol:663` / `constantPriceSpreadKey`），只有 `MAX_PRICE_IMPACT_SPREAD` 是全局键（`FX100Keys.sol:49`）。按 `scripts/config/defaults.ts`：ETH（`:59` `maxSkewImpact = 5e15`）＝ `1e14 + 5e15 + 5e15 = 1.01e16`（0.01% + 0.5% + 0.5% ＝ 1.01%）；WBTC（`:85` `maxSkewImpact = 1e16`）＝ `1e14 + 5e15 + 1e16 = 1.51e16`（0.01% + 0.5% + 1% ＝ 1.51%）。钳顶断言必须**按目标市场现场读回的 `CONSTANT_PRICE_SPREAD` / `MAX_PRICE_IMPACT_SPREAD` / `MAX_SKEW_IMPACT` 重算可达区间**后再把 `max` 下调进去，否则是无断言的空检查。

`allowNegativeSpread` 的取值由调用点决定，没有第三种来源：

| 调用点 | 场景 | `allowNegativeSpread` | 源码 |
| --- | --- | ---: | --- |
| `getExecutionPriceForIncrease` | 一切加仓（开仓/加仓，含 Reader 预览） | 恒 `true`（字面量） | `PositionUtils.sol:625` |
| `getExecutionPriceForDecrease` | 普通减仓/平仓（Market/Limit/StopLoss、Reader 预览） | `true` | `PositionUtils.sol:698` |
| `getExecutionPriceForDecrease` | `Order.isLiquidationOrder(order.orderType())` 为真 | `false` | `PositionUtils.sol:700` |
| `getExecutionPriceForDecrease` | `params.secondaryOrderType == Order.SecondaryOrderType.Adl` | `false` | `PositionUtils.sol:701` |

- `SecondaryOrderType.Adl` 由 `AdlHandler.executeAdl` 在组装执行参数时打上（`src/exchange/AdlHandler.sol:128` → `BaseOrderHandler._getExecuteOrderParams`），ADL 订单本身的 `orderType` 仍是普通 `MarketDecrease`，只能靠这个二级类型区分。
- `PositionUtils.sol::isPositionLiquidatable` 在合成临时订单时**无条件**执行 `cache.params.order.setOrderType(Order.OrderType.Liquidation)`（`:341`，不带 `if (forLiquidation)`），因此开仓后校验、减仓后校验、真清算 gate、Reader 只读清算查询这四个调用点全部走 `allowNegativeSpread=false`——安全校验不会被一笔“改善平衡”的临时 rebate 放行。
- 清算/ADL 只清零下限，**上限沿用普通交易那份 `MAX_DYNAMIC_SPREAD`**，清算执行价同样被它封顶（这是 2026-08-03 团队定案的预期行为，不是缺陷）。

### 4.2 Price Impact Spread

`PositionPricingUtils.sol::getPriceImpactSpread`，返回 `int256` 但恒 `≥ 0`：

```text
orderSize            = abs(params.usdDelta)                    ← 覆盖前的 usdDelta（见 4.3）
priceImpactParameter = PRICE_IMPACT_PARAMETER[marketIndex]     （1e18 = 1）
depth                = ASK / BID_ORDER_BOOK_DEPTH[marketIndex] （1e30 USD，选择见下表）

早退：depth == 0 或 priceImpactParameter == 0 → return 0        ← 防除零守卫

maxPriceImpactSpread = MAX_PRICE_IMPACT_SPREAD                 ← 全局键，无 marketIndex 维度
priceImpactExponent  = Math.mulDiv(orderSize, priceImpactParameter, depth)   （512 位全精度，向下取整）

早退：priceImpactExponent > uint256(LogExpMath.MAX_NATURAL_EXPONENT = 130e18)
      → return maxPriceImpactSpread                            ← 直接返回，不走 exp / max / ÷100 / min

rawPriceImpactSpread
= uint256( max( LogExpMath.exp(priceImpactExponent) − 1e18,
                (orderSize × 1e18) / depth ) ) / 100           ← 两处除法均向下取整

priceImpactSpread = min(rawPriceImpactSpread, maxPriceImpactSpread)
```

Order Book Depth 选择（`params.usdDelta` 符号 × `params.isLong` ＝ `order.isLong()`）：

| 操作 | usdDelta 符号 | Depth |
| --- | --- | --- |
| Long 加仓 | `> 0` | Ask depth |
| Short 减仓 | `< 0` | Ask depth |
| Short 加仓 | `> 0` | Bid depth |
| Long 减仓 | `< 0` | Bid depth |

要点：

- `LogExpMath.exp` 是 Balancer 的定点移植（`src/common/math/LogExpMath.sol`）。复算期望值**必须逐句整数移植**（`TestCode/src/reconciliation/formulas.ts::logExpMathExp` 已有 bit 级一致的实现），不能用浮点 `Math.exp` 顶替；乘除顺序一旦重排就会差 1 wei。
- 因为 `priceImpactExponent` 由 `uint256` 转入，输入恒 `≥ 0`，`MIN_NATURAL_EXPONENT`（`−41e18`）永不触发；`exp(0) = 1e18` 使指数项为 0。
- `÷100` 把“以 1 为 100% 的自然指数结果”转成“1e18 = 100%”的点差标度；除法向下取整。
- 小单场景下线性项 `orderSize × 1e18 / depth` 通常大于指数项，`SignedMath.max` 取线性项——这一点决定了小单期望值可以精确整除、不受 `exp` 精度影响。

### 4.3 Skew Reference

偏斜参考量来自 `getNextOpenInterest(params, true)`——**点差链路只有这一个调用点，且第二参数写死 `true`**（`PositionPricingUtils.sol:166`）：

```text
midPrice = (indexTokenPrice.max + indexTokenPrice.min) / 2          ← Price.sol::midPrice，向下取整

longOpenInterest  = OPEN_INTEREST_IN_TOKENS[marketIndex][true]  × midPrice
shortOpenInterest = OPEN_INTEREST_IN_TOKENS[marketIndex][false] × midPrice

▲ params.usdDelta 在此处被就地覆盖（PositionPricingUtils.sol:303）：
  params.usdDelta = params.tokenDelta × midPrice
```

**这是本章最容易算错的一步**：`getNextOpenInterest` 收到的是 `memory` 结构体引用，`params.usdDelta` 被 `tokenDelta × midPrice` **覆盖**，随后的 `nextLong/nextShort` 全部基于覆盖后的值。由于 `getPriceImpactSpread(params)` 在 `getNextOpenInterest` **之前**调用（`:164` 早于 `:166`），深度冲击分量用的是**覆盖前**的 `usdDelta`（即订单解析出的 `sizeDeltaUsd`），偏斜分量用的是**覆盖后**的值。两个分量的“订单规模”口径不同，复算时不能共用一个数。

- **OI 口径是盯市（mark-to-market），不是成本口径**：用 `MarketUtils.getOpenInterestInTokensInUsd`（即 `openInterestInTokens × midPrice`），不是 `MarketUtils.getCumulativeOpenCosts`。`getNextOpenInterest` 里 `useOpenInterestInTokens=false` 的成本口径分支在 v0.3.2 是死分支（全仓库只有 `PositionPricingUtils.sol:166` 一个调用点且写死 `true`）。**注意：资金费的 skew 用的是同一个盯市口径**——`MarketUtils.sol::getNextFundingAmountPerSize` `:483`／`:486` 取 `openInterestInTokens`，`:490`／`:491` 乘 `indexTokenPrice.midPrice()`，`:503`／`:504` 得 `diffOI × 1e18 / totalOpenInterest`（见 §10.1 / §10.2），全程不经 `getCumulativeOpenCosts`，两条链路一致，不要因为函数名不同而误判。成本口径 `getCumulativeOpenCosts` 另有其用：PnL 基数（`MarketUtils.sol:273`，见 §12.2）、OI 上限校验（`:646`，见 §12.5）、`getOpenInterestWithPnl`（`:787`）、`getMinCollateralFactorForOpenInterest`（`:877`）与 `ReaderUtils.sol:174`，都不参与点差与资金费 skew。
- 选价用 **midPrice**，既不是 `max` 也不是 `min`。

```text
nextLongOpenInterest  = longOpenInterest
nextShortOpenInterest = shortOpenInterest

if (isLong):
    if (usdDelta < 0 && abs(usdDelta) > longOpenInterest)  nextLong = 0        ← 下溢保护分支
    else                                                   nextLong = longOpenInterest + usdDelta
else:
    if (usdDelta < 0 && abs(usdDelta) > shortOpenInterest) nextShort = 0       ← 下溢保护分支
    else                                                   nextShort = shortOpenInterest + usdDelta
```

只有仓位所属方向被改动，另一侧原样带过（`getNextOpenInterestParams`）。这里的 `isLong` 同样是 `order.isLong()`。

`getSkewRef`：

```text
currentDenominator = longOI + shortOI
nextDenominator    = nextLongOI + nextShortOI

skewBeforeAbs = currentDenominator == 0 ? 0
              : abs(longOI − shortOI) × 1e18 / abs(currentDenominator)        ← Precision.mulDiv，向下取整
skewAfterAbs  = nextDenominator == 0 ? 0
              : abs(nextLongOI − nextShortOI) × 1e18 / abs(nextDenominator)   ← Precision.mulDiv，向下取整

skewRef = (skewBeforeAbs + skewAfterAbs) / 2                                   ← 向下取整
```

两项都是**绝对**偏斜率（无符号），`skewRef` 是两者的算术平均；分母为 0 时该项单独取 0（不是整体取 0）。

边界：若 `tokenDelta` 解析成 0（极小单），覆盖后的 `usdDelta` 也是 0，则 `nextLong == longOI`、`skewAfterAbs == skewBeforeAbs`、`balanceWasImproved = false`；但 `priceImpactSpread` 仍按覆盖前的非零 `usdDelta` 计算，不会跟着归零。

### 4.4 Skew Impact

`PositionPricingUtils.sol::getSkewImpact`：

```text
skewImpact = SKEW_IMPACT_FACTOR[marketIndex] × skewRef / 1e18     ← int × uint→int，除法向零截断

if (balanceWasImproved)  skewImpact = -skewImpact                 ← 取负发生在截断之后

minSkewImpact = getInt(MIN_SKEW_IMPACT[marketIndex])
maxSkewImpact = getInt(MAX_SKEW_IMPACT[marketIndex])

return SignedMath.max(minSkewImpact, SignedMath.min(maxSkewImpact, skewImpact))
```

- `MIN_SKEW_IMPACT` / `MAX_SKEW_IMPACT` **只按市场，不分方向**（`FX100Keys.sol:656` / `:663`，与 `MIN/MAX_DYNAMIC_SPREAD` 的 `(marketIndex, isLong)` 不同）；两键的默认值也逐市场不同（ETH `0 / 5e15`、WBTC `0 / 1e16`，见 4.1 末条）。
- 这层 clamp 用 `SignedMath.max(min, SignedMath.min(max, x))`，`min > max` 的错配会让结果恒等于 `min`（与 4.1 分支②的效果相同，但这里没有显式的修正分支）。
- 取整方向：先按**正的幅度**做截断除法，再整体取负——等价于“向零截断”，负值不会被放大。
- v0.3.2 未改动本函数及其两个键（需求方案一.1 明确“这层不用动”），逐字沿用 v0.3.1。

`isBalanceWasImproved`（`PositionPricingUtils.sol::isBalanceWasImproved`）：

```text
currentImbalance = longOI − shortOI                （有符号）
nextImbalance    = nextLongOI − nextShortOI
balanceWasImproved = abs(nextImbalance) < abs(currentImbalance)     ← 严格小于，相等算「未改善」
```

该布尔值同时被 `getSkewImpact` 用来翻符号，并随 `ExecutionPriceResult.balanceWasImproved` 一路带到费率档位与事件里（`usdDelta == 0` 的早退路径固定回 `false`）。

### 4.5 加仓成交价

`PositionUtils.sol::getExecutionPriceForIncrease`（`external view`，Reader 亦经此函数）：

```text
(sizeDeltaUsd, sizeDeltaInTokens) = getIncreaseOrderSize(params, prices)      ← 预解析，见 §3.1

早退：sizeDeltaUsd == 0 →                                       ← PositionUtils.sol:604
      executionPrice = indexTokenPrice.pickPrice(position.isLong())           ← 多取 max、空取 min
      sizeDeltaUsd = sizeDeltaInTokens = 0，dynamicSpread = 0，
      balanceWasImproved = false，且不做 acceptablePrice 校验

(dynamicSpread, balanceWasImproved) = getDynamicSpread(
      usdDelta   = +sizeDeltaUsd,
      tokenDelta = +sizeDeltaInTokens,
      isLong     = order.isLong(),
      allowNegativeSpread = true)
```

**预解析出来的 `sizeDeltaUsd` / `sizeDeltaInTokens` 只是喂给 `getDynamicSpread` 的中间量**（§3.1 的 `indexPrice.max/min` 除法结果不是最终值）；拿到 `dynamicSpread` 之后，两者中的一个会被**含点差的 `executionPrice` 覆盖重算**：

```text
执行价（两种 isSizeDeltaUsd 模式下公式相同）：
  position.isLong()  → executionPrice = ceil( indexTokenPrice.max × (1e18 + dynamicSpread) / 1e18 )
                                        （Precision.mulDiv(..., roundUpMagnitude = true)）
  !position.isLong() → executionPrice = floor( indexTokenPrice.min × (1e18 − dynamicSpread) / 1e18 )
                                        （普通 a × b / c，向下取整）

规模重算：
  isSizeDeltaUsd == true （USD 模式，sizeDeltaUsd 保持 = order.sizeDelta()）
      long  → sizeDeltaInTokens = floor(sizeDeltaUsd / executionPrice)
      short → sizeDeltaInTokens = Calc.roundUpDivision(sizeDeltaUsd, executionPrice)   ← ceil

  isSizeDeltaUsd == false（Token 模式，sizeDeltaInTokens 保持 = order.sizeDelta()）
      long / short 同式 → sizeDeltaUsd = sizeDeltaInTokens × executionPrice            ← 精确乘法，不取整
```

`(1e18 ± dynamicSpread)` 在源码里由 `Calc.sumReturnUint256(a, b)` 完成：`b > 0 → a + |b|`（加法，任意量级都不 revert），否则 `a − |b|`（Solidity 0.8 的 checked 减法，只有 `|b| > a` 才 revert）。传入的符号按买卖侧分：**买侧传 `+dynamicSpread`**（多头加仓 `PositionUtils.sol:633` / `:647`、空头减仓 `:724`），**卖侧传 `−dynamicSpread`**（空头加仓 `:640` / `:654`、多头减仓 `:720`）。由此：

- **负点差时买侧价格下降、卖侧价格上升，两侧都对 trader 有利**；取整方向不随符号改变——买侧恒 `ceil`、卖侧恒 `floor`。
- **越界点差只有一侧 revert，不能当成配置护栏**：`dynamicSpread > 1e18` 时只有走减法分支的卖侧（空头加仓 / 多头减仓）revert，买侧（多头加仓 / 空头减仓）走加法分支照常返回，执行价被按 `(1e18 + dynamicSpread) / 1e18` 成倍放大（例：`dynamicSpread = 2e18` ⇒ 执行价 `= 3 × indexTokenPrice.max`）；`dynamicSpread < −1e18` 时 revert 侧恰好互换（买侧 revert、卖侧成倍放大）。因为 `Config.setInt` 无范围校验（4.1、台账 #2、B32-1-09），`|dynamicSpread| > 1e18` 是可达状态，越界用例必须按方向分写期望：一侧 expect revert，另一侧 expect 畸变执行价，不能四条路径一律写 expect revert。

选价 / 取整配对（加仓）：

| 方向 | 基准价 | spread 施加 | 取整 | 规模重算取整（USD 模式） |
| --- | --- | --- | --- | --- |
| Long increase（买侧） | `indexTokenPrice.max` | `× (1e18 + spread)` | `ceil` | `floor(usd / execPrice)` |
| Short increase（卖侧） | `indexTokenPrice.min` | `× (1e18 − spread)` | `floor` | `ceil(usd / execPrice)` |

最后过 acceptablePrice 闸门（见 4.7）。

**数值例（fixture 见 `05-重要参数边界场景.md` §1.5，已验算）**：`CONSTANT_PRICE_SPREAD=1e14`、`PRICE_IMPACT_PARAMETER=6e17`、`depth=1e37`（10,000,000 USD）、`SKEW_IMPACT_FACTOR=0`、oracle `min=max=3e15`（3,000 USD）、开多 `sizeDeltaUsd=1e34`（10,000 USD，USD 模式）：

```text
线性项 = 1e34 × 1e18 / 1e37 = 1e15
指数   = mulDiv(1e34, 6e17, 1e37) = 6e14   → exp − 1e18 ≈ 6.0018e14 < 1e15，取线性项
priceImpactSpread = 1e15 / 100 = 1e13      （min(·, 5e15) 不生效）
skewImpact = 0（factor = 0）
rawDynamicSpread = 0 + 1e14 + 1e13 = 1.1e14   → clamp([−2e16, 1e18]) 内不变

executionPrice   = ceil(3e15 × (1e18 + 1.1e14) / 1e18) = 3000330000000000   （3,000.33 USD）
sizeDeltaInTokens = floor(1e34 / 3000330000000000)      = 3332966706995563821
（对照：预解析值 floor(1e34 / 3e15) = 3333333333333333333，差 366626337769512 —— 
  预解析值不是最终值，直接拿它当期望会系统性偏大）
```

其中 `exp(6e14) − 1e18 ≈ 6.0018e14` 是浮点近似，只用于说明 `SignedMath.max` 在此 fixture 下取线性项；最终三个期望值（`1e13` / `3000330000000000` / `3332966706995563821`）均为整数精确复算。若构造指数项胜出的用例，必须改用 `LogExpMath` 的逐句整数移植求值，不能沿用该近似。

### 4.6 减仓成交价

`PositionUtils.sol::getExecutionPriceForDecrease`（`public view`）：

```text
早退：order.sizeDelta() == 0 →                                  ← 判据是订单原始 sizeDelta，先于规模解析
      executionPrice = indexTokenPrice.pickPrice(!position.isLong())      ← 多取 min、空取 max
      sizeDeltaUsd = sizeDeltaInTokens = 0，dynamicSpread = 0，
      balanceWasImproved = false，且不做 acceptablePrice 校验

(sizeDeltaUsd, sizeDeltaInTokens) = getDecreaseOrderSize(params)          ← 见 §3.2，全平走恒等分支

allowNegativeSpread = true
if (Order.isLiquidationOrder(order.orderType()) || secondaryOrderType == SecondaryOrderType.Adl)
    allowNegativeSpread = false

(dynamicSpread, balanceWasImproved) = getDynamicSpread(
      usdDelta   = −sizeDeltaUsd,
      tokenDelta = −sizeDeltaInTokens,
      isLong     = order.isLong(),
      allowNegativeSpread)

position.isLong()  → executionPrice = floor( indexTokenPrice.min × (1e18 − dynamicSpread) / 1e18 )
!position.isLong() → executionPrice = ceil ( indexTokenPrice.max × (1e18 + dynamicSpread) / 1e18 )
                                      （Precision.mulDiv(..., roundUpMagnitude = true)）
```

与加仓的关键差别：**减仓的 `sizeDeltaUsd` / `sizeDeltaInTokens` 在拿到执行价之后不再重算**，直接原样返回。减仓规模只由 §3.2 的比例换算决定，与执行价无关；全平走恒等分支，零舍入尘埃。

选价 / 取整配对（减仓）：

| 方向 | 基准价 | spread 施加 | 取整 |
| --- | --- | --- | --- |
| Long decrease（卖侧） | `indexTokenPrice.min` | `× (1e18 − spread)` | `floor` |
| Short decrease（买侧） | `indexTokenPrice.max` | `× (1e18 + spread)` | `ceil` |

**清算 / ADL 三路对比**（同一 OI、同一 oracle、同一规模的改善平衡减多，`min=max=3e15`、`raw = −4.89e15`）：

| 路径 | `allowNegativeSpread` | `dynamicSpread` | 多头减仓执行价 |
| --- | --- | ---: | ---: |
| 普通 `MarketDecrease` | `true` | `−4890000000000000` | `3e15 × (1e18 + 4.89e15)/1e18 = 3014670000000000`（优于 oracle min） |
| `Liquidation` | `false` | `clamp(−4.89e15, 0, 1e18) = 0` | `3000000000000000`（恰等 oracle min） |
| `SecondaryOrderType.Adl` | `false` | `0` | `3000000000000000` |

上表 `raw = −4.89e15` 的出处与前置配置：`05-重要参数边界场景.md` §1.5 公共 fixture + B32-1-07，即 `SKEW_IMPACT_FACTOR = 1e16`、**`MIN_SKEW_IMPACT / MAX_SKEW_IMPACT = ∓5e15`**、`MIN_DYNAMIC_SPREAD / MAX_DYNAMIC_SPREAD = −2e16 / 1e18`。推导：OI 由 `(long = 10D, short = 0)` 变为 `(long = 9D, short = 0)`，前后都是单边 ⇒ `skewBeforeAbs = skewAfterAbs = skewRef = 1e18`；未钳制 `skewImpact = 1e16 × 1e18 / 1e18 = 1e16`，改善方向取负后钳到 `−5e15`；`raw = −5e15 + 1e14 + 1e13 = −4.89e15`。**必须先把 `MIN_SKEW_IMPACT` 写成 `−5e15` 才可达**——按 4.1 提到的 `defaults.ts` 默认值（`minSkewImpact = 0`）`raw` 恒非负，这张表复现不出来。

### 4.7 acceptablePrice 闸门与已知口径陷阱

执行价算完后必须过一次闸门（`src/order/BaseOrderUtils.sol`），不通过**直接 revert**（`FxErrors.OrderNotFulfillableAtAcceptablePrice(executionPrice, acceptablePrice)`），不是夹紧、不是静默通过：

```text
加仓（getExecutionPriceForIncrease）：
    long  要求 executionPrice <= acceptablePrice
    short 要求 executionPrice >= acceptablePrice

减仓（getExecutionPriceForDecrease）：
    long  要求 executionPrice >= acceptablePrice
    short 要求 executionPrice <= acceptablePrice
```

- 清算合成订单把 `acceptablePrice` 设为 `isLong ? 0 : type(uint256).max`（`PositionUtils.sol:339`、`LiquidationUtils.sol`），闸门恒过；Reader 预览同样按方向填 `0` / `max`（`ReaderPricingUtils.sol::getExecutionPrice`），预览不会因闸门 revert。
- `sizeDelta == 0` 的两条早退路径（4.5 / 4.6）**跳过闸门**，源码注释明确说明限价单的 `triggerPrice` 已在别处校验。

核对时的三个口径陷阱：

1. **`order.isLong()` 与 `position.isLong()` 混用**：`getDynamicSpread` 的 `isLong` 入参（决定 depth 选择与 `MIN/MAX_DYNAMIC_SPREAD` 取值）来自 `order.isLong()`；执行价的多空分支与 `pickPrice` 来自 `position.isLong()`；`getIncreaseOrderSize` / `getDecreaseOrderSize` 也用 `position.isLong()`。正常路径两者恒等，移植公式时必须分别取值，不能一律写 `isLong`。
2. **`Reader` 预览恒按非清算口径**：`ReaderPricingUtils.getExecutionPrice` 构造的临时订单 `orderType` 默认为 `MarketIncrease(0)`、`secondaryOrderType` 默认为 `None`，减仓预览拿到的是 `allowNegativeSpread = true` 的结果，不能用它来预测清算执行价。
3. **买侧 / 卖侧的溢出保护不对称**：买侧走 `Precision.mulDiv`（512 位中间值），卖侧是普通 `a × b / c`。极端价格 × 极端点差的边界用例应针对卖侧构造。

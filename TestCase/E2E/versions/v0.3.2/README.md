## 1. 目的

功能分析文档（`Docs/v0.3.2/功能分析流程/`）先说明 v0.3.2 Trade **是什么、用户能做什么、合约如何处理、前端应如何表现**，本目录再把功能需求映射到测试用例并登记结果。它不是脚本索引，也不以脚本执行速度代表功能覆盖完整度。

测试结论分三层记录：

1. **CT（Contract Trade）**：合约交易、定价、账本、事件与错误。
2. **FT（Frontend Trade）**：Trade 页面输入、预览、签名、状态反馈与展示。
3. **XT（Cross-layer Trade）**：同一笔交易的页面、请求参数、交易回执、事件、Reader 和余额差分一致性。

任何一层通过都不能代替另外两层。特别是 TestCode 中使用私钥直接签名、Inline Keeper 或 Driver 构造交易的快速脚本，只能证明它实际断言到的链上链路；未经过页面填写、按钮点击和钱包交互时，不得标记 FT 通过。

## 3. 文档写法

每个功能域统一回答六个问题：

1. **业务含义**：用户为什么需要它。
2. **合约行为**：使用什么字段、订单类型、价格和状态规则。
3. **影响数据**：直接改变什么，间接传导到什么，哪些只是相关而非因果。
4. **跨层要求**：合约、Keeper、Reader、SDK 和前端分别负责什么。
5. **边界值**：零值、等号、差 1、上下限、异常配置、精度与并发如何判定。
6. **测试证据**：页面、请求、交易、事件、Reader、状态和余额需要验证什么。

## 4. 结果判定词

以下状态只写入 [results.md](results.md)，不回填共享设计或版本用例正文。

- `NOT_RUN`：未在 CURRENT 登记的目标版本环境执行。
- `PASS`：步骤全部执行，断言全部成立，证据齐全。
- `FAIL`：被测功能与明确期望不一致。
- `BLOCKED`：环境或依赖不具备，记录解除条件。
- `GAP`：已明确的需求、实现或可测试面缺失，记录缺口与补齐条件。

同一用例只完成部分层或部分断言时，按 CT、FT、XT 分栏分别填写上述状态：未执行的层记 `NOT_RUN`，实现或测试面缺失的层记 `GAP`，不得合并成一个额外状态。

## 5. 最小证据

每条写链用例至少保存：环境与版本、数据集、账户、orderKey、创建/执行交易哈希、区块号、事件、Reader 前后值、USDC/仓位/OI 差分。涉及 FT 时再保存页面关键截图或录屏、实际提交参数、钱包/Flash 模式、页面最终状态和错误提示。

## 6. 自动化完成定义

一个脚本只有同时满足以下条件，才可在矩阵中标记 `AUTO-COMPLETE`：

1. 测试标题能直接说明业务动作和边界，而不是只写历史用例编号。
2. 数据集固定且在报告中可见。
3. 至少存在一个交易前断言、一个执行过程断言和一个交易后断言。
4. 数值期望由公式或前态推导，不以“非空”“成功返回”代替。
5. 报告明确区分 CT、FT、XT 覆盖；页面层只是尚未执行时 FT 记 `NOT_RUN`，页面实现或测试面不存在时才记 `GAP`。
6. 失败时能定位到功能点和断言字段，而不是只输出脚本异常。

## 7. 仓位费用

入口 `PositionPricingUtils.sol::getPositionFees`，费率与折扣部分全部在
`PositionPricingUtils.sol::getPositionFeesAfterReferral` 内一次算完，UI Fee 在
`PositionPricingUtils.sol::getUiFees`，清算费在 `PositionPricingUtils.sol::getLiquidationFees`（见 §8）。

计算顺序固定：后一步的**乘法**作用在前一步**已取整的 token 数量**上（例如 Pro 折扣乘在已取整的
`positionFeeAmount` 上，而不是乘回 `1e30` USD 标度再一起取整），因此整条链不能压成一个大表达式。
注意这与「同一步内部连续两次除法」不同——后者可以合并且结果恒等，见 §7.1。

| 顺序 | 字段 | 锚点 |
| --- | --- | --- |
| 1 | `positionFeeAmount` | `PositionPricingUtils.sol::getPositionFeesAfterReferral` |
| 2 | `pro.traderDiscountAmount` | 同上 |
| 3 | `referral.adjustedAffiliateRewardFactor` → `affiliateRewardAmount` / `referral.traderDiscountAmount` | 同上 |
| 4 | `totalDiscountAmount` → `protocolFeeAmount` | 同上 |
| 5 | `feeReceiverAmount` / `positionFeeAmountForPool` | 同上 |
| 6 | `liquidation.*`（仅 `isLiquidation = true`） | `PositionPricingUtils.sol::getLiquidationFees`（见 §8） |
| 7 | `feeAmountForPool` / `feeReceiverAmount` 合并清算费 | `PositionPricingUtils.sol::getPositionFees` |
| 8 | `funding.*` | `PositionPricingUtils.sol::getFundingFees`（见 §10） |
| 9 | `ui.uiFeeAmount` | `PositionPricingUtils.sol::getUiFees` |
| 10 | `totalCostAmountExcludingFunding` / `totalCostAmount` | `PositionPricingUtils.sol::getPositionFees`（见 §9） |

第 7 步与第 9 步之间没有数值依赖，但按源码次序，`ui.uiFeeAmount` 是在清算费合并之后才算的。

单位约定：所有 `*Factor` 为 `1e30` 标度比例；所有 `*Amount` 为**抵押代币原生精度**的 token 数量；
`sizeDeltaUsd`、`liquidationFeeUsd` 为 `1e30` 标度 USD。除特别注明外，所有乘除都是
`Precision.applyFactor` / 整数除法，一律**向下取整**。

`sizeDeltaUsd` 的取值随调用路径不同：

| 路径 | 传入的 `sizeDeltaUsd` | 锚点 |
| --- | --- | --- |
| 开仓 | `executionPriceResult.sizeDeltaUsd`（按含点差的 `executionPrice` 重算后的值，见 §4） | `IncreasePositionUtils.sol::processCollateral` |
| 平仓 / 清算 | `values.sizeDeltaUsd`（`getExecutionPriceForDecrease` 结果），`isLiquidation = Order.isLiquidationOrder(orderType)` | `DecreasePositionCollateralUtils.sol::processCollateral` |
| 可清算性判定 | `position.sizeInUsd()`（整仓），且强制 `isLiquidation = false`、`uiFeeReceiver = address(0)` | `PositionUtils.sol::isPositionLiquidatable`（构造 `GetPositionFeesParams` 处） |
| Reader 预览 | `positionInfo.executionPriceResult.sizeDeltaUsd`，且强制 `isLiquidation = false` | `ReaderPositionUtils.sol::getPositionInfo` |

### 7.1 基础仓位费

```text
positionFeeFactor
= DataStore.getUint(positionFeeFactorKey(marketIndex, balanceWasImproved))

positionFeeAmount
= floor( floor(sizeDeltaUsd × positionFeeFactor / 1e30) / collateralTokenPrice.min )
```

锚点：`PositionPricingUtils.sol::getPositionFeesAfterReferral`；key 见
`FX100Keys.sol::positionFeeFactorKey(marketIndex, balanceWasImproved)`。

- **两次向下取整**：先在 `1e30` USD 标度上 `applyFactor`（`Math.mulDiv`）取整得到 USD 费额，
  再除以抵押品价格取整成 token 数量。写成嵌套式是为了忠实对应源码语句，但**用精确整数（BigInt）
  计算时，写成两步与写成一步 `floor(sizeDeltaUsd × factor / (1e30 × collateralTokenPrice.min))`
  结果完全相同、不会差 1 个最小单位**——因为对正整数 `m`、`n` 有取整恒等式
  `⌊⌊x/m⌋/n⌋ = ⌊x/(m·n)⌋`。真正会产生 1 单位偏差的是另外两件事：
  (a) 用 JavaScript `Number` 参与 `1e30` 量级运算（见 §1.3 与 §7.7 案例 B）；
  (b) **重排乘除顺序**，把除以价格挪到 `applyFactor` 之前
  （`floor(floor(sizeDeltaUsd / price) × factor / 1e30)` 与链上不等，见 §7.7 案例 A）。
  此外链上 `Precision.applyFactor` 走 `Math.mulDiv`（512 位中间值），
  自己实现时朴素的 `a × f` 在 256 位下可能溢出。
- **选价侧**：`collateralTokenPrice.min`。除以更小的价格得到更大的 token 数量，方向对协议保守。
- **费率两档**由 `balanceWasImproved` 选择，`true` / `false` 是两个独立的 DataStore key，可以配成不同值。
- `positionFeeFactor` 上限 5%（`ConfigUtils.sol::validateRange`，`POSITION_FEE_FACTOR`）。
- 没有 `sizeDeltaUsd == 0` 的早退；此时费额自然为 0。

`balanceWasImproved` 的来源（`PositionPricingUtils.sol::getDynamicSpread` 的第二个返回值，
经 `ExecutionPriceResult` 传入，见 §4）：

```text
balanceWasImproved
= |nextLongOI − nextShortOI| < |longOI − shortOI|        // 严格小于
```

锚点 `PositionPricingUtils.sol::isBalanceWasImproved`。其中 OI 取
`getNextOpenInterest(params, useOpenInterestInTokens = true)`：多空 OI 均为
`MarketUtils.getOpenInterestInTokensInUsd(..., indexTokenPrice.midPrice())`，且 `usdDelta`
在该函数内被**改写**为 `tokenDelta × indexTokenPrice.midPrice()` 后才叠加到对应方向
（`PositionPricingUtils.sol::getNextOpenInterest` / `getNextOpenInterestParams`）。

两个会影响费率档位的分支：

- `getDynamicSpread` 在 `params.usdDelta == 0` 时早退返回 `(0, false)` → 走
  `balanceWasImproved = false` 那一档费率。
- `getNextOpenInterestParams` 中，减仓且 `|usdDelta|` 超过该方向 OI 时，`nextOpenInterest` 夹到 0
  而不是回滚。

### 7.2 Pro 折扣

```text
pro.traderTier = DataStore.getUint(proTraderTierKey(account))

if pro.traderTier == 0:
    pro.traderDiscountFactor = 0
    pro.traderDiscountAmount = 0            // 不读取 proDiscountFactorKey
else:
    pro.traderDiscountFactor = DataStore.getUint(proDiscountFactorKey(pro.traderTier))
    if pro.traderDiscountFactor > 0:
        pro.traderDiscountAmount = floor(positionFeeAmount × pro.traderDiscountFactor / 1e30)
    else:
        pro.traderDiscountAmount = 0
```

锚点：`PositionPricingUtils.sol::getPositionFeesAfterReferral`；key
`FX100Keys.sol::proTraderTierKey(account)` / `proDiscountFactorKey(proTier)`。

- 折扣作用在**已取整的 token 数量** `positionFeeAmount` 上，只有一次向下取整；这一步是「乘在已取整
  结果上」，与 §7.1 内部那两次除法不同，不能与上一步合并。
- `PRO_DISCOUNT_FACTOR` 上限 100%（`ConfigUtils.sol::validateRange`）。
- 结构体字段名是 `fees.pro.traderDiscountFactor`，与 §7.3 的 `fees.referral.traderDiscountFactor`
  是两个不同的值，事件里也分别以 `pro.traderDiscountAmount` / `referral.traderDiscountAmount` 输出
  （`PositionEventUtils.sol::_emitPositionFees`，经 `emitPositionFeesCollected` /
  `emitPositionFeesInfo` 发出）。

### 7.3 推荐返佣

**7.3.1 Factor 来源**

锚点：`ReferralUtils.sol::getReferralInfo`（返回 `code, affiliate, affiliateRewardFactor,
traderDiscountFactor, minAffiliateRewardFactor` 五项）。

```text
if referralStorage == address(0):
    返回 (0, address(0), 0, 0, 0)                     // 全部 factor 为 0

code = referralStorage.traderReferralCodes(trader)

if code == 0:
    totalRebate = 0; discountShare = 0; minAffiliateRewardFactor = 0
else:
    affiliate        = referralStorage.codeOwners(code)      // 可能是 address(0)
    tierLevel        = referralStorage.referrerTiers(affiliate)
    (totalRebate, discountShare) = referralStorage.tiers(tierLevel)      // 单位：基点
    minAffiliateRewardFactor = DataStore.getUint(minAffiliateRewardFactorKey(tierLevel))
    customDiscountShare = referralStorage.referrerDiscountShares(affiliate)
    if customDiscountShare != 0:
        discountShare = customDiscountShare                 // Affiliate 自设值覆盖 tier 默认值

referral.traderDiscountFactor
= basisPointsToFloat( floor(totalRebate × discountShare / 10000) )       // 先在基点上取整

totalRebateFactor                                    // getReferralInfo 内的局部量，不在返回值里
= basisPointsToFloat(totalRebate)

referral.affiliateRewardFactor                       // 这一项才是返回值
= totalRebateFactor − referral.traderDiscountFactor
```

- `totalRebate`、`discountShare` 均 ≤ 10000 基点（`ReferralStorage.sol::setTier` /
  `setReferrerDiscountShare` 的 `require`）。
- `floor(totalRebate × discountShare / 10000)` 是**基点级**取整，再乘 `1e30 / 10000` 放大
  （`Precision.sol::basisPointsToFloat`）。即 trader 折扣率的分辨率只有 1 基点。
- `totalRebateFactor` 不是 `getReferralInfo` 的返回值，只是它的内部局部变量；结构体字段
  `fees.referral.totalRebateFactor` 是在 `getPositionFeesAfterReferral` 里由
  `affiliateRewardFactor + traderDiscountFactor` **重建**的（数值恒等，见 §7.3.2）。
- `code != 0` 但该码无主（`codeOwners[code] == 0`）时仍进入返佣分支，只是 tier 0 通常全 0。

**7.3.2 adjustedAffiliateRewardFactor（完整分支）**

锚点：`PositionPricingUtils.sol::getPositionFeesAfterReferral`。

```text
if referral.referralCode == 0:
    // 整段跳过：totalRebateFactor / adjustedAffiliateRewardFactor /
    // affiliateRewardAmount / referral.traderDiscountAmount / totalRebateAmount 全为 0
else:
    adjustedAffiliateRewardFactor = affiliateRewardFactor          // 默认值
    totalRebateFactor = affiliateRewardFactor + referral.traderDiscountFactor

    // 只有 Pro 折扣严格高于推荐的 Trader 折扣时才重算
    if pro.traderDiscountFactor > referral.traderDiscountFactor:
        adjustedAffiliateRewardFactor
        = pro.traderDiscountFactor > totalRebateFactor
          ? minAffiliateRewardFactor
          : totalRebateFactor − pro.traderDiscountFactor
        if adjustedAffiliateRewardFactor < minAffiliateRewardFactor:
            adjustedAffiliateRewardFactor = minAffiliateRewardFactor

    // v0.3.2 新增：总上限
    totalDiscountFactor = max(pro.traderDiscountFactor, referral.traderDiscountFactor)
    maxAffiliateRewardFactor
    = totalDiscountFactor < 1e30 ? 1e30 − totalDiscountFactor : 0
    if adjustedAffiliateRewardFactor > maxAffiliateRewardFactor:
        adjustedAffiliateRewardFactor = maxAffiliateRewardFactor
```

- **默认分支**（`pro.traderDiscountFactor <= referral.traderDiscountFactor`，含无 Pro 等级的常见情形）：
  `adjustedAffiliateRewardFactor = affiliateRewardFactor`，不做任何调整。上一版文档只写了 Pro 折扣更高
  的那条分支，缺这个默认值。
- `maxAffiliateRewardFactor` 是 v0.3.2 相对 v0.3.1 在**本节费用链路上唯一的实现变化**
  （`PositionPricingUtils.sol::getPositionFeesAfterReferral` 末尾新增 `totalDiscountFactor` /
  `maxAffiliateRewardFactor` / 封顶判断这一段；同文件其余 diff 属 §4 动态点差，
  `src/referral/` 只改了 `ReferralEventUtils.sol` 一行）：Affiliate Reward 与实际生效折扣之和
  不得超过 100%，防止 §7.4 的 uint 减法下溢。它只在 `minAffiliateRewardFactor` 被配得
  过大时才会真正生效 —— `MIN_AFFILIATE_REWARD_FACTOR` 在 `ConfigUtils.sol::validateRange` 里
  **没有**上限校验。
- 默认分支下该上限恒不生效：`affiliateRewardFactor = totalRebateFactor − traderDiscountFactor`
  且 `totalRebateFactor ≤ 1e30`，故必有 `affiliateRewardFactor ≤ 1e30 − traderDiscountFactor`。

**7.3.3 返佣金额**

```text
affiliateRewardAmount
= floor(positionFeeAmount × adjustedAffiliateRewardFactor / 1e30)

referral.traderDiscountAmount
= floor(positionFeeAmount × referral.traderDiscountFactor / 1e30)

totalRebateAmount
= affiliateRewardAmount + referral.traderDiscountAmount
```

`totalRebateAmount` 只用于事件输出（`PositionEventUtils.sol::_emitPositionFees`），不参与任何扣减。
`affiliateRewardAmount` 由 `PositionUtils.sol::handleReferral` →
`ReferralUtils.sol::incrementAffiliateReward` 累加到
`affiliateRewardKey(marketIndex, token, affiliate)`（`delta == 0` 时早退，不写账不发事件），
由 Affiliate 自行 `batchClaimAffiliateRewards` 领取。

### 7.4 最终折扣与协议费

```text
totalDiscountAmount
= max(pro.traderDiscountAmount, referral.traderDiscountAmount)      // 取大者，不相加

protocolFeeAmount
= positionFeeAmount − affiliateRewardAmount − totalDiscountAmount
```

锚点：`PositionPricingUtils.sol::getPositionFeesAfterReferral`。

- 两种折扣**只生效其一**，取金额较大的那个；另一个只出现在事件里。
- 减法是 uint 减法，下溢即 revert。因为 `max` 对 `floor` 单调（`totalDiscountAmount` 等于
  `floor(positionFeeAmount × totalDiscountFactor / 1e30)`）、且
  `adjustedAffiliateRewardFactor + totalDiscountFactor ≤ 1e30`（§7.3.2 的上限），
  有 `affiliateRewardAmount + totalDiscountAmount ≤ positionFeeAmount`，正常配置下不会下溢。
- 折扣不产生转账：它只是让交易者少付（进入 §9 的 `totalCostAmount` 减项）。
- **UI Fee 不在此处扣减**，见 §7.6。

### 7.5 协议与 LP 分成

```text
positionFeeReceiverFactor
= DataStore.getUint(POSITION_FEE_RECEIVER_FACTOR)                  // 全局，非按市场

feeReceiverAmount
= floor(protocolFeeAmount × positionFeeReceiverFactor / 1e30)

positionFeeAmountForPool
= protocolFeeAmount − feeReceiverAmount
```

随后在 `PositionPricingUtils.sol::getPositionFees` 里合并清算费（`isLiquidation = false` 时清算费全为 0；
清算费自身的计算见 §8）：

```text
feeAmountForPool
= positionFeeAmountForPool
+ liquidation.liquidationFeeAmount
− liquidation.liquidationFeeAmountForFeeReceiver

feeReceiverAmount += liquidation.liquidationFeeAmountForFeeReceiver   // 累加，非覆盖
```

注意 `fees.feeReceiverAmount` 在 `getPositionFees` 返回时**已经含**清算费分成，
读事件或 Reader 结果时不能再当作纯仓位费分成。

资金去向（分槽归集，`FX100Keys.sol` 的 `POSITION_FEE_TYPE` / `LIQUIDATION_FEE_TYPE` /
`UI_POSITION_FEE_TYPE`）：

| 路径 | `feeReceiverAmount` | `feeAmountForPool` |
| --- | --- | --- |
| 开仓 `IncreasePositionUtils.sol::processCollateral` | 全额 → `incrementClaimableFeeAmount(POSITION_FEE_TYPE)`（该路径 `isLiquidation = false`，清算费恒为 0） | `positionVault.transferOut` → `market.vault` |
| 平仓/清算 `DecreasePositionCollateralUtils.sol::processCollateral` | `feeReceiverAmount − liquidationFeeAmountForFeeReceiver` → `POSITION_FEE_TYPE`；`liquidationFeeAmountForFeeReceiver > 0` 时另记 `LIQUIDATION_FEE_TYPE` | 同上 |

**平仓/清算路径的门控（算期望值必须先判这一条）**：`DecreasePositionCollateralUtils.sol::processCollateral`
在 `payForCost(fees.totalCostAmountExcludingFunding × collateralTokenPrice.min)` 之后，只有
`collateralCache.result.remainingCostUsd == 0` 时才执行上表的归集；否则走 `else` 分支
`fees = getEmptyFees(fees)` —— 除 `collateralTokenPrice`、`funding.positiveFundingFeeAmount` 与两个
`latest*FundingFeePerSize` 外**所有费用字段清零**（`positionFeeAmount` / `protocolFeeAmount` /
`feeReceiverAmount` / `feeAmountForPool` / `totalDiscountAmount` / `ui.*` / `liquidation.*` /
`referral.*` / `pro.*` 全部为 0）；这些抵押品已在 `payForCost` 中被消耗掉（源码注释：
“the amount was entirely paid to the pool instead of for fees”）。

**清零之后交易未必成功。** `else` 分支的前提就是 `remainingCostUsd > 0`，紧接着的
`if (remainingCostUsd > 0)` 必然命中，无条件进入
`DecreasePositionCollateralUtils.sol::handleEarlyReturn(..., step = "fees")`，结局二选一：

- `collateralCache.isInsolventCloseAllowed == false` → 整笔订单
  **`revert FxErrors.InsufficientFundsToPayForCosts(remainingCostUsd, "fees")`**。
  用户自行发起的减仓 / 全平命中这条分支时就是这一支：结果是**交易失败**，不是「零费用成交」。
- `isInsolventCloseAllowed == true` → 不 revert，发 `PositionFeesInfo` 与 `InsolventClose` 两个事件，
  带着全 0 的 `fees` 提前返回（跳过后面「按 `initialCollateralDeltaAmount` 提取抵押品」的收尾），
  `feeAmountForPool` 归零后不再 `transferOut`，claimable 一分不记，
  后续 `DecreasePositionUtils.sol` 发出的 `PositionFeesCollected` 里费用字段也全是 0。

而 `isInsolventCloseAllowed = isFullyClosed && (isLiquidationOrder || secondaryOrderType == Adl)`
（`DecreasePositionCollateralUtils.sol::processCollateral` 开头；`isFullyClosed` 指 `order.sizeDelta`
恰等于 `position.sizeInUsd()` 或 `sizeInTokens()`，按 `order.isSizeDeltaUsd()` 选边）。
所以「费用字段全 0 而交易仍成功」**只在整仓清算 / 整仓 ADL 上成立**；这也正是
`DecreasePositionUtils.sol` 注释里说的「清算交易应当仍能完成，而手动平仓交易应当 revert」。

两个连带的核对要点：

- 更早的两处 `handleEarlyReturn`（`step = "funding"` / `"pnl"`，分别在付资金费和付负 PnL 之后）受同一条
  `isInsolventCloseAllowed` 门控，但它们传进去的 `fees` **尚未清零**——同一笔交易里
  `PositionFeesInfo` 会显示完整费额而 `PositionFeesCollected` 全是 0，以后者为准。
- `PositionFeesInfo` 只在 `handleEarlyReturn` 内发出，可直接当作「本笔走了资不抵债平仓」的判据。

`remainingCostUsd` 的定义见 §5.4 第 3 条，付费瀑布见 §9。

UI Fee 走另一套账：记到 `claimableUiFeeAmountKey(marketIndex, token, uiFeeReceiver)`
（`FeeUtils.sol::incrementClaimableUiFeeAmount(..., fees.ui.uiFeeAmount, UI_POSITION_FEE_TYPE)`，
`delta == 0` 时早退），不进 `feeReceiverAmount`、也不进 `feeAmountForPool`。但两条路径的调用条件不同：
**开仓路径无条件调用**；**平仓/清算路径的这次调用落在上面那条门控之内**（与
`incrementClaimableFeeAmount` 同处 `remainingCostUsd == 0` 的分支），走 `else` 时根本不调用，
UI Fee 一分不记。

### 7.6 UI Fee

```text
if uiFeeReceiver == address(0):
    uiFeeReceiver = 0; uiFeeReceiverFactor = 0; uiFeeAmount = 0        // 早退

uiFeeReceiverFactor
= min( DataStore.getUint(uiFeeFactorKey(uiFeeReceiver)),
       DataStore.getUint(MAX_UI_FEE_FACTOR) )

uiFeeAmount
= floor( floor(sizeDeltaUsd × uiFeeReceiverFactor / 1e30) / collateralTokenPrice.min )
```

锚点：`PositionPricingUtils.sol::getUiFees`，上限来自 `MarketUtils.sol::getUiFeeFactor`。

- `MAX_UI_FEE_FACTOR` 未配置（为 0）时 `uiFeeReceiverFactor` 恒为 0，UI Fee 为 0。
  `MAX_UI_FEE_FACTOR` 本身上限 5%（`ConfigUtils.sol::validateRange`）。
- 与 §7.1 同样是「applyFactor 取整后再除以价格取整」两步，同样取 `collateralTokenPrice.min`；
  同样地，用精确整数算时合并成一次除以 `1e30 × price` 与链上恒等，不产生 1 单位偏差。
- UI Fee **不从 `positionFeeAmount` 里切分**，而是在 §9 的 `totalCostAmountExcludingFunding`
  里作为**加项**额外向交易者收取，且不参与 `protocolFeeAmount` 的减法。
- 可清算性判定路径传 `uiFeeReceiver = address(0)`（`PositionUtils.sol::isPositionLiquidatable`），
  Reader 预览按调用方传入的地址计算。

### 7.7 数值算例（USDC 抵押，6 位精度）

参数：`sizeDeltaUsd = 1e34`（10,000 USD）、`positionFeeFactor = 5e26`（0.05%）、
`collateralTokenPrice.min = 1e24`（1 USDC = 1 USD）、推荐 tier `totalRebate = 2000bp`、
`discountShare = 5000bp`、`minAffiliateRewardFactor = 5e28`（5%）、
`pro.traderDiscountFactor = 1.3e29`（13%）、`positionFeeReceiverFactor = 5e29`（50%）。

```text
positionFeeAmount            = floor(1e34 × 5e26 / 1e30) / 1e24 = 5e30 / 1e24 = 5_000_000   (5.00 USDC)
pro.traderDiscountAmount     = floor(5e6 × 1.3e29 / 1e30)                     =   650_000   (0.65)
referral.traderDiscountFactor= basisPointsToFloat(2000 × 5000 / 10000 = 1000) = 1e29        (10%)
referral.affiliateRewardFactor = 2e29 − 1e29                                  = 1e29        (10%)

pro(1.3e29) > referral(1e29) → 重算：1.3e29 ≤ totalRebateFactor(2e29)
adjustedAffiliateRewardFactor = 2e29 − 1.3e29 = 7e28 (7%)，≥ min(5e28)，保留
totalDiscountFactor = 1.3e29 → maxAffiliateRewardFactor = 8.7e29，不触顶

affiliateRewardAmount        = floor(5e6 × 7e28 / 1e30)                       =   350_000   (0.35)
referral.traderDiscountAmount= floor(5e6 × 1e29 / 1e30)                       =   500_000   (0.50)
totalDiscountAmount          = max(650_000, 500_000)                          =   650_000   (0.65)
protocolFeeAmount            = 5_000_000 − 350_000 − 650_000                  = 4_000_000   (4.00, 占 80%)
feeReceiverAmount            = floor(4e6 × 5e29 / 1e30)                       = 2_000_000
positionFeeAmountForPool     = 4_000_000 − 2_000_000                          = 2_000_000
```

交易者实付 `5.00 − 0.65 = 4.35`，恰等于 `protocolFeeAmount 4.00 + affiliateReward 0.35`，与
`PositionPricingUtils.sol::getPositionFeesAfterReferral` 注释中的 example 2 一致。

**取整陷阱两例（均用 18 位精度 WETH 作抵押，`collateralTokenPrice.min` 为 `ETH 价 × 1e12`）**

案例 A —— 重排乘除顺序会差 1 wei（`sizeDeltaUsd = 1e33`（1,000 USD）、`positionFeeFactor = 6e26`（0.06%）、
ETH = 3,000 USD 即 `collateralTokenPrice.min = 3e15`）：

```text
链上两步    floor(1e33 × 6e26 / 1e30) = 6e29 (0.6 USD)
            floor(6e29 / 3e15)        = 200_000_000_000_000 wei   (0.0002 ETH)

合并一步    floor(1e33 × 6e26 / (1e30 × 3e15)) = 200_000_000_000_000     ← 与链上相同
先除价格    floor(1e33 / 3e15) = 333_333_333_333_333_333
            floor(333_333_333_333_333_333 × 6e26 / 1e30) = 199_999_999_999_999   ← 少 1 wei
```

案例 B —— 用 `Number` 代替 `BigInt` 会差 1 wei（`sizeDeltaUsd = 1.038e33`（1,038 USD）、
`positionFeeFactor = 5e26`（0.05%）、ETH = 3,000.7 USD 即 `collateralTokenPrice.min = 3.0007e15`）：

```text
费额 USD = floor(1.038e33 × 5e26 / 1e30) = 5.19e29   (0.519 USD)

精确整数  5.19e29 / 3.0007e15 = 172_959_642_750_024 …余 2.9832e15（约 0.994 wei）→ floor = 172_959_642_750_024
IEEE-754  5.19e29 / 3.0007e15 在 double 下恰好等于 172_959_642_750_025.0 → floor 也得 …025   ← 多 1 wei
```

结论：**合并/嵌套写法不产生偏差，浮点与乘除换序才产生偏差**。核对实现一律用 BigInt，并保持
「先 `applyFactor`、后除价格」的顺序（`TestCode/src/reconciliation/formulas.ts::calculatePositionFee`
即按此顺序的 BigInt 连除）。

## 二、需要重点说明的几条

### 2.1 (#1, High) Vault 余额不足未把本地余额一并支付 — **确认真实可触发，建议必修**

复核 `VaultBase._withdrawAssets`（当前代码与报告引用完全一致，未改）后，进一步查看了 `totalAssets()`（`本地余额 + strategy.totalAssets()`）和 `strategyAllocationPercentage` 机制：只要 vault 的策略分配比例不是 100%，本地余额与策略余额就会**常态化并存**（不是极端情况）。也就是说，只要 LPVault 的策略分配比例配置为部分分配（而不是全部转入 `NoopStrategy`），**大额提款就会常态性地触发本地余额分支**，导致本地那部分余额永久滞留在 Vault 里、用户/上层记账却认为已全额支付。

**建议**：这是审计前应该修的，修复本身很简单（报告给的方案就是对的：先转本地余额、再向 strategy 要差额），且不涉及协议经济模型，风险很低、收益很高。

### 2.7 (#7) 加仓回调 eventData 为空 — 复核确认真实存在且是非对称的

额外验证了 `DecreaseOrderUtils.sol` 里为回调准备的 `EventLogData`（`outputToken`/`secondaryOutputToken`/`outputAmount`/`secondaryOutputAmount`/`orderSizeDeltaUsd`/`orderInitialCollateralDeltaAmount` 六个字段都有真实赋值），而 `IncreaseOrderUtils.processOrder` 对应位置确实只 `return eventData;`（空结构体）。**报告的"减仓侧有数据、加仓侧没有"这个不对称性描述完全准确**，不是我的推测。

### 2.10 (#10) Funding 累计指数与 positionPaysLp 独立计算 — 与 R3-B03 系同一区域不同角度

`docs/bugs/BUGS.md` 已经跟踪了 R3-B03（`positionPaysLp` 因 skew 用 EMA、diffOI 用瞬时值，失衡切换时可为负）。本条关注的是另一件事：**即使不考虑 EMA 滞后，`positionPaysLp` 与四个累计 funding 指数各自舍入的路径不同，长期可能累积 dust/漂移**。两者根因不同，但都指向同一段 `MarketUtils.sol` 的 funding 结算代码，建议合并成一次性的 funding 账务复核（可能一起设计 fuzz/invariant 测试）。

### 2.19 (#19) USD 计价减仓未拒绝超额输入 — **复核后确认不成立，可以关闭**

这是我复核中唯一"推翻"报告结论的一条。报告作者自己也写了"可能在代码使用这个函数时，在其他地方进行了限制…时间关系，这里来不及检查"——我去查了调用方 `DecreasePositionUtils.decreasePosition`：

```solidity
if (params.order.sizeDelta() > 0) {
    (cache.sizeDeltaUsd, cache.sizeDeltaInTokens) = PositionUtils.getDecreaseOrderSize(params);
}

uint256 maxSizeDelta = params.order.isSizeDeltaUsd() ? params.position.sizeInUsd() : params.position.sizeInTokens();

// cap the order size to the position size
if (params.order.sizeDelta() > maxSizeDelta) {
    if (/* LimitDecrease 或 StopLossDecrease */) {
        // ... 发 auto-updated 事件
        params.order.setSizeDelta(maxSizeDelta);
        (cache.sizeDeltaUsd, cache.sizeDeltaInTokens) = PositionUtils.getDecreaseOrderSize(params); // 用封顶后的值重新算，覆盖第一次的结果
    } else {
        revert FxErrors.InvalidDecreaseOrderSize(cache.sizeDeltaUsd, params.position.sizeInUsd()); // 直接 revert
    }
}
```

`getDecreaseOrderSize` 第一次调用即使传入超额 `rawSizeDelta` 算出了"看起来超额"的结果，**紧跟着的这段代码要么用封顶后的值重新计算并覆盖掉第一次的结果（限价/止损单），要么直接 revert（市价单等其他类型）**——超额结果从未被后续费用计算、事件发射或资金转账使用过。**报告里担心的"后续状态更新可能 panic 或以更深层错误形式出现"这个场景不会发生**，因为在到达那些更深层逻辑之前，要么已经被覆盖、要么已经 revert。

结论：**#19 可以标记为"已核实不成立"关闭**，不需要修复。#20（向上取整导致提前耗尽 token）是同一函数但不同边界——`rawSizeDelta` 本身没有超过 `sizeInUsd`（所以不触发上面的封顶逻辑），只是取整后 `sizeInTokens` 提前归零——**这个不受上面的保护逻辑覆盖，仍然是开放问题**，建议按报告的修复建议（取整后达到全部 sizeInTokens 时同步把 sizeDeltaUsd 也调整为全部 sizeInUsd）处理，或至少写一个边界测试确认实际影响。

### 2.21 (#21) affiliate reward claim 固定数组越界 — 与审计范围文档的交叉影响

复核确认这就是 `docs/bugs/BUGS.md` 里的 **R2-B02**（状态：`REPORTED（回归）`）——`ReferralEventUtils.emitAffiliateRewardClaimed` 的 `eventData.uintItems.initItems(2)` 之后写入了索引 2（`nextPoolValue`），触发 `Panic(0x32)`，导致**所有非空 batch claim 都无法成功**。这不是新发现，是内部审计团队独立重新踩到了同一个已知问题，说明这个 bug 确实很显眼、容易触发。

**特别提醒**：昨天（2026-07-29）核对 v0.3.1 审计范围时，`src/referral/` 整个目录因为"本轮不上线、tier 未配置"被列为排除范围（见 `docs/audit/2026-07-30-v031-audit-scope.md` §2）。`ReferralEventUtils.sol` 正是 `src/referral/` 下的文件——**也就是说，按当前排除范围，这个已知的 Panic bug 不会被外部审计覆盖到**。这本身不算大问题（因为 referral 功能本来就没启用），但既然这次内部审计又独立发现了它，建议**趁这次一起修掉**（`initItems(2)` 改 `initItems(3)`，改动极小），不要等到将来 referral 模块重新设计审计时才处理——反正修复成本几乎为零，没必要留着一个已知会 100% Panic 的函数在代码库里。

### 2.22 (#22) decrease order 未执行 minOutputAmount — 确认是真实的死代码

复核确认 `_validateOutputAmount` 的两个重载在全仓库确实**零调用点**（`grep` 结果为空），且 `Order.Numbers.minOutputAmount` 的 NatSpec 明确写着这是"减仓/swap 的最低输出保护"。当前所有测试里这个字段都传 0，所以测试套件也不会暴露这个回归。**这是一个用户以为存在、实际完全不生效的保护参数**，建议审计前修复（在 `transferOut()` 前接入相应的 `_validateOutputAmount` 调用），因为一旦产品文档/前端告诉用户"设置最低可接受输出可以保护你"，而实际没有任何校验，属于比较严重的用户预期落差。

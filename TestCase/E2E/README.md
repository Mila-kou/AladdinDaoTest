## 3. 测试目标

验证用户从进入交易页、选择市场、填写订单、提交交易，到查看持仓、订单和历史记录的完整页面功能链路；同时覆盖钱包、网络、行情、keeper、索引服务异常，以及响应式和基础可访问性。

页面 E2E 重点验证：

1. 页面控件可用、状态切换正确、输入限制明确。
2. 页面预览、列表和历史回显与 Reader/交易回执/索引数据一致。
3. 7 种主订单类型、多空触发、仅减仓、止盈止损和免清算保护的状态机正确。
4. 失败语义可区分：取消已退款、冻结未退款、oracle 异常待重试、keeper 超时。
5. 不把依赖服务故障误判为产品功能失败。

## 5. 优先级与执行顺序

- **P0**：核心交易闭环或资金/状态风险。每次发布前必须执行。
- **P1**：主要功能、异常恢复和关键数据回显。版本回归必须执行。
- **P2**：体验、兼容性、本地化和辅助交互。完整回归执行。

建议顺序：

1. 先执行 P0 的环境、钱包、市场、开仓、平仓和撤单场景。
2. 再执行 P1 的限价、TP/SL、保护期、失败分诊和历史回显。
3. 最后执行 P2 的设置、本地化、移动端和键盘访问。

## 6. 组级前置条件

1. 页面连接 Base Sepolia（chainId `84532`），前端地址接线已与部署产物核对。
2. 测试钱包持有足量 Base Sepolia ETH 和 USDC；禁止使用主网资金。
3. keeper、行情源、RPC 和索引服务健康；依赖异常专项除外。
4. 测试账户、订单和持仓可独立清理，避免与其他执行者并发使用同一账户。
5. 涉及精确数值的场景在同一区块记录页面截图、交易哈希和 Reader/链上读数。
6. 等待 keeper 的默认预算为 60 秒；超时先查服务健康，服务异常记 `BLOCKED`，不直接记 `FAIL`。

## 7. 数据核对口径

- 页面展示值使用 T3 显示舍入；记录 locale、单位、千分位和小数位。
- 合约/Reader 精确值使用 T0；页面与权威读数分成两个核对点。
- 杠杆：`sizeInUsd / (collateral - pendingFunding)`，不含浮盈亏。
- 浮盈亏：价格盈亏；不要与包含费用和冲击的“预计可得”混为同一字段。
- 订单 Token Size 按 18 位精度格式化；触发价按合约价格精度解析。
- 失败三态必须可区分：取消已退款、冻结未退款、oracle 异常订单保留待重试。

## 8. 证据要求

- PASS：至少保留关键页面截图；有链上写操作时必须记录交易哈希。
- FAIL：页面截图、交易哈希、读数区块号三件套齐全，并记录控制台/网络错误摘要。
- BLOCKED：记录依赖服务、开始/结束时间、等待时长和解除条件。
- MANUAL（手工核对）：证据要求不降级。除 PASS/FAIL 的常规证据外，必须在对应合约版本的 `results.md` 补记执行人、执行日期、所用钱包账户地址，以及能复核的截图或录屏。

## 9. 范围边界

本轮是页面功能级用例设计，不替代合约层精确账本测试、性能压测、安全审计和浏览器钱包自身兼容性认证。精确资金守恒、费用和 PnL 公式仍应由链上账本用例覆盖，页面用例负责双源回显与用户可理解的状态反馈。

# FX100 费用收取与分配体系改造规范（实施版）
**日期**: 2026-06-13
**状态**: 定稿，src 已实现（`release/v0.3.0`，2026-07-16 核对收官，见 §十）；部署配置（分账器/金库上线切换、keeper claim 任务）仍待运维执行，非合约缺口
**受众**: 合约工程师（在 release 分支实施 + 部署配置）
**涉及模块**: `src/market/MarketUtils.sol`, `src/referral/ReferralStorage.sol`, `src/pricing/PositionPricingUtils.sol`, `src/constants/FX100Keys.sol`；部署层复用 fx-protocol-contracts 既有合约 `RevenuePool.sol`、`ProtocolTreasury.sol`
**设计依据**: `docs/superpowers/specs/2026-05-28-fee-distribution-design.md`（含完整设计讨论与决策过程，本文为其实施提炼版）

## 一、核心原则（三句话）
1. **交易盈亏 Trader-LP 直接对赌**：交易者的盈利与亏损直接与 LP Vault 结算，平台协议**不分成、不担险**。这是 FX100 既有代码的现状行为，**无需改动**。
2. **协议费用三方分账**：开/平仓手续费、清算费的协议分成部分（`feeReceiverAmount`）+ 资金费净额，按可配置比例分给 **协议收益库 / 保险基金 / LP Vault**。
3. **复用 fx 既有合约实现分账**：分账器用 fx 既有 `RevenuePool.sol`，两个金库用 fx 既有 `ProtocolTreasury.sol`。**唯一的 src 合约改动是资金费路由（§四）**，其余皆为部署+配置。

## 二、最终架构（端到端资金流）
```plain text
开/平仓手续费 feeReceiverAmount ┐
清算费 feeReceiverAmount         ├─► claimableFeeAmount ─► FeeHandler.claimFees ─► availableFeeAmount
资金费净额 positionPaysLp(≥0)   ┘                                                       │
                                                                                       │ FeeHandler.withdrawFees
                                                                                       │ (现有逻辑, 100%, 不改)
                                                                                       ▼
                                                              FEE_RECEIVER = fx RevenuePool 分账器
                                                                                       │ keeper 调 claim()
                            ┌──────────────────────────┬───────────────────────────────┼───────────────────────────┐
                            ▼                           ▼                               ▼                           ▼
                      staker (keeper)            treasury 槽                     burners[USDC] 槽            ecosystem 槽
                      stakerRatio = 0            treasuryRatio (~40%)            lockerRatio (~20%)          余数 (~40%)
                      仅触发, 不收款                    │                               │                           │
                                                       ▼                               ▼                           ▼
                                                  协议收益库                        保险基金                     LP Vault
                                              ProtocolTreasury                  ProtocolTreasury           (即时抬升 NAV)
                                              (白名单手动支出)                  (白名单手动支出)
                                                       │
                                                       └─► P2: 跨链回主网 ─► veFXN 收益分配 (手动)

交易者盈亏 ─────────────────────────► LP Vault  (Trader-LP 直接对赌, 不经任何金库)
```

## 三、费用分账：复用 fx `RevenuePool.sol`（零核心合约改动）
### 3.1 机制
`FeeHandler.withdrawFees` 现有逻辑是把 `availableFeeAmount` **100% \`safeTransfer\` 给 \`FEE_RECEIVER\`**。只需将 FX100 DataStore 的 `FEE_RECEIVER` 配成 fx 既有分账器 `RevenuePool.sol` 的地址，费用即全额进入分账器；由 keeper 定期调用 `claim()` 完成三方拆分。
`RevenuePool.sol`（`fx-protocol-contracts/contracts/helpers/RevenuePool.sol`，AladdinDAO `PlatformFeeSpliter`）的 `claim()`：读取自身 token 余额，按 1e9（`FEE_PRECISION`）精度的三个 ratio 拆给 4 个去向，最后一个去向（`ecosystem`）拿余数。普通 `safeTransfer` 进来的余额即可被 `claim()` 读取（`balanceOf`），**无需调用 \`depositReward\`**。
### 3.2 4 槽位映射（FX100 用法）
分账器槽位 │ 映射对象 │ ratio │ 说明
`staker` │ 运营 keeper │ **0** │ `claim()` 的唯一允许调用者（`require(msg.sender == staker)`）；ratio=0 故不收款，纯触发
`treasury` │ **协议收益库**（ProtocolTreasury 实例） │ `treasuryRatio`，如 0.40 │ 协议收入累积池
`burners[USDC]` │ **保险基金**（ProtocolTreasury 实例） │ `lockerRatio`，如 0.20 │ locker 份额转给 burner 地址
`ecosystem` │ **LP Vault** │ 余数（如 0.40） │ 取剩余，即时抬升 LP NAV
**关键点（必读）**：`RevenuePool.claim()` 限定 `msg.sender == staker` 且 staker 同时是收款人。把 `staker` 设为运营 keeper、`stakerRatio = 0`，即可既满足"keeper 触发"又让三个真实去向各自到账——**LP Vault 与 FeeHandler 都无需改一行代码**。
### 3.3 比例配置
```plain text
addRewardToken(
    USDC,                  // _token
    保险基金地址,           // _burner（locker 份额接收方）
    0,                     // _stakerRatio（keeper 不收款）
    treasuryRatio,         // 如 0.40e9 → 协议收益库
    lockerRatio            // 如 0.20e9 → 保险基金
)
// LP Vault 拿 ecosystem 余数 ≈ 0.40
```
约束：`stakerRatio + treasuryRatio + lockerRatio ≤ 1e9`（合约 `_checkRatioRange` 强校验，超过即 revert）。比例后续经 `updateRewardTokenRatio` 由 owner 调整。**不引入任何 FX100 DataStore Key**。

## 四、唯一的 src 合约改动：资金费净额路由
**现状**（`src/market/MarketUtils.sol:529-535`）：
```solidity
if (result.positionPaysLp > 0) {
    positionVault.transferOut(market.collateralToken, market.vault, uint256(result.positionPaysLp)); // → LP Vault
} else {
    IVault(market.vault).transferOut(market.collateralToken, address(positionVault), uint256(-result.positionPaysLp));
}
```
**改为**：资金费净额不再直接转给 LP Vault，而是计入 `claimableFeeAmount`（与开/平仓手续费同一归集通道），随 `claimFees`/`withdrawFees` 流入分账器：
```solidity
if (result.positionPaysLp > 0) {
    // 资金已在 positionVault 内，仅做账面归集，无需 transfer
    FeeUtils.incrementClaimableFeeAmount(
        dataStore, eventEmitter, market.marketIndex,
        market.collateralToken, uint256(result.positionPaysLp)
    );
}
```
**为什么 \`else\` 分支可保留不动**：资金费净额公式恒非负——
```plain text
positionPaysLp = longOI × longFactor × dt + shortOI × shortFactor × dt
               = floorFee × longOI × dt + baseFactor × skew × (longOI − shortOI) × dt
```
两项均 ≥ 0：floor 项恒正；skew 项是 `skew` 与 `(longOI − shortOI)` 同号相乘（见 `MarketUtils.sol:600-660`）。故 `positionPaysLp ≥ 0`，`else`（LP→持仓支付）分支不可达，保留为防御代码即可。

## 五、协议收益库 与 保险基金：fx 既有 `ProtocolTreasury` 实例
两者各部署一个 fx 既有 `ProtocolTreasury`（`fx-protocol-contracts/contracts/helpers/ProtocolTreasury.sol`）实例。FX100 只用其白名单转账与权限调用能力（PegKeeper/buyback 路径用不到，可不授予对应角色）：
```solidity
bytes32 public constant MULTICALL_ROLE      = keccak256("MULTICALL_ROLE");
bytes32 public constant BATCH_TRANSFER_ROLE = keccak256("BATCH_TRANSFER_ROLE");
bytes32 public constant TOKEN_RECEIVER_ROLE = keccak256("TOKEN_RECEIVER_ROLE");

/// 仅 BATCH_TRANSFER_ROLE 可发起；每个收款人必须持有 TOKEN_RECEIVER_ROLE（白名单）
function batchTransfer(address token, address[] calldata receivers, uint256[] calldata amounts) external;

/// 权限化任意调用（如 approve bridge、参与治理）
function multicall(address[] calldata targets, bytes[] calldata data) external;
```
金库 │ 资金来源 │ 用途 │ 支出方式
**协议收益库（ProtocolRevenueTreasury）** │ 分账器 `treasury` 槽 │ 协议收入：运营、回购、跨链 veFXN 分配（P2） │ 治理手动 `batchTransfer`/`multicall`，仅白名单
**保险基金（Insurance Fund）** │ 分账器 `locker`/`burner` 槽 │ 极端事件兜底：穿仓坏账、oracle 事故赔付、LP 严重亏损补偿 │ 纯手动 `batchTransfer` 给白名单（如 LP Vault），无链上自动支付路径
**白名单（TOKEN_RECEIVER_ROLE）初始配置建议**：
- 协议收益库：运营多签、官方 bridge（P2 时加入）、LP Vault
- 保险基金：LP Vault、运营多签

## 六、配套手续费改造（与分账独立，可并行）
这两项属于费用体系的既有缺口，与上述分账架构正交，一并在本规范内交付：
### 6.1 手续费费率 key（先保留原模式）
**现状**：`positionFeeFactorKey(marketIndex, balanceWasImproved)`（`FX100Keys.sol:1380`，`PositionPricingUtils.sol:461`）——费率随是否改善 skew 平衡（`balanceWasImproved`）分两档。
**决定（本期）**：**先保留原 \`balanceWasImproved\` 两档模式，不改 key 结构、不动 src**。上线时把两个参数（`balanceWasImproved=true` / `=false`）配置成**相同值**，使费率在用户视角等价于单一可预测费率，且不破坏现有合约与测试。
**未来可选改造（暂不实施）**：因 skew 激励已在执行价格的动态点差（Skew Impact Spread）中体现，费率层面再做两档属双重激励，后续可把 key 改为 `positionFeeFactorKey(marketIndex, isOpen)`（开/关仓两档）并删除 `balanceWasImproved` 分支。涉及 `FX100Keys.sol`、`PositionPricingUtils.sol`、部署参数脚本——本期不动。
**涉及（本期）**：仅部署参数脚本（两档配同值），无 src 改动。
### 6.2 Referral 权限模式
**现状**：任意地址可注册推荐码，无白名单。
**改造**（`ReferralStorage.sol`）：
```solidity
bool public permissionedMode;
mapping(address => bool) public affiliateWhitelist;

function setPermissionedMode(bool _permissioned) external onlyGov { permissionedMode = _permissioned; }
function setAffiliateWhitelist(address affiliate, bool approved) external onlyGov { affiliateWhitelist[affiliate] = approved; }

function registerCode(bytes32 _code) external {
    if (permissionedMode) require(affiliateWhitelist[msg.sender], "ReferralStorage: not whitelisted");
    require(_code != bytes32(0), "ReferralStorage: invalid _code");
    require(codeOwners[_code] == address(0), "ReferralStorage: code already exists");
    codeOwners[_code] = msg.sender;
    emit RegisterCode(msg.sender, _code);
}
```

`FX100Keys.sol` 的 `BORROWING_FEE_RECEIVER_FACTOR` 继承自 GMX，FX100 无借贷费，从未使用，择机删除。

## 十、实现落地情况（v0.3.0，2026-07-16 核对收官）
对应 17 个变更点中的 B-6/B-7/B-8（+ D-15/D-17 增量），src 侧全部落地，测试背书详见 `2026-07-08-v030-implementation-verification.md`（二）与 `2026-07-13-v030-code-walkthrough.md`（B-6\~B-8、D-15、D-17）。与本文口径的主要出入：
1. **§三"withdrawFees 100% safeTransfer 不改"与实现相反**：`FeeHandler.withdrawFees` 改成了**推送制**——`staticcall` 探测 `FEE_RECEIVER` 是否实现 `IRewardSplitter.depositReward`，是分账器则 `forceApprove` + `depositReward(token, feeType, amount)`（对方按 `(token, key)` 内部记账，只认 `depositReward` 推入的余额，不认 `balanceOf`，防止裸转账污染分配基数）；不是分账器（EOA/普通合约）则优雅降级为原 `safeTransfer`。**升级顺序因此有硬约束**：必须先部署 RevenuePool 并完成三槽 `addRewardToken` 注册，再把 `FEE_RECEIVER` 切过去，否则新逻辑会一直走降级分支、达不到三方分账效果（但不会 revert/卡死）。
2. **破坏性接口变更（超出本文原述）**：`claimFees`/`withdrawFees`/`getAvailableFeeAmount` 三个 external 函数全部新增 `bytes32 feeType` 参数，`claimableFeeAmountKey`/`availableFeeAmountKey` 加 feeType 维度。费用类型从本文隐含的"开平仓费+清算费+资金费混一个通道"拆成三个独立槽位常量：`POSITION_FEE_TYPE` / `FUNDING_FEE_TYPE` / `LIQUIDATION_FEE_TYPE`（清算费独立拆槽是我方 2026-07-13 提案落地，D-15，超出本文范围的增强——可单独把清算费配置成 100% 进保险基金）。keeper claim 脚本需按 3×feeType×token 矩阵调用，漏跑某槽位资金会滞留在 claimable/available（无资金安全问题，但需监控）。
3. **RevenuePool 扩展为"同 token 多槽"模型（超出 §三原述的单槽理解）**：为承接三个 feeType 各自独立比例，`addRewardToken` 支持同一 token 注册多个 `(token, key)` 槽位（同 token+同 key 拒绝重复注册）；`claim()` 遍历全部已注册槽位分别按各自 `stakerRatio`/`treasuryRatio`/`lockerRatio` 拆分。
4. **部署已就绪但未切换**：ignition 部署模块已含 RevenuePool + ProtocolTreasury ×2（`ce59b58` 闭合 P0-2/P0-3 的"合约就绪零部署"缺口），但 `FEE_RECEIVER` 尚未在测试网/生产配置切到分账器地址（P0-4）、keeper 定期 `claim()` 的链外任务尚未上线（P0-5）——这两项是运维/部署清单待办，非合约缺口，参见 `2026-07-13-v030-code-walkthrough.md` 走查总结的"部署 checklist"。
5. **§6.2 Referral 权限模式（P1-2）未实现**：`permissionedMode`/`affiliateWhitelist` 尚未落地，整个 referral 模块延期，待统一处理。
6. **§七参数建议已在测试 fixture 落地为默认值**：`POSITION_FEE_FACTOR` 5bps、`POSITION_FEE_RECEIVER_FACTOR`/`LIQUIDATION_FEE_RECEIVER_FACTOR` 0.5、`LIQUIDATION_FEE_FACTOR` 0.3%，与本文建议值一致。
7. `RevenuePool.claim()` 不发事件，链上核对目前只能靠 Transfer 日志反推；`ProtocolTreasury` 继承的 admin `withdraw(baseToken, recipient)` 是白名单外的管理员出金通道（治理知情项，非漏洞）。

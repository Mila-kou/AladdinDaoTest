# 测试结果输出与看板

## 1. 使用者与目标

| 使用者 | 首要问题 |
|---|---|
| 测试执行人 | 哪些场景失败、失败证据在哪里、是否可以复现？ |
| 开发/合约工程师 | 问题发生在页面、交易、Keeper、Oracle、Indexer 还是协议状态？ |
| 发布负责人 | 规划场景覆盖多少，P0 是否通过，是否存在 Flaky 或 Blocked？ |

测试结果看板属于每次运行的离线快照，不是在线实时监控。服务模式下的“合约参数”页可按已配置的 Project 环境主动发起只读查询；RPC 只由本地服务使用，不会发送到浏览器，也不会读取钱包私钥。

## 2. 权威数据源

```text
TestCase/E2E/SCENARIO-CHECKLIST.md
  └─ 规划场景目录：ID、套件、标题、优先级

Playwright 自定义 Reporter
  └─ 实际结果：Project、环境、状态、核对结果、执行链接、执行时间、尝试、耗时、错误、附件

两者按 SCN-xxx 关联
  └─ results.json → summary.md + dashboard.html

TestCase/E2E/scenarios/*.md + config/test-case-overrides.json
  └─ 测试用例库：原始基线 + 经过校验的页面编辑覆盖层

Test/config/*.params.json + *.params-by-module.csv
  └─ fork 固定区块 / Base Sepolia 查询时最新区块的 DataStore 全量参数、角色成员、不可枚举定义

TestCase/E2E/ContractCodeSummary + Docs/.../需求文档归档/汇总
  └─ 合约核心公式、页面数据公式
```

数据粒度是“一个 SCN 在一个 Playwright Project 中的最终结果”。同一场景跨多个 Project 执行会产生多行；自动化覆盖率按唯一 SCN 去重。

## 3. 结果状态

| 状态 | 口径 |
|---|---|
| PASS | 第一次执行即符合预期 |
| FAIL | 最终仍失败、超时或发生非预期结果 |
| FLAKY | 至少一次失败/超时，重试后通过 |
| BLOCKED | 使用 `blocked` annotation 明确标记外部条件阻塞 |
| SKIP | Playwright skip/fixme 或未选择执行 |
| MANUAL | 手工核对用例：设计上依赖真人操作（浏览器钱包切账户、换设备、拒签），不产出自动化代码；仍必须人工执行并回填证据，显示为 MANUAL 不等于通过 |
| NOT AUTOMATED | 场景目录存在，但本次没有发现对应自动化测试（欠账，不同于 MANUAL） |

一个运行批次可以同时包含自动化和手工用例：看板只对有 spec 的用例启动 Playwright，手工用例保持 `MANUAL`，由 `/runs` 页面的“手工核对清单”按用例回填人工结论。清单里“打开前端并开始”使用测试环境已配置的 Trade 站点地址 `E2E_APP_BASE_URL`（打开其 `/trade`，与环境检查同一口径，不另存一份链接），同时记录该用例的人工开始时间 `manualStartedAt`，与回填时间一起给出人工耗时。回填必须同时给出执行人和实际结果 / 证据，写入 `artifacts/run-batches/<runId>/run.json` 的 `manualVerdict`；批次状态由逐用例状态按 `RUNNING → QUEUED → INTERRUPTED → FAIL → MANUAL_PENDING → NO_AUTOMATION → PASS → PARTIAL` 的优先级推导，自动化部分全绿不会把整批记成 `PASS`，被服务重启打断过的批次也不会因为人工回填变回执行中。自动化用例的结果只能来自 Playwright 产物，接口拒绝人工改写，也拒绝覆盖已带产物结果的用例。

`test.fail()` 等已知失败不会被当成 PASS；如确实是外部阻塞，必须添加 `blocked` annotation 和原因。

“执行状态”和“自动化覆盖完整度”使用不同口径：已经执行且断言全部通过的测试记为 `PASS`；同一业务场景仍有子路径尚未自动化时使用 `coverage-gap` / `PARTIAL` 说明，不能记成 `BLOCKED`。`BLOCKED` 只表示本次测试因环境或外部依赖无法执行或无法完成核对。

## 4. 核心指标

| 指标 | 计算 |
|---|---|
| 规划场景 | 场景目录唯一 SCN 数 |
| 手工核对 | 标记为 MANUAL 的唯一 SCN 数（用例元数据，来自 `config/test-case-overrides.json` 或 `src/reporting/test-environments.ts` 的 `MANUAL_ONLY_IDS` 基线） |
| 自动化覆盖 | 本次发现唯一 SCN /（规划唯一 SCN − 手工核对 SCN）；手工用例既不进分母也不进分子 |
| 最终成功率 | `(PASS + FLAKY) / (PASS + FLAKY + FAIL)` |
| 稳定通过率 | `PASS / (PASS + FLAKY + FAIL)` |
| Blocked/Skip | 单独展示，不进入成功率分母 |
| 累计耗时 | 筛选范围内全部尝试耗时之和，不等于并行墙钟时间 |

同时展示最终成功率和稳定通过率，避免重试后通过掩盖不稳定性。

## 5. 看板布局

默认视图从结论到明细：

1. Run、环境、时间、数据状态；
2. 规划、覆盖、最终成功率、稳定通过率、失败、Flaky、Blocked；
3. 状态分布；
4. S01～S08 套件覆盖与质量；
5. 失败/Flaky/Blocked 优先处理表；
6. 全场景明细；
7. 数据来源和指标定义。

全局筛选：套件、优先级、状态、Project、环境和关键字。

套件筛选与汇总使用完整名称，例如 `S08 · Funding 计提、结算与边界`，保存值仍为稳定的 `S08`。

每条已执行结果额外展示：

- `核对结果`：页面、Reader、事件和本地预期值的对账结论；
- `执行链接`：链接到该场景的执行详情，并可继续查看交易或回执证据；
- `执行时间`：最终一次 Playwright 尝试的开始时间；
- `耗时`：包括重试在内的全部尝试累计耗时，与执行时间不是同一口径。

有结构化执行证据的用例，其 `SCN-xxx` 编号和“核对与交易详情”都会链接到执行详情页。详情页以真实交易为一级步骤：`TX1 / TX2 / TX3 / TX4` 分别对应交易员创建订单、Keeper 执行、交易员创建下一动作、Keeper 执行下一动作；交易数量不是四笔时按实际数量动态生成。每个 TX 使用自己确认区块的 Before/After 快照，单独展示动作摘要、可折叠交易记录以及该动作完成后的 `before / after / Expected Δ / Expected After`。顶部可以切换单笔 TX 或“全流程”；失败交易优先展开，否则默认 TX1。历史证据没有保存某笔交易的中间快照时明确提示缺少独立快照，不把相邻交易合并结果伪装成单笔核对。

核对范围至少包括资金账户与 Vault、仓位原始字段、Position Fee 与协议/LP 分账、Funding factor 与单仓结算、Long/Short OI、Raw Skew、Spread Skew Reference、Dynamic Spread、执行价、PnL 和资金守恒。每个 TX 内仍可使用“全部、资金/Vault、仓位、Fee、Funding、OI/Skew/Spread、PnL、状态/成交”等快速筛选，也可点击具体明细分组；当前显示数量和各状态数量随筛选同步更新。执行详情同时展示测试用例的角色与意图、核心期望、测试数据，并可通过带 `scenario` 参数的链接直达测试用例页面查看或编辑。交易证据至少保留完整哈希、from/to、区块、nonce、交易类型、gas、状态、订单键和签名核验结果；没有可靠的外部浏览器地址时使用本地只读证据接口，不拼接虚假的 Tenderly 链接。

功能用例的“交易概要”跟随当前交易动作显示：Trader 创建动作展示 Margin、Leverage、方向与 USDC 到 OrderVault 的资金流；Keeper 执行动作展示 Position Size、Execution Price，平仓执行还会展示 Base PnL 与 Trader USDC 净变动。成交价同时保留人类可读 USD 值和链上 raw 值；内部价格按 `10^(30 − Index Token decimals)` 换算，不能把 Oracle feed decimals 直接当成协议内部价格精度。当前 TX 的角色、动作标题、交易概要与链上回执合并在一个动作主模块内，测试数据和链上证据使用不同的内嵌子模块样式。版本、环境和全部地址集中到独立的“版本、环境与合约地址”页面；执行详情把本次绑定摘要和跳转入口放在“功能用例说明”的标题区，不再额外占用一个同级面板。顶部摘要不再显示重复的“查看完整功能用例”入口。

功能用例的交易证据也使用“按交易动作核对”：点击某个 TX 后，同时切换该笔交易的 Hash、回执、From/To、区块和关联的 Actual / Expected 核对项；“全流程”恢复全部交易与全部核对。新证据直接保存 `actionKeys`，历史证据则按既有断言名称补齐阶段关系，因此旧批次不需要重跑即可使用该联动。

功能用例核对表的“公式 / 依据”列按语义分块显示：公式中的通用规则与“本次”代入值分别标为“计算规则”和“本次代入”，`note` 作为“核对依据”单独显示。Reporter 只调整展示结构，不改写核对引擎输出的公式、数值或结论。当前证据没有 `formula` 时明确显示“本条证据未保存单项公式”，并链接到当前版本核心公式；功能用例与公式章节的维护映射见 [`FX100-功能用例公式与核对依据索引.md`](../../TestCase/E2E/ContractCodeSummary/v0.3.2/FX100-功能用例公式与核对依据索引.md)。

执行详情中的字段状态使用四种明确口径：

| 状态 | 含义 |
|---|---|
| `PASS` / `FAIL` | 链上 Actual 已与独立来源的 Expected 精确比较；Expected 来自执行区块参数、事件或另一链上数据源 |
| `CALCULATED` | 根据 Before/After 或链上输入得到的派生展示值，例如 Δ、OI USD、Raw Skew；不把自身推导再算成 PASS |
| `NOT_VERIFIED` | 已采集 Actual，但独立复算输入或实现尚不完整，例如当前 Dynamic Spread 的 LogExpMath、缺少 Pool PnL Cap 输入 |

交易场景统一调用 `src/reporting/execution-evidence.ts` 的公共阶段核对入口；用例只声明 `ledger`、`position`、`grace`、`pricing`、`fee-funding` 模块。共享公式位于 `src/reconciliation/formulas.ts`，执行区块的 33 项 Market 参数、全局费率、Funding EMA 与 Grace referral tier 由 `src/reconciliation/chain-parameter-snapshot.ts` 一次性读取。Grace、Fee、Funding Factor 和执行价都必须把本次实际参数代入公式后再比较；历史证据没有保存所需参数时显示 `NOT_VERIFIED`，禁止回退到本地默认值伪造 PASS。

资金、Vault、OI 和累计成本统一采用以下判定顺序：

```text
Expected Δ = f(用户订单输入, 执行区块参数, 已独立复算的 Fee/Funding/PnL)
Expected After = Before + Expected Δ
PASS ⇔ 链上 Actual After = Expected After
```

`Expected Δ` 禁止使用链上 `After − Before` 反推。页面仍会在说明中显示链上 Actual Δ，方便定位差异，但它不参与 Expected 的生成。例如开仓 Margin 使用 `inputMargin − totalCost + positiveFunding`；交易员/OrderVault/PositionVault/LPVault 分别按订单阶段和 Fee/Funding/PnL 资金路由计算；OI 使用订单 `sizeUsd` 与执行价计算。当前 SCN-009/010 的数据是 `10 USDC × 5x = 50 USD`；如果用例改为 `50x`，Expected size 自动变为 `500 USD`，核对代码不硬编码杠杆。

测试代码通过 Playwright annotation 写入业务核对信息：

```ts
testInfo.annotations.push({
  type: 'check-result',
  description: '页面、Reader、PositionIncrease 事件与 BigInt 预期值一致',
});
testInfo.annotations.push({
  type: 'tx-link',
  description: 'Tenderly 交易 | https://dashboard.tenderly.co/...',
});
```

`execution-link` 与 `tx-link` 都可使用；description 支持 `标签 | https://...` 或直接填写 URL。只接受 `http/https` 链接。未填写核对结果时 Reporter 会按最终状态生成兜底文案，但正式交易用例应写出实际核对内容。

```text
artifacts/runs/<run-id>/
├── results.json       # 权威机器可读数据
├── summary.md         # PR/CI/人工复盘摘要
├── dashboard.html     # 自包含离线看板

├── formulas.html      # 合约核心公式资料页
└── page-formulas.html # 需求总结中的页面数据公式

artifacts/latest/
└── 同一份最新结果
```

Playwright 原生 HTML 报告仍保留在 `artifacts/html-report`，用于查看步骤级 Trace；FX100 看板负责跨场景汇总和发布决策，二者不互相替代。

## 7. 数据质量闸门

Reporter 发现以下问题时让整次运行失败：

- 测试标题没有 `SCN-xxx`；
- 本次没有发现任何测试，此时不生成也不覆盖 latest 看板；
- 使用不存在的 SCN 编号；
- 同一 Project 重复声明同一个 SCN；
- 测试被发现但没有 TestResult；
- 结果 JSON 不符合 schema；
- 看板生成失败。

看板顶部会显示数据质量问题，不能静默忽略。

服务仅允许这些固定路由，不提供通用静态目录浏览，因此不能从浏览器读取 `.env.local`、deployment manifest、ABI 或其他项目源码。参数下拉框固定来自 `config/environments/catalog.ts`；未配置 RPC 的环境会显示但禁用。点击查询后，Base Sepolia 每次都重新解析 RPC 的 `latest`，并在该查询时最新块完成一致性读取；fork 环境继续使用各自固定区块。不把旧快照或样例表当作当前值。RPC URL 和 Tenderly 技术 Fork ID 不进入接口响应或快照展示名。

### Base Sepolia Faucet 后台告警与自动补款

`/faucet` 页面（原在主看板，2026-08-12 拆出独立页面）可以为固定 Faucet 设置“告警阈值”和“补款目标余额”。启动后由 Node 看板服务在后台运行，不依赖浏览器页面保持打开：

- 每 30 秒读取一次固定 USDC 的 `balanceOf`，并同时核对 Base Sepolia Chain ID 84532。
- 当余额低于阈值时，先发送 Telegram 低余额告警，再把余额补到目标余额；补款金额严格等于 `目标余额 − 当前余额`。
- 自动补款复用 Base Sepolia `Fund USDC` 的真实 `MockToken.mint` 路径，发送前校验签名地址必须等于链上 `owner()`，交易后回读余额。
- 单次补款后冷却 5 分钟，防止 RPC 延迟或异常状态造成连续交易。
- 服务配置保存于 `config/faucet-auto-funding.json`，审计事件写入 `artifacts/faucet-auto-funding/events.jsonl`；私钥、Bot Token 不写入这两个文件或测试报告。
- 启动前必须在“测试环境 → base-sepolia”配置 Token Owner 私钥、Telegram Bot Token 和 Chat ID。默认状态为停止，不会自动发送交易。

后台服务只在 `npm run dashboard:serve` 进程存活时运行；关闭该 Node 进程即停止检查。若配置文件中的状态为启用，下次启动看板服务时会恢复定时检查。

参数页的“全量”口径是：可枚举 DataStore 键值（按市场、代币、模块、订单类型等维度展开并折叠探测冗余）+ 角色成员 + 41 个不可枚举定义。需要账户、positionKey、timeKey 等业务上下文的动态 Key 会明确标为“不可枚举”，不会用虚构入参伪造当前值。合约自身独立状态变量仍不属于 DataStore 参数口径。

`当前链上原始值` 不因状态为“未设置”而留空：RPC 返回的 `0`、`false`、零地址或零 bytes32 会原样保留；状态列负责说明它是显式非默认配置还是当前类型的默认值。

参数页把 Market 作为一级筛选项，不再单独展示 `Market → INDEX_TOKEN` 映射板块。筛选项直接显示交易对，例如 `market#1 · BTC/USDC`、`market#2 · ETH/USDC`；选择某个 Market 后，列表先展示该 Market 的直接参数及其 INDEX/COLLATERAL Token 相关参数，再展示全局参数。也可以选择“仅全局参数”。其中 ETH 市场的实际 index token 为 WETH，BTC 为项目配置的合成 index 标识地址。

测试用例编辑只在 Node 服务模式开放：PUT 必须来自同源页面，只允许更新已存在的 `SCN-xxx`，并写入固定的 `config/test-case-overrides.json`。原始场景 Markdown 保持不变，便于评审、回退和比较；离线 HTML 自动禁用保存按钮。

服务启动后可以直接验证 HTTP 页面：

```bash
npm run dashboard:verify -- http://localhost:4173/
```

## 10. 测试环境页：启动本地前端与 Keeper（实施说明）

> 2026-09-07 立项。目标是把「起一套指向某环境的本地前端 + Keeper」从手工命令变成环境页上的按钮。
> 本节记录实施要点与已踩过的坑；Keeper 的执行模式本身见 `05-Market-Bundle与Keeper执行模式.md`。

### 10.1 Keeper：扩展现有 KeeperServiceManager

`src/server/keeper-service.ts` 已有 `check | start | status | stop`，spawn `tools/keeper-runner/run.sh`，当前传 `KEEPER_RUN_RPC_URL` + `KEEPER_EXPECTED_CHAIN_ID`。需要补四点：

**① 改用 `--chain-id` 车道参数。** `KEEPER_EXPECTED_CHAIN_ID` 只喂给体检，不决定日志/pid 目录，也不决定 Redis 前缀。多环境并存必须传车道参数，日志才落到 `logs/<chainId>/`，`stop` 也只作用于本车道：

```bash
./run.sh --chain-id 84532 both      # 而非 ./run.sh both
```

**② Fork 环境必须关闭全量扫描**（两个开关成对，单独关前者会直接报错退出）：

```bash
KEEPER_LEGACY_MARKET_STATE_SCAN_ENABLED=false
KEEPER_POSITION_EVENT_CACHE_ENABLED=true
```

不关的话 producer 会扫 Fork 继承的全部仓位（Base Sepolia 快照约 8.4 万个），被 Tenderly 限流到起不来；关掉后每 tick 约 3 秒、只跟踪相关仓位。

**③ 切换环境时必须清事件游标。** 键名 `v0.3.2:<chainId>:keeper:events:lastBlock:position:<emitter 小写>`，值是**裸数字**（不是 JSON，与同前缀下的 JSON 游标不同）。残留值来自上一个 Fork 时，producer 会死等一个当前链永远到不了的块号，订单上链后无人执行。建议启动前自动清理该 chainId 下 `keeper:*`，并先落盘备份到工作区（不要放 `/tmp`）。

**④ 停止要杀到真正的子进程。** `logs/<lane>/*.pid` 记的是 yarn 包装进程，kill 它不会终止 node 子进程，会出现两个 producer 并存、互相抢心跳键（日志报 `heartbeat name collision`）。需要杀进程组或按 `keeper:producer` 等模式兜底。

### 10.2 前端：需要注入的环境变量

| 变量 | 值 | 为什么必须 |
|---|---|---|
| `NEXT_PUBLIC_BASE_SEPOLIA_RPC_URL` | 该环境 RPC | 页面读链 |
| `BASE_SEPOLIA_RPC_URL` | 同上 | 服务端 API 读链 |
| `RELAY_KEEPER_RPC_URL` | 同上 | relay 路由 |
| `NEXT_PUBLIC_MARKETS_DATA_SOURCE=api` | **必填** | 不设会走 split 数据源，配置地址小写后索引 `tokensData`（键为 `/api/tokens` 的 checksum 地址）→ `eligibleMarkets: 0`、Market Unavailable、可用余额恒 0 |
| `NEXT_PUBLIC_GATE_ENABLED=false` | 必填 | 本地 `/api/access-gate/verify` 在模块加载即因缺 `DATABASE_URL` 抛错，必 500 |
| `NEXT_PUBLIC_PRICE_FEED_API_URL` / `NEXT_PUBLIC_API_URL` | 线上 API 或本地价格代理 | 本地 `/api/prices/*` 同样因缺 `DATABASE_URL` 500 |
| `CHAINLINK_BASE_URL` / `_API_KEY` / `_API_SECRET` / `_NETWORK` | 从 keeper `.env` 只抽这 4 行 | 报价源；不读取该文件其余内容 |
| 端口 | **不要用 3010** | 3010 是常驻 `fx100-frontend-local`；用 `next dev -p <port>` 显式指定（被测仓库的 `dev` 脚本把端口写死为 3010） |

**Flash / One-Click 是可选项，且当前缺一块。** `NEXT_PUBLIC_FLASH_ENABLED=true` 打开后，前端 `/api/relay/*` 使用 **Upstash Redis（HTTP 协议）**，与 keeper 用的本地 TCP Redis 不是一回事。只开开关会报 `Redis client was initialized without url or token` → `enqueue failed: Failed to parse URL from /pipeline`，订单在**签名之后、上链之前**失败，两条链上都查不到。要支持 Flash 需额外提供 `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN`，或起 Upstash 兼容层。

Flash 另有三道门，环境变量只是第一道：② 该链 `RelayRouter` 地址非零（84532 已配置）；③ 用户在设置里自行打开。

### 10.3 启动前的前置检查

1. **chainId 必须在前端支持列表内** —— 前端只定义 `BASE_SEPOLIA=84532` 与 `BASE_SEPOLIA_FORK=99917`，且后者 `MARKET_PAIRS` 为空。其它链号（如 tx-fork 的 99911）前端完全不认，钱包连上会是不支持的网络。**给前端用的 Fork 必须建成 84532。**
2. **端口占用** —— `lsof -nP -iTCP:<port> -sTCP:LISTEN`
3. **RPC 可达** —— Fork 被删后仍留在登记里的情况发生过
4. **Redis 游标归属** —— 见 10.1③
5. **合约就位** —— Fork 上验 DataStore / Reader 有 code

### 10.4 页面应当展示的信息

实测中最耗时的不是配置，而是**分不清交易发到了哪条链**：Fork 与真实 Base Sepolia 的 chainId 同为 84532，钱包不会给出任何提示，只能靠 RPC 地址区分。环境页建议直接给出：

- 该环境 **RPC 地址全文**（可复制，供钱包填写）
- **Fork 当前块高 vs 真链当前块高**（一眼看出是否同一条链）
- 一条识别提示：例如给测试地址在 Fork 上充值到易识别的余额（100 ETH），与真链形成对比

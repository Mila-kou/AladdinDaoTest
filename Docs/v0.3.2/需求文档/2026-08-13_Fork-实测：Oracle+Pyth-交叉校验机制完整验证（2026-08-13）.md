## 一、结论先行——两个比"没配置"更严重的新发现

在动手测试之前设想的缺口是"`pythPriceFeedKey` 从未写入 DataStore"。实际在 fork 上一步步接线时，发现**真正的部署缺口比这个更深两层**：

### 发现 1：真实部署的 Oracle 合约，`pyth` 地址是零地址

```bash
cast call 0x83719dDb9d810B87cC9cB17A29d937dF0761497d "pyth()(address)" --rpc-url <base-sepolia-rpc>
# → 0x0000000000000000000000000000000000000000
```

`Oracle.sol` 里 `pyth` 是 `immutable`，只能在部署时通过构造函数写入一次，**之后永远不能改**。也就是说，不管 DataStore 里 `pythPriceFeedKey`/`pythPriceFeedMultiplierKey`/`priceFeedHeartbeatDurationKey` 配置得多完整，`PythPriceFeedUtils.getPriceFeedPrice()` 最终调用的 `IPyth(pyth).getPriceNoOlderThan(...)` 永远是在调一个零地址（`call to non-contract address`，链上会直接 revert）。**这不是配置缺口，是合约实例本身在部署那一刻就没有具备使用 Pyth 的能力**，必须重新部署一个新的 Oracle 实例才能修。

### 发现 2：`ChainlinkDataStreamProvider` 也有一个绑定死的 `oracle` 地址

```solidity
// src/oracle/ChainlinkDataStreamProvider.sol
address public immutable oracle;
modifier onlyOracle() {
    if (msg.sender != oracle) revert FxErrors.Unauthorized(msg.sender, "Oracle");
    _;
}
```

这意味着：即使重新部署了一个 `pyth` 地址正确的新 Oracle，**主 oracle provider（Data Stream）也不会认这个新 Oracle**——它只认它自己构造时绑定的那一个旧 Oracle 地址。所以"修复 Pyth 接线"不是"重新部署一个 Oracle 就完事"，而是**要连主 provider 一起重新部署**，然后把 `oracleProviderForTokenKey` 这类 DataStore 配置全部指向新的一套合约。（`ChainlinkPriceFeedProvider`——备份路径用的那个——构造函数只接收 `DataStore`，没有这种绑定，可以直接复用，不用重新部署。）

**这两条合起来的实际含义**：给现有部署"打开 Pyth 开关"不是一次 DataStore 配置变更能搞定的事，是一次需要重新部署 Oracle + 重新部署 DataStream Provider + 全量切换 DataStore 指向的迁移操作，规模比原先设想的大得多，需要工程排期，不能当成一个小配置项处理。

### 发现 3（延续 2026-08-12 的发现，本次进一步坐实）：Base Sepolia 上 24 个资产里已有 7 个 Pyth 缓存严重陈旧，且 keeper 已实测能修复它们

见 §四。这次不只是查了一遍新鲜度，还真的跑 keeper 把其中一批刷新成功了。

## 二、机制全景图（本次验证覆盖的三层）

```plain text
① 主 oracle：ChainlinkDataStreamProvider  ──┐
② 备份主 oracle：ChainlinkPriceFeedProvider ─┼─→ Oracle._validatePrices() ──→ 跟 Pyth 交叉校验（若非 Pyth 主）──→ ③ Pyth 参考价
```

- 主/备份切换：改 `oracleProviderForTokenKey(oracle, token)` 这一个 DataStore key，指向哪个 provider 合约地址，哪个就是当前"主"。

## 五、参数配置公式与实测正确性

**Pyth/传统 Feed 精度换算 multiplier 公式**（`PythPriceFeedUtils.sol`/`ChainlinkPriceFeedUtils.sol` 注释里给的）：

```plain text
multiplier = 10 ^ (60 - 外部价格源的 decimals - token 自身 decimals)
```

BTC/ETH 这两个 index token 是纯合成资产（`0x0555E30da8f98308EdB960aa94C0Db47230d2B9c` 在 Base Sepolia 上**没有部署任何字节码**，只是一个用作 key 的地址），本次通过读取已经在生产环境里生效的 `dataStreamMultiplierKey`（值为 `1e24`）反推出它们按 **18 位小数**处理（`24 = 60 - 18(Data Stream 精度) - 18(token)`——注：Data Stream 报告本身用 18 位小数，跟 Pyth/传统 Feed 的 8 位小数不是同一个基准，不要混用）。Pyth 和传统 Feed 都是 8 位小数，所以：

```plain text
multiplier = 10 ^ (60 - 8 - 18) = 10^34
```

本次配置的 `pythPriceFeedMultiplierKey`/`priceFeedMultiplierKey` 都用的这个值，§四第 2/4 步实测出来的 BTC/ETH 价格都落在合理区间（$63k/$1.9k 量级），**证明这个公式和取值是对的**。

## 六、Fork 测试方法论笔记（踩过的坑，供以后复用）

这几个坑不是合约逻辑问题，是 fork 测试本身的操作细节，记下来避免以后重复踩：

1. **anvil 的 `eth_sendTransaction` 自动 gas 估算，对这种带 ECDSA 签名验证的复杂调用（`setPrices`/`updatePriceFeeds`）经常在客户端（viem）侧触发 10 秒超时**，但 `cast call`（纯模拟）几秒就能返回真实结果。排查这类"卡住不动"的第一步应该是先用 `cast call ... --trace --with-local-artifacts` 看真实 trace，而不是假设是超时/网络问题。最终解法是显式传 `gas` 参数跳过自动估算（`pythKeeper.ts`/`verifyOracleForkMechanism.ts` 都已经这么改）。
2. **`Oracle.setPrices()` 要求 `tokensWithPrices` 是空的才能设新价格**（`clearAllPrices()` 用于清空）。连续多次调用 `setPrices()` 而不在中间清空，第二次开始会 revert `NonEmptyTokensWithPrices`——这不是 bug，是刻意设计（一批价格设完应该在同一笔用户操作里用完就清，不应该累积悬挂）；写测试脚本时每次 `setPrices()` 成功后要记得 `clearAllPrices()`。
3. **`evm_increaseTime` 会把 fork 的 `block.timestamp` 往前推，但推完之后，从任何真实外部 API（Hermes、Chainlink Data Stream API）现取的数据的时间戳仍然只能反映"真实世界的当前时间"**，不会跟着 fork 的时间一起走。如果 warp 幅度超过了正常的价格新鲜度窗口，会导致**所有**新鲜度相关的检查（不只是你想测的那一个）全部因为"看起来陈旧"而报错，包括跟你本来想测的东西无关的 `MAX_ORACLE_PRICE_AGE`（本次实测这个值在生产环境只有 **60 秒**，非常紧）。**结论**：想干净地测试陈旧场景，优先用"本来就已经陈旧"的真实资产（比如 §四提到的另外 6 个），而不是主动 warp 时间；如果一定要 warp，warp 完成后如果还要继续测试其它路径，记得把相关的 `MAX_ORACLE_PRICE_AGE`/心跳一并放宽，避免不相关的检查跟着一起炸。

## 八、主/备切换机制的真实约束（2026-08-13 补充实测）

背景：讨论"传统 Chainlink Feed 当备份"的两个问题（不全面 + 偏差阈值对 100 倍杠杆太松）之后，提出了"备份期间接受 Pyth 单源，但让链下 keeper 加速刷新"的方案（详见 §九）。这一节专门核实：**主备切换到底是不是自动的、触发条件是什么、切回最少要等多久**——这三个问题直接决定了"备份"在实际运维里到底是什么样子。

### 8.1 切换是纯人工操作，合约里没有任何自动检测/自动切换逻辑

全仓库搜索 `setOracleProviderForToken` 的调用方，**只有 `src/config/Config.sol` 自己定义了这个函数，没有任何其他合约逻辑调用它**（`OrderHandler`/`LiquidationHandler`/`AdlHandler` 等执行路径里都没有"检测到 Data Stream 失败就自动切换 provider"这种代码）。也就是说：

- **没有链上自动熔断机制**。`ChainlinkDataStreamProvider.getOraclePrice()` 验证失败时就是单纯 revert，不会触发任何自动切换，后果是相关 token 的开平仓/清算/ADL 全部卡住，直到有人手动介入。
- **切换动作要求 `CONFIG_KEEPER` 角色**（`onlyConfigKeeper` modifier），必须是运维人工判断"主路径确实出问题了"之后，手动调用 `Config.setOracleProviderForToken(oracle, token, provider)` 才会生效。
- 实测确认部署账户 `0xf82CF35C5c0019861c2cDC65041C8Ac32970D403` 同时持有 `CONTROLLER` 和 `CONFIG_KEEPER` 两个角色，具备执行这个切换的权限。

**这意味着"备份"目前是一个需要人盯着告警、手动决策的应急预案，不是系统自愈能力**——如果要往"自动切换"方向发展，需要额外开发一套链下监控+自动触发切换交易的服务，这是全新的工作量，不是现成能力。

### 8.2 切回最少要等多久：真实配置是 0，且延迟只锁"重复切同一个 provider"，不锁"切换本身"

`ORACLE_PROVIDER_MIN_CHANGE_DELAY` 这个参数在 `Config.setOracleProviderForToken()` 里的判断逻辑：

```solidity
if (block.timestamp - store.getUint(FX100Keys.oracleProviderUpdatedAt(token, provider)) < MIN_CHANGE_DELAY) {
    revert OracleProviderMinChangeDelayNotYetPassed(token, provider);
}
store.setUint(FX100Keys.oracleProviderUpdatedAt(token, provider), block.timestamp);  // 只更新"新 provider"自己的时间戳
```

关键是 `oracleProviderUpdatedAt` 是**按 (token, provider) 这一对 key 分别存的**，且只有被切换**进来**的那个 provider 会刷新自己的时间戳，被切换**出去**的那个 provider 的时间戳完全不动。这带来一个不直观但很重要的结论：**这个延迟锁的是"多快能重新激活同一个 provider"，不是"进了备份之后最少要待多久才能切回"**。

**实测过程**（Base Sepolia 真实部署的 `Config` 合约 `0xa82A9b2b57A3F3767715F8C1736C4177305CDEd7`，走真正的 `setOracleProviderForToken` 前门，不是绕过去直接改 DataStore）：

1. 查真实部署当前的 `ORACLE_PROVIDER_MIN_CHANGE_DELAY` 值：**0**——现在实际上没有任何冷却时间，切换和切回可以做到 0 秒间隔。
2. 在 fork 上完整走了一遍：主（Data Stream）→ 备（传统 Chainlink Feed）→ 立刻切回主，两次切换都在**同一个区块级别的时间尺度内**成功，符合真实配置（延迟=0）。
3. 为了验证"如果以后把延迟调成非 0会怎样"，临时把这个值设成 3600 秒（1 小时），重复"备份→立刻切回主"的动作：
- 立刻**再切一次到刚激活过的那个 provider**（比如切完备份又想再切一次备份）→ 按预期 revert（`OracleProviderMinChangeDelayNotYetPassed`）。
- 但**切到另一个 provider**（也就是正常的"切回主"操作）在同一时刻依然**立刻成功**——因为主 provider 自己的"上次激活时间"是很久以前（它已经稳定运行了很长时间），跟这次延迟窗口无关。
- 用 `evm_increaseTime` 把 fork 时间推过 3600 秒之后，两个方向的切换又都恢复正常。

**结论**：只要"切换到备份"和"切回主"用的是两个不同的 provider 地址（正常情况下当然是这样——备份和主本来就是两个不同合约），**这个延迟参数在实践中基本不会限制"备份期间最少要待多久"——只要主路径确认恢复，运维可以立刻切回，不需要强制等待**。真正会被这个延迟卡住的场景，是短时间内对**同一个** provider 重复切换（比如备份状态下主路径时好时坏，来回切了好几次备份），这更像是一个"防抖/防手滑"的保护，不是"强制最短驻留时间"的设计。

### 8.3 结论：给"方案 B"的可行性一个明确答案

- 触发备份：人工判断 + 手动调用，**没有自动化**，如果要做成"自动检测 Data Stream 异常并自动切换"，是一个独立于本次讨论范围的新开发项。
- 切回主：**没有强制最短等待时间**（真实延迟配置=0；即便配了非 0 延迟，只要没有对同一个 provider 反复切换，也不受影响）——所以运维模型可以是"人工确认主路径恢复后立即切回"，不需要预留一个固定的"备份最短持续时间"。
- 结合 §九 的"备份期间加速 keeper 刷新"方案：既然切回没有强制延迟，加速窗口的时长完全由实际故障处理时间决定，不会被合约层面的冷却时间拉长，进一步降低了这套方案的运维复杂度。

## 九、备份期间的交叉验证方案讨论（2026-08-13，设计阶段，尚未实现）

### 9.1 问题起点：传统 Chainlink Feed 当备份，有两个真实缺陷

1. **不全面**：Base Sepolia 只有 BTC/ETH/LINK 三个资产有传统 Feed；Base 主网大约 12/24 个有，另外 12 个完全没有（详见 `oracle_inventory.md` §三）。
2. **偏差阈值太松**：传统 Feed 是"价格变动超过阈值（部分资产 0.5%）或到心跳时间才更新"的推送式聚合器，100 倍杠杆下 0.5% 的滞后相当于 50% 保证金，风险偏高。

### 9.2 提议："Pyth 当备份 + 继续做交叉验证 + 备份期间让 keeper 按 Hermes 原生频率（3~12 秒）加速刷新"——第一部分卡在合约架构上

`Oracle._validatePrices()` 里 `if (!provider.isPythOnChainProvider())` 这一行，把"Pyth 是当前主 provider"和"继续对 Pyth 做交叉验证"做成了互斥关系——一旦把 Pyth 切成主，代码会自动跳过校验（避免拿 Pyth 校验 Pyth 自己）。**这意味着"Pyth 当备份的同时继续起交叉验证作用"在现在的合约代码下做不到，这是这次讨论中发现的一个真实架构矛盾，不是操作层面能绕开的。**

要真正解决，只有改合约逻辑一条路（比如"主是 Pyth 时改去校验传统 Feed（如果这个资产有的话）"），但这对没有传统 Feed 的 12 个资产依然无解——本质上是"全仓库只接了两个独立数据源，两个都拿去当主的时候，没有第三个源可以再校验"，属于数据源数量的硬约束，不是设计能绕开的。

### 9.3 拆解后仍然成立、且不需要改合约的部分：备份期间让 keeper 加速刷新

接受"备份期间 Pyth 单源、没有交叉验证"这个现实（因为备份本来就是临时应急状态），但让这段时间内**唯一在用**的这个 Pyth 价格尽量新鲜：

- **触发方式**：监听 `Config.sol::setOracleProviderForToken` emit 的 `SetOracleProviderForToken` 事件（带 `oracle`/`token`/`provider` 三个字段），一旦看到某个 token 被切到 Pyth-as-primary（或者传统 Feed 备份，同理），keeper 切到"加速模式"；看到切回 Data Stream，立刻降回正常节奏。§八 已经确认这个切换/切回没有强制冷却时间，所以加速窗口的起止完全跟着真实故障处理节奏走，不会被合约拖长。
- **加速到多快**：Hermes 实测每 3~12 秒就有新报价（见 `oracle_inventory.md` §1.5"离线接口更新频率"一节），理论上可以按这个频率刷新链上缓存。
- **⚠️ 必须是事件触发的短时爆发，不能是常态策略**：按实测单次批量刷新成本 $0.0089 计算，如果按 7.5 秒一次**常年**跑，一个月要 **$3,075**，是正常 30 分钟节奏（$12.8/月）的 **240 倍**；但如果只在备份激活的窗口内跑（比如一次故障处理 1 小时），这 1 小时只要 **$4.27**，完全可以接受。成本测算详见 `oracle_inventory.md` §1.6。

### 9.4 澄清一个容易搞错的参数：备份期间该调紧的是心跳，不是 `MAX_ORACLE_PRICE_AGE`（2026-08-13 24 资产 fork 实测确认）

自然的直觉是"切到 Pyth 当主之后，是不是要把 `MAX_ORACLE_PRICE_AGE`（生产真实值 60 秒）适当放宽，否则容易因为价格太旧成交不了"——方向是对的（备份期间确实存在"新鲜度不够导致成交失败"的真实风险），但具体这个参数不需要动，因为它对 Pyth-as-primary **结构性地不生效**：

- `PythPriceFeedProvider.getOraclePrice()` 返回的 `timestamp` 字段直接就是 `block.timestamp`（源码最后一行 `timestamp: block.timestamp`，注释也写明"the timestamp returned is based on the current blockchain timestamp"）——不是 Pyth 缓存自己的 `publishTime`。`ChainlinkPriceFeedProvider`（传统 Feed）也是同一种写法。
- `Oracle._validatePrices()` 里 `MAX_ORACLE_PRICE_AGE` 判断的是 `validatedPrice.timestamp + maxPriceAge < block.timestamp`，代入 `timestamp = block.timestamp` 后恒为假——只要主 provider 是 Pyth 或传统 Feed，这条检查永远不会触发，调不调这个参数结果都一样。**本轮 24 资产 fork 实测中，Pyth 备份那一轮全程没碰过 `MAX_ORACLE_PRICE_AGE`，24/24 依然全部成功**，正是这一点的直接证据。
- **真正会挡成交的是 `priceFeedHeartbeatDurationKey(token)`**——`PythPriceFeedUtils.getPriceFeedPrice()` 内部调 `IPyth.getPriceNoOlderThan(id, heartbeatDuration)`，这是 Pyth 合约自己独立的新鲜度校验，跟 `MAX_ORACLE_PRICE_AGE` 是两套机制。如果心跳配得比 keeper 实际刷新频率更紧，两次刷新之间就会有交易失败的窗口期——这正是本节"应急 keeper 加速刷新"要解决的问题：不是放宽心跳阈值（放宽=削弱保障），而是让 keeper 刷新跑得比心跳阈值更快，两者要配套设计。
- **次要的另一个参数：`MAX_ORACLE_TIMESTAMP_RANGE`（生产真实值同样是 60 秒）**——限制**同一笔 `setPrices()` 调用内**所有 token 时间戳的最大跨度。如果一笔调用里混了"仍在主路径（Data Stream 真实签名时间，可能已滞后接近 60 秒）"和"已切 Pyth 备份（`timestamp=block.timestamp`，即"现在"）"两类 token，时间差有可能触发 `MaxOracleTimestampRangeExceeded`。正常单笔开平仓只涉及 1 个 index token（USDC 已不走 Oracle 校验），不会踩到；但如果以后 keeper 或批量操作把处于不同 provider 状态的多个资产打包进同一笔调用，需要留意这一点。

### 9.5 现状与下一步

- 这是**设计讨论阶段**，`pythKeeper.ts` 目前还是固定节奏（默认 30 分钟一次），**没有实现**"监听切换事件 → 自动加速/降频"这套状态机。
- 如果要落地，下一步是给 `pythKeeper.ts` 加一个事件监听 + 模式切换逻辑，不需要动合约，可以独立于 §一的 Oracle 重新部署问题先行开发测试。
- 合约层面的"备份期间也能维持双源"（本节 §9.2 提到的方案）建议作为一个单独的排期项提给工程师评估，不是这次讨论的必须前提。

1. 把 24 个资产的 `priceFeedHeartbeatDurationKey` 收紧到 200 秒（此时链上缓存的自然陈旧度已经是几分钟到几十天不等，早已超过 200 秒）。
2. 提交新鲜的 Data Stream 数据（Data Stream 这条腿本身完全新鲜）→ **✅ 按预期 revert**——证实"Pyth 参考价陈旧"确实会挡住主路径，即使主路径自己的数据完全没问题。
3. 跑 `pythKeeper.ts` 的刷新逻辑，一笔交易把 24 个资产的 Pyth 缓存全部刷到几乎实时（读回 age≈-3s，即比链上区块时间还新几秒，正常的读取时序误差）。

### 10.6 本轮踩过的坑（跟 §六 一脉相承，都是真实教训，供以后复用）

1. **不要按资产逐个串行提交 `setPrices()`**：第一次尝试是 24 个资产各发一笔交易，跑到第 13 个左右开始集体 revert——排查发现是生产环境真实的 `MAX_ORACLE_PRICE_AGE=60` 秒被真实撞到了：24 笔交易加起来的链上确认耗时超过了 60 秒，前面成功的资产用的还是同一批"新鲜"数据，后面的就过期了。**修复：把整批资产打包进一笔 `setPrices()` 提交**（这本来也更接近真实 keeper 的做法），失败时才二分定位到具体哪个资产有问题。
2. **`evm_increaseTime` 是不可逆的**：为了制造"Pyth 已过期"的场景，第一反应是把 fork 时钟往前调——调完之后确实能让"过期"场景复现，但调完之后**这个 anvil 实例的时钟永久性地比真实时间快了**，导致后续"keeper 刚推送的全新数据"也会显得"过期"（因为 Hermes 返回的时间戳锚定的是真实世界时间，而 fork 的 `block.timestamp` 已经被人为调快了）——不是 keeper 失败，是测试方法本身自相矛盾。**修复：换一个全新的、没被调过时间的 fork，靠真实流逝的墙钟时间（哪怕只有几分钟）自然让缓存变旧，全程不调用 `evm_increaseTime`**。
3. **心跳阈值要给测试脚本本身的开销留够余量**：不调时钟之后，第一次用 60 秒心跳仍然复现失败——用 `cast run <txhash>` 解码出真实 revert 是 Pyth 自己的 `StalePrice` 错误，原因是这套多步骤脚本本身（24 笔心跳配置交易 + 两次真实 Chainlink API 拉取 + 一次 Hermes 推送）的墙钟耗时累计起来轻松超过 60 秒，等到最后一步提交时，刚刷新的缓存又变陈旧了。**修复：心跳改成 200 秒**——依然比生产环境实际运行节奏（≥1800 秒）紧得多，但给了测试脚本自己的操作开销足够缓冲。
4. **`waitForTransactionReceipt` 不会对链上 revert 抛异常**：第一版偏差测试的 `try/catch` 只在 `catch` 分支里判定"revert 符合预期"，但 viem 的 `waitForTransactionReceipt` 对一笔已经上链但状态为 `reverted` 的交易，是**正常返回**（`receipt.status === "reverted"`），不会抛出异常——导致误判为"没有按预期 revert"。**修复：显式检查 `receipt.status`**，不能只依赖 `try/catch` 兜底。这是本轮唯一的"假阴性"（合约行为其实是对的，是脚本判断逻辑错了），用 `publicClient.simulateContract` 单独复现，加上 `cast run` 解码具体 revert 原因，才最终定位到。
5. **ABI 里漏写返回结构体的字段会导致解码错位、不会报错**：debug 时为 `Oracle.validatePrices()` 手写了一个 ABI，漏掉了 `ValidatedPrice` 结构体最后的 `provider` 字段，viem 没有报错，只是把后面所有字段错位解码成了乱码大数——提醒以后手写 ABI 时优先核对 Solidity 源码里的完整 struct 定义，不要凭记忆或猜测字段顺序。

### 10.7 结论

- **主路径、Pyth 备份、双向切换、2% 偏差校验、Pyth 当主时跳过校验、陈旧阻断、keeper 刷新恢复**——七项机制，全部 24 个资产（或用代表性资产验证的通用合约逻辑）在 fork 上真实跑通，没有发现新的合约层面问题（§一发现的 Oracle/`PythPriceFeedProvider` 双双 `pyth=0x0` 依然是唯一的、且已知的阻塞项，本轮进一步确认这个问题在两个合约上是对称的）。
- 本节所有踩坑记录本质上都是"测试方法论"问题，不是合约 bug——留档是为了下次（包括接下来用户提供的真实 fork 复现环节）不用重新踩一遍。

### 11.2 Tenderly 与 anvil 的关键机制差异（复现前必须适配的三处）

1. **账户模拟方式不同**：anvil 用 `--unlocked` + `anvil_impersonateAccount`，直接 `eth_sendTransaction`；Tenderly Virtual TestNet 用专属的 `tenderly_sendTransaction` RPC 方法（`gas`/`gasPrice` 填 `0x0`，Tenderly 自己处理免 gas 模拟）。写了一个通用的 viem 自定义 transport（`scripts/keeper/tenderlyImpersonate.ts`），拦截 `eth_sendTransaction` 请求转换成 `tenderly_sendTransaction`，其余方法原样透传——这样 §十的四个脚本只需要复制一份、换掉 RPC 常量和 wallet client 的 transport，业务逻辑一行不用改。
2. **合约部署**：`forge create` 走标准签名交易，在任何 EVM RPC（包括 Tenderly）上都能用，只需要用 `tenderly_setBalance` 给一个自己持有私钥的地址（复用了 anvil 默认测试账户 `0xf39Fd6e...`）充值，正常签名部署即可，不需要额外适配。
3. **`multicall3` 需要在自定义 chain 定义里显式声明地址**（`0xcA11bde05977b3631167028862bE2a173976CA11`，标准 CREATE2 部署，fork 出的状态里天然存在）——用 `viem/chains` 的内置链定义时这是自动带的，自定义 `defineChain` 必须手动补上，否则 `publicClient.multicall()` 会报 `ChainDoesNotSupportContract`。

### 11.4 Tenderly 特有的一个新坑：fork 自身时钟会真实漂移，不是靠"不调时钟"就能规避

§六记录过 anvil 的教训是"`evm_increaseTime` 不可逆，人为调快时钟会污染后续新鲜度判断，修复方法是全程不调用它"。这次在 Tenderly fork 上复现陈旧+keeper 恢复测试时，**即使全程没有主动调用任何时间相关 RPC，依然复现了同一类问题**，根因不同：

- 这个 fork 从 2026-08-12 创建到本次测试（2026-08-17）之间放置了几天，实测发现它的 `block.timestamp` 比真实墙钟时间**滞后了约 56,700 秒（约 15.7 小时）**——Tenderly Virtual TestNet 的链上时钟不像 anvil fork 那样在每次交易时自动贴近真实时间，长时间静置会累积出真实的漂移。
- 现象：心跳阈值收紧触发陈旧 revert（符合预期）→ keeper 用 Hermes 真实数据刷新成功 → 但刷新后立刻读回的"新鲜度"显示**负数**（`age = block.timestamp - publishTime < 0`，因为 Hermes 时间戳锚定真实时间，比滞后的 fork 时钟还"新"）→ 紧接着再提交一次 `setPrices()` 依然 revert，看起来像 keeper 没生效。
- 根因定位：Pyth 自己的陈旧判断做的是 `block.timestamp - publishTime` 这个减法，Solidity 0.8.x 默认开启溢出检查，当 `publishTime > block.timestamp`（结果为负）时这个无符号减法会**下溢并 revert**，而不是静默给出负数——这才是"keeper 刚成功、下一笔却又 revert"的真实原因，不是 keeper 逻辑有问题。
- **修复**：用 `evm_increaseTime`（Tenderly 同样支持这个方法）+ `evm_mine` 把 fork 时钟一次性拨到贴近真实时间，之后测试就完全正常（心跳=200 秒，全部 4 步骤按预期通过，读数也变成合理的个位数秒新鲜度）。
- **对以后复现的提示**：如果这个 fork（或任何长时间静置的 Tenderly fork）隔了一段时间没用，重新做陈旧/keeper 类测试前，先 `cast block latest` 看时间戳，跟 `date +%s` 对比一下漂移量，必要时先拨一次时钟，不需要每次都做，只在长时间未使用后需要。

### 11.5 结论

- 除了上述两处环境适配（账户模拟方式、`multicall3` 声明、Tenderly 自身的时钟漂移特性）之外，§十在本地 anvil 上验证过的全部结论在真实 Tenderly fork 上**逐条复现一致**，进一步确认这不是 anvil 模拟环境的偶然结果。
- 本轮**没有**改变这个 fork 上真实协议（`OrderHandler` 等）实际使用的 Oracle——用户如果现在把前端指向这个 fork 交易，走的仍然是原来 `pyth=0x0` 的旧 Oracle，Pyth 交叉校验/备份机制不会被真实触发。如果之后想要"前端真实测试这套修正机制"，需要另外评估并执行 §十一开头提到的 handler 合约迁移，这是一项独立的、更大的工作，建议单独立项。

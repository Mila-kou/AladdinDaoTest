# 用户级场景与项目需求文档追踪矩阵

## 1. 使用原则

项目归档包含讨论版、实施版、测试报告、前端交接和安全评审。E2E 不逐篇复制用例，而是把同一业务事实收敛到一个用户旅程，再用本矩阵追踪来源。

| 状态 | 含义 |
|---|---|
| CURRENT | [Docs/contract-releases/CURRENT.json](../../Docs/contract-releases/CURRENT.json) 所载基线的当前应有行为。须分清两层：**已部署行为** = `deployments[]`（撰写时唯一部署 base-sepolia@v0.3.1，三个 fork 环境均派生于此，@v0.3.1 快照）；**目标主测行为** = `primary`（撰写时 v0.3.2，无部署、准入 NOT_READY）。二者不一致的条目在 §5 逐项追踪；执行时按环境实际部署版本判定，并显式标注「环境基线 ≠ 目标基线」 |
| TARGET | 已定稿但可能尚未部署的目标行为 |
| PENDING | 待评审/待实现，不作为当前通过条件 |
| RISK | 已知缺陷或部署风险，保留复现与修复后目标 |

## 4. 已知冲突与执行记录要求

| 冲突 | 处理 |
|---|---|
| Flash 旧版 24h/90 单/1h 锁 vs 新决策 90 天/大额度/无锁 | 执行 SCN-058 时记录页面/链上实际参数；与部署基线不一致报“版本接线差异” |
| 当前 Dynamic Spread 非负 vs 目标允许 rebate | SCN-050 分成 CURRENT 与 PENDING 两条判定，不互相覆盖 |
| 交易指南称保护 15 分钟，测试夹具存在 120/240/900 秒不同配置 | 页面场景一律读当前部署 `graceStart/graceEnd`，文案承诺与实际配置分别核对 |
| K 线与 Oracle 更新节奏不同 | 不要求数值逐 tick 相等；要求市场、时间、新鲜度和用途不误导 |

每次版本回归须在执行报告中写明：前端 commit/部署时间、合约部署目录、chainId、环境实际部署版本与 CURRENT.json `primary` 是否一致（不一致显式标注「环境基线 ≠ 目标基线」）、Flash 实际生命周期参数、grace 实际时长、Dynamic Spread 模式和已知风险状态。

## 2. 重构目标

每一次交易动作都必须形成独立、可追溯的核对闭环：

```text
Expected Δ = f(订单输入, 执行区块参数, Oracle, 独立公式结果)
Expected After = Before + Expected Δ
Actual Δ = Actual After - Before
PASS ⇔ Actual After = Expected After
```

除此之外，再分别核对：

```text
Event Actual = Formula Expected Event
UI Actual = Chain / Formula Expected Display
```

禁止用 `Actual After - Before` 反推 `Expected Δ`，也禁止把 Event 自己作为该 Event 的 Expected。复杂公式尚未实现或输入缺失时必须显示 `NOT_VERIFIED`，不能用本地默认参数或 Actual 倒推出 PASS。

## 3. 四类证据的职责

| 证据层 | 权威数据 | 主要用途 | 不允许的用法 |
|---|---|---|---|
| 订单输入 | margin、sizeDelta、方向、订单类型、触发价、acceptablePrice | 产生本次动作的业务增量 | 从成交后的仓位反推原始订单输入 |
| 固定参数 / Oracle | 执行区块 DataStore、Referral Tier、Oracle min/max、decimals | 代入公式形成 Expected | 使用配置文件默认值覆盖链上实际参数 |
| Event | Order、Position、Fee、Funding、Oracle 事件及 logIndex | 核对合约执行过程和各费用分量 | 用 Event 值直接证明同一个 Event 正确 |
| 链上状态 / 页面 | Before/After 区块快照、Reader、ERC20、DataStore、页面显示 | 核对最终落账及 UI 一致性 | 只比较格式化后的页面字符串，不比较 raw 值 |

前端页面只参与 UI 用例或明确启用 UI 证据的用例。纯链上自动交易用例没有页面证据时显示 `N/A`，不加载 Trade 页面，也不影响协议核对结果。

## 5. 统一核对记录模型

建议把当前单层 `Reconciliation` 扩展为以下结构：

```ts
interface CheckRecord {
  id: string;
  txStep: string;
  domain: 'order' | 'funds' | 'position' | 'fee' | 'funding' | 'market' | 'risk' | 'ui';
  field: string;
  actual: {
    before?: bigint | boolean | string;
    after?: bigint | boolean | string;
    delta?: bigint;
    sources: SourceRef[];
  };
  expected: {
    delta?: bigint;
    after?: bigint | boolean | string;
    formulaId: string;
    expandedFormula: string;
    inputs: FormulaInput[];
  };
  crossChecks: {
    event?: LayerVerdict;
    ui?: LayerVerdict;
  };
  verdict: 'PASS' | 'FAIL' | 'CALCULATED' | 'NOT_VERIFIED';
  difference?: bigint;
}
```

每一个公式输入都带来源，例如：

```text
sizeDeltaUsd             50e30       Order TX1
positionFeeFactor        2e26        DataStore @ block 45042780
collateralPrice.min      99900000    Oracle @ block 45042780
positionFeeAmount        10010       PositionFeesCollected log#12
UI Fee                   0.01001     Trade page / Positions
```

这样看板能回答“这个 Expected 从哪里来、用了什么参数、哪个事件证明执行过、页面显示是否一致”。

## 6. 资金核对必须分成两层

不能把所有数据都笼统称为“余额”。应明确区分：

### 6.1 实际 Token / Vault 资金流

逐 TX 显示：

- `ΔTrader`；
- `ΔOrderVault`；
- `ΔPositionVault`；
- `ΔLPVaultAssets`；
- `ΔFeeHandler`（历史 Evidence 键名为 `feeReceiverUsdc`）。

独立 TX 快照的开仓流程应拆开：

```text
TX1 创建订单：ΔTrader = -inputMargin，ΔOrderVault = +inputMargin
TX2 执行订单：ΔOrderVault = -inputMargin，抵押品和费用进入对应账本
```

历史证据若把创建和执行合并，只能标记为“组合阶段”，不得伪装成 TX2 独立变化。

### 6.2 DataStore 应收账本

`FeeHandler USDC balance`、事件中的 `feeReceiverAmount` 与 DataStore `claimableFeeAmount` 不是同一个概念：

- 交易执行时，Fee Receiver 分成可能先记入 `claimableFeeAmount`；
- USDC 仍可能保留在 PositionVault，`ΔFeeHandler` 因而为 0；
- keeper 执行 claim / withdraw 后，才核对 FeeHandler、RevenuePool、Treasury、Insurance、LP 的实际 Token 变化。

因此看板必须同时展示：

```text
ΔFeeHandler Token Balance
ΔClaimablePositionFee
ΔClaimableFundingFee
ΔClaimableLiquidationFee
```

两类账本分别守恒，禁止把 claimable 和实际 Token balance 重复相加。

## 7. 固定展示的守恒规则

每种交易动作按适用范围固定展示以下守恒式：

1. 订单托管守恒：`ΔTrader + ΔOrderVault = 0`；
2. 执行资金守恒：按该动作实际参与的 Trader、OrderVault、PositionVault、LPVaultAssets、FeeReceiver 展开；
3. Fee 分账守恒：`Protocol Fee = FeeReceiver Amount + LP Pool Amount`；
4. Funding 守恒：支付端、接收端、LP 或 Claimable Funding 的路由闭合；
5. PnL 守恒：`Trader PnL + LP PnL = 0`，再单独处理 Fee/Funding；
6. OI 守恒：市场 Long/Short OI 的变化与仓位 sizeDelta 一致；
7. 全流程守恒：开仓前到全平后的最终资金、仓位和 OI 闭合。

不同性质的值不能混成一个无名称公式。ERC20 balance、LPVault `totalAssets` 和 DataStore claimable 必须标明是“物理余额”“经济资产”还是“内部应收”。

## 8. 最优可见页面方案

每个 TX 页面保持一个动作一个核对单元：

```text
TX2 · Keeper 执行开多                                   PASS
Block / Tx / Order Key / Actor

[订单输入] [链上参数] [Events] [页面对照]
  5/5       12/12       8/8      N/A

资金流 | 仓位 | Fee | Funding | OI/Spread | Grace | 前端对照

字段            Expected Δ    Actual Δ     Expected After   Actual After   差异   状态
ΔOrderVault     -10 USDC      -10 USDC     0                0              0      PASS
ΔPositionVault  +9.994995     +9.994995    ...              ...            0      PASS
ΔLPVaultAssets  +0.005005     +0.005005    ...              ...            0      PASS

守恒公式（独立一排）
ΣΔ = ΔTrader(0) + ΔOrderVault(-10) + ... = 0 USDC          PASS
```

点击任意一行展开四个证据区：

1. **公式**：显示原始公式、实际代入值、精度和向上/向下取整；
2. **参数**：显示 DataStore key、值、合约地址和执行区块；
3. **事件**：显示 event 名、字段、txHash 和 logIndex；
4. **页面**：显示页面字段、raw 值、格式化值和允许的显示精度。

页面顶部同时给出分层结论：

```text
协议状态 PASS | Event 一致 PASS | 页面一致 N/A | 数据完整性 PASS
```

协议正确但页面错误时应显示“协议 PASS / UI FAIL”，不能合并成一个模糊状态。

## 9. 参数与公式覆盖矩阵

| 模块 | 订单输入 | 执行区块参数 | Event | After 状态 | 页面字段 |
|---|---|---|---|---|---|
| Size / Margin | margin、sizeDelta、leverage | collateral min/max、decimals | PositionIncrease/Decrease | position raw fields | Pay、Size、Leverage、Margin |
| Price / Spread | direction、order type、acceptablePrice | constant/depth/skew/clamp、index min/max | executionPrice、spread | entry price、cumulative cost | Entry、Price Impact、Slippage |
| Fee | tradeSize | positionFeeFactor、receiverFactor | PositionFeesCollected | PositionVault、LPVault、claimable | Fee、Est. Receive |
| Funding | position size、duration | floor/base/min/max、EMA | FundingUpdated、FundingFee | per-size、claimable、Vault | Funding 列、Breakdown |
| Grace | position action | graceBase、tier、multiplier | position timestamps | graceStart/graceEnd | Protection Card |
| PnL | close size、direction | execution price、collateral price | PositionDecrease | Trader/LP/PositionVault | PnL、Est. Receive |
| OI / Skew | sizeDelta | market parameters | Position event | Long/Short OI、Skew、impact pool | Market 面板 |

### 阶段 B：以 SCN-009 为黄金样例

- 完整实现开仓、全平、Fee、Funding、PnL、OI、Grace 和资金守恒；
- 验证 10 USDC、5x 的所有 raw 值和显示值；
- 明确 FeeReceiver balance 与 claimable 的不同路由。

### 阶段 C：迁移订单变体

- SCN-010：Limit 创建、Pending、触发执行、全平；
- SCN-070：多空 × 开平 × acceptablePrice 八象限；
- 公共模块复用，Runner 只传订单意图和证据。

### 阶段 D：接入前端字段核对

- 手工/UI 用例采集下单预览、Positions、Market、Protection Card；
- 先比较 raw 值，再按页面 rounding policy 比较显示值；
- 页面未加载不影响纯链上自动化。

### 阶段 E：反向破坏验证

- 修改一个参数值，相关公式必须 FAIL；
- 修改一个 Event 字段，Event 对照必须 FAIL；
- 修改 After，状态核对必须 FAIL；
- 修改 UI 显示，UI 层必须 FAIL，但协议层保持原结论；
- 删除必要输入，结果必须变为 `NOT_VERIFIED`，不能 PASS。

## 11. 完成标准

- 所有 PASS 均能追溯到订单输入、链上参数、公式和实际数据源；
- 每个 TX 都有独立区块快照，不再用全流程差值代替单笔交易；
- `Expected Δ` 与 `Actual Δ` 分列显示，并显示差异；
- FeeHandler Token Balance 与 Claimable Fee 分开显示；DataStore `FEE_RECEIVER` / RevenuePool 需在 claim/withdraw 动作中另行取证；
- Event、链上状态和 UI 各自给出独立结论；
- 缺少公式或参数时明确 `NOT_VERIFIED`；
- SCN-009 先完整通过，再迁移 SCN-010 和 SCN-070。

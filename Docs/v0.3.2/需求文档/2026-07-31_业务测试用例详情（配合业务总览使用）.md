## 一、开仓与仓位管理

**基础数据**

- 精确记账系列（E2ELedger，G1/G5/SPC/GTOK 各测试组，覆盖 1.1-1.18）默认市场为 ETH/USD（WNT），oracle 价格 2000 USD/ETH；默认名义仓位 50,000 USD，抵押品 10,000 USDC（5 倍杠杆），sizeInTokens = 25e18（= 50,000e30 / 2,000e12）；LP 种子资金 2,000,000～4,000,000 USDC；默认零手续费+零资金费（`_setupCleanParams()` + `_setZeroFunding()`），价格 ±5%（2000→2100/1900）对应 ±2,500 USDC 盈亏。

## 二、杠杆与保证金管理

**基础数据**

- 100倍杠杆边界组（2.1-2.13，`test/integration/MaxLeverage.t.sol`）：仓位规模 SIZE=100,000 USD，入场价 ENTRY_PRICE=2,000 USD/ETH，LP 种子 5,000,000 USDC；开/关仓费率各 0.02%（POSITION_FEE_FACTOR），点差 0.01%（constantPriceSpread），MIN_COLLATERAL_FACTOR=1%（对应100倍上限），清算费=0；订单簿深度/position impact/skew impact/funding 在该组测试中默认清零，仅在"真实参数"子测试（2.11-2.13）中显式还原真实深度（askDepth≈7,923,961、bidDepth≈7,767,179，MAX_PRICE_IMPACT_SPREAD=0.5%）。
- 保证金调整组（2.14-2.19，`test/integration/CollateralAdjustment.t.sol`）：LP 种子 1,000,000 USDC，默认仓位 CA_COLLATERAL=1,000 USDC / CA_SIZE=10,000 USD（10倍杠杆），单次提取 CA_WITHDRAW=100 USDC；本组内开关仓手续费/点差/冲击全部清零以保证抵押品算术精确，minCollateralFactor=1%。
- 平仓三阶段扣减组（2.20-2.25，`test/integration/DecreaseCollateralPhases.t.sol`）：LP 种子 1,000,000 USDC，入场价 2,000 USD/ETH，手续费/点差/资金费/冲击全部清零（保证盈亏纯粹来自价格变动），minCollateralFactor=1%（上限100倍）；核心验证 BUG-003 修复后的三阶段扣减顺序：资金费 → 盈亏 → 手续费。

### 3.6 自动减仓（ADL）状态机与执行

**基础数据**

- v0.3.0 起 ADL 状态为**全局**唯一（不再按 market/isLong 维度）：`isAdlEnabledKey()` / `latestAdlAtKey()` 均无参数
- 业务级标准阈值（`Adl.t.sol`、`AdlSession.t.sol`）：开启阈值 `MAX_PNL_FACTOR_FOR_ADL` = 45%，关闭阈值 `MIN_PNL_FACTOR_AFTER_ADL` = 40%；机制级单测（`AdlExecution.int.t.sol`）用 1%/0.5% 验证同一套迟滞逻辑
- 迟滞（hysteresis）规则：当前 disabled 时用 MAX 阈值判断是否 enable（ratio > MAX）；当前 enabled 时用 MIN 阈值判断是否 disable（ratio ≤ MIN）
- `executeAdl` 前置检查三段：① `isAdlEnabled` 必须 true ② ratio 必须仍 > MIN ③ 目标方向 pnl 必须 > 0；后置检查：nextRatio 必须严格 < prevRatio
- 业务场景标准仓位（`AdlSession.t.sol`/`Adl.t.sol`）：`ADL_COLLATERAL` = 2,000 USDC，`ADL_SIZE` = 100,000 USD（50x），入场价 2,000，±50% 价格（3,000/1,000）触发 50% 浮盈/亏比例，LP 种子 100,000 USDC
- 权限：`ADL_KEEPER` 角色控制 `updateAdlState`/`executeAdl` 调用

### 3.7 LP 池整体风险监控

**基础数据**

- Net Obligation 口径：`getNetObligation = max(0,longPnl) + max(0,shortPnl)`，亏损侧不抵扣盈利侧
- Global Net Obligation Ratio = Σ各市场 netObligation / 资金池 poolUsd；poolUsd=0 时直接返回 0；阈值判定统一为"严格大于"
- v0.3.0 新 OI Reserve 口径：`totalNominalOI = (longOI + shortOI，以 token 计) × indexPrice.max`，需 ≤ `poolUsd × reserveFactor(marketIndex)`（reserveFactor 只按 marketIndex 配置，不再分方向）——相对旧的"分方向独立"口径是重大变更
- Capped PnL 机制：`maxPnlFactorKey(MAX_PNL_FACTOR_FOR_TRADERS, marketIndex, isLong)` 只对正向盈利封顶，亏损不封顶
- Gas 预算：20 个市场做一次全局比率计算，gas 上限 2,000,000

## 五、手续费、执行费补贴与推荐返佣

**基础数据**

- 手续费公式：fee_USDC = mulDiv(SIZE, feeFactor, FLOAT_PRECISION) / USDC_PRICE；USDC_PRICE = 1e24
- 默认口径（P1_FeeParams / P1_Fees / P4 系列）：feeFactor=0.2%（FLOAT_PRECISION*2/1000）、SIZE=50,000e30 → fee=100 USDC；1%档→500 USDC
- FeeSpecialty 系列另用一套口径：feeFactor=1%（1e28）、SIZE=10,000e30、COLLATERAL=5,000e6 → fee=100 USDC；清算费 LIQUIDATION_FEE_FACTOR=0.3%（3e27）、SIZE=10,000e30 → 30 USDC
- POSITION_FEE_RECEIVER_FACTOR：0%＝全进LP池；50%＝LP/可领取各半；100%（FLOAT_PRECISION）＝全进可领取账本
- UI 手续费：需先设 MAX_UI_FEE_FACTOR，再由接收方 exchangeRouter.setUiFeeFactor() 注册自己的费率；累积在独立的 claimableUiFeeAmountKey(mi, token, receiver)，与仓位手续费 claimableFeeAmountKey 互不干扰
- 三步流水线：交易执行 → DataStore 记账 claimableFeeAmountKey（USDC 仍在 posVault）→ feeHandler.claimFees()（posVault→feeHandler，任何人可调用）→ feeHandler.withdrawFees()（feeHandler→FEE_RECEIVER，仅 FEE_KEEPER 角色；v0.3.0 起 FEE_RECEIVER 必须实现 IRewardSplitter.depositReward 拉取转账，EOA 会 revert）
- Trader-LP 直接对赌设计（2026-06-12 定稿）：交易盈亏、清算盈亏 100% 结算给 LP 资金池，协议不参与交易 PnL 分成
- 费率分层：`POSITION_FEE_FACTOR` 的 bool 键位是 `balanceWasImproved`（不是 isLong）——改善失衡=低费率(2e26)，恶化失衡=标准费率(4e26)

## 九、动态价差与价格冲击

**基础数据**

- 精度基准：动态点差/失衡系数使用 WEI_PRECISION=1e18 计价（1e16=1%）；USD 金额用 FLOAT_PRECISION=1e30
- 公式：`dynamicSpread = constantPriceSpread + priceImpactSpread ± skewImpact`；若总和 ≤0 则 clamp 为 0
- 默认常量点差 `FX100_CONSTANT_PRICE_SPREAD = 1e14`（0.01%）
- 默认失衡系数（Fx100Setup 夹具）：ETH `SKEW_IMPACT_FACTOR=2.5e15`(0.25%)／`MAX_SKEW_IMPACT=5e15`；WBTC `SKEW_IMPACT_FACTOR=1e16`(1%，4×ETH)／`MAX_SKEW_IMPACT=1e16`
- `MAX_PRICE_IMPACT_SPREAD` 只封顶 `priceImpactSpread` 分量，不封顶 `constantPriceSpread`
- `priceImpactSpread = max(exp(orderSize·param/depth)-1, orderSize·WEI_PREC/depth) / 100`；多头开仓用 askOrderBookDepth，其余方向用 bidOrderBookDepth
- 成交价：开多 `execPrice = oraclePrice×(1+spread)`；开空 `execPrice = oraclePrice×(1-spread)`（平仓方向符号相反）
- E2E 常用参数（P1_DynamicSpread.t.sol）：`SPREAD_1PCT=1e16`，`NORM_PRICE=2000e12`，`SIZE=50000e30`

**⚠️ 重要风险与测试覆盖现状（Dynamic Spread Floor-at-0，2026-07-31 逐行代码核实）**

`dynamicSpread = constantPriceSpread + priceImpactSpread + skewImpact`——三个参数中只有 `skewImpact` 可能为负；三项之和 `≤0` 时被 floor 成 `0`（`src/pricing/PositionPricingUtils.sol:170-174`，本次已逐行核实与本模块"基础数据"公式一致），即成交价永远不能优于 oracle 价。完整推导、Avantis/GMX 对比、模拟计算见 `docs/analysis/pricing/risk_dynamic_spread_floor_removal.md`（完整版）/`summary_dynamic_spread_floor_removal.md`（精炼版）/`impl_spec_negative_dynamic_spread.md`（落地方案）。

**当前 floor-at-0 设计的测试覆盖（已核实充分，不是遗漏）**：

- `test_dynamicSpread_negativeSkewMakesTotalZero_returnsZeroAndTrue`（本模块 9.5）：验证极端负向失衡下总点差被 floor 归零而非变负。
- `test_Integration_PriceImpact_ZeroWhenDynamicSpreadNonPositive`（本模块 9.23）：验证动态点差非正值时价格冲击归零。
- `test_liqBoundary_E2_priceImpact_balanceImproving_close_noPenalty`（模块三 3.42）：验证清算区救援场景下，"改善平衡"方向本该拿折扣，但被 floor 封顶为 0。
- `test_Integration_Risk_Liquidation_LongClose_CapsWorstExecutionPrice` / `..._ShortClose_...`（模块三 3.74）：直接验证清算判定路径里价格冲击对平仓方向"恒为 0 或对交易者有利"，源码注释原文 `positive is capped to 0`。

**本次逐行代码核实、当前架构下的关键事实**（`src/pricing/PositionPricingUtils.sol`、`src/position/PositionUtils.sol:672-722`、`src/adl/AdlUtils.sol:134`）：

- 清算资格判定（`isPositionLiquidatable`）、清算执行、ADL 执行三者**复用同一套** `getDynamicSpread`/`getExecutionPriceForDecrease` 计算——ADL 内部创建的是 `Order.OrderType.MarketDecrease` 订单，走的是跟普通平仓完全相同的执行价路径，没有任何专门为清算/ADL 设计的分支。
- 仓库里已有 `FX100Keys.MAX_POSITION_IMPACT_FACTOR_FOR_LIQUIDATIONS` 这个 key 及 `MarketUtils.getMaxPositionImpactFactorForLiquidations`/`capPositiveImpactUsdByMaxPositionImpact`，但**从未在 `isPositionLiquidatable`/`getExecutionPriceForDecrease` 的实际定价路径中被调用**——只在几个测试的 `setUp`/独立单元测试里被赋值或单独调用过，是从 GMX fork 继承下来的死代码。
- 今天这一切"没事"，完全是因为 `dynamicSpread` 恒 `≥0`（floor 保证），清算/ADL 判定与执行只会让价格"更差或持平"，不可能出现"因为价格暂时更优而被误判为健康/少扣"的情况。

**测试覆盖的真实缺口（合约尚未修改，不是测试遗漏）**：团队已定案要把 floor 换成 Avantis 式"按市场/方向配置的可负上限"，`impl_spec_negative_dynamic_spread.md` 已给出落地方案，明确要求"判定抄 GMX（正向冲击永远砍成 0）、执行抄 Avantis（清算/ADL 执行价继续 floor-at-0、不给 rebate）"——**这两条新行为目前完全没有对应测试，因为对应的合约改动还没有实施**。建议合约工程师实现该改造后，至少补齐以下几类回归测试（可放在本模块或模块三新增小节，届时同步更新本文档）：

1. 清算/ADL 资格判定：正向 dynamicSpread 场景下，判定用的 `remainingCollateralUsd` 不应把正向 impact 计入，即不能因为这个"临时优惠"而被判定为暂时健康。
2. 清算/ADL 执行价：即使普通开平仓已允许负向 spread，清算/ADL 执行价仍必须锁定在 floor-at-0（不给 rebate）——这是防止未来重构不小心破坏该保护的关键回归测试。

4. 配置护栏：新增的正向上限被强制 `≤` 负向上限的某个比例，防止误配成过大的正向上限。

## 十一、Gasless（免 Gas 交易）与子账户委托

**基础数据**

- 子账户授权三要素（`SubaccountUtils`/`SubaccountApproval` 管理）：`maxAllowedCount`（操作次数上限，主账户自定，无默认值——未设置视为 0）、`expiresAt`（到期时间，**默认值为 0**，即未显式设置必然过期，对应 Bug B06）、`nonce`（每次消费一份新签名的 approval 后自增 1，防重放）
- Relay 中继费（USDC 计价）：base gas limit 由 `RELAY_FEE_BASE_GAS_LIMIT` 配置（测试中设 30,000）；倍率因子 `RELAY_FEE_MULTIPLIER_FACTOR`，默认回退 1×，测试用 1.5×（"15倍"业务表述实指 1.5 倍）；`maxFeeAmount` 由用户签名约定的上限（测试常用 100 USDC）
- Express/Gasless 执行费（B1，v0.3.0 激活）：非豁免订单的 WNT 执行费由 relayer 垫付给 `orderVault`，随 relay 费按当时 oracle 价折算成 USDC 从用户处收回；执行期多退部分以原生 ETH 直接退给用户；`MAX_RELAY_SWAP_WNT_CAP` 是 WNT 垫付总额硬上限，超限直接 revert
- 角色约定：`relayKeeper`（中继/Express 执行者）、`orderKeeper`（普通订单执行 keeper）、`trader`/`relayAccount`（主账户）、`subaccount`/`relaySubaccount`（被授权子账户）
- 子账户订单接收方（`receiver`/`cancellationReceiver`）必须等于主账户地址；`integrationId` 未配置默认放行，配置后若被标记禁用则拒绝；子账户自动补 Gas 金额默认 0，可由主账户设置

- **再看本文档对应模块**：判断"具体哪些数值场景测了、哪些数值场景还没测"，每行都标注了真实测试函数名，可直接去 [fx100-test-ledger.vercel.app](https://fx100-test-ledger.vercel.app/) 搜索核对代码。

**本轮补充函数名过程中发现并已按实际测试代码修正的事项**：模块二 2.8（82→83 USDC）、2.12（1050→1059.998 USDC）；模块十 10.1（改为"USDC 价格波动会影响抵押品美元估值"）、10.5（"最大值"/"最小值"两词互换）——均已直接改写对应行文字，以实际测试断言为准。仍保留在各模块"⚠️ 待人工核对"小节、尚待人工判断的事项：模块三部分行的测试组合覆盖（3.48-3.50）、模块八 8.4/8.22 是否应合并、模块十一 11.33-11.36 四条为 `vm.skip` 占位测试尚未真正验证（状态已标 ⚠️）。

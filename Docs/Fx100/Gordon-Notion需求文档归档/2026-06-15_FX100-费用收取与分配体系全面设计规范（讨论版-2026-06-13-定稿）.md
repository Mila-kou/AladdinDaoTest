## 〇、修订摘要（核心架构）
### 〇.1 2026-06-12 修订：Trader-LP 直接对赌
废除了协议金库参与交易盈亏结算的旧设计，确立：
1. **Trader-LP 直接对赌**：交易者盈亏直接与 LP Vault 结算（保持现有代码，无需修改）。平台协议不参与盈亏分成，也不承担盈亏风险。LP 承担全部交易对手风险，以手续费分成作为风险补偿——与 GMX 模型一致。
2. **协议费用三方分配**：开/平仓手续费（feeReceiverAmount 部分）、清算费（feeReceiverAmount 部分）、资金费率净额，归集后按**可配置比例**分配给三个去向。
随之废除的旧机制：`RevenuePool.pay()`（盈利优先支付）、`deposit()`（亏损分流）、`distributeToLP()`（盈余补偿 LP）、`MIN_REVENUE_POOL_BALANCE` 开仓 gate、`TRADING_LOSS_REVENUE_POOL_FACTOR`、epoch 末 LP 亏损补偿。
### 〇.2 2026-06-13 修订：复用 fx 既有合约实现三方分账（零核心合约改动）
费用三方分账**完全复用 fx 现有合约**，无需改 `FeeHandler`、`LPVault`，也无需新增 FX100Keys：
1. **分账器 = fx 现有 ****`RevenuePool.sol`**（AladdinDAO `PlatformFeeSpliter`）。将 `FEE_RECEIVER` 配成该分账器地址，`FeeHandler.withdrawFees` 把费用 100% 转入分账器（**无代码改动**），再由分账器 `claim()` 按 1e9 精度比例拆 4 槽：`staker` / `treasury` / `burners[token]`（locker 份额）/ `ecosystem`（取余数）。
2. **三个去向映射**（见 §四.2）：`staker`=运营 keeper（ratio 0，仅触发 `claim()`）、`treasury`=**协议收益库**、`burners[USDC]`=**保险基金**、`ecosystem`=**LP Vault**（取余数）。
3. **协议收益库 + 保险基金 = fx 现有 ****`ProtocolTreasury`**** 实例**（AccessControl + 白名单受限 `batchTransfer` + 权限化 `multicall`），资金只能转给白名单地址，纯手动支出。
4. **改名避歧义**：旧文档的"Revenue Pool"（费用累积池）与 fx 分账合约 `RevenuePool.sol` 撞名。本版起，累积池改称 **「协议收益库 / ProtocolRevenueTreasury」**，分账合约称 **「费用分账器 / RevenuePool 分账器（fx 现有）」**。
5. **跨链 veFXN 分配（P2）**：协议收益库收益可部分跨链回主网用于 veFXN 收益分配——白名单加 bridge 地址后手动操作即可，**上线后再开发**。

## 一、背景与费用体系概述
FX100 在 GMX v2 代码基础上深度改造，费用体系在以下维度与 GMX 存在根本差异：
1. **单 USDC 池架构**：所有费用最终以 USDC 计量，无多资产分池问题
2. **协议费用三方分配**：协议费用归集后经 fx 既有分账器按比例分给 协议收益库 / 保险基金 / LP
3. **无借贷费**：FX100 刻意移除 GMX 的借贷费（`BORROWING_FEE_RECEIVER_FACTOR` 为死代码）
4. **金库手工分配**：协议收益库 / 保险基金的对外支出由治理手工触发（白名单受限），无自动分发逻辑

## 三、费用类型详解
### 3.1 开/平仓手续费（Position Fee）
**计算公式**（`PositionPricingUtils.getPositionFees`）：
```plain text
positionFeeAmount = sizeDeltaUsd × POSITION_FEE_FACTOR / FLOAT_PRECISION
```
**分配逻辑**：
```plain text
positionFeeAmount
  ├── affiliateRewardAmount  ← 推荐人奖励（从总量中扣除）
  ├── uiFeeAmount            ← UI 手续费（从总量中扣除）
  └── remainingFeeAmount
        ├── feeReceiverAmount = remainingFeeAmount × POSITION_FEE_RECEIVER_FACTOR
        │     └── → 计入 claimableFeeAmount，经 FeeHandler 归集 → 分账器三方分配（§四）
        └── feeForPool = remainingFeeAmount - feeReceiverAmount
              └── → 留在 LP，归 LP 所有（LP 的第一层份额）
```
**LP 两层份额设计**：`feeForPool` 机制保持不变，是 LP 的第一层份额；`feeReceiverAmount` 进入分账器后 LP 还能拿到 `ecosystem` 余数槽的第二层份额（§四.2）。
**手续费费率结构设计决策（2026-06-15 本期）**：**先保留原 ****`positionFeeFactorKey(marketIndex, balanceWasImproved)`**** 两档模式，不改 key、不动 src**；上线时把两档参数配成相同值，用户视角即等价单一可预测费率。**（未来可选）**因 skew 激励已在动态点差（§3.3）体现，后续可简化为 `positionFeeFactorKey(marketIndex, isOpen)` 开/关仓两档，本期不实施。

### 3.2 资金费率（Funding Fee）
**性质**：FX100 资金费由**持仓方支付给协议侧**（与 GMX 纯多空对流不同）。多空双方各自按持仓时间累积资金费义务与权利，由 `updateFundingState` 周期性结算净额。
**计算公式**（`MarketUtils.sol:600-660`）：
```plain text
longFactor  = clamp(fundingFloorFactor + fundingBaseFactor × skew, min, max)
shortFactor = clamp(-fundingBaseFactor × skew, min, max)
positionPaysLp = longOI × longFactor × dt + shortOI × shortFactor × dt
              = floorFee × longOI × dt + baseFactor × skew × (longOI − shortOI) × dt
```
**净额恒非负（2026-06-12 确认）**：上式两项均 ≥ 0——floor 项恒正，skew 项是 `skew` 与 `(longOI − shortOI)` 同号相乘。因此 `positionPaysLp ≥ 0`，`MarketUtils.sol:531-535` 的 LP→持仓支付分支是**不可达的防御代码**，保留但不参与设计。
**目标资金流向（经分账器分配）**：资金净额**不再转给 LP Vault**，改为留在 PositionVault 并计入 `claimableFeeAmount`（与开/平仓手续费同一归集通道），随 `claimFees`/`withdrawFees` 流入分账器：
```solidity
if (result.positionPaysLp > 0) {
    // 资金已在 positionVault 内，仅做账面归集，无需 transfer
    FeeUtils.incrementClaimableFeeAmount(
        dataStore, eventEmitter, market.marketIndex,
        market.collateralToken, uint256(result.positionPaysLp)
    );
}
```
**当前实现状态**：❌ 净资金费直接进 LP Vault，应改为计入 claimableFeeAmount 经分账器分配（见 §七 BUG-F04）。

### 3.4 执行费（Execution Fee）
Keeper 执行订单的 gas 补偿。FX100 实现**条件性协议补贴**：`orderSize ≥ EXECUTION_FEE_SUBSIDIZE(marketIndex)` 阈值的大单及清算/ADL 由协议承担（executionFee=0），小单用户自付；Keeper 实际获得 `min(实际 gas × gasprice, executionFee)`，多余退还。**当前实现状态**：✅ 机制完整，仅需配置阈值（建议如 \$50,000）。
### 3.5 清算费（Liquidation Fee）
```plain text
liquidationFeeAmount = collateralAmount × LIQUIDATION_FEE_FACTOR
  ├── feeReceiverAmount = liquidationFeeAmount × LIQUIDATION_FEE_RECEIVER_FACTOR
  │     └── → 计入 claimableFeeAmount，经 FeeHandler 归集 → 分账器三方分配（§四）
  └── liquidatorAmount = liquidationFeeAmount - feeReceiverAmount
        └── → 转给清算人（Keeper）
```
清算费从保证金中扣除，不另收；剩余保证金全额退还用户。

### 3.6 UI 手续费（UI Fee）
协议允许前端运营方附加 UI 费，直接归运营方所有，不经过分账器或 LP。`uiFeeAmount` 追踪至 `claimableUiFeeAmount[uiFeeReceiver][token]`，运营方调 `FeeHandler.claimUiFees()` 提取。**当前实现状态**：✅ 完整实现。
### 3.7 推荐奖励（Affiliate Reward）
```plain text
affiliateRewardAmount = positionFeeAmount × referralCode.totalRebate
  ├── traderDiscount = affiliateRewardAmount × referralCode.discountShare → 返给交易者
  └── affiliateReward = affiliateRewardAmount - traderDiscount
        └── → affiliateRewardKey[affiliate][market][token]，Affiliate 调 claimAffiliateRewards() 提取
```
**权限模式缺口**：当前任意地址可注册推荐码（`registerCode` 无白名单）。设计要求 `permissionedMode`，治理白名单控制可注册地址（修复方案见 §七 BUG-F02）。**当前实现状态**：❌ 缺少权限模式（BUG-F02）。

## 四、交易者盈亏结算与协议费用三方分配
### 4.1 交易者盈亏：Trader-LP 直接对赌（保持现状）
**设计原则（2026-06-12 定稿）**：交易者盈亏直接与 LP Vault 结算，协议不参与分成、不承担风险。`DecreasePositionCollateralUtils.sol` 现有逻辑**即为目标行为，无需修改**：
```solidity
// 交易者亏损 → 100% 转入 LP Vault（~L210-214）—— by design
if (values.basePnlUsd + values.totalImpactUsd < 0) {
    params.contracts.positionVault.transferOut(
        cache.pnlToken, params.market.vault,
        collateralCache.result.amountPaidInCollateralToken
    );
}
// 交易者盈利 → 100% 由 LP Vault 支付 —— by design
```
**经济模型**：LP 承担交易对手盈亏波动，以两层手续费份额（feeForPool + 分账器 ecosystem 余数 share）作为风险补偿；保险基金（§4.3）作为极端事件的最后防线（手动）。LP 自身风险敞口由风控参数族（`MAX_PNL_FACTOR_*`、`RESERVE_FACTOR`，见 reserve-risk-control 规范）约束。
### 4.2 协议费用三方分配（复用 fx 既有分账器，零核心合约改动）
**最终架构（端到端资金流）**：
```plain text
开/平仓手续费 feeReceiverAmount ┐
清算费 feeReceiverAmount         ├─► claimableFeeAmount ─► FeeHandler.claimFees ─► availableFeeAmount
资金费净额 positionPaysLp(≥0)   ┘                                                       │
                                                                                       │ FeeHandler.withdrawFees
                                                                                       │ (现有逻辑, 100%)
                                                                                       ▼
                                                              FEE_RECEIVER = fx RevenuePool 分账器
                                                                                       │ keeper 调 claim()
                            ┌──────────────────────────┬───────────────────────────────┼───────────────────────────┐
                            ▼                           ▼                               ▼                           ▼
                      staker (keeper)            treasury 槽                     burners[USDC] 槽            ecosystem 槽
                      stakerRatio = 0            treasuryRatio (~40%)            lockerRatio (~20%)          余数 (~40%)
                      仅触发, 不收款                    │                               │                           │
                                                       ▼                               ▼                           ▼
                                                  协议收益库                        保险基金                     LP Vault
                                              ProtocolTreasury                  ProtocolTreasury           (即时抬升 NAV)
                                              (白名单手动支出)                  (白名单手动支出)
                                                       │
                                                       └─► P2: 跨链回主网 ─► veFXN 收益分配 (手动)

交易者盈亏 ─────────────────────────► LP Vault  (Trader-LP 直接对赌, 不经任何金库)
```
**进入分账器的三类费用**：① 开/平仓手续费的 `feeReceiverAmount`（§3.1）；② 清算费的 `feeReceiverAmount`（§3.5）；③ 资金费率净额 `positionPaysLp`（§3.2，恒 ≥ 0）。三者经现有 `claimableFeeAmount` 通道归集，`FeeHandler.withdrawFees` 把 `availableFeeAmount` 100% 转给 `FEE_RECEIVER`（现有逻辑，无代码改动）。只需令 `FEE_RECEIVER = 费用分账器地址`。
**费用分账器 = fx 现有 ****`RevenuePool.sol`**（`fx-protocol-contracts/contracts/helpers/RevenuePool.sol`，AladdinDAO `PlatformFeeSpliter`）。其 `claim()` 读取自身 token 余额，按 1e9 精度的 `stakerRatio/treasuryRatio/lockerRatio` 拆分，`ecosystem` 拿余数。普通 `safeTransfer` 进来的余额即可被 `claim()` 读取（`balanceOf`），无需 `depositReward`。

## 五、FeeHandler 与费用领取流程
### 5.1 目标流程
```plain text
FX100 合约内累积的协议费用（feeReceiverAmount + 清算费 receiver 部分 + 资金费净额）
  └── claimableFeeAmount[marketIndex][token]（账面归集，资金在 PositionVault）

FeeHandler.claimFees(marketIndex, feeToken)         ← 现有，不变
  └── PositionVault → FeeHandler，availableFeeAmount += feeAmount

FeeHandler.withdrawFees(feeToken)                   ← 现有，不变
  └── safeTransfer(feeToken, FEE_RECEIVER = 费用分账器, amount)   全额转入分账器

费用分账器.claim()                                   ← fx 既有 RevenuePool.sol，keeper 触发
  ├── treasuryRatio → 协议收益库
  ├── lockerRatio   → 保险基金（burner）
  └── 余数          → LP Vault（即时抬升 NAV）
```

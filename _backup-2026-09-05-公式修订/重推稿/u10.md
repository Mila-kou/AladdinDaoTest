## 15. Relay Fee

Relay Fee 是 gasless（代付）路径独有的费用：relayer（交易的 `msg.sender`）先垫付本笔交易的链上 gas 与订单执行费，再在同一笔交易的末尾从**主账户 `account`** 划走等值的 collateral token 作为补偿。它**不进 FeeHandler / 分账器，不进 LP Vault，也不计入仓位的 `totalCostAmount`**，与第 7 节仓位费用、第 14 节执行费属于互不相干的三本账。

所有 Relay 入口（`RelayRouter.sol` 的 `batch/createOrder/updateOrder/cancelOrder`，`SubaccountRelayRouter.sol` 的同名函数加 `removeSubaccount/removeSlot`）都带同一个修饰器：

```text
BaseRelayRouter.sol::withRelay(relayParams, account)

1. startingGas = gasleft()
2. FeatureUtils.validateFeature(GASLESS_FEATURE_DISABLED[address(this)])   // 开关关闭则整笔回滚
3. _handleTokenPermits(account, relayParams.tokenPermits)                  // owner/spender 不符即回滚；
                                                                           // 只有 permit() 调用失败被 try/catch 吞掉
4. relayExecutionFee = 0                                                   // 累加器清零，见 15.2
5. <函数体>：_validateCall(...) + 业务动作（期间可能累加 relayExecutionFee）
6. _payRelayFee(account, relayParams.fee, startingGas)
```

要点：

- **付款方恒为主账户 `account`**（`_payRelayFee` 的第一个参数），即使在子账户路径下签名者是 `subaccount`（`SubaccountRelayRouter.sol::createOrder` 用 `_validateCall(relayParams, subaccount, ...)` 校验签名，但 `withRelay(relayParams, account)` 收费）。
- **收款方恒为 `msg.sender`**（relayer 自己），`_payRelayFee` 里 `_sendTokens(account, fee.feeToken, msg.sender, feeAmount)`。
- 划款走 `Router.pluginTransfer`，因此主账户必须先对 `Router` 授权 collateral token，额度不足直接回滚。
- `_handleTokenPermits` 里的 `IERC20Permit.permit` 被 `try/catch {}` 包住：**permit 失败不会回滚**，只会在后续 `pluginTransfer` 处因授权不足失败。测试不能用"交易没 revert"证明 permit 生效。

### 15.1 Calldata Gas

源码锚点：`BaseRelayRouter.sol::_getCalldataGas`

```text
calldataLength > 50000  →  revert RelayCalldataTooLong（= 50000 不回滚，> 才回滚）

txCalldataGasUsed = calldataLength × 10

memoryWords = floor((calldataLength + 31) / 32)      // 即 ceil(calldataLength / 32)

callMemoryGasUsed
= floor(memoryWords² / 512) + memoryWords × 3         // 平方项是整数除法，向下取整

calldataGas
= txCalldataGasUsed + callMemoryGasUsed
```

`calldataLength` 取的是 `msg.data.length`（本次 relay 外部调用的完整 calldata，含 4 字节 selector），在 `_payRelayFee` 内取值，与 relayer 实际支付的 L1/L2 calldata 成本只是近似关系，不是精确报销。

### 15.2 Relay Gas 与原生币费用

源码锚点：`BaseRelayRouter.sol::_payRelayFee`

**第一分支是免收**（v0.3.1 与 v0.3.2 都有，旧版文档漏写）：

```text
if (DataStore.getBool(isRelayFeeExcludedKey(msg.sender)))  →  直接 return
```

- key 为 `keccak256(abi.encode(IS_RELAY_FEE_EXCLUDED, sender))`（`FX100Keys.sol::isRelayFeeExcludedKey`），**按 relayer 地址（`msg.sender`）登记，不是按用户账户**。
- 命中免收时：不扣款、**不发 `RelayFeePaid` 事件**、不做 feeToken / cap / maxFeeAmount 任何校验。测试要区分"免收"和"费用算出来是 0"（后者仍会发一条 `feeAmount=0` 的事件，见下）。

未免收时：

```text
gasUsed = startingGas - gasleft()          // 不含本函数自身与 tx 基础 21000 gas

relayGasLimit
= gasUsed
+ DataStore.getUint(RELAY_FEE_BASE_GAS_LIMIT)
+ calldataGas                              // 见 15.1

relayFeeMultiplierFactor = DataStore.getUint(RELAY_FEE_MULTIPLIER_FACTOR)
若为 0 则按 Precision.FLOAT_PRECISION = 1e30 处理（即倍数 1.0）

nativeFee
= ceil( relayGasLimit × tx.gasprice × relayFeeMultiplierFactor / 1e30 )
+ relayExecutionFee
```

取整方向：**向上取整只作用于乘子那一项**（`Math.mulDiv(relayGasLimit * tx.gasprice, factor, 1e30, Math.Rounding.Ceil)`），`relayExecutionFee` 是整数直接相加，不参与该次取整。

**`relayExecutionFee` 是本次 relay 调用内 relayer 垫付的订单执行费累加器，不是任何固定配置项**（它随本次 relay/batch 实际代付的执行费变化，不能当常量代入期望值）：

| 项 | 事实 | 锚点 |
| --- | --- | --- |
| 存储位置 | `BaseRelayRouter` 的 `uint256 private relayExecutionFee` | `BaseRelayRouter.sol:38` |
| 生命周期 | 每次进入 `withRelay` 先置 0，函数体内累加，`_payRelayFee` 读取 | `BaseRelayRouter.sol::withRelay` |
| 累加点 1 | 创建订单且未被执行费补贴且 `executionFee != 0` | `BaseRelayRouter.sol::_createOrder` |
| 累加点 2 | 更新订单且未被执行费补贴且 `executionFeeIncrease != 0` | `BaseRelayRouter.sol::_updateOrder` |
| 累加动作 | `router.pluginTransfer(WNT, msg.sender → orderVault, amount)` 后 `relayExecutionFee += amount` | `BaseRelayRouter.sol::_sendExecutionFeeFromRelayer` |
| batch | `_batch` 里逐条 create / update 累加，取消订单不累加 | `BaseRelayRouter.sol::_batch` |
| 恒为 0 的路径 | 纯 `cancelOrder`、`removeSubaccount`、`removeSlot`；以及所有订单都命中执行费补贴时 | 同上 |

执行费补贴判定（`GasUtils.sol::isExecutionFeeSubsidizedAtCreation`）：按 `isSizeDeltaUsd` 取 `executionFeeSubsidizeKey(marketIndex)` 或 `executionFeeSubsidizeSizeKey(marketIndex)`；阈值 `== type(uint256).max` 表示关闭补贴，否则 `sizeDelta >= 阈值` 即补贴。**阈值未配置时读出 0，`sizeDelta >= 0` 恒真 → 全部订单被补贴、`executionFee` 被强制置 0、relayer 不垫付**，此时 `relayExecutionFee = 0`。这是 fork 环境最常见的"nativeFee 只剩 gas 项"的原因。

WNT 地址是编译期常量 `Addresses.WNT = 0x4200...0006`，relayer 必须持有 WNT 且已对 `Router` 授权，否则 `_sendExecutionFeeFromRelayer` 回滚。

### 15.3 支付 Token 数量

源码锚点：`BaseRelayRouter.sol::_payRelayFee`（续）

先做上限与零值分支：

```text
maxRelaySwapWntCap = DataStore.getUint(MAX_RELAY_SWAP_WNT_CAP)
if (maxRelaySwapWntCap != 0 && nativeFee > maxRelaySwapWntCap)
    → revert MaxRelaySwapWntCapExceeded(nativeFee, maxRelaySwapWntCap)
    // 配置为 0 表示不限制；判定用严格大于，等于上限放行

if (nativeFee == 0)
    → emit RelayFeePaid(account, msg.sender, fee.feeToken, 0, gasUsed); return
    // 不读价、不扣款，但事件仍然发出
```

再换算成 fee token 数量：

```text
nativeTokenPrice = oracle.getSecondaryPrice(Addresses.WNT, false)
feeTokenPrice    = oracle.getSecondaryPrice(fee.feeToken,  false)

feeAmount
= ceil( nativeFee × nativeTokenPrice.max / feeTokenPrice.min )

if (feeAmount > fee.maxFeeAmount) → revert InsufficientRelayFee(feeAmount, fee.maxFeeAmount)
if (feeAmount != 0) → Router.pluginTransfer(feeToken, account → msg.sender, feeAmount)
emit RelayFeePaid(account, msg.sender, feeToken, feeAmount, gasUsed)
```

**两个价格都来自 `oracle.getSecondaryPrice(token, false)`，不是本笔交易签名报文里的主签名价 `getPrimaryPrice`**（`Oracle.sol::getSecondaryPrice` / `_getSecondaryPrice`）。原因是 Relay 入口不带 `withOraclePrices` 修饰器，`_payRelayFee` 执行时 `primaryPrices` 是空的，读主价会 `EmptyPrimaryPrice` 回滚。`getSecondaryPrice` 的三条分支必须逐条核：

| 分支 | 条件 | 返回 / 回滚 |
| --- | --- | --- |
| 零地址 | `token == address(0)` | 返回 `Price(0, 0)`（min=max=0） |
| Chainlink 价源 | `priceFeedKey(token)` 已配置 | 返回 `Price(p, p)`，**min == max**，此处 `.max/.min` 的选价差异消失；内部还会校验 `_price > 0` 与 `heartbeatDuration` 过期（`ChainlinkPriceFeedUtils.sol::getPriceFeedPrice`） |
| 历史签名价 | 无 Chainlink 价源 | 取 `latestRecordedPrices[token]`（上一次 `setPrices` 落下的 min/max）；为空 → `EmptySecondaryPrice`；`isADLStart=false` 且 `timestamp + MAX_RECORDED_PRICE_AGE < block.timestamp` → `MaxPriceAgeExceeded` |

陷阱：`MAX_RECORDED_PRICE_AGE` 未配置时读出 0，历史价分支几乎必然命中 `MaxPriceAgeExceeded`，表现为"gasless 下单一律失败"。这是环境配置问题，不是公式问题。

选价侧配对（两侧都对 relayer 有利、对用户保守）：

| 位置 | 选价侧 | 方向含义 |
| --- | --- | --- |
| `nativeTokenPrice.max` | 分子 | WNT 估得更贵 → 用户多付 |
| `feeTokenPrice.min` | 分母 | fee token 估得更贱 → 用户多付 |
| 最终 `feeAmount` | `Math.Rounding.Ceil` | 余数归 relayer |

精度标度：Price 的量纲是"1 个最小单位 token 的 USD 值 × 1e30"，即 `1e30 / 10^decimals`（`ChainlinkPriceFeedUtils.sol::getPriceFeedMultiplier` 注释给出该定义）。因此 `nativeFee`(wei, 1e18) × `WNT 价`(1e12 标度) / `USDC 价`(1e24 标度) 的结果自然落在 USDC 的 1e6 原生精度上，无需额外换算因子。

### 15.4 前置校验、免收分支与回滚清单

`_payRelayFee` 之前，函数体里的 `_validateCall`（`BaseRelayRouter.sol::_validateCall`）按顺序做四组校验：

```text
1. relayParams.desChainId != block.chainid   → revert InvalidDestinationChainId
2. block.timestamp > relayParams.deadline    → revert DeadlinePassed
3. collateralToken = DataStore.getAddress(COLLATERAL_TOKEN)
   collateralToken == address(0)             → revert EmptyToken
   relayParams.fee.feeToken != collateralToken
                                             → revert UnexpectedRelayFeeToken(feeToken, expected)
4. digest = getDigest(structHash)
   digests[digest] 已为 true                 → revert InvalidUserDigest（一次性 digest 防重放）
   RelayUtils.validateSignature(digest, signature, expectedSigner, "call")
```

第 3 组是 **v0.3.2 新增**（v0.3.1 没有这段，客户端可任选 fee token）：`COLLATERAL_TOKEN` 是全局单值配置，未设置或请求用其他 token 都在扣款前回滚，用户不会被扣款。

签名校验有**两段**（`RelayUtils.sol::validateSignature`）：先按 `digest` 直接 `ECDSA.tryRecover`；恢复出的地址不等于期望签名者时，再按 `Minified(bytes32 digest)` 包一层重算 `minifiedDigest` 二次恢复，仍不匹配才 `revert InvalidRecoveredSigner`。测试构造"错误签名"用例时要注意这条兜底路径的存在。

`relayParams.userNonce` 参与 struct hash（`RelayUtils.sol::_getRelayParamsHash`）但**链上没有对应的 nonce 存储与自增**，防重放完全依赖 `digests[digest]` 这张一次性表。相同参数第二次提交会命中 `InvalidUserDigest`；改 `userNonce` 即可得到新 digest。

费用相关的全部回滚点：

| 触发条件 | 错误 | 锚点 | 是否已扣款 |
| --- | --- | --- | --- |
| gasless 功能开关关闭 | `DisabledFeature` | `withRelay` | 否 |
| `tokenPermits[i].owner != account` | `Unauthorized(owner, "permit owner")` | `_handleTokenPermits` | 否 |
| `tokenPermits[i].spender != address(router)` | `InvalidPermitSpender` | `_handleTokenPermits` | 否 |
| `msg.data.length > 50000` | `RelayCalldataTooLong` | `_getCalldataGas` | 否 |
| `fee.feeToken != COLLATERAL_TOKEN` / `COLLATERAL_TOKEN` 未配置 | `UnexpectedRelayFeeToken` / `EmptyToken` | `_validateCall` | 否 |
| `fee.feeToken == address(0)`（免收分支未命中时的兜底） | `EmptyToken` | `_payRelayFee` | 否 |
| `nativeFee > MAX_RELAY_SWAP_WNT_CAP`（cap ≠ 0） | `MaxRelaySwapWntCapExceeded` | `_payRelayFee` | 否 |
| 二级价缺失 / 过期 | `EmptySecondaryPrice` / `MaxPriceAgeExceeded` / `ChainlinkPriceFeedNotUpdated` | `Oracle::_getSecondaryPrice` | 否 |
| `feeAmount > fee.maxFeeAmount` | `InsufficientRelayFee` | `_payRelayFee` | 否 |
| 主账户 collateral 授权/余额不足 | ERC20 transferFrom 失败 | `Router.pluginTransfer` | 否 |
| batch 三个列表全空 | `RelayEmptyBatch` | `_batch` | 否 |

全部回滚都发生在整笔交易内，因此"回滚 = 用户零扣款"成立；但 relayer 已实际消耗的链上 gas 无法回收，这是 relayer 侧风险，不体现在任何合约字段里。

### 15.5 数值示例

配置：`RELAY_FEE_BASE_GAS_LIMIT = 100000`，`RELAY_FEE_MULTIPLIER_FACTOR = 1.2e30`，`tx.gasprice = 1 gwei = 1e9`，`msg.data.length = 1000`，函数体实测 `gasUsed = 400000`，本次 relay 创建了 1 条未被补贴的订单、`executionFee = 1e14 wei`。WNT 报价 3000 USD（价值 `3000 × 1e30 / 1e18 = 3e15`），fee token 为 6 位精度的 USDC，报价 1 USD（价值 `1 × 1e30 / 1e6 = 1e24`）。

```text
memoryWords        = floor((1000 + 31) / 32) = 32
callMemoryGasUsed  = floor(32² / 512) + 32 × 3 = 2 + 96 = 98
calldataGas        = 1000 × 10 + 98 = 10098

relayGasLimit      = 400000 + 100000 + 10098 = 510098

乘子项             = ceil(510098 × 1e9 × 1.2e30 / 1e30)
                   = ceil(5.10098e14 × 1.2) = 612117600000000 wei
relayExecutionFee  = 1e14 = 100000000000000 wei
nativeFee          = 612117600000000 + 100000000000000 = 712117600000000 wei ≈ 0.0007121176 WNT

feeAmount          = ceil(712117600000000 × 3e15 / 1e24)
                   = ceil(2.1363528e30 / 1e24) = 2136353 (向上取整，原值 2136352.8)
                   = 2.136353 USDC
```

校验：`0.0007121176 WNT × 3000 USD ≈ 2.1363528 USD`，与 `2.136353 USDC` 一致（差额为向上取整的 1 个最小单位）。若 `fee.maxFeeAmount < 2136353` 则整笔回滚 `InsufficientRelayFee`。

## 16. 下单与订单字段字典

### 16.1 Order 原始字段

**存储字段**（`Order.sol::Props` = `Addresses` + `Numbers` + `Flags` + `_dataList`；落库 key 见 `OrderStoreUtils.sol` 的常量表）：

| 字段 | 单位 / 类型 | 含义与计算规则 |
| --- | --- | --- |
| `account` | address | 订单和目标仓位归属账户；子账户下单时仍写主账户 |
| `receiver` | address | 减仓输出 token 的接收地址；创建时 `AccountUtils.validateReceiver` 禁止零地址 |
| `cancellationReceiver` | address | 取消时的退款地址；**等于 OrderVault 地址会 revert `InvalidReceiver`**；零地址时两类退款回退目标不同，见 16.5 |
| `callbackContract` | address | 订单完成后的回调合约 |
| `uiFeeReceiver` | address | UI Fee 接收方；零地址表示不收 |
| `marketIndex` | uint256 | 市场标识；创建时过 `MarketUtils.validatePositionMarket` |
| `orderType` | enum | 见下方枚举值表，**不要按名称顺序猜数值** |
| `sizeDelta` | USD(1e30) 或 index token(1e18) | 由 `isSizeDeltaUsd` 决定，不能仅凭数值猜单位 |
| `initialCollateralDeltaAmount` | collateral token 原生精度 | **加仓时落库的是 `orderVault.recordTransferIn(market.collateralToken)` 的实收量，不是 `CreateOrderParams` 的同名入参**；减仓时才直接取入参。"入参被丢弃"只对 `ExchangeRouter` 直连路径成立（该路径靠 multicall 里的 `sendTokens` 决定转入量）；`BaseRelayRouter._createOrder` 与 `SubaccountRouter.createOrder` 都用该入参决定 `pluginTransfer` 进 OrderVault 的数量，实收量因而恰好等于入参——gasless / 子账户加仓单不能把它填 0 |
| `triggerPrice` | contract price (1e30/10^dec) | 非市价单触发价；市价单与清算单不校验 |
| `acceptablePrice` | contract price | 成交价保护边界 |
| `executionFee` | WNT (1e18) | Keeper 预算；不属于仓位保证金；创建时被 WNT 实收量覆盖，再过 `validateAndCapExecutionFee`（只有子账户带回调路径才真夹紧，见下） |
| `callbackGasLimit` | gas | 回调预算；过 `CallbackUtils.validateCallbackGasLimit` |
| `minOutputAmount` | **USD (1e30)** | 仅减仓路径生效，比较对象是 `outputAmount × primaryPrice(outputToken).min`；不足 → `revert InsufficientOutputAmount(outputUsd, minOutputAmount)`（`DecreaseOrderUtils.sol::_validateOutputAmount`，源码注释原文即“treated as a USD value”） |
| `updatedAtTime` | unix seconds | 创建与每次 `updateOrder` 时 `order.touch()` 写入 `block.timestamp` |
| `validFromTime` | unix seconds | 非市价单最早可执行时间；**市价单传非 0 直接 revert `UnexpectedValidFromTime`** |
| `isLong` | bool | 仓位方向，不等同于"买 / 卖按钮文字" |
| `isFrozen` | bool | 冻结订单仍存在，资金不可按已取消处理；冻结时 `executionFee` 被清零 |
| `autoCancel` | bool | 见 16.7；只对 LimitDecrease / StopLossDecrease 有实际效果 |
| `isSizeDeltaUsd` | bool | `sizeDelta` 的单位选择 |
| `_dataList` | bytes32[] | 附加数据；长度受 `MAX_DATA_LENGTH` 限制（`BaseHandler.sol::validateDataListLength`） |

**仅创建期入参、不落库的字段**（`IBaseOrderUtils.sol::CreateOrderParams`）：

| 字段 | 去向 |
| --- | --- |
| `referralCode` | 传给 `ReferralUtils.setTraderReferralCode`，写进 ReferralStorage，不进 Order |
| `numbers.executionFee` | 入参值本身不落库：未补贴分支先用它做下限校验（`wntAmount < 入参` → `revert InsufficientWntAmountForExecutionFee`），随即被 WNT 实收量覆盖再进封顶判定；落库的是覆盖后的值 |

`orderType` 枚举取值（`Order.sol::OrderType`，v0.3.1 与 v0.3.2 完全相同）：

| 值 | 名称 | isIncrease | isDecrease | isMarket | 可否 createOrder |
| --- | --- | --- | --- | --- | --- |
| 0 | `MarketIncrease` | ✓ | | ✓ | ✓ |
| 1 | `LimitIncrease` | ✓ | | | ✓ |
| 2 | `MarketDecrease` | | ✓ | ✓ | ✓ |
| 3 | `LimitDecrease` | | ✓ | | ✓ |
| 4 | `StopLossDecrease` | | ✓ | | ✓ |
| 5 | `Liquidation` | | ✓ | | ✗ `OrderTypeCannotBeCreated` |
| 6 | `StopIncrease` | ✓ | | | ✓ |

注意：`StopIncrease = 6` 排在最后（属于后追加的枚举项），**不是** "Market/Limit/Stop × Increase/Decrease" 的直觉排序；`Liquidation` 不是市价单（`Order.sol::isMarketOrder` 注释明说），但属于减仓单。按 `orderType` 索引的 DataStore 开关（`createOrderFeatureDisabledKey` / `executeOrderFeatureDisabledKey` / `updateOrderFeatureDisabledKey` / `cancelOrderFeatureDisabledKey`）都用这些数值拼 key，写错数值会打开/关闭错误的类型。

`executionFee` 的创建期实际赋值链（`OrderUtils.sol::createOrder`）：

```text
wntAmount = orderVault.recordTransferIn(WNT)
subsidized = GasUtils.isExecutionFeeSubsidizedAtCreation(marketIndex, sizeDelta, isSizeDeltaUsd)

若 subsidized:
    order.executionFee = 0
    wntAmount != 0 → 全额退回 order.receiver()
否则:
    wntAmount < params.numbers.executionFee → revert InsufficientWntAmountForExecutionFee
    params.numbers.executionFee = wntAmount                       // 入参被实收量覆盖
    (executionFee, diff) = GasUtils.validateAndCapExecutionFee(..., shouldCapMaxExecutionFee)
    order.executionFee = executionFee
    diff != 0 → GasUtils.transferExcessiveExecutionFee(...)
```

`shouldCapMaxExecutionFee` 是 `createOrder` / `updateOrder` 的最后一个入参，由路由决定。v0.3.2 一共六个调用点：

| 路由 | createOrder | updateOrder | 锚点 |
| --- | --- | --- | --- |
| `ExchangeRouter`（直连） | `false` | `false` | `ExchangeRouter.sol::createOrder` / `::updateOrder` |
| `BaseRelayRouter`（`RelayRouter` / `SubaccountRelayRouter` 共用） | `false` | `false` | `BaseRelayRouter.sol::_createOrder` / `::_updateOrder` |
| `SubaccountRouter`（子账户直连） | `params.addresses.callbackContract != address(0)` | `order.callbackContract() != address(0)` | `SubaccountRouter.sol::createOrder` / `::updateOrder` |

因此非子账户路径恒不封顶：`validateAndCapExecutionFee` 做完下限校验就原样返回、`diff` 恒为 0。**唯一会启用第 14.3 节封顶分支的路径是 `SubaccountRouter` 且订单带非零 `callbackContract`**（`GasUtils.sol::validateAndCapExecutionFee` 的源码注释明写该封顶是防"恶意子账户填巨额执行费、再把退款打到自己的 callbackContract"）。命中封顶时：

```text
basefee        = block.basefee != 0 ? block.basefee : tx.gasprice
maxExecutionFee = applyFactor(gasLimit × basefee, MAX_EXECUTION_FEE_MULTIPLIER_FACTOR)

maxExecutionFee < minExecutionFee  → revert InvalidExecutionFee(executionFee, min, max)
executionFee <= maxExecutionFee    → (executionFee, diff = 0)
否则                                → (maxExecutionFee, diff = executionFee - maxExecutionFee)
                                      diff 经 GasUtils.transferExcessiveExecutionFee 从 OrderVault
                                      transferOut 到 HOLDING_ADDRESS，并
                                      emit ExcessiveExecutionFee(topic1 = order.account(),
                                                                 data = {account, executionFeeDiff})
                                      HOLDING_ADDRESS 未配置 → revert EmptyHoldingAddress
```

该封顶**不是不可达代码**：`SubaccountRouter` 在 v0.3.2 已实际部署（`ignition/deployments/tx-fork-v032-260902r4/deployed_addresses.json` 的 `Fx100Execution#SubaccountRouter`），"多余执行费转入 `HOLDING_ADDRESS` 并 emit `ExcessiveExecutionFee`"必须作为可测路径覆盖，构造条件是走 `SubaccountRouter` 且 `callbackContract != 0`。

创建期还有一条非空校验（`BaseOrderUtils.sol::validateNonEmptyOrder`）：`sizeDelta == 0 && initialCollateralDeltaAmount == 0` → `revert EmptyOrder`。所以"纯加保证金不改 size"是允许的，"两者都为 0"不允许。

### 16.2 Pay、Margin、Size 与 Leverage

前端根据用户输入生成订单，但合约不会从"杠杆倍数"反推订单规模；合约接收的是已经确定的 `sizeDelta` 和抵押品数量。以下三条是前端派生（T2），合约里没有对应字段：

```text
inputMarginToken = 用户输入的 collateral token 数量

inputMarginUsd
= inputMarginToken × collateralPrice.min

targetSizeDeltaUsd
= inputMarginUsd × targetLeverage
```

开仓实际入仓的保证金必须扣除费用并结算已有仓位 Funding（源码锚点：`IncreasePositionUtils.sol::processCollateral` 与 `IncreasePositionUtils.sol::increasePosition`）：

```text
collateralDeltaAmount                       // 起点 = order.initialCollateralDeltaAmount（OrderVault 实收量）
    -= fees.totalCostAmount
    += fees.funding.positiveFundingFeeAmount

storedCollateralTokenAfterOpen
= oldCollateralToken + collateralDeltaAmount
= oldCollateralToken
+ inputMarginToken
- totalCostAmount
+ positiveFundingFeeAmount

storedCollateralUsd
= storedCollateralTokenAfterOpen × collateralPrice.min
```

分支补全（旧版文档漏写）：`collateralDeltaAmount < 0 且 |collateralDeltaAmount| > position.collateralAmount` 时 **revert `InsufficientCollateralAmount`**，仓位不会被扣成负数；这是"费用吃光加仓保证金"的失败路径。

v0.3.2 变化：`processCollateral` 里新增了 `MarketUtils.settleFundingFees(positionVault, dataStore, eventEmitter, market, negativeFundingFeeAmount, positiveFundingFeeAmount)`，即 Funding 的 LP 侧现金流改在**仓位结算时**按该仓净差执行（详见第 10 节）。上面这条抵押品公式本身在两个版本一致，但它旁边的 LP 账本口径变了，跨版本抄用例时要分开对待。

因此：

- `inputMargin` 是用户提交值；
- `storedCollateral` 是链上仓位最终值；
- `effectiveMargin` 是计算当前风险时进一步计入待结算 Funding 的值；
- 三者不能在页面或测试报告中都写成"Margin"而不标明口径。

### 16.3 触发条件

源码锚点：`BaseOrderUtils.sol::validateOrderTriggerPrice`，执行期由 `ExecuteOrderUtils.sol::executeOrder` 调用。

早退分支：`Order.isMarketOrder(orderType) || Order.isLiquidationOrder(orderType)` 直接 `return`，**市价单与清算单完全不校验 `triggerPrice`**（哪怕字段里写了值）。

价格来源是 `oracle.getPrimaryPrice(market.indexToken)`（本笔交易报文里的签名价），不是 15.3 用的二级价。

| 订单 | Long | Short |
| --- | --- | --- |
| LimitIncrease | `primaryPrice.max <= triggerPrice` | `primaryPrice.min >= triggerPrice` |
| StopIncrease | `primaryPrice.max >= triggerPrice` | `primaryPrice.min <= triggerPrice` |
| LimitDecrease / TP | `primaryPrice.min >= triggerPrice` | `primaryPrice.max <= triggerPrice` |
| StopLossDecrease | `primaryPrice.min <= triggerPrice` | `primaryPrice.max >= triggerPrice` |

规律：**增仓单一律用 `max`（Long）/ `min`（Short）；减仓单一律用 `min`（Long）/ `max`（Short）**；每一侧取的都是对协议保守的那一端。不满足条件 → `revert InvalidOrderPrices(min, max, triggerPrice, orderType)`；落到四类之外的 `orderType` → `revert UnsupportedOrderType`。

同一函数之后还有一条独立校验（`BaseOrderUtils.sol::validateOrderValidFromTime`）：市价单早退；非市价单 `validFromTime > block.timestamp` → `revert OrderValidFromTimeNotReached`。

`InvalidOrderPrices` 与 `OrderValidFromTimeNotReached` 都在 `OrderHandler.sol::_handleOrderError` 的"原样抛出"名单里：**不会导致订单被取消或冻结**，keeper 的交易直接回滚，订单保持 Pending。

触发价只决定"现在是否允许执行"，不等于最终成交价。成交仍要经过动态点差、价格边界和 `acceptablePrice` 校验。

### 16.4 Acceptable Price

源码锚点：`BaseOrderUtils.sol::getExecutionPriceForIncrease` / `getExecutionPriceForDecrease`。传入的 `executionPrice` 已含动态点差（第 4 节），校验通过则原样返回该价作为成交价。

| 操作 | 合约通过条件 | 字段语义 |
| --- | --- | --- |
| 开多 | `executionPrice <= acceptablePrice` | 用户允许的最高成交价 |
| 开空 | `executionPrice >= acceptablePrice` | 用户允许的最低成交价 |
| 平多 | `executionPrice >= acceptablePrice` | 用户允许的最低成交价 |
| 平空 | `executionPrice <= acceptablePrice` | 用户允许的最高成交价 |

不通过时 `revert OrderNotFulfillableAtAcceptablePrice(executionPrice, acceptablePrice)`。该错误**不在** `_handleOrderError` 的原样抛出名单里，因此：市价单 → 被取消并退款；非市价单 → 被**冻结**（`OrderUtils.sol::freezeOrder`，`isFrozen = true`、`executionFee` 清零、抵押品仍锁在 OrderVault），之后只有持 `FROZEN_ORDER_KEEPER` 角色的 keeper 能再执行（`OrderHandler.sol::_validateFrozenOrderKeeper`）。

市价预览可按以下方式生成边界（**前端派生，合约里没有这段逻辑**；fx100-apps 侧的具体实现未核实）：

```text
开多 / 平空：acceptablePrice = referenceExecutionPrice × (1 + slippage)
开空 / 平多：acceptablePrice = referenceExecutionPrice × (1 - slippage)
```

触发单（LimitIncrease / StopIncrease / LimitDecrease / StopLossDecrease）在需求侧恒把 `acceptablePrice` 设成方向哨兵值并隐藏滑点输入，语义是"接受任何市价"（来源：`Docs/V0.3.1/需求文档/2026-07-02_fx100-trading-guide.zh.md` §4.3）。哨兵取的是被比较方向上的开放端，与本节开头的四象限表一一对应：

| 触发单 | 方向 | 哨兵值 | 对应通过条件 |
| --- | --- | --- | --- |
| 开仓（LimitIncrease / StopIncrease） | Long | `type(uint256).max` | `executionPrice <= acceptablePrice` |
| 开仓（LimitIncrease / StopIncrease） | Short | `0` | `executionPrice >= acceptablePrice` |
| 平仓（LimitDecrease / StopLossDecrease） | Long | `0` | `executionPrice >= acceptablePrice` |
| 平仓（LimitDecrease / StopLossDecrease） | Short | `type(uint256).max` | `executionPrice <= acceptablePrice` |

合约对哨兵值没有任何特殊分支，仍按四象限逐条比较；方向写反（例如给开多单写 0）会让任何正的执行价都过不了，必然 `revert OrderNotFulfillableAtAcceptablePrice`，非市价单据此被冻结。测试必须读取链上实际 `acceptablePrice` 字段，不能只按 UI 假设哨兵已正确写入。

### 16.5 订单列表派生字段

| 页面字段 | 计算 | 说明 |
| --- | --- | --- |
| Size (USD) | `isSizeDeltaUsd == true` 时 `order.sizeDelta / 1e30` | **订单里没有 `sizeDeltaInTokens` 字段**，`OrderStoreUtils` 只存 `SIZE_DELTA` + `IS_SIZE_DELTA_USD` |
| Token Size | `isSizeDeltaUsd == false` 时 `order.sizeDelta / 10^indexTokenDecimals` | 合约不强制 18 位：`PositionUtils.sol::getIncreaseOrderSize` 在该模式下直接把 `sizeDelta` 当 token 数量，单位随该市场 index token 自身 decimals（decimals 已被 15.3 说的价格标度 `1e30 / 10^decimals` 吸收，合约层面没有 18 位的硬约束）。当前 tx / oracle / time-fork 的 FXMOCK 均登记为 18 位（`TestCode/config/mock-resources.json`），换市场或换环境前不要照抄除数。USD 模式下挂单期无法给出确定的 token 数（要等执行价） |
| Trigger | 按 16.3 的方向展示 `<=` 或 `>=` | 用 primary 价的 min / max 端 |
| Created / Updated | `updatedAtTime` 按当前 locale 格式化 | 创建与每次 update 都会刷新，不是"创建时间" |
| Earliest execution | `validFromTime` | 只对非市价单有效 |
| Status: Pending | OrderStore 中存在且 `isFrozen == false` | |
| Status: Frozen | OrderStore 中存在且 `isFrozen == true` | 抵押品仍锁在 OrderVault；`executionFee` 已被清零；需 FROZEN_ORDER_KEEPER 才能再执行；用户调 `updateOrder` 会 `setIsFrozen(false)` 解冻并可补充执行费 |
| Status: Executed | 订单已移除且存在 `OrderExecuted` 事件 | |
| Status: Cancelled | 订单已移除且存在 `OrderCancelled` 事件 | |

取消退款的两个接收方回退规则不同（`OrderUtils.sol::cancelOrder`，容易写混）：

```text
抵押品退款（仅增仓单且 initialCollateralDeltaAmount > 0）：
    cancellationReceiver != 0 ? cancellationReceiver : order.account()

执行费退款：
    cancellationReceiver != 0 ? cancellationReceiver : order.receiver()
```

冻结（`OrderUtils.sol::freezeOrder`）的执行费接收方固定是 `order.receiver()`，与 `cancellationReceiver` 无关。

挂单期间不应增加仓位 OI，也不应把 OrderVault 中暂存的抵押品显示成 Position collateral。

### 16.6 子账户槽位与签名

**v0.3.2 把子账户从"地址集合"改成"三键命名槽位"**，这是本节相对 v0.3.1 变化最大的地方：

| | v0.3.1 | v0.3.2 |
| --- | --- | --- |
| 存储模型 | 单个地址 Set：`subaccountListKey(account)` + `dataStore.addAddress/removeAddress` | 每个 index 三个 key：`subaccountSlotKey(account,i)`(string) / `subaccountSlotSubaccountKey(account,i)`(address) / `subaccountSlotActiveKey(account,i)`(bool) |
| 数量上限 | 无 | `SubaccountUtils.MAX_SUBACCOUNT_SLOTS = 4`（Solidity 编译期常量，`Reader.sol:27` 再声明一次） |
| 添加接口 | `addSubaccount(address)` | `addSubaccount(address subaccount, string slot)` |
| 释放接口 | `removeSubaccount(address)`（真删） | `removeSubaccount(address)`（**不释放槽位**）+ 新增 `removeSlot(string)`（真释放） |
| approval 结构 | `SubaccountApproval` 无 `slot` | 新增 `string slot`（结构体第 2 个字段） |
| 读取 | 遍历 address set | `Reader.getSubaccountSlots(dataStore, account)` 返回定长 4 的 `SubaccountSlot[]`；`Reader.getSubaccountInfo(...)` 返回含 `slot/isSlotActive/canExecuteAction` 的聚合视图 |

`addSubaccount` 的槽位选择算法（`SubaccountUtils.sol::addSubaccount`）：

```text
slotIndex = 4（哨兵：未找到）
for i in 0..3:
    isActive = subaccountSlotActive(account, i)
    if isActive && subaccountSlot(account, i) == slot:      // 同名复用，优先级最高
        slotIndex = i; break
    if !isActive && slotIndex == 4:                          // 记住第一个空闲位，继续找同名
        slotIndex = i

slotIndex == 4  →  revert MaxSubaccountSlotsExceeded(account)

if subaccount != 0:
    for i in 0..3:  若 i != slotIndex 且该槽 active 且地址相同 → revert DuplicateSubaccount(account, subaccount)

写入：setString(slotKey, slot); setAddress(slotSubaccountKey, subaccount); setBool(slotActiveKey, true)
emit AddSubaccount(account, subaccount, slotIndex, slot)
```

`removeSubaccount(account, subaccount)`（`SubaccountUtils.sol::removeSubaccount`）**只把匹配槽位的地址置零，不动 slot 名、不动 isActive**：

```text
if subaccount != 0:
    for i in 0..3:
        if slotActive(i) && slotSubaccount(i) == subaccount:
            slotIndex = i; slot = slotString(i)
            setAddress(slotSubaccountKey(i), address(0))     // 只清地址
            break
emit RemoveSubaccount(account, subaccount, slotIndex, slot)   // 找不到时 slotIndex=4、slot=""，仍然发事件、不回滚
```

`removeSlot(account, slot)`（`SubaccountUtils.sol::removeSlot`）才是真正释放容量：命中 active 且同名的槽位后 `removeString + removeAddress + removeBool` 三键全删，emit `RemoveSubaccountSlot` 并 `return`；**没找到匹配槽位时静默返回，既不回滚也不发事件**。

由此得到必须覆盖的行为（Gordon 已确认 by design，记为 R6-B01）：

```text
4 个槽位全部 active
→ removeSubaccount(旧地址)        // 地址清零，槽位仍 active
→ addSubaccount(新地址, "新槽位名")  // 找不到同名，也找不到 !isActive 的空位
→ revert MaxSubaccountSlotsExceeded
```

而 `addSubaccount(新地址, "旧槽位名")` 会命中同名分支、复用该槽位、覆盖地址，因此**能否换绑取决于传的 slot 名是否与旧槽位相同**。前端"更换设备"必须走 `removeSlot` 或复用同名，不能只调 `removeSubaccount`。

另外两条槽位相关事实：

- `addSubaccount(address(0), slot)` 不触发去重循环（`if (subaccount != address(0))` 包住），会写出一个 `isActive = true` 且地址为零的占位槽；`validateSubaccount` 对 `subaccount == address(0)` 直接跳过循环并 `revert SubaccountNotAuthorized`，所以这种槽位占容量但永远不可用。
- 槽位数量与授权有效期是两层独立控制：即便槽位还 active，`handleSubaccountAction` 仍逐次校验 `expiresAt` 与 `maxAllowedCount`（`SubaccountUtils.sol::_validateSubaccountActionCountAndExpiresAt`），过期 → `SubaccountApprovalExpired`，次数用尽 → `MaxSubaccountActionCountExceeded`。

**签名侧变化**（`RelayUtils.sol`）：

```text
v0.3.1: SubaccountApproval(address subaccount,bool shouldAdd,uint256 expiresAt,uint256 maxAllowedCount,
                           bytes32 actionType,uint256 nonce,uint256 desChainId,uint256 deadline,bytes32 integrationId)

v0.3.2: SubaccountApproval(address subaccount,string slot,bool shouldAdd,uint256 expiresAt,uint256 maxAllowedCount,
                           bytes32 actionType,uint256 nonce,uint256 desChainId,uint256 deadline,bytes32 integrationId)
```

`slot` 以 `keccak256(bytes(slot))` 进 struct hash（`RelayUtils.sol::getSubaccountApprovalStructHash`），typehash 随之改变，**v0.3.1 的历史签名在 v0.3.2 上必然恢复出错误地址**。同时新增 `REMOVE_SUBACCOUNT_SLOT_TYPEHASH = RemoveSubaccountSlot(address account,string slot,bytes32 relayParams)` 与对应的 `SubaccountRelayRouter.removeSlot` / `getRemoveSlotDigest` 入口。

subaccount approval 的校验顺序（`SubaccountRelayRouter.sol::_handleSubaccountApproval`）：

```text
signature.length == 0                                  → 直接 return（本次不更新授权，只用已有槽位）
approval.subaccount == 0 || != 入参 subaccount          → InvalidSubaccountApprovalSubaccount
approval.desChainId != block.chainid                   → InvalidSubaccountApprovalDesChainId
block.timestamp > approval.deadline                    → SubaccountApprovalDeadlinePassed
subaccountApprovalNonces[account] != approval.nonce    → InvalidSubaccountApprovalNonce
nonce++（严格递增，与 15.4 的 relay digest 表是两套防重放）
validateSignature(digest, approval.signature, account, "subaccount approval")   // 由主账户签名
→ handleSubaccountApproval：maxAllowedCount>0 才写、expiresAt>0 才写、shouldAdd 才 addSubaccount
```

注意 `maxAllowedCount` 与 `expiresAt` 都是 **>0 才写入**，传 0 表示"本次不修改"，不是"设为 0"。

测试必须同时核对：ABI 参数（`addSubaccount` 多了 string）、typed data（typehash 与 `slot` 哈希）、四个槽位的三键状态（`Reader.getSubaccountSlots`）、`subaccountApprovalNonces` 和 Reader 的 `canExecuteAction`。

### 16.7 autoCancel 语义

源码锚点：`OrderUtils.sol::updateAutoCancelList` / `clearAutoCancelOrders`、`AutoCancelUtils.sol`、`ExecuteOrderUtils.sol::executeOrder`、`OrderHandler.sol::updateOrder`。

`autoCancel = true` 的含义是"把本订单登记进该仓位的自动撤单列表，仓位归零时随之取消"。关键约束：

```text
updateAutoCancelList / validateTotalCallbackGasLimitForAutoCancelOrders 的第一行都是：
    orderType != LimitDecrease && orderType != StopLossDecrease → return
```

即 **`autoCancel` 只对 LimitDecrease（止盈）与 StopLossDecrease（止损）生效**；在其他订单类型上把 `autoCancel` 置 true 会被存进 Order 字段但没有任何实际行为，Reader 读出来是 true，页面据此展示"仓位平掉会自动撤单"就是错的。

**v0.3.2 变化 1**（`OrderUtils.sol::createOrder`）：

```text
v0.3.1:  updateAutoCancelList(dataStore, key, order, order.autoCancel());
         validateTotalCallbackGasLimitForAutoCancelOrders(dataStore, order);   // 无条件调用

v0.3.2:  if (order.autoCancel()) {
             updateAutoCancelList(dataStore, key, order, true);
             validateTotalCallbackGasLimitForAutoCancelOrders(dataStore, order);
         }
```

行为差异：`autoCancel = false` 的 LimitDecrease/StopLossDecrease 订单，v0.3.1 会走一次 `removeAutoCancelOrderKey`（对刚生成的新 key 是 no-op）并且**仍然执行一次 `MAX_TOTAL_CALLBACK_GAS_LIMIT_FOR_AUTO_CANCEL_ORDERS` 总量校验**；v0.3.2 直接跳过。

这条差异的**可触发条件很窄，构造用例前必须先看清**：`getTotalCallbackGasLimitForAutoCancelOrders` 只遍历 `autoCancelOrderListKey(positionKey)` 里**已在册**的订单累加 `callbackGasLimit`，而 `autoCancel = false` 的新单从头到尾都没进过这张列表，它自己的 `callbackGasLimit` 不会被计入；同时每一次 `autoCancel = true` 的加入都当场校验过 `total <= maxTotal`。因此只要配置不变，既有总量恒不超上限，两版表现完全相同。**差异只在“既有总量已经超过上限”时才显形**——现实构造方式是先建满若干 autoCancel 单，再把 `MAX_TOTAL_CALLBACK_GAS_LIMIT_FOR_AUTO_CANCEL_ORDERS` 下调到低于既有总量，此时同仓位再下 `autoCancel = false` 的新单，v0.3.1 回滚 `MaxTotalCallbackGasLimitForAutoCancelOrdersExceeded`，v0.3.2 放行。按“列表接近上限”而不下调配置去设计跨版本回归用例，会复现不出任何差异。

**v0.3.2 变化 2**（`OrderHandler.sol::updateOrder`）：

```text
v0.3.1:  if (order.autoCancel() != autoCancel) { updateAutoCancelList(...); validateTotal...(...); }
         order.setAutoCancel(autoCancel);        // 在 if 外，无条件写

v0.3.2:  if (order.autoCancel() != autoCancel) { updateAutoCancelList(...); validateTotal...(...);
                                                 order.setAutoCancel(autoCancel); }
```

两版对外行为等价（值没变时写不写都一样），属于收敛性修正，不改变期望值。

列表容量与清理：

| 规则 | 事实 | 锚点 |
| --- | --- | --- |
| 列表 key | `autoCancelOrderListKey(positionKey)`，positionKey 由 `BaseOrderUtils.getPositionKey(order)` 得出 | `FX100Keys.sol` |
| 上限 | 先 `addBytes32` 再判 `count > MAX_AUTO_CANCEL_ORDERS` → `revert MaxAutoCancelOrdersExceeded(count, max)`（即等于上限放行，超一条才回滚） | `AutoCancelUtils.sol::addAutoCancelOrderKey` |
| 读列表也受同一上限截断 | `getAutoCancelOrderKeys` 是 `getBytes32ValuesAt(listKey, 0, MAX_AUTO_CANCEL_ORDERS)`：**若该配置在建单后被下调，超出部分的订单读不出来**，总量校验与 `clearAutoCancelOrders` 都会漏掉它们 | `AutoCancelUtils.sol::getAutoCancelOrderKeys` |
| callback gas 总量 | 列表内各单 `callbackGasLimit` 之和 > `MAX_TOTAL_CALLBACK_GAS_LIMIT_FOR_AUTO_CANCEL_ORDERS` → revert | `OrderUtils.sol::validateTotalCallbackGasLimitForAutoCancelOrders` |
| 执行时移除 | 每条订单执行成功后 `updateAutoCancelList(..., false)` 把自己摘掉 | `ExecuteOrderUtils.sol::executeOrder` |
| 取消时移除 | `cancelOrder` 内同样调 `updateAutoCancelList(..., false)` | `OrderUtils.sol::cancelOrder` |
| 触发清空 | 减仓单执行后读 `positionKey` 的 `SIZE_IN_USD`，**== 0 时**才调 `clearAutoCancelOrders`，逐条 `cancelOrder(isAutoCancel=true)` | `ExecuteOrderUtils.sol::executeOrder` |
| 顺序 | `clearAutoCancelOrders` 在主执行费支付**之后**调用，因为每条自动撤单都会按各自 gas 单独付给 keeper | 同上 |
| gas 不足 | 自动撤单路径报 `InsufficientGasForAutoCancellation`，手工取消报 `InsufficientGasForCancellation` | `OrderUtils.sol::cancelOrder` |

所以"部分减仓"不会触发自动撤单，只有把 `sizeInUsd` 减到 0（全平或清算）才会。测试断言要以 `SIZE_IN_USD == 0` 为条件，不能以"发生了减仓"为条件。

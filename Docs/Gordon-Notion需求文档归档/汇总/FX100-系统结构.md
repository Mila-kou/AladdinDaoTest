# FX100 系统结构

> 整理日期：2026-07-30
> 来源：Gordon / FX100 Notion 归档 66 篇中提及的真实合约路径、v0.3.1 验证与审计报告（**未引入文档外的推测模块**）
> 用途：新人建立系统全貌、排障时定位层次、测试时确定断言边界

**核心定位**：部署在 **Base** 上的**预言机驱动**永续合约 DEX。无订单簿，成交价 = 预言机价 ± 动态点差。**单一 USDC LP 池**作为所有市场的唯一对手方，交易者与 LP 直接对赌。

> **最新状态边界**：`release/v0.3.1` 是当前已验证基线；07-29“Dynamic Spread 允许为负”仍处于待评审实施。本文涉及负 spread 时会明确区分“当前 release”与“目标方案”。

## 一、分层结构

| 层 | 职责 | 主要合约 / 模块 |
|---|---|---|
| **接入层** | 用户交互、订单构造、精度换算、会话密钥 | 前端 `fx-base-app` · SDK · Flash 1CT |
| **路由层** | 交易入口分流（自付 gas / 代发 / 子账户） | `src/router/BaseRouter.sol` · `router/relay/BaseRelayRouter.sol` · `router/relay/SubaccountRelayRouter.sol` |
| **订单层** | 订单创建、校验、执行调度、gas 结算 | `src/exchange/OrderHandler.sol` · `order/OrderUtils.sol` · `order/ExecuteOrderUtils.sol` · `order/BaseOrderUtils.sol` · `gas/GasUtils.sol` |
| **业务层** | 仓位增减、OI 记账、执行价与点差 | `src/position/PositionUtils.sol` · `IncreasePositionUtils.sol` · `DecreasePositionUtils.sol` · `DecreasePositionCollateralUtils.sol` · `market/MarketUtils.sol` · `pricing/PositionPricingUtils.sol` |
| **风控层** | 清算判定、自动减仓、储备与净义务闸门 | `src/liquidation/LiquidationUtils.sol` · `adl/AdlUtils.sol` · `MarketUtils` 内的 RESERVE / GNOR 校验 |
| **金库层** | 资金托管与 LP 申赎 | `OrderVault` · `PositionVault` · `src/vault/LPVault.sol` + `VaultBase.sol` + `IStrategy` 实现 |
| **费用层** | 费用归集与三方分账 | `src/fee/FeeHandler.sol` · `RevenuePool.sol`（复用 fx 既有） · `ProtocolTreasury.sol` ×2 · `referral/ReferralStorage.sol` |
| **基础层**（横向支撑） | 价格、配置、权限、链下执行 | `src/oracle/Oracle.sol` + 三 Provider · `DataStore` · `Config` · `FX100Keys` · `RoleStore` · Keeper 集群 · `Reader` |

> **基础层是横向的**，不在请求链路的末端——上面每一层都直接依赖它取价、读配置、验权限。

## 二、四条核心数据流

### 2.1 下单流（创建期）

```plain
前端 → SDK 构造 payload（精度换算：内部推算用 18 位，用户输入用 token 原生位）
  → Router（直连 / Relay）
  → OrderHandler
  → OrderUtils.createOrder
      ├─ orderVault.recordTransferIn(WNT)        收执行费
      ├─ isExecutionFeeSubsidizedAtCreation()    双阈值判定，无需 oracle
      │    命中 → setExecutionFee(0) + 误传 WETH 退回 cancellationReceiver
      │    未中 → validateAndCapExecutionFee + 超额退回
      └─ OrderStore 落库
```

**这一步不取 oracle 价**——这是执行费豁免前移到创建期的关键前提（两个阈值都用原生单位直接比较）。

### 2.2 执行流

```plain
Keeper（ORDER_KEEPER）→ OrderHandler.executeOrder
  → ExecuteOrderUtils
      ① OrderStoreUtils.remove(key)              先移除，防重复执行
      ② validateNonEmptyOrder(order)             用已加载副本
      ③ validateOracleTimestamp                  下界按订单类型三分流
      ④ Oracle 取价（三 Provider + Secondary 缓存）
      ⑤ PositionPricingUtils 算执行价与点差
      ⑥ MarketUtils 风控闸门（OI / RESERVE / GNOR）
      ⑦ Increase / DecreasePositionUtils 结算
      ⑧ 资金在 OrderVault ⇄ PositionVault ⇄ LPVault 间流转
      ⑨ 费用计入 claimableFeeAmount
      ⑩ 全平 → clearAutoCancelOrders（清 TP/SL）
      ⑪ GasUtils.payExecutionFee → keeper
      ⑫ callback hook（63/64 gas 转发）
```

### 2.3 清算 / ADL 流（两条独立路径）

```plain
清算：LIQUIDATION_KEEPER → LiquidationUtils
        → graceEnd 检查（保护期内拒绝）
        → createLiquidationOrder → Decrease 路径

ADL： ADL_KEEPER → updateAdlState（判定 pnlRatio）
        → AdlUtils.executeAdl
        → ⚠️ 不经 graceEnd 检查
```

> **两条路径不共享保护期语义**：grace 只挡 keeper 清算，不挡 ADL 削减。这是待 Gordon 确认的设计意图（交接文档 C14）。

### 2.4 费用流

```plain
开/平仓费 + 清算费 + 资金费净额
  → claimableFeeAmount（账面归集，资金留在 PositionVault）
  → FeeHandler.claimFees / withdrawFees
  → FEE_RECEIVER = RevenuePool 分账器
  → keeper 调 claim()（staker 槽 = keeper，stakerRatio = 0，仅触发不收款）
      ├─ treasury 槽    → 协议收益库    ~40%
      ├─ burners[USDC]  → 保险基金      ~20%
      └─ ecosystem 槽   → LP Vault      余数 ~40%（即时抬升 NAV）
```

**设计要点**：分账器复用 fx 既有 `RevenuePool.sol`，两个金库复用 `ProtocolTreasury.sol`。**唯一的 src 合约改动是资金费路由**（原本直接转 LP Vault，改为计入 `claimableFeeAmount` 走同一通道），其余全是部署+配置。

### 2.5 LP 申赎流

```plain
存款：LPVault.deposit → 无任何 gate（存款无套利路径，MAX_PNL_FACTOR_FOR_DEPOSITS 已删除）

提款：LPVault.initiateWithdrawRequest
        → GNOR 闸门：pnlRatio > 0.65 封锁
        → epoch + withdrawDelaySeconds 等待
        → claimWithdrawRequest
        → VaultBase._withdrawAssets
            balance ≥ assets → 本地转出
            balance < assets → IStrategy.withdraw 补缺口
```

> ⚠️ `VaultBase._withdrawAssets` 的缺口分支存在**强 bug 候选**（`LPPNL-STA-026`）：只调 `IStrategy.withdraw(缺口)`，未把本地 balance 一并转给 receiver，LP claim 会少拿钱；现有绿测把错误值写死。

## 三、风控闸门全景

按触发时机排列，一笔订单要穿过的所有闸门：

| 时机 | 闸门 | 参数 | 未通过 |
|---|---|---|---|
| 创建期 | 执行费双阈值 | `EXECUTION_FEE_SUBSIDIZE` / `_SIZE` | 豁免或要求预付 |
| 创建期 | 最小保证金 / 最小仓位 | `MIN_COLLATERAL_USD` / `MIN_POSITION_SIZE_USD` | 拒绝 |
| 执行期 | 单市场持仓硬上限 | `MAX_OPEN_INTEREST(market, isLong)` | 取消 + 退款 |
| 执行期 | 储备因子（**多空合计口径**） | `RESERVE_FACTOR`：`(longOITokens + shortOITokens) × price.max ≤ RF × poolUsd` | 取消 + 退款 |
| 执行期 | 单仓规模上限 | `MAX_POSITION_SIZE_USD` | 取消 |
| 执行期 | 开仓最低抵押率 | `MIN_COLLATERAL_FACTOR` | 取消 + 退款 |
| 执行期 | 结算 PnL 上限（单边） | `MAX_PNL_FACTOR_FOR_TRADERS`（0.90） | 关仓截断 |
| 全局 | 净义务比触发 ADL | `MAX_PNL_FACTOR_FOR_ADL`（0.75） | 开启 ADL |
| 全局 | ADL 退出线 | `MIN_PNL_FACTOR_AFTER_ADL`（0.50） | 停止 ADL |
| 全局 | LP 提款封锁 | `MAX_PNL_FACTOR_FOR_WITHDRAWALS`（0.65） | 拒绝提款 |
| 清算期 | 清算维持因子 | `MIN_COLLATERAL_FACTOR_FOR_LIQUIDATION` | 可被清算 |
| 清算期 | 15 分钟保护期 | `LIQUIDATION_GRACE_PERIOD_BASE` × tier | keeper 清算被拒 |

### 全局净义务口径（v0.3.0 核心改造）

```plain
net_i    = max(0, longPnl_i) + max(0, shortPnl_i)     // 跨边不轧差，边内轧差
pnlRatio = Σ net_i / poolUsd                          // 全局单一标尺
```

**为什么是全局而非 per-market**：FX100 多空共用同一 USDC 池，单边口径下每边各拿全池做分母 = **池容量被双重计账**。静态 per-market 预算也无法跟踪动态集中的风险（设高漏报、设低误报）。改全局后 4 个 PnL 参数**全部与市场数量无关**，新增市场无需调整任何风控参数。

## 四、预言机层结构

```plain
Oracle.sol
  ├─ ChainlinkDataStreamProvider   （主源，链下签名报价，含 bid/ask）
  ├─ ChainlinkPriceFeedProvider    （备份 / 偏差校验）
  └─ PythPriceFeedProvider + PythPriceFeedUtils

Secondary Price（三层回退）
  ①  address(0)          → 不启用
  ②  Chainlink feed      → 实时
  ③  缓存的 recorded 价   → 持久化缓存
```

**关键语义**：
- **无自动降级**——主源失效时协议**冻结**（不成交、不清算），需治理**手动切换**，切换设时间锁防抖动
- **`isADLStart` 时效语义**：所有「放松风控」的读取（LP 提款、ADL 关闭判断、`executeAdl`）要求严格时效；唯一容忍过期缓存的是「**开启** ADL 保护」的判断——**失效模式永远朝保守方向倒**
- oracle 错误在 `OrderHandler.validateNonKeeperError()` 中被识别为**非用户错误**，直接 revert 而非 freeze 订单——订单完好，恢复后可继续
- 价格格式**统一** `USD × 10^12`（USDC 为 `10^24`），**不按 token 小数位区分**——这是 SDK 精度陷阱的根源

## 五、配置与权限层

| 组件 | 职责 | 风险点 |
|---|---|---|
| `DataStore` | 全局 KV 存储，所有参数的落地处 | **可绕过 Config 直写**，无范围校验、无治理事件 |
| `Config` | 治理入口，含 `allowedBaseKeys` 白名单 | 不在白名单的 key 只能 DataStore 直写 |
| `FX100Keys` | key 派生（`keccak`） | 存在两种派生风格混用 |
| `RoleStore` | 角色权限 | 11 个角色，需严格分离不兼任 |

### Keeper 角色

| 角色 | 职责 |
|---|---|
| `ORDER_KEEPER` | 执行订单（市价单立即、触发单条件满足后） |
| `LIQUIDATION_KEEPER` | 触发清算 |
| `ADL_KEEPER` | `updateAdlState` + `executeAdl`；v0.3.1 起 `refreshLatestRecordedPrices` 已 permissionless |
| `CONFIG_KEEPER` | oracle provider 切换（唯一切换权限）、参数调整 |
| `MARKET_KEEPER` | 市场级配置 |

## 六、关键设计决策（与 GMX V2 的差异）

| 维度 | GMX V2 | FX100 | 影响 |
|---|---|---|---|
| 池结构 | 双池（多头 WETH / 空头 USDC） | **单一 USDC 池** | 储备口径必须改多空合计，否则双重计账 |
| 借贷费 | 有 | **移除** | `BORROW_*` 全部成为 dead keys（P2 清理） |
| 资金费 | 轻仓侧需手动领取 | **自动结算进保证金** | 无 claim 余额；均衡时多头付 floor 给 LP |
| 清算保护 | 无 | **开仓 15 分钟免清算** | 核心差异化；只挡 keeper，不挡 ADL |
| ADL 触发 | per-market | **全局净义务比** | 参数与市场数量无关 |
| 过度减仓保护 | `PnlOvercorrected` | **已删除** | keeper 全权控制单笔幅度 |
| 杠杆显示 | 名义 / 净权益（含浮盈亏） | 名义 / **净抵押**（不含浮盈亏） | 不随价格抖动 |
| 存款 gate | 有 | **无任何 gate** | scaling=0 下存款无套利路径 |
| 价格精度 | 按 token decimals | **统一 `USD × 10^12`** | SDK 不能沿用 `token.decimals` |
| Dynamic Spread | 通常非负冲击 | **最新目标允许普通交易为负** | rebate 仅适用于自愿交易；清算/ADL/安全校验仍 floor-at-0 |

## 七、外部依赖与信任边界

| 依赖 | 类型 | 失效后果 | 缓解 |
|---|---|---|---|
| Chainlink Data Streams | 主价格源 | 协议冻结（不成交不清算） | 手动切备份源，有时间锁 |
| Base Sequencer | L2 排序器 | 故障恢复期保护性拒绝 | sequencer uptime feed |
| Keeper 集群 | 链下执行 | 订单挂起、清算延迟 | 多 keeper 冗余 |
| Relayer | Express 代发 | 免 gas 路径不可用 | 可回退直连 |
| `RevenuePool` / `ProtocolTreasury` | 复用 fx 既有合约 | 分账停滞（资金仍安全） | 治理手动 |
| `IStrategy`（fxSAVE 等） | LP 池收益策略 | LP 提款缺口路径受影响 | ⚠️ 无限授权是攻击面 |

## 九、排障时的层次定位

| 现象 | 先查哪层 | 典型原因 |
|---|---|---|
| 仅 BTC 等非 18 位 token 数值异常 | 接入层（SDK） | `indexToken.decimals` 误用，应为 18 |
| 订单被 cancel 且已退款 | 风控层 | OI / 储备 / 保证金 / 仓位上限 |
| 订单被 freeze 未退款 | 订单层 | 触发单滑点不达 |
| 订单 revert 但订单还在 | 基础层（Oracle） | 价格过期 / 偏离 / sequencer |
| 成交价与预期不符 | 业务层 | 动态点差三段构成 + 取整方向 |
| 杠杆显示高于开仓值 | 接入层（口径） | 持仓杠杆用净抵押，资金费已累积 |
| 浮盈亏与实际到账不符 | 接入层（口径） | 浮盈亏是纯价格盈亏，未含冲击与费用 |
| 保护期不倒计时 | 基础层（配置） | `LIQUIDATION_GRACE_PERIOD_BASE` 配成 0 |
| 分账未到账 | 费用层 | `FEE_RECEIVER` 未切换 / keeper 未调 `claim()` |

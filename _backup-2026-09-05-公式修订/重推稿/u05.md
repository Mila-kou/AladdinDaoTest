## 6. Position PnL

> 源码锚点：`src/position/PositionUtils.sol::getPositionPnlUsdWithExecutionPrice` → `::_getPositionPnlUsd`；上限依赖 `src/market/MarketUtils.sol::getPnl` / `::getCappedPnl` / `::getPoolAmount` / `::getMaxPnlFactor`、`src/price/Price.sol::pickPriceForPnl`。
>
> 版本关系：`_getPositionPnlUsd` 函数体 v0.3.1 → v0.3.2 **无改动**（`git diff d9a7fd2 13880f2 -- src/position/PositionUtils.sol` 该段无 hunk）。本节相对 v0.3.1 文档的改写是**勘误**：原 §6.4 把上限写成“池子总 PnL”，实际是**与本仓同方向的单边 PnL**，且缩放触发条件、选价侧、取整方向此前均未写。

### 6.0 入参与调用点

`_getPositionPnlUsd` 只有两个可变入参：**整仓执行价 `executionPrice`** 与 **本次的 `sizeDeltaInTokens`**。四个调用点：

| 调用点 | executionPrice 来源 | 传入的 sizeDeltaInTokens |
| --- | --- | --- |
| `DecreasePositionCollateralUtils::processCollateral` | `PositionUtils::getExecutionPriceForDecrease`（含动态点差，且已过 `BaseOrderUtils.getExecutionPriceForDecrease` 的 acceptablePrice 校验） | 本次减仓的 `sizeDeltaInTokens` |
| `DecreasePositionUtils::decreasePosition`（部分减仓可行性预估） | 同上 | `position.sizeInTokens()`（整仓），随后自己再按 §6.4 同规则折算成 `estimatedRealizedPnlUsd` |
| `PositionUtils::isPositionLiquidatable` | 同上，但 order 被临时置为 `orderType = Liquidation`（因而 `allowNegativeSpread = false`） | `position.sizeInTokens()`（整仓） |
| `ReaderPositionUtils::getPositionInfo` | `ReaderPricingUtils.getExecutionPrice` | Reader 解析出的 `sizeDeltaInTokens` |

`BaseOrderUtils.getExecutionPriceForDecrease(executionPrice, acceptablePrice, isLong)` 是**纯校验、不做校正**：Long 满足 `executionPrice >= acceptablePrice`、Short 满足 `executionPrice <= acceptablePrice` 时原样返回，否则直接 `revert OrderNotFulfillableAtAcceptablePrice(executionPrice, acceptablePrice)`。成交价**不会**被夹到 `acceptablePrice`。

**必读**：`executionPrice` 是**含动态点差的成交价**，不是 `indexPrice.min` / `.max`。开仓侧同理（§4）。只有下面 §6.3 的“池子单边 PnL”才回退到 `indexPrice` 的 min/max。

### 6.1 整仓市值

```text
positionValue = position.sizeInTokens × executionPrice        # int256，30 位精度 USD
```

乘的是**整仓** `sizeInTokens`，不是本次减仓的 `sizeDeltaInTokens`。

### 6.2 整仓 PnL

```text
Long  totalPositionPnl = positionValue - position.sizeInUsd

Short totalPositionPnl = position.sizeInUsd - positionValue

uncappedTotalPositionPnl = totalPositionPnl        # 快照，之后不参与任何裁剪
```

### 6.3 盈利上限：只裁正 PnL，且只看**本仓方向**的单边池 PnL

```text
if totalPositionPnl <= 0:
    不进入上限逻辑（亏损从不封顶）
else:
    poolTokenUsd  = MarketUtils.getPoolAmount(market) × collateralTokenPrice.min
                  = IVault(market.vault).totalAssets() × collateralTokenPrice.min
    poolPnl       = MarketUtils.getPnl(dataStore, market, prices.indexTokenPrice,
                                       isLong = position.isLong(), maximize = true)
    cappedPoolPnl = MarketUtils.getCappedPnl(dataStore, market.marketIndex,
                                             isLong = position.isLong(),
                                             poolPnl, poolTokenUsd,
                                             MAX_PNL_FACTOR_FOR_TRADERS)

    if cappedPoolPnl != poolPnl AND cappedPoolPnl > 0 AND poolPnl > 0:
        totalPositionPnl = totalPositionPnl × cappedPoolPnl / poolPnl      # 向下取整
```

三处 `isLong` 全部取 `position.isLong()`：`getPnl` 的方向、`maxPnlFactorKey` 的方向、`pickPriceForPnl` 的方向。**“多空合计的池子净 PnL”这个量确实存在**——`MarketUtils::getNetPnl = getPnl(long) + getPnl(short)`（本文档 §12.2 的 `netPnl`），但它服务于 ADL / pnlToPoolFactor 一族（§12），**`_getPositionPnlUsd` 的上限路径不使用它**。v0.3.1 文档 §6.4 把本仓上限写成“池子总 PnL”仍是错的，正确口径是与本仓同方向的单边 PnL。

`getPnl`（`MarketUtils.sol::getPnl`，Price.Props 重载）：

```text
openInterestUsd      = getCumulativeOpenCosts(marketIndex, isLong)   # 该方向全部仓位的开仓成本，30 位 USD
openInterestInTokens = getOpenInterestInTokens(marketIndex, isLong)  # index token 原生精度

if openInterestUsd == 0 OR openInterestInTokens == 0:
    return 0                                                          # 早退，不缩放

price = pickPriceForPnl(indexTokenPrice, isLong, maximize = true)
      = isLong ? indexTokenPrice.max : indexTokenPrice.min

Long  poolPnl = openInterestInTokens × price - openInterestUsd
Short poolPnl = openInterestUsd - openInterestInTokens × price
```

`getCappedPnl`（`MarketUtils.sol::getCappedPnl`）：

```text
if poolPnl < 0:
    return poolPnl                                                    # 负值原样返回，不裁

maxPnlFactor = dataStore.getUint(maxPnlFactorKey(MAX_PNL_FACTOR_FOR_TRADERS, marketIndex, isLong))
maxPnl       = poolTokenUsd × maxPnlFactor / 1e30                     # applyFactor，向下取整
return poolPnl > maxPnl ? maxPnl : poolPnl
```

选价 / 取整 / 精度对照：

| 量 | 选价侧 | 取整 | 精度标度 |
| --- | --- | --- | --- |
| `positionValue` / `totalPositionPnl` | `executionPrice`（含点差） | 精确乘法，无除法 | 30 位 USD |
| `poolPnl` | Long → `indexPrice.max`；Short → `indexPrice.min` | 精确乘法 | 30 位 USD |
| `poolTokenUsd` | `collateralTokenPrice.min` | 精确乘法 | 30 位 USD |
| `maxPnl` | — | 向下 | 30 位 USD |
| 缩放后 `totalPositionPnl` | — | 向下（此分支恒为正） | 30 位 USD |

`totalAssets() = IERC20(asset).balanceOf(vault) + IStrategy(strategy).totalAssets()`（`src/vault/VaultBase.sol::totalAssets`），是**整个 LP Vault**的资产。合约层只保证 `market.vault` 是市场级的单个地址，**是否多个市场共用同一 vault 完全由部署决定**（核对时按环境实读 `market.vault`，不要假设一市场一 vault，也不要用单市场余额去凑）。因此 `poolTokenUsd` 是 vault 级、`poolPnl` 是“市场 × 方向”级——两者维度不同。

但合约层并非处处中立：`MarketUtils.sol::getGlobalNetObligationRatio` 的循环里硬编码了注释“All markets share the same vault”，只取第 0 个市场的 `poolUsd` 当全局池子价值——那是 ADL 侧（本文档 §12.4）的既定假设，**`_getPositionPnlUsd` 本身不带这个假设**（它只读本市场的 `market.vault`）。两边口径不一致时按各自源码走，不要互相套用。

### 6.4 按本次减仓比例折算

```text
positionPnlUsd
= mulDiv(totalPositionPnl, sizeDeltaInTokens, position.sizeInTokens,
         roundUpMagnitude = (totalPositionPnl < 0))

uncappedPositionPnlUsd
= mulDiv(uncappedTotalPositionPnl, sizeDeltaInTokens, position.sizeInTokens,
         roundUpMagnitude = (uncappedTotalPositionPnl < 0))
```

`Precision.mulDiv(int256, uint256, uint256, bool)` 走 `Math.mulDiv`（512 位中间积，不会先乘溢出）：**正 PnL 向下取整、负 PnL 按绝对值向上取整**（即对用户不利方向）。返回值 `(positionPnlUsd, uncappedPositionPnlUsd, sizeDeltaInTokens)` 分别落到事件 `PositionDecrease` 的 `basePnlUsd` / `uncappedBasePnlUsd`。

### 6.5 数值例子（自验算）

前提：index token 18 位（价格标度 = USD × 1e12），抵押品 USDC 6 位（价格标度 = USD × 1e24）。`maxPnlFactor` 取 0.6e30 **仅为本例假设值**，不是任何环境的实读值。

**index token 的 decimals 不由合约保证为 18**（按 `market.indexToken` 逐市场实读）：`src/` 下没有任何一处把 index token 强制成 18 位，价格归一乘数是按 token 逐个配置的 `PRICE_FEED_MULTIPLIER = 10^(60 − feed decimals − token decimals)`（`src/constants/FX100Keys.sol`、`src/config/ConfigUtils.sol`、`src/oracle/ChainlinkPriceFeedUtils.sol::getPriceFeedMultiplier`）。换成 `d` 位 index token 时价格标度变成 `USD × 1e(30−d)`，`sizeInTokens` / `openInterestInTokens` 也按 `d` 位计，本例的 `1e19` / `3e20` / `3.3e15` 都要重算。

> 口径待同步：本文档 §16.5 / §17.1 / §17.2 / §21 按“所有标的统一 18 位”写死了 `/1e18`。那是**当前部署的登记事实**，不是合约保证——本工作区就出现过合成 BTC 的 index token 被误登记成 8 位、按链上实读回改 18 位的先例。核对脚本按 `market.indexToken` 实读 decimals 更稳；实读值与写死的 18 位不一致时以实读为准，那几行待随后统一回写。

```text
仓位：Long，sizeInUsd = 30,000e30 = 3e34，sizeInTokens = 10e18 = 1e19（均价 3,000）
本次减仓：sizeDeltaInTokens = 5e18（半仓）
价格：indexPrice.min = indexPrice.max = 3,300 → 3.3e15；dynamicSpread = 0 → executionPrice = 3.3e15

positionValue      = 1e19 × 3.3e15 = 3.3e34                      # 33,000 USD
totalPositionPnl   = 3.3e34 - 3e34 = 3e33                        # +3,000 USD
uncappedTotal      = 3e33

市场多头侧：cumulativeOpenCosts(long) = 900,000e30 = 9e35
            openInterestInTokens(long) = 300e18 = 3e20
poolPnl = 3e20 × 3.3e15 - 9e35 = 9.9e35 - 9e35 = 9e34             # +90,000 USD

LP Vault：totalAssets = 100,000 USDC = 1e11，collateralTokenPrice.min = 1e24
poolTokenUsd = 1e11 × 1e24 = 1e35                                  # 100,000 USD
maxPnlFactor(MAX_PNL_FACTOR_FOR_TRADERS, market, isLong=true) = 0.6e30
maxPnl = 1e35 × 0.6e30 / 1e30 = 6e34                               # 60,000 USD
cappedPoolPnl = min(9e34, 6e34) = 6e34   → 触发缩放（≠ 且两者均 > 0）

totalPositionPnl = 3e33 × 6e34 / 9e34 = 2e33                       # 3,000 → 2,000 USD

positionPnlUsd          = 2e33 × 5e18 / 1e19 = 1e33                # +1,000 USD（已裁剪）
uncappedPositionPnlUsd  = 3e33 × 5e18 / 1e19 = 1.5e33              # +1,500 USD（未裁剪）
```

### 6.6 核对要点

1. `basePnlUsd ≠ uncappedBasePnlUsd` **⇒** 该方向的单边池 PnL 被 `MAX_PNL_FACTOR_FOR_TRADERS` 削顶（未削顶时两条路径入参完全相同，必然相等）。**反向不成立**：缩放步与折算步各有一次向下取整，小额减仓可能“已削顶但两值仍相等”（例：整仓 total=100、scaled=99，`sizeDeltaInTokens / sizeInTokens = 1/1000` → 两边都是 0）。因此只能用作“不等即削顶”的单向判据，不能用“相等”反证未削顶。
2. 比值 `cappedPoolPnl / poolPnl` 只在**整仓层**严格成立（缩放本身还带一次 floor）；折算到本次减仓后，同区块同方向不同仓位的 `basePnlUsd / uncappedBasePnlUsd` 只在量级上一致，允许 1 wei 级取整偏差，不要写成严格相等断言。
3. 独立复算上限需要三个执行区块快照：`cumulativeOpenCosts(market, isLong)`、`openInterestInTokens(market, isLong)`、`IVault(market.vault).totalAssets()`，外加 `maxPnlFactorKey(MAX_PNL_FACTOR_FOR_TRADERS, market, isLong)`。缺任一项只能做方向性检查（`|basePnlUsd| ≤ |uncappedBasePnlUsd|` 且同号）。
4. 空头仓位的池子 PnL 用 `indexPrice.min`，多头用 `indexPrice.max`——与自身 PnL 用的成交价方向相反，价带宽时两者会明显分叉，不要混用。
5. 亏损方向永不封顶：`totalPositionPnl <= 0` 直接跳过整段上限逻辑，`basePnlUsd == uncappedBasePnlUsd`。
6. 部分减仓的 `sizeDeltaInTokens` 由 `PositionUtils::getDecreaseOrderSize` 决定（USD 模式 Long 向上取整、Short 向下取整），它是 §6.4 分子，取错会连带 PnL 错——见 §5。

## 8. 清算费

> 源码锚点：`src/pricing/PositionPricingUtils.sol::getLiquidationFees`、`::getPositionFees`；生效门 `src/position/DecreasePositionCollateralUtils.sol::processCollateral`；清算单构造 `src/liquidation/LiquidationUtils.sol::createLiquidationOrder`；资金去向 `src/fee/FeeUtils.sol::incrementClaimableFeeAmount`。
>
> 版本关系：`getLiquidationFees` 公式体 v0.3.1 → v0.3.2 无改动。本节相对 v0.3.1 文档的改写是**补分支**：生效门 `isLiquidation`、费率为 0 的早退、合并式的实际读写关系、资金去向此前全部缺失。

### 8.1 生效门：只有 `orderType == Liquidation` 才计清算费

```text
isLiquidation = Order.isLiquidationOrder(order.orderType())
              = (order.orderType() == Order.OrderType.Liquidation)      # src/order/Order.sol::isLiquidationOrder

getPositionFees:
    if isLiquidation:  fees.liquidation = getLiquidationFees(...)
    else:              fees.liquidation 全部字段保持 0
```

全仓库只有一个调用点可能传 `true`：

| 调用点 | 传入的 `isLiquidation` | 结果 |
| --- | --- | --- |
| `DecreasePositionCollateralUtils::processCollateral` | `Order.isLiquidationOrder(order.orderType())` | 唯一可能为 `true` |
| `IncreasePositionUtils::processCollateral` | 常量 `false` | 开仓/加仓恒无清算费 |
| `PositionUtils::isPositionLiquidatable` | 常量 `false`（源码注释：判定是否该清算时不应把清算费算进成本） | 清算判定不含清算费 |
| `ReaderPositionUtils::getPositionInfo` | 常量 `false` | **Reader 永远预览不到清算费** |

**ADL 不收清算费**：ADL 单是 `OrderType.MarketDecrease` + `SecondaryOrderType.Adl`（`src/adl/AdlUtils.sol` 建单处写死 `Order.OrderType.MarketDecrease`；`Order.OrderType` 枚举里没有 ADL 项），`isLiquidationOrder` 为 `false`。普通市价/限价/止损平仓同理恒为 0。

### 8.2 费率为 0 的早退

```text
liquidationFeeFactor = dataStore.getUint(liquidationFeeFactorKey(marketIndex))   # 市场级
if liquidationFeeFactor == 0:
    return 全 0 的 PositionLiquidationFees
    # 注意：此分支连 LIQUIDATION_FEE_RECEIVER_FACTOR 都不读，
    #       事件里的 liquidationFeeReceiverFactor 是 0，而不是配置值
    #       （且因 liquidationFeeAmount == 0，三个条件项整组不会出现，见 §8.6）
```

### 8.3 费用体

```text
liquidationFeeUsd
= sizeDeltaUsd × liquidationFeeFactor / 1e30                          # applyFactor，向下取整，30 位 USD

liquidationFeeAmount
= ceil(liquidationFeeUsd / collateralTokenPrice.min)                  # Calc.roundUpDivision，向上取整，抵押币原生精度

liquidationFeeReceiverFactor
= dataStore.getUint(LIQUIDATION_FEE_RECEIVER_FACTOR)                  # 全局常量 key，非市场级

liquidationFeeAmountForFeeReceiver
= liquidationFeeAmount × liquidationFeeReceiverFactor / 1e30          # applyFactor，向下取整
```

**基数是名义成交规模，不是保证金**。`getLiquidationFees` 的形参虽然叫 `sizeInUsd`，`getPositionFees` 实际传入的是 `params.sizeDeltaUsd`，即 `getExecutionPriceForDecrease` 解析出的本次成交名义 USD。清算路径上：`LiquidationUtils::createLiquidationOrder` 以 `sizeDeltaUsd = position.sizeInUsd()`、`isSizeDeltaUsd = true` 建单，`getDecreaseOrderSize` 对“整仓”分支原样返回 `rawSizeDelta`，所以清算时 `sizeDeltaUsd == position.sizeInUsd()`（这也是 v0.3.1 文档写成 `sizeInUsd` 却“碰巧对”的原因；但字段名与推导必须按 `sizeDeltaUsd` 写，否则 ADL/部分平仓语境下会推错）。

> 口径待同步：本文档 §21 速查表「Liquidation Fee = `sizeInUsd × liqFactor`」与 §22「清算费基数……当前必须按 `sizeInUsd` 断言」仍用形参名 `sizeInUsd`。数值在清算全平场景与本节等价，但字段名不一致，以本节的 `sizeDeltaUsd` 为准，§21/§22 两行待随后统一回写。

选价侧：**本节唯一用到价格的是换算分母** `collateralTokenPrice.min`。`liquidationFeeUsd = applyFactor(sizeDeltaUsd, liquidationFeeFactor)` 里不出现任何价格（`sizeDeltaUsd` 已由上游 `getExecutionPriceForDecrease` 定好）；只有 `liquidationFeeAmount = Calc.roundUpDivision(liquidationFeeUsd, collateralTokenPrice.min)` 这一步取价。分母取**最小价** ⇒ 折算出的扣费 token 数被抬高（对用户不利），与仓位费 `positionFeeAmount`、UI Fee `uiFeeAmount` 的换算分母同为 `collateralTokenPrice.min`。

注意三者**取整方向不同**：仓位费与 UI Fee 用普通整除（向下），只有清算费用 `roundUpDivision`（向上）——复算时不要套同一个取整。

### 8.4 与仓位费合并

`getPositionFees` 里紧跟 `getLiquidationFees` 的两行：

```text
# ① 池子腿：只读 positionFeeAmountForPool（已在 getPositionFeesAfterReferral 里
#    算成 protocolFeeAmount − feeReceiverAmount），不读 feeReceiverAmount
feeAmountForPool
= positionFeeAmountForPool
+ liquidationFeeAmount
- liquidationFeeAmountForFeeReceiver

# ② 分账器腿：+= 而非 =，把清算费的分账器部分并进已有的仓位费腿（§7.5 的 applyFactor 结果）
feeReceiverAmount
+= liquidationFeeAmountForFeeReceiver
```

两行之间**没有数据依赖**（①只读 `positionFeeAmountForPool` 并写 `feeAmountForPool`，②只读写 `feeReceiverAmount`），互换书写顺序结果相同；真正要记住的是**②是累加而不是赋值**——`feeReceiverAmount` 在此之前已含仓位费腿。

`liquidationFeeAmountForPool = liquidationFeeAmount − liquidationFeeAmountForFeeReceiver` 只是 `feeAmountForPool` 中的一段，**没有独立结构体字段，也不进事件**；同理没有 `positionFeeReceiverAmount` 这个字段（v0.3.1 文档凭空造了这个名字），事件里只有合并后的 `feeReceiverAmount`。

### 8.5 资金去向（仅在费用全额付清时执行，见 §9.5）

| 金额 | 去向 | 源码 |
| --- | --- | --- |
| `feeAmountForPool` | `positionVault.transferOut(collateralToken, market.vault, ...)` → LP Vault | `DecreasePositionCollateralUtils::processCollateral` |
| `feeReceiverAmount − liquidationFeeAmountForFeeReceiver` | `incrementClaimableFeeAmount(..., POSITION_FEE_TYPE)` | 同上 |
| `liquidationFeeAmountForFeeReceiver`（>0 时才调） | `incrementClaimableFeeAmount(..., LIQUIDATION_FEE_TYPE)` | 同上 |
| `uiFeeAmount` | `incrementClaimableUiFeeAmount(..., UI_POSITION_FEE_TYPE)` | 同上；清算单 `uiFeeReceiver = address(0)`，故清算时恒 0 |

**清算人（Keeper）在合约层零补偿**：

- 清算费的余额腿 `liquidationFeeAmount − liquidationFeeAmountForFeeReceiver` 并入 `feeAmountForPool` 进 LP Vault，没有任何一条路径转给 keeper；
- 执行费同样拿不到：`LiquidationUtils::createLiquidationOrder` 把清算单的 `executionFee` **硬编码为 0**，而 `GasUtils::payExecutionFee` 首行 `if (executionFee == 0) { return 0; }` 直接早退——**不转原生代币、不发 `KeeperExecutionFee` 事件**，§14.2 的 `keeperExecutionFee = min(executionFee, adjustedGasUsed × tx.gasprice)` 在清算路径恒为 0。

所以清算 Keeper 的 gas 完全自担。用例**不得**断言“清算后 keeper 原生代币余额增加”或“清算 tx 里有 `KeeperExecutionFee`”，否则必然误报缺陷。

### 8.6 事件字段

费用事件由 `PositionEventUtils::_emitPositionFees` 统一构造，但**事件名分两种，不按开仓/减仓划分**——全仓库只有三个调用点：

| 发出点 | 事件名 | `isIncrease` | 何时出现 |
| --- | --- | --- | --- |
| `IncreasePositionUtils.sol:165` | `PositionFeesCollected` | `true` | 每笔开仓/加仓 |
| `DecreasePositionUtils.sol:325` | `PositionFeesCollected` | `false` | 每笔减仓/平仓/清算/ADL（**含穿仓早退的那笔**） |
| `DecreasePositionCollateralUtils.sol:328`（`handleEarlyReturn` 内） | `PositionFeesInfo` | `false` | **只有**偿付不足早退（insolvent close）时 |

即：**常规清算的费用要去 `PositionFeesCollected` 里取，不是 `PositionFeesInfo`**（TestCode 现有核对包 `src/reconciliation/packs/fee-claimable.ts`、`packs/market-open.ts` 读的正是 `PositionFeesCollected`）。穿仓早退时同一笔交易会先后出现 `PositionFeesInfo` 和 `PositionFeesCollected` 两条费用事件，取数必须写明事件名，详见 §9.5。

两种事件的字段布局完全相同。清算费三项是**条件项**，只有 `liquidationFeeAmount > 0` 时才追加：`liquidationFeeAmount`、`liquidationFeeReceiverFactor`、`liquidationFeeAmountForFeeReceiver`。`liquidationFeeUsd` **不进事件**，只能由 `sizeDeltaUsd × factor` 复算。

### 8.7 数值例子（自验算）

```text
market.liquidationFeeFactor      = 0.003e30 = 3e27      （0.3%）
LIQUIDATION_FEE_RECEIVER_FACTOR  = 0.5e30              （50%）
collateralTokenPrice.min         = 1e24                （USDC 6 位，$1）
清算单 sizeDeltaUsd = position.sizeInUsd = 30,000e30 = 3e34

liquidationFeeUsd                  = 3e34 × 3e27 / 1e30 = 9e31            # 90 USD
liquidationFeeAmount               = ceil(9e31 / 1e24)  = 9e7             # 90 USDC
liquidationFeeAmountForFeeReceiver = 9e7 × 0.5e30 / 1e30 = 4.5e7          # 45 USDC → LIQUIDATION_FEE_TYPE claimable
（池子腿）                          = 9e7 - 4.5e7 = 4.5e7                 # 45 USDC → 并入 feeAmountForPool → LP Vault
```

若该仓保证金 3,000 USDC（10x 杠杆），实现按名义规模收 90 USDC = 保证金的 3%；需求规范写的是“0.3% 保证金”= 9 USDC，相差 10 倍（= 杠杆倍数）。差异见 gap 台账 G-01。

## 9. 费用总额

> 源码锚点：`src/pricing/PositionPricingUtils.sol::getPositionFees`（聚合）、`src/position/IncreasePositionUtils.sol::processCollateral`（开仓消费）、`src/position/DecreasePositionCollateralUtils.sol::processCollateral` / `::payForCost` / `::handleEarlyReturn` / `::getEmptyFees`（减仓消费）、`src/position/DecreasePositionUtils.sol::decreasePosition`（全平返还与费用事件）、`src/reader/ReaderPositionUtils.sol::getPositionInfo`（Reader 口径）。

### 9.1 两个聚合量

```text
totalCostAmountExcludingFunding
= positionFeeAmount
+ liquidationFeeAmount
+ uiFeeAmount
- totalDiscountAmount

totalCostAmount
= totalCostAmountExcludingFunding
+ negativeFundingFeeAmount
```

单位全部是**抵押币原生数量**（USDC 6 位），不是 USD。`positiveFundingFeeAmount` **不**进这两个量，它在结算时加回抵押品（开仓路径 §9.3、减仓路径 §9.4）。

不下溢的保证：`totalDiscountAmount = max(proDiscountAmount, referralTraderDiscountAmount)`，两者都是 `applyFactor(positionFeeAmount, factor)`，只要两个折扣因子各自 ≤ 1e30 就有 `totalDiscountAmount ≤ positionFeeAmount`。合约本身**没有**对折扣因子做统一封顶：

- `referral.traderDiscountFactor` 由 ReferralStorage 的 `totalRebate` / `discountShare` 经 `Precision.basisPointsToFloat` 换算（`src/referral/ReferralUtils.sol`），受 basis-point 口径约束；
- `pro.traderDiscountFactor` 直接读 `proDiscountFactorKey(traderTier)` 的配置值，只由配置保证。

`PositionPricingUtils.sol::getPositionFeesAfterReferral` 里的 `maxAffiliateRewardFactor = totalDiscountFactor < 1e30 ? 1e30 − totalDiscountFactor : 0`（`totalDiscountFactor = max(proDiscountFactor, referralTraderDiscountFactor)`，即 §7.3 写的 `max(1e30 − totalDiscountFactor, 0)`，源码带下界钳位而非裸减）封顶的是 `referral.adjustedAffiliateRewardFactor`（联盟奖励），**不约束任何折扣因子**——不要拿它当本式的依据（§7.3）。真正会先撑不住的是同函数的 `protocolFeeAmount = positionFeeAmount − affiliateRewardAmount − totalDiscountAmount`：折扣因子配错超过 1e30 时那里先 revert，本式不会单独下溢。

### 9.2 Reader 口径

`ReaderPositionUtils::getPositionInfo` 在拿到 `getPositionFees` 结果后**用自己的式子覆盖重算**：

```text
totalCostAmountExcludingFunding = positionFeeAmount + uiFeeAmount - totalDiscountAmount     # 少了 liquidationFeeAmount 项
totalCostAmount                 = totalCostAmountExcludingFunding + negativeFundingFeeAmount
```

因为 Reader 恒传 `isLiquidation = false`（§8.1），`liquidationFeeAmount` 本来就是 0，数值与合约口径**等价**；但含义上 Reader 永远不给清算费预览，前端/Keeper 用 Reader 估“被清算会亏多少”会系统性低估一笔清算费。

Reader 还会把 `negativeFundingFeeAmount` 用“虚拟推进后的 per-size”重算（`latestNegative/PositiveFundingFeePerSize` 各加上 `getNextFundingAmountPerSize` 的 delta × 2，源码注释说明单币种市场下 `updateFundingState` 会应用两次、故取半存储、Reader 需还原），所以 Reader 的 `totalCostAmount` 通常比同区块合约实际收取值略大（多算了未落账的 funding）——见 §10 / §19。

### 9.3 消费路径一：开仓 / 加仓（唯一直接用 `totalCostAmount` 的交易路径）

`IncreasePositionUtils::processCollateral`：

```text
collateralDeltaAmount
= collateralIncrementAmount
- totalCostAmount
+ positiveFundingFeeAmount

# 随后在 increasePosition 里：
if collateralDeltaAmount < 0 AND position.collateralAmount < |collateralDeltaAmount|:
    revert InsufficientCollateralAmount(position.collateralAmount, collateralDeltaAmount)
position.collateralAmount = collateralAmount + collateralDeltaAmount
```

开仓路径**没有**“付不清就清零”分支：付不起直接 revert。资金动作固定四步、调用点上没有任何条件分支（`incrementClaimable*` 内部 `delta == 0` 时自身早退 no-op），顺序为：
`settleFundingFees(positionVault, ..., negativeFundingFeeAmount, positiveFundingFeeAmount)` → `incrementClaimableFeeAmount(feeReceiverAmount, POSITION_FEE_TYPE)` → `incrementClaimableUiFeeAmount(uiFeeAmount)` → `positionVault.transferOut(collateralToken, market.vault, feeAmountForPool)`。

注意开仓侧的 `incrementClaimableFeeAmount` 传的是**完整的 `feeReceiverAmount`**（开仓恒无清算费，两者等价），而减仓侧传的是 `feeReceiverAmount − liquidationFeeAmountForFeeReceiver`（§8.5）。

`MarketUtils::settleFundingFees` 只按**该仓 negative 与 positive 的净差**动账：净负 → `incrementClaimableFeeAmount(差额, FUNDING_FEE_TYPE)`（资金留在 PositionVault，只记账）；净正 → LP Vault `transferOut` 差额给 PositionVault；相等 → 不动。

**两条路径传给它的第一个实参不同**：开仓/加仓传的是**应付额** `fees.funding.negativeFundingFeeAmount`（付不起早已 revert，应付即实付）；减仓/平仓/清算传的是 `payForCost` 返回的**实付额** `amountPaidInCollateralToken`（§9.4 ①），抵押品不够时它小于应付额，差额只体现在 `InsufficientFundingFeePayment` 事件里，链上不再补记。复算 `claimableFeeAmount(FUNDING_FEE_TYPE)` 增量时必须用实付额，不能直接拿费用事件里的 `negativeFundingFeeAmount` 减 `positiveFundingFeeAmount`。

### 9.4 消费路径二：减仓 / 平仓 / 清算（**不用** `totalCostAmount`，走分步瀑布）

`DecreasePositionCollateralUtils::processCollateral` 的顺序敏感瀑布：

```text
output    = (basePnlUsd > 0) ? basePnlUsd / pnlTokenPrice.max : 0      # 向下取整；pnlToken 即 collateralToken
                                                                       # 同步由 LP Vault transferOut 到 PositionVault
remaining = position.collateralAmount + positiveFundingFeeAmount

① pay(negativeFundingFeeAmount × collateralTokenPrice.min)
   → settleFundingFees(实付额 amountPaidInCollateralToken, positiveFundingFeeAmount)
   → 实付 < negativeFundingFeeAmount 时另发 InsufficientFundingFeePayment 事件
   → remainingCostUsd > 0 ⇒ handleEarlyReturn(step = "funding")

② pay(-basePnlUsd)                       （仅当 basePnlUsd < 0）
   → 实付额 transferOut 到 LP Vault（亏损 100% 归 LP）
   → remainingCostUsd > 0 ⇒ handleEarlyReturn(step = "pnl")

③ pay(totalCostAmountExcludingFunding × collateralTokenPrice.min)
   → remainingCostUsd == 0 ⇒ 正常分账（§8.5）
   → remainingCostUsd  > 0 ⇒ fees = getEmptyFees(fees)，再 handleEarlyReturn(step = "fees")

④ 提取抵押：先把 order.initialCollateralDeltaAmount 夹到 remaining 以内
   （超出则发 OrderCollateralDeltaAmountAutoUpdated），再 remaining -= 它、output += 它
```

`processCollateral` 到 ④ 就结束了，但**全平还有第 ⑤ 步，发生在它外面**（`DecreasePositionUtils::decreasePosition`，紧随 `position.setCollateralAmount(values.remainingCollateralAmount)` 之后）：

```text
⑤ if position.sizeInUsd == 0 OR position.sizeInTokens == 0:      # 全平
       output.outputAmount += position.collateralAmount          # 即 ④ 之后的 remaining，全额并入 output
       position 的 size / collateral 全部置 0 并从 store 移除
   else:                                                          # 部分平仓
       只把 latestNegative/PositiveFundingFeePerSize 写回仓位，remaining 留在仓位上
```

**漏掉 ⑤ 会系统性少算“用户到手”**——全平时它通常是 output 里最大的一项。交叉佐证：`TestCode/src/reconciliation/formulas.ts::decreaseWaterfall` 的 `fullClose ? remaining : min(requestedWithdrawal, remaining)` 正是把 ④⑤ 合并成一条。

`payForCost(costUsd)`（`::payForCost`）：

```text
if costUsd == 0:  原样返回，不动任何余额，remainingCostUsd = 0

need = ceil(costUsd / collateralTokenPrice.min)          # Calc.roundUpDivision

先扣 output（盈利垫费）：min(output, need)
再扣 remainingCollateral：min(remainingCollateral, 剩余 need)

若仍有缺口：
    remainingCostUsd = 剩余need × collateralTokenPrice.min
```

第三行是 **v0.3.2 的修正**：v0.3.1 写的是 `result.remainingCostUsd = remainingCostInOutputToken`（把 token 数量当 USD 记），v0.3.2 补上了 `× collateralTokenPrice.min`。该值只进 `InsolventClose` 事件与 `InsufficientFundsToPayForCosts` 的 revert 参数，不影响资金流，但影响断言。

注意①③两步传入的 `costUsd` 已经是“token 数量 × price.min”，再被 `roundUpDivision` 除回去正好还原，无二次取整误差；只有②步传的是真 USD（`-basePnlUsd`），会向上取整成 token 数量。

### 9.5 付不清时：**费用全部清零，不是按比例削减**

```text
③ 之后：
if remainingCostUsd > 0:
    fees = getEmptyFees(fees)            # 全部归零，不做任何比例分摊
    return handleEarlyReturn(params, values, fees, cache, "fees")
```

`getEmptyFees` 归零的字段：`positionFeeAmount`、`positionFeeFactor`、`protocolFeeAmount`、`positionFeeReceiverFactor`、`feeReceiverAmount`、`feeAmountForPool`、`positionFeeAmountForPool`、`totalCostAmount`、`totalCostAmountExcludingFunding`、`totalDiscountAmount`、`balanceWasImproved`，以及 referral / pro / ui / liquidation 四个子结构的**全部**字段和 `funding.negativeFundingFeeAmount`。
**只保留**：`collateralTokenPrice`、`funding.positiveFundingFeeAmount`、`funding.latestNegativeFundingFeePerSize`、`funding.latestPositiveFundingFeePerSize`（后两者用于部分平仓时刷新仓位的 per-size 锚）。

**关键：清零只发生在第 ③ 步**。`handleEarlyReturn` 自己**不清零后再发事件**，它的实际顺序是：

```text
handleEarlyReturn(params, values, fees, cache, step):
    if !isInsolventCloseAllowed:
        revert InsufficientFundsToPayForCosts(remainingCostUsd, step)     # step ∈ {"funding","pnl","fees"}

    emit PositionFeesInfo(..., isIncrease = false, fees)     # 用【传入的】fees，不是清零后的
    emit InsolventClose(collateralAmount, basePnlUsd, remainingCostUsd, step)
    return (values, getEmptyFees(fees))                      # 返回值才是清零的
```

因此三种 step 下的事件内容不同：

| step | 触发点 | `PositionFeesInfo` 内容 | tx 末尾 `PositionFeesCollected`（`DecreasePositionUtils:325`） |
| --- | --- | --- | --- |
| `"funding"` | ① 付资金费缺口 | 携带**原始非零**费用（`positionFeeAmount` / `liquidationFeeAmount` / `uiFeeAmount` / `totalCostAmount` 都是应收额） | 全 0 |
| `"pnl"` | ② 付亏损缺口 | 同上，**原始非零** | 全 0 |
| `"fees"` | ③ 付费用缺口 | 已被 ③ 清零，全 0 | 全 0 |

所以一笔 insolvent close 会出现**两条费用事件**，`"funding"` / `"pnl"` 两种 step 下二者数值还相反：`PositionFeesInfo` 里的非零数是**应收而一分未收**的额度（源码注释亦承认此时 `fundingFeeAmount` 与 `feeAmountForPool` 的值可能不准），`PositionFeesCollected` 的全 0 才是实际入账。取数与断言必须写明事件名。

后果（测试断言直接依赖）：

- `PositionUtils::handleReferral` 收到的是 `processCollateral` 的返回值（已清零）→ `affiliateRewardAmount = 0`，该笔不发推荐奖励；三种 step 皆然；
- 不向 LP Vault 转 `feeAmountForPool`，也不增记 `POSITION_FEE_TYPE` / `LIQUIDATION_FEE_TYPE` 的 `claimableFeeAmount` 与 `UI_POSITION_FEE_TYPE` 的 `claimableUiFeeAmount`（这三笔只在 ③ 的 `remainingCostUsd == 0` 分支里发生）。**`FUNDING_FEE_TYPE` 不在此列**：`settleFundingFees` 在 ① 的早退判断之前就已调用，净负时照常增记 `FUNDING_FEE_TYPE`（见下条）；
- ①②两步已经发生的动账（funding 记账、亏损转 LP）**不回滚**，早退是 `return` 而不是 `revert`，交易继续完成平仓。

早退门槛（`processCollateral` 开头即算好，见 `ProcessCollateralCache.isInsolventCloseAllowed`）：

```text
isFullyClosed = order.isSizeDeltaUsd()
              ? order.sizeDelta == position.sizeInUsd
              : order.sizeDelta == position.sizeInTokens
isInsolventCloseAllowed = isFullyClosed
                        AND (Order.isLiquidationOrder(orderType) OR secondaryOrderType == Adl)
```

**v0.3.2 与 v0.3.1 的结构差异**：v0.3.1 的分账门是 `remainingCostUsd == 0 && amountPaidInSecondaryOutputToken == 0`，存在“清零但不早退”的第三条路径；v0.3.2 删除了 secondary output token，门简化为 `remainingCostUsd == 0`，于是**③步清零 ⇔ ③步早退**必然同真同假。

### 9.6 消费路径三：清算判定（`totalCostAmount` 的第三个用途）

`PositionUtils::isPositionLiquidatable`：

```text
collateralCostUsd = fees.totalCostAmount × collateralTokenPrice.min
```

此处的 `fees` 由 `isLiquidation = false`、`uiFeeReceiver = address(0)`、`sizeDeltaUsd = position.sizeInUsd()` 求得，因此 `totalCostAmount = positionFeeAmount + negativeFundingFeeAmount - totalDiscountAmount`（无清算费、无 UI Fee）。详见 §11。

### 9.7 数值例子（自验算，接 §8.7 的清算场景）

```text
positionFeeFactor = 0.0005e30 = 5e26，sizeDeltaUsd = 3e34，collateralTokenPrice.min = 1e24
positionFeeAmount   = 3e34 × 5e26 / 1e30 / 1e24 = 1.5e31 / 1e24 = 1.5e7      # 15 USDC
liquidationFeeAmount= 9e7                                                     # 90 USDC（§8.7）
uiFeeAmount         = 0                                                       # 清算单 uiFeeReceiver = 0
totalDiscountAmount = 0                                                       # 无 referral / pro
negativeFundingFeeAmount = 2e6                                                # 2 USDC

totalCostAmountExcludingFunding = 1.5e7 + 9e7 + 0 - 0 = 1.05e8                # 105 USDC
totalCostAmount                 = 1.05e8 + 2e6      = 1.07e8                  # 107 USDC
```

若该仓抵押 3,000 USDC（3e9）、`basePnlUsd = -2,950e30`（basePnlUsd < 0 ⇒ output 起点为 0）：

```text
① 付 funding：costUsd = 2e6 × 1e24 = 2e30 → need = 2e6
   remaining 3e9 - 2e6 = 2.998e9                                  # 2,998 USDC
② 付亏损：costUsd = 2.95e33 → need = ceil(2.95e33 / 1e24) = 2.95e9
   remaining 2.998e9 - 2.95e9 = 4.8e7                              # 48 USDC
③ 付费用：costUsd = 1.05e8 × 1e24 = 1.05e32 → need = 1.05e8（105 USDC）
   output = 0，remaining 只有 4.8e7 → 实付 4.8e7，缺口 5.7e7
   remainingCostUsd = 5.7e7 × 1e24 = 5.7e31                        # 57 USD
```

因是全平清算单，`isInsolventCloseAllowed = true` → 第③步先 `getEmptyFees`，再发全 0 的 `PositionFeesInfo` + `InsolventClose(step = "fees")`，交易完成；tx 末尾的 `PositionFeesCollected` 同样全 0。这笔清算实际**一分费都没收到**（15 / 90 / 0 全归 0），48 USDC 留在 PositionVault 无归集记录（gap 台账 G-05）。

### 9.8 核对要点

1. 减仓路径不要用 `totalCostAmount` 去凑余额：链上按 ①funding ②亏损 ③费用 三段分别扣，再走 ④提取 / ⑤全平返还；全平且偿付充足时才与线性式等值，一旦任一段付不清，结果与线性式发散。
2. `output` 先垫费再退款：盈利先进 `output`，费用优先扣 `output` 再扣抵押品，所以“到手 = 盈利 − 费用”只在盈利足够覆盖费用时成立；全平时还要加上 ⑤ 的剩余抵押品全额返还。
3. 事件里没有 `totalCostAmountExcludingFunding` 和 `totalDiscountAmount`，只有 `totalCostAmount`；要复核折扣得从条件项 `referral.traderDiscountAmount` / `pro.traderDiscountAmount` 取 `max`。
4. 费用取数先认事件名：常规开仓/减仓/清算读 `PositionFeesCollected`，`PositionFeesInfo` **只在** insolvent close 时出现。看到 `InsolventClose` 时，`PositionFeesCollected` 必然全 0，而同笔的 `PositionFeesInfo` 只有 `step = "fees"` 才全 0——`step = "funding"` / `"pnl"` 的 `PositionFeesInfo` 携带**未清零的应收额**，不能据此判定“已收费”。
5. 不要把“费用为 0”直接当成没收费的缺陷：先查同笔是否有 `InsolventClose`。
6. `remainingCostUsd` 是 30 位 USD（v0.3.2 起），跨版本比对旧证据时注意 v0.3.1 该字段是 token 数量。
7. 清算 tx 里不要断言 keeper 收益：清算单 `executionFee = 0`，既无 `KeeperExecutionFee` 事件也无原生代币转出（§8.5）。

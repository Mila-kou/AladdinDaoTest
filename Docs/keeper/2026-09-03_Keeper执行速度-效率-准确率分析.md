## 0. 结论摘要

| 维度 | 结论 | 关键数字 |
|---|---|---|
| **速度** | 设计上是**秒级**，不是亚秒级。市价单端到端 **≈3–5s**（不含 OrderCreated 所在区块本身）；触发单 **≈5–8s**；清算 **≈6–9s**。时延大头是三段固定节拍：worker 轮询 2s + 价格录入周期 ≈2.3s + 收据确认 ≈2–2.5s | 见 §2 预算表 |
| **效率** | 单 worker 进程**严格串行**（一次一单），单分片吞吐 **≈0.3 单/秒 ≈ 17–20 单/分**。扩容只能靠加分片（每分片一把私钥）。producer 是**单实例不可水平扩展**（价格环写入 check-then-act 非原子，`priceBuffer.ts:100-108` 自述） | 见 §3 |
| **准确率** | 链上执行价的**正确性有合约兜底**（keeper 只提交签名报文，价格由合约解码），但 keeper 自身的**决策正确性**有 5 处结构性风险，其中 2 处高危：① 触发单用 **mid 价**弹出、用 **bid/ask** 校验，导致 4 类 Stop 单可能**漏触发**；② token decimals 只来自 SDK 静态表、无链上交叉校验，一旦与链上登记不一致，触发索引会**整体错位 10^n 倍** | 见 §4 |
| **可测性** | **全链路没有任何时延指标**——`keeper:metrics:*` 只有 4 类计数器，heartbeat 只有 attempts/failures，无 P50/P95。要测"速度"必须先从日志时间戳反推或加埋点 | 见 §5 |

## 1. 时延链路拆解（速度）

### 1.1 四条链路的节拍来源

```
                     ┌─ 事件发现 ─┐  ┌─ 排队 ─┐  ┌─ 组价 ─┐  ┌─ 广播 ─┐  ┌─ 确认 ─┐
市价单   OrderCreated → ws 即时/轮询5s → 2s 轮询 → Redis 本地 → 4~5 次 RPC → 500ms 轮询 × 2s 出块
触发单   价格变动     → 录入周期 ≈2.3s  → 2s 轮询 → 同上      → 同上        → 同上
清算     价格变动     → 录入周期 ≈2.3s  → 2s 轮询 → +2 次预检 RPC → 同上    → 同上
中继     API 写队列   → 250ms 轮询      → —        → 同上        → 同上
```

### 1.2 逐段依据

| 段 | 值 | 代码 |
|---|---|---|
| WS 事件发现 | 出块即达（`auto` = hybrid，ws 加速 + 轮询兜底权威游标） | `providers/index.ts`、`providers/websocketProvider.ts` |
| 轮询事件发现 | `KEEPER_POLL_INTERVAL_MS` 默认 **5000ms**（ws 不可用时唯一通路） | `chain/env.ts:197` |
| 价格录入周期 | **不是 1Hz**。`scheduleNext` 是「跑完再排下一次」，真实周期 = `intervalMs + 本次抓取耗时` = 1000ms + 1342ms ≈ **2.34s**（26 token @ 并发 8，团队实测值见 `.env.example`） | `chain/priceRecorder.ts:244-250` |
| worker 出队节拍 | ordWorker **2000ms（硬编码，无 env 开关）**；adl/liq 2000ms（可 env 覆盖）；relWorker 250ms | `entrypoints/ordWorker.ts:110`、`adlWorker.ts:110`、`liqWorker.ts:155`、`env.ts:708` |
| 快排（fast-drain） | 成功消费一条后 `setImmediate` 立即再拉，积压时可消掉 2s 空转；但**重试/空队列/抛错不快排** | `infra/workerRunner.ts:524-526` |
| 组价 | 纯 Redis 本地：每 token 一次 `LRANGE`（典型 2 token = 2 次往返）+ 最多 15 份报文 ABI 解码 | `chain/priceBuffer.ts:122-140`、`minMaxPriceSelector.ts:145-167` |
| 广播 | 无 nonce/gas 覆写，viem 自行 `eth_getTransactionCount(pending)` + `eth_estimateGas` + 费率读块 + `eth_sendRawTransaction` ≈ **4~5 次 RPC 往返** | `ordWorker.ts:744-765`、`chain/submitGate.ts:5-8` |
| 收据确认 | `pollingInterval` 已从 viem 默认 4000ms 降到 **500ms**（`KEEPER_RPC_POLLING_INTERVAL_MS`），Base 2s 出块 → ≈2–2.5s | `chain/wallet.ts:184-191`、`env.ts:638` |
| 清算额外预检 | `Reader.getPosition` + `Reader.isPositionLiquidatable` 两次串行读 | `entrypoints/liqWorker.ts:370-395` |

### 1.3 端到端预算（典型值，Base 2s 出块 + 80ms RTT）

| 链路 | 发现 | 排队 | 组价 | 广播 | 确认 | **合计** |
|---|---|---|---|---|---|---|
| 市价单（ws） | ~0s | 0–2s（均 1s） | ~0.1s | 0.3–0.5s | 2–2.5s | **≈3–5s** |
| 市价单（仅轮询） | 0–5s | 0–2s | ~0.1s | 0.3–0.5s | 2–2.5s | **≈5–10s** |
| 触发单 | 0–2.3s | 0–2s | ~0.1s | 0.3–0.5s | 2–2.5s | **≈5–8s** |
| 清算（价格驱动） | 0–2.3s | 0–2s | ~0.3s | 0.3–0.5s | 2–2.5s | **≈6–9s** |
| 清算（费用驱动，非价格变动触发） | **0–30s**（等 producer tick 重算近似清算价） | 0–2s | ~0.3s | 0.3–0.5s | 2–2.5s | **≈33–36s** |
| 中继（gasless） | ~0s | 0–0.25s | ~0.1s | 0.3–0.5s | 2–2.5s | **≈2.7–3.5s** |

> 「费用驱动清算」那一行是最容易被忽略的：清算索引里的近似清算价只在 `store.refresh()`（producer 30s tick，`producer.ts:915-932`）重算，价格钩子只做"价格穿越"比对。纯粹由资金费/借贷费累积推到爆仓线、而指数价没动的仓位，最坏要等满一个 30s tick 才会被发现。

## 2. 吞吐与效率

### 2.1 单分片吞吐上限

`startReliableWorker` 用 `inFlight` 布尔量**严格串行**——一个 worker 循环同时只处理一条（`infra/workerRunner.ts:247, 253-256`）。所以：

```
单分片吞吐 = 1 / 单条耗时 ≈ 1 / (0.1 + 0.4 + 2.3) ≈ 0.35 单/秒 ≈ 21 单/分
```

扩容路径只有**加分片**：每个 ordWorker 进程一把独立私钥（`ORDER_KEEPER_PRIVATE_KEYS` + `KEEPER_WALLET_INDEX`，`chain/wallet.ts:10-18`），多分片竞争消费同一个队列 key。**同一把私钥跑两个进程会撞 nonce**（`submitGate` 只在进程内排队，`chain/submitGate.ts:26-29` 明确写了这条边界）。

producer 则**不能水平扩展**：价格环写入是 `LINDEX → LPUSH → LTRIM` 的 check-then-act，两个 producer 会写重复槽位（`chain/priceBuffer.ts:100-108` 自述，待改 Lua）。

### 2.2 效率上已经做对的部分（回归时不要改坏）

- `KEEPER_MULTICALL_BATCH_BYTES=8192`（viem 默认 1024）——团队实测 marketState refresh **提速 4.5 倍**（`.env.example`；`store.ts:84-100`）
- `KEEPER_RPC_POLLING_INTERVAL_MS=500`（viem 默认 4000）——每笔省约 4s 死等，直接把单分片上限从「两个区块一单」拉到现在的水平（`wallet.ts:161-168`）
- `KEEPER_ORACLE_FETCH_CONCURRENCY=8`——实测 26 token：并发 1 → 7186ms，8 → 1342ms，16 → 811ms
- 市价单**本地过期闸**：先本地按 `REQUEST_EXPIRATION_TIME` 判死，省掉一整笔"注定 revert"的 tx + 收据等待（`ordWorker.ts:637-668`）
- ordWorker 双循环分离：订单执行与二级价格刷新各自一个 runner，`submitGate` 只锁广播、不锁收据等待，互不阻塞（`ordWorker.ts:934-960`）

### 2.3 效率上的四个真实问题

**E-1（高）重试退避在"占坑"状态下 sleep，造成队头阻塞。**
`await sleep(delay)` 发生在 `inFlight = true` 期间（`workerRunner.ts:505`；pending-tx 分支同理 `:455`）。默认 `RETRY_DELAY_MS = 5000`（`domain/types.ts:369`），buffer-gap 预算更狠：**10 次 × 5000ms = 50s**（`workerRunner.ts:242-243`）。也就是说单个 token 的喂价断流，会让**整个 orders 队列**停摆 50s，而不只是那一条单。更讽刺的是：睡醒之后该条目是 `LPUSH` 回队列头部、而消费端 `RPOPLPUSH` 从尾部取（`infra/queue.ts:27`、`workerRunner.ts:508`），即它本来就排到最后去了——这 5s/50s 纯属白等。

**E-2（中）marketState 的两个重读盘无并发上限，靠 viem 无界扇出。**
`loadPositions` 有 `KEEPER_STATE_POSITIONS_READ_CONCURRENCY=4` 兜着（`store.ts:547-585`），但 `loadLiquidationChecks`（`store.ts:833`）和 `loadPositionPnl`（`store.ts:720`）是**一次 multicall 塞入全部仓位**。viem 内部按 8192 字节切块后用 `Promise.allSettled` **全部并发下发**（`node_modules/viem/_cjs/actions/public/multicall.js:78`）。`isPositionLiquidatable` 单次 calldata ≈420 字节 → 每块 ≈19 条 → **5000 仓位 = 一次性打出 ≈263 个并发 `eth_call`**。这不只是效率问题，见 A-4。

**E-3（低）价格选择器重复解码。**
录入时已把 `min/max` 解好存进槽位（`priceRecorder.ts:175-192`），选择器却对每个 in-window 槽位重新 `decodeReport`（`minMaxPriceSelector.ts:146-149`）。最多 15 槽 × N token 的冗余 CPU，量级不大但是纯浪费。

**E-4（低）事件轮询用 `console.log` 打印整个解码数组。**
`pollingProvider.ts:178` 每轮把 `decodedLogs` 整体打印，且走的是 `console` 而非结构化 logger（不受 `LOG_LEVEL` 控制）。批量下单时日志量会暴涨。

## 3. 准确率（判定正确性）

先划清边界：**链上成交价的正确性不依赖 keeper 的算术**——keeper 只把 Chainlink 签名报文原文 `fullReport` 提交上去，价格由合约自己解码校验。keeper 的 `min/max/decimals` 只影响**它自己的决策**（要不要弹出、要不要清算、挑哪个槽位）。下面按危害排序。

### A-1（高危）触发单：**mid 价弹出、bid/ask 校验**，4 类 Stop 单会漏触发

- 弹出侧：`triggerIndex.popReady(token, decimals, currentIdx)`，其中 `currentIdx = (min + max) / 2n` 是**中间价**（`producer.ts:1187`、`triggerIndex.ts:243`）
- 校验侧：ordWorker 用**方向标量**（买用 ask=max，卖用 bid=min）跑 `isTriggerCrossed`（`ordWorker.ts:299-315`、`minMaxPriceSelector.ts:150-156`）

两者不等价，且**不对称**：

| 触发条件 | 归属桶 | 弹出条件 | 关系 | 后果 |
|---|---|---|---|---|
| `ask ≤ trig`（LimitIncrease 多、LimitDecrease 空） | fall | `mid ≤ trig` | ask ≥ mid ⇒ 成立必弹出 | 只多弹，**不漏** |
| `bid ≥ trig`（LimitIncrease 空、LimitDecrease 多） | rise | `mid ≥ trig` | bid ≤ mid ⇒ 成立必弹出 | 只多弹，**不漏** |
| `bid ≤ trig`（**StopLossDecrease 多**、**StopIncrease 空**） | fall | `mid ≤ trig` | bid ≤ mid ⇒ **成立未必弹出** | **漏触发** |
| `ask ≥ trig`（**StopLossDecrease 空**、**StopIncrease 多**） | rise | `mid ≥ trig` | ask ≥ mid ⇒ **成立未必弹出** | **漏触发** |

- 漏触发幅度 = 半个 Chainlink bid/ask 价差。价格继续走会自然补上，但**价格恰好停在价差带内并横盘时，止损单会一直不执行**。
- 反方向的"只多弹"也不是免费的：多弹 → 入队 → 出队 → 校验不过 → 重新 ZADD 回索引（`ordWorker.ts:702-723`），价格在触发价附近震荡时可以每个录入周期（≈2.3s）循环一次，持续占用串行 worker 槽位，挤压真单。
- 代码注释里承认了这个设计（`ordWorker.ts:694-700` "the index pops on the mid price while we verify against the side-relevant bid/ask scalar"），但只讨论了"多弹"，**没有讨论"漏弹"**。

**测试点**：把 SL/StopIncrease 的 triggerPrice 设在当前 mid 与 bid（或 ask）之间，喂稳定价 → 期望执行，实际预期不执行。

### A-2（高危）token decimals 只有 SDK 单一来源，无链上交叉校验

`lookupTokenDecimals` 只查 `@fx-io/sdk` 静态 token 表（`chain/marketConfig.ts:59-66`），录入时还有 `?? 18` 兜底（`priceRecorder.ts:171`）。而触发索引的分数计算是：

- 订单侧分数：`scaleBigIntPriceToScore(triggerPrice_链上刻度, decimals_SDK)`（`triggerIndex.ts:167`）
- 价格侧阈值：`scaleBigIntPriceToScore(mid_按SDK_decimals算出的刻度, decimals_SDK)`

两边的 `decimals` 都取自 SDK，但 `triggerPrice` 来自**链上 Order 结构（链上 decimals 刻度）**。SDK 与链上不一致时，两侧相差 `10^(D_sdk − D_chain)`：

- SDK=18 / 链上=8（WBTC 类）→ 订单分数**大 10^10 倍** → fall 桶**每个 tick 全弹**（无限重弹循环），rise 桶**永不弹**
- 反向不一致则症状对调

这不是假想：工作区已有过 WBTC 合成 index token 8→18 位的登记修正记录。keeper 侧**没有任何启动期校验**去比对 SDK decimals 与链上 DataStore 登记。

**测试点**：在 fork 上故意让某 token 的 SDK 登记与链上登记差 10 位，下一张限价单和一张止损单，观察索引行为。这条应作为**上线前置校验项**（建议 boot 时读链上 decimals 断言）。

### A-3（中）成交价是"10 秒回看窗口内的方向极值"，不是"执行那一刻的价"

组价窗口 `fromMs = max(validFromTime, updatedAtTime, now − 10s)`（`domain/orders/oracleWindow.ts:30`），然后在窗口内取方向极值——多头开仓取 `max(ask)`、空头开仓取 `min(bid)`（`minMaxPriceSelector.ts:150-167`）。设计意图是反 MEV（keeper 不能在窗口里挑对自己有利的时刻），但代价是：

- **新市价单**：`updatedAtTime` 很近，窗口被压到 1–2s，只有 1–2 个槽位，偏离很小
- **老触发单**：`updatedAtTime` 是下单时刻，`now − 10s` 生效，窗口拉满 10s，≈4 个槽位取极值 → 成交价系统性地**偏向不利于用户**，偏离幅度 = 10s 内该方向的价格极差

也就是说**同一个市场、同一个方向，触发单的滑点系统性大于市价单**。这在前端显示值核对（Phase 1/2）里是可观测的偏差来源，值得单独立用例。

### A-4（中）RPC 限流会**静默缩小清算覆盖面**

承 E-2：`loadLiquidationChecks` 的所有分块并发下发，`allowFailure: true` 时任何一块失败 → 该块内所有仓位在**本 tick 完全没有清算判定**。代码确实会 WARN（`store.ts:117-130` "those positions are NOT represented in this tick"）并单独重跑一条来打印 revert 原因，但**没有重试、没有降级、没有把失败仓位保留上一代结果**。仓位规模上去后撞到 provider 限流，就是"一部分仓位周期性地对清算隐形"。

**测试点**：制造 429/超时，断言 WARN 出现且 `failed > 0`，并确认这些仓位在该 tick 未进入清算队列。

### A-5（中）`MAX_RETRIES = 1`：连续两次瞬时故障 = 订单被永久丢弃

`domain/types.ts:368`。重试预算耗尽后直接 `ackFromProcessing` 丢弃（`workerRunner.ts:473-495`），而 **`OrderCreated` 只发一次**，默认 `auto` 事件模式下**没有任何机制会重新发现这张单**（`onchain-all-orders` 回捞 provider 存在但不是默认）。所以：RPC 抖两下 → 用户的单永远躺在链上不执行，直到人工介入。

配套的错误分类还有一层风险：`classifyError` 先按 selector/错误名精确判，判不出来时**退化为消息子串匹配**（`infra/errors.ts:199-202`，大小写不敏感 `includes`）。一旦某个 RPC 层的报错消息里恰好含有终止类错误名，就会被判成 `terminal` → **不消耗重试预算直接丢弃**（`workerRunner.ts:396-402, 434-446`）。

### A-6（低）清算/ADL 判定基于最多 30s 前的快照

价格钩子用的近似清算价来自上一次 `store.refresh()`（`producer.ts:1067-1085`），费用累积在两次 refresh 之间不反映。安全性上有兜底——liqWorker 广播前会用**同一组数值价格**跑 `Reader.isPositionLiquidatable` 精确复核（`liqWorker.ts:363-369` 明确写了"近似永不授权执行"），所以不会误清算；代价是**延迟**（见 §1.3 最后一行）和无效入队。

## 4. 可测性缺口（做性能测试前必须先解决）

1. **完全没有时延指标**。`keeper:metrics:*` 只有 4 个计数器（buffer coverage gap ×4 类、过期单、relay 资金不足、context rejected），heartbeat 只有 attempts/failures/lastFailureTs（`infra/heartbeat.ts:96-110`）。**没有 P50/P95、没有分段耗时、没有队列深度时间序列**。
2. 唯一可用的时间锚点是队列条目里的 `createdAt`（`domain/orders/enqueue.ts:88-91`）与日志时间戳。要量化"速度"，最低成本方案是：解析 producer 的 `order queued` 与 ordWorker 的 `transaction confirmed` 两条日志按 `orderKey` 配对，得到端到端时延；再用 `tick complete` 的 `phaseMs`（`store.ts:270-277`，这个已经有分段归因，做得很好）看 producer 侧。
3. `.env.example` 里关于价格录入的注释与实现有出入：写的是"重叠的 tick 会被跳过"，但 `scheduleNext` 是串行链式调度（`priceRecorder.ts:244-250`），`tickInFlight` 恒为 false，永远不会发生重叠。写断言时以代码为准。

## 5. 建议的测试用例骨架

### 5.1 性能类（需要能跑起来的环境，见前置约束）

| ID | 场景 | 核对数据 | 期望 |
|---|---|---|---|
| PERF-01 | 单张市价单端到端 | `order queued` → `transaction confirmed` 时间差 | ≤5s（ws 模式）；分段占比与 §1.3 预算一致 |
| PERF-02 | 50 张市价单一次性下单、单分片 | 全部确认耗时 / 队列最大深度 | ≈50 ÷ 0.35 ≈ 145s；无丢单 |
| PERF-03 | 同 PERF-02，3 分片（3 把私钥） | 总耗时 | ≈1/3，且**无 nonce 冲突报错** |

## 3. 订单数量转换

订单只带一个 `sizeDelta` 和一个计价开关 `isSizeDeltaUsd`（`Order.Flags.isSizeDeltaUsd`）：为 `true` 时 `sizeDelta` 是 USD（`1e30`），为 `false` 时是 index token 数量（token decimals）。合约必须把这一个数展开成成对的 `(sizeDeltaUsd, sizeDeltaInTokens)`，再去更新仓位与 OI。

**加仓与减仓的结构完全不同，这是本节最容易算错的地方：**

| | 加仓 | 减仓 |
| --- | --- | --- |
| 换算依据 | **执行价**（含点差） | **仓位自身的 sizeInUsd / sizeInTokens 比例**（与执行价无关） |
| 步骤 | 两步：`getIncreaseOrderSize` 预解析 → `getExecutionPriceForIncrease` **覆盖重算另一半** | 一步：`getDecreaseOrderSize` 等比销账，**不覆盖重算** |
| 事后闸门 | 无 | `decreasePosition` 四道尺寸闸门（夹紧 / revert / 强制全平） |

### 3.1 加仓订单

**第一步：`getIncreaseOrderSize` 预解析**

源码锚点：`src/position/PositionUtils.sol::getIncreaseOrderSize`（L492-515），由 `getExecutionPriceForIncrease`（L593）在 L599 调用。

```text
rawSizeDelta = order.sizeDelta

早退：rawSizeDelta == 0 → (sizeDeltaUsd, sizeDeltaInTokens) = (0, 0)

isSizeDeltaUsd = true：
  sizeDeltaUsd       = rawSizeDelta                                 （L504/L507，最终值）
  Long  sizeDeltaInTokens = rawSizeDelta / indexPrice.max           （L504，向下取整；中间量）
  Short sizeDeltaInTokens = ceil(rawSizeDelta / indexPrice.min)     （L507，Calc.roundUpDivision；中间量）

isSizeDeltaUsd = false：
  sizeDeltaInTokens = rawSizeDelta                                  （L510，最终值）
  Long  sizeDeltaUsd = rawSizeDelta × indexPrice.max                （L511-512，精确乘，无取整；中间量）
  Short sizeDeltaUsd = rawSizeDelta × indexPrice.min                （同上）
```

**这一对里只有「随后会被覆盖重算的那一半」是纯中间量**，另一半（恒等于 `rawSizeDelta`）从头到尾不变，就是最终落账值。必须按计价模式分开看：

| 计价模式 | 恒等保留 = 最终值 | 被覆盖 = 纯中间量 |
| --- | --- | --- |
| `isSizeDeltaUsd = true` | `sizeDeltaUsd = rawSizeDelta`（写进 `position.sizeInUsd`、OI、事件；同时是 L604 早退判定量、`getPriceImpactSpread` 的 orderSize、L637/L641 覆盖重算的被除数） | `sizeDeltaInTokens`（L637/L641 用 `executionPrice` 覆盖） |
| `isSizeDeltaUsd = false` | `sizeDeltaInTokens = rawSizeDelta`（写进 `position.sizeInTokens`、OI、事件；同时是 L651/L655 覆盖重算的被乘数） | `sizeDeltaUsd`（L651/L655 用 `executionPrice` 覆盖；覆盖前承担 L604 早退判定与 `getPriceImpactSpread` 的 orderSize） |

中间量的下游只有 `PositionPricingUtils.getDynamicSpread`（`getExecutionPriceForIncrease` L617-627 把这一对作为 `usdDelta` / `tokenDelta` 传入）；token 计价下它在被覆盖前还是 L604 `sizeDeltaUsd == 0` 早退判定的被测量（见上表）。两种计价模式下，中间量都**不会**写进事件、仓位或 OI：

- `usdDelta` 决定 `priceImpactSpread` 的 orderSize 与 ask/bid depth 选择（`getPriceImpactSpread`，`PositionPricingUtils.sol` L188-215；该调用在 L164 发生，早于下面的覆写）；
- `tokenDelta` 决定 skew：`getNextOpenInterest(params, true)` 内部会把 `params.usdDelta` **覆写**成 `tokenDelta × indexPrice.midPrice()`（L303）再算 next OI、`balanceWasImproved`（L254-258）与 `skewRef`（L223/L236-251）。

L604 早退的实际触发条件两种计价模式下等价，都是 `order.sizeDelta == 0`：USD 计价时 `sizeDeltaUsd` 恒等于 `rawSizeDelta`；token 计价时 `rawSizeDelta == 0` 已在 `getIncreaseOrderSize` 内部早退成 `(0, 0)`，要靠 `rawSizeDelta × price == 0` 额外命中则需 index 价为 0，实际不可达。

所以 USD 计价加仓时，用 `indexPrice.max/min` 当作 `sizeDeltaInTokens` 的最终除数是错误口径（见 3.4 数值例，$3000 / 0.1% 点差下，预解析值比最终值高约 0.1%——等于点差比例，wei 级尾差见 3.4；足以让 `sizeInTokens`、entry price、PnL 的期望值全错）；token 计价加仓则不存在这个坑，`sizeDeltaInTokens` 本身即最终值。

**第二步：按执行价覆盖重算**

源码锚点：`src/position/PositionUtils.sol::getExecutionPriceForIncrease`（L593-670）。

```text
早退（L604-615）：sizeDeltaUsd == 0 →
      返回 { sizeDeltaUsd: 0, sizeDeltaInTokens: 0,
             executionPrice: indexPrice.pickPrice(position.isLong)   // Long→max，Short→min
             dynamicSpread: 0, balanceWasImproved: false }
      —— 不算点差，也不做 acceptablePrice 校验（纯加保证金路径）

否则先算 dynamicSpread（§4.1），再算 executionPrice（§4.5）：
  Long  executionPrice = ceil(indexPrice.max × (1e18 + dynamicSpread) / 1e18)   // Precision.mulDiv(..., true)
  Short executionPrice =      indexPrice.min × (1e18 - dynamicSpread) / 1e18    // 整数除法，向下取整

isSizeDeltaUsd = true（sizeDeltaUsd 保持 rawSizeDelta 不变，只覆盖 token 数）：
  Long  sizeDeltaInTokens = sizeDeltaUsd / executionPrice           （L637，向下取整）
  Short sizeDeltaInTokens = ceil(sizeDeltaUsd / executionPrice)     （L641，Calc.roundUpDivision）

isSizeDeltaUsd = false（sizeDeltaInTokens 保持 rawSizeDelta 不变，只覆盖 USD）：
  Long / Short sizeDeltaUsd = sizeDeltaInTokens × executionPrice    （L651/L655，精确乘，无取整；两侧同式，只是 executionPrice 不同）
```

`dynamicSpread` 是 `int256`、可为负：`Calc.sumReturnUint256(1e18, spread)` 与 `Calc.sumReturnUint256(1e18, -spread)` 分别实现「加 / 减带符号点差」，负点差时 Long 的乘数小于 `1e18`、Short 的大于 `1e18`。

最后一道是 **acceptablePrice 校验，不是夹紧**（`src/order/BaseOrderUtils.sol::getExecutionPriceForIncrease`，在 `PositionUtils` L659-661 调用）：

```text
Long  要求 executionPrice <= acceptablePrice
Short 要求 executionPrice >= acceptablePrice
不满足 → revert OrderNotFulfillableAtAcceptablePrice(executionPrice, acceptablePrice)
```

该校验发生在 `sizeDeltaInTokens` 算完之后，通过时不改任何数值；不通过则整笔回滚（市价单被取消，限价/止损单被冻结）。

**下游使用**

`src/position/IncreasePositionUtils.sol::increasePosition`（L53）直接取 `ExecutionPriceResult` 的两个值：

```text
position.sizeInUsd    += sizeDeltaUsd          （L109-111）
position.sizeInTokens += sizeDeltaInTokens     （L112）
updateOpenInterest(+sizeDeltaUsd, +sizeDeltaInTokens)   （L121）
```

`sizeDeltaUsd == 0` 时跳过 `validateOpenInterestReserve`（L129）与保证金充足性校验，并以 `forLiquidation = true` 调用 `validatePosition`（L153-162：纯增加保证金的存款不应因储备占满而失败，但不允许存完仍可被清算）。

### 3.2 减仓订单

**等比销账（无覆盖重算）**

源码锚点：`src/position/PositionUtils.sol::getDecreaseOrderSize`（L517-550）。整段只读仓位的 `sizeInUsd / sizeInTokens`，**不读价格、不读点差、不读执行价**。

```text
rawSizeDelta = order.sizeDelta

早退：rawSizeDelta == 0 → (0, 0)

isSizeDeltaUsd = true：
  全平恒等分支：position.sizeInUsd == rawSizeDelta
      → (rawSizeDelta, position.sizeInTokens)            精确清零，无取整、无尾差
  否则：
      Long  sizeDeltaInTokens = ceil(sizeInTokens × rawSizeDelta / sizeInUsd)   （向上）
      Short sizeDeltaInTokens =      sizeInTokens × rawSizeDelta / sizeInUsd    （向下）
      sizeDeltaUsd = rawSizeDelta

isSizeDeltaUsd = false：
  全平恒等分支：position.sizeInTokens == rawSizeDelta
      → (position.sizeInUsd, rawSizeDelta)               精确清零
  否则：
      Long  sizeDeltaUsd =      sizeInUsd × rawSizeDelta / sizeInTokens         （向下）
      Short sizeDeltaUsd = ceil(sizeInUsd × rawSizeDelta / sizeInTokens)        （向上）
      sizeDeltaInTokens = rawSizeDelta
```

`getExecutionPriceForDecrease`（`PositionUtils.sol` L673）只把这对值原样带出，**不像加仓那样用执行价回算**；`executionPrice` 只影响 PnL 与费用（§4.6 / §6），不影响销账数量。`getPositionPnlUsdWithExecutionPrice` 返回的第三个值也是原样透传的 `sizeDeltaInTokens`。

减仓侧的 `getDynamicSpread` 入参为负值（`-sizeDeltaUsd`、`-sizeDeltaInTokens`），且 Liquidation 或 `secondaryOrderType == Adl` 时以 `allowNegativeSpread = false` 调用（§4.1）。

**`decreasePosition` 的四道尺寸闸门**

源码锚点：`src/position/DecreasePositionUtils.sol::decreasePosition`（L60）。**闸门 1～4 每次改写 `order.sizeDelta` 后都会重新调用 `getDecreaseOrderSize`，最终写仓位/OI 的是闸门之后的值；除闸门 1 的 revert 分支外，每一次改写都会先 emit `OrderSizeDeltaAutoUpdated`。**

| 闸门 | 行 | 触发条件 | 行为 |
| --- | ---: | --- | --- |
| 0 零尺寸 | L71-73 | `order.sizeDelta == 0` | 不调用 `getDecreaseOrderSize`，`(sizeDeltaUsd, sizeDeltaInTokens)` 保持 `(0,0)`，走纯提取保证金路径；无事件 |
| 1 超仓 | L79-97 | `order.sizeDelta > maxSizeDelta` | 按 `orderType` 分叉，见下（Limit/StopLoss 分支 emit `OrderSizeDeltaAutoUpdated(nextSizeDelta = maxSizeDelta)`） |
| 2 全平归一化（**v0.3.2 新增**） | L102-116 | `isSizeDeltaUsd && sizeDeltaUsd < sizeInUsd && sizeDeltaInTokens == sizeInTokens` | emit `OrderSizeDeltaAutoUpdated(nextSizeDelta = position.sizeInUsd)` → `setSizeDelta(sizeInUsd)` → 重算成全平 |
| 3 保证金不足强平 | L206-217 | 部分平且 `estimatedRemainingCollateralUsd + estimatedRemainingPnlUsd < MIN_COLLATERAL_USD` | emit `OrderSizeDeltaAutoUpdated(nextSizeDelta = maxSizeDelta)` → `setSizeDelta(maxSizeDelta)` → 重算成全平 |
| 4 残仓过小 | L219-234 | 部分平且 `sizeInUsd > sizeDeltaUsd` 且 `sizeInUsd - sizeDeltaUsd < MIN_POSITION_SIZE_USD` | emit `OrderSizeDeltaAutoUpdated(nextSizeDelta = maxSizeDelta)` → `setSizeDelta(maxSizeDelta)` → 重算成全平 |

```text
maxSizeDelta = isSizeDeltaUsd ? position.sizeInUsd : position.sizeInTokens     （L75-76，与 sizeDelta 同单位）

OrderSizeDeltaAutoUpdated 事件字段（src/order/OrderEventUtils.sol L77-97）：
  key（bytes32）/ sizeDelta（uint）/ nextSizeDelta（uint）/ isSizeDeltaUsd（bool）
```

事件第一个数值字段 `sizeDelta` 取的是 **emit 当时**的 `params.order.sizeDelta()`——闸门 2/3/4 之前若已被上一道闸门改写过，这里就不是用户下单原值。闸门 3、4 都嵌在 `cache.sizeDeltaUsd < position.sizeInUsd` 的部分平仓分支里（L132），**它们与闸门 2 都可以在「没有超仓」的普通部分平仓上触发**。

闸门 1 按 `orderType` 分叉，这是审计中最常漏掉的分支：

```text
order.sizeDelta > maxSizeDelta 时：
  orderType ∈ { LimitDecrease(3), StopLossDecrease(4) }
      → emit OrderSizeDeltaAutoUpdated(orderKey, sizeDelta, maxSizeDelta, isSizeDeltaUsd)
      → order.setSizeDelta(maxSizeDelta)，重算 → 静默下调为全平
  其它（MarketDecrease(2)、Liquidation(5)）
      → revert FxErrors.InvalidDecreaseOrderSize(cache.sizeDeltaUsd, position.sizeInUsd)
```

闸门 2（v0.3.2 新增，v0.3.1 无此分支）处理的是「多头按 USD 比例平仓，token 向上取整把仓位 token 吃干净」的尾差：此时若不归一化，`sizeInUsd` 还剩一点而 `sizeInTokens` 已为 0，PnL / 费用 / OI / 事件会用两个不一致的口径。

触发门槛可精确推导。记 `U = position.sizeInUsd`、`T = position.sizeInTokens`、`d = cache.sizeDeltaUsd`；闸门 2 自身的前两个条件已保证 `isSizeDeltaUsd == true` 且 `d < U`，因而 `getDecreaseOrderSize` 走的正是多头 `Calc.roundUpDivision` 分支：

```text
闸门 2 触发（多头）  ⟺  ceil(T × d / U) == T  ⟺  T × (U − d) < U      ← 严格整数判据

推导：d < U ⟹ T×d/U < T ⟹ ceil(T×d/U) ≤ T；
      正整数下 ceil(a/b) == T ⟺ a > b × (T − 1)，代入 a = T×d、b = U：
      T×d > U×T − U  ⟺  T × (U − d) < U。（T = 0 时两边同为 0 < U，判据仍相符）
```

**构造边界用例时必须用上面这条整数不等式。**本文档其余位置的 `/` 一律按 Solidity 整数除法读，而下面这条量纲说明里的 `U / T` 是实数除法，两者在边界上结论相反：

```text
量纲读法（估量级用，不能当判据）：
  剩余未平 USD = U − d  <  U / T   （实数除法）
               即：剩余的 USD 不足该仓位一个 token-wei 所对应的入场价值
  换算成美元：门槛 = 仓位入场均价（USD/token） × 10^(−index token decimals)

反例：U = 1e33，T = 333333333333333333，U − d = 3000000000000000
  整数判据：T × (U − d) = 999999999999999999000000000000000 < 1e33     → 触发（链上真实行为）
  整除读法：U / T = 3000000000000000，3000000000000000 < 3000000000000000 为假 → 不触发
  按整除读法写期望值，这一格会得到假 FAIL。
```

当前登记的所有市场 index token 均为 18 位（`TestCode/config/mock-resources.json` 三套 fork 登记的 index token decimals 均为 18、collateral token 为 6；oracle 报价 decimals 各 fork 并不相同——tx-fork 为 18，oracle-fork / time-fork 为 8——那只影响喂价构造，与本门槛无关；文档 §21 亦记「所有标的统一 18 位」），因此门槛 ≈ 入场均价 × `1e-18` 美元——$3000 均价下约 `3e-15` 美元，实际只能靠构造 `sizeDelta = sizeInUsd - k`（k 为极小整数）命中，不是自然可达的场景。若将来登记非 18 位 index token，该门槛会按上式显著抬高。**空头方向与 token 计价模式没有对称分支**：空头走整除向下，`d < U` 且 `T ≥ 1` 时 `floor(T×d/U) ≤ T − 1`，取不到 `T`；token 计价则直接被闸门 2 条件自身的 `params.order.isSizeDeltaUsd()`（L103）挡在门外，根本进不了这个分支（即便进去，`sizeDeltaUsd` 的 ceil 也受同一量纲差保护——`rawSizeDelta < sizeInTokens` 时算不到 `sizeInUsd`）。

指路（跨节口径）：合约侧 `sizeInTokens` / `sizeDeltaInTokens` 一律是 index token 的原生 decimals，`PositionUtils.sol` 里出现的 `1e18` 全部是点差比例的 `Precision.WEI_PRECISION`，没有一处把标的精度写死为 18，所以上面的门槛只能写成 `10^(−index token decimals)`。主文档 §16.5（`Token Size = sizeDeltaInTokens / 1e18`）、§17.1 / §17.2（「所有市场统一按 18 位仓位精度」）、§21 速查表（「所有标的统一 18 位」）仍是写死 18 位的旧写法——那是「当前登记市场恰好都是 18 位」的巧合口径，不是合约保证；以本节口径为准，待那几节改写时同步。

闸门 3 之前还有两处只改保证金、不改尺寸的动作（属 §17 范围，此处仅列出以免误判事件顺序）：`initialCollateralDeltaAmount` 超额夹紧（L119-128，emit `OrderCollateralDeltaAmountAutoUpdated`）、以及保证金不足时把 `initialCollateralDeltaAmount` 置 0（L179-198，同样 emit 该事件；若此时 `sizeDeltaUsd == 0` 则 `revert UnableToWithdrawCollateral`）。闸门全部走完后，若判定为全平（`sizeDeltaUsd == sizeInUsd`）且 `initialCollateralDeltaAmount > 0`，再把它置 0（L239-241，此处不发事件）。

**下游使用**

```text
position.sizeInUsd    -= sizeDeltaUsd
position.sizeInTokens -= sizeDeltaInTokens
updateOpenInterest(-sizeDeltaUsd, -sizeDeltaInTokens)
若 sizeInUsd == 0 或 sizeInTokens == 0 → 两者同时清零、退还全部保证金、删除仓位
```

`DecreasePositionCollateralUtils.processCollateral` 会再调一次 `getExecutionPriceForDecrease`（L84），但此时 `params.order.sizeDelta` 已被闸门改写，取到的与 `decreasePosition` 缓存中的一致。

计价模式约束：

- 清算单由 `src/liquidation/LiquidationUtils.sol::createLiquidationOrder`（L33）建单，固定 `sizeDelta = position.sizeInUsd`（L76）、`isSizeDeltaUsd = true`（L91）；ADL 单由 `src/adl/AdlUtils.sol::createAdlOrder`（L110）建单，固定 `isSizeDeltaUsd = true`（L150）且建单时校验 `sizeDeltaUsd <= position.sizeInUsd`（否则 `revert InvalidSizeDeltaForAdl`，L115）。两者都在同一笔交易内建单并执行，因此闸门 1 的 revert 分支对它们实际不会触发。
- `OrderHandler.updateOrder` 禁止把 `Liquidation` 单改成 token 计价：`revert FxErrors.InvalidSizeDeltaTypeForOrder`（`src/exchange/OrderHandler.sol` L141-143）。市价单本身不可更新（`OrderNotUpdatable`）。
- `isSizeDeltaUsd` 还决定执行费补贴阈值读哪个 key：`src/gas/GasUtils.sol::isExecutionFeeSubsidizedAtCreation`（L239-258）—— USD 计价读 `executionFeeSubsidizeKey(marketIndex)`，token 计价读 `executionFeeSubsidizeSizeKey(marketIndex)`，阈值为 `type(uint256).max` 表示关闭补贴，否则 `sizeDelta >= 阈值` 即补贴。

### 3.4 取整/选价速查表与数值例

按「加仓 / 减仓 × USD / Token 计价」四类展开多空，共 7 行。**取整方向一律取对交易者不利的一侧**，两侧幅度都在 1 token-wei 的量级：加仓侧 Long 向下少拿 token、Short 向上多背 token，两者都压低同价位下的 PnL；减仓侧则**不是「不影响即时净值」**——合约的已实现 PnL 是**按 token 份额比例分摊整仓 PnL**（§6.3），不是「本笔 token 数 × 执行价 − 本笔 USD 数」，因而「已实现 + 剩余未实现」相对整仓 PnL 存在一个恒 ≤ 0 的修正项：

```text
记 U = position.sizeInUsd、T = position.sizeInTokens、
   d = sizeDeltaUsd、t = sizeDeltaInTokens、P = executionPrice（下式不含 §6.4 盈利上限裁剪）

整仓 PnL     R = T×P − U（Long）／ U − T×P（Short）                     （§6.2）
已实现       realized = mulDiv(R, t, T, R < 0)                          （PositionUtils.sol L234-236，负值按绝对值向上）
减仓后仓位   sizeInUsd = U − d，sizeInTokens = T − t                    （DecreasePositionUtils.sol L268-271，不做基准补正）
剩余未实现   rem = (T−t)×P − (U−d)（Long）／ (U−d) − (T−t)×P（Short）

Long   realized + rem − R = d − U×t/T ，t = ceil(T×d/U)  ⟹ U×t/T ≥ d ⟹ 该项 ≤ 0
Short  realized + rem − R = U×t/T − d ，t = floor(T×d/U) ⟹ U×t/T ≤ d ⟹ 该项 ≤ 0
（mulDiv 的 ≤1 wei 取整同向叠加，也压向交易者不利的一侧）
token 计价减仓同理，只是被取整的换成了 d：Long d = floor(U×t/T)、Short d = ceil(U×t/T)，
代入同一修正项仍恒 ≤ 0（速查表 7 行无例外）

两侧偏差同号（恒 ≤ 0，仅当 T×d/U 与 R×t/T 同时整除才取 0），
|偏差| < U/T + 1 ≈ 入场均价 × 1 token-wei
```

所以减仓取整的主要影响仍是已实现 / 未实现的切分与剩余仓位的 `sizeInTokens` 基准（事后是否吃亏取决于后续价格路径），但「已实现 PnL + 剩余未实现 PnL = 整仓 PnL」**不是恒等式**，不能拿它当 wei 级守恒 / ΣΔ 断言的不变量——偏差量级恰好就是 3.2 认定必须精确处理的那一个 token-wei 入场价值（18 位 index token、$3000 均价下约 `3e-15` 美元）。

| 场景 | 计价模式 | 方向 | 被算出的量 | 除数/乘数 | 取整 |
| --- | --- | --- | --- | --- | --- |
| 加仓 | USD | Long | `sizeDeltaInTokens` | `executionPrice`（≈ index.max×(1+spread)） | 向下 |
| 加仓 | USD | Short | `sizeDeltaInTokens` | `executionPrice`（≈ index.min×(1−spread)） | 向上 |
| 加仓 | Token | Long / Short | `sizeDeltaUsd` | `executionPrice` | 精确乘（无取整） |
| 减仓 | USD | Long | `sizeDeltaInTokens` | `sizeInTokens / sizeInUsd` | 向上 |
| 减仓 | USD | Short | `sizeDeltaInTokens` | `sizeInTokens / sizeInUsd` | 向下 |
| 减仓 | Token | Long | `sizeDeltaUsd` | `sizeInUsd / sizeInTokens` | 向下 |
| 减仓 | Token | Short | `sizeDeltaUsd` | `sizeInUsd / sizeInTokens` | 向上 |

数值例（18 位 index token，价格标度 `1e12`，即 $3000 记为 `3e15`；`dynamicSpread = 1e15`，即 0.1%）：

```text
【加仓 · Long · USD 计价】sizeDeltaUsd = 3e33（$3000）
  预解析 tokens（喂 skew）= 3e33 / 3e15                 = 1000000000000000000
  executionPrice = ceil(3e15 × (1e18+1e15)/1e18)        = 3003000000000000
  最终 tokens    = 3e33 / 3003000000000000（向下）      =  999000999000999000
  → 用预解析值当最终值会多算 999000999001000 wei（≈ 0.000999 token），
    相对最终值高估 999000999001000 / 999000999000999000 = 1.000000000000001e-3，
    即点差比例 0.1% 再带一点 wei 级尾差（executionPrice 的 ceil 与整除叠加所致）

【加仓 · Short · USD 计价】sizeDeltaUsd = 3e33
  预解析 tokens = ceil(3e33 / 3e15)                     = 1000000000000000000
  executionPrice = 3e15 × (1e18-1e15)/1e18              = 2997000000000000
  最终 tokens    = ceil(3e33 / 2997000000000000)        = 1001001001001001002
  （精确值 1e21/999 = 1001001001001001001.001…，ceil 进 1）

【减仓 · USD 计价 · 部分平】position: sizeInUsd = 1e33，sizeInTokens = 333333333333333333
  平掉 sizeDeltaUsd = 3e32（30%）：
  Long  tokens = ceil(333333333333333333 × 3e32 / 1e33) = 100000000000000000
  Short tokens =      333333333333333333 × 3e32 / 1e33  =  99999999999999999
  → 同一笔 USD 数量，多空的 sizeDeltaInTokens 相差 1 wei：
    多头向上取整多销 1 wei，剩余 sizeInTokens 少 1 wei；空头相反。
  → 取 executionPrice = 3e15 精确复算「已实现 + 剩余未实现」相对整仓 PnL R 的偏差：
    Long  R = −1000000000000000：realized = −300000000000001，rem = −1000000000000000
          和 = −1300000000000001，偏差 = −300000000000001（−3.0e-16 美元）
    Short R = +1000000000000000：realized = +299999999999999，rem = −2000000000000000
          和 = −1700000000000001，偏差 = −2700000000000001（−2.7e-15 美元）
    两侧偏差都 < 0（对交易者不利），且 |偏差| < U/T + 1 ≈ 3.0e15（3.0e-15 美元）；
    这一 dust 之外的差异才落在剩余仓位的 sizeInTokens 基准上（见上文说明）

【减仓 · 全平】sizeDeltaUsd == sizeInUsd
  → 恒等分支，sizeDeltaInTokens = sizeInTokens，精确清零，不产生 dust
```

核对陷阱：

1. **加仓不要用 index 价当除数**（3.1）；USD 计价下 `sizeDeltaInTokens` 的期望值必须先算 `dynamicSpread` → `executionPrice`。token 计价下反过来：`sizeDeltaInTokens` 就是订单原值，要重算的是 `sizeDeltaUsd`。
2. **减仓不要用执行价换算 token 数**；减仓 token 数只由仓位的 `sizeInUsd / sizeInTokens` 比例决定。
3. 期望值必须在闸门之后取，且 `OrderSizeDeltaAutoUpdated` 不是超仓专属：四道闸门共有四处 emit 点（闸门 1 的 Limit/StopLoss 静默下调分支，以及闸门 2、3、4），其中闸门 2/3/4 都发生在**未超仓的普通部分平仓**上。断言事件时还要注意事件里的 `sizeDelta` 字段是 emit 当时的订单值（可能已被前一道闸门改写），`nextSizeDelta` 才是改写后的目标。
4. `Reader.getExecutionPrice`（`src/reader/ReaderPricingUtils.sol::getExecutionPrice`）复用同一对函数，但把 `acceptablePrice` 设成 `type(uint256).max` / `0`（L51，永不 revert），**且完全不跑 `decreasePosition` 的四道闸门**；用它做超仓、残仓过小或保证金临界的平仓预览，会得到与实际执行不同的 `sizeDeltaUsd / sizeDeltaInTokens`。
5. 「极小额加仓拿到 0 token」**只发生在 USD 计价的多头**，且要区分两个不同的阈值（18 位 index token、$3000 单价下两者都在 `1e-15` 美元量级，但不相等）：

   ```text
   最终 sizeDeltaInTokens = 0   ⟺ 0 < sizeDeltaUsd < executionPrice     （L637 整除向下）
   预解析 tokenDelta      = 0   ⟺ 0 < sizeDeltaUsd < indexPrice.max     （L504 整除向下）
   ```

   正点差下 `executionPrice > indexPrice.max`，两条线之间存在一段夹缝 `indexPrice.max ≤ sizeDeltaUsd < executionPrice`：此时最终 token 数已经是 0（仓位只涨 `sizeInUsd`、不涨 `sizeInTokens`），但预解析 `tokenDelta ≥ 1`，`getNextOpenInterest` 覆写出的 `usdDelta ≠ 0`，next OI 真的会变，**`balanceWasImproved` 不必然为 `false`**。只有更严的 `sizeDeltaUsd < indexPrice.max` 才使 `tokenDelta = 0` → next OI == current OI → `balanceWasImproved = false`（`PositionPricingUtils.sol` L303 + L254-258；注意此时 `skewRef` 仍等于当前 skew，不为 0）。
   **USD 计价空头没有这个陷阱**：预解析（L507）与覆盖重算（L641）两处都是 `Calc.roundUpDivision`，而 `roundUpDivision(a,b) = (a+b-1)/b` 在 `0 < a < b` 时恒为 **1**，所以空头极小额开仓的 `sizeDeltaInTokens` 最小是 1 wei，不是 0；照多头口径给空头算期望值会得到假 FAIL。token 计价两侧的 `sizeDeltaInTokens = rawSizeDelta`，同样不为 0。

版本差异：`getIncreaseOrderSize` / `getDecreaseOrderSize` 两版逐字相同；v0.3.2 的实质变化只有 `decreasePosition` 新增闸门 2（全平归一化），以及点差改用 `Calc.sumReturnUint256` 支持负点差（影响 `executionPrice`，见 §4）。

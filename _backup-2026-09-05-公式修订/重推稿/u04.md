## 5. 仓位字段更新

> 本节所有 `sizeDeltaUsd` / `sizeDeltaInTokens` 均指**解析后的最终值**（加仓来自 `getExecutionPriceForIncrease`，减仓来自被归一化后的 `order.sizeDelta` 再过 `getDecreaseOrderSize`），不是订单原始字段，也不是中途被覆盖的预解析中间量。取错来源会让整条期望值链跑偏，见 §3 / §4。
>
> v0.3.2 已删除减仓的二次输出通道：`values.output.outputToken` 恒为 `market.collateralToken`，`secondaryOutputToken` / `secondaryOutputAmount` / swap 回退路径全部移除（`DecreasePositionCollateralUtils.sol::processCollateral`、`DecreaseOrderUtils.sol::getOutputEventData`）。所有 PnL、费用、退款都在同一个抵押品 token 上结算。

### 5.1 加仓后规模

源码：`IncreasePositionUtils.sol::increasePosition`、`PositionUtils.sol::getExecutionPriceForIncrease`。

```text
sizeDeltaUsd      = executionPriceResult.sizeDeltaUsd
sizeDeltaInTokens = executionPriceResult.sizeDeltaInTokens

nextSizeInUsd    = oldSizeInUsd    + sizeDeltaUsd
nextSizeInTokens = oldSizeInTokens + sizeDeltaInTokens
```

必须成对写明的分支：

| 分支 | 条件 | 结果 |
| --- | --- | --- |
| 纯充值早退 | `getIncreaseOrderSize` 解析出 `sizeDeltaUsd == 0` | `sizeDeltaInTokens = 0`、`dynamicSpread = 0`、`balanceWasImproved = false`、`executionPrice = indexPrice.pickPrice(isLong)`（Long=max、Short=min）；规模两项都不变 |
| USD 模式 Long | `isSizeDeltaUsd && isLong` | `sizeDeltaInTokens = floor(sizeDeltaUsd / executionPrice)`（executionPrice 含点差，`indexPrice.max` 只是它的输入） |
| USD 模式 Short | `isSizeDeltaUsd && !isLong` | `sizeDeltaInTokens = ceil(sizeDeltaUsd / executionPrice)` |
| Token 模式 | `!isSizeDeltaUsd` | `sizeDeltaInTokens` 直接取订单值；`sizeDeltaUsd = sizeDeltaInTokens × executionPrice` |

其它写回与副作用：

- 首开归零：`position.sizeInUsd() == 0` 时，在算费之前先把 `negativeFundingFeePerSize` / `positiveFundingFeePerSize` 重置为市场当前值，因此新仓的第一笔 funding 从本次执行时刻起算。
- `increasedAtTime = block.timestamp`。
- OI：`PositionUtils.sol::updateOpenInterest` 以 `(+sizeDeltaUsd, +sizeDeltaInTokens)` 调用；`sizeDeltaUsd == 0` 时**整体 no-op**（两项 OI 都不动）。

### 5.2 减仓后规模与订单规模归一化

源码：`DecreasePositionUtils.sol::decreasePosition`、`PositionUtils.sol::getDecreaseOrderSize`。

减仓的规模换算**不读 Oracle 价格**，是按仓位自身的 `sizeInUsd : sizeInTokens` 等比销账：

```text
raw = order.sizeDelta
raw == 0                                → (0, 0)

isSizeDeltaUsd = true:
  raw == sizeInUsd                      → (raw, sizeInTokens)                        # 整仓，不做除法
  Long                                  → (raw, ceil(sizeInTokens × raw / sizeInUsd))   # 向上取整
  Short                                 → (raw, floor(sizeInTokens × raw / sizeInUsd))  # 向下取整

isSizeDeltaUsd = false:
  raw == sizeInTokens                   → (sizeInUsd, raw)
  Long                                  → (floor(sizeInUsd × raw / sizeInTokens), raw)
  Short                                 → (ceil(sizeInUsd × raw / sizeInTokens), raw)
```

在进入结算前，`order.sizeDelta` 和 `order.initialCollateralDeltaAmount` 会被下面这条**归一化阶梯**依次改写。凡改写 `order.sizeDelta` 的步骤（①②⑤⑥）之后都会**重新调用 `getDecreaseOrderSize`**；③④⑦ 只改 `initialCollateralDeltaAmount`，不触发重算。期望值必须按改写后的值算：

| 序 | 条件 | 动作 | 事件 |
| --- | --- | --- | --- |
| ① | `order.sizeDelta > maxSizeDelta`（`maxSizeDelta = isSizeDeltaUsd ? sizeInUsd : sizeInTokens`），且订单是 `LimitDecrease` / `StopLossDecrease` | `setSizeDelta(maxSizeDelta)`，随后重算 | `OrderSizeDeltaAutoUpdated` |
| ①' | 同上条件，但订单是其它类型（Market / Liquidation / ADL） | `revert InvalidDecreaseOrderSize` | — |
| ② **v0.3.2 新增** | `isSizeDeltaUsd && sizeDeltaUsd < sizeInUsd && sizeDeltaInTokens == sizeInTokens` | **把 `sizeDeltaUsd` 放大到整仓**：`setSizeDelta(sizeInUsd)`，随后重算 | `OrderSizeDeltaAutoUpdated` |
| ③ | `order.initialCollateralDeltaAmount > position.collateralAmount` | 夹到 `position.collateralAmount`（不重算规模） | `OrderCollateralDeltaAmountAutoUpdated` |
| ④ | 仅当 `sizeDeltaUsd < sizeInUsd`（部分减仓）：预估后 `!willBeSufficient` 或 `estimatedRemainingCollateralUsd + estimatedRemainingPnlUsd < MIN_COLLATERAL_USD` | `sizeDeltaUsd == 0` 时 `revert UnableToWithdrawCollateral`；否则**先**用置 0 之前的 `initialCollateralDeltaAmount` 执行 `estimatedRemainingCollateralUsd += initialCollateralDeltaAmount × collateralTokenPrice.min`，**再** `setInitialCollateralDeltaAmount(0)`（不重算规模） | `OrderCollateralDeltaAmountAutoUpdated` |
| ⑤ | ④ 之后仍 `estimatedRemainingCollateralUsd + estimatedRemainingPnlUsd < MIN_COLLATERAL_USD` | 升级为全平：`setSizeDelta(maxSizeDelta)`，随后重算 | `OrderSizeDeltaAutoUpdated` |
| ⑥ | `sizeInUsd > sizeDeltaUsd` 且 `sizeInUsd - sizeDeltaUsd < MIN_POSITION_SIZE_USD` | 升级为全平：`setSizeDelta(maxSizeDelta)`，随后重算 | `OrderSizeDeltaAutoUpdated` |
| ⑦ | `sizeDeltaUsd == sizeInUsd && initialCollateralDeltaAmount > 0` | **强制 `setInitialCollateralDeltaAmount(0)`**（不重算规模） | 无事件 |

②的语义：USD 模式 Long 的等比销账对 Token 数向上取整，取整后可能恰好吃掉全部 `sizeInTokens`；此时把 USD 规模一并放大到整仓，让 PnL、费用、OI 和事件用同一个 USD 口径。条件本身不判方向，但 Short 走向下取整、`raw < sizeInUsd` 时不可能等于 `sizeInTokens`，实际只对 Long 生效。

④的加回顺序是本条的关键：**加回发生在置 0 之前，加回的是置 0 前的原值**（源码注释写明用意是“把这笔钱加回来以避免仓位被全平”）。若按“先置 0 再加回”理解，加回的是 0，⑤级条件会被误判为成立，从而凭空产出一条并不存在的“自动升级全平 + `OrderSizeDeltaAutoUpdated`”期望。

⑦是本节最容易算错的一条：**只要判定为全平（含手动全平、被④⑤⑥升级的全平、清算、ADL），`order.initialCollateralDeltaAmount` 一律被置 0**，因此 §5.4 里“用户主动提取额”这一项恒为 0，保证金不是靠它退回的（见 §5.4 第 ⑥ 步与 §5.5）。

④的预估口径分三段，锚点不同——PnL 预估与四个入参的构造都在 `DecreasePositionUtils.sol::decreasePosition`，判定本身在 `PositionUtils.sol::willPositionCollateralBeSufficient`：

```text
# DecreasePositionUtils.sol::decreasePosition（估算已实现 / 剩余 PnL）
estimatedPositionPnlUsd   = getPositionPnlUsdWithExecutionPrice(..., sizeDeltaInTokens = sizeInTokens)
estimatedRealizedPnlUsd   = mulDiv(estimatedPositionPnlUsd, sizeDeltaInTokens, sizeInTokens,
                                   roundUpMagnitude = estimatedPositionPnlUsd < 0)
estimatedRemainingPnlUsd  = estimatedPositionPnlUsd - estimatedRealizedPnlUsd

# DecreasePositionUtils.sol:155-160（四个入参在此构造；函数内对应 values.* 字段名）
positionSizeInUsd         = sizeInUsd - sizeDeltaUsd
positionCollateralAmount  = collateralAmount - initialCollateralDeltaAmount
realizedPnlUsd            = estimatedRealizedPnlUsd
openInterestDelta         = -sizeDeltaUsd          # 喂 getMinCollateralFactorForOpenInterest；加仓路径传 0，见 §5.3

# PositionUtils.sol::willPositionCollateralBeSufficient（函数体）
remainingCollateralUsd    = positionCollateralAmount × collateralTokenPrice.min
                            + min(realizedPnlUsd, 0)          # 只减亏损，不加盈利
remainingCollateralUsd < 0                        → willBeSufficient = false（提前返回）
minCollateralFactor       = max(getMinCollateralFactorForOpenInterest(openInterestDelta),
                                市场 MIN_COLLATERAL_FACTOR)
minCollateralUsdForLeverage = positionSizeInUsd × minCollateralFactor / 1e30    # Precision.applyFactor
willBeSufficient          = remainingCollateralUsd >= minCollateralUsdForLeverage
```

`/ 1e30` 不可省：`Precision.applyFactor(value, factor) = mulDiv(value, factor, FLOAT_PRECISION = 1e30)`（口径同 §1.2）。漏掉它右侧会大 1e30 倍，`willBeSufficient` 恒为 false，④ 会被算成“任何部分减仓都触发”，直接产出假缺陷。⑤ 的触发条件里没有这个因子（它只比 `estimatedRemainingCollateralUsd + estimatedRemainingPnlUsd` 与 `MIN_COLLATERAL_USD`），但会因为 ④ 被误触发而拿到“已加回 `initialCollateralDeltaAmount`”的那一版输入，两级的期望值都要重算。

`estimatedPositionPnlUsd` 用的是**本次减仓的 executionPrice**（`getExecutionPriceForDecrease`，含点差），不是裸 index 价（源码此处的 “estimate pnl based on indexTokenPrice” 注释已与实现不符）。

写回：

```text
nextSizeInUsd    = oldSizeInUsd    - sizeDeltaUsd
nextSizeInTokens = oldSizeInTokens - sizeDeltaInTokens
decreasedAtTime  = block.timestamp
```

OI 以 `(-sizeDeltaUsd, -sizeDeltaInTokens)` 调用 `updateOpenInterest`。

### 5.3 加仓抵押品变化

源码：`IncreasePositionUtils.sol::processCollateral` + `increasePosition`。加仓**没有支付瀑布，也没有 output 通道**，所有成本直接与保证金净额相抵：

```text
collateralIncrementAmount = order.initialCollateralDeltaAmount   # 已由 IncreaseOrderUtils 从 orderVault 划入 positionVault

collateralDeltaAmount                                            # int256
= int256(collateralIncrementAmount)
- totalCostAmount
+ positiveFundingFeeAmount

totalCostAmount
= positionFeeAmount + liquidationFeeAmount(加仓恒为 0) + uiFeeAmount
- totalDiscountAmount
+ negativeFundingFeeAmount

nextCollateralAmount = sumReturnUint256(oldCollateralAmount, collateralDeltaAmount)
```

分支与副作用：

- 余额闸门：`collateralDeltaAmount < 0 && position.collateralAmount < |collateralDeltaAmount|` → `revert InsufficientCollateralAmount(collateralAmount, collateralDeltaAmount)`。这是加仓路径上唯一一处**token 数量口径**的保证金不足早退（USD 杠杆口径的那一道是下面的 `InsufficientCollateralUsd`）；加仓不会像减仓那样“部分支付”。
- funding 结算（v0.3.2 变更）：`MarketUtils.settleFundingFees(negativeFundingFeeAmount, positiveFundingFeeAmount)` 按**本仓净差**执行——负>正则把差额记入 `FUNDING_FEE_TYPE` claimable；正>负则由 LP vault 向 positionVault 划出差额。注意加仓路径传的是**应付额** `negativeFundingFeeAmount`（减仓路径传的是实付额，见 §5.4.2 第 ③ 步）。v0.3.1 的 LP 现金流由 `updateFundingState` 产生，v0.3.2 已改为结算时刻按仓触发，详见 §10。
- 费用去向：`fees.feeAmountForPool` 由 positionVault 无条件划给 `market.vault`；`fees.feeReceiverAmount` 记入 `POSITION_FEE_TYPE` claimable；`fees.ui.uiFeeAmount` 记入 `UI_POSITION_FEE_TYPE` claimable。加仓路径没有“费用付不起就清空”的分支。
- 写回后 `negativeFundingFeePerSize` / `positiveFundingFeePerSize` 更新为 `fees.funding.latest*`。
- 事件 `PositionIncrease.collateralDeltaAmount` = 上式 `collateralDeltaAmount`，**符号 = 保证金的净变化方向**（正=保证金增加）。注意与 `PositionDecrease` 相反，见 §5.5。

加仓的两道校验闸门（`sizeDeltaUsd > 0` 时才跑前两条）：

```text
sizeDeltaUsd > 0：
  MarketUtils.validateOpenInterestReserve(...)                       → 储备不足回退
  willPositionCollateralBeSufficient(positionSizeInUsd=新规模,
                                     positionCollateralAmount=新保证金,
                                     realizedPnlUsd=0, openInterestDelta=0)
    !willBeSufficient → revert InsufficientCollateralUsd(remainingCollateralUsd)

始终：
  validatePosition(shouldValidateMinPositionSize=true,
                   shouldValidateMaxPositionSize=true,
                   shouldValidateMinCollateralUsd=true,
                   forLiquidation = (sizeDeltaUsd == 0))
```

`openInterestDelta = 0` 是加仓路径的实参（OI 已在调用前更新过，因此不再叠加增量），与减仓路径传 `-sizeDeltaUsd` 不对称，核对 `minCollateralFactor` 时不要互相套用。

最后一条的含义：**纯充值保证金（`sizeDeltaUsd == 0`）会按“可清算判定”口径校验**（因子取 `MIN_COLLATERAL_FACTOR_FOR_LIQUIDATION`），若充值后仍处于可清算状态则回退 `LiquidatablePosition`，防止充值后立刻被清算；带规模的加仓则用 `MIN_COLLATERAL_FACTOR` 口径，同样会在命中时回退。

### 5.4 减仓支付瀑布与输出

源码：`DecreasePositionCollateralUtils.sol::processCollateral` / `payForCost`。

**支付优先级是本节的核心：每一笔成本都先扣 `output.outputAmount`，扣不完才动 `remainingCollateralAmount`。** 而 `output.outputAmount` 在第一步就已经装入了正 PnL 兑出的 token，所以“盈利先垫费”是常态，而不是例外。用线性加减式（把所有成本都从保证金里减）会在有正 PnL 时算错分账，全平时更会整整丢掉一份保证金。

**5.4.1 单笔支付原语 payForCost**

```text
payForCost(costUsd):
  costUsd == 0 → 立即返回 (amountPaidInCollateralToken = 0, remainingCostUsd = 0)

  need = ceil(costUsd / collateralTokenPrice.min)      # Calc.roundUpDivision，单位 = 抵押品 token

  ① if output.outputAmount > 0:
       take = min(output.outputAmount, need)
       amountPaidInCollateralToken += take
       output.outputAmount         -= take
       need                        -= take
     need == 0 → 返回

  ② if remainingCollateralAmount > 0:
       take = min(remainingCollateralAmount, need)
       amountPaidInCollateralToken += take
       remainingCollateralAmount   -= take
       need                        -= take
     need == 0 → 返回

  ③ remainingCostUsd = need × collateralTokenPrice.min      # USD，30 位标度
```

三处取整/选价要配对记牢：`need` 用 **`collateralTokenPrice.min` 向上取整**；`remainingCostUsd` 回乘的也是 `collateralTokenPrice.min`（v0.3.2 修复；v0.3.1 这里直接把 token 数当 USD 返回）。funding 与费用两笔传入的 `costUsd` 本身就是 `tokenAmount × collateralTokenPrice.min`，向上取整后原样还原为该 token 数；只有负 PnL 传的是真 USD，会实打实向上取整。

**5.4.2 六步瀑布**

```text
起点：
  output.outputToken        = market.collateralToken
  output.outputAmount       = 0
  remainingCollateralAmount = position.collateralAmount

① 正 PnL 先兑成 token 进 output（basePnlUsd > 0 时）
     deductionAmountForPool = floor(basePnlUsd / collateralTokenPrice.max)   # 向下取整 + 选 max，双重利于池子
     output.outputAmount   += deductionAmountForPool
     LP vault → positionVault 划出同额

② 收到的 funding 进保证金
     remainingCollateralAmount += positiveFundingFeeAmount

③ payForCost(negativeFundingFeeAmount × collateralTokenPrice.min)
     settleFundingFees(实付额 amountPaidInCollateralToken, positiveFundingFeeAmount)   # 按净差
     实付额 < negativeFundingFeeAmount → emit InsufficientFundingFeePayment
     remainingCostUsd > 0 → handleEarlyReturn(step = "funding")

④ payForCost(-basePnlUsd)（仅 basePnlUsd < 0）
     实付额 > 0 → positionVault → market.vault 划出实付额
     remainingCostUsd > 0 → handleEarlyReturn(step = "pnl")

⑤ payForCost(totalCostAmountExcludingFunding × collateralTokenPrice.min)
     totalCostAmountExcludingFunding = positionFeeAmount + liquidationFeeAmount
                                       + uiFeeAmount - totalDiscountAmount
     remainingCostUsd == 0：
       positionVault → market.vault 划出 feeAmountForPool
       claimable[POSITION_FEE_TYPE]    += feeReceiverAmount - liquidationFeeAmountForFeeReceiver
       claimable[LIQUIDATION_FEE_TYPE] += liquidationFeeAmountForFeeReceiver（> 0 时）
       claimable[UI_POSITION_FEE_TYPE] += uiFeeAmount
     remainingCostUsd > 0：
       fees = getEmptyFees(fees)                 # 费用字段清零，仅保留 positiveFundingFeeAmount、
                                                 # 两个 latest*PerSize 与 collateralTokenPrice
       handleEarlyReturn(step = "fees")

⑥ 用户主动提取（仅部分减仓才可能非 0）
     initialCollateralDeltaAmount > remainingCollateralAmount
       → 夹到 remainingCollateralAmount，emit OrderCollateralDeltaAmountAutoUpdated
     initialCollateralDeltaAmount > 0：
       remainingCollateralAmount -= initialCollateralDeltaAmount
       output.outputAmount       += initialCollateralDeltaAmount
```

③的 `settleFundingFees` 传的是 `payForCost` 的**实付额** `amountPaidInCollateralToken`，与加仓路径不同（加仓传的是应付额 `negativeFundingFeeAmount`，见 §5.3）。付不满时事件 `InsufficientFundingFeePayment` 同时给出应付与实付两个值，是唯一能还原缺口的地方。

⑤的 `remainingCostUsd > 0` 分支还有一处**必须记入金库守恒断言**的资金去向：该分支只执行 `getEmptyFees`，源码里既没有向 `market.vault` 的 `transferOut`，也没有 `incrementClaimableFeeAmount`，而 `payForCost` 已经实扣了 `amountPaidInCollateralToken`。这笔已扣的 token 滞留在 `positionVault`，既不入池也不入 claimable（源码注释却称“已整笔付给池子”）——差异台账已按缺陷候选立项。该分支只在“全平的清算 / ADL”路径可达（否则先 revert，见 5.4.4），做 ΣΔ 守恒核对时须为它单列一项。

**全平（含清算 / ADL）时第 ⑥ 步恒为空操作**：`order.initialCollateralDeltaAmount` 已在 §5.2 阶梯⑦被置 0。真正把保证金还给用户的是 `DecreasePositionUtils.sol::decreasePosition` 里的清仓分支：

```text
position.collateralAmount = values.remainingCollateralAmount
若 nextSizeInUsd == 0 或 nextSizeInTokens == 0：
    output.outputAmount += position.collateralAmount        # ← 保证金在这里回到 output
    sizeInUsd = sizeInTokens = collateralAmount = 0
    PositionStoreUtils.remove(...)
```

**5.4.3 数值例（USDC 6 位，`collateralTokenPrice.min = max = 1e24`）**

全平、盈利 50 USDC、欠 funding 2 USDC、费用 5 USDC、原保证金 1000 USDC：

```text
① output = floor(50e30 / 1e24) = 50_000_000        remaining = 1_000_000_000
② positiveFunding = 0                              remaining = 1_000_000_000
③ need = ceil(2e6×1e24 / 1e24) = 2_000_000 → 全部从 output 扣
                                                   output = 48_000_000, remaining 不变
⑤ need = 5_000_000 → 仍全部从 output 扣            output = 43_000_000, remaining 不变
⑥ initialCollateralDeltaAmount = 0（全平强制）      无动作
清仓分支：output = 43_000_000 + 1_000_000_000 = 1_043_000_000
```

用户实收 1043 USDC = 1000 保证金 + 50 盈利 − 2 funding − 5 费用。**保证金 `remainingCollateralAmount` 自始至终没被扣过**——若按旧的线性式“从保证金里减成本”，会既把 7 USDC 重复扣一次，又漏掉 1000 USDC 的本金，期望值会算成 43 USDC。

部分减仓、盈利 3 USDC、费用 5 USDC、请求提取 100 USDC、原保证金 200 USDC：

```text
① output = 3_000_000                remaining = 200_000_000
⑤ need = 5_000_000 > output → 先扣光 output（3_000_000），余 2_000_000 从保证金扣
                                     output = 0, remaining = 198_000_000
⑥ 100_000_000 ≤ 198_000_000 → remaining = 98_000_000, output = 100_000_000
```

用户实收 100 USDC，仓位留 98 USDC，合计 198 = 200 + 3 − 5。

> 此例只演示 §5.4 瀑布本身，未代入 §5.2 阶梯④的预估闸门。链上这笔提取额是否会被④置 0（进而使 ⑥ 步为空、`remaining` 停在 198_000_000），取决于剩余规模与 `minCollateralFactor`，端到端用例必须先过 §5.2 那一层再套本例。

**5.4.4 破产平仓与早退**

源码：`DecreasePositionCollateralUtils.sol::handleEarlyReturn`。

```text
isFullyClosed = order.isSizeDeltaUsd ? order.sizeDelta == sizeInUsd
                                     : order.sizeDelta == sizeInTokens
isInsolventCloseAllowed = isFullyClosed
                          && (isLiquidationOrder(orderType) || secondaryOrderType == Adl)

!isInsolventCloseAllowed → revert InsufficientFundsToPayForCosts(remainingCostUsd, step)
isInsolventCloseAllowed  → emit PositionFeesInfo + InsolventClose(step)，并返回 getEmptyFees(fees)
```

`step` 取值只有 `"funding"` / `"pnl"` / `"fees"` 三种，可用来定位是哪一步破产。注意两处口径陷阱：

- 走到 `"fees"` 早退时，`fees` 在早退**之前**就已被 `getEmptyFees` 清零，所以该路径的 `PositionFeesInfo` 里**费用类字段全部为 0**（`positiveFundingFeeAmount`、两个 `latest*FundingFeePerSize` 和 `collateralTokenPrice` 仍保留真实值）；走 `"funding"` / `"pnl"` 早退时 `PositionFeesInfo` 报的还是真实费用。断言时不要写“整个事件全 0”。
- `getEmptyFees` 保留的只有 `positiveFundingFeeAmount`、两个 `latest*FundingFeePerSize` 与 `collateralTokenPrice`，`negativeFundingFeeAmount` 被清零——即便第 ③ 步实际付掉了部分 funding，事件里也读不出来（源码注释自认此点）。破产平仓的实付 funding 只能从 `InsufficientFundingFeePayment` 的 `amountPaidInCollateralToken` 反推。

**5.4.5 输出金额校验（v0.3.2 新接线）**

源码：`DecreaseOrderUtils.sol::processOrder` → `_validateOutputAmount`。在 `decreasePosition` 返回之后、`transferOut` 之前执行：

```text
outputTokenPrice = oracle.getPrimaryPrice(outputToken).min      # outputToken 恒为抵押品 token
outputUsd        = outputAmount × outputTokenPrice              # 30 位标度 USD

outputUsd < order.minOutputAmount → revert InsufficientOutputAmount(outputUsd, minOutputAmount)
```

**比较口径是 USD，不是 token 数量**：字段名叫 `minOutputAmount`，实际被当作 30 位标度的 USD 值使用（源码注释明写 “minOutputAmount is treated as a USD value”）。构造用例时若按 token 数量填该字段，会得到“几乎永远通过”的假阴性。v0.3.1 的同名函数只有定义、没有任何调用点，即该滑点保护在 v0.3.1 完全失效，v0.3.2 才真正接线——跨版本用例不能共用同一期望结果。

### 5.5 减仓写回、清仓与事件符号

源码：`DecreasePositionUtils.sol::decreasePosition`、`PositionEventUtils.sol::emitPositionDecrease`。

```text
sizeInUsd        = oldSizeInUsd    - sizeDeltaUsd
sizeInTokens     = oldSizeInTokens - sizeDeltaInTokens
collateralAmount = values.remainingCollateralAmount
decreasedAtTime  = block.timestamp

if (sizeInUsd == 0 || sizeInTokens == 0):          # 注意是「或」
    output.outputAmount += collateralAmount
    sizeInUsd = sizeInTokens = collateralAmount = 0
    PositionStoreUtils.remove(...)
else:
    negativeFundingFeePerSize = fees.funding.latestNegativeFundingFeePerSize
    positiveFundingFeePerSize = fees.funding.latestPositiveFundingFeePerSize
    PositionStoreUtils.set(...)
```

`||` 是防御性条件：任一腿归零就把另一腿一并抹平并删仓，避免留下只有 USD 或只有 Token 的残仓。等比销账下两腿通常同时归零，该分支的非对称触发只可能来自取整残差（残量上界未在链上核实）；一旦触发，被抹平的那一腿不会回写 OI，OI 侧只按 `sizeDeltaUsd` / `sizeDeltaInTokens` 扣减。仓位被删时**不写回 `latest*FundingFeePerSize`**。

减仓后的校验（`DecreasePositionUtils.sol:302-323`，在 OI 更新与 `handleReferral` 之后执行）：仅当 `sizeInUsd != 0 || sizeInTokens != 0` 才调用 `validatePosition`，且 `shouldValidateMinPositionSize` / `shouldValidateMaxPositionSize` / `shouldValidateMinCollateralUsd` 全为 `false`、`forLiquidation = false`。**这三个开关关掉的不是全部校验**：

- 关掉的只有 `MIN_POSITION_SIZE_USD`、`maxPositionSizeUSD` 两项独立校验，以及 `isPositionLiquidatable` 内部的 `MIN_COLLATERAL_USD` 那一条判据。
- 仍然执行 `validateBasicPositionInfo`（两腿非零 + 市场启用）。
- **仍然无条件执行可清算判定**：`isPositionLiquidatable(shouldValidateMinCollateralUsd = false, forLiquidation = false)`，剩下两条判据照常生效——`remainingCollateralUsd <= 0`（reason `"< 0"`），或 `remainingCollateralUsd < sizeInUsd × MIN_COLLATERAL_FACTOR / 1e30`（reason `"min collateral for leverage"`）。命中即 `revert LiquidatablePosition(reason, remainingCollateralUsd, minCollateralUsd, minCollateralUsdForLeverage)`。`forLiquidation = false` 只是把因子由 `MIN_COLLATERAL_FACTOR_FOR_LIQUIDATION` 换成 `MIN_COLLATERAL_FACTOR`。
- 断言 revert 入参时注意：`shouldValidateMinCollateralUsd = false` 时 `info.minCollateralUsd` **从未被赋值**（`PositionUtils.sol:400-405` 只在开关为真的分支里写它），所以这条 revert 的第三个参数**恒为 0**，不是市场配置的 `MIN_COLLATERAL_USD`。

所以“允许手动平掉一个处于部分可清算状态的仓位”**只对全平成立**（`sizeInUsd == 0 && sizeInTokens == 0` 时整个 `validatePosition` 被跳过）；部分减仓后若剩余仓位仍不满足杠杆口径，交易会以 `LiquidatablePosition` 回退。

本工作区已登记 26/26 市场两个 minCF 相等——它的含义是**这道校验与清算判定同口径**（只少 `MIN_COLLATERAL_USD` 一条判据），部分减仓没有任何缓冲带，剩余仓位必须真正脱离清算线才能成交；但它**不等于“部分平掉一个已到清算线的仓位必然 revert”**。`isPositionLiquidatable` 判的是**减仓之后**的仓位（在 size / collateral 写回与 OI 更新之后才调用），分子 `remainingCollateralUsd`（剩余保证金 + 剩余 PnL + 正 funding − 剩余整仓的平仓成本）在等比减仓下近似守恒，而阈值 `sizeInUsd × minCF` 随剩余规模等比缩小：

- `remainingCollateralUsd <= 0`：任何部分减仓都 revert（reason `"< 0"`）。
- `remainingCollateralUsd > 0`：需要剩余 `sizeInUsd <= remainingCollateralUsd / minCF`。平掉的比例不够则 revert（reason `"min collateral for leverage"`），比例足够大则脱线成交。
- 被 §5.2 阶梯 ⑤ / ⑥ 升级为全平的订单根本不走这道校验（被外层 `sizeInUsd != 0 || sizeInTokens != 0` 守卫整体跳过）。

数值反例（`minCF = minCF_liq = 1%`、平仓费率 5 bp、`MIN_COLLATERAL_USD` 取 1 USD；忽略 funding 与点差，价格在减仓前后不变）：仓位 `sizeInUsd = 1000`、`collateral = 50`、未实现 PnL = −44.9，减仓前 `remainingCollateralUsd = 50 − 44.9 − 0.5 = 4.6 < 1000 × 1% = 10`，确已在清算线内且 > 0。

```text
平掉 60%：已实现 PnL = −26.94，已平腿平仓费 0.3 → 剩余 collateral = 22.76
          剩余 size = 400，剩余 PnL = −17.96，剩余平仓费 0.2
          remainingCollateralUsd = 22.76 − 17.96 − 0.2 = 4.60 ≥ 400 × 1% = 4.0  → 通过，交易成功
平掉 50%：已实现 PnL = −22.45，已平腿平仓费 0.25 → 剩余 collateral = 27.30
          剩余 size = 500，剩余 PnL = −22.45，剩余平仓费 0.25
          remainingCollateralUsd = 27.30 − 22.45 − 0.25 = 4.60 < 500 × 1% = 5.0  → revert LiquidatablePosition
```

分子两次都落在 4.60（≈ 减仓前的 4.6），变的只有阈值。两组都能先过 §5.2 的 ④（`50 − 26.94 = 23.06 ≥ 4.0`、`50 − 22.45 = 27.55 ≥ 5.0`）与 ⑤（两组的 `estimatedRemainingCollateralUsd + estimatedRemainingPnlUsd` 都是 5.10 ≥ 1），不会被升级成全平，所以确实会走到尾部这道校验。把“必然 revert”写进期望，会在“大比例部分平仓临界仓位”这一类用例上判出假缺陷——正是本节要防的失败模式。

事件字段：

```text
PositionDecrease.collateralDeltaAmount                          # int256
= cache.initialCollateralAmount - position.collateralAmount     # 执行前 - 执行后

> 0：仓位抵押品净减少（全平时等于原全部保证金）
< 0：仓位抵押品净增加（收到的 funding 大于全部成本时可能出现）
```

**符号约定与加仓相反**：`PositionIncrease.collateralDeltaAmount` 正值表示保证金增加，`PositionDecrease.collateralDeltaAmount` 正值表示保证金减少。两个事件不能用同一套符号断言。

`DecreaseOrderUtils` 回传给外层的三个量同样要注意口径：

| 字段 | 取值 | 陷阱 |
| --- | --- | --- |
| `outputAmount` | `values.output.outputAmount` | 全平时已包含全部退回保证金 |
| `orderSizeDeltaUsd` | `cache.sizeDeltaUsd` | 是归一化**之后**的值，可能被放大到整仓 |
| `orderInitialCollateralDeltaAmount` | `params.order.initialCollateralDeltaAmount()` | 全平时被强制改写为 **0**，不能用它展示“本次提取保证金” |

### 5.6 减仓路径回退闸门速查

| 回退 | 触发点 | 条件 |
| --- | --- | --- |
| `InvalidDecreaseOrderSize` | `DecreasePositionUtils::decreasePosition` | `sizeDelta > maxSizeDelta` 且非 Limit/StopLoss 减仓 |
| `UnableToWithdrawCollateral` | 同上 | 部分减仓预估不足，且 `sizeDeltaUsd == 0`（纯提保证金） |
| `PositionShouldNotBeLiquidated` | 同上 | 清算类订单但 `isPositionLiquidatable` 判否 |
| `InsufficientFundsToPayForCosts(remainingCostUsd, step)` | `DecreasePositionCollateralUtils::handleEarlyReturn` | 任一支付步骤有缺口且非「全平的清算/ADL」 |
| `LiquidatablePosition(reason, remainingCollateralUsd, minCollateralUsd, minCollateralUsdForLeverage)` | `DecreasePositionUtils::decreasePosition` 尾部 `validatePosition` | 减仓后仓位非空，且 `remainingCollateralUsd <= 0` 或 `< sizeInUsd × MIN_COLLATERAL_FACTOR / 1e30`（不含 `MIN_COLLATERAL_USD` 判据；该开关关闭使入参 `minCollateralUsd` 恒为 0） |
| `InvalidPositionSizeValues` / `DisabledMarket` | 同上（`validateBasicPositionInfo`） | 市场被停用即回退；两腿非零一项在该调用点因外层守卫恒真 |
| `InsufficientOutputAmount(outputUsd, minOutputAmount)` | `DecreaseOrderUtils::_validateOutputAmount` | `outputAmount × collateralPrice.min < minOutputAmount`（USD 口径） |

注：`MinPositionSize` / `MaxPositionSize` 两项在减仓尾部的 `validatePosition` 里被显式关闭，不会从该路径回退；它们只在加仓路径（§5.3）生效。

## 13. LP Vault 字段

代码锚点：`src/vault/VaultBase.sol`（抽象基类，NAV / 换算 / 转出 / 策略分配）、`src/vault/LPVault.sol`（存款、提款请求、epoch、提款 gate）。v0.3.2 相对 v0.3.1 **只改了一处**：`VaultBase::_withdrawAssets` 的缺口路径（见 §13.8）；`LPVault.sol` 逐字未变。

### 13.1 精度与常量

| 名称 | 值 | 说明 |
| --- | --- | --- |
| `PRECISION` | `1e18` | `VaultBase` 内部精度。**注意不是 `1e30`**，NAV、`allocationPercentage` 全用这一档 |
| `assetScalar` | `10 ** (18 - asset.decimals())` | 构造函数固定（`VaultBase::constructor`）。USDC(6) → `1e12`；`decimals > 18` 会在部署时下溢 revert |
| LP share decimals | `18` | `ERC20Upgradeable` 默认，未覆写 |
| `strategyInfo.allocationPercentage` | `uint128`，1e18 标度 | `1e18` = 100% |
| `strategyInfo.minDeposit` | `uint128`，asset 原生单位 | 同时作为两道闸门的门槛（§13.9） |

### 13.2 Total Assets 与 Scaled Assets

```text
totalAssets
= IERC20(asset).balanceOf(LPVault)        // 本地余额
+ IStrategy(strategy).totalAssets()       // 策略持仓

totalAssetsScaled = totalAssets × assetScalar
```

`VaultBase::totalAssets` / `VaultBase::totalAssetsScaled`。两者都是**实时读余额**，不是账本累加，所以交易侧每一次池子收付立即反映在 NAV 上。

v0.3.2 里改变 `totalAssets` 的全部路径：

| 方向 | 触发点 | 代码锚点 |
| --- | --- | --- |
| 流入 | **LP 存款**（用户 → LPVault） | `LPVault::deposit` 的 `safeTransferFrom` |
| 流入 | 开仓 `feeAmountForPool`（PositionVault → market.vault） | `IncreasePositionUtils::processCollateral` |
| 流入 | 平仓 `feeAmountForPool` | `DecreasePositionCollateralUtils::processCollateral` |
| 流入 | 交易者负 PnL 用抵押品实付的部分 | `DecreasePositionCollateralUtils::processCollateral`（`basePnlUsd < 0` 分支） |
| 流出 | 交易者正 PnL（market.vault → PositionVault） | `DecreasePositionCollateralUtils::processCollateral`（`basePnlUsd > 0` 分支） |
| 流出 | 该仓净正 funding（`positive > negative` 的差额） | `MarketUtils::settleFundingFees` |
| 流出 | LP 提款兑付 | `LPVault::claimWithdrawRequest(s)` → `VaultBase::_withdrawAssets` |
| （不改 `totalAssets`） | 本地余额 ↔ 策略的划拨 | `VaultBase::_tryAllocate`（v0.3.2 恒不触发，§13.9） |

- `MarketUtils::settleFundingFees` 在 `negative > positive` 时走的是 `FeeUtils.incrementClaimableFeeAmount`（记 claimable，资金留在 PositionVault），**不进 LP Vault 余额**——这一侧不影响 `totalAssets`。
- `totalAssets` 是实时读余额、无账本校验，所以**任何人直接向 vault 地址（或策略地址）转 asset 都会抬高 `totalAssets`**，NAV 随之跳变，且不产生任何事件。对账时不能假定 NAV 只被上表路径驱动。

### 13.3 NAV

```text
totalSupply == 0：nav = 1e18

否则：
nav = totalAssetsScaled × 1e18 / totalSupply        // 向下取整
```

`VaultBase::nav`。`totalSupply` 包含已发起提款请求的锁定份额——`initiateWithdrawRequest` 是「从用户 burn、再 mint 给 vault 自己」，总量不变，所以发起请求本身不影响 NAV（§13.6）。

### 13.4 Assets 与 Shares

```text
_convertToAssets(shares, nav)
= shares × nav / 1e18 / assetScalar

_convertToShares(assets, nav)
= assets × assetScalar × 1e18 / nav        // 一次向下取整
```

`VaultBase::_convertToAssets` / `_convertToShares`；公开视图 `convertToAssets` / `convertToShares` 用当前 `nav()`。
`VaultBase::_mintShares` 在 v0.3.2 无任何调用点，是死代码。

数值例（USDC 6 位，`assetScalar = 1e12`）：

```text
本地余额 1,200,000,000（1200 USDC）+ 策略 0 → totalAssets = 1.2e9
totalAssetsScaled = 1.2e9 × 1e12 = 1.2e21
totalSupply = 1e21（1000 份额）
nav = 1.2e21 × 1e18 / 1e21 = 1.2e18        // 1.2 USDC/份额

存入 100 USDC（1e8）：
shares = 1e8 × 1e12 × 1e18 / 1.2e18 = 83,333,333,333,333,333,333   （8.3333…e19 向下取整）

以同一 nav 赎回该份额：
83,333,333,333,333,333,333 × 1.2e18 = 9.99999999999999999996e37
/ 1e18 = 99,999,999,999,999,999,999
/ 1e12 = 99,999,999 → 99.999999 USDC
（合并写成 / 1e30 结果相同：9.99999999999999999996e37 / 1e30 = 99,999,999）
```

核对口径三条：

- **两次连续整除可以合并。** 对正整数 `m`、`n` 有 `⌊⌊x/m⌋/n⌋ = ⌊x/(m·n)⌋`，所以 `_convertToAssets` 写成 `(shares×nav)/1e18/assetScalar` 与一次性 `(shares×nav)/(1e18×assetScalar)`（USDC 即 `/1e30`）对任意输入结果**完全相同**。前端 / SDK 合并了这两次除法**不构成差异**，不要据此开缺陷。
- **真正不能动的是乘除顺序**：必须先 `shares × nav` 再整除，不能先除 `assetScalar` 或先除 `1e18` 再乘——先除后乘会丢精度，与链上差 1 wei 级。
- **`_convertToShares` 与 `_convertToAssets` 不互逆**：上例存入 100.000000 USDC、以同一 nav 赎回只拿回 99.999999 USDC，两次向下取整合计留 1 个 asset 最小单位在池子里。E2E 不得用「存多少 = 赎多少」做断言，应按「赎回 ≤ 存入，且差额 ≤ 1 个最小单位（同 nav 下）」核对。

### 13.5 存款

`LPVault::deposit(assets, receiver)`：

```text
1. assets == 0                      → revert ErrorZeroAmount
2. shares = _convertToShares(assets, nav())     // nav 在 transferFrom 之前读 = 存款前的池子
3. safeTransferFrom(msg.sender → LPVault, assets)
4. _mint(receiver, shares)
5. _tryAllocate()                                // §13.9
6. emit Deposit(caller, receiver, assets, shares)
```

存款路径**没有任何风控 gate**（无 PnL / 净义务判定），与《2026-07-22_FX100-储备金与风控体系改造规范(实施版-2026-06-12)》§6.2「存款：不设任何 gate」一致（该编号指需求文档，不是本文的 §6.2）。第 2 步先算份额、第 3 步才收钱，所以本笔资金不参与自身定价。

### 13.6 发起提款请求

`LPVault::initiateWithdrawRequest(shares)`：

```text
shares == 0 → revert ErrorZeroAmount

_burn(msg.sender, shares)
_mint(address(this), shares)                     // 总量不变 → NAV 不变
lockedShares[msg.sender] += shares

unlockAt = ((block.timestamp + withdrawDelaySeconds + 86399) / 86400) × 86400   // 向上取整到下一个 UTC 整日

若 requests 非空且最后一条 unlockAt == 本次 unlockAt：
    requests[len-1].shares += shares             // 合并，不新增 requestId
否则：
    requests.push({shares, unlockAt, claimed:false})

emit InitiateWithdrawRequest(caller, shares, unlockAt)
```

- 只与**最后一条**比对 `unlockAt`，不遍历全数组；所以「今天发起 A，明天发起 B，后天又发起一笔与 A 同 unlockAt 的」这种情况不会合并到 A。
- `shares` 存进 `uint128`，是显式截断转换（不是 checked 加法），超过 `2^128-1` 会静默截断；实际份额规模不可达该量级。
- 没有取消/撤回请求的接口：份额一旦锁进 vault，只能等 claim。

### 13.7 兑付提款

`LPVault::claimWithdrawRequest(requestId, receiver)` / `claimWithdrawRequests(requestIds[], receiver)`，执行顺序：

```text
1. _advanceEpoch()
2. _validateWithdrawalsAllowed()          // 全局净义务 gate
3. currentNav = nav()                     // 只取一次，本次 claim 全程复用
4. 逐条 _claimWithdrawRequest(...)        // 三道校验 + 置 claimed + 释放 lockedShares
5. assets = _convertToAssets(Σshares, currentNav)
6. _burn(address(this), Σshares)          // 在 nav 取值之后 burn，本次换算不受自身影响
7. _withdrawAssets(assets, receiver)      // §13.8
```

**第 2 步（gate）**，`LPVault::_validateWithdrawalsAllowed` → `MarketUtils::isGlobalNetObligationRatioExceeded(dataStore, oracle, MAX_PNL_FACTOR_FOR_WITHDRAWALS, isADLStart = false)`：

```text
globalNetObligationRatio > MAX_PNL_FACTOR_FOR_WITHDRAWALS
    → revert WithdrawGlobalNetObligationRatioExceeded(ratio, threshold)
```

`globalNetObligationRatio` 的取价口径（`MarketUtils::getGlobalNetObligationRatio`，复算时四点缺一不可，**不要只按 §12.4 的化简式算**）：

```text
分子：逐市场累加
    indexTokenPrice = oracle.getSecondaryPrice(market.indexToken, isADLStart = false)
    netObligation_i = max(getPnl(..., isLong=true,  maximize=true), 0)
                    + max(getPnl(..., isLong=false, maximize=true), 0)

分母：只在循环的 i == 0 那一轮取一次
    collateralTokenPrice = oracle.getSecondaryPrice(market.collateralToken, isADLStart = false)
    poolUsd = getPoolUsdWithoutPnl(market, collateralTokenPrice, maximize = false)
            = IVault(market.vault).totalAssets() × collateralTokenPrice.min

poolUsd == 0 → 直接返回 0（不判超限，gate 放行）
否则 ratio = Precision.toFactor(Σ netObligation_i, poolUsd) = Σ × 1e30 / poolUsd   // 向下取整
```

- 分子 `maximize = true`（PnL 取对交易者最有利侧），分母 `maximize = false`（抵押品取 **min** 价）——两侧方向相反，复算时用错任何一侧都会读出与链上不同的门槛判定（假缺陷 / 漏缺陷）。
- 两侧都走 `getSecondaryPrice(token, false)`，即**次级价且要求严格新鲜**；价格过期时该取价函数自身 revert，gate 不会「静默放行」。
- 分母只取 `marketIndices[0]` 那个市场的 `vault`，依赖「所有市场共用同一 LPVault」这一部署不变量（源码注释写明，合约层零校验）。
- 严格大于才 revert，**等于放行**。
- `MAX_PNL_FACTOR_FOR_WITHDRAWALS` 是全局单键，不带 marketIndex / isLong。
- 存款侧无对应 gate。

**第 4 步（每条请求的三道校验）**，`LPVault::_claimWithdrawRequest`，顺序固定：

```text
request.unlockAt > block.timestamp        → revert WithdrawRequestNotUnlocked
request.unlockAt >= currentEpoch.startTime → revert WithdrawRequestEpochNotEnded
request.claimed                            → revert WithdrawRequestAlreadyClaimed
```

即「时间闸 + epoch 闸」双条件：请求必须已解锁，**且**其 `unlockAt` 必须落在当前 epoch 起点之前。

**第 5 步（批量与逐条的取整差）**：`claimWithdrawRequests` 先把各条 `shares` 求和再换算一次，`claimWithdrawRequest` 每条各换算一次。**在同一个 nav 快照下**，同一组 n 条请求逐条 claim 拿到的总额比批量 claim 最多少 n−1 个 asset 最小单位（`Σ floor(x_i) ≤ floor(Σ x_i)`），差额留在池子里。实际逐条 claim 分散在多笔交易里，每笔留下的取整余尘会让 nav 微升，后续几条的单价随之抬高，因此该上界只在「同一 nav」的对照实验里严格成立，跨交易比较时只能作为量级参考。

**事件口径**：`ClaimWithdrawRequest` 事件里的 `assets` 是在 `_claimWithdrawRequest` 内**按该条单独换算**的值。批量 claim 时各条事件金额之和 ≤ 第 7 步实际转出的 `assets`。核对转账金额要用 ERC20 Transfer / 余额差，不能加总事件字段。

### 13.8 资产转出（v0.3.2 改）

`VaultBase::_withdrawAssets(assets, receiver)`，同时服务 LP 提款兑付与 `transferOut`（下文）：

```text
balance = IERC20(asset).balanceOf(LPVault)

balance >= assets:
    safeTransfer(receiver, assets)                       // 单笔转出，结束

balance < assets:
    shortage = assets - balance
    balance != 0 → safeTransfer(receiver, balance)       // ① v0.3.2 新增：先把本地余额发出去
    before = IERC20(asset).balanceOf(receiver)           // ② v0.3.2 新增
    IStrategy(strategy).withdraw(asset, shortage, receiver)
    after  = IERC20(asset).balanceOf(receiver)
    received = after >= before ? after - before : 0
    received != shortage → revert ErrorStrategyWithdrawalMismatch(shortage, received)   // ③ v0.3.2 新增
```

几点要注意：

- ① 是 v0.3.1 的漏发修复。v0.3.1 缺口路径只从 Strategy 取 `shortage` 给 `receiver`，本地 `balance` **不转**，receiver 实收 `= shortage < assets`，而份额已 burn，差额永久留在 vault（LP 少拿）。
- ③ 校验的是**恰好相等**，不是「至少」：Strategy 少给会 revert，多给同样 revert；`receiver` 在同一笔里被别的路径打款也会破坏该等式。
- 校验用的是 `receiver` 的余额差，不是 vault 的。若 `receiver` 是会在 `withdraw` 回调里再转走资产的合约，等式不成立、整笔 revert。
- v0.3.2 默认部署的 strategy 是 `src/periphery/NoopStrategy.sol`（`totalAssets` = 自身余额，`withdraw` 是裸 `transfer` 且不检查返回值）。它的余额恒为 0（除非有人直接给策略地址转账），所以**一旦进入缺口分支就必然失败**：标准 ERC20 的 `transfer` 余额不足直接 revert，报的是 ERC20 自己的余额不足错误、整笔交易回滚（前面 ① 的本地余额转出也一并回滚）；只有当 asset 是「失败返回 false 而不 revert」的非标准 token 时，才会走到 `received = 0 ≠ shortage` 的 `ErrorStrategyWithdrawalMismatch`。
- ①②③ 三点都作用在 `balance < assets` 这一条分支内；`balance >= assets` 的正常路径 v0.3.1 与 v0.3.2 完全一致。

`VaultBase::transferOut(token, to, amount)`：`CONTROLLER_ROLE` 限定，`token != asset` → `revert ErrorInvalidToken`，随后走同一个 `_withdrawAssets`。市场侧支付交易者正 PnL、净正 funding 走的都是它，所以上面的缺口路径与 mismatch revert 同样作用在交易结算路径上（可达性见 §13.9 末段）。

### 13.9 Strategy 分配（三道闸门）

`VaultBase::_tryAllocate()`，v0.3.2 唯一调用点是 `LPVault::deposit`：

```text
strategyAssets = IStrategy(strategy).totalAssets()
localAssets    = IERC20(asset).balanceOf(LPVault)

闸门①  localAssets < minDeposit                                  → return
        cachedTotalAssets = strategyAssets + localAssets
闸门②  !(strategyAssets × 1e18 < allocationPercentage × cachedTotalAssets)  → return
        newAllocation = cachedTotalAssets × allocationPercentage / 1e18 - strategyAssets   // 先向下取整再相减
闸门③  newAllocation < minDeposit                                → return

forceApprove(strategy, newAllocation)
IStrategy(strategy).deposit(asset, newAllocation)
```

- **闸门③ 是原文档漏掉的一道**：即使本地余额够、占比也低于目标，只要本次可分配额低于 `minDeposit` 也直接返回，不分配。
- 闸门② 用交叉相乘避免除法，等价于 `strategyAssets / cachedTotalAssets < allocationPercentage / 1e18`（严格小于）。
- 闸门② 成立时 `floor(cachedTotalAssets × pct / 1e18) ≥ strategyAssets`，闸门③ 之前的减法不会下溢。
- `allocationPercentage ≤ 1e18` 时 `newAllocation ≤ localAssets`，不会超发；配置 > 1e18 会让 `deposit` 因余额不足 revert。
- 三道闸门都是**静默 return**，不 revert，也不 emit，所以 `deposit` 不会因为分配失败而失败。

**v0.3.2 现状：分配路径永远不触发。** `strategyInfo` 只在 `VaultBase::__VaultBase_init` 里写入，`LPVault::initialize` 传的是 `(_strategyMinDeposit = 0, _strategyAllocationPercentage = 0)`，而 `VaultBase` / `LPVault` **都没有对外的 setter**（`_updateStrategyMinDeposit` / `_updateStrategyAllocationPercentage` 均为 internal 且仅被 init 调用）。`allocationPercentage = 0` 使闸门② 恒不成立（`strategyAssets × 1e18 < 0` 为 false）。因此 `IStrategy.totalAssets()` 恒为 0（除非有人直接给策略地址转账），`totalAssets ≡ LP Vault 本地余额`。

由此推出的 §13.8 可达性，要按**两条调用路径分开说**：

- **LP claim 路径：缺口分支不可达。** `strategyAssets ≡ 0` 时 `nav = ⌊balance × assetScalar × 1e18 / totalSupply⌋`，于是
  `assets = ⌊shares × nav / 1e18 / assetScalar⌋ ≤ shares × balance / totalSupply ≤ balance`（`shares` 是 `totalSupply` 的子集，锁定份额也计入 `totalSupply`），`balance >= assets` 恒成立，永远走单笔转出分支。
- **`transferOut` 路径：缺口分支可达。** 支付交易者正 PnL（`DecreasePositionCollateralUtils` 的 `IVault(params.market.vault).transferOut(...)`）与净正 funding（`MarketUtils::settleFundingFees`）走的是同一个 `_withdrawAssets`，与 LP 本地余额之间**没有任何合约层不变量保证**——单笔正 PnL 只被 `MAX_PNL_FACTOR_FOR_TRADERS` 相对**该侧**池子 USD 封顶（`PositionUtils::getPositionPnlUsd`），多空两侧叠加、以及后续 funding 兑付连续扣减之后，池子仍可能不足以覆盖某一次兑付。此时按 §13.8 的顺序：先把本地余额发给 PositionVault，再向余额为 0 的 NoopStrategy 要 `shortage` → 裸 `transfer` 余额不足 revert → **整笔平仓/结算失败**。

  注意报错口径：这里报的是 ERC20 的余额不足错误，**不是** `ErrorStrategyWithdrawalMismatch`。

- **覆盖策略**：缺口分支本身可以用「把 LP 池压到不足以支付本次正 PnL / 净正 funding」的挤兑场景在 E2E 触达（期望是整笔 revert 的负向用例）；而 `ErrorStrategyWithdrawalMismatch` 这条具体错误、以及 §13.9 的三道闸门，需要换一个会「少给 / 多给」的策略实现或单测 mock（必要时配合升级代理注入 setter）才能覆盖。

`VaultBase::updateStrategy(newStrategy)`（`DEFAULT_ADMIN_ROLE`，`newStrategy == 0` → `revert ErrorZeroAddress`）只改地址，**不迁移旧策略里的资产**：换掉之后 `totalAssets` 立刻少掉旧策略那部分，NAV 同步跳变。

### 13.10 Epoch 与提款延迟

```text
initialize:
    _epochStartTime >= block.timestamp → revert StartTimeInThePast
    currentEpoch = { duration, index: 0, startTime, endTime: startTime + duration - 1 }

_advanceEpoch()（仅 claimWithdrawRequest(s) 调用）:
    block.timestamp >= currentEpoch.endTime 时：
        epochs[index] = { startTime, endTime }        // 归档
        index    += 1
        startTime = 旧 endTime + 1
        endTime   = startTime + duration - 1
```

- `initialize` 的 revert 条件与错误名相反：实际是「起始时间不在过去（>= now）就 revert」，错误名 `StartTimeInThePast` 属命名误导，不影响行为。
- `_advanceEpoch` 是 `if` 不是 `while`：**一次调用最多推进一个 epoch**。若长期无人 claim，`currentEpoch` 会落后于实际时间，需要多次成功 claim 才追得上。
- epoch 推进和 claim 在同一笔交易里：被 gate 或三道校验 revert 的调用会把推进一起回滚，所以**只有成功的 claim 才会真正推进 epoch**。
- `updateEpochDuration(newDuration)`（`DEFAULT_ADMIN_ROLE`）只写 `currentEpoch.duration`，当前 epoch 的 `endTime` 不变 → 新时长从下一个 epoch 起生效。
- `updateWithdrawDelaySeconds(newDelay)`（`DEFAULT_ADMIN_ROLE`）只影响此后新建的请求，已存在请求的 `unlockAt` 不重算。
- `updateOracle(newOracle)`（`DEFAULT_ADMIN_ROLE`，`0` → `revert ErrorZeroAddress`）换的是提款 gate 用的取价源。

## 14. 执行费

代码锚点：`src/gas/GasUtils.sol`（估算/校验/封顶/结算）、`src/order/OrderUtils.sol::createOrder`、`src/exchange/OrderHandler.sol::updateOrder`、`src/order/ExecuteOrderUtils.sol::executeOrder`、`src/order/OrderUtils.sol::cancelOrder|freezeOrder`、`src/router/ExchangeRouter.sol`、`src/router/SubaccountRouter.sol`。

创建/改单时按**固定三步**走：① 创建期豁免判定 → ② 最低执行费校验 → ③ 最大执行费封顶（只在一条路径上生效）。命中 ① 时跳过的只是 **②③ 这两步**；`callbackGasLimit` 的上限校验在 `createOrder` 里位于豁免分支之外，豁免单同样要过（见 §14.1）。

### 14.1 创建期豁免判定

`GasUtils::isExecutionFeeSubsidizedAtCreation(dataStore, marketIndex, sizeDelta, isSizeDeltaUsd)`：

```text
isSizeDeltaUsd == true:
    usdThreshold = dataStore.getUint(executionFeeSubsidizeKey(marketIndex))    // EXECUTION_FEE_SUBSIDIZE，USD 1e30
    usdThreshold == type(uint256).max → false                                  // MAX = 关闭豁免
    否则 subsidized = (sizeDelta >= usdThreshold)

isSizeDeltaUsd == false:
    sizeThreshold = dataStore.getUint(executionFeeSubsidizeSizeKey(marketIndex))  // EXECUTION_FEE_SUBSIDIZE_SIZE，index token 原生单位
    sizeThreshold == type(uint256).max → false
    否则 subsidized = (sizeDelta >= sizeThreshold)
```

- 两条分支都是原生单位直接比较，**都不读 oracle**。
- 键未在 DataStore 设置时 `getUint` 返回 `0`，而 `sizeDelta >= 0` 恒真 → **未配置 = 全场豁免执行费**（不是全场收费）。极性与「MAX = 关闭」相反，是运维记忆点，也是测试环境常见的「执行费永远为 0」的原因。

`OrderUtils::createOrder`：

```text
wntAmount  = orderVault.recordTransferIn(WNT)          // 本笔实际收到的 WNT
subsidized = isExecutionFeeSubsidizedAtCreation(dataStore, marketIndex, sizeDelta, isSizeDeltaUsd)

subsidized:
    order.executionFee = 0
    wntAmount != 0 → orderVault.transferOut(WNT, order.receiver(), wntAmount)    // 误传的 WNT 原路退给 receiver

否则:
    wntAmount < params.numbers.executionFee → revert InsufficientWntAmountForExecutionFee(wntAmount, executionFee)
    params.numbers.executionFee = wntAmount                                      // 以实收 WNT 为准

—— 以下与豁免与否无关，两条分支都执行 ——
CallbackUtils.validateCallbackGasLimit(dataStore, order.callbackGasLimit())
    callbackGasLimit > MAX_CALLBACK_GAS_LIMIT → revert MaxCallbackGasLimitExceeded

if (!subsidized):
    → §14.2（最低执行费）+ §14.3（封顶）
```

- **`validateCallbackGasLimit` 是公共校验**：源码里它排在豁免 if/else 之后、`if (!isExecutionFeeSubsidizedAtCreation)` 之前，**豁免单一样要过**。豁免单只要 `callbackGasLimit > MAX_CALLBACK_GAS_LIMIT` 照样 `revert MaxCallbackGasLimitExceeded`，不要按「豁免就整段跳过」去推期望。
- 另有一道条件性的回调 gas 校验：`order.autoCancel()` 为 true 且订单类型是 `LimitDecrease` / `StopLossDecrease` 时，`OrderUtils::validateTotalCallbackGasLimitForAutoCancelOrders` 校验该仓位下自动取消单的回调 gas **总量** `<= MAX_TOTAL_CALLBACK_GAS_LIMIT_FOR_AUTO_CANCEL_ORDERS`，超限 revert；这一道同样与豁免无关。
- **多传的 WNT 不退**：非豁免分支把 `executionFee` 直接改写成 `wntAmount`，所以用户 `sendWnt` 多打的部分全部计入执行费（只在 §14.3 封顶生效且超限时才被切走，去向见 §14.3）。

`OrderHandler::updateOrder` 按**改单后的 sizeDelta / isSizeDeltaUsd** 重判豁免：

```text
receivedWnt = orderVault.recordTransferIn(WNT)
subsidized  = isExecutionFeeSubsidizedAtCreation(store, order.marketIndex, 新 sizeDelta, 新 isSizeDeltaUsd)

subsidized（改大过线）:
    executionFeeRefund = order.executionFee + receivedWnt
    order.executionFee = 0
    executionFeeRefund != 0 → orderVault.transferOut(WNT, order.receiver(), executionFeeRefund)   // 已付执行费全额退

否则（含改小掉线）:
    以 (order.executionFee + receivedWnt) 为待校验金额走 §14.2 + §14.3
    不足 minExecutionFee → revert InsufficientExecutionFee                                        // 必须随附补足的 WNT
```

改单路径**不校验 `callbackGasLimit`**——该字段在 `updateOrder` 里不可改，`validateCallbackGasLimit` 全仓库只有 `OrderUtils::createOrder` 一个调用点。

其它前置：市价单不可改（`Order.isMarketOrder` → `revert OrderNotUpdatable`）；不支持的 orderType → `revert UnsupportedOrderType`；`Liquidation` 单且 `!isSizeDeltaUsd` → `revert InvalidSizeDeltaTypeForOrder`。

**清算 / ADL 单不经 `createOrder`**：`src/liquidation/LiquidationUtils.sol` 与 `src/adl/AdlUtils.sol` 直接构造 `Order.Props`，`executionFee` 写死 `0`，执行期 `payExecutionFee(0)` 首行返回，keeper 链上零补偿。

### 14.2 最低执行费

`GasUtils::adjustGasLimitForEstimate` + `GasUtils::validateExecutionFee`：

```text
estimatedGasLimit
= 增仓单：INCREASE_ORDER_GAS_LIMIT + order.callbackGasLimit
  减仓单：DECREASE_ORDER_GAS_LIMIT + order.callbackGasLimit
  其它 orderType → revert UnsupportedOrderType

oraclePriceCount = 3 + swapsCount
                 // GasUtils::estimateOrderOraclePriceCount；v0.3.2 全部调用点都传 swapsCount = 0 → 恒为 3

gasLimit
= ESTIMATED_GAS_FEE_BASE_AMOUNT_V2_1
+ ESTIMATED_GAS_FEE_PER_ORACLE_PRICE × oraclePriceCount
+ estimatedGasLimit × ESTIMATED_GAS_FEE_MULTIPLIER_FACTOR / 1e30      // applyFactor，向下取整

minExecutionFee = gasLimit × tx.gasprice

executionFee < minExecutionFee → revert InsufficientExecutionFee(minExecutionFee, executionFee)
```

- `tx.gasprice` 取的是**创建 / 改单这笔交易**的 gas price，不是将来执行那笔的。fork / 测试网 `gasprice ≈ 0` 时 `minExecutionFee = 0`，任何金额（含 0）都过校验。
- `order.callbackGasLimit` 在本节的作用只有一个：直接抬高 `estimatedGasLimit`，从而抬高 `minExecutionFee`。它的**上限校验不在本节**，而在 §14.1 的公共路径上（豁免单也要过）。
- v0.3.2 删除了 `GasUtils::estimateExecuteSwapOrderGasLimit`（swap 单估算），运行时等价——本版本没有可创建的 swap 订单类型。

数值例（下列常量为**示例值，非部署实值**）：

```text
ESTIMATED_GAS_FEE_BASE_AMOUNT_V2_1  = 600,000
ESTIMATED_GAS_FEE_PER_ORACLE_PRICE  = 250,000
ESTIMATED_GAS_FEE_MULTIPLIER_FACTOR = 1.2e30        （120%）
INCREASE_ORDER_GAS_LIMIT = 3,000,000，callbackGasLimit = 0
tx.gasprice = 2e7 wei（0.02 gwei）

estimatedGasLimit = 3,000,000
gasLimit = 600,000 + 250,000 × 3 + 3,000,000 × 1.2 = 4,950,000
minExecutionFee = 4,950,000 × 2e7 = 9.9e13 wei = 0.000099 ETH
```

### 14.3 最大执行费封顶

`GasUtils::validateAndCapExecutionFee` 在 §14.2 之后立刻执行，**第一步就是开关判定**：

```text
shouldCapMaxExecutionFee == false → 直接返回 (executionFee, executionFeeDiff = 0)
                                    // 不封顶、不产生 diff、不转 HOLDING
```

`shouldCapMaxExecutionFee` 在 v0.3.2 的全部取值：

| 入口 | createOrder | updateOrder | 锚点 |
| --- | --- | --- | --- |
| `ExchangeRouter`（直连） | `false` | `false` | `ExchangeRouter::createOrder` / `::updateOrder` |
| `SubaccountRouter`（子账户） | `params.addresses.callbackContract != address(0)` | `order.callbackContract() != address(0)` | `SubaccountRouter::createOrder` / `::updateOrder` |
| `BaseRelayRouter`（Relay / Express，含 `SubaccountRelayRouter`） | `false` | `false` | `BaseRelayRouter::_createOrder` / `::_updateOrder` |

→ **唯一会触发封顶的路径是 `SubaccountRouter` 且订单带非零 `callbackContract`。** 其余路径的执行费不设上限。Relay 路径另有全局键 `MAX_RELAY_SWAP_WNT_CAP` 对 relayer 单笔垫付的原生费设硬上限、超限直接 revert（见 §15），与本节封顶是两套机制。

封顶生效时：

```text
basefee = block.basefee != 0 ? block.basefee : tx.gasprice
          // 非 EIP-1559 链、eth_call / eth_estimateGas 下 block.basefee 为 0，回退到 tx.gasprice

maxExecutionFee
= gasLimit × basefee × MAX_EXECUTION_FEE_MULTIPLIER_FACTOR / 1e30    // gasLimit 同 §14.2 的调整后值；applyFactor 向下取整

maxExecutionFee < minExecutionFee
    → revert InvalidExecutionFee(executionFee, minExecutionFee, maxExecutionFee)   // 参数自相矛盾，整笔失败

executionFee <= maxExecutionFee
    → 返回 (executionFee, 0)

否则
    → 返回 (maxExecutionFee, executionFeeDiff = executionFee - maxExecutionFee)
       order.executionFee 被写成 maxExecutionFee
```

**运维坑：`MAX_EXECUTION_FEE_MULTIPLIER_FACTOR` 未配置时 `getUint` 返回 `0`** → `maxExecutionFee = 0`；只要 `minExecutionFee > 0`（即 `tx.gasprice > 0`）就必然命中 `maxExecutionFee < minExecutionFee`，`revert InvalidExecutionFee`。也就是说在唯一会封顶的那条路径（`SubaccountRouter` + 非零 `callbackContract`）上，**忘配这个键 = 该路径全部下单/改单直接失败**。排查「子账户带回调下单必 revert」时先查这个键。

`executionFeeDiff != 0` 时，调用方（`OrderUtils::createOrder` / `OrderHandler::updateOrder`）立刻调 `GasUtils::transferExcessiveExecutionFee`：

```text
holdingAddress = dataStore.getAddress(HOLDING_ADDRESS)
holdingAddress == address(0) → revert EmptyHoldingAddress          // 整笔下单/改单失败

orderVault.transferOut(WNT, holdingAddress, executionFeeDiff)      // WNT，不解包
emit ExcessiveExecutionFee(account, executionFeeDiff)
```

**`executionFeeDiff` 只有这一个去向。** 不退还用户，不进 keeper，也不存在任何「按规则退款 / 补贴」分支——v0.3.2 源码里没有第二个消费 `executionFeeDiff` 的调用点。

数值例（接 §14.2 的示例值，`MAX_EXECUTION_FEE_MULTIPLIER_FACTOR = 3e30`，`basefee = 2e7`）：

```text
maxExecutionFee = 4,950,000 × 2e7 × 3 = 2.97e14 wei = 0.000297 ETH
用户经 SubaccountRouter（callbackContract != 0）随单发 1e15 wei（0.001 ETH）：
    executionFeeDiff = 1e15 - 2.97e14 = 7.03e14 wei → HOLDING_ADDRESS（WNT）
    order.executionFee = 2.97e14
同一笔改走 ExchangeRouter：shouldCap = false → order.executionFee = 1e15，无 diff
```

### 14.4 Keeper 结算与退款

`GasUtils::payExecutionFee`，三个调用点：`ExecuteOrderUtils::executeOrder`、`OrderUtils::cancelOrder`、`OrderUtils::freezeOrder`。

```text
executionFee == 0 → 立即 return 0
                    // 豁免单、清算/ADL 单、已冻结过的单都在这里结束，keeper 拿不到任何链上补偿

startingGas -= gasleft() / 63          // 扣掉 63/64 转发余量
gasUsed = startingGas - gasleft()

adjustedGasUsed
= EXECUTION_GAS_FEE_BASE_AMOUNT_V2_1
+ EXECUTION_GAS_FEE_PER_ORACLE_PRICE × oraclePriceCount               // 恒 3
+ gasUsed × EXECUTION_GAS_FEE_MULTIPLIER_FACTOR / 1e30                 // applyFactor，向下取整

executionFeeForKeeper = min(executionFee, adjustedGasUsed × tx.gasprice)   // tx.gasprice 是执行交易的
refundFeeAmount       = executionFee - executionFeeForKeeper
```

付款顺序与去向：

```text
1. bank.transferOutNativeToken(keeper, executionFeeForKeeper)
       解包 WNT → 原生币发 keeper；发送失败 → 重新包成 WNT 发 keeper；再失败 → 发 HOLDING_ADDRESS
       （TokenUtils::withdrawAndSendNativeToken → depositAndSendWrappedNativeToken → transfer）
   emit KeeperExecutionFee(keeper, amount)

2. refundFeeAmount == 0 → return 0，结束

3. bank.transferOut(WNT, 调用合约, refundFeeAmount)；IWNT.withdraw(refundFeeAmount)   // 解包成原生币

4. CallbackUtils::refundExecutionFee(dataStore, key, callbackContract, refundFeeAmount, ...)
       callbackContract != 0 且有代码（isValidCallbackContract）
       且 gasleft()/64×63 >= REFUND_EXECUTION_FEE_GAS_LIMIT（否则 revert InsufficientGasLeftForCallback）
       → 带 value 调 callbackContract.refundExecutionFee{gas: REFUND_EXECUTION_FEE_GAS_LIMIT}
       成功 → emit ExecutionFeeRefundCallback，返回 0（退款进了回调合约，不到 refundReceiver）
       回调地址无效 / 调用 revert → 落到第 5 步

5. TokenUtils::sendNativeToken(refundReceiver, refundFeeAmount)
       原生币发送失败 → 包成 WNT 发 refundReceiver → 再失败 → 发 HOLDING_ADDRESS
   emit ExecutionFeeRefund(receiver, amount)，返回 refundFeeAmount
```

`refundReceiver` 按调用点不同：

| 调用点 | refundReceiver |
| --- | --- |
| `ExecuteOrderUtils::executeOrder` | `order.receiver()` |
| `OrderUtils::cancelOrder` | `order.cancellationReceiver()`；为 `address(0)` 时退回 `order.receiver()` |
| `OrderUtils::freezeOrder` | `order.receiver()` |

`freezeOrder` 的特殊顺序：先把 `order.executionFee` 置 0 并落盘，再拿冻结前的旧值调 `payExecutionFee`。所以冻结后的订单 `executionFee = 0`，后续执行或取消时 keeper 不再有链上补偿。

数值例（接前例，执行期 `EXECUTION_GAS_FEE_BASE_AMOUNT_V2_1 = 600,000`、`EXECUTION_GAS_FEE_PER_ORACLE_PRICE = 250,000`、`EXECUTION_GAS_FEE_MULTIPLIER_FACTOR = 1.0e30`、`gasUsed = 1,200,000`、执行 `tx.gasprice = 2e7`）：

```text
adjustedGasUsed = 600,000 + 750,000 + 1,200,000 = 2,550,000
adjustedGasUsed × gasprice = 5.1e13
executionFee = 9.9e13
executionFeeForKeeper = min(9.9e13, 5.1e13) = 5.1e13
refundFeeAmount = 9.9e13 - 5.1e13 = 4.8e13 → order.receiver()（无有效回调合约时）
```

### 14.5 子账户自动补 Gas

`SubaccountRouter::_autoTopUpSubaccount`，在 `createOrder` / `updateOrder` / `cancelOrder` 主逻辑之后调用：

```text
amount = SubaccountUtils.getSubaccountAutoTopUpAmount(dataStore, account, subaccount)
amount == 0                                → return（静默）
WNT.allowance(account, router) < amount    → return（静默）
WNT.balanceOf(account) < amount            → return（静默）

nativeTokensUsed = (startingGas - gasleft()) × tx.gasprice + executionFee
                   // createOrder 传 params.numbers.executionFee；updateOrder / cancelOrder 传 0
amount = min(amount, nativeTokensUsed)

router.pluginTransfer(WNT, account → SubaccountRouter, amount)
TokenUtils.withdrawAndSendNativeToken(dataStore, WNT, subaccount, amount)   // 解包成原生币发子账户
emit SubaccountAutoTopUp(account, subaccount, amount)
```

三个早退分支都是静默 return，不 revert，主账户授权或余额不足时下单照常成功、只是不补 gas。补给的是**原生币**，`amount` 以「本笔实际消耗的原生币（gas + 执行费）」封顶，不会超额补。

# ETH 加仓放大后被清算 · 场景记录

## 1. 一句话概述

## 4. 核心问题答案：Liquidatable + SL 满足时 keeper 执行 SL 还是清算？

**keeper 为两笔 SL 各发了一笔独立执行交易（OrderHandler 通道），两笔均被合约冻结（OrderFrozen，零成交），随后由 LiquidationHandler 清算收尾。** 不是"SL 从未尝试、直接取消"。区分铁证：清算费 0.3%（$287.15）+ 两条通道两个合约地址。判定订单命运须以链上事件序列为准，前端 "Cancelled" 抹掉了 Frozen 中间态。

## 6. 本场景确立/强化的产品语义（核对手册增补）

- **调杠杆本质=加仓/减仓**：Adjust Leverage「保证金固定、调仓位规模」，升杠杆发市价加仓单、只对 Size Change 增量收 0.05% 开仓费；Target Size 基准为 Equity（含 PnL+资金费）。
- **SL 执行的抵押守卫**：陈旧小额 reduce-only 单在仓位放大后执行会击穿最小抵押/杠杆守卫而被冻结（`min collateral for leverage` / `pnl`）。
- **两条 keeper 通道**：普通触发单走 OrderHandler `0x84162e52…`；清算走 LiquidationHandler `0x40a99db1…`。清算费 0.3% 是清算的唯一铁证特征。
- **insolvent 禁止手动平仓**：仓位达 Liquidatable 时 Close Position 按钮灰化为 "Pending Liquidation"、Est.Receive 0、提示"cannot be closed manually"——防穿仓抢跑（正确设计）。
- **保护面板状态谱**（本场景补全，第六班逐拍）：You are protected → **Successfully rescued** → being rescued → **You'll be liquidated** → You have been liquidated；含临期 Add Margin 自救入口。价格反弹时可"暂逃"（Liquidatable/Expired 态存活约 1 分钟后价格回落再被清算）。
- **保护倒计时不因加仓重置**（本场景铁证）：加仓前后 06:02→05:05 连续递减，15 分钟窗锚定初次开仓——与减仓不重置合并，加/减仓/刷新均不重置。

## 7. 待评估的产品语义疑点（第六班提出，建议立缺陷/需求确认）

**"免清算保护"在保护窗内冻结 SL，使用户无法主动止损** —— 本场景中 SL 触发条件满足后被 Frozen（根因是 TPSLSIZE-012 的抵押守卫，但即便 SL 正常放大，保护窗内减仓能否执行本身也需确认），用户在保护期内**既不会被清算、也无法止损离场**，只能眼看亏损从约 −$654 放大到 −$954.78（清算收尾）。"保护"在此变成"锁仓禁止止损"。
- 待厘清：保护窗内用户主动 SL/减仓/平仓是否应被允许？（对照 LOG-035 保护期内 TP 可执行 PASS、17:37 保护期内主动减仓 PASS——**主动平仓/减仓在保护期内是可以的**，故本例 SL 冻结主因仍是 012 的 size 未放大击穿守卫，而非"保护禁止止损"）。
- 结论倾向：**非"保护禁止止损"缺陷，而是 012 的下游后果**——但需求侧仍建议确认"保护窗内 + 已达清算门槛"时用户主动平仓的预期行为。关联 OC-17 / SCN-B32 系列，留下一轮定性。

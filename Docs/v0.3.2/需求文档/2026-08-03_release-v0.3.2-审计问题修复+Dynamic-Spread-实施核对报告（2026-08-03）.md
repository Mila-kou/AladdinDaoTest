### 3.3 清算/ADL 是否保留正向上限——已定案：保留，与普通交易一致

方案文档三.1/三.2 的原始设计意图是"清算/ADL 完全不受这次改动影响，保持今天 floor-at-0、**无上限**的行为"。实际实现里：

```solidity
if (!params.allowNegativeSpread && minDynamicSpread < 0) {
    minDynamicSpread = 0;          // ✅ 下限按方案清零，没有 rebate
}
if (maxDynamicSpread < minDynamicSpread) {
    maxDynamicSpread = minDynamicSpread;
}
return (Calc.clamp(dynamicSpread, minDynamicSpread, maxDynamicSpread), balanceWasImproved);
```

清算/ADL 路径**只清零了下限**，**上限 `maxDynamicSpread` 沿用了普通交易那一份配置**——跟"清算完全不设上限"的原始设计不完全一致。第一轮核对时把这个当作一处待确认的偏离提出。

**✅ 2026-08-03 团队已拍板**：**保留现状（清算/ADL 沿用普通交易的 `maxDynamicSpread` 上限），不再单独放开**，理由是"与其他交易保持一致"——即工程师当前的实现就是最终设计，不需要改代码。已同步更新 [impl_spec_negative_dynamic_spread.md](../analysis/pricing/impl_spec_negative_dynamic_spread.md) §九.3 和相关业务文档，把这一点从"待确认的偏离"改为"确认的设计决策"。

- 部署仍需注意：`scripts/config/defaults.ts` 目前把 `maxDynamicSpread` 默认配到 `WEI_PRECISION`（100%，等效无上限）——既然清算/ADL 也复用这同一个值，未来任何市场调整 `maxDynamicSpread` 都会**同时影响清算执行价**，配置时要按"这个数值同时管着清算和普通交易"来对待，不能只按单个市场的 UX 目标配置。
- 建议后续补一条测试：清算/ADL 场景下构造 `dynamicSpread` 超过市场配置 `maxDynamicSpread` 的情况，确认清算执行价确实被这个上限封顶（这是新确认的预期行为，不是要防御的 bug）。

### 5.4 〔2026-08-05 新增〕funding 结算架构确认：`updateFundingState` 与 `settleFundingFees` 的职责拆分，需要产品/工程决策

`src/` 正式同步 `release/v0.3.2` 基线后确认了 §5.3 第 2 点提到的关联的最终形态：

- `MarketUtils.updateFundingState`（全市场级、周期性调用）现在**只做累计**——更新每个市场的资金费率指数（per-size 累计值），**不产生任何真实价值转移，也不做 claimable 手续费记账**。
- `MarketUtils.settleFundingFees`（**按持仓单独调用，只在开仓/减仓时触发**）现在是**唯一**真正做 LP vault 转账 / claimable 手续费记账的地方。

这个"累计 vs 结算分离"的架构本身更清晰（累计是全局、无副作用的状态更新；结算是按持仓、有真实资金流动的操作），但推翻了三条测试最初的假设——"仅调用一次全局 `updateFundingState` 就能让 `positionPaysLp` 路由进 claimable 账本"在新架构下不再成立（必须真的走到某个持仓的开/减仓、触发 `settleFundingFees`，才会有资金流动/记账）。受影响的三条测试（均已 `vm.skip(true)`，注释里已写明原因，测试本身不需要进一步动作）：

- `test/integration/core/FundingFee.int.t.sol::test_INT_FUNDING_11_PositionPaysLpRoutesToClaimable`
- `test/integration/core/FundingFee.int.t.sol::test_INT_FUNDING_NUM_06_Exact266RoutesToClaimable`
- `test/e2e/accounting/phase1/P9_UsdcPricePrecision.t.sol::test_UB3_fundingFeePayment_usesMin`

**需要产品/工程决策的问题**：这个"累计-only + 按持仓才结算"的架构是否就是最终设计意图？如果是，上述三条测试应该重写为断言新的 accrual-only 行为（而不是继续断言"全局调用即路由 claimable"）；如果不是（即产品仍然希望有某种"spread 捕获即时进 claimable"的语义），则需要工程师补一个不同的实现路径。在决策落地前，这三条测试保持 skip 不动。

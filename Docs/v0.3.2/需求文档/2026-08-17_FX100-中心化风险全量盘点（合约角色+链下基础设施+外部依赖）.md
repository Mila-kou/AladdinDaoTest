# FX100 中心化风险全量盘点（合约角色 + 链下基础设施 + 外部依赖）

**日期**: 2026-08-17

**状态**: 事实盘点完成，不含改造方案（决策/优先级留给产品/安全侧）

**受众**: 合约工程师、运营、安全

**范围**: 不限于合约和 keeper，覆盖整个体系——链上角色、链下运维、外部服务商依赖、L2 基础设施

**关联文档**: [docs/analysis/TEST_REVIEW_FINDINGS.md 问题 12](https://github.com/AladdinDAO/fx100-contracts/blob/docs/testing-standards/docs/analysis/TEST_REVIEW_FINDINGS.md)

## 一、结论先行

最严重的发现不是任何单一角色，而是一个**组合事实**：当前 Base Sepolia 共享测试环境里，几乎所有管理角色（`CONFIG_KEEPER`/`LIMITED_CONFIG_KEEPER`/`MARKET_KEEPER`/`ORDER_KEEPER`/`LIQUIDATION_KEEPER`/`ADL_KEEPER`/`FEE_KEEPER`）**默认全部收敛到同一个地址**（部署脚本 `resolveRoleAddress()` 的 fallback 逻辑：未显式配置就用 `bootstrapAdmin`），链上实测这个地址（`0xf82CF35C5c0019861c2cDC65041C8Ac32970D403`）是**一个没有字节码的裸 EOA**（不是多签、不是时间锁），而这个**同一个地址还是 `DataStore`/`LPVault`/`ProtocolTreasury`/`InsuranceTreasury` 这些核心合约的 `TransparentUpgradeableProxy` admin**——意味着一把私钥丢失或泄露，攻击者不仅能拿到几乎全部业务权限，还能直接换掉核心合约的实现代码，做任何事。这是当前**测试网**的配置现状，本文档不判断上线时是否会/应该改变，但这是必须在上线前明确核实并改变的一条。

以下按风险严重程度分组列出全部发现的中心化点。

---

## 二、能直接动用户/协议资金的

### 2.1 `ProtocolTreasury.multicall` 完全绕过 `batchTransfer` 白名单（链上代码事实）

`src/fee-distribute/ProtocolTreasury.sol:52-57`：

```solidity
function multicall(address[] calldata targets, bytes[] calldata data) external onlyRole(MULTICALL_ROLE) {
    for (uint256 i = 0; i < targets.length; i++) {
        (bool success,) = targets[i].call(data[i]);
        if (!success) revert ErrorMulticallFailed();
    }
}
```

`targets`/`data` 完全任意——`batchTransfer`（同文件 :63-71）虽然对 `receivers[]` 做了 `TOKEN_RECEIVER_ROLE` 白名单校验，但持有 `MULTICALL_ROLE` 的地址可以直接构造 `token.transfer(任意地址, 全部余额)` 的 calldata 走 `multicall` 执行，白名单校验对这条路径**形同虚设**。`ProtocolTreasury`/`InsuranceTreasury` 是同一份合约部署两次，两边都受此影响。

`ignition/modules/Fx100Fee.ts:54-58`：`TREASURY_MULTICALL_ROLE` 和 `TREASURY_BATCH_TRANSFER_ROLE` 授予**同一个** `feeKeeper` 地址——单一地址即可无视白名单转走金库全部资产。`feeKeeper` 若未显式配置，同样 fallback 到 `bootstrapAdmin`。

`docs/superpowers/specs/2026-08-13-treasury-cross-chain-bridge-design.md`（本次刚设计、尚未实现的跨链桥）明确保留这条"白名单+multicall"人工兜底路径不移除——这个风险会原样带入新设计，不会因为跨链桥上线而消失。

### 2.2 `RevenuePool.claim()` / `FeeHandler.withdrawFees()`（代码推断，未逐一链上核实持有者）

- `RevenuePool.claim()` 只有 `staker` 地址能调——需要单独核实这个地址当前配置成谁。
- `FeeHandler.withdrawFees` 受 `onlyFeeKeeper`——同一个 `feeKeeper`/`bootstrapAdmin` 收敛问题。

### 2.3 优惠券账户 / 跨链桥（设计中，尚未实现，标注供上线前一并评审）

- 优惠券账户设计文档明确"沿用本仓库现有的 `CONTROLLER`/admin role 校验模式"，未定义独立角色——意味着它复用的正是上面这套已经高度收敛的权限体系，不是新增了一个更细粒度的授权。
- 跨链桥新增 `BRIDGE_OPERATOR_ROLE`，可触发 `bridgeProfitToMainnet` 从金库拉资金并发起跨链销毁；协调层合约还会被授予 `ProtocolTreasury` 上现有的 `BATCH_TRANSFER_ROLE`+`TOKEN_RECEIVER_ROLE`。

## 三、能升级合约、改变协议一切行为的（比任何单一角色都严重）

### 3.1 核心合约走 Transparent Proxy，admin 是同一个裸 EOA（链上+代码事实）

`ignition/modules/Fx100Base.ts:32-35`、`Fx100Fee.ts:26-42`：`DataStore`、`LPVault`、`ProtocolTreasury`、`InsuranceTreasury` 均通过 OpenZeppelin `TransparentUpgradeableProxy` 部署，**proxy admin 全部是 `bootstrapAdmin`**。链上实测该地址 `cast code` 返回空字节码——是纯 EOA，不是多签/时间锁合约。

一个地址如果同时是这些合约的 proxy admin，**理论上可以随时把实现合约换成任意恶意代码**，不需要通过任何业务角色的权限校验——这是能想到的最高权限单点，其严重性覆盖了本文档列出的所有其它风险点（拿到这把钥匙，其它角色怎么设计都不重要了）。

### 3.2 `TIMELOCK_ADMIN` 是一个"挂了名字但没接线"的死角色（代码事实）

`src/access-control/AccessStoreProxy.sol` 定义了 `onlyTimelockAdmin` 修饰符和对应角色，`ignition/modules/Fx100Role.ts` 也确实 grant 了这个角色——但**全仓库搜索确认没有任何函数实际使用 `onlyTimelockAdmin` 这个修饰符**，只有定义那一行命中。仓库里也没有独立的 `TimelockController` 合约。也就是说，这个角色名字暗示"有时间锁延迟保护"，但实际上**不提供任何实质防护**，容易让人误以为关键操作已经有时间锁兜底，实际没有。

## 四、能改变交易执行结果的

### 4.1 CONTROLLER 角色本身（链上实测正常，非风险异常项）

链上实测 `getRoleMemberCount(CONTROLLER)` = 16，与部署脚本预期的 15 个核心合约 + `bootstrapAdmin` 完全吻合，**没有发现未记录的额外持有者**。这一项本身"按设计运作"，风险归结到 §3.1（谁能升级这些持有 CONTROLLER 的合约）。

### 4.2 订单执行/清算/ADL 三个角色目前无职责分离（代码事实，问题 11 已详细展开）

`ORDER_KEEPER`/`LIQUIDATION_KEEPER`/`ADL_KEEPER`/`FROZEN_ORDER_KEEPER` 默认全部 fallback 到 `bootstrapAdmin` 同一 EOA——同一个人可以执行订单、强制清算、触发 ADL，没有职责分离设计（即便未来分开配置到不同地址，代码层面也没有强制"这三个角色必须是不同实体"的约束）。链上（Base Sepolia）实测持有者数量：`ORDER_KEEPER` 13、`LIQUIDATION_KEEPER` 4、`ADL_KEEPER` 3——数量上有冗余迹象，但部署脚本本身按单地址设计，链上这些数字是历次部署累积授权形成的，无法区分"真正在跑的 keeper 机器人"和"忘记撤权的历史遗留"。

### 4.3 Oracle 价格提交权限（简要，未深挖）

`Oracle.setPrices` 的调用方就是执行订单/清算的 keeper 自己在传签名价格数据——不构成独立的额外中心化点，风险已归并在 §4.2。

## 五、影响可用性但不直接偷钱的

### 5.1 recorded-price keeper：全局连锁单点故障（仓库文档已有记录）

`docs/superpowers/specs/2026-08-01-recorded-price-keeper.md` 描述的场景：`latestRecordedPrices[token]` 只作为交易副作用被动刷新，某个冷门资产超过 24 小时无交易就会导致 `Oracle.getSecondaryPrice` 对该 token 硬 revert；而读取路径是**遍历全部市场**的，20 个市场里只要 1 个过期，全局调用直接 revert。影响范围：LP 提款 revert、ADL 状态无法更新、ADL 执行受阻（均为 🔴 级）、前端可用流动性显示异常/无法开仓（🟡 级）。这是一个**依赖独立定时 job 持续刷新、job 一旦停摆就连锁拖垮全局功能**的架构性单点，跟 keeper 执行订单是两个不同的单点故障源，需要分别有应急预案（问题 11 的方案目前只覆盖"用户关仓/清算"，不覆盖这一个）。

### 5.2 Keeper 运维：单机部署 + 私钥明文环境变量（仓库代码事实）

`fx100-apps/apps/keeper` 用单个 systemd 模板单元（`fx100-keeper@.service`）部署，靠实例名区分 order/adl/liquidation/relay 等角色 worker——**单机部署，没有看到容器编排、多实例、多区域冗余的痕迹**。私钥通过明文环境变量读取（`keeper.env`，按角色拆分成 `ORDER_KEEPER_PRIVATE_KEY`/`ADL_KEEPER_PRIVATE_KEY` 等，也支持逗号分隔的多 key 池），生产环境文件路径 `/etc/fx100-keeper/keeper.env`，权限 `root:fx100keeper 0640`——**没有找到 KMS/HSM 之类托管密钥服务的集成痕迹**，是裸文件形式的密钥管理。这台机器本身就是一个未在链上体现、但实际影响巨大的单点（机器宕机=所有 keeper 角色同时失效；机器被入侵=所有 keeper 私钥一次性泄露）。

### 5.3 Chainlink Data Streams / Pyth：外部服务商依赖（行业常识 + 文档核实）

两者都是第三方专业数据服务商运营的基础设施，不是 FX100 自己的系统——FX100 对它们的可用性、运维节奏、商业决策没有控制权。已核实 `docs/analysis/oracle/oracle_inventory.md` 目前讨论的是"数据源覆盖度/交叉校验架构约束"这类风险，**没有专门讨论"服务商本身停摆/被监管勒令下架"这类更基础的依赖风险**——这是一个记录上的空白，不是说这个风险不存在。

### 5.4 RPC 依赖（仓库文档事实）

各 `.env.example` 样例里的 RPC 配置以公共端点为主（`llamarpc.com`、Base 官方 `sepolia.base.org`）和 Tenderly fork 测试端点，**没有在样例文件里看到 Alchemy/Infura/QuickNode 等付费商用 RPC 的配置痕迹**——真实生产环境用的 RPC 提供商信息不在这些样例里（可能在未提交的真实环境变量中，本次查不到）。如果前端/keeper 生产环境确实只依赖单一公共 RPC，这个 RPC 服务出问题会直接影响可用性。

### 5.5 Base L2 Sequencer 中心化（行业常识，非 FX100 自身设计）

Base 是 Coinbase 运营的 OP-Stack Layer2，目前排序器（Sequencer）由 Coinbase 单方运营，没有去中心化机制（OP-Stack 设计了 force-include 机制作为兜底，但存在延迟）。这是选择部署在 Base 上就继承的系统性风险，跟 FX100 自己的合约/运维设计无关，但既然要梳理"整个体系"，这一条也是真实存在的依赖。

## 六、已知且已经主动决策接受的信任集中（不是遗漏，是权衡后的选择）

### 6.1 USDC 硬编码为 $1，不再做 oracle 校验

`docs/analysis/oracle/summary_usdc_oracle_single_point_of_failure.md`：核心结论是不修补从未真正生效过的"2% Chainlink vs Pyth 交叉校验"，而是在 `Oracle.sol` 价格入口把 USDC 硬编码为常量 $1，让 USDC 彻底退出 oracle 风险面——因为 FX100 所有市场共享同一个 vault、USDC 是唯一抵押品，这本身也是一种"信任集中"（完全信任 USDC 这个稳定币不脱锚），但这是问题 1 里已经讨论过、主动决策接受的风险，不是本次盘点的新发现，收录进来是为了让"整个体系的信任集中点"清单完整。

## 八、未覆盖 / 需要进一步确认的点

- 链上 13/4/3 个 keeper 地址里，哪些是真正在跑的机器人、哪些是历史遗留未撤权——需要运维方核对台账，代码/链上都无法区分。
- Keeper 是否有异地灾备/多可用区——本次按调研范围要求未深挖，仅凭单个 systemd service 文件推断为单机部署。
- 真实生产环境 RPC 提供商身份——样例文件里查不到，可能在未提交的真实环境变量中。
- `RevenuePool.staker`、`FeeHandler` 的 `feeKeeper` 当前具体配置的地址——本次未逐一核实，只确认了角色机制本身。

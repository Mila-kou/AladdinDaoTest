# 测试用例完成代码化

## 1. 目标

FX100 后续会持续增加复杂交易组合，但核心操作相对稳定：开仓、Limit 下单与触发、添加或修改 TP/SL、部分平仓、全平、价格调整、时间推进、清算和 ADL。

测试框架的下一阶段目标不是继续按“一个场景一个大型 Runner”复制代码，而是把这些稳定操作建设成可复用动作，通过声明操作顺序快速组合新用例，并由框架统一完成环境校验、交易执行、状态采集、独立预期计算、断言、证据和清理。

期望新增组合用例时，主要编写：

1. 使用哪个环境、市场和 Trader；
2. 按什么顺序执行哪些动作；
3. 每一步需要哪些默认核对和场景特定断言；
4. 是否快照回滚或保留链上证据。

## 2. 当前架构与能力

当前 TestCode 已经是一个可运行的测试平台雏形，而不是单纯的 Playwright UI 脚本集合：

```text
测试设计与版本矩阵
        ↓
Spec 编排层（Playwright）
        ↓
Scenario Runner（业务流程）
        ↓
Driver / Legacy Adapter
        ↓
RPC / 合约 / Oracle / Keeper / 前端
        ↓
原始 Evidence
        ↓
Reconciliation 独立复算
        ↓
Reporter / Dashboard / Evidence Archive
```

### 2.1 用例体系

目前并存两类用例：

- `SCN-xxx`：80 条用户级 E2E 场景，回答“用户路径是否成立”；
- `CT/XT/FT-*`：版本级功能原子，回答“合约层、跨层和前端层分别验证了什么”。

当前自动化规模：

- 18 个 `.spec.ts` 文件；
- 33 个测试声明；
- 15 个 SCN 场景；
- 18 个 CT/XT/FT 功能用例；
- SCN 自动化覆盖为 15/80，约 18.75%。

Playwright 配置了五个 project，因此 `test:list` 会把 33 个测试声明展开成 165 个实例。165 不是独立业务用例数，后续统计应以唯一 Case ID 为准。

### 2.2 已具备的优势

- 五类执行环境：`dev-readonly`、`tx-fork`、`oracle-fork`、`time-fork`、`base-sepolia`；
- 真实 Trader/Keeper 签名和真实协议合约执行；
- Fork 快照、Oracle 调价、时间推进、Inline/Service Keeper 能力；
- CURRENT、环境绑定、manifest、chainId 和 bytecode 的运行前闸门；
- 每用例独立 Trader、Mock Market Bundle 和环境能力约束；
- Before/After、交易、事件、账本和公式输入的结构化 Evidence；
- BigInt 独立计算，区分计算复算、事件对照、守恒、恒等式和缺数据；
- Playwright Reporter、HTML 看板和 Evidence Archive 的完整证据链。

### 2.3 当前主要问题

1. Spec 层重复环境检查、Trader、快照、Evidence 写入和断言逻辑；
2. Scenario Runner 同时承担流程、驱动、采集、断言和证据组装，逐渐成为大型模块；
3. Expected 公式分散在 Runner、`reconciliation` 和 `execution-evidence.ts` 中；
4. TypeScript Driver 与 `tools/fx100-legacy` 动态加载实现并存；
5. SCN 与 CT/XT/FT 只有结果兼容，缺少机器可读的双向覆盖映射；
6. 前端页面目前主要通过可选 hook 接入，尚未形成稳定的 Page/Flow/Assertion 层；
7. 环境变量控制面较大，签名、环境、Trader、持久化和 UI 开关存在组合复杂度。

## 3. 目标架构

```text
Case Registry
├── SCN 用户场景
├── CT/XT/FT 功能原子
└── requirement / action / environment / evidencePolicy
             ↓
Scenario DSL / Case Definition
             ↓
Unified Test Harness
├── runtime guard
├── capability validation
├── trader fixture
├── snapshot transaction
└── evidence writer
             ↓
Reusable Actions / Flows
├── Market / Limit / Stop
├── TP/SL / Position Management
├── Price / Time
└── Liquidation / ADL
             ↓
Drivers
├── Protocol / Fork / Oracle / Keeper
└── Wallet / UI
             ↓
Collectors → Independent Models → Reconcilers
             ↓
Verdicts → Reporter → Dashboard → Archive
```

核心原则：

- 场景负责声明“做什么、按什么顺序做”；
- Action/Flow 负责“怎样执行”；
- Driver 负责和链、合约、Keeper、Oracle、钱包、页面交互；
- Collector 只采集原始事实；
- Model 独立计算 Expected，不能复制生产 SDK 答案；
- Reconciler 比较 Expected 与 Actual；
- Reporter 只消费结构化结果，不参与业务计算。

### 3.1 并行开发边界

交易执行与数据核对可以并行开发，两边通过版本化 Evidence 契约衔接：

| 工作面 | 责任范围 | 不应修改 |
|---|---|---|
| 交易执行 | Spec、Scenario DSL、Action / Flow、Driver、Runner、钱包与 Keeper 调用 | 公式、核对状态聚合、看板业务判定 |
| 数据核对 | Evidence Schema、Collector 输出规范、Formula Registry、Check Pack、Check Engine、Verdict 聚合、报告数据适配 | 发送交易、修改 Oracle、推进时间、执行 Keeper 的实现 |

共享边界只有 `EvidenceEnvelope` / `ActionEvidence`：执行侧产生原始事实，核对侧不依赖 Runner 预存的 `passed` / `sum`。Schema 变更必须升级 `schemaVersion`，并保留旧证据 Adapter，禁止两边同时修改同一 Runner 文件。

### 3.2 证据能力分发，不按用例编号分发

核对引擎不应继续使用 `SCN-009 -> deriveScn009Evidence` 这类编号查找表。当前生产目标为 Evidence V3；V2 已冻结，只作为历史附件与旧 `runMarketFlow` 桥接格式，由显式 Adapter 正规化到 V3。每份 Evidence 声明动作形状与能力：

```ts
interface EvidenceEnvelope {
  schemaVersion: 3;
  caseId: string;
  variantId: string;
  executionId: string;
  flowType: 'read-only' | 'create-only' | 'create-execute' | 'create-cancel' | 'roundtrip' | 'multi-phase';
  capabilities: EvidenceCapability[];
  environment: EnvironmentIdentity;
  actions: ActionEvidence[];
}

type EvidenceCapability =
  | 'transaction' | 'order-events' | 'position-state' | 'ledger' | 'claimable-ledger'
  | 'fee' | 'funding' | 'oracle' | 'parameters'
  | 'keeper' | 'indexer' | 'frontend';
```

核对引擎按 `flowType + capabilities + CheckPlan` 选择核对包，但不把 Evidence 的自述当成授权：Envelope capability 必须覆盖各 Action capability，交易、事件、参数、Oracle、前端等已出现事实必须与 capability 一致；`flowType` 还要满足最小动作形状。最终 PASS 必须绑定代码侧可信 `CheckPlan`，未绑定计划、空核对行或只传入外部 PASS 行最多只能得到完整性缺口，不能 PASS。声明应有但缺失的能力记 `NOT_VERIFIED`；对当前动作不适用的能力记 `NOT_APPLICABLE`。

## 4. 场景 DSL

后续组合用例应接近以下形式（`SCN-101` / `SCN-102` 仅为示意编号：SCN 目录固定 80 条不再增号，真实用例必须使用矩阵中已登记的 CT/XT/FT 编号或既有 SCN，见 CLAUDE.md 测试标准第 2 条）：

```ts
const oracleForkEnvironment = {
  targetProject: 'oracle-fork',
  marketMode: 'mock-market',
  oracleMode: 'mock-oracle',
  marketCompatibility: 'mock-only',
  timeMode: 'normal-block-time',
  signingMode: 'trader-keeper-private-key',
  mockResourceAlias: 'default-mock',
  environmentSetup: '独享 oracle-fork；初始化 default-mock；执行后恢复 Oracle 并回滚快照',
} satisfies TestEnvironmentDefinition;

scenario('SCN-101', {
  environment: oracleForkEnvironment,
  actors: ['traderA'],
  isolation: 'snapshot',
})
  .openMarket({
    actor: 'traderA',
    side: 'long',
    order: 'market',
    collateral: usdc(100),
    size: usd(500),
  })
  .addTpSl({
    actor: 'traderA',
    takeProfit: price(110),
    stopLoss: price(95),
  })
  .movePrice(price(110.01))
  .executeTriggeredOrders()
  .expectPosition('traderA', { status: 'closed', reason: 'take-profit' })
  .expectLedgerBalanced()
  .expectNoPendingOrders();
```

复杂组合也只改变动作顺序：

```ts
scenario('SCN-102', {
  environment: oracleForkEnvironment,
  actors: ['longTrader', 'shortTrader'],
})
  .openMarket({ actor: 'longTrader', side: 'long', size: usd(1000) })
  .placeLimit({ actor: 'shortTrader', side: 'short', trigger: price(102), saveAs: ref.order('short-entry') })
  .movePrice(price(102))
  .executeTriggeredOrders()
  .increase({ actor: 'longTrader', collateral: usdc(20), size: usd(200) })
  .partialClose({ actor: 'longTrader', percent: 50 })
  .movePrice(price(80))
  .liquidate({ actor: 'longTrader' })
  .adl({ actor: 'shortTrader', size: usd(100) })
  .expectMarketAccounting()
  .expectLedgerBalanced();
```

场景代码不直接保存 `orderKey`、`positionKey` 或 `txHash`，而是通过逻辑引用和 Scenario Context 管理：

```ts
const position = ref.position('main');
const tpOrder = ref.order('take-profit');

scenario
  .openMarket({ savePositionAs: position, ... })
  .addTpSl({ position, tpSaveAs: tpOrder, ... })
  .movePriceToTrigger(tpOrder, { beyondBy: raw(1) })
  .expectOrder(tpOrder, { status: 'executed' });
```

`openMarket` 是业务 Flow，必须显式展开为两个原子动作：

```ts
.submitMarketIncrease({ saveAs: ref.order('open'), ... }) // ORDER_PENDING
.executeOrder({ order: ref.order('open'), savePositionAs: position }) // POSITION_OPEN
```

`placeLimit` 只创建待执行订单，不能与“已建仓”语义共用同一 `open()` 名称。

## 5. 可复用动作

第一阶段建设以下稳定动作：

```ts
type TradeAction =
  | OpenPositionAction
  | PlaceLimitOrderAction
  | IncreasePositionAction
  | AddTpSlAction
  | UpdateTpSlAction
  | CancelOrderAction
  | PartialCloseAction
  | ClosePositionAction
  | MovePriceAction
  | AdvanceTimeAction
  | ExecuteOrderAction
  | LiquidateAction
  | AdlAction;
```

建议提供三层复用能力：

1. 原子动作：`openMarket`、`placeLimit`、`moveOracleRaw`、`executeOrder`；
2. 业务流程：`openWithTpSl`、`triggerTakeProfit`、`openAndLiquidate`、`openAndAdl`；
3. 参数矩阵：对方向、订单类型、退出方式和边界数据批量展开。

矩阵展开后的每组数据必须拥有独立可寻址身份、执行结果和 Evidence，不能只给矩阵总结论。身份分三层：

- `caseId`：业务规则或边界不同时独立；
- `variantId`：同一规则的方向、金额、市场等参数化样本；
- `executionId`：每次真实执行唯一。

## 6. 统一执行器

每种 Action 使用相同生命周期：

```ts
interface ActionExecutor<T extends TradeAction> {
  validate(context: ScenarioContext, action: T): void;
  execute(context: ScenarioContext, action: T): Promise<ActionExecution>;
}

interface ActionDefinition<T extends TradeAction> {
  type: T['type'];
  defaultCheckPacks: CheckPackId[];
}

interface CheckEngine {
  reconcile(input: {
    action: TradeAction;
    execution: ActionExecution;
    evidence: ActionEvidence;
    packs: CheckPackId[];
  }): Promise<CheckRecord[]>;
}
```

统一执行顺序：

1. 校验环境和动作能力；
2. 获取提交前观测快照（非最终权威 Before）；
3. 执行交易、调价或时间操作；
4. 等待明确事件或链上状态，不使用固定 sleep，并首先判别 `Executed / Cancelled / Frozen`；
5. 取得 receipt 后钉定执行块；执行类动作的权威 `Before = executionBlock - 1`、`After = executionBlock`；
6. 检查提交到执行窗口是否受第三方交易污染；
7. 记录订单输入、交易、事件、参数、Oracle 与原始快照；
8. Check Engine 使用独立模型计算 Expected 并生成 CheckRecord；
9. 更新 Scenario Context；
10. 场景结束时执行全流程守恒与清理。

### 6.1 动作目的

每个动作必须声明 `purpose: 'setup' | 'primary' | 'support' | 'cleanup'`。主动作与清理动作分开聚合；cleanup 失败不得掩盖 primary 结论，但必须标记运行需人工处理。

## 7. 状态机与构建期校验

组合场景必须受状态机约束：

```text
NONE
 ├─ open/limit → ORDER_PENDING
 │                 ├─ execute → POSITION_OPEN
 │                 └─ cancel  → NONE
 │
POSITION_OPEN
 ├─ increase       → POSITION_OPEN
 ├─ addTpSl        → POSITION_OPEN + CONDITIONAL_ORDERS
 ├─ partialClose   → POSITION_OPEN
 ├─ close          → CLOSED
 ├─ liquidate      → LIQUIDATED
 └─ adl            → POSITION_OPEN / CLOSED
```

在运行前拒绝非法组合：

- 无仓位时平仓或添加仓位级 TP/SL；
- Market 单配置 Limit trigger；
- Limit 单缺少触发价；
- 价格尚未满足时声明订单应成交；
- 未达到可清算状态就执行清算；
- 未满足市场条件就执行 ADL；
- 非 `time-fork` 使用时间推进；
- `mock-only` 场景切换到普通部署市场。

落地语义如下：

- `src/domain/test-environment.ts` 是上述八个环境字段、枚举和兼容性规则的唯一类型入口；Scenario DSL 与看板用例登记共同引用它；
- `build()` 先对整条动作序列做静态演练，失败时不会调用任何 Executor；Harness 再把计划环境与本次实际解析的 Market、Oracle、时间、签名和资源别名逐项核对，并把实际选择放入 `ScenarioContext.resolvedEnvironment` 供 Executor 使用；
- `LimitIncrease` 的价格条件与合约 `BaseOrderUtils.validateOrderPrices` 一致：long 为 `price.max <= trigger`，short 为 `price.min >= trigger`；“执行过 movePrice”本身不代表已触发；
- 清算和 ADL 不能用任意一次调价代替条件判断。`movePrice.assess[]` 声明要评估的逻辑仓位，Driver/独立模型必须把 `SATISFIED / NOT_SATISFIED / NOT_CHECKED`、来源和区块写入该 Action 的 `parameters[]`（名称为 `precondition.<liquidation|adl>.position:<ref>`）；只有带来源的 `SATISFIED` 才允许下一动作调用清算或 ADL Executor；
- 普通 Market 全平不要求预先调价；价格条件只约束 Limit/Stop、清算和 ADL；
- 时间推进使用独立 `advanceTime({ seconds })` Action，只有 `time-fork + controllable-time` 可构建。

## 8. 价格和时间是一等动作

价格变化必须显式出现在场景时间线中：

```ts
.movePrice({
  index: { min: price(99.9), max: price(100.1) },
  collateral: { min: price(0.999), max: price(1.001) },
  timestamp: 'next-block',
})
```

同时提供业务语义封装：

```ts
.movePriceToTrigger(tpOrder, { beyondBy: raw(1) })
.movePriceToLiquidation(position, { beyondBy: raw(1) })
.movePriceByPercent(-20)
.advanceTime(hours(8))
```

所有高层动作最终都转换为明确的 Oracle `min/max/timestamp` 或区块时间，并把转换结果写入 Evidence。

## 9. 动作级默认核对

基础断言由动作自动携带，场景作者只补充业务特有断言。

| 动作 | 默认核对 |
|---|---|
| Market 开仓 | 订单状态、仓位、方向、size、collateral、执行价、fee、OI、余额 |
| Limit 触发 | 触发条件、执行价格、acceptablePrice、订单离队 |
| 添加/修改 TP/SL | 关联仓位、方向、触发价、size、订单类型 |
| 部分平仓 | size/OI 减少、PnL、fee、剩余仓位、TP/SL 同步 |
| 全平 | 仓位清零、关联挂单、资金返还、PnL、OI |
| 调价 | Oracle min/max/timestamp 和执行区块价格 |
| 清算 | 可清算模型、清算事件、仓位移除、费用和损失分配 |
| ADL | ADL 条件、削减规模、PnL、市场、保险和资金账本 |

所有 PASS 必须有独立 Expected 来源。缺少必要输入时必须是 `NOT_VERIFIED`，不能从 Actual 反推 Expected，也不能用事件字段证明同一个事件字段正确。

### 9.1 Check Plan 与 Check Pack

DSL 中的 `ScenarioCheckPlan` 只声明产品希望启用哪些默认核对，不在 Runner 里复制公式：

```ts
interface CheckPlan {
  defaultPacks: CheckPackId[];
  additionalPacks?: CheckPackId[];
  disabledChecks?: Array<{ checkId: string; reason: string }>;
}
```

进入核对引擎前，它必须解析成带版本的可信 `CheckPlan`。该计划不仅列 CheckPack，还固定 flow、Action 顺序/用途/允许结果、必需 capability，以及每个 Action 的交易分组：

```ts
interface CheckPlan {
  id: string;
  version: string;
  flowType: FlowType;
  actions: Array<{
    type: string;
    purpose: ActionPurpose;
    outcomes: ActionOutcome[];
    requiredCapabilities?: EvidenceCapability[];
    transactions: {
      rules: Array<{
        id: string;
        roles: TransactionRole[];
        min: number;
        max: number;
        anchor: 'order-submission' | 'terminal-execution' | 'oracle-ref';
        actors?: Address[];
        targets?: Address[];
      }>;
    };
  }>;
  packs: CheckPack[];
}
```

每笔 `TransactionRef` 必须唯一落入一条规则；超出基数、角色无规则、锚点不成立或同时命中多条规则均为无效证据。Market roundtrip 的提交腿固定为唯一 trader 交易，执行腿固定为唯一 keeper/service 终态交易。可选 Oracle support 交易必须同时满足唯一 `OracleRef.transactionHash + blockNumber` 双向锚点，以及由可信部署配置注入的 actor/to 白名单；白名单绝不能从 Evidence 自己反推。默认 `market-open.roundtrip@2` 不允许未配置的 support 交易。核对聚合会在内部重新运行计划并精确比较调用方传入的 CheckRecord，避免用同 packId 的伪 PASS 行冒充计划输出。

禁用默认核对必须有理由，不允许静默跳过。金额为 0 通常仍应生成 `Actual=0 / Expected=0` 的核对行，而不是因“没发生”整组消失。

`XT-MKT-OPEN-001` 的核对计划为：

```ts
checkPlan: {
  defaultPacks: [
    'order.market-increase-created',
    'order.executed',
    'position.increased',
    'pricing.increase',
    'fee.position',
    'market.open-interest',
    'ledger.transaction',
    'order.no-attached-protection',
  ],
  additionalPacks: [
    'cleanup.full-close',
    'ledger.whole-flow',
  ],
}
```

### 9.2 CheckRecord 唯一机器契约

```ts
interface CheckRecord {
  id: string;
  packId: string;
  actionId: string;
  purpose: 'setup' | 'primary' | 'support' | 'cleanup' | 'whole-flow';
  subject: 'chain-state' | 'chain-event' | 'keeper' | 'indexer' | 'frontend';
  comparison:
    | 'formula-vs-state' | 'formula-vs-event' | 'event-vs-state'
    | 'state-vs-indexer' | 'indexer-vs-ui' | 'formula-vs-ui'
    | 'invariant' | 'presence';
  actual: CheckValue;
  expected: CheckValue;
  before?: CheckValue;
  after?: CheckValue;
  actualDelta?: CheckValue;
  expectedDelta?: CheckValue;
  expectedAfter?: CheckValue;
  sources: SourceRef[];
  formula?: {
    id: string;
    version: string;
    expanded: string;
    inputs: FormulaInput[];
    rounding?: string;
  };
  verification: 'FULL_RECOMPUTE' | 'EVENT_ANCHORED' | 'IDENTITY' | 'PRESENCE' | 'NOT_VERIFIED';
  severity: 'blocking' | 'warning';
  verdict: 'PASS' | 'FAIL' | 'NOT_VERIFIED' | 'NOT_APPLICABLE';
  difference?: string;
  tolerance?: string;
}
```

TypeScript + Zod Schema 是唯一机器真身；`fx100-verify-handbook` 记录领域公式和陷阱，`fx100-testcode-ops` 记录工程运行纪律，两者都只引用 Schema，不复制一份字段定义。

`FULL_RECOMPUTE` 且带 `formula` 的记录必须至少包含一个可追溯 `FormulaInput`；每项都具备 `name / value / source`。Schema 会把空 `formula.inputs` 当成框架错误，而不是让该行继续输出 PASS。若 Expected 的关键输入来自同一个被核事件，该行只能是 `EVENT_ANCHORED`；只有参数、Oracle 或状态等独立原始来源齐备后才能升级为 `FULL_RECOMPUTE`。

### 9.3 分层结论与聚合

“被测对象”与“比较方式”是两个维度，不把“交叉一致”伪装成独立数据层。顶层分别聚合：

```ts
interface LayerVerdicts {
  chainState: LayerVerdict;
  chainEvent: LayerVerdict;
  keeper: LayerVerdict;
  indexer: LayerVerdict;
  frontend: LayerVerdict;
  evidenceIntegrity: LayerVerdict;
  cleanup: LayerVerdict;
}
```

新生成的报告使用 `ReconciliationReport schemaVersion=2`，强制保存 `evidenceDigest=sha256(canonical Evidence V3)`、`checkPlan.id/version`、`checkPlanDigest` 和必填的 `integrity.status / invalid / reasons[]`。`checkPlanDigest` 覆盖 flow、Action 契约、交易规则/可信地址以及 CheckPack id/version，避免参数化白名单复用同一标签而无法区分。动态/部署特定计划必须使用独立 id/version 登记到可信计划注册表。摘要是公开身份而不是签名：渲染前由 `reconciliation` 层用注册的可执行计划对 canonical Evidence 重放，并对比整份 canonical Report；仅复制正确 digest 但自造 PASS 行仍为 `INVALID_EVIDENCE`。Reporter 只消费该验证结果，不实现第二套公式。同一信任门还会重新正规化 Evidence、重算证据 digest，并精确核对 caseId、variantId、executionId，environment.name/chainId/deploymentId/release，Fork provider/displayName，以及 Mock/deployed market 的 mode/resourceAlias/marketIndex/可选 marketAddress；`networkId` 和当前语义不统一的 `forkBlockNumber` 不伪称已绑定。任何旧 V1 未绑定报告、摘要不一致、跨环境附件或 Report 内部 status/layer/check 自相矛盾都显示 `INVALID_EVIDENCE`，不得回退到 runner 断言洗成 PASS。

聚合规则：

- blocking Check `FAIL` -> 对应层 `FAIL`；
- 声明必须但缺数据的 blocking Check `NOT_VERIFIED` -> 对应层 `INCOMPLETE`；
- 本轮未要求执行的层 -> `NOT_RUN`，不记 FAIL；
- 层间比较缺任一侧 -> `NOT_APPLICABLE`；
- `NOT_RUN` 与 `NOT_APPLICABLE` 不参与总体降级；
- 任一必需层 `INCOMPLETE` -> 总体 `PASS_WITH_GAPS`；
- cleanup 与 primary 分开聚合；
- 总体状态使用 `PASS / PASS_WITH_GAPS / FAIL / BLOCKED / INVALID_EVIDENCE`。

Keeper 还需另行输出发现延迟、提交延迟、成功率、漏单、重复执行和 Oracle 新鲜度等 `ServiceMetrics`；这些是服务质量指标，不全部塞入单笔交易 CheckRecord。

### 9.4 交易链接与实际数据

交易链接和 Actual 是一等证据。每个链上动作的报告页必须直接展示：

- txHash、可验证的 Explorer URL、blockNumber、actor、orderKey、gasUsed；
- 钉块 Before、Actual After、Actual Delta；
- Expected Delta、Expected After、Difference 和 tolerance；
- 公式展开值、参数与数据来源；
- 原始 Evidence 文件入口。

Evidence 应保存执行时的 Explorer 身份与链接，不用当前环境的 fork 猜测历史交易链接。已删除或无法确认身份的 fork 只展示 hash，不生成可能指向新 fork 的错误 URL。

```ts
interface TransactionRef {
  txHash: Hex;
  blockNumber: DecimalString;
  blockHash?: Hex;
  actor: Address;
  role: 'trader' | 'keeper' | 'admin' | 'oracle' | 'service';
  orderKey?: Hex;
  gasUsed: DecimalString;
  status: 'SUCCESS' | 'REVERTED' | 'UNKNOWN';
  receipt?: {
    transactionHash: Hex;
    blockNumber: DecimalString;
    blockHash?: Hex;
    status: 'SUCCESS' | 'REVERTED' | 'UNKNOWN';
    gasUsed: DecimalString;
  };
  explorer?: {
    provider: 'basescan' | 'tenderly-vnet';
    networkId?: string;
    transactionUrl: string;
  };
}

// eth_getBlockByNumber(..., true) 的扫描事实不是 Action 交易，未知第三方不伪造 role。
interface ScannedTransactionRef {
  txHash: Hex;
  blockNumber: DecimalString;
  blockHash?: Hex;
  transactionIndex?: DecimalString;
  actor: Address;
  to?: Address;
  nonce?: DecimalString;
  transactionType?: string;
  role?: 'trader' | 'keeper' | 'admin' | 'oracle' | 'service';
}

interface ScannedBlockRef {
  blockNumber: DecimalString;
  blockHash: Hex;
  transactionHashes: Hex[];
}

type WindowContaminationEvidence = {
  status: 'NOT_CHECKED';
  fromBlock?: DecimalString;
  toBlock?: DecimalString;
  source?: EvidenceProvenanceRef;
  note?: string;
} | {
  status: 'CLEAN' | 'POLLUTED';
  fromBlock: DecimalString;
  toBlock: DecimalString;
  inspectedBlocks: ScannedBlockRef[];
  inspectedTransactions: ScannedTransactionRef[];
  // CLEAN 必须为 []；POLLUTED 必须非空。
  unexpectedTransactions: ScannedTransactionRef[];
  source: {
    source: 'block-scan' | 'execution-collector';
    path: string;
    blockNumber: DecimalString;
  };
  note?: string;
};
```

Evidence JSON 中所有链上整数使用十进制字符串，避免 BigInt 无法序列化以及跨语言读取时丢失精度；TypeScript 计算模型在核对入口再显式转为 `bigint`。

`evidenceIntegrity=PASS` 需要同时满足：Schema 有效且字段严格；transaction 与独立 receipt 的 hash、blockHash、block、status、gas、nonce 对应；同一 actor 的成功交易 nonce 按全局链上顺序严格递增；同一高度的 transaction/receipt/snapshot/扫描块只能有一个 blockHash；执行动作的 Before/After 为 N−1/N 且 After 对应唯一 Keeper/Service 交易块；执行 txHash、orderKey、结果事件以及此前唯一提交订单一致，已经 EXECUTED/CANCELLED 的 orderKey 不得再次消费；可信 CheckPlan 的 flow/Action/交易分组/capability 和全部 CheckPack 输出一致；污染窗口为 V3 `CLEAN`，逐块连续覆盖提交到执行的闭区间并截止执行块，`parentHash` 不得形成自环/未来环，`transactionIndex` 与区块顺序一致，`inspectedBlocks.transactionHashes` 与 `inspectedTransactions` 完整对应，包含提交/执行交易且没有未登记交易；多个 completed window 的重叠块必须完全一致，相邻窗口必须正确接链，存在未扫描链段则保留完整性缺口；Explorer 省略或其 provider、URL、txHash 可以相互验证。`NOT_CHECKED` 绝不能由“窗口两端快照相同”或一条 `source.path` 推断为 `CLEAN`。V2 的 `CLEAN/POLLUTED` 因缺逐块凭证，迁移时都以 V3 `NOT_CHECKED` 承载原声明；旧 CLEAN 只能记完整性缺口，旧 POLLUTED 仍保持 `INVALID_EVIDENCE`，不得被洗成可通过状态。

### 11.1 Playwright 前端证据与核对接缝

前端用例继续由 Playwright 执行，但 Playwright 的职责是操作页面并采集原始事实，不作为 Expected 和最终 Verdict 的权威来源。带 `frontend` capability 的 Action 可以在 Evidence V3 中提供可选 `frontend` 段；历史 V2 前端证据仍通过 Adapter 读取：

- 页面身份：`pageUrl / route / buildId / locale / walletAddress / chainId`；
- 页面观察：稳定业务字段名、DOM 展示文本、规范化值、单位、语义 locator、采集时间和截图路径；
- 钱包请求：`method / from / to / value / calldata`，以及按 ABI 解码后的 `functionName / decodedArgs`；
- 链上结果仍使用同一 Action 的 transaction、event 与 execution block 快照。

前端核对按以下链路拆分，任一段都可单独定位失败原因：

```text
Case Intent
   ↓ intent-vs-ui
页面输入、展示值与校验状态
   ↓ ui-vs-wallet-request
注入钱包收到的真实请求与解码参数
   ↓ wallet-request-vs-event / state-vs-ui
链上事件、状态、Indexer 与最终页面展示
```

RPC 合约用例不声明 `frontend` capability，前端层聚合为 `NOT_RUN`；声明了 capability 但缺少页面观察或钱包请求时为 `INCOMPLETE / NOT_VERIFIED`，不得继承合约层 PASS。页面格式化允许声明容差与单位换算，但原始文本和规范化值必须同时保留，以区分“链上值错误”和“前端格式化错误”。敏感信息（私钥、RPC 密钥、完整认证信息）不得进入 Evidence。

执行侧与核对侧的前端接缝固定如下：

1. Playwright Action 采集 `frontend.observations[]`，同时保存 `displayedText` 与规范化后的 `normalizedValue`；
2. 在点击确认前后截获注入钱包的真实 `walletRequests[]`，按 ABI 解码后保存函数名与参数；
3. 链上成交后仍使用同一个 Action 的 receipt、event 和钉块 snapshot，不另造“前端 Actual”；
4. 前端 Check Pack 只产生 `subject=frontend` 的 CheckRecord，可使用 `intent-vs-ui`、`ui-vs-wallet-request`、`wallet-request-vs-event`、`state-vs-ui`、`indexer-vs-ui` 等 comparison；
5. Reporter 走同一通用 CheckRecord 表格，不允许 Playwright 断言另起一套页面；
6. 未声明 `frontend` capability 为 NOT_RUN；已声明但 observation、wallet request 或对应核对行缺失为 INCOMPLETE/NOT_VERIFIED，绝不能继承 chain-state PASS。

5. 使新 Action 输出 Evidence V3，并同时通过 V2 兼容回放与 V3 契约测试。

### 阶段 C：提炼核心动作

1. 从 SCN-009 提炼 `openMarket`、`close` 和基础账本核对；
2. 从 SCN-010 提炼 `placeLimit`、`movePrice` 和 `executeTriggeredOrders`；
3. 从现有仓位管理场景提炼 `increase`、`partialClose`；
4. 补齐 `addTpSl`、`updateTpSl`、关联订单同步；
5. 接入 liquidation 和 ADL。

### 阶段 D：独立核对模型扩展

1. 将公式从 Runner 和 Reporter 迁入 `reconciliation`；
2. Runner 只产生动作输入和原始 Evidence；
3. 每个 TX 独立 Before/After/Expected/Actual；
4. 固定核对资金、仓位、Fee、Funding、PnL、OI、订单和守恒；
5. Reporter 只渲染 CheckRecord。

### 阶段 E：规模化组合

1. 增加 Market、Limit、TP、SL、部分平仓、全平、清算、ADL 的矩阵生成器；
2. 建立 SCN 与 CT/XT/FT 双向覆盖映射；
3. 把每个矩阵数据集生成成独立 Case ID；
4. 逐步迁移 `fx100-legacy` 到 TypeScript Driver；
5. 为状态机、Driver 和公式增加本地快速单测。

## 12. 完成标准

测试用例代码化框架达到以下状态，才视为“完成代码化基础建设”：

- 新组合场景主要由动作声明组成，不再复制交易执行代码；
- 新增普通组合用例控制在约 20～50 行；
- 每一步动作都有独立 Before/After、交易、事件、参数和 CheckRecord；
- 每个链上动作都有可验证的交易链接（不可用时只展示 hash）、block、actor、orderKey 和 gas；
- 页面直接显示钉块 Before、Actual After、Actual Delta、Expected Delta、Expected After 和 Difference；
- Market、Limit、TP/SL、关仓、价格调整、清算、ADL 可以任意合法组合；
- 非法操作顺序在执行前被状态机拒绝；
- 基础断言由动作自动附带，场景只写特有断言；
- Expected 只有一个独立模型入口；
- Check Pack 按动作形状和 Evidence capability 选择，不按用例编号查找派生器；
- primary、setup、support、cleanup 分开聚合，缺数据与不适用不得冒充 PASS；
- SCN、CT/XT/FT、代码、需求和证据可以双向追踪；
- 用例覆盖统计按唯一 Case ID 计算，参数样本和执行记录分别使用 variantId / executionId，不使用 Playwright project 展开数；
- Reporter 与 Dashboard 能按动作时间线展示链上状态、事件、Keeper、Indexer、前端、cleanup 和数据完整性结论。

## 13. 总结

当前系统在真实链上执行、环境隔离和证据审计方面已经具备良好基础。下一阶段重点应从“继续复制更多 Spec/Runner”转为建设 `Case Registry + Scenario DSL + Unified Harness + Reusable Actions + State Machine + Independent Reconciliation`。

完成这一层后，Market、Limit、TP/SL、部分平仓、全平、价格变化、清算和 ADL 都可以作为稳定积木组合；新增场景的主要工作将变成描述操作顺序和业务特定预期，而不是重新编写执行、取证和核对代码。

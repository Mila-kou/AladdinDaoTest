## 21. 全字段速查

> 本表是前 20 节的索引，不是独立结论。每行的「源码锚点」列给出 v0.3.2 唯一权威实现；与正文冲突时以源码为准，与本表冲突时说明正文尚未回写。
> 三个必须成对读的属性：**取整方向**、**选价侧（min / max / mid / secondary）**、**精度标度（1e30 USD / index token 原生精度 / 1e18 点差 / collateral 原生精度）**。表中每行都已标注，缺一即视为该行不可用于算期望值。
> 一条全局纪律：Oracle 价的量纲是「1e30 USD ÷ token 最小单位」，已把 token decimals 折进价里。因此 `USD ÷ price` 得到的是**该 token 的最小单位数**，不是 1e18 定点数；index token 不保证 18 位，凡涉及 token 数量与显示值互换处一律按该市场 index token decimals 取，**不得写死 `/1e18`**。

## 23. E2E 预期值计算顺序

> 顺序即语义：任何一步提前或延后都会算出不同的期望值。带 ⚠️ 的步骤是最容易漏的。

### 23.1 加仓（Market / Limit / Stop Increase）

1. 读取本笔执行所用的 Oracle `indexTokenPrice.{min,max}` 与 `collateralTokenPrice.{min,max}`（`MarketUtils::getMarketPrices`）。
2. **预解析**订单规模：`PositionUtils::getIncreaseOrderSize`。USD 模式得 `(sizeDeltaUsd, 预解析 sizeDeltaInTokens)`（Long `floor(/index.max)`、Short `ceil(/index.min)`）；Token 模式得 `(预解析 sizeDeltaUsd, sizeDeltaInTokens)`（Long × `index.max`、Short × `index.min`）。**每种模式里只有带「预解析」标记的那一个是中间量，另一个就是最终值**：USD 模式的 `sizeDeltaUsd` 与 Token 模式的 `sizeDeltaInTokens` 全程不变。
3. 若 `sizeDeltaUsd == 0`：早退，`executionPrice = pickPrice(isLong)`，`dynamicSpread = 0`，`balanceWasImproved = false`，后续步骤全部跳过。
4. ⚠️ **点差三分量必须按源码顺序求值**（`PositionPricingUtils::getDynamicSpread`）：先读 `constantPriceSpread`，**紧接着**算 `priceImpactSpread` —— 此时 `orderSize = abs(usdDelta)` 用的是步骤 2 的**原始** `sizeDeltaUsd`，`depth` 按 `usdDelta` 符号与 `isLong` 选 ask / bid。
5. ⚠️ **`usdDelta` 会被就地覆写**：随后才调用 `getNextOpenInterest(params, true)`，它把 `params.usdDelta` 改写成 `tokenDelta × indexPrice.mid`（`tokenDelta` 即步骤 2 的预解析 `sizeDeltaInTokens`），并用 `openInterestInTokens × indexPrice.mid` 求当前 / 下一期 OI，据此得 `balanceWasImproved`（`|nextImbalance| < |currentImbalance|`）与 `skewImpact`。USD 模式下 `预解析 tokenDelta × mid ≠ sizeDeltaUsd`，**若按覆写后的值倒算 `priceImpactSpread`，点差就会算错**，执行价与回写后的规模随之全线偏移。
6. 求和后夹紧：`dynamicSpread = clamp(constantPriceSpread + priceImpactSpread + skewImpact, MIN_DYNAMIC_SPREAD[market][isLong], MAX_DYNAMIC_SPREAD[market][isLong])`（加仓恒 `allowNegativeSpread = true`；若 `maxDS < minDS` 先把 `maxDS` 抬成 `minDS`）。
7. 计算 `executionPrice`：Long `ceil(index.max × (1e18 + ds) / 1e18)`；Short `floor(index.min × (1e18 − ds) / 1e18)`。
8. ⚠️ **回写规模**：USD 模式重算 `sizeDeltaInTokens`（Long `floor(sizeDeltaUsd / executionPrice)`、Short `ceil(sizeDeltaUsd / executionPrice)`）；Token 模式重算 `sizeDeltaUsd = sizeDeltaInTokens × executionPrice`。**步骤 2 的预解析值到此作废**，此后所有公式（仓位规模、入场价、OI、事件）都用回写后的值。
9. 用 `BaseOrderUtils::getExecutionPriceForIncrease` 校验 `acceptablePrice`（Long 要求 `executionPrice <= acceptablePrice`，Short 相反）。
10. 计算 Funding：`negativeFundingFeeAmount = ceil(… / collateralPrice.min)`、`positiveFundingFeeAmount = floor(… / collateralPrice.max)`（两者都是单次 `Precision.mulDiv`、分母是 `1e30 × price`）。
11. 计算 position fee（用步骤 5 的 `balanceWasImproved` 选费率档）、referral、Pro、UI fee；加仓 `isLiquidation = false`，不计清算费。
12. ⚠️ 结算 Funding 到 LP：`settleFundingFees(negativeFundingFeeAmount, positiveFundingFeeAmount)` 按**净差**单向流动（加仓传的是**应付全额**，见 22.2）；随后才增记 `POSITION_FEE_TYPE` / UI 可领费用。
13. 计算入仓抵押品：`collateralDelta = initialCollateralDeltaAmount − totalCostAmount + positiveFundingFeeAmount`。
14. 更新仓位规模：`sizeInUsd += sizeDeltaUsd`、`sizeInTokens += sizeDeltaInTokens`（均为回写值）。
15. 更新 OI / cumulative open costs、可领费用账本、PositionVault 与 Market Vault 余额预期。
16. 单独计算 Keeper execution fee 与 refund（`GasUtils::payExecutionFee`）。
17. 用余额、DataStore、仓位字段、事件四层断言核对；事件按 **key** 取值（`dynamicSpread` 已移入 `intItems`，见 22.3）。

**回写步骤的数值示例**（自验，取 **18 位 index token**；非 18 位标的把价的标度换成 `1e30 / 10^decimals` 后同法计算）：`indexPrice.max = 3e15`（即 $3000 —— `3000 × 1e30 / 1e18`），`sizeDeltaUsd = 3e34`（$30,000 × 1e30），`dynamicSpread = 1e15`（+0.1%）。

```text
预解析 sizeDeltaInTokens = 3e34 / 3e15            = 10000000000000000000  （10.000000 标的）
executionPrice = ceil(3e15 × 1.001e18 / 1e18)     = 3003000000000000      （$3003）
最终 sizeDeltaInTokens  = 3e34 / 3003000000000000 = 9990009990009990009   （9.990010 标的）
两者相差 9990009990009991 ≈ 0.009990 标的
entryPrice = sizeInUsd / sizeInTokens             = 3003000000000000      （= executionPrice）
```

若误用预解析值，入场价会被算成 $3000、仓位数量多出约 0.01 标的，后续 PnL 与清算价全线偏移。

### 23.2 减仓 / 平仓 / 清算 / ADL

1. 读取 Oracle `indexTokenPrice` 与 `collateralTokenPrice`。
2. 按仓位等比销账求 `(sizeDeltaUsd, sizeDeltaInTokens)`：`PositionUtils::getDecreaseOrderSize`。全平走恒等分支直接取整仓两个字段。
3. 若 `sizeDelta > maxSizeDelta`（USD 模式取 `sizeInUsd`、Token 模式取 `sizeInTokens`）：Limit / StopLoss Decrease 截断到整仓并发 `OrderSizeDeltaAutoUpdated` 后重算；其他类型回退 `InvalidDecreaseOrderSize`。
4. ⚠️ **归一为全平之一 —— token 被吃光**（v0.3.2 新增）：`isSizeDeltaUsd && sizeDeltaUsd < sizeInUsd && sizeDeltaInTokens == sizeInTokens` 时，把 `sizeDelta` 改写为整仓 `sizeInUsd`、发 `OrderSizeDeltaAutoUpdated` 并重算。
5. 把 `initialCollateralDeltaAmount` 截断到 `position.collateralAmount`（超出时发 `OrderCollateralDeltaAmountAutoUpdated`）。
6. **仅当此刻 `sizeDeltaUsd < sizeInUsd`（仍是部分减仓）才进入下面这一整块**（`DecreasePositionUtils::decreasePosition`），块内四步按序执行：
   - 6a. 先跑一次 `getExecutionPriceForDecrease` 得预估执行价，据此算整仓预估 PnL，再按 `sizeDeltaInTokens / sizeInTokens` 等比拆出 `estimatedRealizedPnlUsd`，余下为 `estimatedRemainingPnlUsd`。
   - 6b. 用 `willPositionCollateralBeSufficient` 得 `estimatedRemainingCollateralUsd`。若 `!willBeSufficient` 或 `estimatedRemainingCollateralUsd + estimatedRemainingPnlUsd < MIN_COLLATERAL_USD`：`sizeDeltaUsd == 0` 时回退 `UnableToWithdrawCollateral`；否则发 `OrderCollateralDeltaAmountAutoUpdated` 把 `initialCollateralDeltaAmount` 归零（并把该笔金额按 `collateralPrice.min` 折回 `estimatedRemainingCollateralUsd`）。
   - 6c. ⚠️ **归一为全平之二 —— 剩余抵押不足**：归零后仍 `estimatedRemainingCollateralUsd + estimatedRemainingPnlUsd < MIN_COLLATERAL_USD` → 发 `OrderSizeDeltaAutoUpdated`、`setSizeDelta(maxSizeDelta)` 并重跑 `getDecreaseOrderSize`。
   - 6d. ⚠️ **归一为全平之三 —— 残仓过小**：`sizeInUsd > sizeDeltaUsd && sizeInUsd − sizeDeltaUsd < MIN_POSITION_SIZE_USD` → 同样发事件、改写为整仓并重算。

   命中 4 / 6c / 6d 任意一条后，**步骤 8 起的 `dynamicSpread` / `executionPrice` / PnL / 费用 / OI / 事件全部按整仓 `sizeInUsd` 重算**。贴近 `MIN_COLLATERAL_USD` 或 `MIN_POSITION_SIZE_USD` 的部分减仓用例若仍按“仓位还在”建期望值，链上实际已全平，必然产生假缺陷。
7. 若此刻已是全平（`sizeDeltaUsd == sizeInUsd`）且 `initialCollateralDeltaAmount > 0`，强制归零（此处**不发**事件）。清算单在进入结算前还要再跑一次 `isPositionLiquidatable`，不满足则回退 `PositionShouldNotBeLiquidated`。
8. 判定 `allowNegativeSpread`：`Order.isLiquidationOrder(orderType)` 或 `secondaryOrderType == Adl` 时为 `false`（`minDS` 抬到 ≥0），否则 `true`。
9. 用 `(−sizeDeltaUsd, −sizeDeltaInTokens)` 求 `dynamicSpread` 与 `balanceWasImproved`；三分量的求值顺序与 `usdDelta` 覆写陷阱同 23.1 步骤 4-6（减仓的 `tokenDelta` 是步骤 2/4/6 定下的等比销账值）。
10. 计算 `executionPrice`：Long `floor(index.min × (1e18 − ds) / 1e18)`；Short `ceil(index.max × (1e18 + ds) / 1e18)`。⚠️ **减仓没有回写步骤**——`sizeDeltaInTokens` 与 `sizeDeltaUsd` 保持等比销账（或归一后）的值，不随 `executionPrice` 改变。
11. 用 `BaseOrderUtils::getExecutionPriceForDecrease` 校验 `acceptablePrice`。
12. 计算 PnL：整仓 PnL 按**本步的 `executionPrice`**（含点差）求出，正 PnL 先过池子 `MAX_PNL_FACTOR_FOR_TRADERS` 等比封顶，再按 `mulDiv(totalPnl, sizeDeltaInTokens, sizeInTokens, roundUpMagnitude = totalPnl < 0)` 取本次已实现部分。
13. 计算 Funding、position fee（用步骤 9 的 `balanceWasImproved`）、referral、Pro、UI fee；仅 `Order.isLiquidationOrder` 为真时计清算费（ADL 不计）。
14. 按支付瀑布结算：正 PnL 先进 output（从 Market Vault 转入 PositionVault）→ 正 Funding 进抵押品 → 付负 Funding → 付负 PnL → 付其余费用 → 退还提取额（全平退全部剩余）。每步先扣 output 再扣抵押品。
15. ⚠️ 付完负 Funding 后**立即** `settleFundingFees(实际已付额, positiveFundingFeeAmount)`（早于负 PnL 与费用两步）；若实际已付 < 应付，另发 `InsufficientFundingFeePayment`（3 个 uint 字段）。
16. 更新仓位规模、OI、Vault 与可领费用账本；`sizeInUsd` 或 `sizeInTokens` 归零时整条仓位删除、剩余抵押品全额转入 output。**这一整块仍在 `decreasePosition` 内部完成**（`DecreasePositionUtils::decreasePosition` 266-300 行），早于下一步。
17. ⚠️ `decreasePosition` **返回之后**、`positionVault.transferOut` **之前**，才校验 `outputAmount × oracle.getPrimaryPrice(outputToken).min >= order.minOutputAmount`，不满足回退 `InsufficientOutputAmount`（`DecreaseOrderUtils::processOrder` 50-56 行；v0.3.2 起才真正生效）。因为回退会把步骤 16 的状态变更一并回滚，所以对成功路径的数值期望没有影响；但失败路径的期望必须按“仓位、OI、账本全部维持原状、一个事件都不发”建，不能按“先改后拦”建。
18. 单独计算 Keeper execution fee 与 refund。
19. 四层断言核对；`PositionDecrease` 事件的 `dynamicSpread` 在 `intItems`，`secondaryOutput*` 字段已不存在。

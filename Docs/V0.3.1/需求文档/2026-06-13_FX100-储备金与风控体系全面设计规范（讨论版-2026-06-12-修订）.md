## 一、背景与问题范围
FX100 是基于 GMX v2 代码库深度改造的永续合约协议，但在以下核心架构上与 GMX 存在根本差异。当前代码保留了 GMX 的风控公式，在 FX100 架构下会产生错误的风控结果。本文件覆盖识别出的所有风控缺口，提出完整的修复设计。

### 2.2 FX100 单池架构的核心风险特征
**多空天然对冲**：FX100 只有 USDC 池，LP 真正需要支付的是净 PnL（profitable side），而非单边名义 OI。当多空平衡时：
```javascript
LP 当前总义务 = max(0, longPnL) + max(0, shortPnL) ≈ 0
```
当价格介于多头平均入场价与空头平均入场价之间时，两侧都处于亏损状态，LP 义务为零。即便名义 OI 很大，只要多空平衡，LP 的实际风险极低。
**高资本效率的基础**：FX100 可以允许每个市场的名义 OI 远大于 poolUsd（RESERVE_FACTOR \> 1），同时通过全局净义务口径的 ADL + 提款 gate 保证 LP 的实际义务始终受控（§六）。
### 2.3 PendingPnL 缩放系数 = 0 的 FX100 特殊设计
FX100 刻意将 `pendingPnlScalingFactor = 0`，LP NAV 不反映交易者盈亏，为 LP 提供稳定的出入价格。这一设计需要以下补偿机制确保 LP 安全：
1. `MAX_PNL_FACTOR_FOR_WITHDRAWALS`：高 PnL 状态封锁 LP 提款（防按虚高 NAV 逃跑、把 pending 亏损甩给留守 LP）
2. ADL：自动降低赢面仓位，防止 LP 被过度消耗
**存款不需要 gate**（2026-06-12 确认）：scaling=0 下 NAV 不含 pending PnL，高 pending 盈利时存款等于按虚高 NAV 买入、兑现后 NAV 下跌——存款人自担损失、原 LP 反而受益，不存在套利路径（§5.3）。`MAX_PNL_FACTOR_FOR_DEPOSITS` 参数删除。
**当前状态**：WITHDRAWALS gate 是**死代码**（参数已定义，调用缺失），本设计接线；ADL 已实现（需改全局口径）。

## 四、Layer 1 — RESERVE_FACTOR（per-market 多空合计名义 OI 容量控制，2026-06-12 修订）
### 4.1 设计原则
每个 market 独立配置 `RESERVE_FACTOR`，**语义为该市场多空合计名义 OI 相对于 LP 池的占比上限**：`RESERVE_FACTOR_i = (Long + Short) 名义 OI 上限 / poolUsd`。
> 💡 RESERVE_FACTOR 控制的是**容量**（capacity），不是 LP 当前义务（obligation）。高 RF + 多空平衡 → 大量 OI 但 LP 义务极低 → **高资本效率**。高 RF + 多空失衡 → 由全局净义务口径的 ADL + 提款 gate 兜底（§六）。单边极端集中 → 由 per-side MAX_OPEN_INTEREST 硬顶兜底（已实现）。容量与失衡分工明确：RF 只管"这个市场总共能开多大"。
**市场间独立性**：各市场 RESERVE_FACTOR 独立设置，总和可远超 1。闲置市场（无开仓）的分配额度浪费可接受，因为约束是容量上限，而非资源预分配。
### 4.2 约束公式（多空合计）
开/增仓时校验（与方向无关，任一侧增仓都检查合计值）：
```javascript
(longOITokens_i + shortOITokens_i) × price.max ≤ RESERVE_FACTOR_i × poolUsd
```
多空合并用同一 `price.max` 折算，量纲一致；`price.max` 是保守的容量估算。

### 4.4 实现方案（不再需要 isLong 参数）
```solidity
function validateOpenInterestReserve(
    DataStore dataStore,
    Market.Props memory market,
    MarketPrices memory prices
) internal view {
    uint256 poolUsd = getPoolUsdWithoutPnl(dataStore, market, prices.collateralTokenPrice, true);
    uint256 reserveFactor = getReserveFactor(dataStore, market.marketIndex);  // per-market，可 > 1

    // 多空合计名义 OI（2026-06-12 修订：sum，而非每边各查一次）
    uint256 totalNominalOI = (
        getOpenInterestInTokens(dataStore, market.marketIndex, true)
            + getOpenInterestInTokens(dataStore, market.marketIndex, false)
    ) * prices.indexTokenPrice.max;

    uint256 maxAllowed = Precision.applyFactor(poolUsd, reserveFactor);

    if (totalNominalOI > maxAllowed) {
        revert FxErrors.InsufficientReserveForOpenInterest(totalNominalOI, maxAllowed);
    }
}
```
**DataStore 键**：`FX100Keys.RESERVE_FACTOR(marketIndex)`，per-market 独立配置（不再区分 isLong）。

MAX_PNL_FACTOR_FOR_DEPOSITS ← 🗑 删除（2026-06-12，存款无需 gate，见 §5.3）

### 5.2 状态机（2026-06-12 修订）
> ⚠️ **口径（详见 §六）**：状态机的驱动量统一为**全局净义务比**——ADL 触发与 WITHDRAWALS gate 使用同一个全局 pnlRatio；存款任何状态都允许。单边口径在 FX100 单池架构下会双重计账池容量；TRADERS cap 是唯一保留单边口径的检查。
```javascript
per-market 净义务: net_i = max(0, longPnl_i) + max(0, shortPnl_i)
全局净义务比:      pnlRatio = Σ_i net_i / poolUsd（ADL 与 gate 同一把尺子）

状态一（Safe）:   pnlRatio ≤ 0.65  → LP 存款✅ / 提款✅ / ADL不触发
状态二（Danger）: 0.65 < pnlRatio ≤ 0.75 → LP 存款✅ / 提款❌ / ADL不触发
状态三（ADL）:    pnlRatio > 0.75  → LP 存款✅ / 提款❌ / ADL触发（执行策略 §6.3）
状态四（Buffer）: 0.50 ≤ pnlRatio ≤ 0.75 → ADL执行后稳定区，提款仍封锁直到 < 0.65

存款任何状态都允许：新资金摊薄 pnlRatio，反而是自救通道（§5.3）
```
### 5.3 提款必须 gate、存款无需 gate：不对称性论证（2026-06-12 修订）
`validateMaxPnl()` 已实现（`MarketUtils.sol:L1194`）但从未被调用；本设计只为**提款**接线。
**提款缺 gate 的攻击路径（真实，必须修复）**：pnlRatio = 0.72 时，LP 持有者感知高 pending PnL，无 gate 封锁 → 按**虚高 NAV 卖出**退出（NAV 未含 pending 义务）→ 兑现后损失由留守 LP 承担。
**存款为什么不需要 gate（旧版"DEPOSITS gate 攻击路径"已证伪）**：旧版声称高 pnlRatio 时存款可套利——**方向写反了，不成立**：
```javascript
pool = 1000, supply = 1000, NAV = 1，pending 盈利 880（ratio 0.88）
存款人投入 1000 → 按 NAV=1 获得 1000 shares
兑现 880 → assets = 2000 − 880 = 1120 → NAV = 0.56

存款人取回 560，亏 440
原 LP：本来跌到 0.12，现在 0.56——反而被存款人救了
```
scaling=0 下 NAV 不含 pending PnL，高 pending 盈利时存款 = **按虚高 NAV 买入**，兑现后下跌，损失存款人自担、原 LP 受益。买高卖低无套利可言，机制自带反激励，无需合约封锁。该误判源于 GMX 语境（GLP 定价**包含** pending PnL，DEPOSITS factor 用于定价封顶）；FX100 scaling=0，理由不适用。存款不封锁的额外好处：高风险状态下新资金可自由进入，摊薄 pnlRatio、加速回到安全区（封锁存款反而阻断自救通道）。
> ⚠️ **已知接受的镜像行为（P2 监控）**：交易者**深度亏损**未兑现时（= LP 未实现收益），存款人可按不含该收益的 NAV 入场搭便车，稀释老 LP 未实现收益。不造成偿付风险，且深度亏损会被清算快速兑现、窗口极小，类似"除息前买入"，接受之。前端应展示全局净义务比让存款人知情。
### 5.4 修复方案：仅提款路径调用 gate
`LPVault.deposit()` **不加任何检查**（维持现状）。
```solidity
// LPVault.claimWithdrawRequest()：新增 PnL gate（全局净义务口径）
function claimWithdrawRequest(uint256 requestId, address receiver) external nonReentrant {
    _advanceEpoch();
    // ... existing checks ...
    _validatePnlForWithdrawal();  // Σ net_i / poolUsd ≤ MAX_PNL_FACTOR_FOR_WITHDRAWALS
    // ... 后续提款逻辑
}
```
### 5.5 实现细节：LPVault 计算全局净义务比（仅提款路径）
- LPVault 存储 `dataStore`、`oracle` 地址引用（admin 可配置）
- 迭代 `allMarkets`，对每个 market 计算 `net_i = max(0, longPnl_i) + max(0, shortPnl_i)` 并**累加**
- `Σ net_i > MAX_PNL_FACTOR_FOR_WITHDRAWALS × poolUsd` → claim revert
全局求和同时补上了跨市场聚合缺口（§3.4）：所有市场共用同一 USDC 池，提款 gate 关心的是 LP 的总义务。

## 六、净义务口径 — NET_RESERVE_FACTOR 的移除与替代
### 6.1 决策：移除 NET_RESERVE_FACTOR（2026-06-11）
早期版本设计了 per-market `NET_RESERVE_FACTOR`（开/增仓时校验 `net_i ≤ factor × poolUsd`）。移除理由：
1. **开仓时点检查的边际价值低**：新开仓位以当前价入场，pending PnL ≈ 0，对当前净义务几乎无贡献。净义务的膨胀来自价格变动而非开仓动作。
2. **误伤对冲性开仓**：净义务高企时，反方向开仓实际降低 LP 风险，但 validateNetReserve 无差别封锁所有开仓，阻断市场自我修复路径。
3. **MAX_PNL_FACTOR 体系覆盖同一风险量**：PnL 参数状态机直接作用于 pending 收益 P，且 ADL 是**主动减仓**，强于被动封锁开仓。
4. **简化运营**：叠加 2026-06-12 删除 DEPOSITS（§5.3）后，风险参数收敛为 **per-market RESERVE_FACTOR + 4 个全局/单边 PnL 参数**，风险度量统一为一个"全局净义务比"。
### 6.2 移除的前提条件：PnL 检查口径必须从"单边"改为"净义务"
> 🚨 **这是 06-11 修订的核心修正。不做此修正，不能移除 NET_RESERVE_FACTOR。**

### 6.3 ADL 全局化与执行策略（2026-06-12 修订）
**为什么 per-market ADL 阈值不可行**（06-11 版的缺陷，已废弃）：净义务的分布是**动态集中**的，静态的 per-market 预算两个方向都设不出来：
```javascript
设高了（每市场 0.75）：3 个市场各 net_i = 0.4，Σ = 1.2 已超池，
  但每个市场单独看都 < 0.75 → ADL 永不触发，整体早就该 ADL 了

设低了（0.90 / N 均分）：10 个市场每个只剩 0.09，
  单个热门市场 net_i = 0.09 就被 ADL，而全局义务也只有 0.09 → 过度触发，资本效率全毁
```
这与移除 NET_RESERVE_FACTOR 的理由同源：**静态 per-market 预算无法跟踪动态集中的风险**。因此 ADL 触发改为**全局口径**，与提款 gate 同一把尺子：
```javascript
触发条件: Σ_i net_i / poolUsd > MAX_PNL_FACTOR_FOR_ADL（全局单参数，0.75）
退出条件: Σ_i net_i / poolUsd ≤ MIN_PNL_FACTOR_AFTER_ADL（全局，0.50）
```
4 个 PnL 参数（WITHDRAWALS / MIN_AFTER_ADL / ADL / TRADERS）全部与市场数量无关，新上市场不需要调整任何风控参数。原 `Σ ADL_i ≤ 0.90` 治理纪律废弃。

### 6.5 PnL 口径精确定义、键结构与 Gas 可行性（2026-06-12 补充，给合约工程师）
#### 6.5.1 longPnl_i / shortPnl_i 的精确定义：单侧聚合净 PnL，不是"盈利仓位求和"
`net_i = max(0, longPnl_i) + max(0, shortPnl_i)` 中的 PnL **沿用现有 ****`getPnl`**（`MarketUtils.sol:L195-234`），它算的是**该侧全部仓位的聚合净值**：
```solidity
// O(1)：只读两个累计量，无仓位遍历
int256 openInterest = getCumulativeOpenCosts(dataStore, marketIndex, isLong);   // 该侧累计开仓成本
uint256 openInterestInTokens = getOpenInterestInTokens(dataStore, marketIndex, isLong);
int256 openInterestValue = openInterestInTokens * price;                        // 该侧当前总价值
pnl = isLong ? openInterestValue - openInterest : openInterest - openInterestValue;
```
**含义与边界，避免误解**：
- **侧内盈亏互抵**：同侧内 A 仓位盈利 +100、B 仓位亏损 −60 → 该侧聚合 PnL = +40。这不是"所有 pending 盈利仓位的 P 之和"（那需要遍历全部仓位逐一挑正值，O(N) 仓位，链上 gas 不可行）。
- **跨侧不互抵**（max(0,·) 分别取正再相加）：多空同时盈利时两侧义务叠加——这正是 sum 口径相对单边口径的修正点（§6.2）。
- **经济含义**：聚合净值 = 若该侧全部仓位以当前价同时平仓，LP 的净支付额。侧内亏损仓位的"抵扣"以其**抵押品为上限**，由清算引擎保证（亏损逼近抵押品前被强制平仓）——与 GMX 同假设。

#### 6.5.3 Σ net_i 的 Gas 可行性
每个市场的 net_i 计算量：4 个 DataStore 读（两侧的 cumulativeOpenCosts + openInterestInTokens，cold SLOAD ≈ 2.1k each）+ 1 次价格读取 + 算术 ≈ **15\~20k gas/市场**。20 个市场全量迭代 ≈ **300\~400k gas**，外加一次 `vault.totalAssets()`。
- ✅ **claim 提款路径**：低频操作（7 天锁定后），可接受
- ✅ **ADL keeper 路径**：keeper 交易，gas 由协议运营承担，可接受
- ❌ **绝不放进开仓/平仓交易路径**（本设计也没有放——开仓只查本市场 RESERVE_FACTOR，O(1)）
#### 6.5.4 价格来源：分层取价 + 持久缓存
现状问题：`Oracle.primaryPrices` 是 per-tx 设置、执行后 `clearAllPrices()` 清除（`Oracle.sol:L125`，GMX 模式），**不能依赖**；keeper 也不可能为一笔 claim 批量签名 20 个市场的价格。
```javascript
对每个 market 的 indexToken：
1. 有 Chainlink feed → ChainlinkPriceFeedUtils.getPriceFeedPrice(dataStore, token)
   （同步读，已有实现，Tier A 资产直接用）
2. 无 feed → 读"最近记录价"缓存 latestRecordedPrice[token]
   （新增：keeper setPrices 时顺手写入持久缓存 {price, timestamp}，不随 clearAllPrices 清除）
3. 缓存超过 staleness 上限（建议 24h）→ 该市场计价不可信：
   - claim 路径：revert（保守，等 keeper 刷新该市场价格后再 claim）
   - ADL 路径：该市场以缓存价计入 Σ（触发判断宁可偏旧不漏算），但不允许对该市场执行 ADL
```
无 feed 资产（如 Pyth-only 长尾市场）的最近记录价由日常交易活动自然刷新（每笔订单执行都 setPrices）；活跃市场缓存永远新鲜，僵尸市场超龄则按上述降级处理。

## 八、其他风险场景
### 8.1 Oracle 缺口与价格跳跃窗口
**风险**：Keeper oracle 签名有 `MAX_ORACLE_PRICE_AGE = 60s` 有效期，极端波动时价格可能已大幅偏移。
**当前保护**：`MAX_ORACLE_REF_PRICE_DEVIATION_FACTOR = 2%`（链外签名价格与 Chainlink 参考价差超 2% → 拒绝）
**建议**：
1. 主网将 `MAX_ORACLE_PRICE_AGE` 降至 30s
2. 生产环境 ETH heartbeat 从 3600s 降至 300s
3. 大波动期间 ADL Keeper 优先执行
### 8.2 USDC 脱锚风险（P2）
若 USDC/USD 脱锚，LP 池 USDC 价值缩水而 USD 计价的 PnL 义务不变，LP 实质亏损。建议引入 `USDC_DEPEG_THRESHOLD`（例如 0.98），低于此值时暂停开仓。
### 8.3 ADL Keeper 单点故障
若 Keeper 延迟或离线，全局净义务比超过 ADL 阈值但无人执行 ADL，LP 继续承担风险。
**建议**：
1. 实现 WITHDRAWALS gate（Layer 2）作为被动保护
2. Keeper 监控告警：全局净义务比 \> 0.65 告警，\> 0.75 PagerDuty
3. Chainlink Automation 作为去中心化 ADL 触发备份（P2）
### 8.4 7 天提款锁定与 PnL Gate 的交互
LP 已 burn shares 后（initiateWithdrawRequest），若等待期内全局净义务比超过 WITHDRAWALS 阈值，claim 会被 gate 封锁，LP 被迫继续暴露风险。
**建议**：在 claim 时检查 gate，gate 封锁期间 `unlockAt` 不消耗（或允许 LP 取消请求并重新发起）。

## 十一、测试用例要求
### Layer 1 — RESERVE_FACTOR（per-market 多空合计名义 OI 容量，2026-06-12 修订）
- T-R01: `(longOITokens+shortOITokens) × price.max` \< RESERVE_FACTOR × poolUsd → 开仓成功
- T-R02: 合计名义超限 → revert InsufficientReserveForOpenInterest（无论本次增仓是 Long 还是 Short——验证检查与方向无关）
- T-R03: **sum 口径验证**：同一合计总量下，分布不同（long 3.0 + short 0 vs long 1.5 + short 1.5）→ 检查结果一致
- T-R04: RESERVE_FACTOR = 3.0（\>1）时，合计名义 OI = 2.8× poolUsd → 开仓成功（验证 factor \> 1 合法）
- T-R05: 单边吃满全部合计额度（long 3.0 + short 0）→ RESERVE_FACTOR 通过，但仍受 per-side MAX_OPEN_INTEREST 约束（验证两个检查互补独立）
- T-R06: 两个市场 RESERVE_FACTOR 之和远超 1 时，各市场独立检查均通过 → 开仓成功（无跨市场聚合）
### 净义务口径（替代原 NET_RESERVE_FACTOR；ADL 全局口径见 §6.3）
- T-N01: 多空平衡（longPnl ≤ 0，shortPnl ≤ 0）→ Σ net = 0，gate 全开、ADL 不触发
- T-N02: **多空同时盈利**（单市场 longPnl = 0.4 × poolUsd，shortPnl = 0.4 × poolUsd）→ Σ = 0.8 \> ADL(0.75) → ADL 触发（单边口径下两边均 \< 0.75 不会触发——口径修正的核心验证）
- T-N03: 多空同时盈利（longPnl = 0.4，shortPnl = 0.3）→ Σ = 0.7 \> WITHDRAWALS(0.65) → claim revert，但 \< ADL(0.75) → ADL 不触发（状态二验证）
- T-N04: 验证用 sum 而非 \|差\|：longPnl = 0.4，shortPnl = 0.3 → net_i = 0.7（非 0.1）
- T-N05: **跨市场聚合（gate）**：两市场各 net_i = 0.35，全局 Σ = 0.7 \> WITHDRAWALS(0.65) → claim revert
- T-N06: **跨市场聚合（ADL）**：两市场各 net_i = 0.4（单独看均远低于 0.75），全局 Σ = 0.8 \> ADL(0.75) → ADL 触发（per-market 口径下永不触发——2026-06-12 修正的核心验证）
- T-N07: **ADL 选市策略**：market A net = 0.5，market B net = 0.3 → 合约允许 ADL A；ADL 亏损侧（pnl ≤ 0）→ revert（验证目标方向必须盈利）
- T-N08: **ADL 退出条件**：ADL 执行至全局 Σ ≤ MIN_PNL_FACTOR_AFTER_ADL(0.50) 后，继续 ADL → revert（防过度减仓）
- T-N09: 多空同时盈利触发 ADL 时，优先减仓盈利较大一侧（Keeper 策略回归验证）
- T-N10: TRADERS cap 单边维持：单边 pnl \> 0.9 × poolUsd 时结算被 cap；连续结算后 pool 余额恒 \> 0（不会资不抵债）
- T-N11: **聚合口径验证（§6.5.1）**：同侧 A 仓位盈利 +100、B 仓位亏损 −60 → 该侧 PnL = +40（侧内互抵），net_i 按 +40 计入（非 +100）
- T-N12: **取价分层（§6.5.4）**：无 Chainlink feed 的市场用最近记录价计入 Σ；缓存超 staleness 上限 → claim revert、该市场禁止被 ADL
### Layer 2（PnL Gate，全局净义务口径；2026-06-12：存款无 gate）
- T-G01: Σ net_i / poolUsd \< WITHDRAWALS(0.65) → deposit 允许，claim 允许
- T-G02: **存款永不封锁**：Σ net_i / poolUsd = 0.88（高位）→ deposit 仍成功，且 shares 按当前 NAV（不含 pending PnL）铸造——验证存款人按虚高 NAV 买入、自担后续 NAV 下跌（§5.3 回归测试）
- T-G03: Σ net_i / poolUsd \> WITHDRAWALS(0.65) → claimWithdrawRequest revert
- T-G04: Σ net_i \> ADL(0.75) → ADL 触发，执行后 Σ net_i \< minAfterAdl(0.50)
- T-G05: Σ net_i / poolUsd \< WITHDRAWALS 后 claim 成功
- T-G06: 高 pnlRatio 时存入大额 USDC → pnlRatio 被摊薄，可使提款 gate 重新打开（验证存款的自救通道作用）

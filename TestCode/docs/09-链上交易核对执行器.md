# 链上交易核对执行器（verify-tx）

## 1. 目的

给「已经在链上发生的交易」补一份独立核对：贴 tx hash，执行器读回执、事件、`execBlock−1 / execBlock` 钉块状态与 DataStore 参数，按 tx 类型挑核对包（pack）用 v0.3.2 合约口径独立复算期望值，出一份与跑批附件同形的证据 JSON（`evidenceV2 + reconciliationReport + checks`）和唯一结论（PASS / FAIL / NOT_VERIFIED）。

它解决三类跑批覆盖不到的场景：

1. 手工在页面 / 钱包发起的交易（手工测试工作台的合约层结果需要证据，不能只写「看了一眼余额」）；
2. 自动化 spec 之外的 tx 组合（单笔平仓、清算单、Keeper 服务执行的订单）；
3. 事后复核：某次跑批的 tx 想换一套 pack 或换元数据重新核对。

执行器不实现任何公式。期望值与判定全部来自 `src/reconciliation/packs/*`，公式口径唯一依据是 [`TestCase/E2E/ContractCodeSummary/v0.3.2/FX100-核心字段计算公式.md`](../../TestCase/E2E/ContractCodeSummary/v0.3.2/FX100-核心字段计算公式.md)（每条核对行的 `formulaBasis.section` 指向其章节），并回 `Github/fx100-contracts@release-v0.3.2/src` 源码复核。

代码位置：

| 层 | 文件 | 职责 |

## 2. 前置

1. 工程可跑：`npm install`、`npm run typecheck` 通过；`npm run doctor` 对目标环境通过。
2. 目标环境在可信环境目录里（`config/environments/catalog.ts::environmentNames`：`dev-readonly / tx-fork / oracle-fork / time-fork / base-sepolia`），其 RPC 已在 `.env` / `.env.local` 配好。执行器只走 `src/execution/runtime-environment.ts::resolveRuntimeTestEnvironment` 解析 RPC 与 chainId，不接受命令行传 URL。
3. 基线登记齐全：`Docs/contract-releases/CURRENT.json` 的 `environments.<env>.forkOf`、`deployments[]`、`primary.head`、`frontend.head`，以及 `config/mock-resources.json` 的 `resources.<env>.chainId`——元数据默认值全部从这些登记文件取（§4）。
4. tx 必须还在目标环境的链上（Fork 重建后旧 tx 不存在，见 §8）。
5. 看板路径额外需要 `npm run dashboard:serve`（静态 `dashboard:build` 页面里「链上核对」按钮禁用）。

只读操作：执行器不发交易、不改链上状态、不写密钥；日志与错误文本里的 URL 一律脱敏为 host。

## 3. 三种用法

### 3.1 CLI：`npm run verify:tx`

```bash
npm run verify:tx -- --env tx-fork --case XT-MKT-OPEN-001 \
  --tx 0x550367d3c6f360cd355d9e9eb88a0f1ae43a1f97d14e3c3be498345bdeadb535 \
  --tx 0x6d1131c00df876341fabf281c131e5d369e4b3151a4738c62441c88efea7417b \
  --note "手工平仓复核"
```

- `--tx` 可重复或逗号分隔，按链上顺序给（下单 / Keeper 执行 / 平仓 / Keeper 执行）；看板路由最多 32 笔（`normalizeTxHashes`），CLI 不封顶；
- `--case` 缺省为 `adhoc-tx-verify`，给了必须符合 `CT|XT|FT-<域>[-<子段>]-NNN` 或 `SCN-NNN`；
- 输出：终端打印 `[元数据] [交易] [核对计划] [核对行] [结论]` 五段（适配器有告警时另加一段 `[适配器告警]`），证据 JSON 默认落 `artifacts/manual-verify/<env>/<yyyyMMdd-HHmmss>-<case|adhoc>.json`（`--out` 改路径，`--json` 改为在终端打印完整证据 JSON 并附 `outPath`）。

### 3.2 看板逐条引导：测试用例页抽屉「链上核对」

1. `npm run dashboard:serve`，打开 `http://localhost:4173/test-cases`，在「版本功能用例（CT/XT/FT）」分区点某条用例的「记录结果」（或从「手工测试工作台」创建手工批次后进入逐条引导）。
2. 抽屉里的「链上核对」块：选环境（下拉来自 `/api/environments`，默认 `tx-fork`），tx hash 每行一个；「元数据覆盖」折叠区留空即登记默认值。
3. 点「核对」→ `POST /api/verify-tx`，页面渲染唯一结论徽章、分层 layers、核对行表（含 `§` 章节列）、元数据表（值 / 来源 / 出处，覆盖值高亮）、tx 明细、计划 / pack / 告警。此时服务端不落盘。
4. 点「回填」→ `POST /api/manual-runs/attach`（证据 JSON 原样内联上传，服务端不接受路径引用）：
   - 落盘 `TestCase/E2E/manual-runs/<批次 id 或 adhoc>/<caseId>/verify-<时间戳>.json`；
   - 服务端按核对行**重新推导**结论（不信任上传的 `summary.verdict`），把证据路径填进「证据链接」，把「合约层」下拉锁到映射值（§6），实际结果留空时自动填一句摘要。
5. 点「保存并追加到 results.md」→ 一行追加进 `TestCase/E2E/versions/<release>/results.md` 标记区（追加不覆盖）。

### 3.3 以后：Playwright spec 内调用（未实现）

runner（`runTxVerify`）已与入口解耦，spec 在动作结束后拿到 tx hash 即可复用它给出独立核对，再经 reporter 挂为执行证据。本阶段**没有**接入任何 spec，看板跑批门槛（P4）也未接：`tx-verify.adhoc` 计划不在可信计划注册表（`src/reconciliation/check-plan-registry.ts` 登记 4 个计划：`market-open.roundtrip@2`、`market-close.roundtrip@1`、`market-close.cleanup-roundtrip@1`、`liquidation.forced-close@1`；**verify-tx 目前只取 `market-open.roundtrip@2`**（`src/reconciliation/verify-tx.ts` 的 `findTrustedCheckPlan`），market-close / liquidation 两包已注册但尚未接入执行器），跑批信任门会把 adhoc 产物判 INVALID_EVIDENCE。手工回填走的是 attach 的重推导，不经过该门。

## 4. 元数据默认值与覆盖

所有默认值出自既有登记文件，解析在 `src/reconciliation/adapters/tx-metadata.ts::resolveTxVerifyBaseMetadata`（纯函数，不读 RPC）。证据 JSON `data.metadata.resolvedFrom` 逐字段记 `default / override`，`data.metadata.sources` 记出处。

| 字段 | 默认来源 | CLI flag | UI 字段（`render-test-cases.ts`） |
|---|---|---|---|
| `env` | 无默认，必填；须在 `environmentNames` 内 | `--env <name>` | 环境下拉 `#vc-tx-env`（默认 tx-fork，记住上次选择） |
| `hashes` | 无默认，必填，看板 ≤ 32 笔 / CLI 不限 | `--tx <hash>`（可重复 / 逗号分隔） | tx hash 文本框 `#vc-tx-hashes`（每行一个） |
| `caseId` | `adhoc-tx-verify` | `--case <id>` | 抽屉当前用例 ID（自动带入） |
| `contractVersion` | `CURRENT.json environments.<env>.forkOf` → `deployments[id].releaseLabel / version`（缺登记退绑定表 `bindings.<env>.release`） | `--contract-version <v>` | 合约版本 `#vc-tx-ov-contractVersion` |
| `contractHead` | 部署版本 = `primary.version` 取 `primary.head`；= `comparison.version` 取 `comparison.head`；否则绑定表 `contractCommit`（不一致时告警） | `--contract-head <sha>` | 合约 head `#vc-tx-ov-contractHead` |
| `frontendHead` | `CURRENT.json environments.<env>.frontend.head ?? frontend.head`（缺则空串 + 告警） | `--frontend-head <sha>` | 前端 head `#vc-tx-ov-frontendHead` |
| `chainId` | Fork 环境取 `config/mock-resources.json resources.<env>.chainId`，否则绑定表 `environmentChainId`；再与 RPC `eth_chainId` 交叉核对，不一致告警 | `--chain-id <n>` | 无（看板只展示，不提供覆盖） |
| `executedAt` | 最后一笔 tx 所在区块 timestamp（`eth_getBlockByNumber`） | `--executed-at <iso>` | 执行时间（ISO）`#vc-tx-ov-executedAt` |
| `note` | 无 | `--note "…"` | 备注 `#vc-tx-ov-note` |
| `batchId` | 无（落到 `adhoc` 段） | 无（CLI 不进 manual-runs） | 逐条引导模式自动带手工批次 id |
| 输出路径 | `artifacts/manual-verify/<env>/<yyyyMMdd-HHmmss>-<case|adhoc>.json` | `--out <path>` | 回填落 `TestCase/E2E/manual-runs/<batchId|adhoc>/<caseId>/verify-<ts>.json` |

覆盖只改写元数据与 envelope 的自述字段，不改变核对本身；`contractVersion` 覆盖成与环境登记不一致的值时会在告警里写明「绑定校验会标出」。

## 5. 输出与退出码

证据 JSON 顶层：`id / title / source / generatedAt / request / summary / checks / data / evidenceV2 / reconciliationReport`。

- `summary`：`verdict`（PASS / FAIL / NOT_VERIFIED）、`exitCode`、`reasons[]`、`counts`（按 verdict 计数）、`reportStatus`、`layers`；
- `checks[]`：与 tests/B 功能用例附件同形的扁平摘要（`name = "<actionId> <id>"`、`passed`、`verification`、`verdict`、`severity`、`note`、`ledgerFieldId`）；
- `reconciliationReport.checks[]`：完整 `CheckRecord`（`formula.inputs` 逐项带来源、`formulaBasis`、`ledgerFieldId`、`before/after/Δ`）；
- `data.metadata`：§4 全部字段 + `perTx[]`（hash / block / 时间 / role / kind / actionId / orderKey）；
- `data.plan`：计划 id@version、digest、`trust`（registered / adhoc）、`applied / excluded / noPack / notes`；
- `data.formulaBasis.byCheckId`：`"<actionId> <id>" → { formulaId?, section, title?, ledgerFieldId? }`。

唯一结论的推导（`verify-tx.ts::verdictFromRows`，attach 重推与 CLI 退出码同源）：

| 条件 | 结论 | CLI 退出码 |
|---|---|---|
| 任一 blocking FAIL，或报告 `INVALID_EVIDENCE` | FAIL | 1 |
| 无上述，但存在 NOT_VERIFIED 行 / warning FAIL / 缺 pack 的 tx / 没有核对行 | NOT_VERIFIED | 2 |
| 其余（全部 PASS 或 NOT_APPLICABLE，且每笔 tx 都被 pack 覆盖） | PASS | 0 |
| 参数不合法 / 读链或组装证据失败（`TxVerifyInputError` / `TxVerifyChainError`） | —（终端打印原因） | 3 |

### 元数据一致性核对行 `metadata.chain-id`（blocking）

每次运行都会在核对行末尾追加一条计划外的核对行 `metadata.chain-id`（packId `tx-verify.metadata`，等级 `IDENTITY`）：把本次证据**断言**的 chainId（登记值，或 `--chain-id` / UI「元数据覆盖」手填值）与 RPC 实际返回的 `eth_chainId` 逐字比较。

| 情形 | 该行 | 对整体结论 |
| --- | --- | --- |
| 一致 | PASS | 不影响 |
| 不一致（例如 `--chain-id 84532` 却连的是 99911） | **FAIL（blocking）** | 整体 FAIL、退出码 1——证据被贴到了错误的链/环境，其余行即使全 PASS 也不可采信 |
| RPC `eth_chainId` 读不到 | NOT_VERIFIED | 按 schema 不得 PASS；整体至少 NOT_VERIFIED |

这一行**不参与** `ReconciliationReport` 的完整性聚合（报告只统计可信计划内的行），只并入 verdict 与输出；`[元数据]` 段里 `chainId … · RPC eth_chainId=…` 若带 `⚠ 不一致`，对应的就是这行 FAIL。实测：2026-09-06 对 tx-fork 上 XT-MKT-OPEN-001 的 4 笔 tx，默认 chainId 时该行 PASS、退出码 0；`--chain-id 84532` 时该行 FAIL、退出码 1。


看板路由状态码：400 参数不合法、502 读链失败、403 非同源、500 其它异常。

注意 `reportStatus` 与唯一结论是两个东西：`PASS_WITH_GAPS` 常见于 `evidenceIntegrity=INCOMPLETE`（执行窗口污染扫描凭证缺失，见 §8），此时只要核对行全 PASS，唯一结论仍是 PASS。

## 6. 结论如何进 results.md 与台账

### 6.1 results.md（版本功能用例结果台账）

- 看板路径：回填后「合约层」被锁到映射值——`PASS → PASS`、`FAIL → FAIL`、`NOT_VERIFIED → GAP`（NOT_VERIFIED 不在 results.md 词汇表，记 GAP 表示核对缺口）；若 `CURRENT.json` 该环境该层的 `admissionScope` 禁用了 PASS，则改记 BLOCKED 并在状态栏说明。锁定后下拉只能改得更差、不能改得更好；证据列自动加入 `TestCase/E2E/manual-runs/…/verify-*.json` 相对路径；点「保存并追加到 results.md」写入标记区。
- CLI 路径：在看板「记录结果」抽屉手工填同一映射，证据列填 `TestCode/artifacts/manual-verify/<env>/<file>.json`（工作区相对路径）。CLI 产物不会自动进 manual-runs。
- 两条路径的结论都不能高于证据：`verification=NOT_VERIFIED` 的行永远是 NOT_VERIFIED，schema 禁止判 PASS。

### 6.2 核对字段台账（`config/reconciliation-fields.json` · 看板「核对数据控制台」）

核对行携带 `ledgerFieldId`（`src/reconciliation/ledger-field-id.ts::contractLedgerFieldId`：`formulaBasis.section` 的前两级章节号 → `c-<章>-<节>`，只认第 1～20 章，与 seed 出行规则同一函数）。重跑 seed 时：

```bash
npx tsx scripts/seed-reconciliation-fields.ts --dry-run --verbose   # 先看统计与逐行回链，不写盘
npx tsx scripts/seed-reconciliation-fields.ts                        # 写 config/reconciliation-fields.json
npm run dashboard:build -- artifacts/latest/results.json             # 刷新核对数据控制台页
```

seed 除 `artifacts/latest/results.json` 外，还扫描 `TestCase/E2E/manual-runs/**/verify-*.json`（看板回填）与 `TestCode/artifacts/manual-verify/**/*.json`（CLI）里的 `reconciliationReport.checks`：

- 合约章节行（`c-`）按 `ledgerFieldId === row.id` 精确匹配；没有派生 id 的旧产物退回标题 / 章节 / 公式文本的模糊规则；参数行（`p-`）与配对行（`pair-`）仍走模糊规则；
- `verification=NOT_VERIFIED` 的行不算覆盖（没算出来的字段不能叫「已生效」）；
- 同一 caseId 的同一核对行只保留 `generatedAt` 最新的产物一处回链，`coveredBy[].rowId` 形如 `TX2 fee.position.amount @ TestCode/artifacts/manual-verify/tx-fork/<file>.json`；
- `implemented` 每次重算；`candidate / accepted` 是人工裁决，seed 不回退。

2026-09-06 干跑对照：只有旧产物（无 `ledgerFieldId`）时模糊规则把 `§6.6 核对要点` 的行同时记到 `c-9-8（9.8 核对要点）`；换成带 id 的新产物后该误配消失，`c-8-5 资金去向` 等 2 行改由精确匹配补上，仅靠手工核对升为 implemented 14 行（2026-09-06 干跑：采纳 11 份、跳过 2 份；数字随手工核对累积变化）。

## 7. 证据等级说明

`CheckRecord.verification` 由 pack 按输入来源如实标注，引擎与 schema（`src/reconciliation/schema/check-record.ts`）强制两条：`NOT_VERIFIED` 不得判 PASS；`FULL_RECOMPUTE` 必须登记至少一个可追溯 `formula.inputs`（每项带 `source.layer / path / blockNumber / txHash`）。

| 等级 | 何时 | 例（market-close.decrease@1） |
|---|---|---|
| `FULL_RECOMPUTE` | 全部输入来自 `execBlock−1` 钉块状态（Reader 仓位、Vault 余额、DataStore 键）、订单意图或 DataStore 参数，没有任何一项取自执行事件 | `order.size-delta.effective`（§5.2）、`position.size-delta-in-tokens`（§3.2）、`ledger.conservation`（§5.4） |
| `EVENT_ANCHORED` | 任一输入来自执行事件（`executionPrice`、`dynamicSpread`、`basePnlUsd`、费用与 funding 金额），期望值是「按事件给的输入同序复刻」而不是独立重算 | `pricing.decrease.execution-price`（§4.6：`dynamicSpread` 取自事件 `intItems`，未独立移植 `getDynamicSpread` 前不升级）、`fee.position.amount`（§7.1）、`settlement.waterfall.output`（§5.4） |
| `IDENTITY` / `PRESENCE` | 恒等式（多侧数据必须相等 / 同号）或存在性（事件是否出现、仓位是否移除、Keeper 执行是否成功） | `pnl.cap-direction`、`fee.liquidation.not-charged`、`position.removed-on-full-close` |
| `NOT_VERIFIED` | 缺关键输入（`execBlock−1` 状态未采集、参数未读到、事件缺字段）；引擎为 pack 声明的必需输入自动生成 `<pack>.required-input.<name>` 行；pack 内则以 `notVerified()` 写明「本应如何算」与缺什么 | 清算包在 `execBlock−1` 的 funding per-size / skewEMA 未采集时，成交价 / PnL / 费用只能锚事件，判定条件缺输入即 NOT_VERIFIED |

缺 `execBlock−1` 状态时只允许降级标注，不允许用 0、`Actual` 或执行后状态顶替去凑一个「能算」的期望值。

## 8. 已知限制

1. **Fork 历史块**：Tenderly 私有 fork 重建后旧 tx 不存在（`TxVerifyChainError`，退出码 3）；fork 点之前的区块也读不到 `execBlock−1` 钉块状态，相关行降级 NOT_VERIFIED。三个环境的实际部署版本随 `CURRENT.json environments.<env>.forkOf` 变化，重建后请先重跑再回填。
2. **尚无 pack 的 tx 类型**（`verify-tx.ts::noPackReason`）：取消 / 冻结、仅 Funding 结算、Limit / StopLoss / StopIncrease 创建类、`reverted` 回执、单独给出的创建 tx（开仓需 `submitMarketIncrease + executeOrder` 成对为 TX1/TX2 才接 `market-open.core`）。这些 tx 被列入 `noPack`，结论最高只到 NOT_VERIFIED。
3. **P4 跑批门槛未接**：只有严格 4 笔「开 → 平」命中注册计划 `market-open.roundtrip@2`；其它组合用 `tx-verify.adhoc@1`，看板跑批信任门判 INVALID_EVIDENCE，产物只作手工核对材料（attach 重推不受影响）。
4. **evidenceIntegrity=INCOMPLETE**：执行窗口污染扫描（V3 CLEAN/POLLUTED 逐块凭证）尚未接入 tx-hash 路径，`reportStatus` 停在 `PASS_WITH_GAPS`。
5. **前端 / Indexer 层不在范围**：`layers.frontend / indexer` 恒为 NOT_RUN，前端显示值核对走 docs/07。
6. **清算包依赖采集深度**：`MIN_COLLATERAL_USD`、`execBlock−1` 的 funding / skewEMA 未采集时按可靠方向下结论，否则 NOT_VERIFIED（`packs/liquidation.ts` 头注释）。
7. 手工核对产物只按 `ledgerFieldId` 精确回链台账；`§23.x`（流程附录）等第 20 章以外的依据不出台账行，`keeper.close-execution` 一类行因此没有 `ledgerFieldId`，属预期。

## 9. 设计约束

### 9.1 P0 修复的三处（已落地，回归时不得倒退）

1. **事件字段按 key 名取值，不按下标**（`adapters/tx-hashes.ts` 解码 EventEmitter 日志）：v0.3.2 事件字段已重排，`dynamicSpread` 改为 `int256` 且落在 `intItems`；按位置取值会把别的字段当点差。
2. **缺 `execBlock−1` 状态一律降级 NOT_VERIFIED，不顶替**（`packs/decrease-shared.ts` 头注释 · `engine/check-engine.ts` 必需输入检查）：以前「能算就算」的做法会把执行后状态或 0 当输入，产出看起来 PASS 的假复算。
3. **RPC / chainId 只走既有运行时解析，错误文本脱敏**（`adapters/tx-hashes.ts` · `verify-tx.ts::maskText`）：不拼 URL、不把密钥写进证据或日志；RPC `eth_chainId` 与登记 chainId 不一致只告警并如实记录。

### 9.2 不能让步的四条

1. **期望值只按 v0.3.2 合约源码口径**：公式只在 packs 里实现（依据 `FX100-核心字段计算公式.md` 章节并回 `Github/fx100-contracts@release-v0.3.2/src` 复核），runner / CLI / 看板路由不实现、不改写任何公式或判定。
2. **证据等级诚实**：`NOT_VERIFIED` 不得判 PASS；`FULL_RECOMPUTE` 必须登记可追溯输入；缺 `execBlock−1` 状态就降级标注，不许为了「能算」偷换口径。schema 在 `checkRecordSchema.superRefine` 里硬拦。
3. **RPC 与 chainId 一律走 `resolveRuntimeTestEnvironment`**：不自己拼 URL、不读 `.env / pk.txt / Devconfig / Memory`，任何密钥不进代码、证据与日志。
4. **事件解析按 key 名取值不按下标**：所有从 `EventLog` 取字段的代码都以 `<type>Items` + key 名定位，禁止用位置索引。

另外两条工程纪律：结论只有一层（`verdictFromRows`，attach 与 CLI 同源，产物里的 `summary.verdict` 不被信任、一律重推）；核对行只能由 pack 产生，`aggregateReport` 会重跑 CheckPlan 并比对 checks 摘要，产物层以外改写核对行会被判 INVALID_EVIDENCE（`ledgerFieldId` 因此在 pack 的 `row()` 内派生，market-open 系只在产物 `data.formulaBasis.byCheckId` 补派生）。

## 10. 故障排查

| 现象 | 原因 / 处理 |
|---|---|
| `参数错误：--env=… 不在可信环境目录` / `不是合法交易哈希` / `--case=… 不符合用例编号规范`（退出码 3） | 按 `npm run verify:tx -- --help` 的用法修正；用例编号先存在于 `TestCase/E2E/versions/<release>/Trade-测试用例矩阵.md` 再用 |
| `读链 / 组装证据失败：…`（退出码 3 / 看板 502） | tx 不在该环境链上（Fork 重建、贴错环境）或 RPC 未配置；核对 `CURRENT.json environments.<env>.forkOf` 与 `config/mock-resources.json resources.<env>.chainId`，看 `[元数据]` 里 `RPC eth_chainId … ⚠ 不一致` |
| 结论 NOT_VERIFIED，`reasons` 含 `缺 pack 的 tx N 笔：TX1(create)` | 只给了创建 tx：开仓要把 `submitMarketIncrease` 与其 `executeOrder` 一起给（TX1/TX2 配对）；平仓给「提交减仓 + Keeper 执行」两笔；清算给清算单执行 tx |
| `排除 pack market-close.decrease@1：…`（预检失败） | 该 pack 对当前 tx 组合不适用（如减仓事件解不出 / 缺 execute 快照），看排除原因；不是核对失败 |

| `reportStatus=PASS_WITH_GAPS`、`evidenceIntegrity=INCOMPLETE` 但结论 PASS | §8.4 的已知缺口，不影响唯一结论；results.md 记 PASS 时证据列带产物路径即可 |
| 看板「静态模式：链上核对需通过 npm run dashboard:serve 打开本页」 | 用 `dashboard:serve` 而不是打开 `artifacts/latest/test-cases.html` |

# FX100 并行会话作业规程

> 适用：同一工作区里同时有多条会话（人或 Agent）在跑测试，尤其是「临时插入一个版本验证」这种打断式作业。
> 来源：2026-09-05 并行会话干扰审计（会话 A 测 v0.3.2/tx-fork 期间，会话 B 临时插入 v0.3.1 + 新 RPC 回归验证）。
> 结论一句话：**链上层天然隔离，本机共享工装会互相打架**——当天实际发生了 4 处干扰。

---

## 一、三条铁律

### 铁律 1：临时 fork 必须申请独立 chainId

这不是最佳实践，是**唯一防线**。

keeper 的 Redis 键前缀是 `<KEYSPACE_VERSION>:<chainId>:`，而 `KEYSPACE_VERSION` 是**硬编码字面量** `"v0.3.2"`（`Github/fx100-apps@develop/packages/sdk/src/configs/keyspace.ts:18`，注释明写 MUST stay a literal）。它**不跟随被测合约版本**——你测 v0.3.1，键照样写 `v0.3.2:<chainId>:*`。

所以两条会话的 keeper 数据是否会串，**只由 chainId 决定**。

2026-09-05 的教训：临时 fork 保留了父链的 `84532`（与真 Base Sepolia 同号），起 keeper 时撞上残留游标，producer 回放了 117 万个块，3 分钟写了 31MB 日志、堆了 2.7 万个 orders 键。

### 铁律 2：不碰共享单一事实源与登记文件

见 §四「绝对不能碰」清单。临时会话**默认只读**。

### 铁律 3：动别人的东西之前先问，走之前先还原

工作区是共享的，`git status` 里混着多条会话的 WIP。提交**只显式列自己的路径**，禁用 `git add -A` / `git commit -a`。

### Redis 前缀

```
v0.3.2:<chainId>:keeper:*            # 订单队列、事件游标
heartbeat:keeper:v0.3.2:<chainId>:*  # 心跳
```

**清理时只按自己的 chainId 前缀删，绝不 `FLUSHDB`：**

```bash
redis-cli --scan --pattern 'v0.3.2:<你的chainId>:keeper:*' | xargs -r redis-cli del
```

删之前先把旧值落盘到**工作区**（不要放 `/tmp`，scratchpad 会被清空）。

## 三、Do：临时插入版本验证的标准流程

### 1. 开工前先看现场

```bash
lsof -nP -iTCP:3010 -sTCP:LISTEN; lsof -nP -iTCP:3110 -sTCP:LISTEN
redis-cli --scan --pattern '*keeper*' | sed 's/:[^:]*$//' | sort -u
cd TestCode && npx tsx scripts/frontend-fork-patch.ts status
git status --porcelain | head -30          # 认清哪些是别人的 WIP
```

### 2. 建 fork：走标准命令，用临时槽位

```bash
cd TestCode
npm run env:vnet:create -- --env func-fork          # 独立 chainId 99914
npm run env:vnet:create -- --env func-fork --dry-run # 只看参数不写文件
```

对**已登记**的槽位会被护栏拦下（2026-09-05 新增），提示里会说明重建会连锁摧毁什么。确实要覆盖才加 `--force`。

> 临时槽位目前只登记在 catalog，共享登记文件（绑定表 / mock 资源 / playwright project）尚未接线，脚本会优雅停下而不是写半套。完整接线是待办。

### 3. 起服务：全部用独立端口与独立环境文件

```bash
# 前端（端口可覆盖，默认 3110）
FX100_DEV_PORT=3110 <launch.json: fx100-frontend-devfork>

# keeper（日志/pid 按 chainId 分层，不会误杀别人的进程）
cd TestCode/tools/keeper-runner
KEEPER_ENV_FILE=<你自己的 env> KEEPER_CHAIN_ID=99914 ./run.sh both
```

### 4. 前端 fork 补丁：指定作用的 worktree

```bash
cd TestCode
npx tsx scripts/frontend-fork-patch.ts status --frontend-root ../Github/fx100-apps@<你的分支>
npx tsx scripts/frontend-fork-patch.ts apply  --frontend-root ../Github/fx100-apps@<你的分支>
```

不传 `--frontend-root` 时作用于默认的 `../Github/fx100-apps@develop`——**那是共享 worktree，补丁是全局二值开关，不区分谁打的**。两条会话都要用前端时，各自派生自己的 worktree。

### 5. 跑用例：别污染看板

`artifacts/latest` 的合并 key 是 `id:project`，**不含 chainId / release / deploymentId**（`src/reporting/latest-snapshot.ts:11-13`）。临时验证若用 Playwright reporter 打同一个 project 名，会把别人的行逐条顶掉，还会盖上 release 标签伪装成准入材料。

- **临时验证优先用独立探针**（`artifacts/ui-smoke/` 下的 tsx 脚本），不经 reporter
- 必须跑 spec 时加 `--reporter=list`
- 结果只写自己版本的 `TestCase/E2E/versions/<release>/results.md`

## 四、Don't：绝对不能碰

### 文件

| 文件 | 后果 |
|---|---|
| `Docs/contract-releases/CURRENT.json` 的 `primary` / `environments.*` / `admissionScope` | 单一事实源，改了会连锁影响别人的目标基线判定与看板标签 |
| `TestCode/.env.local` | 三个环境的 RPC 都在里面 |
| `TestCode/config/tenderly-vnets.json` | VNet 在用记录 |
| `TestCode/config/environment-bindings.json` | 环境↔部署绑定 |
| `TestCode/config/mock-resources.json` | Mock Market 登记 |
| 别人的 `TestCase/E2E/versions/<别的版本>/results.md` | 无跨进程锁，last-writer-wins |
| `Github/` 下被测源码克隆的 HEAD | 见下 |

> 对单一事实源确有改动需求时：**当场单独提交，只带该路径**，并通知其他会话。

### 命令

| 命令 | 为什么 |
|---|---|
| `npm run env:vnet:create -- --env tx-fork`（不带 --force） | 已被护栏拦下；加 `--force` 会抹掉别人的环境与版本登记 |
| `git add -A` / `git commit -a` | 会夹带别人的 WIP |
| `git -C Github/fx100-apps@develop pull` | 共享 checkout，行号锚点会漂（见下） |
| `redis-cli FLUSHDB` | 清掉所有会话的 keeper 状态 |
| `./run.sh stop`（不指定 chainId） | 改造前会杀掉所有会话的 keeper；现已按 chainId 分层，但仍要确认作用域 |
| 看板 :4173 的写类按钮（环境配置 / Tenderly Forks / 参数设置 / 结果回填） | 单实例全局生效，同一时间只让一条会话操作 |

### 共享 checkout 的 pull

`Github/fx100-apps@develop` 是共享 worktree。2026-09-05 09:38 有人 `pull --ff-only` 把它从 `dfa36d0b` 推到 `1912f460`（57 文件 +7027/-1251，`apps/keeper` 下多个文件整体删除），而当天 01:36 写的 `TestCase/E2E/ContractCodeSummary/v0.3.2/FX100-Keeper代码公式.md` 行号锚点因此可能失效。

- 需要新代码 → 用 `git worktree` 派生 `Github/fx100-apps@<分支名>`，别动共享的
- 确实要 pull → 同步回写 `CURRENT.json` 的 `frontend.head` / `headAt`，并通知引用了行号的人

## 五、共享资源风险表

| 资源 | 严重度 | 干扰机制 | 现状 |
|---|---|---|---|
| 前端 fork 补丁三文件 | HIGH | 全局二值开关，一方 revert 另一方就踩空 | 已支持 `--frontend-root` 分 worktree |
| 端口 3010 | HIGH | UI spec 默认连 3010，会静默连到别人的前端而不报错 | 临时前端已挪到 3110 |
| chainId 复用 | HIGH | Redis 只靠 chainId 隔离；`run.sh` 的 chainId 闸只看 `eth_chainId`，分不出同号的两条链 | 已开 func-fork/99914 |
| `env:vnet:create` 连锁覆盖 | HIGH | 一条命令改写 5 处登记 | 已加 `--force` 护栏 |
| `artifacts/latest` 合并 | HIGH | key 不含 chainId，跨会话互顶 | **未修**，靠规程规避 |
| keeper pid/日志单槽 | HIGH | 看板「停止 Keeper」会误杀别人的进程 | 已按 chainId 分层 |
| `KEEPER_CHAIN_ID` 被 `.env` 覆盖 | HIGH | `set -a; source` 在命令行变量之后执行 → 「体检全绿、前缀写错链」的假绿灯 | 已修 |
| Redis 键 | MEDIUM | 同 chainId 即共用 | 靠铁律 1 |
| relay 队列键 | MEDIUM | 只按 chainId 分片，同号会互相消费对方的签名请求 | 靠铁律 1 |
| 同一 working tree | MEDIUM | WIP 混在一起 | 靠提交纪律 |
| `artifacts/parameter-cache/<env>/` | MEDIUM | 借用别人环境名 dump 会覆盖 | 用 `tools/config-dump/dump-config.mjs --out <独立目录>` |
| 看板 :4173 写类 API | MEDIUM | 单实例全局生效 | 同一时间一条会话操作 |
| Chainlink 凭证配额 | LOW | 两个 keeper 共用配额，表现为订单执行超时 | 同一时刻只允许一个 keeper 真发单 |

## 六、收尾还原清单

```bash
# 1. 停自己的服务（按自己的 chainId，别扫全局）
cd TestCode/tools/keeper-runner && KEEPER_CHAIN_ID=<你的> ./run.sh stop
# 停自己的前端与临时代理（先 lsof 确认 pid 归属再 kill）

# 2. 前端 fork 补丁恢复到你接手时的状态
cd TestCode && npx tsx scripts/frontend-fork-patch.ts status   # 先看，再决定 apply/revert

# 3. 清自己的 Redis 键（只按自己的 chainId 前缀）
redis-cli --scan --pattern 'v0.3.2:<你的chainId>:keeper:*' | xargs -r redis-cli del

# 4. 删自己建的 Tenderly environment（未登记的要带 --environment-id）

# 5. 撤掉 tracked 文件里的临时改动
git checkout -- .claude/launch.json     # 若你加过临时配置

# 6. 通知：如果动过共享文件或 pull 过共享 checkout
```

## 八、已知未解决

1. **`artifacts/latest` 的合并 key 不含 chainId/deploymentId** — 跨会话污染只能靠规程规避，根治要改 `src/reporting/latest-snapshot.ts` 的 resultKey。
2. **`func-fork` 只登记在 catalog** — 共享登记文件（`environment-bindings.json` / `mock-resources.json` / playwright project）尚未接线，临时槽位目前只能建 fork、跑不了完整用例链。
3. **前端 dev 端口在被测仓库里仍是硬编码** — `apps/fx-base-app/package.json` 的 `"dev": "next dev -p 3010"`。我们绕开的办法是 `yarn workspace fx-base-app exec next dev -p <port>`；建议向前端团队提改成 `next dev -p ${PORT:-3010}`。
4. **preview 启动器读不到工作区里的 env 文件**（沙箱 `Operation not permitted`），临时前端的 env 仍需放会话 scratchpad；工作区 `TestCode/tmp-session/` 留持久副本。
5. **`internal-dashboard` 端口硬编码 3011**，无 env 口。

## 一、目标（三句话）
1. **大额订单创建时就不收 WETH 执行费**，而不是「先收后退/先收后卡死」。
2. 小额订单（\< 阈值）维持现状：创建期必须预付执行费，否则 revert。
3. 与 Express Mode 配合，实现**用户全程不持有 ETH/WETH 即可开仓**，理想情况下大额开仓「零执行费」。
---
## 二、当前行为与问题（为什么要改）
### 2.1 现状：豁免发生在「执行期」，且不退款
`src/order/ExecuteOrderUtils.sol:70-95`：
```solidity
uint256 executionFee = params.order.executionFee();
uint256 minOrderSize = dataStore.getUint(FX100Keys.executionFeeSubsidizeKey(market.marketIndex));
uint256 estimatedOrderSizeUsd = params.order.sizeDelta();
if (!params.order.isSizeDeltaUsd()) {
    estimatedOrderSizeUsd = estimatedOrderSizeUsd * prices.indexTokenPrice.midPrice();
}
if (estimatedOrderSizeUsd >= minOrderSize) {
    executionFee = 0;           // 仅改局部变量
}
GasUtils.payExecutionFee(..., executionFee, ...);   // fee=0 → 早返回，什么都不做
```
问题链：
- **创建期** `OrderUtils.createOrder`（`src/order/OrderUtils.sol:98-157`）→ `GasUtils.validateExecutionFee`（`src/gas/GasUtils.sol:179-191`）**不看 size**，只要 `executionFee >= gasLimit * tx.gasprice`。所以无论多大的单，主网（gasprice\>0）都被强制预付 WETH。
- **执行期** 命中补贴把 `executionFee` 设 0 → `payExecutionFee(0)` 第一行 return → 用户预付的 WETH **既不付 keeper、也不退用户，永久卡死 OrderVault**（= **BUG-B03**）。
- 补贴分支里**没有任何 treasury→keeper 转账**（已核实），注释「subsidised by treasury」目前是空头支票。
### 2.2 衍生现象：市价单「免费」、TP/SL 收 ETH
测试网 `tx.gasprice≈0` 时 `minExecutionFee=0`，市价前端不加地板 → fee=0 → 免费；TP/SL 前端加 `0.00004 ETH` 地板 → 收费。**合约对两者完全对称**，差异纯属前端地板不一致（详见 E2E spec §5）。本改造从合约侧把「大单免费」做实，前端两条路径即可统一对齐。

## 三、核心设计：把 size 豁免前移到 `createOrder`
### 3.1 双阈值：USD 阈值 + Token-Size 阈值（创建期均无需 oracle）
**核心思路（2026-06-14 用户定稿）**：token 模式也要在创建期豁免、与 USD 模式一致。问题是创建期没有 oracle 价格、token-size 换不成 USD。解法：**为每个市场配置两个同口径阈值**，按订单 mode 选用对应阈值，两者都用「原生单位直接比较」，**都不需要价格**。
Key │ 单位 │ 适用 │ 现状
`EXECUTION_FEE_SUBSIDIZE`（已有） │ USD 1e30 │ `isSizeDeltaUsd = true` │ 保留不动
`EXECUTION_FEE_SUBSIDIZE_SIZE`（**新增**） │ index token 原生单位（如 ETH=1e18） │ `isSizeDeltaUsd = false` │ 新增 per-market key
> 不要重命名已有 key（会改 keccak 哈希、破坏已部署配置）；新增独立 key 即可。新 key 默认 `MAX`（关闭）。
```solidity
/// @return subsidized 该订单是否在创建期即豁免执行费（两种 mode 均可判定，均无需 oracle）
function isExecutionFeeSubsidizedAtCreation(
    DataStore dataStore,
    uint256 marketIndex,
    uint256 sizeDelta,
    bool isSizeDeltaUsd
) internal view returns (bool) {
    if (isSizeDeltaUsd) {
        uint256 usdThreshold = dataStore.getUint(FX100Keys.executionFeeSubsidizeKey(marketIndex));
        if (usdThreshold == type(uint256).max) return false;     // 关闭态短路
        return sizeDelta >= usdThreshold;                        // sizeDelta 已是 USD
    } else {
        uint256 sizeThreshold = dataStore.getUint(FX100Keys.executionFeeSubsidizeSizeKey(marketIndex));
        if (sizeThreshold == type(uint256).max) return false;    // 关闭态短路
        return sizeDelta >= sizeThreshold;                       // sizeDelta 是 token 单位，直接比 token 阈值
    }
}
```
**配置一致性（治理需保证）**：`sizeThreshold ≈ usdThreshold / 参考价`，使「token 模式」与「等值 USD 模式」豁免门槛一致。否则用户可挑门槛更低的 mode 蹭免费执行（标的只是免 gas、风险低，但应避免）；价格大幅漂移时治理需同步更新 token 阈值，或接受粗粒度漂移（这是一个门槛 gate，非精确账目）。
### 3.2 `createOrder` 改动（`src/order/OrderUtils.sol`）
在 `recordTransferIn(WNT)` 之后、`validateAndCapExecutionFee` 之前插入分支：
```solidity
uint256 wntAmount = orderVault.recordTransferIn(Addresses.WNT);

bool subsidized = isExecutionFeeSubsidizedAtCreation(
    dataStore, params.numbers.marketIndex, params.numbers.sizeDelta, params.isSizeDeltaUsd
);

if (subsidized) {
    order.setExecutionFee(0);
    // 用户即使误传了 WETH，也原路退回，避免再次产生卡死
    if (wntAmount > 0) {
        orderVault.transferOut(Addresses.WNT, order.cancellationReceiver(), wntAmount);
    }
    // 跳过 validateAndCapExecutionFee（不要求最低费）
} else {
    if (wntAmount < params.numbers.executionFee) revert InsufficientWntAmountForExecutionFee(...);
    params.numbers.executionFee = wntAmount;
    (executionFee, executionFeeDiff) = GasUtils.validateAndCapExecutionFee(...);
    order.setExecutionFee(executionFee);
    if (executionFeeDiff != 0) GasUtils.transferExcessiveExecutionFee(...);
}
```
### 3.3 `ExecuteOrderUtils` 改动：**删除**执行期 size 判定块
因为两种 mode 现在都在创建期判定，执行期那段「size 判定 + 归零」（`src/order/ExecuteOrderUtils.sol:70-95`）**整段删除**，直接用 `order.executionFee()` 调 `payExecutionFee`：
```solidity
GasUtils.payExecutionFee(..., params.order.executionFee(), ...);   // 豁免单此值本就是 0
```
效果：
- USD / token 模式：创建期就 fee=0，执行期 `order.executionFee()` 为 0，`payExecutionFee(0)` no-op，无残留。
- 非豁免单：`order.executionFee()` 为创建期收取的正常费，照常付 keeper + 退多余。
- **BUG-B03 被彻底消除**：不存在「执行期临时归零但有预付款残留」的场景了，无需方案 B 兜底。

## 四、🔴 关键约束：keeper 补偿（必须想清楚再上）
`executionFee = 0` 意味着**执行订单的 keeper 在链上拿不到任何补偿**。这分两条路：
路径 │ 谁付订单执行 gas │ 结论
直连（用户自己发 createOrder + 公共 keeper 执行） │ 无人补偿公共 keeper │ **公共 keeper 没动力执行 fee=0 单 → 大额订单可能挂着不成交**
Express/Relay（用户签名 + fx100 自建 keeper 执行） │ fx100 自建 keeper 自吃 gas │ ✅ 可行，与 \[\[2026-06-10-express-mode-design\]\] 一致
**两个可选方案，二选一或并存：**
- **A（推荐，配合 Express）**：fx100 承诺为豁免单运营自建执行 keeper，gas 成本由协议（交易手续费）吸收。简单、零额外合约逻辑，但**必须确保自建 keeper 覆盖豁免单的执行**，否则订单悬挂。
- **B（更稳健，独立于谁运营 keeper）**：在执行期为豁免单实现真实的 `treasury → keeper` 转账（按 `adjustGasUsage * tx.gasprice` 计算），使第三方公共 keeper 也愿意执行。工作量更大，需要一个 treasury 资金源 + 防滥用上限。
**本规范默认走 A**（与 Express Mode 路线一致）。若未来要开放第三方 keeper，再上 B。

## 五、配置建议（双阈值 + 最低仓位）
参数 │ 单位 │ 含义 │ 建议
`EXECUTION_FEE_SUBSIDIZE`（per-market） │ USD 1e30 │ USD 模式单：≥ 此 size 创建期免执行费 │ 见下
`EXECUTION_FEE_SUBSIDIZE_SIZE`（per-market，**新增**） │ index token 原生单位 │ token 模式单：≥ 此 size 创建期免执行费 │ 与上面**等值**：`= USD阈值 / 参考价`
`MIN_POSITION_SIZE_USD`（全局，当前 10 USD） │ USD 1e30 │ \< 此 size 直接 revert `MinPositionSize` │ 维持
- **「最小开仓金额 = 最小 gas 所需 size → 完全免费开仓」**（用户原话）：把每市场 `EXECUTION_FEE_SUBSIDIZE` 设为 `MIN_POSITION_SIZE_USD`（10 USD），并把 `EXECUTION_FEE_SUBSIDIZE_SIZE` 设为等值 token 数。此时所有合法单都 ≥ 阈值 → 全部豁免。**代价：协议承担 100% 开仓执行 gas**（靠手续费补回），直连路径执行费机制等于全关、完全依赖自建 keeper（见 §四）。商业决策，技术成立。
- 🔴 **部署硬性要求（升级版）**：每市场配置 JSON **必须同时显式写 \`executionFeeSubsidize\` 与 \`executionFeeSubsidizeSize\`**，且保持等值。两者默认 `MAX`（关闭）。`configureMarket.ts` 对两者的缺省回退都要改成缺失即 `throw`（当前 `executionFeeSubsidize` 回退 `"0"` 是 footgun）。

## 七、边界与不变量（实施时必须保持）
1. 非豁免单（size \< 对应阈值 / 或阈值=MAX）行为**完全不变**：创建期要求足额 WETH，不足 revert `InsufficientExecutionFee`。
2. 豁免单创建期 `order.executionFee()` 必须为 0，且 OrderVault 不因该单残留任何 WNT。
3. 创建期豁免判定**两种 mode 都不依赖 oracle**：USD 模式比 USD 阈值，token 模式比 token 阈值。
4. Liquidation/ADL 单 `executionFee` 恒为 0，行为不变。
5. 取消订单（`OrderUtils.cancelOrder`）退款逻辑对豁免单（fee=0）应 no-op，不报错。
6. 执行期不再做任何 size 判定（已删除）；`payExecutionFee` 始终用 `order.executionFee()`。

## 八之二、Express 模式的执行费币种问题（真实症结：relay 无法 wrap 原生 ETH）
### 机制对比（已核实）
- **直连模式**：`BaseRouter.sendWnt(receiver, amount) external payable`（`src/router/BaseRouter.sol:33`）把用户 `msg.value` 的原生 ETH wrap 成 WNT 投入 OrderVault；ExchangeRouter 是 `PayableMulticall`，前端一次 multicall `[sendWnt(orderVault, execFee), createOrder]` 带 `msg.value`。**用户自己的 tx 携带原生 ETH，链上 wrap 成 WETH**。
- **relay 模式**：relay router **无 payable / 无 msg.value 入口**，tx 由 relayer 发出，用户没有原生币流入。只能用 `pluginTransfer`（ERC20 transferFrom）拉钱，故 `BaseRelayRouter.sol:96` 拉的是 **WNT(WETH) ERC20**，要求用户**预先持有 WETH 并 approve**。
### 真实症结（非退款）
执行期的 charge/refund 是正常逻辑，不是问题。唯一症结：**relay 拿不到原生 ETH 也就无法 wrap**，所以**非豁免的小额单在 express 下强制用户持有 WETH(ERC20)**——这才是打破「零 ETH/WETH」的点，且只影响小单。
### 解法（决定：**选 B —— relayer 垫付 WETH，合约改动最小**，2026-06-15 用户定）
- **B（选定）**：**relayer 垫付 WETH** 执行费（relayer 持 WETH float，从自身余额转入 OrderVault），折进 USDC relay 费向用户报销。执行费维持非零真实值，走正常 charge/refund 路径。
- A（未选）：express 订单一律免执行费（execFee=0），执行由 fx100 自建 keeper 承担、聚合 USDC 补回。需 createOrder 资金来源标记 + 触及核心校验路径，且执行 keeper 白干（撞 §四）。
- **不要把执行费改收 USDC 进 OrderVault**：`payExecutionFee` 用原生币付 keeper，收 USDC 就得链上 USDC→ETH 兑换（引 DEX/oracle 依赖、复杂、有风险）。无谓。
### 方案 B 实现要点（两档，按是否接受退款落到用户分）
**改动核心：执行费来源 用户 → relayer**
1. `BaseRelayRouter._createOrder`：把 `_sendTokens(account, Addresses.WNT, orderVault, executionFee)` 的来源从**用户**改成 **relayer**（relayer 持 WETH float 直接 transfer 进 OrderVault，或 `pluginTransfer(msg.sender, …)`，relayer 预先 approve）。
2. `_payRelayFee` / 费用公式：把执行费换算成 USDC 加进 relay 费的 `feeAmount`，用户用 USDC 报销 relayer 垫付的 WETH。前端 `maxFeeAmount` 估算需同步含这部分。
**退款去向：定 B1（2026-06-15 用户定）—— 退款直接给用户、合约保持不变、与直连方式一致**。执行期多付部分退款走 `order.receiver()`（`src/order/ExecuteOrderUtils.sol:94`）= 用户、原生 ETH，与直连完全相同的 charge/refund 逻辑，**\`OrderUtils\`/\`ExecuteOrderUtils\`/\`Order\`/\`GasUtils\` 一行不动**。退款金额仅为 gas 估算误差（user-favorable，非安全问题）；用户会攒一点 ETH 灰尘，可接受。
（备选 B2「严格零 ETH」需给 Order 加退款接收人字段 + 改 `ExecuteOrderUtils:94`，触核心合约，**不采用**。）
**⚠️ 不要新增 \`OrderType\` 枚举值**：B 无需新订单类型——执行费来源是 relay router 内部的事，与订单类型正交。新增 `OrderType` 会污染「订单做什么」维度（驱动 `createOrderFeatureDisabledKey`/secondaryOrderType 等），改动面巨大。
### 方案 B 风控与链下接口（2026-06-15 用户要求）
1. **🔴 合约：最大执行费上限（防 relayer 被迫垫付过多 WETH）**。机制**已存在**：`validateAndCapExecutionFee` + `MAX_EXECUTION_FEE_MULTIPLIER_FACTOR`（`FX100Keys.sol:381`）。但 relay 当前**主动放弃**——`BaseRelayRouter.sol:106` 调 `createOrder(account, params, false)`（`shouldCapMaxExecutionFee=false`）。
- **最小改法**：relay 路径改传 `true`，复用既有 multiplier 上限（相对 basefee）。
- **可选硬上限**：新增绝对值 key（如 `MAX_EXECUTION_FEE` per-market），给 relay 一个与 basefee 无关的天花板。
- 建议 relay 路径**超限直接 revert**（而非静默 cap 把超额送 HOLDING），让 relayer 永不超额垫付。
1. **链下：relay 提供报价 API**。后端按当前 gasprice 计算所需 WETH 执行费，**折算成 USDC**，加上 relay 自身 gas 费，返回「用户应付 USDC 总额」给前端；前端据此设签名里的 `maxFeeAmount`（留 slippage 余量）。WETH→USDC 用 oracle 价（`nativeTokenPrice.max / feeTokenPrice.min`，与链上 `_payRelayFee` 同口径）。
2. **relay 费理论不应为 0，但允许 0 以做免费服务**。已支持：`isRelayFeeExcludedKey(msg.sender)`（`BaseRelayRouter.sol:200`）对白名单 keeper 跳过 USDC 收费——**无需改合约**，治理配置即可。
- ⚠️ 注意：relay 费=0 **且** relayer 垫付 WETH 时，relayer/协议**全包**（relay gas + 执行费），是完全免费模式，成本由协议吸收。正常运营 relay 费应 \> 0 覆盖成本。
### 方案 B 的额外好处：绕开 §四 keeper 补偿难题
B 下执行费是真实非零（relayer 垫付）→ 执行 keeper 走正常路径**能从订单 executionFee 拿到补偿**。所以 **express 订单完全不撞 §四 的「fee=0 keeper 白干」问题**。§四 的 keeper 补偿讨论只剩「直连大单按 §3 size 豁免（execFee=0）」那条仍需自建 keeper / 方案 B(§四)。
> 注：选 B 只是 **express 的执行费方案**；**§三（直连大单创建期 size 豁免 + 修 B03）独立保留**，仍建议实施，服务直连路径。

## 九、验收测试（已在 E2E spec 设计，实施后激活）

## 十、实现落地情况（v0.3.0，2026-07-16 核对收官）
对应 17 个变更点中的 C-9\~C-14，src 侧 5/6 落地（脚本项未做），测试背书详见 `2026-07-08-v030-implementation-verification.md`（三）与 `2026-07-13-v030-code-walkthrough.md`（C-9\~C-14）。与本文口径的主要出入：
1. **§3.2 退款收款人与本文不同**：创建期误传 WNT 的退款实际转给 `order.receiver()`，而非本文写的 `cancellationReceiver`——两者通常是同一用户，已确认低风险，测试按实际行为（`receiver`）断言。
2. **超出本文范围的增强——\`updateOrder\` 豁免重判**（`OrderHandler.sol`）：本文只规定创建期判定，工程师额外在改单路径加了重判 + 双向状态迁移：改大过线（非豁免→豁免）已付执行费全额退回；改小掉线（豁免→非豁免）要求随附足额 WNT，否则 `revert InsufficientExecutionFee`。这堵住了"改单绕过豁免线"的口子，前端"改小"操作需要按新 size 预判豁免状态并随附执行费。
3. **§八之二 relay 执行费上限（P0-7）实现口径与本文建议不同**：本文建议 relay 路径传 `shouldCapMaxExecutionFee=true`（复用 `MAX_EXECUTION_FEE_MULTIPLIER_FACTOR`）或加 per-market 绝对值 key；实际实现是全局键 `MAX_RELAY_SWAP_WNT_CAP`，对 relayer 单笔垫付的 `nativeFee`（gas 报酬 + 垫付执行费合计）设硬上限，超限直接 `revert MaxRelaySwapWntCapExceeded`，安全性等价但极性不同——**\`cap = 0\` 是"不设限"**（与执行费豁免键"MAX = 关闭"极性相反，是运维记忆点），已在部署脚本层加 throw 兜底强制显式配置。
4. **Express 折算价源超出本文预期改为 secondary oracle**（`ee15494`，本文写作时未预见）：`RelayParams` 删除了 `oracleParams` 字段且从签名 digest 编码中移除，relay 交易不再携带任何价格；WNT/feeToken 折算改用链上 `oracle.getSecondaryPrice`（Chainlink feed 优先，无 feed 回退持久缓存）。这是一个 breaking change——旧签名/前端/relayer/报价 API 全部需要同步切换，不可与旧版本混跑。
5. **§五/§八 P0-5 部署脚本项未完成**：`configureMarket.ts` 尚未把两个执行费豁免阈值（`executionFeeSubsidize`/`executionFeeSubsidizeSize`）的缺省行为改成"缺失即 throw"；`executionFeeSubsidizeSize` 在部署脚本层目前零支持。**合约层两键缺省值均为 0**，意味着"缺省 = 全场免执行费"（USD 模式与 token 模式各自独立生效）——按现状部署会处于全免状态，已用测试固化（`EFS-B03`/`EFS-B06`），必须列入上线 checklist 强制处理，不能仅靠合约默认值。
6. §四 keeper 补偿仍走本文默认的方案 A（自建 keeper 覆盖豁免单执行），尚未有链上 `treasury→keeper` 转账（方案 B）落地；本条依赖运维承诺而非合约保证。
详细的逐条实现讲解、风险点评估与手动执行测试命令，见 `docs/superpowers/specs/2026-07-13-v030-code-walkthrough.md` §C-9\~C-14 与 `docs/superpowers/specs/2026-07-08-v030-implementation-verification.md` 三节。
